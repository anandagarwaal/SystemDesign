Design a News Aggregator

Ingest the world's articles, dedup the same story across outlets, and serve a fresh ranked feed in under 200 ms.

Why this lesson, for your mission: A news aggregator looks easy — "just show articles" — which is exactly the trap. The L6/L7 signal is recognizing this is two systems wearing one hat: a write-heavy ingestion pipeline and a read-heavy serving path. The candidate who keeps them separate, buffers ingestion with a queue, and reads from a cache/index sounds senior. The one who content-hashes to dedup the same story across 50 outlets sounds staff.

Functional Requirements

Anchor on what the user actually does. The reference breakdown lists three core flows.[1]

#Users should be able to…
1View an aggregated feed of articles drawn from thousands of publishers, optionally filtered by category (Tech, Sports, World…).
2Scroll the feed "infinitely" — a personalized, recency-and-popularity-ranked stream.
3Click an article to read it (open the full piece on the publisher's page).

Out of scope (say so out loud): authoring content, comments, social graph, push notifications. Naming these buys you credibility and time.

The "-ilities" decide the architecture. State each as a target, not an adjective.

Capacity Estimation

Only compute numbers that change a decision. Round hard.

  • Sources: ~100K RSS/crawl sources, polled every ~20 min ⇒ ~83 polls/sec — modest, but spiky.
  • Ingest volume: ~1–2M articles/day ⇒ ~15–25 writes/sec average, with breaking-news bursts many times that. Implication: the write path needs a buffer (queue), not a synchronous DB write.
  • Read QPS: say 100M DAU × ~10 feed loads/day ≈ 1B reads/day ⇒ ~12K read QPS, peaking ~30K+. Implication: read path is 1000× the write path — this is a read-heavy system; optimize reads ruthlessly.
  • Storage: ~2M articles/day × ~10 KB metadata ≈ 20 GB/day ≈ 7 TB/yr. Trivial for the store; the hot recent window (last few days) is what must be fast.
The one number that matters: reads dominate writes by ~1000×. That single ratio justifies splitting ingestion from serving and putting a cache in front of reads.

Data Flow

This is a pipeline system, so trace one article from source to screen before drawing boxes. Each stage is an independent stateless worker reading from and writing back to the queue.

StageWhat happens
1. Poll / crawlScheduler dispatches due sources to fetch workers; RSS via etag/If-Modified-Since, others crawled. Raw items pushed to the queue.
2. DedupCompute a content_hash (normalized title + body). Drop exact repeats; near-duplicates get clustered (Deep Dive 1).
3. Parse / extractPull title, summary, lead image, publish time, canonical URL from messy HTML/feeds.
4. Categorize / rankClassify into a category; compute a base score from recency + source authority + early popularity.
5. Store / indexWrite enriched article to the article store, the search index, and the feed cache.
6. ServeFeed service reads precomputed, cached, ranked pages — no heavy compute on the request path.

The seam between stage 5 (pipeline writes) and stage 6 (serving reads) is the system's spine: the pipeline can fall over without taking reads down with it.

Map each requirement onto components. Note how the queue cleanly cleaves the write path from the read path.

Request flow. GET /v1/feed hits the feed service → reads the precomputed page for that category from the cache by cursor → returns items + next_cursor. A cache miss falls back to a recency-sorted query against Elasticsearch, then backfills the cache. GET /v1/articles/{id} reads the article store (cacheable, immutable once published).

★ Staff-level signal The move that separates senior from staff is naming the two independent failure domains and designing the seam between them. Ingestion is write-heavy, bursty, and depends on flaky upstreams — so you buffer it behind a queue and let workers scale and retry. Serving is read-heavy and latency-bound — so you read from a cache/index that's already been populated. If the entire ingestion pipeline is down, reads keep serving slightly stale content. State that out loud — it's the availability-over-consistency NFR made concrete.

Deep Dives

This is where 60% of an L6/L7 interview lives. Each dive states the problem, the options, and a justified pick.

1. Ingestion at scale — polling and deduping the same story

Scheduling. Naively polling 100K sources on a fixed timer wastes requests on dead feeds and lags hot ones. Use an adaptive cadence: shorten poll_interval for sources that publish often, lengthen it for stale ones; honor etag/If-Modified-Since so unchanged feeds cost a cheap 304. A coordinator pushes due jobs into the queue; the worker pool autoscales on queue depth, decoupling "how often we check" from "how fast we process."

Dedup is the hard part. One event ("election result") is published by dozens of outlets within minutes. Three layers:

LayerCatchesMechanism
ExactSame article re-fetched, syndicated verbatimContent hash of normalized title+body; seen-set lookup → drop.
Near-dupReworded versions of one wire storyMinHash / SimHash fingerprint; group by Hamming distance.
Story clusterIndependent coverage of one eventEmbedding similarity within a time window → assign cluster_id.

The feed shows one canonical article per cluster ("…and 40 more"), so a breaking story doesn't flood the feed with 40 near-identical cards. Content hashing for exact dups is cheap and high-value; mention embeddings/clustering as the next tier without over-engineering it.

2. Ranking and personalization — precompute vs. compute-at-read

The feed score blends recency (time-decay), popularity (early clicks/shares), source authority, and category affinity to the user. The question is where the work happens.

ApproachProCon
Compute at readAlways fresh, fully personalizedHeavy CPU on every request — blows the 200 ms budget at 30K QPS.
Precompute globalRead is a cheap cache lookupSame feed for everyone — no personalization.
Hybrid (pick)Precompute ranked category pages; re-rank a small top-N per user at readA little read-time cost, bounded and cacheable

The pipeline maintains per-category ranked lists in the cache (the expensive global scoring done once at ingest). At read time the feed service takes the top slice and applies a lightweight personalization re-rank by category affinity. Heavy global ranking is amortized across all readers; personalization stays cheap and per-request.

3. Serving the feed fast — caching and stable pagination

Caching. Per-category ranked pages live in Redis; the feed service rarely touches the database. A CDN/edge cache absorbs the long read tail for anonymous and category feeds.

Pagination must be cursor-based, not offset. New articles arrive constantly; with OFFSET 40 the second page would skip or repeat items as the list shifts under you. The cursor encodes (score, article_id) of the last item, so "give me what comes after this" is stable even as the head of the feed changes — the user keeps scrolling a consistent stream and the query stays O(page), not O(offset).

4. Freshness vs. cost — and breaking-news spikes

Freshness costs money: faster polling = more fetch/compute, deeper personalization = more read-time work. Tune cadence by source tier — poll major wires every minute, long-tail blogs hourly — so spend tracks value.

Breaking news is the stress test: one event drives a fetch surge (every outlet publishes) and a read surge (everyone opens the app). The queue absorbs the write burst — workers scale on depth, lag grows gracefully instead of dropping data. On reads, the cache plus CDN soak the spike since everyone wants the same few hot stories. Graceful degradation: if the pipeline lags, serve slightly stale cached feeds rather than erroring — exactly the availability-over-consistency tradeoff, made operational.

Check yourself — retrieval practice

Answer from memory before scrolling back up.

1. Why put a durable queue between the pollers and the processing workers?

The queue absorbs spikes and lets the two failure domains scale and fail independently.

2. The same story is published by 40 outlets. The cheapest first defense is:

A content hash catches exact/syndicated dups cheaply; clustering handles the near-dups next.

3. Why is offset pagination wrong for a constantly-updating feed?

A cursor on (score, id) stays stable as the head of the feed changes; offset does not.

4. To hit p99 feed latency under 200 ms at 30K QPS, you should:

Amortize heavy global ranking at ingest; keep only cheap per-user re-ranking on the read path.
