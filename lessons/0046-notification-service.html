Design a Notification Service

Deliver billions of notifications a day across push, SMS, email, and in-app — fast for the urgent, never twice, and only to people who still want them.

Why this lesson, for your mission: A notification service is a pipeline problem dressed up as a CRUD problem. Seniors describe "API writes a row, worker sends it." Staff candidates name the three forces that actually shape it — fan-out (one event, many recipients and channels), flaky third parties you don't control (APNs/FCM/Twilio/SES), and at-least-once delivery that demands idempotency so retries don't double-send. Get those three right and the rest is plumbing.

Functional Requirements

Scope to what a notification platform must do; push everything else out loud.

The user should be able to…Detail
Send a notificationA client service calls the API with a recipient, content, and type; the system delivers it.[1]
Reach multiple channelsPush (APNs/FCM), SMS, email, and in-app — chosen per notification and per user.[1]
Respect user preferencesPer-channel and per-category opt-out, plus quiet hours; never deliver what a user muted.[1]
Use templatesSenders pass a templateId + variables, not raw rendered text, so content is consistent and localizable.

Out of scope (say this aloud): the business logic that decides when to notify lives in the calling service; we are the delivery substrate. Also out: rich campaign authoring UIs and analytics dashboards — we emit delivery events, a separate system aggregates them.

Non-Functional Requirements

PropertyTarget / priority
Throughput / scalabilityAbsorb spiky fan-out — a single marketing blast or a viral event enqueues millions of messages in seconds; scale workers on queue depth, not request rate.
ReliabilityAt-least-once handoff to the provider: a crash mid-send must retry, never silently drop. Exactly-once effect is approximated with idempotency.
LatencyTiered. Transactional (OTP, "your code is 1234") targets seconds end-to-end; marketing is throughput-bound and may lag minutes.
AvailabilityThe ingestion API stays up even when a downstream provider is degraded — buffer in a queue, degrade per-channel, don't fail the whole send.

The central tension is latency vs. throughput. A login OTP and a "50% off" blast cannot share one FIFO queue, or the blast starves the OTP. The resolution — priority lanes — is developed in the deep dives.

Capacity Estimation

Estimate only the numbers that change the design. These are back-of-envelope figures, derived here, not quoted from a source.

QuantityEstimateDesign implication
Send rate500M users × ~10 notifs/day ≈ 5B/day ≈ ~58k/sec average, ~300k/sec at peakTrivial for a queue, but synchronous per-message calls to providers won't keep up — you need pooled, async workers and connection reuse.
Fan-out amplification1 logical event → up to millions of recipients × up to 4 channelsIngestion must be cheap and bursty; the expansion belongs behind the queue, not in the request path.
Status records~5B sends/day × ~200 B ≈ ~1 TB/day of delivery eventsWrite-heavy, short-lived: a wide-column store (Cassandra) with TTL beats a relational table you'd never query individually.

The math that matters: 300k/sec is nothing for Kafka but lethal if each message opens a fresh TLS connection to APNs. The bottleneck is the provider edge, not the queue — so the design optimizes pooling, batching, and backpressure there, and keeps storage cheap and disposable.

Core Entities & API

Notification — one logical message: recipient, type/category, template + variables, requested channels. Device / Contact — a user's registered push tokens, phone numbers, and email addresses. Preference — per-user, per-category, per-channel opt-in state plus quiet-hours window. DeliveryAttempt — one try on one channel (status, provider, timestamps) for tracking.

EndpointPurpose
POST /v1/notificationsSend one: { userId, category, templateId, vars, channels, priority, dedupeKey }. Returns a notificationId. Async — 202 Accepted.
POST /v1/notifications:batchBulk enqueue for campaigns; the body is a recipient list or a segment reference, expanded server-side.
GET /v1/notifications/{id}Fetch delivery status per channel (queued / sent / delivered / failed).
PUT /v1/preferencesUpdate a user's opt-outs and quiet hours.
POST /v1/devicesRegister/refresh a device push token (APNs/FCM) for the caller.

The sending service is identified by its API credential; the recipient userId is in the body, but the caller's identity (for auth and rate-limit accounting) comes from the token, never the payload.

Data Flow

This is a data-processing pipeline, so trace one notification end to end:

#StageWhat happens
1IngestAPI validates the request, checks the dedupeKey, writes a Notification row, and returns 202 immediately.
2Enrich & filterA processor resolves the user's devices/contacts, applies preferences and quiet hours, and renders the template — dropping muted channels here.
3RouteThe surviving per-channel messages are fanned out onto a queue per channel (push / SMS / email / in-app), tagged with priority.
4DeliverChannel worker pools pull, batch, and hand off to the provider (APNs/FCM/Twilio/SES), applying retries + backoff on transient errors.
5TrackWorkers and provider webhooks/feedback write DeliveryAttempt status; failures past max-attempts go to a DLQ.

The decisive move is putting enrichment and filtering before the queues: by the time a message hits a channel queue, it is already addressed, rendered, allowed, and prioritized — workers just deliver.

High-Level Design

Six components, split cleanly between accept & decide and deliver:

ComponentRole
Ingestion APIAuth, validation, idempotency check, writes the Notification, returns 202. Stays fast and always-on.
Processing serviceResolves recipients, applies preferences/quiet hours, renders templates, routes to per-channel queues.
Channel queuesOne durable queue per channel (Kafka/SQS), each with priority lanes. Buffers bursts; decouples send rate from provider rate.
Channel workersPer-channel pools that batch and call APNs/FCM/Twilio/SES; handle retries, backoff, and rate limits.
StoresNotification + preference DB (relational), device/token store, and a status store (Cassandra, TTL'd) for DeliveryAttempts.
DLQHolds messages that exhausted retries for inspection and replay, so one bad provider doesn't loop forever.

Flow: POST → API enqueues to an intake topic → processing expands and filters → per-channel queues → workers deliver to providers → status written, failures to DLQ. Each channel scales independently; a Twilio outage backs up only the SMS queue while push keeps flowing. This mirrors the queue-decoupling pattern from Lesson 07 (Messaging & Async).

★ Staff-level signal The interview turns on three sentences: filter before you fan out (preferences/quiet-hours applied pre-queue, so workers never deliver muted messages), a queue per channel with priority lanes (so a marketing blast can't starve an OTP and a dead provider isolates to one channel), and at-least-once + idempotency (retries are safe because a dedupe key makes a re-send a no-op). Everything else is detail.

Deep Dives

1 · The fan-out pipeline — a queue per channel + worker pools

The naive design sends synchronously inside the request: resolve devices, call APNs, then SMS, then email, then return. It collapses the instant one provider is slow and can't absorb a million-recipient blast. The fix is to make ingestion a cheap write and do all expansion asynchronously behind durable queues.

ChoiceOptionTradeoff
Queue topologyOne shared queue for all channelsSimple, but a slow channel (SMS) head-of-lines fast ones (push), and you can't scale or fail channels independently.
Queue topologyQueue per channelEach channel scales and fails on its own; matches each provider's distinct rate limits and retry profile. Slightly more infra.
Fan-out placementExpand recipients in the APIBlocks the caller and risks a giant synchronous transaction for big segments.
Fan-out placementExpand behind the queueAPI stays O(1); a processing tier streams the segment into per-channel messages, checkpointing progress.
Pick & justify: A queue per channel, fed by a processing tier that does fan-out after the 202. Channels have genuinely different physics — APNs/FCM take batched HTTP/2 calls, SMS is rate-limited and pricey, email tolerates seconds of delay — so isolating them lets each worker pool autoscale on its own queue depth and apply its own retry policy. This is the same fan-out-on-write reasoning as Lesson 16 (News Feed): pre-compute and buffer the heavy expansion instead of doing it in the read/request path.

2 · Third-party gateways & provider failures — retries, backoff, DLQ

You don't own delivery; APNs, FCM, Twilio, and SES do. They rate-limit you, return transient 5xx/429s, time out, and reject bad tokens. Push providers are explicitly best-effort and store-and-forward — if a device is offline, APNs holds (and may coalesce) a notification and delivers later, with no hard guarantee.[2] FCM lets you set message priority and a time-to-live so non-urgent messages don't deliver stale.[3]

Resilience pattern at the provider edge:
  • Pooled, reused connections — APNs uses a long-lived HTTP/2 connection with token auth; keep it open and multiplex, never one connection per message.[2]
  • Classify the error — transient (429/5xx/timeout) → retry; permanent (invalid/expired token) → don't retry, prune the device instead.
  • Retry with exponential backoff + jitter — so a struggling provider isn't hammered (see Lesson 22 for the token-bucket math you respect here).
  • Circuit breaker per provider — trip on sustained failures, shed load, and let the queue absorb the backlog instead of melting down.
  • DLQ after N attempts — exhausted messages move to a dead-letter queue for inspection/replay, never an infinite loop.

An adapter per provider normalizes these quirks behind one internal interface, so the worker logic is provider-agnostic and a new SMS vendor is a new adapter, not a rewrite.

3 · Idempotency & dedup — never double-send

At-least-once means duplicates are inevitable: a worker can deliver to APNs, then crash before ACKing the queue, so the message reappears and sends again. Two senders firing the same OTP twice is the same hazard at the front door. Both are solved with idempotency keyed on a stable token.

LayerMechanism
IngestionCaller supplies a dedupeKey (e.g. orderId + "shipped"); the API records it and rejects/no-ops a repeat within a window.
ProcessingA processed-message marker (key = notificationId + channel) makes re-delivery of a queue message a no-op.
ProviderPass a provider-side idempotency/collapse identifier where supported so the provider itself coalesces duplicates.
Pick & justify: Enforce idempotency at ingestion and at the worker, backed by a fast store (Redis with TTL) keyed on a stable id. True exactly-once across a network is impossible; exactly-once effect via a dedupe key is what you actually ship — the same at-least-once + idempotency reasoning as the job scheduler. Pair it with delivery tracking: each DeliveryAttempt row (queued → sent → delivered → failed) is updated by workers and by provider feedback (APNs feedback / FCM responses, SES/Twilio webhooks), giving GET /notifications/{id} its answer and feeding token-pruning of dead devices.

4 · Preferences, quiet hours, rate limiting & prioritization

Sending correctly is half the job; sending appropriately is the other half — and it's where staff judgement shows. Filtering must happen before the channel queues so workers never even see a muted message.

ConcernApproachNote
Preferences / opt-outPer-user, per-category, per-channel flags checked in the processing tier.Cache hot preferences; a muted channel is dropped pre-queue, not at delivery.
Quiet hoursHold non-urgent messages until the user's local window opens.Transactional messages (OTP, security) bypass quiet hours by category.
Rate limitingPer-user caps ("max 5 marketing/day") + per-provider throughput limits.Token bucket per user and per provider — see Lesson 22.
PrioritizationSeparate priority lanes/queues: transactional > marketing.Workers drain high-priority first so an OTP never waits behind a blast.

State the breadth/depth ratio aloud: you went deep on fan-out, provider resilience, idempotency, and policy — the parts that fail or anger users in production — and kept auth, storage schemas, and template rendering shallow because that's not where this design breaks.

Check yourself — retrieval practice

Answer from memory before scrolling back up.

1. Why use a separate queue per channel instead of one shared queue?

Per-channel queues let each scale, fail, and rate-limit independently; SMS can't stall push.

2. At-least-once delivery can send twice. What makes a resend safe?

Idempotency keyed on a stable id (e.g. notificationId+channel) gives exactly-once effect.

3. Where should preferences and quiet hours be applied?

Filter pre-queue so workers never deliver muted messages; it's cheaper and avoids leaks.

4. A provider returns sustained 5xx errors. Best handling?

Exponential backoff + circuit breaker protects the provider; a DLQ stops infinite loops.
