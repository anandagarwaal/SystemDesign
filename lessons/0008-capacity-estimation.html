Capacity Estimation

Do the minimum math that changes a decision — and say so out loud.

Why this lesson, for your mission: Junior candidates grind through ritual QPS-and-storage math to look rigorous. Staff candidates compute exactly one number — the one that decides an architecture — and skip the rest. This lesson teaches you the cheats so the arithmetic costs you nothing, and the judgement to know when not to bother at all.

1 of 6

1. The default is: skip it

Start here, because it is the most important framing and the one most candidates get wrong. HelloInterview's stance is blunt: routine capacity estimation is "often unnecessary", and you should tell your interviewer up front that you'd like to skip estimations and only do the math later, when it's needed.[1] There is no dedicated "capacity estimation" timebox in their 35–45 minute framework at all.[1]

The rule is simple: estimate only when a number will change the design. If knowing the write rate decides whether one database suffices or you must shard, compute it. If the number just decorates a whiteboard and leads to no decision, don't — it burns minutes you need for the deep dives, the section that actually carries an L6/L7 interview.

And don't fear the arithmetic. As HelloInterview puts it, "don't worry if you're not good at mental arithmetic under pressure, most people aren't."[1] The cheats below exist so you never have to be.

★ Staff-level signal The move is doing the minimum math that changes a decision and naming it: "The only number that matters here is write QPS, because it decides whether a single Postgres instance is enough or we need to shard. Read QPS we'll absorb with a cache, so I won't bother pricing it." That sentence shows judgement. Grinding through five calculations that all conclude "yeah, that's fine" shows the opposite.

2. The size cheat sheet

Data sizes are powers of 1000 (close enough; the powers-of-2 difference doesn't matter at this altitude). One ASCII character is ~1 byte, so a tweet of 280 chars is ~300 bytes, a small JSON object is ~1 KB, and a photo is ~1 MB. Memorize the ladder and stop there:

UnitSizeMental anchor
KB10³ bytesOne short JSON object / a paragraph of text
MB10⁶ bytesOne photo, a minute of MP3
GB10⁹ bytesA short video; fits easily in RAM
TB10¹² bytesA large table; a single big disk
PB10¹⁵ bytes"This needs sharding / a data lake"

The only judgement call this enables: does the dataset fit on one machine? Tens of GB fit in RAM; a few TB fit on one node's disk; PB-scale forces distribution. That threshold is usually the whole reason you're estimating storage.

3. The time cheat sheet

The single most useful fact in interview estimation: there are 86,400 seconds in a day, which you round to 100,000. Rounding to 100k (rather than the real 86.4k) makes every division trivial and the answer is correct to order of magnitude — which is all you want.

Per-day → per-second (QPS), the lazy way: divide the daily count by 100,000.
  • 1 million / day ≈ 1,000,000 / 100,000 = ~10 QPS (real answer ~12)
  • 100 million / day ≈ ~1,000 QPS
  • 1 billion / day ≈ ~10,000 QPS (real answer ~12k)
Memorize one anchor — 1B/day ≈ ~12k QPS — and scale it up or down by 10s. You will almost never need more precision than this.

Estimation is about the order of magnitude, not the digits. "About 1,000 QPS" and "about 10,000 QPS" lead to different designs; "1,150 vs 1,200 QPS" lead to the same one. Round hard, round early, and never apologize for it.

4. Latency numbers worth knowing

The classic "Latency Numbers Every Programmer Should Know" (the Jeff Dean / Peter Norvig numbers) exist so you can reason about where a bottleneck lives.[2] You don't memorize the table to recite it — you internalize the one ordering it teaches: memory >> SSD >> disk >> cross-region network.

OperationRough latency
L1 cache reference~1 ns
L2 cache reference~4 ns
Main memory (RAM) reference~100 ns
SSD random read~100 µs
Network round trip within a datacenter~0.5 ms
Disk (HDD) seek~10 ms
Network round trip California ↔ Netherlands~150 ms[2]

The orders of magnitude are the point: RAM is ~1,000× faster than an SSD read, an SSD is ~100× faster than a disk seek, and a single cross-Atlantic round trip (~80–150 ms) dwarfs everything that happens inside one datacenter. This is why caching beats hitting disk, why you keep chatty services co-located, and why you replicate data near users instead of one round-trip per request to a distant region. Every one of those is a design decision a latency number justifies.

5. A worked example — and what each number decides

Suppose: 200M daily active users (DAU), each posts 2 tweets/day, with a 100:1 read:write ratio. Walk it once and tie every result to a decision.

Write QPS

200M × 2 = 400M writes/day. Divide by 100k → ~4,000 write QPS. Apply a peak multiplier of ~2–3× (more below) → ~10k peak write QPS.
So therefore: 10k writes/sec is more than a single primary database wants to absorb durably → this is the number that justifies sharding writes (e.g. by user ID). This is the one calculation worth doing.

Read QPS

100 × write = ~400k read QPS average, ~1M at peak.
So therefore: the system is overwhelmingly read-heavy, so the design needs a read path built around caching and read replicas — you fan reads out across replicas / a CDN / a feed cache rather than scaling the primary. (Notice we needed the ratio, not a precise read QPS, to reach that conclusion.)

Storage over 5 years

A tweet is ~300 bytes of text; round to ~1 KB with metadata. 400M tweets/day × 1 KB = ~400 GB/day → ~150 TB/year → ~750 TB over 5 years (text only; media lives in blob storage / a CDN separately).
So therefore: text alone is hundreds of TB — too large for one node's disk → confirms a sharded / distributed store. The same calculation that decided write sharding decides storage sharding, so you only had to do it once.

★ Staff-level signal Notice we computed three numbers but only one decision driver was new: "10k peak write QPS plus ~750 TB ⇒ we shard." Read QPS only confirmed "read-heavy ⇒ cache," which the ratio told us without arithmetic. A staff candidate says exactly that and spends the saved minutes on how to shard. The estimation is a 2–3 minute sanity check that earns one architectural sentence — not the centerpiece.

6. Peak vs average

The numbers above are daily averages, but traffic is bursty — lunchtime, a live event, a viral moment. Capacity has to survive the peak, not the mean. Apply a rough 2–3× multiplier to average QPS to get a peak figure, and size against that. It rarely changes the order of magnitude, but it's the difference between "~4k QPS, one beefy DB might do" and "~10k peak, we're sharding for sure" — i.e. it can flip the exact decision you were estimating to make. State the multiplier explicitly so the interviewer sees you accounted for burst, not just steady state.

7. How it shows up in the interview

Estimation is a 2–3 minute, optional sanity check that justifies an architectural choice — never a standalone phase. The shape is always: number → "so therefore" → decision.

The clean delivery:
  • Default to skipping — "I'll skip upfront estimation and compute numbers when they affect a decision."[1]
  • When you do estimate, name the one number that matters and why: "Write QPS is the number that decides single-DB vs sharded."
  • Round aggressively — 100k seconds/day, powers of 10. Out loud.
  • Always close with a decision — every number ends in "so therefore we…". A number with no "so therefore" should not have been computed.
  • Account for peak with a 2–3× multiplier when sizing.

A number that doesn't move the design is a tell that you're computing for show. The staff move is the discipline to not compute it — and to say why.
