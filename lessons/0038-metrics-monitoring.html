Design a Metrics Monitoring System

Ingest a 5M-points/sec firehose, serve sub-second dashboards over weeks of history, and fire alerts in under a minute — Datadog/Prometheus from first principles.

Why this lesson, for your mission: A metrics platform is a write-dominated, time-series workload. The senior answer reaches for "just put it in a database." The staff answer recognizes that a generic OLTP/OLAP store collapses under this write rate and series count, picks a purpose-built TSDB, and treats tag cardinality — not raw QPS — as the central scaling problem. This is a favorite L6/L7 prompt precisely because it punishes the lazy default.

Phase 1 · 0–5 minClarify the problemPin scope and the few NFRs that will drive every later decision.

Ask before you design

  • “How many hosts and metrics, and what scrape interval?” — Hosts × metrics ÷ interval gives the ingest rate.
  • “How long must we retain data, and at what resolution?” — Retention tiers drive downsampling and storage.
  • “Push from agents or pull by scraping?” — It affects discovery, firewalls and staleness detection.

Functional Requirements

Scope ruthlessly. Three core capabilities, plus delivery as a satellite concern.[1]

#Users should be able to…
1Emit metrics. Services and agents push/expose time-series data points: name + tags + value + timestamp (e.g. http.latency{service=checkout,region=us} 142 @t).
2Query & visualize. Users query and plot metrics on dashboards with filters, aggregations, and arbitrary time ranges.
3Alert on thresholds. Users define alert rules that fire when a metric crosses a threshold over a window, with notifications (email/Slack/PagerDuty).

Out of scope (say it explicitly): log aggregation, distributed tracing, ML anomaly detection.[1] Naming the boundary is itself a signal.

Phase 2 · 5–10 minEstimate what mattersOnly the numbers that change a decision — say the implication out loud.

Capacity Estimation

Only the numbers that change a decision.

  • Ingest rate: 500k servers × 100 points / 10s ≈ 5M points/sec.[1] At ~100–200 B/point that's ~1 GB/s on the wire. → Horizontally sharded ingestion; no single node absorbs this.
  • Cardinality (the real number): a unique series = metric name × every tag-value combination. latency{service, host, endpoint, status} with 200 services × 500k hosts × 50 endpoints × 10 statuses is billions of series. Each needs its own index entry and chunk stream.[2] This — not QPS — is what breaks the system.
  • Storage: raw at ~1 GB/s ≈ 86 TB/day before compression. TSDB compression (delta-of-delta + XOR) gets ~1.3 bytes/sample[3] → ~1 order of magnitude smaller. Downsampling drops long-term cost by another order.
  • Retention tiers: raw 15d → 1-min 90d → 1-hour 2y. Each tier is a separate, cheaper, smaller dataset.

Interviewer pushback

“Why not store metrics in Postgres?”

Staff answer: 5M inserts/s into B-tree indexes won't keep up, and range scans over raw rows are slow. A TSDB appends, compresses by delta-of-delta, partitions by time and downsamples.

Say to move on → “~5M points/s is heavy, but cardinality is the number that breaks systems. Let me define series and APIs.”

Check before continuing

What defines a unique "series" in this system?

A series is metric name × every tag-value combination; each unique combination needs its own index entry and chunk stream.

Reread the "Cardinality" bullet in the capacity box.

Why is cardinality "the number that breaks systems," rather than raw ingest QPS?

Ingest QPS scales predictably with host count, but one unbounded tag (like a user_id) can multiply series count without limit, exploding index and memory cost.

Think about what happens to the index if one tag has millions of distinct values, versus what happens if you just add more hosts.

Data Model

A series is identified by a fingerprint = hash(metric name + sorted label set); everything else hangs off it. Data is organized into immutable time blocks (e.g. 2 h) that each carry their own inverted label index and compressed chunks, so a query prunes by time first, then by labels, and old blocks can be dropped or downsampled wholesale. Cardinality limits live in tenant configuration because they are the system's real capacity unit.

Phase 4 · 17–27 minHigh-level designA simple end-to-end design that satisfies every functional requirement.

Data Flow — the ingestion pipeline

Trace one point end to end:

  1. Collect. Agents on each host either push to a collector or expose a /metrics endpoint that the platform scrapes on a fixed interval (15–30s).[4]
  2. Ingest & buffer. Stateless ingesters validate, hash the series key, and write to a durable queue (Kafka) partitioned by series — decoupling the firehose from storage and absorbing spikes.
  3. Store. Consumers append to the time-series store: recent data to an in-memory/WAL hot tier, older blocks compacted and compressed to disk/object storage.
  4. Fan out. The same stream feeds two readers: the query/dashboard path (range reads against rollups) and the alerting evaluator (continuous rule checks).

Phase 5 · 27–47 minDeep dives & tradeoffsGo deep where the system breaks; compare alternatives and justify the pick.

Deep Dives

1. The time-series storage engine — why a purpose-built TSDB

The interviewer's trap: "store points in Postgres / Cassandra." Walk through why both lose.

OptionWhy it fails here
RDBMS (B-tree)Random-write index updates per point; can't keep up with 5M/s. Row-per-point storage is huge.
Generic KV / CassandraHandles writes, but no native time-range scan, compression, or rollups — you rebuild a TSDB poorly on top.
Purpose-built TSDBAppend-only, time-partitioned, columnar, compressed. Exactly this workload.

What makes a TSDB fast: (a) data is append-only ordered by time — no random writes; (b) it's partitioned into time blocks so a range query touches only relevant blocks; (c) values are stored columnar per series and compressed with delta-of-delta on timestamps + XOR on floats, hitting ~1.3 bytes/sample.[3] Columnar + vectorized execution is what lets specialized engines beat a row store 10–25× on these queries.[2]

Downsampling + retention tiers. A background compactor rolls raw points into pre-aggregated blocks: raw → 1-min → 1-hour, each a coarser, smaller copy.[3] Old raw data expires per its tier. Thanos, for example, has the compactor build 5-min and 1-hour downsamples in object storage automatically for fast long-range queries.[3] This is the LSM/compaction idea from Lesson 03 applied to time, and the rollup-then-store pattern echoes the aggregation pipeline in Lesson 42.

2. The ingestion firehose & cardinality explosion

5M points/sec is "just shard it." The hard part is cardinality. A single high-cardinality tag — a user_id, a request_id, a container hash — multiplies series count without bound. Each new series costs an index entry, a posting list, and its own chunk; high cardinality increases write amplification: more index updates on compaction, larger posting lists to merge, less-compressible data.[5] This is the "cardinality bomb."[2]

How to keep cardinality bounded:
  • Partition by series hash, not by metric name — spreads hot series and load evenly across ingesters/storage nodes.
  • Reject/limit unbounded tags at ingest (no raw IDs as labels); enforce per-tenant series budgets.
  • Co-locate a series' points on one shard so range reads and compaction stay local.
Staff move: state up front that you'd cap cardinality at the door rather than let the storage tier absorb it.
Check before continuing

What compression technique lets a TSDB hit ~1.3 bytes/sample?

Delta-of-delta on timestamps and XOR on values exploit the fact that consecutive samples change little, driving compression to ~1.3 bytes/sample.

Reread the sentence citing "~1.3 bytes/sample."

Why does one high-cardinality tag like user_id specifically increase write amplification, not just storage size?

Cardinality explosion multiplies the number of distinct series, and each series carries its own index entry and posting list — compaction work scales with series count, not just byte volume.

3. Querying efficiently over ranges

"Show 2 weeks of p99 latency" naïvely scans billions of raw points — far over the seconds-latency budget. The read path instead matches query step to a rollup tier: a 2-week chart at hourly resolution reads pre-aggregated 1-hour blocks, not raw. Time partitioning prunes blocks outside [from, to]; columnar layout reads only the value column; aggregations push down into the engine. The result: query cost scales with the number of plotted points, not the raw ingest rate.

4. The alerting pipeline — push vs pull, evaluating without rescans

An alert "p99 > 500ms for 5 min" must fire within a minute[1] — you cannot re-scan history every cycle. The evaluator runs each rule on a fixed interval against only the recent window in the hot tier, keeping a small rolling state per rule (the for duration). Sharding rules across evaluators keeps each cycle bounded.

★ Staff-level signal Three things separate the staff answer: (1) you choose a purpose-built TSDB and can articulate why a row store fails — append-only, time-partitioned, columnar, compressed, with rollup tiers; (2) you name tag cardinality as the central scaling problem and bound it at ingest rather than hoping storage absorbs it; (3) you design an incremental alerting evaluator that works on rolling windows, never rescanning history. Senior candidates scale QPS; staff candidates scale series.

Privacy

Metrics should be operational, not personal — but labels leak. Rule: no user ids, emails, IPs or request ids as label values; ingest-time label allow-lists and PII pattern checks reject or hash offending values (which also defends cardinality). Tenancy: strict isolation; cross-tenant query federation disabled by default. Retention: raw 15 days, rollups longer — raw PII accidentally ingested ages out quickly, and a delete-series API exists for emergencies. Access: business-sensitive metrics (revenue, signups) in restricted folders.

First bottleneck: head-tier memory from series churn (short-lived containers create new series constantly) — addressed by churn-aware limits and shorter head blocks. What forces a redesign: requirement to query arbitrary high-cardinality dimensions (per-user metrics), which belongs in an OLAP/event store (alternative C), not a TSDB.

Wrap-up · 58–60 minClose strongRecap decisions and tradeoffs in 60 seconds; name what you would do next.

Closing Summary (60 seconds)

A metrics system is a write-optimized time-series store with cardinality as its main scaling risk. Agents send points to stateless ingesters that validate them, enforce series limits and partition by series hash into Kafka. A purpose-built TSDB appends and compresses points in time-partitioned blocks, flushes them to object storage and downsamples into rollup tiers. Queries choose the right resolution. Alert rules evaluate incrementally on recent data. At 10× we add ingesters, partitions and nodes, with tenant cardinality limits.
