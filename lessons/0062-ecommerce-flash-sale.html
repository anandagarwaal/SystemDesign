System Design · Lesson 62 · Phase 4 — Case Study · Hard

Design an E-Commerce / Flash Sale System

A normal checkout you could build in a weekend — until 5 million people race for 10,000 units at noon and a single oversold SKU becomes a refund-and-PR incident.

Why this lesson, for your mission: An e-commerce store is an easy CRUD app right up to the moment a flash sale turns one row of inventory into the most contended object in the building.[1] The staff signal is not "I can write a checkout" — it's recognizing that you are running two systems with opposite priorities (an AP, cache-everything browse path and a CP, never-oversell inventory path), then shedding and serializing the spike at the door instead of scaling a fundamentally contended row. That framing — borrowed straight from Ticketmaster and online auctions — is what separates an L6/L7 hire from a senior one.

Phase 1 · 0–5 minClarify the problemPin scope and the few NFRs that will drive every later decision.

Ask before you design

  • “How many units and how many shoppers at the sale start?” — The demand-to-inventory ratio decides whether we need a waiting room.
  • “How long can an item sit in a cart before it's released?” — The reservation TTL shapes inventory holds.
  • “Is there a per-customer purchase limit?” — Limits are a key anti-bot and fairness control.

Functional Requirements

Lock scope to what a buyer actually does end-to-end, and call out the flash sale as a first-class requirement rather than "just more traffic." Push reviews, recommendations, returns, and seller onboarding out of scope and say so.

#Users should be able to…Note
1Browse and search the product catalogRead path — by far the highest volume
2Add items to a cartPer-user state; cheap, soft, no inventory claim yet
3Checkout: reserve → pay → place orderWrite path — the hard part; payment + order creation
4Buy limited-inventory items in a flash saleThe crux: millions contend for thousands of units; no overselling

Non-Functional Requirements

One sentence carries the whole design: prioritize availability and low latency for browse, but prioritize consistency on inventory — never sell the same unit twice. Different NFRs for different paths is the framing move, exactly as in the auction and ticketing problems.[1]

★ Staff-level signal Say out loud that you are deliberately running two consistency regimes in one product: AP (available, eventually consistent, cache-first) for browsing, and CP (strongly consistent, willing to reject) for the inventory decrement. The number-one failure mode in this interview is letting the strongly-consistent inventory machinery — locks, the primary DB — leak onto the read path and take the whole site down with it. Naming and enforcing that split is the single highest-leverage sentence you'll say.

Say to move on → “Availability for browse and strict consistency on inventory. The spike is what matters, so let me size it.”

Phase 2 · 5–10 minEstimate what mattersOnly the numbers that change a decision — say the implication out loud.

Capacity Estimation

Only estimate the numbers that change a decision. For a flash sale exactly one thing matters: the spike. Assume a sale of 10,000 units opening to ~5M interested users arriving within the first ~10 seconds.

QuantityEstimate (own assumptions)Design implication
Peak arrival5M users / ~10s ≈ 500k req/s at the door, vs. a steady-state baseline of maybe 5k req/s~100× spike. You cannot provision the inventory DB for 500k writes/s — you must shed and pace load before it reaches the contended row.
Contended write target10,000 successful decrements total; everyone else must fail fastThe entire problem is funneling 500k req/s of intent into ≤10k correct writes without overselling and without melting the DB.
Read : write ratio~1000 : 1 — browsing/refreshing dwarfs buyingOptimize the read path independently; serve stock-availability reads from cache, never the primary.

Inventory itself is tiny — one hot row (or a few) per SKU. The challenge is never storage; it's extreme concurrent contention on a single small, hot counter. That single observation is what makes this a "hard" case study.

Interviewer pushback

“Can't we autoscale to handle 500k requests per second?”

Staff answer: Autoscaling lags by minutes and the database can't absorb that write contention anyway. Absorb the spike at the edge and a waiting room, and admit only what the inventory path can handle.

Say to move on → “~500k requests/s for 10k units: hundreds of times more demand than stock. Let me define entities.”

Phase 3 · 10–17 minAPI & data modelLock the contract and the storage shape before drawing boxes.

Core Entities & API

Entities: Product (id, title, price, description — the catalog), Inventory (productId, available count, optional reserved count), Cart (userId, line items), Reservation (userId, productId, qty, expiry — a short TTL hold), and Order (userId, items, total, status: pending | paid | confirmed | failed). The available counter and the Order status are where the consistency story lives.

User identity always comes from the auth token, never the request body.

EndpointPurpose
GET /v1/products?query=&page=Search / list catalog — served from cache + search index.
GET /v1/products/{id}Product detail page (PDP), incl. cached availability flag.
POST /v1/cart/itemsAdd to cart: {productId, qty} — soft, no inventory claim.
POST /v1/checkoutReserve: atomically decrements stock and creates a Reservation + Order(pending); returns orderId. Idempotency-Key header required.
POST /v1/orders/{id}/payPay + place: charges via the payment system, flips Order → paid; idempotent.

Splitting reserve from pay is intentional: the buyer gets a short window to enter payment while the unit is held. That window is the entire reason the overselling problem exists — identical to the reserve→pay split in Ticketmaster.

Data Model

Postgres is the source of truth for inventory and orders; Redis holds the sale-time gate: a (possibly sharded) stock counter per SKU, a per-user purchase set to enforce limits, TTL reservation keys, and the waiting-room queue. The Postgres CHECK (available >= 0) plus conditional decrement means the database refuses to oversell even if the Redis gate is wrong. Idempotency keys make every retry return the same order.

Interviewer pushback

“Why a Reservation separate from Order?”

Staff answer: Holding a unit during checkout must expire automatically if payment doesn't finish; an order is the durable result. Separating them keeps holds cheap and self-cleaning.

Say to move on → “Reservation with a TTL and idempotent orders. Now browse versus buy paths.”

Browsing never touches inventory: it's served by the CDN and caches. High-Level Design

An API Gateway (auth, routing, rate-limit) and a CDN front everything. Requests fan out to stateless services that share no critical-path infrastructure between the browse and buy paths.

Flow. browse → CDN/Catalog Service → cache/replica (never touches inventory primary). checkout → optional waiting room → Inventory Service does an atomic decrement; if it succeeds, it writes a Reservation and enqueues an OrderRequested event and returns fast. The Order Service consumes the event, creates Order(pending); the client then calls pay, which drives the payment system; on success the Order flips to paid and the reservation is committed; on timeout/failure the reservation's TTL releases the unit back to stock.

Interviewer pushback

“Why can the order be created asynchronously?”

Staff answer: Only the inventory decrement must be synchronous. Order rows, payment and emails go through a durable queue, so a slow payment provider doesn't stall checkout during the spike.

Say to move on → “Deep dives: overselling, async checkout, cached reads and the thundering herd.”

Phase 5 · 27–47 minDeep dives & tradeoffsGo deep where the system breaks; compare alternatives and justify the pick.

Deep Dive 1 — Overselling under extreme contention (the central problem)

The hazard: 500k requests per second all read "1 unit left," all believe they won, and you ship 40,000 orders for 10,000 units.[1] The fix has two parts — make the decrement atomic, and make the hold auto-expiring. Mechanisms, escalating in quality:

MechanismHowWhy it fails / wins
Read-then-write in app codeSELECT count, check > 0, then UPDATE count-1Broken. Classic race: the check and the write aren't atomic, so concurrent buyers all pass the check. This is the oversell bug.
DB row lock (SELECT … FOR UPDATE)Lock the inventory row per checkoutBad at scale. Correct, but serializes 500k req/s on one row → lock queue, latency cliff, deadlocks. A lock is not a high-throughput tool.[2]
Conditional atomic decrement (DB)UPDATE inventory SET avail=avail-1 WHERE id=? AND avail>0; success ⇔ 1 row affectedGreat. One statement, atomic, no app-level race, no oversell. But the primary still eats the full write spike.[2]
Redis atomic decrement + TTL hold (staff pick)DECR / Lua on a hot Redis counter; reject if it goes negative; set a per-user reservation key with TTLGreat, and the staff pick for a flash sale. Single-threaded Redis serializes the decrement for free at >100k ops/s, keeps the spike off Postgres, and the TTL is the hold-release. Reconcile to Postgres asynchronously.[1]
The staff pick — and why. A Redis atomic counter as the front-line inventory gate, with Postgres as the durable source of truth.[1] The reasoning matters more than the choice:
  • Atomicity beats locking. A conditional decrement (or single-threaded Redis op) makes the operation correct without holding a lock across the network round-trip — so throughput isn't capped by lock duration. See common patterns on atomic counters vs. locks.
  • The hold is ephemeral, so store it ephemerally. A 5-minute reservation is not durable business data; a Redis key with a TTL releases the unit automatically if payment never lands — no sweeper, no cron, no stuck stock (the same lazy-expiry insight from Ticketmaster).
  • Belt and suspenders. The final order commit still re-checks against Postgres in a transaction with the conditional decrement, so even a total Redis outage degrades to "more sold-out surprises" but cannot oversell. Redis is an optimization on top of a DB that is itself correct.
  • Hot-key sharding. If a single SKU's counter saturates one Redis shard, split the stock into N sub-counters (e.g. 10×1,000) and decrement a random one — classic hot-key fan-out.

Even an atomic counter doesn't help if 500k req/s reach it. For the most contended sales, put a queue-based admission / virtual waiting room in front of the Inventory Service (Deep Dive 4) so the counter only ever sees a paced trickle. This is the same load-shedding move as Ticketmaster's virtual queue[1] and the bid-serialization discipline in online auctions.

Deep Dive 2 — Decoupling checkout from order fulfillment via a queue

Order placement does a lot: create the order record, reserve inventory, charge payment, notify warehouse, email the buyer. Doing all of that synchronously inside the checkout request means one slow downstream (a sluggish PSP, a warehouse API hiccup) stalls the whole request and amplifies the spike. The fix: accept fast, fulfill asynchronously.

Queue-backed order pipeline.
  • Once inventory is atomically claimed, the checkout endpoint writes an OrderRequested event to a durable log (Kafka/SQS) and returns orderId + "pending" immediately.
  • Downstream consumers (Order Service, payment driver, notifications) process the event independently and can scale, retry, and fail in isolation.
  • The queue acts as a buffer that flattens the spike: the contended decrement is bounded by stock, and everything after it drains at a steady, provisioned rate.
  • Backpressure is natural — if fulfillment lags, the queue grows but the user already has a confirmed "order received."
★ Staff-level signal The insight to verbalize: the only thing that must be synchronous and strongly consistent is the inventory decrement. Everything else — order rows, payment, emails — can be pushed onto a durable queue and made eventually consistent. Drawing that line precisely (sync CP gate, async AP tail) is the senior-to-staff jump; juniors try to make the entire checkout one ACID transaction and then can't scale it.

Deep Dive 2b — Idempotent order placement + payment

Spikes mean retries: the client times out and resubmits, the gateway retries, the queue redelivers (at-least-once). Without idempotency you get duplicate orders and double charges — the single worst outcome for trust. Make both placement and payment idempotent.

LayerIdempotency mechanismEffect
Checkout APIClient sends a unique Idempotency-Key; server stores key → result in a dedup tableRetried checkout returns the same orderId, never a second order.[3]
Queue consumerConsumers are idempotent on orderId (upsert / dedup on event id)At-least-once redelivery is safe; reprocessing is a no-op.
Payment chargePass the order's idempotency key to the PSP (e.g. Stripe Idempotency-Key)The payment system charges the card exactly once even on retry.[3]

Pair this with the saga pattern: if payment ultimately fails or the reservation TTL lapses, a compensating action releases the held unit back to stock and marks the Order failed. See the payment system lesson for the full charge/refund state machine and webhook reconciliation.

Deep Dive 3 — Caching the catalog read path vs. the consistent write path

During a flash sale, reads outnumber writes ~1000:1 — everyone is refreshing the product page waiting for the drop. Serve those reads from anything except the inventory primary.

ReadWhere it's servedConsistency
Product details, images, price, descriptionCDN + Redis cache (long TTL), search index for listingsEventually consistent — fine; catalog rarely changes mid-sale.
"In stock / sold out" badge on the PDPCached availability flag (short TTL) or pub/sub fan-out from InventoryApproximate is OK — the authoritative check is the atomic decrement at checkout.
Actual decrement at purchaseInventory Service only (Redis counter → Postgres)Strongly consistent — the one place correctness is non-negotiable.
★ Staff-level signal The move is to decouple "is it available?" (a cached hint) from "claim it" (the atomic truth). Showing a slightly stale "in stock" badge and then failing fast at checkout for the unlucky majority is correct and cheap; trying to show every user a perfectly live count would put the read spike directly on the contended counter and defeat the entire design. Accepting a little staleness on the read path to protect the write path is exactly the AP/CP judgement this question is testing.

Deep Dive 4 — Taming the thundering herd

At t=0 millions of clients (and their auto-refreshing tabs) hit the same endpoints in the same second. Three compounding layers defend against it:

Layered defense against the spike.
  • Absorb at the edge. Serve the sale landing page + assets from the CDN; never let static reads reach origin. A countdown timer and client-side jitter spread out the initial connect.
  • Virtual waiting room / queue-based admission. Enqueue arrivals (e.g. a Redis sorted set keyed by arrival time for fairness), show position + ETA over SSE, and dequeue at a controlled rate into an "admitted" set with a TTL — exactly the Ticketmaster pattern.[1] The Inventory Service only serves admitted users, so the counter sees a bounded stream.
  • Fail fast, don't queue forever. Once stock hits zero, return "sold out" immediately at the gate; don't admit users to fight over nothing. Reject early and cheaply rather than letting load pile onto the DB.
  • Cache-stampede guards. On expiry of the availability cache, use a single-flight / request-coalescing lock so one request refreshes while others serve stale — prevents a herd from hammering the origin at once.

The unifying principle across all four deep dives: don't scale the contended core to the spike — serialize and shed load before it gets there. A queue converts an unbounded burst into a bounded, paced stream; an atomic counter makes each admitted request correct; idempotency makes retries safe; caching keeps the 99.9% of read traffic away from the one row that actually matters.

Wrap-up · 58–60 minClose strongRecap decisions and tradeoffs in 60 seconds; name what you would do next.

Closing Summary (60 seconds)

A flash sale is an admission-control and atomic-inventory problem. The CDN serves static sale pages and a waiting room admits shoppers at a sustainable rate. Checkout does one synchronous action: an atomic decrement-if-available in Redis with a reservation TTL, backed by a conditional update in Postgres, so units are never oversold. Everything else (order creation, payment, notifications) runs asynchronously through an idempotent queue. Browse reads show a cached, slightly stale stock hint. At 10× only the edge and waiting room scale.

Check yourself — retrieval practice

Answer from memory before scrolling back up.

1. Why does a read-then-write inventory check oversell under a flash sale?

The read and the write aren't atomic — concurrent requests all read the same positive count and all decrement, selling more than exists.

2. Why is a Redis atomic decrement preferred over SELECT … FOR UPDATE here?

A row lock is correct but serializes 500k req/s on one row, causing a latency cliff; an atomic counter is correct AND high-throughput.

3. What does pushing order fulfillment onto a durable queue buy you?

Only the inventory decrement must be synchronous and consistent; everything after it (orders, payment, email) can drain from a buffering queue.

4. Why is an idempotency key essential on the checkout and payment calls?

Spikes cause retries and at-least-once redelivery; without idempotency you get duplicate orders and double charges — the worst trust outcome.
