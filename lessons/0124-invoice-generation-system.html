Design an Invoice Generation System

Building a distributed system that transforms order events into legal, immutable invoices at scale.

Why this lesson, for your mission: Invoice systems look simple on the surface but touch every part of a mature platform: event sourcing, immutability, batch processing, storage patterns, and compliance. The staff move is recognizing that this is really a state machine problem wrapping around an immutable ledger, not a CRUD API. Get the event-driven architecture right and you see the same DNA in billing, audit logging, and financial reconciliation systems.

Phase 1 · 0–5 minClarify the problemPin which events trigger invoices and the immutability contract.

Ask before you design

  • "What events trigger invoice generation — payment only, or shipment too?" — This sets whether the invoice is order-based (one per order) or payment-based (multiples). Legal invoices are often order-based and immutable on issue.
  • "Can invoices be amended or voided after issuance?" — Regulatory frameworks differ. US SaaS invoices are immutable; some jurisdictions require amendment trails. This shapes your schema and audit strategy.
  • "What's the delivery format — API, email, PDF, or all three?" — Format requirements affect the data pipeline and storage.

Phase 2 · 5–10 minEstimate what mattersInvoice volume, storage, and the peak write rate across regions.

Capacity Estimation

Invoice generation rate

100M DAU × 0.1 orders/day ≈ 10M orders/day ≈ ~115 invoices/sec average, peaking at ~500/sec during sales events. Implication: a single write service can handle this; sharding is a "later" concern.

Storage

Each invoice ~3 KB (metadata + 20 line items). 10M/day × 365 days × 3 KB ≈ 11 TB/year. Implication: multi-node relational DB or distributed blob store + index. Archive to cold storage after 90 days; retention is 7 years per legal.

Invoice number space

Sequential counter: 10M/day × 365 ≈ 3.65B invoices/year. A 64-bit integer handles trillions without overflow. Implication: a Redis counter is your bottleneck; batching is essential.

Interviewer pushback

"Why not use a UUID or ULID instead of a sequential invoice number?"

Staff answer: Sequential invoices are a legal/compliance requirement in most jurisdictions and part of the customer-facing invoice ID. UUIDs are fine internally for idempotency keys, but the user-facing number must be monotonic.

Say to move on → "With ~500 invoices/sec peak and 11 TB/year storage, I'll define the entity model and access patterns."

Interviewer pushback

"Should invoice_number be globally unique or per-customer?"

Staff answer: Globally unique. Each invoice is a legal document in the company ledger, and accounting systems expect monotonic, non-repeating IDs. Per-customer sequences introduce coordination and audit complexity.

Phase 4 · 17–27 minHigh-level designEvent sourcing → processing → storage, with a single source of truth.

Data Flow

Invoices are triggered by external events (order placed, payment received) and flow through a processing pipeline that assigns a unique number, validates the order data, and persists an immutable record. The pipeline is entirely event-driven; no invoice is ever manually created.

Single source of truth: the invoice ledger. All reads reflect that log; all writes go through event sourcing.

High-Level Design

The invoice generator consumes order and payment events from Kafka. For each event, it acquires a unique invoice number from Redis, fetches order details, constructs the invoice, writes it to Postgres (with a UNIQUE constraint on the invoice number for safety), and immediately emits an InvoiceCreated event. Downstream consumers handle PDF rendering and email delivery asynchronously.

Reads go through read replicas or a cache (Redis with TTL matching invoice finality). All writes are single-threaded per customer (via Kafka partitioning) to preserve order. Invoice state is immutable after creation; amendments (if allowed) are modeled as a separate InvoiceAdjustment entity that references the original invoice.

Interviewer pushback

"What happens if the invoice number counter crashes?"

Staff answer: Each write server leases a block of numbers (e.g. 10,000) from Redis before crash. On crash, the batch is lost but invoices stay uniquely numbered. If Redis itself crashes, a backup or persistent log gives you recovery; gaps in the sequence are acceptable.

Say to move on → "The design is event-driven and immutable. The hard parts are idempotency and handling late/duplicate events."

Phase 5 · 27–47 minDeep dives & tradeoffsGo deep where the system breaks; compare alternatives and justify the pick.

Deep Dives

Deep Dive 1 — Idempotent invoice generation

The pipeline must be idempotent: if an event is replayed, no duplicate invoice is created. Use a deduplication key (order_id + event_version) and check for existing invoices before allocating a new number. Store the dedup key in the invoice record.

Pattern:
  • Consumer receives event with idempotency_key = order_id:v1
  • Query: SELECT * FROM invoices WHERE idempotency_key = ?
  • If found, return existing invoice (idempotent success)
  • If not found, acquire number, insert, emit event
  • Store idempotency_key as a UNIQUE constraint to guard against race conditions

Deep Dive 2 — Sequential invoice numbering under concurrency

A global counter ensures uniqueness but is a bottleneck. Batch allocation is the fix: each write service instance requests a batch (e.g., numbers 1,000,000–1,000,999) from Redis via INCRBY, then serves locally. If an instance crashes, the batch is lost but the sequence is preserved.

ScenarioHandling
10 write servers, 500 invoices/secEach requests 1,000-number batch; average leak is 5 numbers/crash (negligible)
Counter reaches capacity (2^63)Rotate to a new counter (e.g., INV-2026-* with year prefix); old sequences archived
Late/reordered Kafka eventsDeduplicate by order_id; ignore if invoice already exists

Deep Dive 3 — Immutability and amendments

An invoice is immutable once issued. If amendments are required (e.g., tax correction), create a credit memo (a negative invoice) or amended invoice that references the original. Never overwrite the original ledger entry. This preserves the audit trail and satisfies most regulatory requirements.

Amendment strategy:
  • Original invoice is locked (status = ISSUED, read-only)
  • Create InvoiceAmendment entity referencing original_invoice_id
  • Amendment carries the deltas (adjusted amount, new tax); original stays unchanged
  • Ledger shows both; accounting recognizes the pair as a correction

Deep Dive 4 — Late event handling and out-of-order delivery

Kafka guarantees in-order delivery per partition but partitions can lag. If an event arrives after the invoice is already issued, the dedup key prevents a duplicate. If events arrive out of order (e.g., payment before order acknowledgment), handle via event enrichment: the consumer waits for the order service to acknowledge before generating the invoice.

Deep Dive 5 — Storage and archival

Live invoices stay in Postgres; after 90 days, archive to cold storage (S3 Glacier). Keep an index in DynamoDB mapping invoice_id → S3 location for retrieval. Full retention is 7 years per compliance; queries older than 90 days hit the archive.

★ Staff-level signal A senior engineer recognizes this as an event-sourcing problem and models the state machine. A staff engineer goes further: they identify idempotency as the non-negotiable property, design the dedup key before sketching the pipeline, and justify the batch-leasing counter as a tradeoff that avoids bottlenecks while staying simple. They know immutability is legally mandated and build for audit trails from the start, not as a bolt-on. They also recognize that amendments are a separate entity type, not an update to the original ledger.

Interviewer pushback

"Why Kafka instead of a simple database trigger?"

Staff answer: Triggers are synchronous and tightly coupled; if the PDF renderer is slow, the order service blocks. Kafka decouples and provides a durable queue; if the invoice service crashes, events are replayed from the partition. Also, other services (accounting, taxes) can subscribe to the same event stream.

Authentication & Authorization

GET /v1/invoices/{invoice_id} is customer-facing; enforce that a user can only read invoices for their own orders. Internally, the invoice generator is a service-to-service call authenticated via mTLS. Audit logs are read-only for compliance staff, never modified or deleted.

Security

ThreatMitigation
Unauthorized accessCustomer reads own invoices only; service-to-service mTLS
Invoice tamperingImmutable DB schema (no UPDATE); cryptographic signatures on PDFs
Invoice duplicationIdempotency key + UNIQUE constraint prevents double-issue

Privacy

Invoices contain PII (customer name, email, address). Encrypt at rest (AES-256). Right to erasure: when a customer deletes their account, soft-delete the invoice but retain a hash for dispute resolution; final deletion after 7-year retention. GDPR: store customer location; if EU resident, GDPR complies with erasure and portability. CCPA: log all accesses to PII for breach audits.

Audit & Compliance

Every invoice is immutable and signed. Store a cryptographic hash of the final PDF. Maintain an append-only audit log of all invoice reads and amendments. Financial/tax authorities expect to see: invoice issued date, sequence number, amount, and signature. Design for 7-year retention in cold storage.

Interviewer pushback

"How do you handle GDPR erasure for a 7-year audit log?"

Staff answer: PII (name, email) is soft-deleted; invoice remains as a hashed record. If full deletion is required, anonymize the record (keep amount, date, counter, hash) and log the erasure for audit. Most regulations accept this approach.

2 · Closing Summary (60 seconds)

The invoice system is event-driven and immutable: order events trigger unique, sequentially numbered invoices stored in Postgres. Idempotency via dedup keys prevents duplicates. Redis counter with batch leasing avoids bottlenecks. Async PDF rendering and archival to cold storage keep the hot path fast. At 10×, sharding by customer or date window is the first major architectural change. Legal and compliance requirements drive every decision: immutability, audit trails, and 7-year retention are non-negotiable. The design prioritizes correctness and auditability over raw scale.

Check yourself — retrieval practice

Answer from memory before scrolling back up.

1. Why use an event-sourcing pattern for invoices instead of a synchronous CRUD API?

Event sourcing provides a durable queue (Kafka), allows other services to subscribe, and creates an immutable ledger that auditors can inspect. CRUD APIs are tightly coupled and synchronous.

2. How should invoice numbers be generated to ensure uniqueness at 500/sec?

Batching reduces coordination overhead and avoids a per-write round-trip to Redis. DB SEQUENCE bottlenecks at high throughput. UUIDs are not sequential and violate compliance requirements for monotonic invoice numbers.

3. If the same order event is replayed from Kafka, how should the system handle it?

Idempotency keys (order_id + event version) are the mechanism; check if the invoice already exists and return it if so. Updating invoices violates immutability. The counter doesn't help here; deduplication does.

4. Why is immutability a core requirement for invoices?

Immutability is legally mandated for financial records in most jurisdictions. It supports auditability, fraud prevention, and dispute resolution. Amendments are new entities, not updates to the original.

Ask me anything. How would you handle invoice amendments or corrections? What strategies would you use to detect fraudulent duplicate invoices? How would you design the system differently if invoices had to be available in multiple currencies and tax regimes?
