Deep Dive: API Design — REST vs GraphQL

The API is the contract every client depends on. Choosing its shape — and getting pagination, idempotency, and auth right — is a quiet staff-level skill.

Why this lesson, for your mission: In almost every case study you'll define a "Core Entities & API" section, and interviewers read it as a tell. A junior lists endpoints. A staff candidate picks REST, GraphQL, or gRPC for a stated reason, then nails the cross-cutting details that separate a toy API from a production one: idempotency keys so a retried payment doesn't double-charge, cursor pagination so a feed doesn't break under writes, and an auth/rate-limit story. This lesson gives you a crisp decision rubric and the handful of details to drop into every API design.

REST done well

REST models your system as resources (nouns) addressed by URLs, manipulated with HTTP verbs.[1] The discipline is more than "JSON over HTTP" — it's using the protocol's own semantics so caches, proxies, and clients behave predictably.

VerbMeaningIdempotent?
GETRead a resource; safe, no side effects, cacheable.Yes
POSTCreate a sub-resource / trigger an action.No
PUTReplace a resource wholesale at a known URL.Yes
PATCHPartially update fields of a resource.No (usually)
DELETERemove a resource.Yes

Idempotency is the property that doing the operation twice has the same effect as once — and it's the single most important word in API design. Networks retry; a client that times out on a POST /payments doesn't know if the charge happened. The fix is an idempotency key: the client sends a unique Idempotency-Key header, the server records the result against that key, and a replay returns the original result instead of charging again.[3] Stripe does exactly this — mention it for any write that must not duplicate.

Status codes, versioning, pagination

  • Status codes carry meaning: 2xx success, 4xx client error (400 bad input, 401 unauthenticated, 403 unauthorized, 404 missing, 409 conflict, 429 rate-limited), 5xx server error. Don't return 200 with an error body.
  • Versioning: evolve without breaking clients via a URL prefix (/v1/) or a header. Prefer additive, non-breaking changes; reserve a version bump for genuine contract breaks.
  • Pagination — cursor beats offset: ?limit=20&offset=100 is simple but breaks under writes — insert a row and page 6 repeats an item or skips one, and large offsets force the DB to scan-and-discard. Cursor (keyset) pagination passes an opaque pointer to the last item seen (?limit=20&after=eyJpZCI6...) and queries WHERE id < cursor ORDER BY id LIMIT 20 — stable under concurrent writes and index-friendly at any depth. Use cursors for feeds and large/append-heavy lists.

(HATEOAS — responses embedding links to related actions — is the purest form of REST but rarely implemented in practice; know the term, don't over-invest.)

GraphQL

GraphQL exposes a single endpoint (POST /graphql) and a typed schema; the client sends a query describing exactly the fields it wants, and the server returns precisely that shape.[2] Each field is backed by a resolver function. It exists to kill two REST pain points on rich, nested data:

  • Over-fetching: a REST GET /users/42 returns the whole user object even when the mobile client needs only the name and avatar.
  • Under-fetching / multiple round-trips: rendering a profile screen needs the user, their last 3 posts, and each post's comment count — three or more REST calls. One GraphQL query fetches the whole tree in a single request, which is a big win on high-latency mobile networks.[2]
The N+1 resolver problem — GraphQL's signature trap
  • A query for "10 posts, each with its author" naively runs 1 query for posts + 10 queries for authors — the resolver for author fires once per post. At scale this hammers the database.[2]
  • Fix — DataLoader batching: instead of resolving each author immediately, collect all author IDs requested in one tick and issue a single WHERE id IN (...) batch query, then de-multiplex the results. This collapses N+1 into 2 queries.
  • Caching is harder: because everything is one POST URL, you lose HTTP/CDN caching for free; you cache at the resolver/field layer (e.g. persisted queries, response caches keyed by query+vars) instead.
  • New risks: a client can ask for a hugely deep/expensive query, so you add query depth/complexity limits and cost analysis.

Choosing — and the cross-cutting concerns

Default heuristic: REST for public, cacheable, resource-oriented APIs; GraphQL when many heterogeneous clients fetch deep, varied slices of a graph and over/under-fetching is real; gRPC between your own services where you control both ends and want speed. These aren't exclusive — many companies expose REST/GraphQL at the edge and gRPC internally.

Whatever you pick, these concerns are identical and worth a sentence each in an interview: authentication/authorization (bearer token / OAuth — see Lesson 115), rate limiting (429 + a token bucket — see Lesson 22), pagination (cursors), idempotency (keys on writes), and error design (consistent machine-readable error bodies).

★ Staff-level signal Junior candidates list endpoints. Staff candidates make the API a contract. They say "POST /payments needs an idempotency key because the client will retry on timeout and we must never double-charge,"[3] and "I'll use cursor pagination on the feed so concurrent posts don't shift the page." When they propose GraphQL they immediately name the N+1 problem and reach for DataLoader and query-cost limits — showing they know the operational cost, not just the buzzword.[2] The tell is that they discuss how the API behaves under retries, writes, and abuse, not just its happy-path shape.

In the interview

In the "Core Entities & API" step: (1) list the 3-4 core entities, (2) pick a style with one sentence of justification ("REST — this is a public CRUD-ish API and I want CDN caching on reads"), (3) sketch 4-6 endpoints with the right verbs and status codes, (4) proactively drop the two details that signal seniority — an idempotency key on the critical write and cursor pagination on the big list — and (5) name auth + rate limiting in a line. Don't agonize over REST vs GraphQL; state a default fast and spend your depth budget on idempotency, consistency, and pagination instead.

Check yourself — retrieval practice

Answer from memory before scrolling back up.

1. Why does cursor pagination beat offset pagination?

A cursor anchors to the last item seen, so inserts don't shift pages and the DB seeks instead of scanning-and-discarding at large offsets.

2. What does an idempotency key on a POST prevent?

The server records the result against the key, so a replay after a timeout returns the original outcome instead of charging again.

3. What problem is GraphQL specifically designed to solve?

Clients request the exact fields they need in one query, eliminating fixed over-sized responses and many sequential REST calls.

4. How does DataLoader fix GraphQL's N+1 problem?

Instead of one DB call per parent, it collects all requested IDs and issues a single batched query, collapsing N+1 into ~2 queries.
