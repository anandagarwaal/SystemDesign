Deep Dive: MapReduce, Hadoop & HBase

The idea that started big data — move the compute to the data — and why disk round-trips later handed the crown to Spark.

Why this lesson, for your mission: MapReduce is the ancestor every modern batch engine descends from. A senior candidate can recite "map then reduce." The staff answer explains why the model exists — moving computation to data so a thousand commodity machines can chew through petabytes — names the phase that dominates the cost (shuffle & sort), and explains exactly why MapReduce's per-step disk round-trips made Spark inevitable. You learn this not to deploy it, but so that when you say "Spark" or "a batch DAG" you can defend the lineage and know what problem it actually solved.

The big idea — move compute to the data

Before 2004, processing a petabyte meant pulling data to a few big, expensive machines — and the network became the wall. Google's MapReduce inverted it: store the data spread across thousands of cheap machines, then ship the small program to wherever each chunk already lives and run it locally.[1] Compute is light; data is heavy; so you move the light thing. This single inversion is the foundation of all of big data.

The programmer writes just two pure functions and the framework handles the terrifying parts — distribution, parallelism, machine failure, and data movement:[1]

FunctionSignature (conceptually)Job
map(k1, v1) → list(k2, v2)Process one input record, emit zero+ intermediate key/value pairs.
reduce(k2, list(v2)) → list(v3)Receive all values for one key, aggregate them into the result.

Between them sits the part the framework owns and the programmer never writes: shuffle & sort — grouping every value by its key and routing it to the right reducer.[1] The whole model is just map → shuffle/sort → reduce. That rigidity is its strength (trivially parallel, trivially recoverable) and, later, its fatal weakness.

Internals — the meat

1 · The map phase

Input lives on HDFS (Hadoop's distributed file system) split into large blocks — typically 128 MB. MapReduce assigns one map task per input split, and the scheduler tries to place that task on the very machine holding the block — data locality, the practical payoff of "move compute to data."[1] Each map task runs your map() over its records and emits intermediate (k2, v2) pairs to a local in-memory buffer that spills to local disk (not HDFS) as it fills.

2 · Partitioning — deciding who reduces what

Every intermediate key must reach exactly one reducer, and all values for a key must reach the same one. A partitioner decides which: by default hash(key) mod R, where R is the reducer count.[1] Each map task therefore writes its output already split into R partitions on local disk. Choose the partition function badly — or have one hot key — and one reducer gets a mountain while the rest idle: classic data skew, the same enemy you fight in Spark.

3 · Shuffle & sort — the expensive part

This is the heart of the cost. Once maps finish (or begin finishing), each reducer must pull its partition from every map task across the network — an all-to-all transfer.[1] As the data lands, the framework merge-sorts it by key so that each reducer sees keys in order with all values for a key grouped together. Shuffle & sort is what makes reduce possible, and it is the single most expensive thing MapReduce does: it touches local disk on the map side, crosses the network, and merges on the reduce side. If you remember one cost model: the shuffle is the bill.

4 · The reduce phase

Each reduce task receives its keys in sorted order and calls your reduce(k2, list(v2)) once per key, with an iterator over all that key's values. The output is written to HDFS (replicated for durability), one output file per reducer.[1] A job with R reducers produces R output files — often the input to the next MapReduce job in a chain.

5 · Combiners — shrinking the shuffle early

The key optimization. A combiner is a "mini-reduce" that runs on the map side before the shuffle, pre-aggregating a map task's output so less data crosses the network.[1] For word count, instead of shipping ("the", 1) ten thousand times, the combiner emits ("the", 10000) once. It only works when the reduce operation is commutative and associative (sum, max, count — yes; average — not directly). This is the direct ancestor of Spark's reduceByKey-over-groupByKey advice.

6 · Fault tolerance via re-execution

With thousands of commodity machines, failure is routine, not exceptional — so the design assumes it. The master pings workers; a silent worker is presumed dead and its tasks are simply re-executed elsewhere.[1] This is cheap precisely because map/reduce are deterministic pure functions over immutable input: re-running a task gives the same answer. Completed map output sits on a failed node's local disk, so completed maps are re-run on failure; completed reduce output is safe on replicated HDFS. The master also runs backup ("speculative") tasks for the last few stragglers and takes whichever finishes first — taming the long tail.[1]

7 · Why disk round-trips make it slower than Spark

Here is the defining weakness. MapReduce materializes every stage boundary to disk: map output to local disk, reduce output to replicated HDFS.[1] A single map→reduce pass tolerates that. But real analytics and ML are iterative and multi-stage — chains of jobs, loops that reuse a dataset. MapReduce has no way to keep a working set in memory between steps, so every iteration pays a full round-trip to disk plus three-way replication. Spark's answer (last lesson) was to keep intermediates in memory across steps and recompute lost partitions from lineage instead of re-reading replicated disk — the same fault-tolerance guarantee, an order of magnitude less I/O.[4] That one difference is the whole story of why Spark replaced MapReduce for most jobs. See Lesson 101 — Apache Spark.

Word-count walkthrough

Counting words across a corpus — the "hello world" of MapReduce.
  • Input split: the corpus is blocks on HDFS; one map task per block, placed for data locality.
  • Map: for each line, emit (word, 1) for every word → ("the",1) ("cat",1) ("the",1)…
  • Combine (map side): sum locally → ("the",2) ("cat",1), shrinking what gets shuffled.
  • Partition: hash("the") mod R picks the reducer; all "the" pairs head to the same one.
  • Shuffle & sort: each reducer pulls its partition from every mapper; framework merge-sorts by key.
  • Reduce: reduce("the", [2, 5, 3, …]) sums to ("the", 4217), written to HDFS.

The Hadoop ecosystem

MapReduce is the paper; Hadoop is the open-source implementation, and over time it grew into a stack. Google's GFS, MapReduce, and Bigtable papers map almost one-to-one onto Hadoop's HDFS, MapReduce/YARN, and HBase.

LayerWhat it isGoogle ancestor
HDFSDistributed file system — durable storage for huge files on commodity disks.GFS[2]
YARNCluster resource manager — schedules compute (CPU/RAM) across the cluster.(borg-era schedulers)
MapReduce / HiveBatch compute engine; Hive adds SQL on top.MapReduce[1]
HBaseLow-latency wide-column store for random reads/writes on HDFS.Bigtable[3]

HDFS — the storage layer

HDFS splits each file into large blocks (default 128 MB) and spreads them across the cluster. The architecture is one master, many workers:[2]

  • NameNode — the master. Holds all metadata (the directory tree, which blocks make up each file, where each block lives) in memory. It never touches file data. Historically a single point of failure, later made highly available with a standby NameNode.
  • DataNodes — the workers. Store the actual blocks on local disk and serve reads/writes directly to clients, reporting block health back to the NameNode via heartbeats.
  • Block replication — each block is replicated (default ×3) across DataNodes, ideally across racks, so a disk or whole rack can die without data loss. This is durability-by-replication — and exactly the disk cost Spark's lineage model avoids paying on intermediate data.

YARN — the resource layer

Original Hadoop bolted scheduling onto MapReduce itself. YARN (Yet Another Resource Negotiator) split that out into a general cluster manager: a ResourceManager hands out containers (CPU/RAM) and a per-application ApplicationMaster negotiates and oversees its tasks. Decoupling resource management from the compute model is what let Spark, Flink, and others run on the same Hadoop cluster — YARN is one of the cluster managers Spark targets.

Hive — SQL over MapReduce

Almost nobody wants to hand-write map and reduce functions. Hive lets analysts write SQL against data in HDFS and compiles each query into one or more MapReduce (later Tez/Spark) jobs underneath. It brought a schema (the Hive metastore) and the familiar table abstraction to raw files — the conceptual seed of the modern SQL-on-the-lake / data-warehouse-on-object-storage pattern.

HBase — Bigtable-style wide-column store

MapReduce is batch: great throughput, terrible for a single random read. HBase fills that gap as an open-source Bigtable: a distributed, sorted, wide-column store layered on top of HDFS for low-latency random reads and writes.[3] Its data model is a sparse, multidimensional sorted map — rows keyed by a sorted row key, grouped into column families, with cell versions by timestamp. Tables are split into regions by row-key range and served by RegionServers; writes hit a write-ahead log plus an in-memory memstore, then flush to immutable SSTable/HFile files compacted over time — the LSM-tree pattern Bigtable introduced.[3] HBase is the random-access companion to HDFS's batch bulk store.

When it still matters — and why Spark replaced it for most jobs

MapReduce still earns its keep when…
  • The job is a single, enormous, one-pass batch over data far bigger than cluster RAM — a giant sort, a massive ETL scan — where in-memory caching buys nothing and rock-solid disk-spilling matters.
  • You're on a legacy Hadoop estate: existing Hive/MR pipelines, petabytes already on HDFS, jobs that simply work and aren't worth rewriting.
  • HDFS and HBase themselves remain widely deployed even where the MapReduce compute engine is gone.
…but Spark replaced it for most jobs because…
  • In-memory beats disk: iterative/multi-stage jobs (ML, graphs, chained ETL) avoid the per-step disk + replication round-trip — often an order of magnitude faster.[4]
  • Richer model: a general DAG of operators, not rigid map→reduce; plus SQL, streaming, and ML on one engine.
  • Better ergonomics: high-level DataFrame/SQL APIs vs hand-written Java map/reduce classes.
★ Staff-level signal Don't treat MapReduce as a relic to skip. Use it to justify your batch choice from first principles: "the model is map → shuffle/sort → reduce, and the cost concentrates in the shuffle, so I minimize data movement with a combiner / pre-aggregation." Then name the boundary: "MapReduce materializes every step to disk, so for our iterative feature pipeline I'd use Spark to keep working sets in memory and recover via lineage instead of paying the round-trip." Knowing that GFS→HDFS, MapReduce→Spark, and Bigtable→HBase are the same ideas re-implemented — and that HDFS/HBase outlived the MR compute engine — is the breadth that separates "I've used Spark" from "I understand why the field landed here." Re-explaining "map then reduce" is not the staff move; reasoning about the disk-vs-memory tradeoff is.

In the interview

You'll rarely propose MapReduce in a 2024-era design — but it's the lens that proves you understand batch processing rather than name-dropping Spark. It shows up in data-processing designs like the ad click aggregator (Lesson 36) as the conceptual model for the pre-aggregation layer. When it comes up:

  • Lead with the principle. "Move compute to data, express it as map → shuffle/sort → reduce." One sentence, then go to the hard part.
  • Name the shuffle. The interesting depth is "where does data cross the network, and how do I shrink it" — combiners, partitioning, skew. Same answer as Spark; show you know it's universal.
  • Justify Spark by the disk tradeoff. If asked why not MapReduce, say "iterative job → keep it in memory, recover via lineage" — not "Spark is newer."
  • Place HDFS/HBase correctly. HDFS = durable bulk store; HBase = low-latency random access; MapReduce/Spark = compute. Don't make a batch engine serve point reads. See the glossary.

Check yourself — retrieval practice

Answer from memory before scrolling back up.

1. What is the core idea that makes the MapReduce model scale to petabytes?

MapReduce ships the small program to the data (data locality) rather than moving heavy data to compute.

2. Which phase of a MapReduce job is the dominant cost, and why?

Shuffle & sort is the all-to-all network transfer plus merge-sort by key — the expensive part to minimize.

3. Why is Spark usually faster than classic MapReduce on iterative jobs?

MapReduce writes every step to disk; Spark caches in memory and recovers via lineage, not disk replicas.

4. In the Hadoop stack, what is HBase's role relative to HDFS?

HBase is an open-source Bigtable: a wide-column store on HDFS for low-latency random access (YARN schedules; Hive does SQL).

Primary source

Dean & Ghemawat, "MapReduce: Simplified Data Processing on Large Clusters," OSDI 2004. The original paper — the programming model, the master/worker execution flow, partitioning, the combiner, fault tolerance via re-execution, backup tasks, and data locality. Pair it with the GFS and Bigtable papers to see the full storage-plus-compute trilogy that Hadoop, HDFS, and HBase re-implemented.
