Design a Distributed Message Queue

Buffer work between producers and consumers so a burst, a slow worker, or a crashed worker never loses a message.

Why this lesson, for your mission: A message queue is the system whose entire value is delivery semantics under failure. Seniors describe "producers push, consumers pull." Staff candidates name the delivery guarantee out loud (at-least-once), explain why exactly-once delivery is impossible and that visibility timeout + idempotency is the real answer, and know exactly where this differs from a log like Kafka. Get those three moves right and you've passed the bar.

Functional Requirements

Mirror the Amazon SQS surface area — five operations, nothing more.[1]

The user should be able to…Detail
Create a queueProvision a named queue with config (visibility timeout, retention, FIFO vs standard).[1]
Send a messageA producer enqueues a message (payload up to a size cap) onto a named queue.[1]
Receive messagesA consumer pulls one or more available messages to process them.[2]
Delete / ack a messageAfter successful processing the consumer deletes the message so it is never redelivered.[2]
Delete a queueTear the queue down, discarding any messages still in it.[1]

Out of scope (say it aloud): the business logic inside the consumer, fan-out pub/sub to many subscribers (that's a topic/log — see Lesson 07), and message transformation. We move bytes from producer to consumer durably; the handler does the work.

Non-Functional Requirements

PropertyTarget / priority
DurabilityAn acknowledged send is never lost — persist + replicate before acking the producer. This is the whole point of a queue.
Delivery guaranteeAt-least-once by default: every message is delivered until a consumer deletes it; duplicates are possible and handled via idempotency.[2]
AvailabilityHighly available for both send and receive; favor availability over strict ordering for the standard queue (AP-leaning).
ScalabilityEffectively unbounded throughput for standard queues; horizontal scaling of producers and consumers.[3]
LatencyLow-latency send; receive uses long polling so consumers don't burn CPU spinning on an empty queue.[4]

The central tension is ordering vs. throughput. Strict global FIFO forces serialization and caps throughput; "best-effort order, unlimited scale" is the standard queue. We design the standard queue first, then show what FIFO costs.

Capacity Estimation

Estimate only the numbers that bend the design.

QuantityEstimateDesign implication
Throughput~100k–1M messages/sec across many queues, payload ~1 KBNo single broker holds it all — partition each queue across many brokers/shards. Throughput, not storage, is the driver.
In-flight retentionMessages held only until acked; unacked messages retained up to ~days[1]A queue is a buffer, not an archive. Steady-state storage is small; backlog from a dead consumer is the spike to plan for.
Backlog burstConsumer outage → minutes of arrivals pile up: 100k/sec × 600s ≈ 60M messagesMust spill to durable disk, not RAM. Buffering for a slow/down consumer is the explicit job — size storage for the outage, not the average.

The math that matters: volume is trivial to store but the working set must absorb a consumer outage without dropping anything. That pushes us to a durable, replicated, append-friendly store per partition.

Core Entities & API

Queue — a named, configured channel. Message — payload + metadata (id, receive-count, enqueue time). Receipt handle — a per-receive token a consumer must present to delete/extend a specific delivery, so a stale handle can't delete a message that has since been redelivered.[2]

EndpointPurpose
POST /v1/queuesCreate a queue: { name, fifo, visibilityTimeout, retention }. Returns queueUrl.
DELETE /v1/queues/{q}Delete the queue and discard its messages.
POST /v1/queues/{q}/messagesSend: { body, groupId? }. Returns messageId.
GET /v1/queues/{q}/messages?max=N&wait=20Receive up to N messages with long-poll wait seconds; returns bodies + receipt handles.
DELETE /v1/queues/{q}/messagesAck: delete by { receiptHandle } after successful processing.

The owning account is derived from the auth token, never sent in the body. Note there is no "consume" that both reads and deletes in one step — separating receive from delete is what enables redelivery.

High-Level Design

Trace each operation through the boxes. The hard part lives between "receive" and "delete."

ComponentRole
Producer/consumer SDKTalks HTTP to the front end; hides retries, batching, long-poll.
Front end / API gatewayAuth, rate-limit, route a queue to its partition(s) by consistent hash.
Metadata storeQueue configs, partition map, ownership. Small, strongly consistent (e.g. a coordination store).
Broker (per partition)Owns an ordered, durable commit log of messages; tracks in-flight + visibility per message; replicated.
ReplicasEach partition is replicated to N nodes; an ack to the producer waits for a write quorum.

Send flow: producer → front end routes to a partition → broker appends to the log, replicates to a quorum, then acks the producer (durable before ack). Receive flow: consumer long-polls → broker returns the next visible messages and marks each in-flight (invisible) for the visibility timeout, handing back a receipt handle. Delete flow: consumer finishes work → calls delete with the handle → broker removes the message. If delete never comes, the timeout expires and the message becomes visible again for redelivery.

★ Staff-level signal The interview turns on one sentence: receive does not delete — it hides. A message has a lifecycle (visible → in-flight → deleted, or back to visible on timeout), not a boolean. That single decision is what makes the queue tolerate a crashed consumer (at-least-once), and it forces the consumer to be idempotent. Everything below — ordering, replication, DLQ, scaling — is a refinement of that lifecycle.

Deep Dives

1 · Delivery semantics — why at-least-once + idempotency is the real answer

Three guarantees exist, and you must name which one you're building:

GuaranteeMechanismFailure mode
At-most-onceDelete on receive (fire-and-forget).Consumer crashes after receive, before processing → message lost.
At-least-onceVisibility timeout; delete only after success.[2]Consumer finishes, crashes before delete → message redelivered → duplicate.
Exactly-onceDedup + transactional commit of read+side-effect.Impossible across a network for delivery; achievable only for effect.

You cannot get exactly-once delivery: any ack can be lost in flight, so the sender must choose to retry (risking a duplicate) or not (risking a loss). The practical answer the interviewer wants: at-least-once delivery + idempotent consumers. The queue guarantees the message arrives; the consumer uses an idempotency key (e.g. messageId or a business key) so a duplicate is a no-op — giving exactly-once effect. SQS standard queues are explicitly at-least-once; FIFO queues add exactly-once processing via a dedup window, not magic.[2][5] This is the same reasoning as Lesson 07; revisit idempotency in the glossary if it's fuzzy.

Pick & justify: Default to at-least-once and push idempotency to the consumer. It's cheaper, more available, and composes — versus exactly-once "delivery," which doesn't exist and whose closest approximation (FIFO dedup) sacrifices throughput. Say the magic line: "at-least-once + idempotency ≈ exactly-once effect."

2 · The in-flight / visibility-timeout / ack lifecycle & the dead-letter queue

This is the engine room. When a consumer receives a message the broker doesn't delete it — it marks it in-flight and starts a visibility timeout, during which the message is hidden from other consumers.[2] Three outcomes:

Lifecycle outcomes:
  • Success → consumer calls delete with its receipt handle → message gone. The happy path.
  • Crash / slow → no delete before the timeout → message becomes visible again → redelivered. At-least-once in action.
  • Still working → a long job extends the timeout (heartbeat / change-visibility) so a healthy job isn't re-run beneath it.[2]

Set the timeout above the expected processing time. Too short → healthy work is redelivered and duplicated; too long → a real crash sits undetected and throughput stalls. A poison message (one that always fails, e.g. malformed) would otherwise loop forever, eating capacity. The fix is a dead-letter queue: track a per-message receiveCount, and after maxReceiveCount redrive the message to a separate DLQ for inspection instead of redelivering it endlessly.[6]

Pick & justify: Visibility timeout (not delete-on-read) + receipt handles + a DLQ after N attempts. This gives crash tolerance, prevents one bad message from starving the queue, and turns "stuck" into an observable, drainable thing. Add backoff between redeliveries so a flaky downstream isn't hammered.

3 · Ordering — FIFO vs standard, partitions & message groups

Global strict ordering and unlimited throughput are in tension: total order means a single serialization point. So queues offer two modes.

ModeOrder & dedupThroughput
StandardBest-effort ordering; at-least-once; duplicates possible.[3]Nearly unlimited — partition freely across brokers.
FIFOStrict order within a message group; exactly-once processing via a dedup window.[5]Bounded; order forces per-group serialization.

The unlock for FIFO scale is the message group ID: ordering is guaranteed only within a group, and different groups are processed in parallel.[5] Pick a group key that needs internal order but is independent of others — e.g. userId so one user's events stay ordered while millions of users run concurrently. This is the same partitioning idea as a Kafka partition key: order per key, parallelism across keys.

Pick & justify: Default to standard — most workloads only need at-least-once, not global order, and standard scales effortlessly. Reach for FIFO with a well-chosen group key only when a specific entity's events must not reorder. Don't buy global ordering you don't need; it's the most expensive guarantee on the menu.

4 · Durability & replication of the log; scaling consumers; push vs pull

Each partition is a durable, append-only commit log on disk, replicated to N nodes. A producer's send is acked only after a write quorum persists it, so a single node failure loses nothing; a leader serves reads/writes and a follower is promoted on failover. Appending to a log is sequential I/O — cheap and fast — which is why both queues and logs are built this way.

Scaling consumers:
  • Competing consumers — many consumers pull from one queue; each message goes to exactly one of them. Add consumers to drain a backlog; autoscale on queue depth / age of oldest message.
  • Long polling > short polling — a receive call waits up to ~20s for a message instead of returning empty immediately, cutting empty-receive cost and latency.[4]
  • Pull, not push — consumers pull at their own pace, so a slow consumer can't be overwhelmed (no backpressure problem); the queue is the buffer. Push (broker→consumer) gives lower latency but needs flow control.

Queue vs. log — the contrast to draw. A queue (SQS) has competing consumers and deletes on ack: once one consumer processes a message it's gone, so it's ideal for distributing work items. A log (Kafka) retains messages and tracks a per-consumer-group offset: many independent groups can each read the whole stream, and you can replay by rewinding the offset.[5] Choose a queue for task distribution and at-least-once work; choose a log for fan-out, replay, and event sourcing. The fuller treatment is in Lesson 07 and the technology survey in Lesson 09.

State the breadth/depth ratio aloud: you went deep on semantics, lifecycle, ordering, and durability — the parts that fail in production — and kept the API and routing shallow because that's not where this design breaks.

Check yourself — retrieval practice

Answer from memory before scrolling back up.

1. What does the visibility timeout actually do when a message is received?

Receive hides (in-flight) but never deletes; no delete before the timeout means the message is redelivered.

2. At-least-once delivery can produce duplicates. What makes that safe?

A duplicate becomes a no-op via an idempotency key — at-least-once + idempotency ≈ exactly-once effect.

3. How does a FIFO queue keep order yet still scale out?

Order is guaranteed only within a message group; distinct groups process in parallel for throughput.

4. What is the core difference between a queue and a log?

Queues delete acked work (competing consumers); logs retain and track per-group offsets for replay/fan-out.
