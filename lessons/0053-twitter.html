Design Twitter / X

A read-heavy timeline for hundreds of millions of users — where the interview lives or dies on how you handle the account that follows nobody's rules: the celebrity.

Why this lesson, for your mission: Twitter is the canonical "timeline fan-out" problem, and it's deceptively dangerous: the naive answer works for 99.9% of accounts and explodes on the other 0.1%. A senior recites "fan-out on write vs. read." A staff candidate derives the hybrid from the follower-count distribution, names celebrity fan-out as the bottleneck before the interviewer asks, and treats the push/pull threshold as a tunable knob, not dogma. This lesson trains the second behavior — and it shares its spine with Facebook News Feed and Instagram, so the patterns compound.

Functional Requirements

Scope ruthlessly. Four capabilities cover the core of a timeline product; everything else you name as out-of-scope so the interviewer sees you noticed it and chose to defer.

#Users should be able to…
1Post a tweet (text, optionally media) that their followers can see.
2Follow other users (a uni-directional follow edge).
3View a home timeline of tweets from people they follow, and page through it.
4Like / retweet a tweet (engagement that feeds both counts and ranking).

Out of scope: replies/threads, DMs, search, ads, notifications, follower-of-follower recommendations. State this explicitly so the interviewer knows the boundary is deliberate.

Non-Functional Requirements

NFRs set the targets the design must hit. For a timeline the dominant tension is the classic one — you trade consistency for availability and low read latency, because nobody is harmed by seeing a tweet a few seconds late.

PropertyTarget / priority
Read/write ratioRead-heavy — timelines are viewed far more than tweets are posted (on the order of 100:1 or more).
Timeline latencyLow — home-timeline read <200ms (p99 <500ms). This is the path that must feel instant.
AvailabilityHighly available, prioritized over strong consistency for the timeline.
ConsistencyEventual — a few seconds of tweet staleness in a timeline is fine.
ScaleHundreds of millions of users; follower counts span from zero to 100M+ for the largest accounts.

Capacity Estimation

Only compute numbers that change a decision. Two numbers matter here: can we afford to precompute timelines for everyone, and what is the write blast-radius of the worst-case poster? (Figures below are my own back-of-envelope estimates, not quoted from a source.)

Can we precompute (materialize) a timeline per user?

  • Keep ~800 recent tweet IDs per timeline; an ID + minimal metadata is ~few bytes, so a timeline is a few KB.
  • ~5KB × ~500M active users ≈ ~2–3 TB. That is trivially cheap on modern infra. Implication: precomputation is affordable — the constraint is write cost, not storage.

What is the write cost of a single tweet?

  • An average user posts → fan out to a few hundred followers. Cheap, bounded.
  • A celebrity with 100M followers posts → fan out to 100M timelines in one shot. Implication: one tweet can trigger ~100M writes — this is the bottleneck the whole design must answer.

Tweet ingest: even hundreds of millions of tweets/day is only thousands of writes/sec on average — small. Implication: the system is not write-throughput-bound on tweets; it is bound by fan-out amplification at the tail.

Core Entities & API

Three core entities. Note that Follow is a uni-directional edge — modeling it as a directed graph is what later lets you query "who follows X" cheaply, which fan-out depends on.

EntityShape
UserAn individual account, with a cached followerCount (drives the push/pull decision).
FollowDirected edge: (followerId → followedId).
TweetContent with id, authorId, body, media?, createdAt.

Derive the acting user from the auth token, never from the request body.

EndpointPurpose
POST /v1/tweetsCreate a tweet. Body: { body, media? }; author from token.
POST /v1/followFollow a user. Body: { followedId }.
POST /v1/tweets/{id}/likeLike (or unlike) a tweet; idempotent per user.
POST /v1/tweets/{id}/retweetRetweet — creates a tweet referencing the original.
GET /v1/timeline?cursor=&pageSize=Read the home timeline. Returns { items: Tweet[], nextCursor }.

The timeline uses a cursor, not an offset — a constantly-growing list makes offset paging produce duplicates and skips. (See Lesson 16 for the full cursor-vs-offset deep dive; we won't repeat it here.)

Data Flow

Twitter is a feed-generation pipeline, so it's worth tracing the lifecycle of a single tweet end to end before we draw boxes.

  1. Write: client → POST /tweets → Tweet Service persists the tweet to the Tweet Store, returns 200.
  2. Fan-out decision: service emits a tweet-created event to a queue. Workers look up the author's followerCount: below threshold → push; above → skip fan-out and mark the author as a "pull" source.
  3. Materialize: for push authors, workers append the tweetId into each follower's timeline cache entry.
  4. Read: client → GET /timeline → Timeline Service reads the precomputed list from cache, merges in recent tweets from the celebrities this user follows (pulled live), ranks, hydrates bodies, returns a page.

The asymmetry is the whole story: the write path does the heavy lifting for normal authors so the read path stays a near-instant lookup — except for the celebrity tail, which we deliberately invert.

High-Level Design

Trace each request through the boxes. Keep the HLD simple by default; the cleverness belongs in the deep dives, not here.

ComponentResponsibility & store
Tweet ServiceStateless service behind the gateway. Writes tweets to the Tweet Store (e.g. Cassandra/DynamoDB, keyed by tweetId; partition by author for author-timeline reads).
Follow / Graph ServiceStores follow edges. Partition key follower, sort key followed; plus a reverse index on followed for "who follows X" (the list fan-out walks).
Fan-out workersConsume the tweet-created queue (Kafka) and append tweetId into each follower's timeline — for push authors only.
Timeline cacheRedis holding the materialized per-user timeline (a capped list of tweet IDs). The hot path for reads.
Timeline ServiceServes GET /timeline: read precomputed list, merge in celebrity pulls, rank, hydrate, paginate.
Engagement ServiceHandles likes/retweets; stores counts (often in a counter store) and feeds ranking signals.

Write path: POST /tweets → Tweet Store → emit event → fan-out workers append to follower timelines (push authors). Read path: GET /timeline → Timeline Service reads the cached list → merges recent celebrity tweets → ranks & hydrates → returns a page.

Deep Dive 1 — Fan-out on write vs. fan-out on read

This is the heart of the problem. "Fan-out" = the work of getting one tweet in front of N followers. The only question is when you do it: at write time (push) or at read time (pull).

Fan-out on read (pull)

Store nothing extra. When a user opens their timeline, look up everyone they follow, gather each one's recent tweets, merge, and sort. Writes are trivial — one insert. Reads are brutal: a user following 1,000 accounts fans a single read into 1,000 sub-queries plus an in-memory merge, all inside a sub-200ms budget. Wrong for a read-heavy product as the default.

Fan-out on write (push)

When a tweet is created, immediately append its tweetId into every follower's materialized timeline (via the queue + workers). Reads become a single list lookup — blazing fast, exactly what a read-heavy system wants. The cost moves to write time and to storage (the ~2–3TB above — cheap).

DimensionFan-out on write (push)Fan-out on read (pull)
Read latencyFast — one list lookupSlow — N lookups + merge
Write costHigh — write to N timelinesCheap — one insert
Write amplification1 tweet → N writes1 tweet → 1 write
StorageHigher (materialized lists)Minimal
Worst caseCelebrity tweets (100M writes)Heavy followers (1000s of reads)
Best forRead-heavy, normal fan-outInactive users / huge authors

Why neither alone wins. Push gives the latency we need but detonates on celebrities (100M writes per tweet). Pull stays cheap on writes but blows the read budget for active users (1,000-way merge per open). The follower-count distribution is bimodal — hundreds of millions of normal accounts, a tiny tail of enormous ones — so a single uniform strategy is wrong by construction.

Deep Dive 2 — The hybrid & the celebrity problem (the staff answer)

The judgement call: push for the rest, pull for the huge accounts. Don't fan out a 100M-follower tweet to 100M timelines. Instead, flag high-follower accounts, skip precomputation for them, and merge their recent tweets in at read time.

  1. On post: if the author's followerCount is below a threshold → fan out on write (push to all follower timelines). If above → do not fan out; just persist the tweet and mark the author as a pull source.
  2. On read: load the user's precomputed timeline, look up the small set of celebrities this user follows, pull their recent tweets, and merge-sort the two streams.

The merge is cheap because a single user follows only a handful of celebrities — the expensive list (their normal follows) is already materialized, and the tiny list (celebrities) is gathered live. You've moved exactly the bimodal tail to the strategy that suits it.

★ Staff-level signal The senior says "use a hybrid." The staff candidate explains why the threshold exists at all: it's a knob set by the follower-count distribution, not a magic number. They say out loud, "Push is correct until write amplification exceeds the read cost it saves — which happens precisely at celebrity scale, so I move that tail to pull." They name the celebrity fan-out as the real bottleneck, size it (~100M writes per tweet), and design around that tail rather than the average case — and they admit they'd measure the threshold in production (and even make it per-account adaptive) rather than hard-code it.

Deep Dive 3 — Storing tweets & the social graph

The tweet store

Tweets are immutable, append-only, and read by ID or by author. A wide-column store (Cassandra) or a key-value store (DynamoDB) fits: partition by authorId with createdAt as the clustering key, so "recent tweets by author X" — exactly what celebrity pull needs — is a single efficient range scan. The timeline cache holds only IDs; bodies are hydrated from this store on read, kept hot behind a tweet-level cache.

The social graph

The graph is two adjacency lists per relationship: following (who I follow — read on timeline assembly) and followers (who follows me — walked during fan-out). Store both directions so each query is a cheap lookup rather than a scan. At Twitter scale this is a partitioned store with a reverse index; a dedicated graph database is usually overkill for a follow graph this shallow — name that tradeoff rather than reaching for Neo4j reflexively.

DataAccess patternStore choice
TweetsBy id; recent-by-author range scanWide-column / KV, partition by author
Follow graphBoth directions, cheap lookupsPartitioned KV + reverse index
Materialized timelineRead constantly, append on fan-outRedis (capped list of IDs)

Deep Dive 4 — Timeline cache, hot accounts & trending

Caching the timeline

Hold each materialized timeline as a capped list in Redis (e.g. last ~800 IDs, trimmed on insert) with LRU eviction, so the common read never touches a database. Timelines are the perfect cache citizen — read constantly, written by fan-out workers, and tolerant of the few-seconds staleness we already accepted. For users who haven't logged in for months, skip materialization entirely and reconstruct on demand (pull) — there's no point burning writes on a timeline nobody reads.

Hot / celebrity accounts on the read side

A viral tweet is read by millions at once. In a sharded tweet cache, that single tweetId lives on one node, which melts while the rest sit idle — a hot key. Replicate the hottest tweets so every node can serve them and the load balancer spreads the read storm across all N. The one-time cost is N cold misses on first read; the steady-state win is enormous. (Same hot-key fix as Lesson 16.)

ApproachBehaviorVerdict
Sharded cacheEach tweet on one node — viral tweet melts that shard.Hot key
Replicated cacheAny node serves the tweet; reads spread across all N.Great

Trending

"What's trending" is a different problem from the timeline: it's a top-K over a stream of hashtags/terms in a sliding window, not per-user materialization. You don't compute it exactly over the firehose — you approximate (e.g. Count-Min Sketch for frequencies, a heap for the current top-K) per region and window. We have a whole lesson on this exact machinery — see Lesson 28 · Top-K — so in an interview you'd name it, sketch the streaming-approximation approach, and move on rather than rebuilding it inline.

★ Staff-level signal Notice that celebrity fan-out (write side), the viral hot-key tweet (read side), and trending (stream side) are three faces of one phenomenon — extreme popularity skew — attacked in three places. Staff candidates connect them: pull-on-read tames skew at write time, cache replication tames it at read time, and approximate top-K tames it on the stream. Recognizing that one long-tail distribution drives all three bottlenecks — and that each is solved on its own side rather than by one grand mechanism — is the unifying insight.

Check yourself — retrieval practice

Answer from memory before scrolling back up.

1. Why is pure fan-out on write a poor fit for celebrity accounts?

Storage is cheap (~2–3TB). The killer is write amplification: one celebrity tweet → ~100M timeline writes.

2. What hybrid strategy do staff candidates arrive at for Twitter?

Normal authors are precomputed (push); celebrity tweets are pulled live and merged in — driven by the follower distribution.

3. Why partition the tweet store by author with createdAt clustering?

Celebrity pull asks for an author's recent tweets at read time — author partition + time clustering makes that a cheap range scan.

4. How is "trending" fundamentally different from the home timeline?

Trending is top-K over a sliding window of terms — solved with streaming approximation (Count-Min Sketch + heap), not per-user fan-out.
