Design a Web Search Engine (Google Search)

Take tens of billions of crawled pages and answer any keyword query, ranked, with snippets, in under 200 ms.

Why this lesson, for your mission: Web search is the hardest read-path interview there is: an enormous, sharded inverted index, a brutal latency budget, and ranking that has to be both good and cheap. The L6/L7 signal is whether you can derive the mechanics under "just use a search cluster" — the inverted index built from the crawl, why the index is partitioned by document, the scatter-gather fan-out it forces, and multi-stage retrieve-then-rerank — rather than naming a product. Crawling is its own problem; here we assume the corpus exists (Lesson 35) and focus on indexing, serving, and ranking.

Functional Requirements

State the scope tightly, then defend the boundary. The corpus arrives from the crawler[1] — we do not crawl here.

#The user should be able to…
1Submit a keyword query and get a ranked list of matching web pages.
2Paginate through results (next page / more results) deterministically.
3See a title + snippet (the matching passage, terms highlighted) for each result.

Out of scope (name them, then drop them): crawling the web (see Lesson 35), spell-correction/autocomplete, ads, personalization, images/video verticals, and full anti-spam. We index a known corpus and serve ranked text results.

The two tensions to name up front.
  • Latency vs. corpus size — you cannot scan tens of billions of docs per query, so everything hinges on the inverted index living mostly in memory.
  • Relevance vs. latency — the best ranking signals are expensive, so you can only afford them on a tiny candidate set — the seed of multi-stage ranking.

The punchline: read-heavy + brutal latency + a corpus too big for one node. That trio forces a sharded, mostly-in-memory inverted index served by scatter-gather, and ranking split into cheap-then-expensive stages.

Core Entities & API

Entities: Document (docId, URL, title, text, plus static signals like pageRank), Term → PostingList (the inverted index entry: docIds + positions + per-doc weight), and the transient Query.

EndpointPurpose
GET /v1/search?q=&cursor=&n=Ranked results. cursor for pagination, n page size. User (if any) derived from auth token, never the body.
GET /v1/results/{docId}/snippet?q=Generate/return the query-specific snippet for one result (often inlined in search).
POST /v1/index/documentsInternal: indexer ingests a crawled+parsed doc into the inverted index.
DELETE /v1/index/documents/{docId}Internal: drop a dead/de-indexed URL (tombstone, compacted later).

Note cursor, not page: with an index changing under you and ranking that varies, offset pagination double-shows or skips results. Encode the last (score, docId) seen into an opaque cursor — the staff-correct choice for a live, ranked corpus, exactly as in Lesson 25.

Data Flow — the indexing pipeline (doc → searchable)

This is a data-processing system, so trace one crawled page from the corpus to being queryable. Indexing is offline/streaming and decoupled from serving.

  1. Source: the crawler (Lesson 35) drops raw HTML + extracted text into blob storage and emits a "doc ready" event.[1]
  2. Parse & tokenize: strip boilerplate, lowercase, split on whitespace/punctuation, drop stop-words, stem ("running"→"run") — same analysis chain as Lesson 25.[2]
  3. Build postings: for each term, append docId (with positions + a term weight) to that term's posting list; this is index construction.[2]
  4. Compute static signals: precompute query-independent scores per doc — PageRank from the link graph, plus length, language, spam score.[1]
  5. Publish segments: build immutable index segments and ship them to the document shards; deletes are tombstones, merged away during compaction.[2]

Because indexing is offline and append-mostly, the serving path never blocks on writes — fresh segments are swapped in. PageRank is computed in batch over the whole link graph, so it lags the crawl by design; freshness for new pages comes from the streaming indexer, not from recomputing global signals.

Deep Dive 1 — The inverted index, built from the crawl

Don't say "use a search cluster" and move on — explain what it's doing. A forward index maps document → terms; searching it means scanning every doc, impossible at tens of billions. An inverted index flips it to term → posting list, the set of docIds containing that term, usually with term positions and a per-doc weight.[2] Brin & Page's original Google design stored exactly this — posting lists in "barrels" plus a lexicon of terms.[1]

"search"  → [(d12, tf=4, pos=[3,40,..]), (d88, tf=1), (d903, tf=7), ...]
"engine"  → [(d12, tf=2), (d88, tf=3), (d51, tf=1), ...]
"index"   → [(d12, tf=9), (d903, tf=2), ...]

A single-word query is now a posting-list read, not a corpus scan. A multi-word query is an intersection (AND) of posting lists — and posting lists are stored sorted by docId precisely so intersection is a linear merge. Term positions enable phrase queries ("web search engine" as a phrase) and, at serve time, snippet generation — find the doc passage where the query terms cluster and highlight them. Postings are heavily compressed (delta-encode docId gaps) so the hot index fits in memory.[2] The inverted-index basics carry straight over from Lesson 25; what's new here is scale and ranking.

Deep Dive 2 — Sharding the index: document vs. term, and scatter-gather

The index doesn't fit on one node, so it must be partitioned. There are exactly two ways, and naming the tradeoff is the staff signal — same fork as Lesson 25, but web-scale makes the answer sharper.[2]

Term-partitioned (by keyword)Document-partitioned (by docId)
LayoutEach shard owns some terms; that term's entire posting list lives there.Each shard owns some docs and a full mini-index over only those docs.
Query workRoute to the few shards holding the query terms — low fan-out.Scatter to every shard, each searches locally — high fan-out.
Hot-spot riskSevere — a common term ("the") is one colossal list on one node.Low — load and storage spread evenly across all shards.
Multi-term queriesCross-node posting-list shipping to intersect — network-heavy.Intersection is local within each shard — no cross-shard traffic.
Indexing a new docOne doc touches many term-shards (a write per term).One doc → one shard. Simple, local, parallel.
The pick: document-partitioned, the standard choice for web search.[2] You accept fan-out (every shard hit per query) to win even load, local intersection, simple indexing, and no catastrophic term hot-spots. The fan-out cost is paid with scatter-gather:
  • Scatter: the coordinator sends the query to all (or a tier of) shards in parallel.
  • Local top-K: each shard ranks its own docs and returns just its top K — tiny payloads.
  • Gather + merge: the coordinator does a k-way merge into a global top-K, then re-ranks.

Real systems add a hierarchy: a root coordinator over leaf shards, often grouped into intermediate aggregators so the merge itself fans out. Latency is bounded by the slowest shard — picked up in DD4.

Deep Dive 3 — Ranking: multi-stage retrieve-then-rerank

Returning matches is easy; returning the best matches in tens of ms is the whole game. You cannot run an expensive scorer over a million-entry posting list per query, so ranking is staged: cheap recall first, expensive precision last.

Stage 0 — query-independent signals

Some signals don't depend on the query and are precomputed per doc: the headline one is PageRank, which scores a page by the link structure of the web — a page is important if important pages link to it.[1] Stored in the static-signal store and folded in at rank time.

Stage 1 — retrieval / first-pass scoring (cheap, per shard)

Each shard scores its local matches with a cheap text-relevance function over the posting list. The standard is BM25 (Okapi BM25): a refinement of TF-IDF that rewards term frequency with diminishing returns and normalizes for document length, so long docs don't win just by being long.[3] The point of this stage is recall: get a few hundred plausible candidates per shard fast, not perfect order.

score(d) ≈ Σ_terms  IDF(t) · ( tf(t,d)·(k+1) ) / ( tf(t,d) + k·(1 − b + b·|d|/avgLen) )
            └ rarer terms count more ┘   └ TF saturates ┘   └ length-normalized ┘

Stage 2 — re-ranking (expensive, on the candidate set)

The merged global candidate set (say a few hundred to a few thousand docs) is small enough to score with rich, costly signals: a blend of BM25 + PageRank + freshness + (in modern systems) a learning-to-rank model or neural ranker. Only the final top N survive.[2]

★ Staff-level signal The retrieve-then-rerank split is the lever that makes web ranking affordable: BM25 over posting lists is cheap and runs on every shard for recall; the expensive model runs once, on a few thousand merged candidates, for precision. Saying "we'd run an ML ranker" is senior; explaining why it can only run on the candidate set after scatter-gather merge — and that PageRank is a precomputed static signal, not a per-query cost — is staff. Naming a modern third tier (below) unprompted seals it.
Modern semantic tier (bonus depth). Lexical BM25 misses synonyms ("car" vs "automobile"). Add embedding retrieval: encode docs and the query into vectors and do approximate nearest-neighbor search in a vector database (Lesson 40) as a parallel first-stage retriever, then merge its candidates with the BM25 candidates before re-ranking. This "hybrid retrieval" is how current search blends keyword and semantic matching.

Deep Dive 4 — Serving latency budget & the tiered index

The 200 ms p99 budget with fan-out to thousands of shards is the real engineering problem. Three moves.

Keep the hot index in memory; tier the rest

RAM access is ~100× faster than SSD, so the index that serves the latency-critical path lives in memory. But tens-to-hundreds of TB in RAM is brutally expensive, so use a tiered index: a small hot tier (high-PageRank / frequently-matched docs) fully in memory answers most queries; a larger cold tier on SSD is consulted only when the hot tier lacks enough good results.[2] Most queries terminate in the hot tier, so average latency tracks RAM, not disk.

Tame the tail (slowest-shard problem)

With high fan-out, the query is as slow as its slowest shard — a tail-latency trap. Mitigations: hedged/backup requests (re-issue to a replica if a shard is slow and take the first reply), and return-after-N-of-M (respond once enough shards have answered, tolerating a tiny completeness loss for a big p99 win).

Cache the Zipfian head

Query traffic is heavily skewed — a small set of queries repeats constantly. A distributed query-result cache (and CDN/edge layer) with a short TTL matched to the freshness budget deduplicates the popular head, dropping their latency to a few ms and shielding the shards from most QPS.

TechniqueWhat it buys
Tiered index (hot RAM / cold SSD)Most queries answered at memory speed without paying to keep all of it in RAM.
Hedged requests / N-of-Mp99 decoupled from the single slowest shard.
Query-result cache + CDNPopular-query latency in ms; massive QPS relief on the index fleet.

Check yourself — retrieval practice

Answer from memory before scrolling back up.

1. What is an inverted index in a web search engine?

Inverted = term → posting list of docIds, turning a corpus scan into a posting-list read and intersection.

2. Why shard the web index by document rather than by term?

Doc-partitioning spreads load evenly and keeps intersection local; the cost it accepts is scatter-gather fan-out.

3. How does multi-stage ranking keep top-result quality affordable?

Stage 1 BM25 gives cheap recall per shard; stage 2 runs the expensive ranker once on the merged candidates.

4. Why keep hot index shards in RAM and cache popular queries?

A skewed (Zipfian) head means caching + a hot in-memory tier serve most traffic at memory/ms speed, taming p99.
