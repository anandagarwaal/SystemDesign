Design Tinder

A geo-bounded swipe feed, a billion writes a day, and a match that must never go missing.

Why this lesson, for your mission: Tinder looks deceptively simple — show profiles, swipe, match. The L6/L7 signal is recognizing that the simple-looking parts hide three hard problems: a geospatial candidate index, a write-heavy swipe store at billions of ops/day, and a correctness guarantee (a mutual like must become a match). Pick the right primitive for each, and justify when you can trade exactness for scale.

Functional Requirements

Scope tightly. Three core flows carry the whole interview; everything else (messaging, super-likes, boosts) is out of scope unless prompted.

#Users should be able to…
1Create a profile and set match preferences (age range, max distance, interested-in).[1]
2See a stack of nearby candidate profiles that match their filters, ordered for swiping.[1]
3Swipe left (no) or right (yes) on a candidate.[1]
4Get a match (and a notification) when two users like each other.[1]

Out of scope: chat/messaging, media upload pipeline, recommendation ML ranking, payments. Name them, then set them aside.

Non-Functional Requirements

These are the constraints that actually shape the architecture. State a target for each.

Low-latency feed< 300 ms to serve the stack[1]Can't query-time scan all users by geo + age; needs an index or precompute.

Note the tension: the swipe path wants strong consistency (matches), while the feed path wants low latency and tolerates eventual consistency (a slightly stale candidate is fine).

Capacity Estimation

Only the numbers that change a decision. Anchor on swipe volume — it's the headline.

  • DAU: ~20M active users.[1]
  • Swipes: ~100 swipes/user/day → 2B swipes/day ≈ 23K writes/sec average, call it ~70K/sec peak.[1] → Implication: a write-optimized, horizontally sharded store (Cassandra-class), not a single SQL primary.
  • Swipe storage: a swipe row ≈ {actorId, targetId, dir, ts} ≈ ~50 bytes. 2B/day ≈ 100 GB/day ≈ ~36 TB/year. → Implication: sharded storage + TTL/archival on old swipes.
  • Feed reads: each user fetches a stack of ~25–50 candidates many times/day → read-heavy on the candidate index. → Implication: the geo index must serve fast, bounded queries.

High-Level Design

Trace each request through the boxes. Two clear paths: the read path (recommendations) and the write path (swipes → match).

Deep Dive 1 — Generating the recommendation stack

The naive query is the trap: SELECT * FROM users WHERE age BETWEEN ? AND ? AND lat BETWEEN ? AND ? scans far too much and is slow.[1] We need a real geospatial index plus precompute decisions.

Geo filtering: pick the primitive

ApproachHowWhen
GeohashEncode lat/long into a string prefix; nearby points share prefixes. Query the cell + 8 neighbors.Simple, works on any KV/SQL store with a B-tree index. Good default.
Redis GEOBuilt-in sorted-set geo (GEOADD/GEOSEARCH) — geohash under the hood, in memory.Fast radius queries, low latency; great fit for a hot, frequently-updated index.
QuadtreeRecursively subdivide space; dense areas get deeper nodes.When density is wildly uneven (a city vs. rural) and you want adaptive cell sizes.

Precompute vs. query-time

Hybrid wins.
  • Precompute (cache): a background job builds each active user's stack ahead of time and serves it instantly on app open.[1]
  • Query-time fallback: when the cached stack is exhausted, query a geospatial index (e.g. Elasticsearch / Redis GEO) live.[1]
  • Staleness control: short TTL (< 1 hour) on cached stacks; invalidate on location/preference change.[1]

Deep Dive 2 — Detecting a mutual match

The whole product hinges on this not being missed. Model the match as a reverse lookup, not a join.

The simple mental model

On POST /swipes {targetId, dir:"right"}: persist the swipe, then check whether the target already swiped right on me. If yes → create a Match and notify both. That's it — no batch job, no graph traversal.

The consistency problem

Two users can swipe right on each other at nearly the same instant. With naive independent writes, each read can miss the other's not-yet-committed swipe → a match is silently lost.[1]

Make the pair-write atomic. Route both directions of a pair to the same place using a canonical key — sort the two ids: swipe:{min(a,b)}:{max(a,b)}. Then set-my-swipe-and-check-the-other in one atomic step (e.g. a Redis Lua script, or a conditional write on a single partition).[1] Because both writers touch the same key, the second one deterministically observes the first → the match is created exactly once.
  • Durability: keep the authoritative swipe log in Cassandra; use the atomic structure for the match decision.[1]
  • Idempotency: creating the Match keyed on the same canonical pair makes re-delivery safe.
★ Staff-level signal Don't reach for distributed transactions or a saga here. The match check is just a reverse lookup on a single, canonically-keyed partition — co-locate both swipes of a pair and the consistency problem evaporates. Articulating that the hard-looking "consistent match" requirement collapses into a same-shard atomic op is exactly the judgement that separates senior from staff.[1]

Deep Dive 3 — Never showing the same profile twice

The seen-set is per-user and grows forever (every swipe adds to it). At 100 swipes/day, a long-time user has tens of thousands of seen ids — too much to ship to the client or scan on every feed call.

StrategyGuaranteeCost
Exact set in swipe DBPerfect — query "have I swiped X?"Exact but heavy: a lookup/filter against a growing store per candidate.
Client-side recent cacheCovers the last K swipes cheaply.Bounded; doesn't cover deep history.[1]
Bloom filter (server)No false negatives — a swiped profile is never shown.Tiny memory; small false-positive rate occasionally hides an unseen profile.[1]
★ Staff-level signal Recognize that exactness isn't required here. A Bloom filter per user is the right call: it guarantees you never re-show a swiped profile (no false negatives), and the only failure mode is occasionally skipping a valid candidate (a false positive) — invisible in a feed of millions. Trading a sliver of recall for orders-of-magnitude less memory is the probabilistic-structure judgement L6/L7 wants to hear.[1]

Deep Dive 4 — Scaling the swipe write volume

2B swipes/day is the dominant load.[1] A single relational primary can't absorb ~70K writes/sec — choose a write-optimized, horizontally scalable store.

Cassandra, sharded by user.
  • Why Cassandra: LSM-tree storage = cheap, fast appends; linear horizontal scaling; no single write bottleneck.[1]
  • Partition key = actorId: a user's swipes co-locate, so "did I swipe X?" reads hit one partition. Spreads write load evenly across the ring.
  • Tune for writes: high write CL is unnecessary for the log itself; the match decision is handled by the atomic pair-key path (Deep Dive 2), so the durable log can favor availability.
  • TTL/archival: old swipes can age out of hot storage to keep partitions lean (~36 TB/year otherwise).

Separating the two stores is the point: the Swipe log (Cassandra) optimizes for throughput and durability; the match-decision structure (atomic, canonically-keyed) optimizes for correctness. Different requirements, different tools.

Check yourself — retrieval practice

Answer from memory before scrolling back up.

1. Why route both directions of a pair to one canonical key on a swipe?

Sorting ids into one key co-locates both swipes, so the second writer deterministically sees the first — the match check becomes a same-shard atomic op.

2. Why is a Bloom filter acceptable for the per-user seen-set?

A Bloom filter has no false negatives — a swiped profile is never re-shown. Its only cost is rare false positives (skipping a valid candidate), which is invisible at feed scale.

3. Why choose Cassandra sharded by actorId for the swipe log?

LSM-tree appends absorb ~70K writes/sec with linear scaling; partitioning by actorId co-locates a user's swipes and spreads write load evenly.

4. Why precompute candidate stacks instead of always querying live?

Precomputed stacks serve instantly on open (< 300 ms), with a live geo-index query as fallback when the cache is exhausted; short TTLs bound staleness.
