Deep Dive: PostgreSQL

The relational default that scales further than people think — and the one ceiling you must name before they make you.

Why this lesson, for your mission: At L6/L7 it is not enough to say "I'll use Postgres." The interviewer wants to know that you understand why it stays correct under concurrency (MVCC), what that costs you (bloat, VACUUM), how you read fast (the right index), how you survive a crash (the WAL), and exactly where the single-primary write path runs out of road. Naming that ceiling before you're cornered is the move that reads as staff.[1]

1 of 5

What it is & the data model

PostgreSQL is an open-source object-relational database: data lives in tables of typed rows, you query it with SQL, and it gives you the full relational toolkit — joins, foreign keys, constraints, and transactions.[1] Its defining promise is ACID: every transaction is Atomic (all-or-nothing), Consistent (constraints always hold), Isolated (concurrent transactions don't corrupt each other), and Durable (a committed write survives a crash).[2] That is why it is the safe default for anything where correctness matters — orders, payments, balances, inventory.

What lifts it above a plain SQL store is the richness of its type system and extensibility. Beyond numbers and text it ships native JSONB (binary, indexable JSON), arrays, ranges, full-text search vectors, and first-class geospatial types via PostGIS.[3] So the lazy "I need flexible documents, so NoSQL" reflex is often wrong — JSONB lets one engine hold both your relational core and a semi-structured blob, indexed and transactional. See Lesson 03 for the relational-vs-document framing this builds on.

Internals — the part that earns depth

MVCC: how concurrency stays correct

Postgres uses Multi-Version Concurrency Control. A write never overwrites a row in place — it writes a new version of the row and marks the old one as still-visible-to-older-transactions.[4] Each transaction sees a consistent snapshot of the data as of the moment it started, so readers never block writers and writers never block readers.[4] That is the property that makes Postgres feel fast and safe under concurrent load: a long analytics read doesn't freeze the checkout path.

The consequence you must name: those old row versions ("dead tuples") don't vanish on commit. They pile up until VACUUM reclaims them; autovacuum runs this in the background.[5] If a table churns faster than VACUUM keeps up — or a long-running transaction holds an old snapshot open — you get table and index bloat: wasted disk, slower scans, and in the worst case transaction-ID wraparound pressure. Knowing that MVCC's elegance is paid for by VACUUM is exactly the cause-and-cost reasoning interviewers probe for.

Indexes: B-tree and its specialized cousins

The default index is a B-tree: balanced, ordered, ideal for equality and range lookups (=, <, >, BETWEEN, ORDER BY).[6] But the staff-level vocabulary is the specialized index types Postgres offers when a B-tree is the wrong shape:

IndexBuilt forTypical use
B-treeOrdered scalar valuesEquality & range; the default[6]
PartialA filtered subset of rowsIndex only WHERE status='active' to keep it tiny[6]
GINValues containing many itemsJSONB, arrays, full-text search[7]
GiSTGeometric / nearest-neighbourGeospatial, ranges, similarity[7]

The reflex to show: a partial index on a hot subset (e.g. unshipped orders) is smaller, fits in cache, and is faster than indexing the whole table — a cheap, high-signal optimization.[6]

MVCC leaves dead tuples behind; if churn outpaces autovacuum, table and index bloat grows.

If autovacuum were disabled entirely on a busy table, what would you expect to happen over time?

The WAL: durability and crash recovery

Before any change touches the actual data files, Postgres first appends a record describing it to the Write-Ahead Log and flushes that to disk.[8] The rule is simple: log first, then apply. If the server crashes mid-write, recovery replays the WAL to bring the data files back to a consistent committed state — that is the "D" in ACID made concrete.[8] The same WAL stream is what feeds replication (below), so one mechanism delivers both crash safety and replicas.

Isolation levels

SQL defines a ladder of isolation, trading strictness for concurrency. Postgres's default is Read Committed; you can opt up to Repeatable Read or Serializable when an operation must behave as if it ran alone.[9]

LevelPreventsNote
Read CommittedDirty readsThe default; each statement sees latest commits[9]
Repeatable Read+ non-repeatable readsSnapshot fixed at first read[9]
Serializable+ phantoms / write skewStrictest; may abort with a serialization error[9]

Staff signal: know that Serializable doesn't lock everything — it detects conflicts and asks the loser to retry, so your app must handle serialization-failure retries.[9]

Check yourself

Under Postgres's write-ahead logging, what happens before a change touches the actual data files?

Log first, then apply. On crash, Postgres replays the WAL to reach a consistent committed state.

Why must an application be ready to retry under Serializable isolation, unlike Read Committed?

Postgres implements Serializable via conflict detection, not universal locking — a transaction can be aborted with a serialization error and must be retried by the app.

Scaling & replication

Postgres replicates by shipping its WAL. Two flavours matter:

  • Streaming (physical) replication — a standby replays the primary's WAL byte-for-byte, producing an identical copy. Great for read replicas and failover; it copies the whole cluster and both sides must run the same major version.[10]
  • Logical replication — decodes the WAL into row-level changes published per-table. It can replicate a subset of tables across major versions, which makes it the tool for zero-downtime upgrades, partial replication, and feeding downstream systems / CDC.[11]

Read replicas let you fan out read traffic to standbys, which is how a single Postgres serves enormous read volume — but replication is asynchronous by default, so replicas lag and a read-after-write may see stale data. This is the same consistency tradeoff covered in Lesson 06. Partitioning splits one big logical table into smaller physical child tables (by range or hash), so queries and VACUUM touch less data and old partitions drop cheaply.[12]

The write-scaling ceiling — name this before they make you
  • Vanilla Postgres has one primary that accepts all writes. Read replicas scale reads; they do not scale writes.[10]
  • You climb a long way first: bigger box (vertical scale), partitioning, connection pooling, offloading reads to replicas.
  • You outgrow it when sustained write throughput or dataset size exceeds one primary. Then you shard — app-level, or with Citus — or move that workload to a write-optimized store (Cassandra/Dynamo, see Lesson 09).
  • Honest framing: "Postgres isn't the bottleneck until billions of rows or sustained high write QPS" — don't shard prematurely.[1]

5 of 5 — comprehensive check

★ Staff-level signal Seniors say "use Postgres." Staff candidates reason about the internals and their costs in one breath: "MVCC lets the analytics read run without blocking checkout, but it generates dead tuples, so I'd watch autovacuum and add a partial index on the hot subset." And they name the ceiling proactively: "this stays on a single primary; reads fan out to replicas, and the day sustained write QPS outgrows one box I'd partition first and shard only if forced — I wouldn't shard on day one."[1] Reaching for Postgres by default, knowing precisely why and when it breaks, and refusing to over-engineer is the simple-by-default judgement the bar looks for.

In the interview

When you put a relational box on the whiteboard, justify it in one line ("ACID across the payment and inventory writes"), then be ready for the two predictable follow-ups: "How does it stay consistent under load?" (MVCC + isolation level) and "How does this scale?" (replicas for reads, partitioning, then the single-primary write ceiling and your sharding plan).[1] Mentioning a partial or GIN index, or that you stream the WAL to replicas, signals hands-on depth without you over-explaining the basics. Don't volunteer a SQL-vs-NoSQL essay — pick the tool for the requirement and move on.
