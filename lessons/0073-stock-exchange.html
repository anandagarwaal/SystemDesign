System Design · Lesson 73 · Phase 4 — Case Study · Hard

Design a Stock Exchange / Matching Engine

The venue itself: one tiny piece of memory where every order in the world lines up, and the rule that decides who trades first must be the same answer every single time.

Why this lesson, for your mission: Most candidates reflexively reach for queues, databases, and horizontal sharding — and at a stock exchange every one of those instincts is wrong on the hot path. The matching engine is a single-threaded, in-memory state machine measured in microseconds, not a distributed CRUD service. The L6/L7 signal is knowing when to delete the distributed system: collapse the core to one deterministic thread for latency and fairness, and recover durability through an append-only log and replay rather than a database write per order. This is the opposite of Lesson 30 (Robinhood) — there you built a broker that routes out to an exchange; here you build the exchange.

Ask before you design

  • “Which order types and time-in-force options?” — Order types define matching logic complexity.
  • “What latency and fairness guarantees must we give participants?” — Microsecond determinism rules out databases and multithreaded matching.
  • “How is market data distributed?” — Equal-latency fan-out pushes toward multicast feeds.

Functional Requirements

An exchange matches buyers to sellers directly — it is the counterparty-discovery venue, not a broker forwarding orders elsewhere.[3] Scope the core operations:

#Users should be able to…Why it shapes the design
1Place an order (limit or market, buy or sell) for a symbolThe latency-critical write that mutates the order book
2Cancel / replace a resting order they ownMust be as fast and as ordered as a place — it races fills
3Have crossing orders matched into trades by a deterministic ruleThe heart of the engine: price-time priority matching
4Receive a market-data feed (book updates + trade prints)Massive fan-out read path, separate from matching

Order types in scope: limit and market, plus the standard time-in-force flags (IOC — immediate-or-cancel, FOK — fill-or-kill, GTC — good-till-canceled). Out of scope (say so): clearing & settlement (T+1), custody, market surveillance, complex order types (icebergs, stop-loss), and multi-asset support. Naming exclusions bounds the 45 minutes — a senior signal in itself.

Capacity Estimation

Estimate only the numbers that change a decision. For an exchange, two do: the per-order time budget and the market-data fan-out.

QuantityRough mathDesign implication
Per-order time budgetTarget ~1M orders/sec on one core → ~1 µs/order of CPU budgetNo network hop, no disk, no lock, no GC pause fits in 1 µs → matching must be in-memory and single-threaded
Order book memory~10k symbols × ~10k resting orders × ~200 B ≈ ~20 GBThe entire active book fits in RAM on one server — no reason to involve a database on the hot path

The punchline: the working set is small enough to live in memory, and the time budget is too small for anything else. Those two facts, together, justify deleting the database from the critical path — the single most counterintuitive (and most senior) move in the design.

Core Entities & API

Entities: Order (id, symbol, side, price, qty, type, TIF, sequence number), OrderBook (per symbol: two sorted sides of resting orders), Trade (a match: aggressor + resting order, price, qty, timestamp), and an append-only EventLog of every accepted command in arrival order. Participant identity comes from the authenticated session, never the message body.

Real exchanges use binary session protocols (e.g. FIX / native ITCH-OUCH-style), but interview-friendly REST/WS sketches the contract:

EndpointPurpose
POST /v1/ordersSubmit a new order (symbol, side, price, qty, type, tif + client_order_id). Returns an ack with the exchange-assigned id and accepted sequence number.
DELETE /v1/orders/{id}Cancel a resting order; may race a fill (responds canceled or too-late).
PUT /v1/orders/{id}Cancel/replace (amend price or qty) — modeled as cancel + new for priority rules.
GET /v1/book/{symbol}Snapshot of the top-of-book / depth (for late joiners syncing to the live feed).
WS|multicast /v1/marketdata/{symbol}Subscribe to the real-time feed: order-book deltas + trade prints.

Data Model

The hot-path data model lives in pre-allocated memory, not a database: per-symbol arrays of price levels holding intrusive FIFO lists of orders, plus a hash index from order id to node. Prices are integer ticks (never floating point) so matching is exact and deterministic. The only durable structure on the critical path is the sequenced input log; everything else — trades, exec reports, book snapshots — is derived from it and persisted downstream.

Why are prices stored as integer ticks, never floating point?

0.1 + 0.2 ≠ 0.3 in binary floats. Exactness is required for both correctness and byte-identical replay.

Would two replicas computing with floats always agree on whether 10.01 ≥ 10.01?

How does the book cancel an order by id in O(1)?

Hash locates, doubly-linked list unlinks in O(1) — no scanning.

High-Level Design

Picture a thin, fast funnel into one core, with everything durable and fan-out pushed to the edges so the core stays pure.

ComponentRole
Gateway / session tierTerminates client connections, authenticates, parses the binary protocol, runs cheap stateless validation. Stateless and horizontally scaled.
Pre-trade risk gatePer-participant checks (credit/buying-power, position & rate limits, fat-finger price bands) before an order reaches the book.[5]
SequencerStamps every accepted command with a single global, monotonic sequence number and appends it to the input event log — this fixes the canonical order of the universe.[1]
Matching engineSingle-threaded, in-memory. Consumes the sequenced log, mutates the limit order book, emits trades + book deltas. Deterministic: pure function of the log.[1]
Replica engines (hot standby)Identical engines replaying the same log in lockstep (state-machine replication). On primary failure, a replica is already warm at the same state.[4]

Downstream (off hot path)Drop-copy, clearing, surveillance, persistence — all consume the same event log asynchronously, never blocking matching.

Order flow. POST /orders → gateway validate → risk gate → sequencer appends to the log (this is the durable commit point) → matching engine consumes the next sequence number, matches against the book, emits trades + deltas → publisher multicasts the result; replicas replay the same entry. The order is durable the instant it's in the log — before it's matched — so a crash mid-match loses nothing: a replica resumes from the same log position.

★ Staff-level signal The whole interview hinges on one inversion of instinct: the database is not on the critical path; the log is. A senior engineer reaches for a sharded DB + a queue + worker pool and gets correctness but milliseconds of latency and nondeterministic interleaving. A staff engineer says "the active book is ~20 GB and my budget is ~1 µs, so I'll match on a single thread against in-memory data, sequence all input into an append-only log, and get durability + HA from replaying that log into hot replicas." This is the LMAX architecture[1] and the classic state-machine replication result[4] — and being able to justify removing the distributed machinery is the signal.

Deep Dive 1 — The in-memory limit order book & price-time priority

The order book is, per symbol, two sorted collections: bids (buyers, sorted high→low) and asks (sellers, sorted low→high). A limit order book holds resting orders that aren't yet matchable; a marketable order "crosses the spread" and trades immediately.

The matching rule: price-time priority (FIFO)

An incoming aggressor matches the best available price first; within a price level, the order that arrived earliest fills first.[3] Example: an incoming buy of 100 @ $10 hits the lowest asks — fully consuming the oldest $10 ask before touching a newer one, then walking up to $10.01 if size remains. Whatever doesn't fill rests in the book at its limit, taking its place at the back of that price level's queue.

The data structure that makes it microsecond-fast

NeedStructureWhy
Find best bid/askSorted map of price level → queue (or array indexed by price tick)O(1) top-of-book; ticks are discrete so an array of price levels is cache-friendly
FIFO within a levelDoubly-linked list / ring of orders at each levelO(1) append on arrival and O(1) remove on cancel
Cancel by order idHash map: order id → node pointerO(1) locate, then unlink from its level

Place, cancel, and match all become near-O(1) on contiguous, pre-allocated memory — no allocation, no pointer-chasing across the heap, no locks. (Compare Lesson 23, online auction: an auction is a slow, single-winner version of the same crossing logic; an exchange is the continuous, high-frequency limit.)

Deep Dive 2 — Single-threaded deterministic engine + log & replay (the staff insight)

Why one thread? Because the obvious alternatives all lose:

ApproachWhat breaks
DB write per orderA disk/round-trip is 100 µs–ms — 100–1000× over budget; and it serializes anyway
Multi-threaded book w/ locksLock contention + nondeterministic interleaving → not reproducible, not fair, and slower under contention
Queue + worker poolReorders work; "who was first" becomes ambiguous → fairness violated
Single thread, in-memoryNothing — a tight loop over RAM has no contention, predictable cache behavior, and a single well-defined order

A single core can comfortably do millions of simple matches per second, and a busy symbol's matching is inherently serial anyway (you can't match the same book in parallel without locks). The constraint becomes a feature: one thread defines a total order for free.[1]

Durability without a database: log first, then match

The sequencer appends every accepted command to an append-only event log on fast storage before the engine acts on it. The matching engine is then a pure, deterministic function: state(n) = apply(state(n-1), log[n]). Because output depends only on the log, durability and recovery are just "keep the log" — exactly event sourcing (revisit Lesson 6 on replication).

High availability via state-machine replication

Run replica engines that consume the same log in the same order. By the state-machine replication principle, deterministic replicas fed identical inputs reach identical states.[4] A hot standby is therefore always at the primary's exact state; failover = promote a replica + resume from the last sequence number. No state is lost because no state ever lived only in the primary — it lives in the log.

Why determinism is non-negotiable here: it powers three things at once — fairness (one defined order), recovery (replay reproduces the book exactly), and HA (replicas stay byte-identical). Lose determinism (a wall-clock read, a hash-map iteration order, a thread race) and all three collapse simultaneously.

Deep Dive 3 — Market-data dissemination (multicast fan-out)

The engine emits a stream of book deltas and trade prints. Thousands of subscribers (HFT firms, brokers, data vendors) want it with minimal, equal latency. Unicasting to each is billions of messages/sec and — worse — gives whoever's first in the send loop an unfair head start.

  • UDP multicast for fairness + fan-out. The publisher sends each update once onto a multicast group; the network delivers a copy to every subscriber roughly simultaneously. One send, N receivers — and no participant is systematically favored by send order.
  • Sequence numbers + a recovery channel. Multicast is lossy (UDP). Every message carries a monotonic sequence number; a subscriber that detects a gap requests retransmit from a separate recovery service rather than slowing the main feed.
  • Snapshots for late joiners. A subscriber connecting mid-session grabs a periodic full book snapshot, then applies live deltas from the snapshot's sequence number forward — the same snapshot-plus-delta pattern as the price firehose in Robinhood (Lesson 30), but here it's the read side of this exchange, not a feed from an external one.

Critically, fan-out lives outside the matching thread. The engine writes to a fast output buffer; a separate publisher tier does the network work, so dissemination scale never steals the core's microseconds.

Deep Dive 4 — Pre-trade risk checks

Regulators (and the exchange's own survival) require that obviously-bad orders are stopped before they touch the book — without blowing the latency budget.[5] The tension: risk checks add work to the hottest path.

  • What to check: buying-power / credit limits, max order size & rate (throttle a runaway algo), and price bands / fat-finger guards (reject a buy 50% through the book that's likely an error).
  • Where to put it: in the gateway / risk gate before the sequencer — so rejected orders never enter the log or the book, keeping the engine's input clean and its order canonical.
  • How to keep it fast: precompute per-participant limits into in-memory counters updated on each accepted order; the check is a handful of integer comparisons (sub-microsecond), not a database lookup. Risk state is itself rebuilt by replaying the log.

Done right, risk is a cheap, deterministic filter on the ingress — protecting the market without turning the hot path into a synchronous database call.

Check yourself

Asks: 50 @ $10.00 (A, older), 50 @ $10.00 (B), 100 @ $10.01. A buy for 80 @ $10.01 arrives. What fills?

Best price ($10.00) first; within it, time priority (A before B). Nothing reaches $10.01.

Step 1: which price level is best for a buyer? Step 2: within that level, who was first?

Why not match one hot symbol on 8 threads for 8× throughput?

Every match mutates the same best price. Parallelism means locks, and lock acquisition order is nondeterministic → unfair, unreplayable.

Can two threads both consume the best ask at the same time without coordinating?

Why is unicast market data *unfair*, not just inefficient?

Sending 5,000 copies in sequence gives a systematic head start. Multicast = one send, everyone at once.

With 5,000 sends in a loop, how much later does subscriber #5,000 get it?

Filter at ingress with in-memory integer counters: the engine's input stays clean and its loop stays fast.

Privacy

The sensitive data is participant trading intent: who is buying or selling what, and at what size. Controls: public market data is anonymous (no participant ids in the feed); order and fill details are delivered only to the owning member and its clearing firm; internal access to identified order data is restricted and audited. Regulatory reporting (e.g. consolidated audit trails) shares identified data only with regulators. Retention: order and trade records kept for years under books-and-records rules on immutable storage; PII of individual end customers largely stays at brokers, not the exchange.

Wrap-up · 58–60 minClose strongRecap decisions and tradeoffs in 60 seconds; name what you would do next.

Closing Summary (60 seconds)

A stock exchange is a deterministic state machine. Gateways authenticate participants and run pre-trade risk checks. A sequencer assigns a total order to commands, journals and replicates them, and feeds single-threaded matching engines that each hold in-memory order books for a symbol group with price-time priority. Each engine matches in microseconds and emits trades and book deltas. Standbys replay the same stream for failover at an exact sequence, and market data goes out over UDP multicast so participants get equal latency. At 10× we repartition symbols across more engines.

How does the design provide durability and high availability without a per-order database write?

Log-first commit plus state-machine replication: replicas replay the same ordered log to identical state, so failover loses nothing.

Reread 'Durability without a database'.

Why is determinism in the matching engine treated as non-negotiable, not just nice-to-have?

One defined order = fairness; replay reproduces state exactly = recovery; identical replicas = HA. A clock read or hash-iteration race kills all three.

Reread 'Why determinism is non-negotiable'.

A multiplayer game server must be replayable for anti-cheat and fail over without losing state. Which idea transfers?

Any 'replayable + failover-able' state machine is the same pattern: sequenced input log + deterministic apply.
