Replication & CAP

Copies of your data buy availability and read scale — until the network splits and forces you to choose.

Why this lesson, for your mission: Every distributed datastore replicates, and every replication scheme hides a consistency-vs-availability tradeoff. At L6/L7 the signal isn't reciting "CAP says pick two" — it's making the C-vs-A call per feature in your NFR step and then naming the concrete mechanism (single-leader, quorum, sync vs async) that delivers it. That's the difference between "we'll use Cassandra" and a defensible design.

Why replicate at all

Replication means keeping copies of the same data on multiple nodes. You do it for three reasons, and it's worth being precise about which one you're solving for:

GoalWhat replication buys you
AvailabilityIf one node dies, a replica serves the request. No single point of failure.
Read scalingSpread read traffic across many replicas. (Writes are harder — see below.)
Durability / localitySurvive a disk or datacenter loss; keep a copy near the user to cut latency.

Note replication is not sharding (Lesson 05). Sharding splits different data across nodes to scale capacity; replication copies the same data for availability and read throughput. Real systems do both: shard, then replicate each shard.

Three ways to replicate

The architectures differ in who is allowed to accept a write.

ModelHow it worksUse when
Single-leader
(primary–replica)		 One node is the leader; all writes go to it. The leader streams its change log to read replicas. Default for Postgres, MySQL, most RDBMS. Reads ≫ writes; you want simple, strong-ish consistency. The common case.
Multi-leader Several leaders accept writes (often one per datacenter) and replicate to each other. Powerful but introduces write conflicts that need resolution. Multi-region writes, offline-capable clients. Use sparingly — conflict handling is the hard part.
Leaderless
(Dynamo-style)		 No leader; clients write to several nodes and read from several nodes. Consistency is tuned with quorums. Used by DynamoDB, Cassandra, Riak. High availability and write throughput across many nodes; you accept tunable, eventual consistency.

Sync vs async replication — the durability/latency knob

In a single-leader setup, the leader can wait for replicas to acknowledge a write (synchronous) or return to the client immediately and ship the change in the background (asynchronous).[2]

SynchronousAsynchronous
DurabilityStrong — replica has the data before client sees success.Weaker — a leader crash before replication loses the write.
Write latencyHigher — pay the slowest replica's round trip.Lower — client unblocked immediately.
AvailabilityWorse — a stalled replica blocks writes.Better — leader keeps accepting writes.

Most production single-leader systems use semi-synchronous: one replica is synchronous (so no write is lost) and the rest are async (so one slow replica doesn't stall everything).[2]

Replication lag and stale reads

Async replication is fast but replicas lag behind the leader — usually milliseconds, sometimes seconds under load. That lag produces two classic bugs:[2]

Read-your-own-writes: A user posts a comment (write → leader), then refreshes (read → a lagging replica) and their own comment is gone. Fix: route a user's reads to the leader for a short window after they write, or pin them to a replica known to be caught up.

Stale reads in general: Any reader hitting a behind replica sees old data. Usually fine for a feed, not fine for a balance check. The fix is to decide — per read path — whether staleness is acceptable.

CAP: what the network partition forces

The CAP theorem says a distributed system can guarantee at most two of Consistency, Availability, and Partition tolerance.[1] But networks will partition — packets drop, links fail — so partition tolerance is non-negotiable. That collapses the choice to a real one: during a partition, do you choose consistency or availability?[1]

Concretely, imagine the network splits two replicas and a write arrives:

  • Choose C: refuse the write (or read) unless you can confirm it's consistent across nodes — return an error. The data stays correct; the feature is briefly unavailable.
  • Choose A: accept the write/serve the read from whatever node you can reach — stay up, reconcile later. The feature stays available; some reads may be stale or conflicting.
The practical interview framing. Don't choose globally — choose per feature.[1] Ask: "if this data is briefly stale or unavailable, who gets hurt?"
  • Bank balance / inventory count / seat reservation → consistency. Stale data means overdraft, overselling, or a double-booking.[1]
  • Social feed / likes / recommendations → availability. A few-second-old feed is fine; an error page is not.[1]
The safe default for most features is availability with eventual consistency — reach for strong consistency specifically when money, inventory, or booking a limited resource is involved.[1]

The consistency spectrum

"Consistent" isn't binary. Know these four points and when each is acceptable:

ModelGuaranteeAcceptable for
StrongEvery read sees the latest committed write. Behaves like one copy.Balances, inventory, locks, anything where being wrong costs money.
Read-your-writesYou always see your own writes; you may not see others' instantly.Profile edits, your own posts — the read-your-own-writes fix.
CausalOperations that depend on each other appear in order (reply never before its parent).Comment threads, chat — order matters, global agreement doesn't.
EventualReplicas converge given enough time with no new writes. Reads may be stale.Feeds, view counts, recommendations, analytics dashboards.

Quorums: tuning consistency in leaderless systems

Leaderless stores let you dial consistency with three numbers: N replicas, W nodes that must ack a write, R nodes consulted on a read. The key rule:

If W + R > N, every read overlaps at least one node that saw the latest write — so a read is guaranteed to see it. That gives you strong consistency without a leader.[1]
  • N=3, W=2, R=2 → 2+2 > 3 ✓ strong, tolerates one node down for reads and writes.
  • N=3, W=1, R=1 → 1+1 < 3, fast and highly available, but reads can be stale (eventual).
  • N=3, W=3, R=1 → writes need all nodes (slow, fragile), reads cheap.
Cassandra and DynamoDB expose this per query, so you can pick strong for one operation and eventual for another.

PACELC: the part CAP leaves out

CAP only describes behavior during a partition. PACELC adds the rest: if Partition, choose A or C; Else (normal operation), choose Latency or Consistency. Even with a healthy network, waiting for replicas to agree costs latency — so the consistency tax is always being paid, not just during failures. DynamoDB is "PA/EL" (favors availability and low latency); a strongly-consistent store is "PC/EC."

How CAP shows up in the interview

This is a process, not a fact to recite. The sequence that earns the signal:

  1. In the NFR step, state the C-vs-A choice out loud, per feature. "Checkout inventory needs strong consistency; the product feed can be eventually consistent."
  2. Let that choice drive the datastore. Strong → single-leader RDBMS or a CP store; available → Dynamo/Cassandra with eventual consistency.
  3. Name the mechanism. "Strong via quorum W+R>N," or "writes go to the single leader, reads from replicas with read-your-writes for the author."
★ Staff-level signal Seniors say "we'll use an eventually consistent database." Staff candidates make the consistency decision per feature, not per system — and tie each choice to a concrete mechanism. "Reviews are eventually consistent on Cassandra at W=1,R=1; order placement is strongly consistent via a single-leader Postgres so we never double-charge." Naming the knob (quorum, leader, sync replica) proves you know how the guarantee is enforced, not just its label — and showing you'd relax consistency where it's cheap demonstrates the judgement that you're not blindly buying strong consistency everywhere.

Check yourself — retrieval practice

Answer from memory before scrolling back up.

1. During a network partition, what does CAP force you to choose between?

Partitions are unavoidable, so the real CAP choice collapses to consistency vs availability.

2. With N=3 replicas, which quorum gives strongly consistent reads?

W+R > N (2+2 > 3) guarantees read and write sets overlap on a current node.

3. Which feature is the clearest case for choosing consistency over availability?

Booking a limited resource risks double-booking if stale — money/inventory/seats need strong C.

4. Why does asynchronous replication trade durability for latency?

Async returns immediately (low latency) but unreplicated writes vanish if the leader dies.
