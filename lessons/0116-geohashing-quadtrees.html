Deep Dive: Geospatial Indexing (Geohashing & Quadtrees)

"Find the 20 drivers nearest to me" sounds trivial — until you realize a normal index can't do it. Here's how maps actually answer proximity queries.

Why this lesson, for your mission: Proximity is one of the most common interview themes — Uber, Yelp, Tinder, a heat map, a food-delivery dispatch all hinge on "what's near this point?" The trap is that a B-tree on (lat, lng) can't answer it efficiently, and saying "I'll compute distance to every row" fails instantly at scale. A staff candidate names a real geospatial index — geohash, quadtree, or H3 — and explains the 2D-to-1D trick and the edge cases. This lesson hands you that vocabulary and the one tricky failure mode (boundary neighbors) interviewers love to probe.

1 of 4

Why a normal index fails

A B-tree indexes one ordered dimension. You can index lat or lng, but a near-me query needs both together: a box around a point. Filtering lat BETWEEN … AND lng BETWEEN … uses at most one index and still scans a wide stripe of the planet, then computes distance to everything in it.[2] The core problem: 2D locality doesn't map onto 1D order — two points can be close on Earth but far apart in any single-column sort. Geospatial indexes exist to encode 2D proximity into something a database can index efficiently.

Geohashing — 2D into a 1D string

A geohash recursively divides the world into a grid and encodes a lat/lng into a short base-32 string.[1] The mechanism:

  • Interleave the bits of latitude and longitude, repeatedly halving the range (binary subdivision), then base-32 encode the result.[1]
  • The magic property — shared prefix = spatial proximity: the longer the common prefix of two geohashes, the closer the points. 9q8yy and 9q8yz are neighbors; 9q8 is a bigger box containing both.
  • Precision = length: more characters → smaller cell. A 5-char hash is ~5 km; 6-char ~1 km; 7-char ~150 m. Pick the length to match your search radius.

Now the near-me query is a prefix match on an ordinary B-tree/string index: WHERE geohash LIKE '9q8yy%' returns everything in that cell — fast, indexable, shardable. This is how Redis geospatial commands (GEOADD/GEOSEARCH) work under the hood: they encode locations as a 52-bit geohash score in a sorted set and range-scan it.[1]

The boundary problem — the edge case interviewers probe
  • Two points can be physically adjacent but sit in different cells with different prefixes — your target is 10 m away but just across a cell border, so a single prefix query misses it.[1]
  • Fix: query the target cell plus its 8 neighbors (the surrounding 3×3 grid of geohash cells), union the results, then sort by true distance. Geohash neighbor computation is a standard, cheap operation.
  • Hot spots / skew: a fixed-grid cell over Times Square holds millions of points while a rural cell holds three. Fixed grids don't adapt to density — which is exactly what quadtrees fix.

Quadtrees — a grid that adapts to density

A quadtree is a tree where each node represents a square region and splits into four quadrants only when it exceeds a capacity (say 100 points).[2] Dense areas (a city) subdivide deeply into tiny cells; sparse areas (an ocean) stay as one big node. A near-me query descends the tree to the leaves overlapping your search box — O(log n) and naturally load-balanced by density, since every leaf holds a bounded number of points. The cost is that it's a dynamic in-memory structure that must be rebuilt/rebalanced as points move, vs. a geohash string you can drop in any database column.

Two more you should name: R-trees (used by PostGIS / Postgres GiST indexes — index bounding boxes, great for polygons and ranges, not just points)[2] and Uber's H3 (hexagonal grid — hexagons have uniform distance to all neighbors, avoiding the corner-vs-edge distortion of squares).

★ Staff-level signal A junior on a "find nearby" problem says "I'll query the database for locations near the user." A staff candidate immediately names why that's hard — "a B-tree can't index two dimensions, and scanning every row doesn't scale" — and reaches for a concrete index: "Geohash the locations, store them in a Redis sorted set or an indexed column, and do a prefix range query."[1] The deeper tell is volunteering the boundary edge case ("I'll also query the 8 neighbor cells so I don't miss a point just across a cell border") and the density trade-off ("if hot cells like a stadium are a problem, a quadtree or H3 adapts to density where a fixed geohash grid doesn't"). Naming the failure mode before being asked is the signal.

In the interview

For any proximity feature (Yelp, Uber, Tinder, heat maps, dispatch): (1) call out that a plain index can't do 2D range; (2) pick geohash as the simple default — "encode each location, store in Redis/an indexed column, prefix-query the cell"; (3) immediately add "and the 8 neighboring cells, then re-rank by true distance" to handle boundaries; (4) if density skew or moving objects come up, upgrade to a quadtree (adaptive) or mention PostGIS R-trees / H3. That progression — name the problem, simple index, edge case, density upgrade — is a clean breadth-then-depth answer.
