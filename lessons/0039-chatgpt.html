Design ChatGPT (LLM Chat Service)

A streaming chat product on top of an LLM, where the GPU — not the database — is the scarce resource you must engineer around.

Why this lesson, for your mission: Most case studies bottleneck on storage or QPS. This one bottlenecks on compute: GPUs are the scarce, expensive resource [1]. The staff move is to stop treating the model server like a normal stateless web service and instead model it as a queued, batched, autoscaled fleet — then layer streaming and a growing context window on top. Nail those three and you've shown L6/L7 judgement.

Functional Requirements

The interviewer wants two core flows; everything else (editing/branching, images/audio, sharing, custom GPTs, tool calling, web browsing, full-text search) is explicitly out of scope [1] — say so early to control breadth.

#Requirement
1A user can send a chat message and receive an AI-generated response, streamed token by token as it is generated.
2Conversations are multi-turn: prior turns are retained and the chat's context is carried into each new prompt [1].
3The system serves many concurrent users, each with their own independent session.

Scope note: we treat the LLM as a black box we call — not something we train or whose internals we run [1]. The interesting system is the serving layer, not the model.

Non-Functional Requirements

NFRTarget / priority
Low time-to-first-token (TTFT)Latency to the first token matters more than total completion time — a blank screen feels broken even if the full answer is fast [1].

Capacity Estimation

Only estimate the numbers that change the design. Here, every number points back at the GPU.

Concurrency. 200M DAU, say each sends 10 messages/day → 2B messages/day ≈ ~23k messages/sec average, multiples higher at peak. A response can take 10–30s to stream, so an open message holds a GPU slot far longer than a normal HTTP request — concurrent in-flight generations, not QPS, is the load metric that matters.

GPU throughput is the ceiling. One GPU generates on the order of tens of tokens/sec per stream. With continuous batching it can serve many streams at once, but throughput is finite. If average concurrency is, say, 1M in-flight generations and one GPU handles ~10–20 concurrent streams, you need tens of thousands of GPUs. Implication: the design is a capacity-management problem — queue, batch, prioritize.

Context/history storage is cheap by comparison. A conversation is text: a few KB per turn. Even billions of turns is terabytes, not the bottleneck. Implication: store history in a boring, cheap, horizontally-sharded store; spend your design budget on the GPU fleet.

Core Entities & API

Entities: User · Conversation (ordered list of messages, owned by a user) · Message (role = user/assistant, content, tokens, createdAt). User identity is derived from the auth token, never sent in the body.

EndpointPurpose
POST /v1/chat/completionsSend a message in a conversation; response is an SSE stream of tokens (Content-Type: text/event-stream), terminated by a [DONE] event.
GET /v1/conversationsList the caller's conversations (paginated, most-recent first).
GET /v1/conversations/{id}Fetch full message history for one conversation (to render / resume) [1].
POST /v1/conversationsCreate a new conversation.
Request shape for the streaming call:
  • conversation_id — which thread (server loads prior context from it).
  • message — the new user turn.
  • Server replies with SSE: each event carries a token/chunk; the client appends as they arrive.

High-Level Design

Trace one message through the boxes. Two flows: generate (the hard path) and read history (the easy path).

ComponentRole on a POST /v1/chat/completions
API gateway / LBAuth, rate-limit, terminate TLS. Routes to a stateless API server.
Chat API serverLoads conversation history from the store, assembles the prompt (history + new message), and submits a generation job to the inference queue. Holds the SSE connection open and relays tokens to the client.
History storeConversation + Message rows, sharded by user_id (or conversation_id). Cheap, durable, horizontally scalable (e.g. Cassandra/DynamoDB).
Inference queueBuffers generation requests in front of the GPU fleet so workers are never starved and bursts don't drop. The control point for prioritization.
GPU inference fleetPool of GPU workers running the model. Pull jobs, batch them, stream tokens back. Autoscaled. The scarce resource.

Read path is trivial: GET /v1/conversations/{id} hits the history store directly — no GPU involved. After a generation completes, the API server persists the assistant message so the next turn can replay it.

Deep Dives

This is the 60%. Four hard parts, each mapped to an NFR.

1 · Streaming responses — why SSE

The model produces tokens one at a time over many seconds. We want the user to see them as they appear (low TTFT), so we cannot wait for the full response. We need a server-push channel — and the choice between SSE and WebSocket is a classic staff discrimination (see Lesson 02 and Lesson 02).

NeedSSEWebSocket
DirectionOne-way server→client — exactly our token streamFull-duplex — more than we need here
TransportPlain HTTP; auto-reconnect built inSeparate protocol upgrade; manage reconnect yourself
Infra fitWorks through HTTP proxies/CDNs easilyOften needs special proxy config
Pick SSE. The token stream is one-directional, the new prompt arrives in a normal POST body, and SSE rides ordinary HTTP with built-in reconnection. WebSocket's full-duplex channel is capability we don't use — paying its complexity tax would be over-engineering. The cost: the request is held open for the whole generation, so the front tier must handle many long-lived connections (lots of idle sockets, little CPU) — size for connection count, not request rate.

2 · Serving the model — the GPU inference fleet

The mistake juniors make: treat the model server like a stateless API behind a round-robin LB. It isn't. A generation runs for tens of seconds, pins a GPU, and GPUs are too expensive to leave idle. Model it as a queue in front of a pool of GPU workers — the same producer/consumer shape as an async job system (Lesson 07) and an autoscaling fleet (Lesson 10).

Batching is the whole game. A GPU is most efficient processing many sequences in parallel. Continuous (in-flight) batching lets the worker add new requests to the running batch and evict finished ones token-by-token, instead of waiting for a fixed batch to complete. This keeps the GPU saturated and raises tokens/sec/GPU dramatically.

The queue decouples bursty arrivals from finite workers: requests wait briefly rather than being dropped or starving a worker. It's also where you enforce priority (deep dive 4).

Autoscaling the GPU fleet tracks queue depth / TTFT, but GPUs are slow and costly to spin up — scale on sustained signals, keep warm headroom, and accept some queueing rather than over-provisioning the most expensive box in the building.

Long generation means a worker is committed for the duration; track per-stream progress, support cancellation when the client disconnects (free the slot immediately), and cap max output length.
★ Staff-level signal Say the words: "The GPU fleet is not a stateless service — it's a queued, continuously-batched, autoscaled pool of the scarcest resource in the system." Routing across GPU workers and scheduling generations is the central challenge [1]. A senior describes an LB in front of model servers; a staff candidate describes batching economics, queue-depth-driven autoscaling, and slot reclamation on disconnect — and ties each back to "idle GPU is burned money."

3 · Conversation context & memory

Multi-turn means each prompt carries prior turns so the model "remembers." But the model has a fixed context window (a token limit), and resending the whole history every turn both risks overflow and grows inference cost linearly with conversation length.

StrategyWhat it doesTradeoff
Send full historyReplay every turn into the promptSimple; overflows the window and gets expensive as it grows
Truncation (sliding window)Keep the most recent N turns / tokensBounded cost; silently forgets older context
SummarizationCompress old turns into a running summary, keep recent turns verbatimPreserves gist cheaply; summary can lose detail, costs an extra LLM call
Pick: hybrid. Keep recent turns verbatim for fidelity, summarize the older tail to stay within the window and control cost — without making the assistant "feel forgetful" [1]. Persist messages in the history store and assemble the context server-side on each turn, so the client only sends the new message.

4 · Cost & capacity management

Because the GPU is the bottleneck, demand will exceed supply at peak. You manage it at the queue, not by buying infinite GPUs.

  • Rate limiting per user — stops a heavy user from monopolizing GPUs [1] (token-bucket at the gateway).
  • Prioritization / tiers — paid tiers get a better experience: separate or higher-priority queues so their jobs are scheduled first [1].
  • Queue + backpressure — under overload, queue (raising TTFT gracefully) rather than dropping; shed or slow lowest-priority free traffic first.
  • Cap output length & context — bounds the worst-case GPU time per request, making capacity predictable.

The throughline: storage is cheap, the GPU is precious, so every lever — batching, queueing, truncation, rate limits, tiers — exists to extract more useful tokens per GPU-second.

Check yourself — retrieval practice

Answer from memory before scrolling back up.

1. Why is SSE preferred over WebSocket for streaming the model's tokens?

Tokens flow server→client only; SSE is purpose-built one-way push over HTTP with reconnect, so WebSocket's duplex is unused complexity.

2. What makes the GPU fleet different from a normal stateless web tier?

GPUs are expensive and finite; long generations pin them, so you queue, continuously batch, and autoscale rather than round-robin like web servers.

3. How do you keep multi-turn context within the model's window as it grows?

A hybrid keeps fidelity on recent turns while compressing the old tail, bounding both window overflow and per-turn inference cost.

4. Where do you stop one heavy user from monopolizing scarce GPUs?

Capacity is managed at the queue: per-user rate limits plus tier-based priority decide whose generation a finite GPU runs next.
