Deep Dive: Apache Spark

How an in-memory DAG engine buried MapReduce's disk round-trips — and where it still loses to a true streaming engine.

Why this lesson, for your mission: The moment a design needs to chew through a day of raw events — sessionize logs, train features, backfill a year of clickstream — someone says "run a Spark job." The senior answer stops there. The staff answer explains why Spark's RDD lineage, lazy DAG, and in-memory caching beat MapReduce's per-step disk writes, names the one operation that dominates the cost (shuffle), and knows when a true streaming engine like Flink is the better pick. Knowing the internals lets you defend the batch layer instead of name-dropping it.

1 of 6

What it is

Apache Spark is a distributed, in-memory engine for large-scale data processing — batch jobs, SQL, streaming, and ML over clusters of commodity machines.[1] It's the spiritual successor to Hadoop MapReduce: same "ship the computation to the data, recover from machine failures" philosophy, but it fixed MapReduce's defining weakness.

MapReduce wrote the output of every map and reduce step back to disk (HDFS) before the next step could read it.[2] For a single pass that's tolerable; for the iterative and multi-stage jobs that dominate real analytics and ML, each iteration paid a full round-trip to disk plus replication. Spark's core idea was to keep intermediate results in memory across steps and recompute lost pieces from lineage rather than re-reading replicated disk — reportedly an order of magnitude faster on iterative workloads.[2] Same fault-tolerance guarantees, far less I/O.

RDDs, DataFrames, and lazy evaluation

The core abstraction

The original abstraction is the RDD — Resilient Distributed Dataset: a read-only, partitioned collection of records spread across the cluster that you transform with functional operators (map, filter, reduceByKey).[2] Two properties make it work: it's immutable (a transformation produces a new RDD), and it remembers its lineage — the exact sequence of operations that built it from stable input. If a partition is lost to a dead executor, Spark recomputes just that partition from lineage instead of replicating data.[2]

Today you mostly write DataFrames / Datasets — a higher-level, schema-aware table API that compiles down to the same execution machinery but lets the optimizer (Catalyst) reason about your query.[1] Same engine, richer optimization surface; RDDs are the foundation you reach for only when you need raw control.

Transformations vs actions

This is the most-missed Spark concept and a clean interview tell. Operations split into two kinds:

KindExamplesWhat happens when you call it
Transformationmap, filter, join, groupByNothing runs. Spark just records it onto the lineage graph.
Actioncount, collect, save, showTriggers execution of the whole graph built up so far.

Transformations are lazy: calling filter then map builds a plan but executes nothing.[1] Only an action forces Spark to actually run. Laziness isn't a quirk — it's why the optimizer can fuse adjacent steps, push filters down to the source, and avoid materializing intermediates you never asked for. The whole pipeline is optimized as one unit, not step by step.

DAG, stages, tasks, and the shuffle

When an action fires, Spark turns the lineage into a DAG (directed acyclic graph) of transformations and the DAG scheduler splits it into stages.[1] The split point is the expensive operation — a shuffle. Within a stage, work is divided into tasks, one task per partition, and tasks are the unit Spark ships to executors to run in parallel.[1] The hierarchy:

Job → Stages → Tasks → Partitions.
  • An action launches a job.
  • A job is cut into stages at every shuffle boundary (operations that need data movement).
  • Each stage runs as a set of tasks — one per partition of the data.
  • Partitions are the fundamental unit of parallelism: more partitions = more tasks = more concurrency (up to the number of executor cores). Too few starves the cluster; too many adds scheduling overhead.

Why do stages break where they do? Because dependencies between RDD partitions come in two flavors:[2]

DependencyMeaningExamplesCost
NarrowEach parent partition feeds one child partition — no data crosses the network.map, filter, unionCheap; pipelined inside one stage.
WideEach child partition pulls from many parent partitions — data must be repartitioned across the cluster.groupByKey, join, reduceByKeyA shuffle: the expensive part.

A shuffle is Spark redistributing data across the network so that all records with the same key land on the same partition — necessary for grouping, joining, and aggregating by key.[1] It is the single most expensive thing Spark does: it writes intermediate map outputs to local disk, transfers them over the network, and is the boundary that forces a new stage. Almost all Spark tuning — choosing reduceByKey over groupByKey, broadcasting a small table to avoid a join shuffle, fixing skew — is about doing fewer/smaller shuffles. If you remember one cost model for Spark, it's this: narrow is free, wide is a shuffle, shuffle is the bill.

Check yourself

What is the defining cost of a "wide" dependency compared to a "narrow" one?

Wide dependencies (groupByKey, join) require a shuffle — the expensive network repartitioning step.

Which dependency type needs data to move across the network to land on the right partition?

Why does Spark specifically cut a new stage at a shuffle boundary, rather than at every operation?

Narrow deps chain freely inside a stage since nothing crosses the network. A shuffle needs all tasks to finish writing before the next stage can read, which is the real synchronization boundary.

Ask what a shuffle requires that a plain map or filter doesn't: waiting for every upstream task to finish.

The cluster model

A Spark application has three roles:[1]

  • Driver — runs your main() and the SparkContext; builds the DAG, schedules stages/tasks, and tracks where everything lives. The brain. If it dies, the app dies.
  • Executors — worker JVM processes on cluster nodes that actually run tasks and hold cached partitions in memory. Parallelism = executors × cores per executor.
  • Cluster manager — allocates executors on the cluster: YARN, Kubernetes, Mesos, or Spark's standalone manager. Spark is decoupled from it, so the same job runs anywhere.[1]

Why in-memory + DAG beats MapReduce. MapReduce expressed everything as rigid map→shuffle→reduce steps, materializing each step's output to replicated disk before the next began.[2] Spark keeps working sets in memory, models the whole job as a DAG so it can pipeline narrow transformations inside a stage without touching disk, and only spills/shuffles at wide boundaries. Fewer disk round-trips, fewer materializations, and recompute-from-lineage instead of replication-for-safety. That's the entire performance story in one sentence.

Spark SQL, streaming, and when to use it

Spark SQL + Catalyst. DataFrame/SQL queries don't execute as written — they pass through Catalyst, Spark's query optimizer, which applies rule-based and cost-based rewrites (predicate pushdown, column pruning, join reordering) and generates optimized JVM code.[1] This is why DataFrames usually beat hand-written RDD code: the optimizer sees the whole logical plan and the engine doesn't.

Structured Streaming = micro-batch. Spark's streaming model treats a live stream as an unbounded table that grows, and processes it in small micro-batches — it runs the same batch engine repeatedly over tiny slices of newly arrived data.[1] You get exactly-once semantics and the full DataFrame/SQL API on streams, at the cost of latency bounded by the batch interval (typically hundreds of milliseconds to seconds, not true per-event).

Spark vs Flink — micro-batch vs true streaming.
  • Spark Structured Streaming: micro-batch — buffers events into small batches, then runs a batch job per batch. Excellent throughput, unified batch+stream code, latency typically sub-second to seconds.
  • Flink: a true event-at-a-time streaming engine with streaming as the native model. Lower, more consistent latency (single-digit to tens of milliseconds) and richer event-time/windowing semantics — the better pick when low latency is the hard requirement.
  • Rule of thumb: Spark wins for heavy batch + "good enough" streaming on one stack; Flink wins when true low-latency streaming is the headline NFR. (Next lesson covers Flink in depth.)

Deployment modes. Submit with spark-submit in cluster mode (driver runs inside the cluster — production) or client mode (driver runs where you launched it — interactive/notebooks), onto YARN, Kubernetes, or standalone.[1] Managed offerings (Databricks, EMR, Dataproc) wrap all of this.

When to reach for it — and when NOT

Reach for Spark when…
  • You need large-scale batch / ETL: backfills, sessionization, joining huge datasets, feature pipelines.
  • The job is iterative or multi-stage (ML training, graph algorithms) where in-memory caching pays off.
  • You want one engine for batch + SQL + streaming + ML over data in a lake/warehouse.
  • Latency tolerance is seconds-to-minutes, not milliseconds — analytics, not request serving.
Do NOT reach for it when…
  • You need true low-latency streaming (single-digit ms per event) — that's Flink.
  • You need low-latency point queries / serving — that's an OLAP store or key-value DB, not a batch engine.
  • The data is small enough for one machine — a single node, Pandas, or DuckDB is simpler and faster.
  • You need transactions / OLTP — Spark is a processing engine, not a database of record.
★ Staff-level signal Don't say "we'll Spark it" and move on. Say "this is an append-only event firehose we need to roll up daily, so a batch DAG over partitioned data fits — but the cost lives in the shuffle on the groupBy, so I'll pre-aggregate with reduceByKey and broadcast the small dimension table to avoid a wide join." Then show the boundary: if the requirement is sub-second per-event latency, you'd reach for Flink instead of forcing Spark's micro-batch.

In the interview

Spark almost always shows up as the batch / pre-aggregation layer in data-processing designs — the "compute the rollups" half of a lambda or kappa architecture (Lesson 36 — ad click aggregator), feeding cooked results into an OLAP serving store (Lesson 95 — ClickHouse / OLAP). When you get there:

  • Justify by workload. "Large-scale multi-stage batch over event data → distributed DAG engine like Spark." One sentence, then move to the hard part.
  • Lead with the shuffle. The interesting depth is "where does data move across the network, and how do I shrink it" — partitioning, pre-aggregation, broadcast joins, skew handling.
  • Place it correctly. Spark cooks; an OLAP store serves; a queue buffers. Don't make Spark answer low-latency reads — route those to the serving tier.
  • Name the Flink boundary. If they push on streaming latency, flag micro-batch vs true streaming and when you'd switch. Naming the alternative you rejected is the breadth signal.

What would you expect to happen to recovery time if a Spark job had an extremely long, un-checkpointed lineage chain and lost a partition deep in it?

Lineage-based recovery trades storage cost for recompute cost. A long, uncheckpointed chain means a lost partition triggers a long recomputation — which is exactly why long pipelines checkpoint periodically.

Lineage is a recipe for rebuilding data. What happens if the recipe is very long and something is lost near the end?

Why would using far too few partitions for a large dataset hurt performance even on a big cluster?

Tasks map one-to-one to partitions. If there are fewer partitions than available cores, the extra capacity goes unused no matter how big the cluster is.
