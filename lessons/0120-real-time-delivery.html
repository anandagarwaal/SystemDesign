Deep Dive: Real-Time Delivery (WebSockets, SSE, Polling)

Plain HTTP only lets the client pull — but chat, live scores, notifications, and collaborative editing need the server to push. These four options are how you bend a pull protocol into push, and choosing among them is a staple staff-level decision.

Why this lesson, for your mission: The moment a design needs "the other user sees my message instantly," the interviewer is testing whether you understand that HTTP is request/response — the server can't speak unless spoken to. A senior candidate says "use WebSockets" reflexively. A staff candidate names the four options (short poll, long poll, SSE, WebSocket), picks the cheapest one that meets the requirement (one-way notifications don't need a full-duplex socket), and then — the real signal — talks about the part everyone forgets: scaling millions of persistent connections across a fleet, which is a fundamentally different problem from scaling stateless request/response. This lesson gives you both the menu and the hard scaling story behind it.

1 of 5

The problem: HTTP is client-pull

HTTP is a request/response protocol: the client asks, the server answers, the exchange ends.[1] There is no built-in way for a server to wake up later and say "hey, something changed." That's fine for fetching a page or calling an API (see Networking & APIs, Lesson 2) — the client always initiates.

But a huge class of systems needs the opposite direction: the server has new data and must push it to clients it isn't currently being asked by. Chat messages arriving (WhatsApp, Lesson 19), live sports scores, a notification badge incrementing, the live comment feed under a stream (FB Live Comments, Lesson 24), a cursor moving in a collaborative doc — all of these are server→client push. The whole topic of "real-time delivery" is a set of techniques for getting push-like behavior out of a protocol that was designed for pull. There are four, and they trade off latency, overhead, direction, and complexity.

The four options

From cheapest/dumbest to most powerful: short polling (ask repeatedly on a timer), long polling (ask, but the server holds the request open until it has something), Server-Sent Events (one persistent HTTP stream, server→client only), and WebSockets (one persistent TCP connection, full-duplex both ways).

Short polling

The client hits a normal endpoint on a fixed timer — GET /messages?since=… every few seconds. Dead simple, no special infra, works through any proxy. The costs are brutal at scale: latency is bounded by your interval (poll every 5s → up to 5s late), and the vast majority of requests return "nothing new," burning bandwidth, server CPU, and battery for empty answers. Fine for low-frequency, latency-tolerant updates (a dashboard that refreshes every 30s); wrong for chat.

Long polling

A smarter twist: the client sends a request, and the server does not respond until it actually has data (or a timeout fires). The instant an event occurs, the held request returns with it, and the client immediately opens a new one. This gives near-real-time latency over ordinary HTTP, with no empty responses in the steady state — its big virtue is that it works everywhere HTTP works, no protocol upgrade needed. The downsides: each message costs a full request/response cycle (re-establish, headers), it ties up a server connection slot while idle-waiting, and it's awkward for high-frequency bidirectional traffic. Long polling is the classic fallback when WebSockets are blocked by a proxy.

Server-Sent Events (SSE)

SSE is a standardized, one-way server→client stream layered on a single long-lived HTTP response.[2] The client opens an EventSource connection; the server keeps the response open and writes UTF-8 text "events" down the pipe as they happen.[2] Because it's just HTTP, it passes through most proxies and load balancers, and the browser EventSource API gives you automatic reconnection and a last-event-ID resume mechanism for free.[2] The trade-off is right in the name: it's one-way and text-only. The client still sends its own actions via ordinary HTTP requests. That's a perfect fit for fan-out feeds — notifications, live scores, a stock ticker, a comment stream — where the server does nearly all the talking.

WebSockets

A WebSocket starts as an HTTP request with an Upgrade: websocket header; once the server agrees, that same TCP connection is "upgraded" into a persistent, full-duplex channel where both sides can send small binary/text frames at any time with minimal per-message overhead.[3] This is the only option that gives true low-latency bidirectional communication, which is why it's the default for chat, multiplayer games, and collaborative editing where both parties push constantly. The price is complexity and cost: the connection is stateful and long-lived, you typically build your own message framing / heartbeats / reconnect logic, and — the big one — you now have to scale millions of open connections, which is the next section and the actual hard part.

Mental model. Short poll = "Are we there yet? … Are we there yet?" Long poll = "Tell me when we're there" (and ask again the moment you're told). SSE = a one-way radio the server broadcasts on. WebSocket = a phone call — either side talks whenever. Pick the least powerful tool that meets the requirement: don't open a duplex socket to push a notification badge.

Scaling persistent connections — the hard part

Stateless request/response scales trivially: any server can handle any request, so you put them behind a load balancer and add boxes. Persistent connections break that assumption. Once a client holds an open WebSocket (or SSE stream) to one specific server, all the interesting problems follow from the fact that the connection — and the knowledge of "who is connected where" — is state living on a particular machine.

Connection state & routing to the right server

Say Alice's socket terminates on server S3 and Bob's on S7. When Bob sends "hi Alice," S7 receives it — but the connection that can deliver it lives on S3. No amount of load balancing helps here, because the destination isn't "any server," it's "the exact server holding Alice's connection." So you need two things: a way to keep a client pinned to its server, and a way to route a message to whichever server holds the recipient.

  • Sticky sessions / connection-id routing: the load balancer must keep each client on the same backend for the life of the connection. For a WebSocket there's nothing to re-route after the upgrade anyway, so this is natural — but it means the LB can't freely rebalance, and a backend dying drops every connection it held.
  • A connection registry: a shared store (e.g. Redis) maps user_id → server_id so any server can discover where a given user is currently connected.

The pub/sub backplane (Redis)

The standard fan-out solution is a pub/sub backplane. Every app server subscribes to the messaging layer (commonly Redis Pub/Sub, or Kafka for durability). When S7 receives Bob's message, it doesn't try to find Alice itself — it publishes the message to a channel (say, the channel for Alice's user-id or her chat room). The backplane delivers it to whichever server(s) hold subscribers for that channel; S3 sees it on its subscription and writes it down Alice's socket. This decouples "which server received the message" from "which server holds the recipient," so you can add app servers freely — they all share one logical message bus. (This is the same fan-out machinery behind FB Live Comments, Lesson 24 and chat delivery in WhatsApp, Lesson 19.)

C10K → C10M

The classic C10K problem was the early-2000s realization that handling 10,000 simultaneous connections on one box required moving off thread-per-connection to event-driven I/O (epoll/kqueue, non-blocking sockets). Modern servers push toward C10M — millions of connections per node — but every idle connection still costs memory (socket buffers, app-level state) and file descriptors, so capacity planning for a real-time system is dominated by connection count and memory, not request QPS. This reframes your estimation: "100M users, 5% concurrent = 5M live sockets; at a few KB each plus headroom, that's the box count," not "X requests per second."

Load balancer & lifecycle concerns

  • L4 for WebSockets: there's no per-request routing once the connection is upgraded, so an L4 (transport) load balancer that pins the whole TCP connection to one backend is the natural fit — see Load Balancing, Lesson 121. An L7 LB can carry WebSockets too, but you're paying for HTTP parsing you don't use after the handshake.
  • Heartbeats: idle connections get silently killed by NATs, proxies, and timeouts, so both sides send periodic ping/pong heartbeats to keep the path alive and to detect a dead peer quickly.
  • Reconnection & resume: connections will drop (deploys, network blips, mobile handoffs). Clients need exponential-backoff reconnect, and the server needs a way to replay anything missed during the gap (SSE's last-event-ID, or a per-user message cursor) so a reconnect doesn't lose messages.
  • Graceful deploys: because connections are pinned and stateful, restarting a server drops thousands of sockets at once. Drain slowly and lean on client reconnect + resume so a deploy is a blip, not an outage.

Choosing — a decision rubric

Match the direction and frequency of the data to the cheapest option that satisfies it:

Pick by what the traffic actually needs
  • Low-frequency, latency-tolerant updates (dashboard refresh, "any new orders?") → short polling. No infra, good enough.
  • One-way, server-driven, real-time (notifications, live scores, ticker, live comment feed) → SSE (or long polling as the no-upgrade fallback). Don't pay for a duplex socket you won't use.
  • Two-way, high-frequency, low-latency (chat, collaborative editing, presence, multiplayer) → WebSockets. This is the case that justifies the connection-scaling complexity.
  • Constraint check: if a corporate proxy/old client blocks WebSocket upgrades, fall back to long polling. If you only need server→client, prefer SSE over WS for the simpler, HTTP-native operational story.
★ Staff-level signal Senior candidates jump straight to "WebSockets" for anything labeled real-time. Staff candidates do three things. First, they pick the least-powerful sufficient tool: "this is one-way notifications, so SSE — I don't need full-duplex, and SSE gives me auto-reconnect and resume over plain HTTP for free; I'd only reach for WebSockets if the client also pushed at high frequency." Second — the move that separates levels — they pivot from the protocol to the scaling problem nobody asked about yet: "the protocol choice is the easy 20%; the real work is that a persistent connection is state on one box, so I need sticky/L4 routing, a connection registry, and a Redis pub/sub backplane to fan a message to the exact server holding the recipient." Third, they re-frame capacity around concurrent connections and memory (C10K/C10M), not request QPS, and they pre-empt reconnect/heartbeat/graceful-deploy as first-class concerns. Naming the backplane and the connection-as-state problem unprompted is the whole signal.

In the interview

When a design needs push, deliver it in this arc: (1) name why HTTP isn't enough — "this is server→client push and HTTP is client-pull." (2) Choose with a reason from the menu — "notifications are one-way, so SSE; chat is bidirectional and high-frequency, so WebSockets." (3) Immediately go to scaling persistent connections — "each socket is state on one server, so I pin clients with sticky/L4 routing and use a Redis pub/sub backplane plus a user→server registry to deliver to the right box." (4) Re-frame capacity as concurrent connections × memory, not QPS. (5) Pre-empt the lifecycle — heartbeats, reconnect-with-resume, graceful drain on deploy. That's breadth-then-depth: a fast justified protocol pick, then 60% depth on the backplane and connection scaling, which is where the L6/L7 conversation actually lives.
