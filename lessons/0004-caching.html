System Design · Lesson 04 · Phase 1 — Core Concepts

Caching

Trade a little staleness for a lot of speed — and know exactly when that trade is worth making.

Why this lesson, for your mission: Caching is the single most common lever for hitting a latency NFR in an interview. But reaching for it reflexively is a senior tell. The staff move is to justify the cache — confirm there's a read-heavy hot-key problem, then speak fluently about invalidation. "There are only two hard things in computer science: cache invalidation and naming things." Interviewers test whether you respect that.

1 of 6

What a cache is, and why

A cache stores frequently accessed data in fast memory so you avoid repeating an expensive operation. It buys you two things [1]:

  • Latency. A cache hit on Redis takes around 1ms versus 20–50ms for a typical database query [1] — a 20–50× speedup that compounds at scale.
  • Offloading the database. Every read served from cache is a read your database doesn't do, letting it spend its capacity on writes and avoiding premature (expensive) scaling [1].

The catch is the whole reason this lesson exists: a cache holds a copy of the truth. The moment the source changes, the copy is wrong. Everything hard about caching descends from that one fact.

Where caches live

"Cache" is not one box. Data can be cached at several layers between the user and your database, each cheaper to hit than the last:

LayerWhereGood for
Client cacheBrowser / app memoryUser-specific data, avoiding round-trips entirely
CDNEdge, near the userStatic assets — images, video, JS [1]
In-process cacheInside the app serverFeature flags, config — small, rarely-changing data [1]
Distributed cacheRedis / Memcached clusterShared application data across many servers [1]

An in-process cache is fastest (no network hop) but each server has its own copy — they drift, and it doesn't survive a restart. A distributed cache adds a network hop (~1ms) but is shared and survives deploys. In interviews, "a cache" almost always means a distributed cache, and almost always Redis [1].

Caching patterns

This is who writes to the cache, and when. There are four classic patterns. You will use the first one almost every time.

PatternHow it worksTradeoff
Cache-aside
(lazy loading)		 App checks cache. On a miss, app reads the DB, writes the result back into the cache with a TTL, returns it [1]. Default, used ~90% of the time [1]. Only requested data is cached. Cost: a cold miss does extra work, and stale entries linger until TTL or explicit eviction.
Read-through App always talks to the cache; the cache itself fetches from the DB on a miss. App code stays simple, but you need a cache layer that supports it. Same staleness story as cache-aside.
Write-through Writes go to cache and DB synchronously, together. Cache is always fresh; writes are slower (two hops) and you cache data that may never be read.
Write-back
(write-behind)		 Writes hit the cache immediately; the DB is updated asynchronously later. Fastest writes, highest throughput — but if the cache dies before flushing, you lose data. Use only when some loss is tolerable.
Default to cache-aside. It's the pattern you'll describe by reflex: "on a read, check the cache; on a miss, hit the DB, populate the cache with a TTL, and return." Reach for write-through only when you can't tolerate stale reads, and write-back only when you can tolerate losing recent writes for raw write speed.
Check yourself

Which pattern is the default, used about 90% of the time in interviews?

Cache-aside is the reflex default: on a miss, read the DB, populate the cache with a TTL, return.

Reread the box calling out the default pattern.

What breaks if the cache node dies right after a write-back write, before the DB is updated?

Write-back trades durability for write speed: the write only lives in cache until the async flush, so a crash before that flush loses it.

Reread the write-back row's tradeoff column.

Why does write-through make writes slower than cache-aside?

Write-through writes synchronously to both stores on the critical path, so the caller waits for both hops instead of one.

Eviction policies

A cache is finite. When it fills, something must go. That decision is the eviction policy:

PolicyEvicts
LRU — Least Recently UsedThe entry untouched the longest. The sensible default; matches most access patterns.
LFU — Least Frequently UsedThe entry accessed the fewest times. Better when popularity is stable over time.
FIFO — First In, First OutThe oldest inserted entry, ignoring how often it's used. Simple but rarely optimal.
TTL — Time To LiveNot really eviction — every entry self-expires after a set time. Combine with LRU to bound staleness.
Check yourself

Which eviction policy is the sensible default for most access patterns?

LRU tracks recency of access, which matches how most real workloads actually behave: recently used data tends to be used again soon.

Reread the LRU row's second sentence.

When would LFU outperform LRU for choosing what to evict?

LRU can wrongly evict a consistently popular item just because it wasn't touched in the last few seconds. LFU's frequency count survives that noise when popularity is stable.

Reread the LFU row: "Better when popularity is stable over time."

4 of 6

The hard problems

This is the deep-dive gold. Saying "I'll add a cache" is senior. Naming and mitigating these failure modes is staff.

1 · Invalidation & staleness

The hardest part, full stop. When a user updates their profile in the DB, the cached copy is now wrong; you must delete or update it [1]. Two strategies:

  • TTL only: let entries expire. Simple, but you serve stale data for up to the TTL window.
  • Write-time invalidation: on a write, explicitly delete (or update) the key. Fresh immediately, but every write path must remember to do it — easy to miss, hard to test.

The honest answer in an interview is to pick: "TTL of 60s plus delete-on-write for the profile key — I accept up to 60s of staleness if a delete is missed." A concrete pick beats hand-waving.

2 · Thundering herd / cache stampede

When a popular entry expires, many concurrent requests all miss at the same instant and pile onto the database to regenerate it [1] — sometimes enough to take the DB down. Mitigations:

  • Request coalescing (locking): only the first request recomputes; the rest wait for that single result.
  • Staggered / jittered TTL: add randomness to expiry times so keys don't all die together [1].
  • Early recomputation: refresh a hot key before it expires, in the background.

3 · Hot keys

One key — a celebrity's profile, a viral tweet — gets so much traffic it overwhelms a single cache node. Spread the load: replicate the value across multiple keys/nodes, or add a small in-process cache in front of the hot key so most reads never reach the shared cache at all.

4 · Cache penetration

Requests for keys that don't exist (often malicious) always miss the cache and always hit the DB — the cache provides zero protection. Defend by caching the negative result (a "not found" marker with a short TTL), or with a Bloom filter that cheaply rejects keys known not to exist.

And when the whole cache falls over? A full cache outage dumps 100% of traffic onto a DB sized for ~10%. Defenses: a small in-process fallback cache, circuit breakers to shed load, and graceful degradation [1]. Mentioning this unprompted signals you think about failure, not just the happy path.
Check yourself

A popular key expires and floods the database with misses at the same instant. What is this?

A stampede / thundering herd: mitigate with request coalescing (one recompute) or jittered TTLs so keys don't expire together.

Reread the "Thundering herd" subsection heading and its mitigations.

Requests for keys that never exist always miss and always hit the DB. What defends against this?

Cache penetration bypasses the cache entirely because a nonexistent key can never be a hit. Caching the negative result, or filtering it out with a Bloom filter, closes that gap.

Reread the "Cache penetration" subsection.

Why does write-time invalidation fix staleness immediately but TTL-only invalidation not?

TTL bounds staleness only by time, so a key can be wrong for up to the full TTL window. Deleting on write removes the stale copy at the instant of the write instead.

Reread the two invalidation strategies and compare when each removes the stale value.

How does a hot key problem differ from a thundering herd, even though both involve one popular key overwhelming something?

Hot keys are a sustained load-distribution problem on a single node. A stampede is a synchronized burst caused by many clients missing at the same expiry moment.

Redis specifically

Redis shows up in nearly every case study, and not only as a cache. It's a key-value store with a rich set of data structures — strings, hashes, lists, sets, sorted sets, bitmaps, hyperloglogs [2] — which lets a single technology solve several problems at once. (Memcached, by contrast, is a simple key-value store of strings and binary blobs [2] — pick it only when you want pure, dumb caching.)

Redis is effectively single-threaded for command execution. That sounds like a limitation but is a feature: each command runs to completion with no locks, so operations are atomic — which is exactly what makes the patterns below safe.

UseHow Redis does it
CacheStrings/hashes with TTL — the bread and butter [2].
Rate limitingAtomic INCR on a per-user key with expiry — a counter that can't race [2].
LeaderboardsSorted sets keep members ranked by score; top-N is a single command [2].
Distributed locksOne key as a lock to coordinate across servers — e.g. holding a concert ticket during checkout [2].
Sessions / metricsShared store for session data and computed metrics [2].

That versatility — caching, locking, sessions, rate limiting, ranking in one box [2] — is exactly why "use Redis for X" is such a frequent move. Know which data structure backs each use; that's the depth marker.

Check yourself

Which Redis structure most directly powers a ranked leaderboard?

Sorted sets store members by score, so reading the top N is one command — the canonical leaderboard primitive.

Reread the Redis use-case table row for leaderboards.

Why does Redis being single-threaded make an atomic INCR-based rate limiter safe from race conditions?

With no concurrent command execution, there is no window where two clients read-then-write the same counter and clobber each other's update.

Reread the sentence connecting single-threaded execution to "no locks" and "atomic."

Why would you pick Memcached over Redis for a workload, given Redis can do everything Memcached does plus more?

Memcached's narrower feature set is the point: less to configure or misuse when all you need is a plain key-value cache.

How caching shows up in an interview

Sequencing matters as much as the content. Caching is almost never part of your first high-level design pass — the HLD should be the simplest thing that satisfies the functional requirements. You introduce caching in a deep dive, driven by a specific non-functional requirement: "reads must be under 50ms at p99" or "the DB can't take this read load."

★ Staff-level signal Don't reach for a cache reflexively. The senior move is "add Redis." The staff move is the question first: "do we actually have a read-heavy, hot-key problem here?" If reads are infrequent or data changes every request, a cache adds latency and complexity for no benefit [1] — say so and skip it. When you do cache, immediately address invalidation with a concrete pick (TTL + delete-on-write, with a stated staleness budget). Naming the stampede / hot-key / penetration failure modes unprompted is what separates "knows what a cache is" from "has run one in production."
Check yourself

When should you introduce a cache in a system design interview?

Keep the HLD simple; add caching in a deep dive driven by a concrete NFR — and only when reads are frequent and stable.
