Design a Q&A / Forum (StackOverflow / Reddit)

A massively read-heavy content platform where the design lives or dies on three things: caching the hot tail, counting votes at scale, and ranking feeds that change every second.

Why this lesson, for your mission: A Q&A/forum looks deceptively simple — it's "just CRUD with upvotes." That framing is the trap. The staff move is to recognize this as a read-heavy serving problem where 99% of traffic hits a small hot set, votes are a high-contention distributed-counter problem, and "sort by hot" is a ranking system in disguise. A senior builds the CRUD; a staff candidate names the three bottlenecks up front, sizes them, and spends the interview on the deep dives — not the API.

Phase 1 · 0–5 minClarify the problemPin scope and the few NFRs that will drive every later decision.

Ask before you design

  • “How are feeds ranked — new, top, hot?” — Hot ranking blends score and recency and must be recomputed as votes arrive.
  • “Are comments nested arbitrarily deep?” — Nesting depth decides the comment tree storage model.
  • “Does reputation or karma matter for permissions?” — Reputation must be derived reliably from votes.

Functional Requirements

Scope ruthlessly, then say out loud what you're deferring so the interviewer knows you saw it. The core loop of every forum is: ask, answer, vote, browse.

#Users should be able to…
1Post a question and answers (and comment on either).
2Vote (upvote/downvote) on questions and answers.
3Browse feeds sorted by hot / top / new, and page through them.
4Search existing content by keyword, and earn reputation from votes.

Out of scope (state it): moderation tooling, private subforums, badges/gamification details, real-time notifications, edit history.

Non-Functional Requirements

This is where you commit to the priorities that shape every later decision. A forum is overwhelmingly a reading product — the design must optimize the read path and accept eventual consistency on the write path.

PropertyTarget / priority
Read/write ratioHeavily read-heavy — roughly 100:1 reads to writes. This is the dominant fact.
LatencyReads (question page, feed) < 200ms p99; search a bit looser.
AvailabilityHighly available, prioritized over strong consistency for votes/counts.
ConsistencyEventual is fine — a vote count being off by a few for a second harms nobody.
Scale~100M DAU, billions of stored questions/answers, a small viral hot set.

Say to move on → “A heavily read, eventually consistent product. Let me size read skew, vote rate and corpus.”

Phase 2 · 5–10 minEstimate what mattersOnly the numbers that change a decision — say the implication out loud.

Capacity Estimation

Only compute numbers that change a decision. Three matter here: how skewed reads are (does caching pay off?), the vote write rate (does a single counter survive?), and total corpus size (does search need its own store?).

How skewed are the reads?

  • 100M DAU, say ~30 page views each → ~3B reads/day ≈ 35K reads/sec average, multiples higher at peak.
  • Classic long-tail: the front page + a few thousand trending questions absorb the vast majority of traffic. Implication: a cache over a tiny hot set serves most reads — caching isn't an optimization, it's the architecture.[1]

What is the vote write rate, and can one row hold it?

  • Writes are ~1% of traffic → low thousands/sec globally — but they concentrate. A front-page post can take thousands of votes/sec onto one counter.
  • Implication: a single hot row becomes a write-contention hotspot — this is a distributed-counter problem, not a SET count = count + 1.[3]

How big is the corpus?

  • Billions of posts × a few KB of text ≈ tens of TB of content. Implication: the primary store can hold it cheaply, but full-text search over it needs a dedicated inverted index, not LIKE '%...%'.[2]

Interviewer pushback

“Why will a cache work so well here?”

Staff answer: Reads follow a power law: a few thousand hot questions get most traffic, so a small cache gets a hit rate above 95% and cuts database load about 20×.

Say to move on → “Power-law reads make caching the design, and hot posts create counter contention. Let me define entities.”

Phase 3 · 10–17 minAPI & data modelLock the contract and the storage shape before drawing boxes.

Core Entities & API

Four entities. The key modeling choice is that comments form a tree (a comment replies to a comment), while answers are a flat list under a question — get this right and the read query stays cheap.

EntityShape
Questionid, authorId, title, body, tags, score, createdAt.
Answerid, questionId, authorId, body, score, createdAt.
Commentid, parentId, parentType, authorId, body — a node in a tree.
Vote(userId, targetId) → +1 / -1. The pair is unique — one vote per user per target.

Derive the acting user from the auth token, never from the request body.

EndpointPurpose

POST /v1/questions/:id/answersPost an answer to a question. Body: { body }.

GET /v1/search?q=&tags=Full-text search over questions/answers.

Note GET /feed uses a cursor, not an offset — feeds shift constantly, so offset paging causes duplicates and skips.

Data Model

Durable content is relational and read-optimized: answers are clustered under their question, comments carry a materialized path so a whole thread is one prefix scan, and votes are a unique (user_id, target_id) row that makes voting idempotent. Scores, hot rankings and reputation are derived — maintained from the vote event stream in Redis and async workers, never computed on the read path.

Interviewer pushback

“Adjacency list or materialized path for comments?”

Staff answer: A materialized path (or path column) fetches a whole thread in one ordered range query; an adjacency list needs recursive queries.

Say to move on → “Answers are a flat list and comments form a tree. Now the simple HLD.”

Anonymous pages come from the CDN; cache misses assemble question pages behind a Redis cache. Feeds are ranges over precomputed Redis sorted sets. A vote writes the unique vote row and emits one event that drives the score counter, the hot/top ranker (which updates the sorted sets) and reputation. Search is fed by CDC.

High-Level Design

Keep the HLD boringly simple; the cleverness belongs in the deep dives. Trace each request through stateless services in front of a primary store, with a cache, a counter system, and a search index hanging off the side.

ComponentResponsibility & store
Post ServiceCRUD for questions/answers/comments. Writes to the Post Store (relational or wide-column, keyed by id).
Vote ServiceRecords the unique (user,target) vote and increments the target's score via the counter system.[3]
Feed ServiceServes GET /feed for hot/top/new from precomputed, cached ranked lists.
Cache (Redis)Holds hot question pages and the materialized feed lists. Absorbs the bulk of reads.[1]
Search Service + indexElasticsearch/inverted index, fed asynchronously from the Post Store via CDC.[2]
Reputation workerConsumes vote events and updates each author's reputation asynchronously.

Read path: GET /questions/:id → check cache → on miss, read Post Store, assemble answers + comment tree, populate cache. Write path: POST /votes → Vote Service records vote → increments counter → emits an event consumed by the reputation worker and the feed re-ranker.

Interviewer pushback

“Why not recompute feed rankings on every request?”

Staff answer: Ranking all posts per request is expensive. Maintain sorted feed lists per community, updated from vote events and cached.

Say to move on → “Deep dives: caching the hot tail, vote counting, feed ranking, search and comment trees.”

Phase 5 · 27–47 minDeep dives & tradeoffsGo deep where the system breaks; compare alternatives and justify the pick.

Deep Dive 1 — Read-heavy serving: caching the hot tail

With a 100:1 read ratio and a brutal long-tail distribution, caching is the design. The whole goal is to make the common read never touch the database. Two things to cache: rendered question pages and feed lists.

Use Redis as a look-aside cache in front of the Post Store. A question page (body + top answers + counts) is read-mostly and tolerant of brief staleness, so it caches beautifully with a modest TTL. See Lesson 4 · Caching for the eviction and invalidation patterns.[1]

DecisionChoice & reason
StrategyLook-aside (cache-aside) — app checks cache, falls back to DB, writes back on miss.
InvalidationTTL + write-through on edit. A new answer/vote bumps the cached page or lets TTL expire it.
Hot keyA viral question is one key on one shard — replicate it so all nodes can serve it.[1]
★ Staff-level signal The senior says "add a cache." The staff candidate quantifies why it works here specifically: the read distribution is power-law, so a cache holding a few thousand hot items achieves a >95% hit rate and collapses DB load by ~20×. They name the hot-key problem proactively — a single viral post melting one cache shard — and reach for replication of hot keys plus a tiny per-node local cache to absorb the storm, exactly the read-side mirror of the celebrity write-skew from the News Feed lesson.

Deep Dive 2 — Vote counting at scale (the hot counter)

Voting looks trivial until a post hits the front page and takes thousands of votes per second. Naively, every vote is UPDATE posts SET score = score + 1 WHERE id = ? — and that one row becomes a write-contention hotspot, serializing on a single lock.[3] This is a distributed counter problem.

ApproachBehaviorVerdict
One row, +1 per voteAll writes serialize on a single hot row.Melts at scale
Sharded countersSplit into N sub-counters; sum on read. Spreads contention N-way.[3]Good
Batched / asyncBuffer increments in Redis, flush aggregates to DB periodically.Great for hot

The practical answer combines both: accumulate votes in an in-memory counter (Redis INCR, naturally atomic and fast), and asynchronously flush the running total to the durable store. The displayed count is served from Redis — eventually consistent, which the NFRs already permit. The unique (user, target) record (preventing double-voting) is written separately and durably.

Idempotency matters. A vote must be idempotent per user per target: voting twice doesn't add two. Store the (userId, targetId) pair with a uniqueness constraint; the counter only moves on a state transition (none→up, up→down), not on every click. This is the correctness backbone under the fast eventual-consistency front.

Deep Dive 3 — Ranking feeds: hot / top / new

"Sort by new" is trivial (order by createdAt). "Top" is an aggregate over a window (order by score within last day/week). "Hot" is the interesting one — it must blend score and recency so fresh-but-good content outranks old-but-high-score content, and it must decay over time.

Reddit's classic hot formula is essentially log10(score) + age/45000 — a time term that grows steadily so newer posts get a standing bonus, plus a logarithmic score term so the first 10 votes matter far more than votes 1000–1010.[4] The key insight: because the time component increases monotonically, you don't have to constantly re-sort the whole corpus — a post's hot score is computable from (score, createdAt) at write/vote time.

FeedOrder byHow it's served
NewcreatedAt descIndexed range scan; trivial.
Topscore desc, windowedPrecomputed per time window, cached.
HothotScore(score, age)Recompute on vote; keep a cached ranked list.

Don't rank on the read path. Precompute the hot/top lists into a cached, materialized ranking (e.g. a Redis sorted set keyed by hot score) and update it as votes arrive. Reads become a cheap range read off the sorted set; the expensive scoring happens once per vote, not once per page view — separating generation from serving, the same move as feed ranking.

★ Staff-level signal Staff candidates connect the dots between deep dives: the hot counter (DD2) feeds the hot ranking (DD3) feeds the cached feed list (DD1). They note the vote event is the single trigger that fans out to three subsystems — counter, re-ranker, reputation — and argue for an event-driven design (one vote → emit event → consumers) instead of synchronous writes to four places. They also flag that exact global ranking is unnecessary: approximate, eventually-consistent ordering is perfectly acceptable for a feed, and that relaxation is what makes precomputation cheap.

Deep Dive 4 — Full-text search & comment-tree storage

Search: an inverted index, fed asynchronously

You cannot serve keyword search from the transactional store — LIKE '%term%' is a full scan and ignores relevance. You need a dedicated inverted index (Elasticsearch), kept in sync with the Post Store via change data capture so writes don't block on indexing.[2] Search is read-heavy and tolerant of seconds of indexing lag — the perfect candidate for an async, separate store. The full treatment is in Lesson 25 · Post Search.

Comment trees: adjacency list vs. materialized path

Comments are a tree (replies to replies). The storage choice determines how cheaply you can load a whole thread.

ModelHow it worksTradeoff
Adjacency listEach comment stores its parentId.Simple writes; reading a deep tree needs N recursive queries.
Materialized pathEach comment stores its full ancestor path (e.g. 1/4/9).One indexed prefix query loads the whole subtree; paths cost on move.

For a forum, reads dominate and comments rarely move, so materialized path (or a closure table) wins: a single prefix range query fetches an entire thread, which you then assemble into a tree in memory. Most real systems cap nesting depth, which keeps trees shallow and cacheable as part of the question page.

Reputation: derived, asynchronous, idempotent

Reputation is a derived aggregate of vote events (+10 for an answer upvote, −2 for a downvote, etc.). Never compute it on the read path. A reputation worker consumes the same vote-event stream that feeds the counter, applies the rules, and updates a per-user reputation total. Because it replays events, it must be idempotent — each vote event applied exactly once — so reputation stays correct even if events are redelivered.

Interviewer pushback

“A post gets thousands of votes per second. What breaks?”

Staff answer: A single row UPDATE score = score + 1 serializes on a lock. Record idempotent vote rows, aggregate increments asynchronously in batches, and serve slightly stale scores from cache.

Privacy

Content is public by design, but votes and browsing are not. Controls: individual votes are never shown publicly (only aggregates); pseudonymous usernames; IP addresses retained briefly for abuse prevention. Deletion: users can delete posts/accounts — content can be removed or dissociated from the account (licensed content may remain anonymized per terms); caches and search are purged via the same event path. Private communities excluded from CDN caching and search indexing. Minors: age-gated NSFW communities.

Interviewer pushback

“How do you handle vote manipulation and spam?”

Staff answer: Detect voting rings with graph analysis, rate-limit new accounts, weight votes by account trust, and moderation queues fed by reports and classifiers.

Wrap-up · 58–60 minClose strongRecap decisions and tradeoffs in 60 seconds; name what you would do next.

Closing Summary (60 seconds)

A Q&A forum is a read-heavy system with hot counters. Pages for anonymous readers are cached at the CDN and in Redis, so power-law traffic rarely reaches the database. Votes are idempotent rows whose increments aggregate asynchronously into scores. The same vote events update hot-ranking feed lists and reputation. Comments use a materialized path so a thread loads in one query, and posts are indexed in Elasticsearch through change events. At 10× we add cache replicas, shards and search nodes.

Check yourself — retrieval practice

Answer from memory before scrolling back up.

1. Why is caching the central architecture of a Q&A site, not an add-on?

A ~100:1 read ratio plus a power-law hot set means a small cache serves the vast majority of reads — that's the design, not a tweak.

2. What breaks when a front-page post takes thousands of votes per second?

Naive count = count + 1 serializes on one hot row. Shard the counter and batch increments in Redis, flushing async.

3. What makes a "hot" feed harder to serve than "new" or "top"?

Hot mixes score and recency with decay. Precompute it into a cached sorted set on each vote — don't rank on the read path.

4. Why store a comment thread using a materialized path on a forum?

Reads dominate and comments rarely move, so a path prefix query fetches the whole thread at once — far cheaper than recursive lookups.
