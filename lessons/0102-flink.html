Deep Dive: Apache Flink

A record-at-a-time stream processor that gets exactly-once correct results from out-of-order, unbounded data — and how it differs from Spark's micro-batch.

Why this lesson, for your mission: The moment a design needs "react to events in milliseconds, not minutes" — fraud detection, real-time ad aggregation, live leaderboards — the senior answer is "process the stream." The staff answer explains how a stream processor stays correct: event time vs processing time, watermarks for late data, windowing, and checkpointed state for exactly-once. Flink is the canonical true-streaming engine, and knowing its internals lets you defend it against Spark Streaming instead of name-dropping a buzzword.

What it is

Apache Flink is a distributed engine for stateful computation over unbounded and bounded data streams.[1] Its core philosophy is streaming-first: it processes data one record at a time as events arrive, rather than collecting them into batches first. A continuous "unbounded" stream (a Kafka topic that never ends) and a finite "bounded" dataset (yesterday's log files) are both just streams to Flink — batch is simply the special case of a stream with a known end.[1]

This inverts the older Hadoop/Spark mental model, where the primitive is a batch and streaming is bolted on as many tiny batches. In Flink, the primitive is the continuous dataflow, and a bounded job is a streaming job that happens to terminate. That single design choice is why Flink can deliver millisecond latency — there is no batch interval to wait out before a record is processed. (Contrast with Lesson 101 — Spark, whose Structured Streaming is micro-batch by default.)

Internals — the meat

1 · Event time vs processing time

The single most important concept in stream processing is which clock you use.[2]

  • Event time — the timestamp embedded in the record, i.e. when the event actually happened at the source (a click fired at 12:00:03).[2]
  • Processing time — the wall-clock time on the machine when the operator handles the record (it arrived in Flink at 12:00:07, four seconds later).[2]

They diverge because of network delays, retries, backpressure, and mobile clients that buffer offline and dump events hours later. Processing time is simple and low-latency but non-deterministic — replaying the same input gives different window results. Event time gives correct, reproducible results that match reality, at the cost of having to wait for stragglers. Production analytics almost always wants event time. But event-time processing raises a hard question: events arrive out of order, so how does the engine know when it has seen "enough" of time-window 12:00–12:01 to emit its result? That is exactly what watermarks solve.

2 · Watermarks — handling out-of-order & late events

A watermark is a special marker injected into the stream that asserts: "event time has now progressed to T; do not expect any more events with a timestamp ≤ T."[2] It is the engine's notion of completeness — a heuristic threshold that lets event-time windows know when to fire.

Watermarks flow with the data. When a windowing operator receives a watermark for T, it knows every window that ends at or before T is complete and can emit its aggregate. The watermark is generated with a bounded out-of-orderness allowance — e.g. "watermark = max-event-time-seen − 5s" tolerates events up to 5 seconds late.[2] This is the fundamental latency vs completeness tradeoff: a larger allowance catches more stragglers but delays every result; a tighter one fires fast but risks dropping late data.

Late events are records that arrive after the watermark has already passed their window. Flink gives you explicit control: drop them (default), route them to a side output for separate handling, or keep windows open with allowed lateness so a late event re-fires an updated result. Naming this policy is a staff-level detail — "what happens to the click that shows up 10 minutes late?" is a question juniors forget to answer.

3 · Windowing — tumbling, sliding, session

Unbounded streams have no end, so to aggregate you must slice time into finite windows.[2] The three canonical types:

WindowShapeUse it for
TumblingFixed size, non-overlapping, back-to-back (every 1 min).Per-minute counts, hourly rollups — each event in exactly one window.
SlidingFixed size, overlapping by a slide step (5-min window every 1 min).Moving averages, "last 5 min" metrics refreshed often.
SessionDynamic size, closed by a gap of inactivity (no events for 30 min).User activity bursts, sessions — boundaries depend on the data, not the clock.

Windows are keyed (per user, per ad, per device), and each window's partial result lives in state until its watermark fires it. Which brings us to the part that makes Flink hard to operate — and hard to compete with.

4 · Stateful operators & state backends

Most useful stream computations are stateful: a running count, a window's accumulator, the last value seen per key, a join buffer. Flink makes state a first-class, managed primitive — operators read and write keyed state that Flink partitions, persists, and recovers for you.[1] You don't bolt on an external Redis; the state lives with the operator for local, low-latency access.

Where that state physically lives is the state backend:[3]

  • HashMap (heap) backend — state lives as objects on the JVM heap. Fastest access, but bounded by memory and subject to GC pressure. Good for small state.[3]
  • RocksDB backend — state lives in an embedded LSM-tree key-value store on local disk, spilling beyond RAM.[3] This is what lets Flink hold terabytes of state per job (large joins, huge keyspaces) and supports incremental checkpoints — only changed SST files get uploaded, not the whole state. The tradeoff is per-access serialization overhead vs the pure-heap backend.

5 · Checkpointing — Chandy-Lamport for exactly-once

If an operator holds state and a machine dies, you must recover that state consistently — without losing data or double-counting. Flink does this with asynchronous distributed snapshots, a variant of the Chandy-Lamport algorithm.[4]

The mechanism: Flink injects special checkpoint barriers into the stream at the sources. A barrier flows downstream with the records. When an operator has received the barrier on all its input channels (barrier alignment), it snapshots its current state to durable storage (e.g. S3/HDFS) and forwards the barrier onward.[4] Because the barrier cleanly separates "records before the snapshot" from "records after," the set of all operator snapshots forms a globally consistent cut of the entire pipeline — without ever stopping the stream.

What "exactly-once" really means. On failure, Flink restores every operator's state from the last checkpoint and rewinds the sources (e.g. Kafka offsets) to that point. State is exactly-once internally. End-to-end exactly-once output additionally needs either an idempotent sink or a transactional sink (two-phase commit) so replayed records don't produce duplicate side effects. Saying "exactly-once" without naming the sink requirement is the most common interview overclaim.[4]

6 · The job graph

A Flink program is a dataflow graph: sources → transformations (map, keyBy, window, aggregate) → sinks. Flink compiles your logical graph into a physical JobGraph, then parallelizes each operator into subtasks spread across TaskManagers (workers), coordinated by the JobManager (master).[1] A keyBy triggers a network shuffle so all records for a key land on the same subtask (where that key's state lives); chained operators that don't need a shuffle are fused into operator chains to avoid serialization between them. This is the same logical/physical plan idea as MapReduce and Spark, but executed as a long-running, always-on topology rather than a job that starts and finishes.

Flink vs Spark Streaming

Both are distributed, fault-tolerant, JVM-based engines that do windowed aggregation with exactly-once semantics. The architectural fork is true streaming vs micro-batch.[1]

DimensionFlink (true streaming)Spark Structured Streaming (micro-batch)
Processing modelRecord-at-a-time, continuous dataflow.Tiny batches at a trigger interval (a "stream of batches").
LatencyMillisecond / sub-second.Hundreds of ms to seconds, set by batch interval.
Core abstractionStream is primary; batch is a bounded stream.Batch (RDD/DataFrame) is primary; stream is repeated batches.
State & windowingRich keyed state, event time, watermarks, session windows native.Capable, but historically less flexible for complex event-time logic.
Ecosystem fitBest when streaming IS the workload.Best when you already run Spark for batch/ETL/ML and want one engine.

When each wins. Reach for Flink when low latency is a hard requirement and the logic is genuinely stream-native — fraud scoring per transaction, real-time alerting, complex event processing, large stateful joins on the hot path. Reach for Spark when your team already lives in Spark for batch ETL and ML, your latency tolerance is seconds not milliseconds, and operational simplicity (one engine, one skill set) beats squeezing out the last bit of latency. Spark's Continuous Processing mode narrows the latency gap but micro-batch remains its default and most mature path.

When to reach for it — and when NOT

Reach for Flink when…
  • You need sub-second latency on a continuous stream — alerting, fraud, real-time aggregation.
  • Correctness over out-of-order / late events matters — you need event time + watermarks.
  • The job is heavily stateful — large windows, streaming joins, big keyed state (RocksDB, TBs).
  • You need exactly-once stateful processing with consistent recovery.
Do NOT reach for it when…
  • The workload is batch/ETL with no latency pressure — a warehouse or Spark batch is simpler.
  • A few seconds of latency is fine and you already run Spark — don't add a second engine.
  • The logic is stateless and trivial — a Kafka consumer or simple function may suffice.
  • Your team can't carry the operational cost — Flink state, checkpoints, and tuning are non-trivial.
★ Staff-level signal Don't say "I'll use Flink for real-time." Say "reads here are event-time aggregations over an out-of-order stream, so I need watermarks to bound lateness, keyed state in RocksDB for the per-user windows, and checkpointing for exactly-once — Flink gives all three natively, and Spark's micro-batch would add a batch-interval of latency I can't afford." Then show judgement: if the team already runs Spark and the SLA is seconds, you might reject Flink to avoid a second engine. The staff move is grounding the pick in latency + state + correctness, and naming the operational cost you're taking on — not explaining what a window is.

In the interview

Flink shows up as the stream-processing brain in nearly every real-time design — the ad click aggregator, real-time fraud, live dashboards (Lesson 75 — real-time analytics). When you reach the "how do we aggregate the firehose?" moment:

  • Lead with event time. "I'll aggregate on event time with watermarks so late clicks land in the right minute bucket." One sentence proves you know the hard part.
  • Name the state backend. Per-key windows over millions of users → RocksDB state with incremental checkpoints. Don't hand-wave "it keeps state."
  • Claim exactly-once carefully. Checkpoints give exactly-once state; pair with an idempotent or transactional sink for end-to-end. Mentioning the sink caveat is the depth signal.
  • Justify vs Spark out loud. "True streaming for ms latency" vs "micro-batch if seconds are fine and we already run Spark." Naming the rejected alternative is the breadth signal.

Check yourself — retrieval practice

Answer from memory before scrolling back up.

1. What problem does a watermark solve in event-time stream processing?

A watermark asserts no more events with timestamp ≤ T are expected, letting event-time windows fire on completeness.

2. How does Flink take a consistent snapshot without stopping the running stream?

Flink injects barriers (Chandy-Lamport variant); aligned operators snapshot state, forming a consistent global cut live.

3. What is the core architectural difference between Flink and Spark Structured Streaming?

Flink is true record-at-a-time streaming (ms latency); Spark defaults to micro-batch at a trigger interval.

4. Which workload is the WEAKEST fit for choosing Apache Flink?

Latency-insensitive batch ETL on an existing Spark stack adds a second engine for no gain — wrong fit for Flink.
