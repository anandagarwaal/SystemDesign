Design Real-Time Analytics / Event Tracking (Amplitude)

A write-firehose pipeline where billions of raw events become sub-second dashboard queries — ingest cheaply, aggregate in flight, read pre-cooked.

Why this lesson, for your mission: Product analytics (Amplitude, Mixpanel, Heap, GA4) is the canonical "ingest a firehose, serve fast aggregates" interview. It tests four staff-level muscles at once: reliable high-throughput ingestion, the streaming-vs-batch (lambda/kappa) decision, columnar OLAP over row stores, and approximation (HyperLogLog) when exact distinct counts are too expensive. The senior answer stores events and queries them. The staff answer never scans raw events on the read path at all — it decides up front what to pre-aggregate, what to approximate, and what to keep exact.

Phase 1 · 0–5 minClarify the problemPin scope and the few NFRs that will drive every later decision.

Ask before you design

  • “What query types — counts, funnels, retention, unique users?” — Funnels and uniques drive rollup and sketch design.
  • “How fresh must dashboards be?” — Seconds of freshness requires a streaming aggregation layer.
  • “Is exact accuracy required, or are approximate uniques acceptable?” — Approximate HLL uniques make rollups mergeable and cheap.

1 · Functional Requirements

Strip product analytics to the flows that actually shape the design — the write path (SDK → us) and the read path (dashboard → us).

#Requirement
1Client SDKs emit events (page_view, signup, purchase…) with properties; we ingest them reliably (no silent loss, survives offline/retries).
2We durably store the raw event stream so it can be re-processed and explored later.
3Users can query & aggregate: event counts, unique users (DAU/MAU), funnels, retention — sliced by property/time, near real time.
4Users view dashboards that issue many of those aggregate queries with sub-second latency.

Out of scope (say so): SDK auto-instrumentation internals, A/B experiment assignment, identity-resolution/stitching across devices, GDPR deletion workflows, and billing. Name them to bank breadth credit, then defer to spend your time on the pipeline and storage depth.

2 · Non-Functional Requirements

The "-ilities" here are in productive tension: write volume is enormous, but reads must feel instant, and freshness fights cost. Rank them out loud.

NFRTarget / priorityWhy it bites
Write throughput~1M events/sec peak, burstyNo single DB write path survives; need a partitioned log buffer.
FreshnessNear real time, ~seconds to low minutes"Live" dashboards; forces a streaming layer, not nightly batch.
Query latencyp99 < 1s for aggregatesCan't GROUP BY trillions of raw rows; pre-aggregate + columnar.
DurabilityNo silent event lossAnalytics drives decisions; at-least-once ingest with replay.
Scale / costTrillions of stored events, cheaplyRaw to object storage; hot rollups stay small in OLAP.
The tension to name. Streaming gives you seconds of freshness but can drift (late events, processor bugs). Batch over the immutable raw lake gives you correctness but lags. And exact distinct-count (unique users) is memory-murderous at this scale. You resolve all three with the same instinct: do expensive work once on write, approximate where the product tolerates it, keep the raw truth to recompute. That instinct drives every deep dive below.

4 · Core Entities & API

Entities: Event (eventId, userId, deviceId, name, timestamp, properties{}, projectId), User (userId, identify-properties), Rollup (projectId, eventName, dims, windowStart, granularity, count, hllSketch).

EndpointPurpose

Two design tells live here. (a) Batching: SDKs buffer events locally and flush in gzipped batches so a flaky mobile network never drops data and we amortize request overhead. (b) Fast 202: the collector acknowledges as soon as the batch is durably buffered — it never blocks on aggregation.

5 · Data Model

Three tiers of the same events, each with a different retention and shape: the raw lake (immutable Parquet, forever-ish), a recent raw columnar table for funnels and ad-hoc exploration (e.g. 90 days), and rollups whose uniques are stored as mergeable HLL states so any time range can be answered without raw scans. Everything is keyed first by project_id, which is both the tenancy boundary and the primary pruning key.

6 · Data Flow

Follow one event from a tap to a dashboard tile:

  1. Emit → SDK records an event, buffers it on-device, and flushes a batch to POST /v1/events:batch (retries on failure).
  2. Collect → a stateless Collector validates schema/API key, dedups on eventId, appends to Kafka (partitioned by projectId/userId), and returns 202.
  3. Archive → a sink writes the raw stream to an object-storage lake (S3/GCS) — the immutable source of truth for replay & batch recompute.[2]
  4. Aggregate (speed) → Flink[3] consumes Kafka, maintains tumbling windows per (event, dims), and emits counts + HLL sketches for uniques.
  5. Store cooked → rollups are upserted into a columnar OLAP store (ClickHouse/Druid).[4]
  6. Reconcile (batch) → periodic Spark jobs re-aggregate the lake and overwrite rollups for accuracy (lambda).[5]
  7. Serve → the Query service answers GET /insights/* from cooked buckets — never a raw scan.

This is the same two-tier write, pre-aggregated read shape as the Ad Click Aggregator — but here events are not money, so we trade a little accuracy (approximate uniques) for far cheaper reads.

9 · Deep Dives

Deep Dive 1 — High-throughput, reliable ingestion (SDK → Collector → Kafka)

At ~1M events/sec the ingest path's only job is to accept fast and lose nothing — aggregation happens downstream. Three mechanisms make that hold:

ConcernMechanismGuarantee
Flaky clientsSDK buffers on-device, batches + gzips, retries with backoff.[1]Survives offline; amortizes overhead.
OverloadBackpressure: collector returns 429/503; SDK backs off & keeps its buffer.No data dropped under spikes.
DurabilityAppend to Kafka (replicated), ack only after; at-least-once delivery.[2]Crash ⇒ replay, never a silent gap.

At-least-once + dedup, not exactly-once-at-ingest. Forcing exactly-once on the write path would slow ingest. Instead accept duplicates (a retried batch re-sends events) and dedup on the client-generated eventId — the collector checks a recent-id set in Redis, and the aggregation layer is idempotent per eventId within its window. This is the deliberate contrast with the Ad Click Aggregator, where each event was billable and demanded strict exactly-once; here events are cheap, so at-least-once + idempotent dedup is the right, simpler call.

Why a log, not direct-to-DB. Kafka decouples a bursty 1M/s producer from slower, stateful consumers, gives bounded retention for replay (reprocess after a bug), and lets you add new consumers (a new metric, a new warehouse sink) without touching ingest.[2]

Deep Dive 2 — Lambda vs. kappa: streaming for freshness, batch for accuracy

Freshness and correctness pull in opposite directions, so name the architecture explicitly. The speed layer (Flink tumbling windows) gives seconds-fresh counts; the batch layer (Spark over the immutable lake) recomputes authoritative numbers and overwrites drift.[5]

ArchitectureShapeTradeoff
LambdaSpeed (Flink) + batch (Spark) layers, reconciled in OLAP.[5]Two codebases to keep in sync, but maximally robust.
KappaOne stream path; reprocess by replaying the log.[6]Simpler ops; replaying long ranges can be slow/costly.

Late events. Mobile reconnects mean an event can arrive long after its window closed. Use Flink watermarks + bounded allowed-lateness so windows finalize promptly; anything later than the bound is repaired by the batch layer.[3] State the lateness bound — it's a correctness knob, not a default.

Pick. Lead with kappa for its operational simplicity (one pipeline; replay the log to backfill), and add a batch reconciliation only where the product demands ledger-grade accuracy. For most analytics, slightly approximate-but-fresh beats perfectly-accurate-but-late — the opposite of the billing system.

Deep Dive 3 — Columnar OLAP storage vs. row stores

A dashboard query is "sum/count over millions of rows, touching 2–3 columns, filtered by time." Row stores (Postgres/MySQL) read whole rows off disk and choke; columnar OLAP (ClickHouse, Druid, Pinot) stores each column contiguously, so a query reads only the columns it needs and skips the rest.[4]

PropertyRow store (OLTP)Columnar OLAP
I/O per aggregateReads full rowsReads only needed columns[4]
CompressionModestHigh (like-typed columns compress 5–10×)[4]
Best atPoint reads / updatesScans, GROUP BY, time-range rollups
Time pruningIndex lookupsPartition by time; skip non-matching blocks[7]

Partition rollups by (projectId, eventName, day) and sort within partition by timestamp so a time-range query scans only the relevant blocks. This is also where the time-series database concepts (downsampling, retention tiers) apply directly.

Deep Dive 4 — Pre-aggregation/rollups + approximate distinct counts (HyperLogLog)

Two compounding tricks make reads trivial. (a) Multi-granularity rollups: Flink emits minute buckets in real time; cron jobs roll those into hour/day/week. A "last 90 days" query reads ~90 day-rows, not 130k minute-rows — the planner picks the coarsest bucket that satisfies the requested granularity. (b) Approximate uniques: exact COUNT(DISTINCT userId) per slice would need a full id-set per bucket — hundreds of MB each. Instead store a HyperLogLog sketch (~12–16 KB, ~2% error) per (event, dims, window).[8]

HLL's superpower is that sketches are mergeable: union the per-minute sketches to answer a per-day or arbitrary-range unique-user count without re-reading raw events.[8] That mergeability is exactly why it fits the rollup model — see the deeper treatment in Lesson 41 (data structures for big data). Keep counts exact (cheap, additive) but uniques approximate (HLL) — and tell the interviewer the product tolerates ~2% on DAU/MAU but never on revenue.

★ Staff-level signal Say the quiet part: "Events here aren't money, so I'll optimize for cheap, fresh reads — at-least-once ingest with eventId dedup, approximate uniques via mergeable HLL, and exact counts only where they're cheap." Then contrast it explicitly with the Ad Click Aggregator, where billing forced strict exactly-once and zero approximation. Choosing where to be approximate, pre-aggregating on write so reads never scan raw, and defaulting to kappa-with-optional-batch instead of reflexively bolting on a second pipeline — that judgment is what separates staff from senior.

15 · Privacy

Product analytics is behavioral tracking — the core privacy challenge of this system. Consent: SDKs honor consent/opt-out signals (GDPR/ePrivacy, CCPA "do not sell") before sending. Minimization: IP addresses used for geo lookup then dropped; property allow-lists and automatic PII detection (emails, phone numbers in properties) with redaction. Deletion: user deletion requests must reach every tier — ClickHouse mutations/partition rewrites, lake Parquet rewrites (batched), and rollups (HLL can't remove one user, so deletion SLAs rely on recomputing affected windows or accepting aggregate-only residue per policy). Retention: per-plan raw retention; aggregates longer. Residency: EU data kept in EU regions.

Interviewer pushback

“How do you honor a user's deletion request in immutable columnar data?”

Staff answer: Keep user id mappings separate, delete or pseudonymize by rewriting affected partitions on a schedule, and exclude deleted users from future rollups.

18 · Closing Summary (60 seconds)

Real-time analytics is high-throughput ingest feeding cheap, fresh reads. SDKs batch events with ids, and stateless collectors authenticate, deduplicate and append them to Kafka. Flink computes per-minute rollups with mergeable HyperLogLog sketches for unique users, while raw events land in a lake and a columnar OLAP store for ad hoc queries. Dashboards hit rollups first and raw columns only when needed, and the replayable log handles reprocessing. At 10× we add collectors, partitions and OLAP nodes with tiered storage.

Check yourself — retrieval practice

Answer from memory before scrolling back up.

1. Why is at-least-once + dedup preferred over exactly-once on the ingest path here?

Events aren't billable, so the simpler at-least-once path plus eventId dedup keeps ingest fast without inflating counts.

2. Why store a HyperLogLog sketch instead of exact distinct user-id sets?

HLL trades ~2% error for kilobyte-sized, mergeable sketches — union per-minute sketches to get range uniques cheaply.

3. What makes columnar OLAP beat a row store for dashboard aggregates?

Columnar stores read only needed columns and compress them well, so wide scans and GROUP BY are dramatically cheaper.

4. In the lambda model, what job does the batch layer do for the speed layer?

The speed layer gives freshness; the batch layer re-aggregates the immutable raw lake for authoritative, drift-free numbers.
