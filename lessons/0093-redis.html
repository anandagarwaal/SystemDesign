Deep Dive: Redis

One in-memory box that solves caching, ranking, locking, and rate limiting — if you know which data structure and which tradeoff backs each.

Why this lesson, for your mission: Redis is the single most-reached-for technology in an L6/L7 interview. Saying "I'll add Redis" is free; the staff move is knowing why it's fast (single-threaded event loop), what you're trading (durability vs latency in RDB/AOF), and which primitive powers each pattern. This lesson is the depth behind the name-drop — so you can survive the follow-up "and what happens when the primary fails?"

1 of 6

What it is & the data model

Redis (REmote DIctionary Server) is an in-memory data-structure server [1]. The whole dataset lives in RAM, and you address it through a single flat keyspace — but the values are not opaque blobs. Each key points at a typed structure with its own commands, which is what separates Redis from a dumb key-value cache. The core types [1]:

TypeWhat it holdsCanonical use
StringBytes up to 512 MB; ints for atomic INCRCache values, counters, flags
HashField → value map under one keyAn object (a user record) without re-serializing
ListOrdered linked list, push/pop both endsSimple queues, recent-activity feeds
SetUnordered unique membersTags, unique visitors, set algebra
Sorted set (ZSET)Members ranked by a numeric scoreLeaderboards, priority queues, time series
StreamAppend-only log with consumer groupsEvent queues, durable pub/sub
HyperLogLogProbabilistic cardinality counterUnique counts in ~12 KB, small % error
Geo / BitmapGeospatial index / bit array"Nearby" queries; dense boolean flags

The lesson to internalize: in an interview you don't say "store it in Redis," you say "store it in a sorted set keyed by region." Naming the structure is the depth signal.

Internals — the part that wins follow-ups

1 · The single-threaded event loop

Redis executes commands on a single thread, one at a time, via an event loop over multiplexed sockets [2]. Beginners hear "single-threaded" and assume slow — the opposite is true, and understanding why is the whole point.

  • Why it's fine: the work is in RAM, so each command is microseconds; the bottleneck is the network/syscalls, not CPU. One thread saturates a NIC before it saturates a core [2].
  • The gift: no locks, no race conditions inside Redis. Every command — including INCR and multi-key scripts — is atomic by construction [2]. This is precisely what makes the rate-limiter and lock patterns below correct.
  • The implication / trap: a single slow command blocks everything. KEYS * or a giant ZRANGE over millions of elements stalls the whole server. Staff answer: avoid O(N) commands on big keys; use SCAN. (Modern Redis offloads I/O and key-eviction to helper threads, but command logic stays single-threaded [2].)

2 · Persistence: RDB vs AOF — the durability tradeoff

RAM is volatile, so Redis offers two on-disk persistence modes [3]. This is the most common "go deeper" prompt, because it is a pure durability-vs-performance tradeoff.

RDB (snapshot)AOF (append-only file)
What it writesPoint-in-time fork+dump of the whole datasetA log of every write command, replayed on restart
DurabilityLose everything since the last snapshot (minutes)Lose ≤1s with everysec fsync; near-zero with always [3]
Restart speedFast — load one compact binary fileSlower — replay the log (mitigated by rewrite/compaction)
Runtime costPeriodic fork can spike latency/memoryConstant small write + fsync overhead
The pick: for maximum durability, run AOF with everysec (≤1s loss) — the common default. For fast backups/restores, RDB. Production often runs both: AOF for recovery, RDB for compact backups [3]. And the honest caveat — even AOF always doesn't make Redis a system of record; if you need true ACID durability, your source of truth is the database, and Redis is the accelerant.
Check yourself

Which persistence choice limits data loss to about one second of writes?

AOF with everysec fsync bounds loss to ≤1s; RDB loses everything since the last snapshot, which can be minutes.

Look at the "Durability" row of the RDB vs AOF table.

Why does single-threaded execution make a multi-step command like INCR automatically safe from race conditions, with no locks needed?

With one thread executing commands one at a time, there is no window for another command to read or write the same key mid-operation — atomicity falls out of the execution model itself.

Think about what "race condition" requires: two things running at once. Does Redis's event loop ever allow that for command execution?

What actually breaks if you run KEYS * on a Redis instance holding millions of keys?

Because command logic is single-threaded, one O(N) command monopolizes the only thread — every other client waits. That is exactly why SCAN exists as the incremental alternative.

Reread "The implication / trap" bullet — what does "stalls the whole server" mean concretely for a single-threaded model?

Eviction & TTL — what happens when RAM fills

Set maxmemory, and when Redis hits it the eviction policy decides what goes [4]. Two failure shapes to know:

  • noeviction (default): reject writes with an error once full. Safe for a system of record; dangerous for a cache (writes start failing).
  • allkeys-lru / allkeys-lfu: evict the least recently / frequently used key. The right choice for a cache — let cold data fall out. LFU resists one-off scans polluting the cache [4].
  • volatile-* variants only evict keys that carry a TTL, leaving persistent keys alone.

TTL itself is per-key expiry (EXPIRE / SET ... EX). Redis expires keys lazily (on access) plus a background sampler — so an expired key can briefly occupy memory before it's reclaimed. The memory model: data + per-key overhead live in an allocator (jemalloc); fragmentation and that overhead mean usable data is meaningfully less than raw RAM — size with headroom.

Check yourself

What happens under noeviction once maxmemory is reached?

noeviction is the default: it protects existing data by refusing new writes rather than deleting anything.

Reread the first bullet under eviction policies.

Why is allkeys-lru the right eviction policy for a cache, but noeviction is right for a system of record?

A cache is disposable and backed by a real store, so evicting cold keys is safe. A system of record is the only copy, so losing data to eviction is unacceptable — better to reject the write.

Ask what recovers the data after an eviction in each case — is there another copy anywhere?

Patterns it powers

Each pattern is "a data structure + an atomicity guarantee." That framing is the staff-level fluency.

PatternStructure & mechanism
CacheString/hash + TTL, cache-aside. The default use — see Lesson 4 · Caching for invalidation and stampede.
Rate limitingAtomic INCR on a per-user windowed key with EXPIRE; a Lua script for sliding-window. See Lesson 22 · Rate Limiter.
LeaderboardSorted set: ZADD to score, ZREVRANGE for top-N, ZRANK for "my rank" — all log-time. See Lesson 47 · Leaderboard.
Distributed lockSET key val NX PX ttl for a single-node lock; Redlock across N independent nodes for HA — with caveats below.
Pub/SubFire-and-forget channels. No persistence — a subscriber that's offline misses the message.
Queues / StreamsLists for simple queues; Streams add an append-only log + consumer groups + acks for at-least-once delivery.
Redlock caveat (say this unprompted). A single-node lock vanishes if that node dies. Redlock spreads the lock over N independent masters and needs a majority — but Martin Kleppmann's well-known critique shows it isn't safe for correctness under GC pauses, clock skew, or network delays. The staff stance: use Redis locks for efficiency (avoid duplicate work), and if you need correctness, add a fencing token or use a consensus store (ZooKeeper/etcd) instead.
Check yourself

What is the correct staff-level caveat about using Redis for locking?

Redlock can break under GC pauses and clock skew; use it for efficiency and reach for fencing tokens or a consensus store for correctness.

Reread the Redlock caveat box — what's the "staff stance"?

Why can't Redis Pub/Sub guarantee a subscriber receives every message, while Streams can?

Pub/Sub is fire-and-forget with no backing log, so an offline subscriber simply misses messages. Streams persist an append-only log with consumer groups and acks, so a consumer can catch up later.

Scaling & high availability

A single Redis is one process on one machine — bounded by one box's RAM and exposed to that box's failure. Three mechanisms address this [5]:

MechanismWhat it gives you
ReplicationAsync primary→replica copies for read scaling and a warm standby. Async means a failover can lose the last writes the primary hadn't shipped yet.
SentinelA monitoring quorum that detects a dead primary and auto-promotes a replica, updating clients. HA without sharding.
Redis ClusterHorizontal sharding across nodes via 16384 hash slots; each key maps to a slot via CRC16, each node owns a slot range [5]. Scales beyond one box's RAM.

Hash slots (not consistent hashing of keys directly) make resharding clean: to rebalance, you move slots between nodes, not rehash every key. Multi-key operations only work when keys share a slot — force that with hash tags like user:{42}:cart, where only the brace-wrapped part is hashed.

Redis vs Memcached

RedisMemcached
Data modelRich typed structuresOpaque string/blob only
Persistence / HARDB+AOF, replication, ClusterNone — pure volatile cache
ThreadingSingle-threaded logic, atomic opsMulti-threaded, scales cores for raw GET/SET
Pick it whenYou need ranking, locks, counters, durabilityYou want dead-simple, multi-core key-value caching

Default to Redis; reach for Memcached only when the job is genuinely "a big, dumb, multi-threaded cache of strings" and you want nothing else.

★ Staff-level signal The senior answer is "use Redis." The staff answer leads with the tradeoff before being asked: "Redis as a cache-aside layer, AOF everysec since this is best-effort and the DB is the source of truth, allkeys-lru eviction, and Cluster with hash slots once we outgrow one node's RAM." You proactively flag the sharp edges — async replication can lose writes on failover, Redlock isn't a correctness lock, an O(N) command blocks the single thread — and you don't over-explain that it's in-memory. Picking a config and naming its failure mode in one breath is the move.

How does Redis Cluster decide which node owns a given key?

CRC16 maps each key to one of 16384 hash slots; nodes own slot ranges, so resharding moves slots rather than rehashing keys.

Reread the Redis Cluster row of the scaling table.

Why can promoting a replica after a primary failure silently lose recent writes?

Async replication means the primary can ack a write to the client before shipping it downstream. If it crashes in that gap, the promoted replica never had that write.

Look at the "Replication" row — what does "async means a failover can lose the last writes" imply about acknowledgment timing?

Why do multi-key operations in Redis Cluster require a hash tag like user:{42}:cart?

Without a shared hash tag, related keys could land on different nodes, and multi-key commands can't span nodes. The tag forces only the tagged substring into the hash, colocating the keys.

In the interview

Redis almost never belongs in your first high-level pass. It enters in a deep dive, pulled in by a specific NFR — a latency target, a read-load problem, a "rank users by score" functional requirement. When it does, drive the conversation in this order: (1) which structure (sorted set, hash, string-counter), (2) why it's safe (single-threaded atomicity), (3) the durability/eviction config and what you're trading, (4) how it fails and HA's answer (replication lag, Sentinel/Cluster). Hitting all four unprompted is the difference between mentioning Redis and owning it.

Check yourself

Why does Redis "almost never belong in your first high-level pass," instead entering only via a deep dive?
