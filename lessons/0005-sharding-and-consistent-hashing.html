Sharding & Consistent Hashing

When one machine isn't enough, you split the data across many — and the hard part is deciding how.

Why this lesson, for your mission: At L6/L7, sharding is rarely the interesting part — anyone can say "shard the database." The signal is in the shard key you pick, whether it matches the access pattern, and whether you name the hot-partition risk and its fix before the interviewer probes. This lesson gives you the vocabulary and the judgment to do that cleanly.

1 of 6

Scale up, then scale out

There are two ways to handle more load. Vertical scaling (scaling up) means a bigger box: more CPU, more RAM, faster disks. It's the simplest move and you should reach for it first — a well-tuned single database with read replicas handles far more than most candidates assume.[1] But a single machine has a ceiling: you eventually run out of the biggest instance money can buy, and a single node is a single failure domain.

Horizontal scaling (scaling out) means more boxes, each holding a slice of the data. Splitting one logical dataset across many machines is called sharding (or partitioning — the terms are used interchangeably). Each machine owns a shard (a partition) of the whole.

You shard when you've genuinely outgrown one node: storage in the terabytes, writes in the tens of thousands per second, or read volume that replicas can't absorb.[1] The biggest mistake candidates make is sharding too early — it adds real complexity (cross-shard queries, rebalancing, hotspots), so it should be the answer to a measured limit, not a reflex.[1]

Check before continuing

Splitting one dataset across many machines, each owning a slice, is called what?

Horizontal scaling adds more boxes and splits data across them; sharding and partitioning name that split.

Reread the difference between vertical (bigger box) and horizontal (more boxes).

Why does the lesson treat sharding too early as "the biggest mistake," rather than a safe default?

Every shard is a new failure domain and a new cross-shard query problem. That cost is only worth paying once one node genuinely can't keep up.

Two ways to split: range vs hash

Once you've decided to partition, you need a rule that maps each row to a shard. There are two classic strategies.[2]

Range partitioning assigns contiguous ranges of the key to each shard — e.g. users A–F on shard 1, G–M on shard 2. Hash partitioning runs the key through a hash function and uses the result to choose a shard, scattering neighbours far apart.

StrategyGood atBad at
Range (by key range)Range scans — "all events from March" sit together on a few shards. Natural for time-series and sequential data.Hot spots: a popular range (today's date, latest IDs) hammers one shard while others idle.[1]
Hash (by hash of key)Even spread — load is distributed across all shards, so no single shard is naturally a bottleneck.[1]Range queries die: adjacent keys land on different shards, so "all events from March" must fan out to every shard.[2]

The tension is the whole point: hashing buys even load but destroys locality; ranges buy locality but invite hotspots. DDIA notes some systems split the difference with compound keys — hash the first part to spread the data, then keep a sorted secondary part for ranged scans within a partition (e.g. hash user_id but sort that user's posts by timestamp).[2]

Check before continuing

Which strategy gives even load but makes "all rows from last March" expensive to query?

Hashing scatters adjacent keys across shards, so range scans fan out to every shard. Range partitioning keeps them together but risks hotspots.

Look at the "Bad at" column for the Hash row.

Why does a compound key hash the first part but keep the second part sorted, instead of hashing the whole key?

The compound key gets both properties at once: even spread from the hashed prefix, and cheap local range scans from the sorted suffix.

3 of 6

The shard key is the decision

The shard key (a.k.a. partition key) is the field you split on, and choosing it is the architectural call — almost everything else follows from it. Two forces pull on the choice:

  • Spread load evenly. A key with high cardinality and uniform access keeps every shard roughly equally busy.
  • Match the access pattern. Pick a key so the queries you run most often hit one shard, not all of them. On Instagram, sharding posts by user_id keeps a user's posts, likes, and comments on one shard[1] — a profile page is one shard's work. But a global query like "trending posts" must now hit every shard and aggregate.[1]

These two forces often conflict, and resolving that tradeoff out loud is the senior move. The trap that turns it into a staff conversation is the hot partition (the "celebrity problem"): one key gets wildly disproportionate traffic — Taylor Swift's shard getting hammered while the rest sit idle.[1] Even a perfect hash can't save you, because all of one celebrity's reads/writes share a single key.

★ Staff-level signal Derive the shard key from the access pattern, then name the hot-partition risk and a mitigation before you're asked. For a chat app: "I'll shard messages by channel_id so a channel's history is one shard — but a celebrity AMA channel becomes a hot partition. I'd salt the key (channel_id:bucket, fanning that one channel across N sub-shards) or give known celebrity entities a dedicated path — a separate cache or replica tier — rather than letting them sit in the general pool." Naming the failure mode and the fix unprompted is exactly the breadth-then-depth judgment interviewers grade at L6/L7.
Check before continuing

A hash spreads different keys evenly across shards, but it cannot split the traffic for a single key. One celebrity's key is still one key.

Why naive hashing breaks: the rebalancing problem

The obvious way to hash is shard = hash(key) % N, where N is the number of nodes. This spreads keys evenly and is trivial to implement — until N changes. Add or remove one node and N changes, so hash(key) % N changes for almost every key.[1]

Concretely: add one node to a 10-node cluster and roughly 90% of your data has to move to a new home.[1] That's a storm of network traffic and cache misses every time you scale — exactly when you can least afford it. Naive modulo hashing makes the cluster brittle precisely at the moment of growth.

Check before continuing

You add one node to a 10-node cluster using hash(key) % N. Roughly how much data must move?

Changing N changes hash(key) % N for nearly every key, so ~90% remaps. Consistent hashing is what gets you the ~10% case.

Reread the sentence right after the modulo formula.

Why does changing N in hash(key) % N remap almost every key, instead of just the keys near the new node?

There's no locality in modulo arithmetic — the output for a given key depends entirely on N, so one new node scrambles the mapping for almost everyone.

Think about what the formula actually computes when N changes from 10 to 11.

5 of 6

Consistent hashing: move only K/N keys

Consistent hashing fixes the rebalancing problem. The mental picture is a ring: imagine the entire hash output space (say 0 to 2³²−1) bent into a circle.[1]

How the ring works
  • Hash each node to a point on the ring (e.g. hash(node_id)).
  • Hash each key to a point on the same ring.
  • A key is owned by the first node you hit walking clockwise from the key's point.

Now add a node. It lands at one spot on the ring and claims only the keys in the arc between it and the previous node clockwise — every other key stays exactly where it was.[1] Remove a node and its keys simply roll over to the next node clockwise. On average only about K/N keys move (K keys, N nodes) instead of nearly all of them — adding one node to a 10-node ring moves ~10%, not ~90%.[1]

Virtual nodes

Plain consistent hashing has a flaw: with few nodes placed randomly, the arcs are uneven, so some nodes own far more of the ring than others. The fix is virtual nodes — each physical node is hashed to many points around the ring (say 100–200 "vnodes"). This smooths the distribution, and when a node leaves, its load is spread across many neighbours instead of dumped entirely on one.[2] Virtual nodes also make it easy to give beefier machines more vnodes (more capacity), and they're what real systems actually deploy.

Who uses it. Distributed caches like Memcached and Redis Cluster use consistent hashing to spread keys across cache nodes; distributed databases like Cassandra and DynamoDB use it (with virtual nodes) for sharding so nodes can join and leave elastically.[1] Dynamo's original paper is where much of this entered mainstream practice.
Check before continuing

On the hash ring, which node owns a given key?

A key belongs to the first node encountered moving clockwise from the key's point. Adding a node only steals the arc behind it.

Reread the three bullets under "How the ring works."

What breaks if you use plain consistent hashing with just a few real nodes and no virtual nodes?

Few random points on a ring rarely divide it evenly. Vnodes turn one lumpy node into many small points, smoothing load and spreading failover across many neighbours.

How it shows up in an interview

Keep the two ideas distinct, because they answer different questions:

ConceptBring it up when…
ShardingOne DB can't hold the data or serve the throughput. State the trigger (storage / write rate / read rate), then name your shard key and justify it from the access pattern.
Consistent hashingNodes come and go and you want elastic scaling without massive data movement — distributed caches, Cassandra/Dynamo-style stores. It's the how behind a shard key that survives resizing.

You rarely need to derive the ring math unless asked — saying "I'll use consistent hashing for the shard key so we can add nodes without remapping everything" is usually enough signal.[1] Spend your words instead on the shard key and the hotspot mitigation; that's where the depth lives.
