Key Technologies Tour

Six workhorse technologies, on a reference card — what each is, its killer feature, and exactly when to reach for it.

Why this lesson, for your mission: A senior candidate says "I'll use a database and a queue." A staff candidate names PostgreSQL for the transactional core and Kafka for the durable event log — each with a one-line justification tied to the requirement on the whiteboard. This lesson is your fast-recall deck so you can do exactly that, and just as importantly, know what each tool is not for.[1]

How to use this card

This is a reference, not a tutorial. The job in an interview is breadth-then-depth: name the right tool quickly, justify it in one line, and be ready to go deep on the one or two that matter to your design.[1] Don't try to compare SQL vs NoSQL in the abstract — pick the right tool for the requirement and move on.[1]

PostgreSQL and Redis

1 · PostgreSQL / relational — the strong default

What it is: a relational database — structured tables, SQL, decades of tooling. Killer feature: ACID transactions plus arbitrary joins and rich index types (B-tree, multi-column, geospatial, even GIN for full-text).[1] Reach for it when: you have transactional data with relationships and need correctness — orders, payments, users. Start here by default and justify a move away only when a real requirement forces it. It scales further than people assume: read replicas, partitioning, and connection pooling carry you a very long way.

2 · Redis — the in-memory swiss army knife

What it is: an in-memory key-value store with first-class data structures.[2] Killer feature: microsecond latency, plus the data structures unlock whole patterns — INCR with TTL for a rate limiter, a sorted set (ZADD/ZRANGE) for a leaderboard, SETNX / Redlock for a distributed lock, and pub/sub for fan-out.[1] Reach for it when: you need a cache, a counter, a leaderboard, a lock, or ephemeral session state. Prefer it over Memcached for the richer toolbox.[1] Not your source of truth, and don't ask it to do search.

Check before continuing

Why is PostgreSQL the recommended starting default in a design interview?

Correctness plus flexible querying covers the common case; you justify moving away only when a real requirement forces it.

Reread the "1 · PostgreSQL" paragraph's killer feature line.

What breaks if you tried to build a live top-N leaderboard on plain Postgres instead of a Redis sorted set?

Redis's sorted set keeps members ordered by score in memory, so ZRANGE returns ranked results in O(log n). Postgres would need to sort or scan an index on every read.

Think about what data structure ZADD/ZRANGE actually maintains, and what the alternative costs on disk-backed rows.

Cassandra and DynamoDB

3 · Cassandra — write-optimized at scale

What it is: a wide-column, leaderless distributed database.[1] Killer feature: an append-only LSM-tree storage engine that makes writes cheap, with no single leader to bottleneck and tunable consistency (you pick the read/write quorum per query). Reach for it when: ingest is write-heavy and predictable — time-series, event logs, IoT, messaging — and you need horizontal, multi-region scale. The catch: you design the table around the query before you write a row; ad-hoc queries, joins, and transactions are out.

4 · DynamoDB — managed key-value with predictable latency

What it is: AWS's fully managed key-value / wide-column store.[1] Killer feature: single-digit-millisecond latency at effectively any scale with zero operational overhead. Reach for it when: your access patterns are known up front and you want managed scaling — this is the home of access-pattern-first modeling and single-table design (you co-locate related items under composite keys so one query serves a screen). Pricey for bulk storage (~$1.25/GB/mo vs S3's $0.023), so keep blobs in S3 and references in Dynamo.[1]

Check before continuing

What is the design catch that comes with choosing Cassandra?

Cassandra trades query flexibility for write throughput: model the table around the access pattern upfront, because ad-hoc queries, joins, and transactions are unavailable later.

Reread the last sentence of the Cassandra paragraph.

Why does the lesson recommend storing large blobs in S3 with only a reference in DynamoDB, rather than the blob itself in Dynamo?

At ~$1.25/GB/mo versus S3's ~$0.023/GB/mo, storing bulk bytes in Dynamo is a large and needless cost multiplier. Keep the cheap object store for bytes, the fast key-value store for metadata.

Kafka and Elasticsearch

5 · Kafka — the durable, replayable log

What it is: a distributed append-only log that doubles as a message queue and event store, retaining data for a configurable window.[1] Killer feature: durability + retention means consumers can replay from any offset, and many independent consumer groups can read the same partition at their own pace.[1] Reach for it when: you're streaming events, decoupling producers from consumers, smoothing bursty load, or doing event sourcing — e.g. a banking ledger where every transaction is stored and replayable.[1] Don't put it on a synchronous path with a tight (<500ms) latency budget.[1]

6 · Elasticsearch — search, not storage

What it is: a Lucene-based search and analytics engine.[1] Killer feature: the inverted index — it maps terms to documents, so full-text, fuzzy (typo-tolerant), and faceted queries are fast where a SQL LIKE scan would crawl.[1] Reach for it when: you need full-text search, autocomplete, or log/analytics aggregation — think tweet search or event search. The staff move: treat it as a derived index fed from your primary store (often via a Kafka/CDC pipeline), never as your source of truth.

★ Staff-level signal The move from senior to staff is precision of vocabulary and knowing the boundaries. Don't say "a database" — say "Postgres for the transactional order table, because we need ACID across the payment and inventory writes." Don't say "a queue" — say "Kafka, because we need replay for the audit log and three teams consume the same stream independently." Equally, signal the negatives: "Elasticsearch will index this for search, but it's not the source of truth — Postgres is, and we stream changes into ES via CDC." Naming what a tool is not for is what tells the interviewer you've actually run these in production.[1]
Quick decision reflexes
  • "I have relationships" → not a reason on its own; NoSQL handles relationships too.[1] Reach for Postgres because you need transactions + ad-hoc queries.
  • "I need it fast / counted / ranked" → Redis.
  • "Firehose of writes" → Cassandra (or DynamoDB if you want it managed on AWS).
  • "Decouple, buffer, or replay events" → Kafka.
  • "Search by text" → Elasticsearch, fed from your primary store.
Check before continuing

Why can several independent teams each replay the same Kafka topic from their own offset?

Retention plus per-consumer-group offsets is the mechanism: the log stays put, and each group moves through it independently.

Reread "Killer feature" under Kafka — what two properties combine to enable replay?

Why does the lesson warn against putting Kafka on a synchronous path with a sub-500ms latency budget?

Durability and replication are exactly what make Kafka good for async decoupling, but that same overhead is a poor fit when a caller is blocked waiting on the answer within milliseconds.

Think about what durability and multi-consumer fan-out cost you in latency versus a direct synchronous call.

Why does the staff-level move keep Elasticsearch fed via CDC from Postgres instead of writing to both directly from the application?

Writing to two systems from the app risks partial failure and divergence. CDC streams changes from the already-committed source of truth, so the index can never get ahead of or contradict it.

Think about what happens if an app write to Postgres succeeds but the parallel write to Elasticsearch fails.

Across all six technologies, why does naming what a tool is NOT for signal staff level more than naming what it IS for?

Anyone can repeat a killer feature from documentation. Knowing where a tool breaks down, like Kafka's latency floor or Dynamo's blob cost, comes from having actually operated it.

Both Cassandra and DynamoDB are write-optimized wide-column-style stores. What is the actual deciding factor between them?

The two solve the same shape of problem; the choice comes down to operational ownership, not raw capability, since both need query-first modeling and neither does joins or transactions.
