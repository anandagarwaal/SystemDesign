System Design · Lesson 50 · Phase 4 — Case Study · Hard

Design a Recommendation System

"Customers who bought this also bought…" and the Netflix home row. The ML is a detail; the win is a two-stage serving system that returns ranked items in tens of milliseconds.

Why this lesson, for your mission: Recommendations is the interview where candidates panic about machine learning and forget they're system designers. At L6/L7 the signal is the opposite: treat the model as a black box and design the system around it. The load-bearing insight is the two-stage architecture — cheap candidate generation narrows millions of items to hundreds, then an expensive ranking model scores only that shortlist. Pair that with an offline pipeline that precomputes embeddings/features and an online tier that serves in <~100ms, and you've shown the staff-level move: separating what's slow and batchable from what's fast and online.

Phase 1 · 0–5 minClarify the problemPin scope and the few NFRs that will drive every later decision.

Ask before you design

  • “Which surface — home feed, related items, or both?” — A context item changes retrieval from user-to-item to item-to-item.
  • “How fresh must recommendations be after a user interaction?” — Session-level freshness needs online features, not just daily batch.
  • “What's the business objective — clicks, watch time, purchases?” — The objective defines the ranking label and the A/B metrics.

1. Functional Requirements

Keep scope narrow. The product is "given a user (and optionally a context item), return a ranked list of items they're likely to engage with." Everything else — the ML training loop internals, search, ads — is explicitly out of scope so you can spend the budget on the serving system.[1]

#Users should be able to…Note
1Get a personalized feed of recommended itemsHome page / "For You" row, ranked by predicted engagement
2See "related to this item" recommendations"Customers who bought this also bought…"; item-to-item
3Have their interactions shape future recsClicks, watches, purchases feed back into the model

The third item is what makes this a pipeline, not a CRUD app: the system must close the loop from interaction → training data → updated model → better recs.

2. Non-Functional Requirements

State the target, not just the "-ility." Three NFRs define this design.[1]

FreshnessNew items recommendable in minutes–hours; recs reflect recent behaviorCold-start handling; streaming features; periodic re-index

The headline tension is low-latency serving vs scale: you cannot run a heavy model over millions of items inside a 100ms request. That single constraint forces the entire two-stage architecture.

3. Capacity Estimation

Only the numbers that change the design. Two matter here, and they pull in opposite directions.

QuantityEstimateDesign implication
Catalog size~10M itemsScoring all 10M with a deep model per request is impossible in 100ms → must narrow first.
Serving QPS100M DAU × a few rec requests → ~10k–100k req/s peakEach request fans out to retrieval + ranking → ranking model must be cheap per candidate and run on a shortlist of ~100s.
Interaction eventsBillions/day of clicks, views, purchasesFirehose → streaming ingest + batch storage; this is the training-data and feature source.
Embedding store10M items × ~256-dim float vector → a few GBSmall enough to hold in an in-memory ANN index → fast retrieval.
The number that forces the architecture. 10M items × 10k–100k QPS means a brute-force "score everything" approach would need to evaluate billions of item-scores per second. That's absurd. So the system must do cheap retrieval to get from 10M → ~hundreds, then spend its model budget ranking only those. Latency × catalog size is the constraint that creates candidate generation → ranking.[2]

Interviewer pushback

“Why not rank the whole catalog with the best model?”

Staff answer: 10M items × a deep model per request is impossible in 100 ms. Retrieve ~500 candidates cheaply with ANN, then rank only those.

Say to move on → “We can't score 10M items per request in 100 ms, so we narrow first. Let me define entities and the API.”

5. Data Model

The model is split along the offline/online line. Offline tables are append-only and time-stamped for point-in-time correctness (training must only see features as they were at impression time). Online stores hold the latest features and embeddings keyed by entity id. The most important and most-forgotten table is the impression log: what was shown, with which model version and features — without it there is no clean training data.

6. Data Flow — interaction to recommendation

This is an ML pipeline, so trace the loop once before drawing boxes. There are two clocks: a slow offline clock (hours) and a fast online clock (milliseconds).[1]

  1. Collect: the app emits interaction events to a stream; they land in a data lake / warehouse as training data and feature material.[3]
  2. Train (offline, batch): periodic jobs train the retrieval and ranking models on logged interactions; produce fresh user + item embeddings.[2]
  3. Index (offline): item embeddings are loaded into an ANN index; features are written to a feature store for fast online lookup.[3]
  4. Serve (online): a request fetches the user's vector/features → candidate generation retrieves ~hundreds → ranking scores them → return the top N.[2]
  5. Loop: what the user does with those recs becomes step-1 events → the model gets better. The feedback loop is the product.

9. Deep Dives

This is 60% of the interview. Four hard parts, each with the alternative and a justified pick. Keep the ML at "interview depth" — name the technique, explain why the system is shaped that way, don't derive loss functions.

Deep Dive 1 — The two-stage funnel: candidate generation → ranking

You can't run a high-quality model over 10M items in 100ms, and you don't need to — most items are obviously irrelevant. So split the work into two stages with opposite tradeoffs, the architecture popularized by YouTube's deep-learning recommender.[2]

StageJobTradeoff
Candidate generation10M → ~hundreds. High recall, cheap, approximate.Few features, fast lookup (ANN). OK to be imprecise — just don't miss good items.
Ranking~hundreds → ordered top N. High precision, expensive.Rich features per (user,item), heavy model. Affordable only because the set is small.

The funnel is the whole trick: precision is expensive, so you only pay for it on a set that recall already shrank. Many systems add a third re-ranking / filtering step for business rules — remove already-seen items, enforce diversity, apply region/policy filters — after scoring.[2]

Why two stages and not one big model? A single model good enough to rank would be far too slow to evaluate 10M times per request; a model fast enough to score 10M items would be too weak to rank well. Splitting lets each stage optimize a different objective — recall cheaply, then precision expensively — which is exactly the latency × scale constraint from capacity estimation, solved.

Deep Dive 2 — Retrieval: collaborative filtering vs content-based vs embeddings/ANN

Candidate generation needs a way to go from "this user/item" to "similar items" fast. Three families, and the modern answer combines them via embeddings.[2]

ApproachIdeaWeakness
Collaborative filtering"Users like you liked X." Learns from the interaction matrix, no content needed.Cold start: useless for brand-new users/items with no interactions.
Content-based"Similar to what you liked," using item features (genre, text, category).Handles new items, but stays in a filter bubble; needs good features.
Embedding + ANN (pick)Learn dense vectors for users and items; retrieval = nearest neighbors.Needs a training pipeline + an index, but is fast and unifies both signals.

The modern default is the two-tower model: one tower encodes the user (history, profile), another encodes the item (content), trained so a user vector lands near items they engaged with.[2] At serving time you precompute every item vector into an ANN index and, per request, embed the user once and do an approximate nearest-neighbor search to retrieve candidates in single-digit milliseconds. This is exactly the vector-search machinery from Lesson 40, Vector Databases — say "ANN index over item embeddings" and the interviewer knows you've connected the dots.

In practice you run several candidate generators in parallel (embedding ANN, recent-popular, content-based, "also bought" co-occurrence) and union their outputs — diversity of sources guards against any one being weak.[2]

Deep Dive 3 — Offline batch vs online serving, and the cold-start problem

The defining architectural line is the offline/online split. Anything slow, heavy, or shared across users is precomputed offline; only the per-request, per-user work happens online.[3]

WorkWhereWhy
Train models, compute item embeddingsOffline (batch, hours)Expensive, shared by all users, doesn't change minute-to-minute.
Build ANN index, write feature storeOffline → publishedPrecompute so the online path is a lookup, not a computation.
Embed the user, retrieve + rankOnline (ms)Depends on this request's user/context; can't be precomputed for everyone.

Precompute vs real-time is a spectrum, not a binary. For very high-traffic or stable surfaces you can precompute the full rec list per user nightly and just serve it (cheap, but stale). For personalization that must react to the current session you compute online. A common hybrid: precompute candidates, rank online with fresh session features.

Cold start is the inevitable follow-up. Embedding/CF methods need history that new users and items don't have. Handle it explicitly:
  • New user: fall back to popular/trending or a quick onboarding survey; switch to personalized once a few interactions exist.
  • New item: lean on content-based features (you have its metadata even with zero interactions) so it's recommendable on day one, then let interactions refine its embedding.
  • Freshness: re-index embeddings frequently and stream recent interactions into online features so the system reflects "what you did 5 minutes ago," not just last night's batch.

Deep Dive 4 — Feature store, low-latency serving, and the A/B feedback loop

Two operational problems separate a demo from a production recommender, and both are pure systems work.

Feature store + training/serving skew. The ranking model needs the same features online (at serving) that it saw offline (at training). If the offline pipeline computes a feature one way and the online path another, predictions silently degrade — this is training/serving skew. A feature store solves it: features are computed once and written to both an offline store (for training) and a low-latency online store (for serving, e.g. an in-memory cache / KV store), guaranteeing consistency.[3] Online, the Ranking Service fetches features for ~hundreds of candidates in a single batched read — fanning out per-candidate would blow the latency budget.

ConcernMove
Latency budgetBatch feature fetch; cap candidate count; keep the ranking model small enough to score ~100s in tens of ms.
Graceful degradationIf ranking or features are unavailable, serve candidate order or a cached popular list — never return blank.
ConsistencyFeature store as single source of truth for both training and serving.

A/B testing & the feedback loop. Offline accuracy (does the model predict held-out clicks?) does not equal business value. The only honest measure of a recommender is an online A/B test: ship the new model to a fraction of traffic, compare engagement (CTR, watch time, purchases, retention) against control, roll out if it wins.[1] This closes the loop — interactions logged from live traffic become tomorrow's training data, and the experiment framework is how you safely decide what to keep. Beware feedback loops that narrow: a model that only ever shows popular items gets data only on popular items; inject exploration (some randomized/novel candidates) so the system keeps learning.

★ Staff-level signal The senior-vs-staff tell is refusing to get pulled into ML math. Say up front: "I'll treat the models as black boxes and design the serving system." Then structure the whole answer around two decisions — the candidate-generation → ranking funnel (recall cheaply, precision expensively, justified by latency × catalog size) and the offline/online split (precompute embeddings, features, and index offline; do only per-user retrieval + ranking online). Proactively raise the three things juniors miss: cold start (content features for new items, popularity for new users), training/serving skew (a feature store as the fix), and that online A/B testing — not offline accuracy — is ground truth, with exploration to avoid a self-reinforcing feedback loop. Naming what you're not going to derive is itself the staff move.[2]

15. Privacy

Recommendations are built on behavioral profiling, which regulators scrutinize. Consent and control: personalization settings, "not interested", view/delete history, and a non-personalized option (required for large platforms under the EU DSA). Minimization: training data keyed by pseudonymous ids; sensitive categories (health, sexuality, religion) excluded from targeting features. Deletion: erasure removes the user's events, online features and embedding; models are retrained on schedule so the user's influence ages out. Inference risk: recommendations themselves can reveal sensitive interests on shared devices — offer profile switching and hide sensitive recs from notifications.

Interviewer pushback

“How do you avoid training/serving skew?”

Staff answer: One feature definition feeds both the offline store and the online store, and serving logs features so training uses what was actually served.

16. Scaling 10× Without Changing the Architecture

10× = ~1B DAU-equivalent traffic (up to ~1M requests/s) or 100M items.

ComponentTodayAt 10×Knob turned
Ranker~200 GPUs~2,000, or fewer with distillationMore replicas; cap candidates; lighter pre-ranker before the heavy model
ANN index10M vectors on ~20 nodes100M vectors, shardedShard index; product quantization to cut memory
Feature store~220 GB online~2 TBMore shards; TTL for inactive users
Event pipeline~20 brokers~200More partitions; sampling of low-value events
TrainingDaily10× dataMore GPUs; incremental training; data sampling

First bottleneck: ranking inference cost. What forces a redesign: generative/sequence models that condition on long session histories per request, shifting serving toward LLM-style infrastructure.

18 · Closing Summary (60 seconds)

A recommendation system is a two-stage funnel with an offline/online split. Offline pipelines train models, compute user and item embeddings and build an ANN index. Online, a stateless service retrieves ~500 candidates from several sources (ANN, co-engagement, popular), fetches fresh features from a feature store, ranks candidates with a heavier model within ~100 ms, then applies filters and diversity rules. Interactions stream back as features and training data. Cold start uses content embeddings and exploration. At 10× we add ranker capacity.

Check yourself — retrieval practice

Answer from memory before scrolling back up.

1. Why is recommendation split into candidate generation then ranking?

10M items × 100ms budget makes brute-force scoring impossible; cheap retrieval narrows to hundreds, then expensive ranking scores only those.

2. How does embedding-based retrieval find candidates fast at serving time?

Item vectors are precomputed offline into an ANN index; per request you embed the user once and do nearest-neighbor lookup in milliseconds.

3. What is the standard fix for the new-item cold-start problem?

A brand-new item has no interactions for collaborative filtering, but you do have its metadata, so content-based features make it recommendable on day one.

4. Why is online A/B testing the real measure of a recommender?

A model can win offline yet lose on engagement; an A/B test on live traffic measures CTR/watch-time and closes the feedback loop.
