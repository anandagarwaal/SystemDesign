Section A — Computers & programs

Process vs. program

1. A "process" is best described as:

A program is the static code; a process is that code actually executing, with its own memory, variables, and current position — you can run the same program twice and get two independent processes.

Client-server model

2. When you open a website, which best describes what happens?

Client-server is a two-party conversation: the client asks, the server answers, over a network — and that exchange is disposable, not a permanent merge of the two machines.

Client-server, intuition

3. Why do we separate "client" and "server" instead of running everything on one machine?

The split lets one well-resourced machine serve thousands of lightweight clients, and lets the server be the single place that owns shared state — that's the seed of every "scaling" problem you'll study later.

APIs

4. An API is:

API = Application Programming Interface: a contract (what requests look like, what responses come back) that lets two pieces of software talk without knowing each other's internals.

Section B — Networking basics

IP address vs. domain name

5. Why do we type "google.com" instead of an IP address?

The network only understands numeric IP addresses for routing. DNS is a lookup service that maps the memorable name to that number, every single request.

Request/response, intuition

6. If a server is slow to respond, what does the client experience, and why?

Basic request/response is synchronous from the client's point of view: it asked, so it waits. This exact pain point is *why* system design has caching, async queues, and CDNs — they all exist to shorten or avoid that wait.

Latency vs. bandwidth

7. Latency and bandwidth are different because:

Latency = delay (like the time for one truck to make a delivery). Bandwidth = throughput (how many trucks the highway can carry per hour). A highway can have high bandwidth and still have high latency.

Section C — Data & storage

Memory (RAM) vs. disk

8. If a process is killed, data held only in RAM:

RAM is volatile — it needs continuous power and a live process to hold its contents. Disk (or a database, which writes to disk) is what survives a crash or restart. This is the entire reason "durability" is a design concern.

What a database is

9. A database is best described as:

A database adds structure (tables/documents/keys), a query interface, and durability guarantees on top of raw storage — a plain file gives you none of those for free.

Why not just use one big file, intuition

10. Why don't large apps just store all their data in one giant text file instead of a database?

Concurrent access, fast lookup by key, and partial updates are exactly what a database solves and a flat file doesn't. Every "index", "lock", and "transaction" concept later in this course is a refinement of that same problem.

Section D — Scale & failure (the seeds of system design)

Why one machine isn't enough

11. The core reason big products (not a personal blog) don't run on a single machine is:

It's a resource ceiling, not a rule — every machine has finite capacity. Once traffic or data outgrows one machine's ceiling, you must spread work across more than one. That single sentence is the reason "distributed systems" exist at all.

Failure as a normal event

12. In a system with thousands of machines, hardware failing:

If a machine fails once every few years on average, having thousands of them means something is failing somewhere most days. This is why replication and redundancy aren't optional extras — they're the baseline assumption of the whole field.

Redundancy, intuition

13. If failure is routine at scale, why does keeping multiple copies of data (on different machines) help?

Redundancy converts "a machine died" from an outage into a non-event, because a live copy elsewhere absorbs the traffic. Every replication and failover topic later is a variation on this idea.

The system design interview, purpose

14. A system design interview mainly evaluates:

There's no single correct architecture. The interview is a proxy for "can this person make and defend engineering tradeoffs" — which is why judgement matters more than memorized diagrams.

Tradeoffs, the core habit

15. "There is no free lunch in system design" mainly means:

Faster usually costs more or gets less consistent; simpler usually scales worse; more available usually costs more consistency or money. Naming the tradeoff, not avoiding it, is the skill.
