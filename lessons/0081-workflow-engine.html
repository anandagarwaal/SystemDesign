Design a Workflow Engine (Temporal / Zapier)

Durably execute multi-step workflows that survive crashes, span days, retry failed steps, and fire from triggers.

Why this lesson, for your mission: A workflow engine is the purest test of durable execution — can a long-running, multi-step process resume exactly where it left off after a process, a host, or a whole data-center dies? Seniors reach for a state-machine table and a cron loop. Staff candidates recognize that the winning model is event sourcing: persist the workflow's decision history and replay it to reconstruct in-memory state, decoupling orchestration from the activities that do the real work. Getting that one idea across — plus retries, idempotency, and triggers — is the whole interview.

Functional Requirements

Two product flavors share one engine: durable execution (Temporal/Cadence, code-defined workflows) and automation (Zapier, no-code trigger→action chains). Scope to the shared core.

The user should be able to…Detail
Define a workflowDeclare an ordered graph (DAG) of steps — sequential, branching on results, and parallel fan-out/fan-in.
Run steps in orderThe engine executes each step, passes outputs forward, and branches on conditions until the workflow completes.
Retry failed stepsA failed step is retried per policy; on permanent failure, run compensation (undo) or fail the run cleanly.
Trigger runsStart a workflow on a schedule (cron) or an event (webhook / queue message), not only by manual call.
Observe run stateInspect where a run is, every step's status, inputs/outputs, and full history for debugging and audit.

Out of scope (say it aloud): the business logic inside each step (the user's code / the third-party API), a visual workflow editor UI, and per-tenant billing. We orchestrate; the step does the work.

Non-Functional Requirements

PropertyTarget / priority
DurabilityNo lost progress. Once a step completes, that fact is persisted before we move on — a crash mid-workflow must resume from the last committed step, never restart from zero.
ReliabilityAt-least-once step execution across worker/orchestrator failures; exactly-once effect via idempotency. Every retry, timeout, and compensation is itself durable.
Long-runningA workflow may live seconds to months (e.g. a 30-day trial drip, a human-approval wait). State cannot sit in a process's memory.
ScaleMillions of concurrent open workflows; tens of thousands of step-completions/sec at peak across many tenants.
Multi-tenant isolationOne tenant's slow or hot workflow must not starve others — fair scheduling and per-tenant queues / rate limits.

The central tension: durability vs. long duration. You cannot hold a month-long workflow in RAM, yet you must resume it perfectly. The resolution — persist history, replay to rebuild state — is the spine of the whole design.

Capacity Estimation

Estimate only what changes the design.

QuantityEstimateDesign implication
Open workflows at rest~10M concurrent, mostly idle (waiting on timers/events)Idle workflows must cost ~nothing — keep them as rows/history in durable store, not live processes or threads.

The number that matters: 10M idle workflows. A design that keeps a thread or container per running workflow dies instantly. The whole architecture exists to make a waiting workflow cost a database row, and to wake it cheaply when a timer fires or an event arrives.

Core Entities & API

Workflow Definition — the versioned DAG/code template ("onboard-customer"). Workflow Execution (Run) — one live instance with its own runId, current state, and event history. Activity / Step — one unit of real work (call an API, send an email) and its attempts. History Event — an immutable append to a run's log (StepScheduled, StepCompleted, TimerFired, …).

EndpointPurpose
POST /v1/workflowsRegister/version a workflow definition (DAG or code). Returns workflowId.
POST /v1/workflows/{id}/runsStart a run with { input, idempotencyKey }. Returns runId; the key dedupes double-starts.
POST /v1/runs/{id}/signalDeliver an external event/signal (approval, webhook payload) into a waiting run.
GET /v1/runs/{id}Fetch current state + full step history for the observability view.
POST /v1/runs/{id}/cancelRequest cancellation; the engine runs compensation, then closes the run.
POST /v1/triggersRegister a schedule (cron) or event trigger (webhook/topic) that starts a given workflow.

The owning tenant/user is derived from the auth token, never sent in the body.

High-Level Design

The defining split is orchestrator vs. worker: a stateful engine that decides the next step and persists history, and a stateless worker fleet that runs the steps. They talk only through durable task queues.

ComponentRole
API / Frontend serviceValidates, authenticates, starts runs, accepts signals, serves the run/history read API.
History storeAppend-only event log per run (source of truth), sharded by workflowId. Durable, never only in memory.
Orchestrator (matching/history service)On each event, appends to history, decides the next step(s), and enqueues an activity task. Holds no long-lived workflow state in RAM — it replays history.
Task queuesDurable queues (one logical queue per task type/tenant) buffering activity tasks for workers; lease + ACK semantics.
Worker fleetStateless; pulls a task, runs the user's activity code, reports the result back, which becomes the next history event.
Timer / trigger serviceDurable timers (sleeps, retry backoff, schedules) + event/webhook ingestion that injects signals or starts runs.

Flow (start a run): POST /runs → API writes a WorkflowStarted event to history → orchestrator reads history, decides step 1, enqueues an activity task → a worker leases it, runs the activity, reports success → orchestrator appends StepCompleted, decides step 2, and so on. A sleep(30 days) becomes a durable timer row, not a blocked thread — when it fires, the timer service appends TimerFired and the orchestrator resumes. The run's "liveness" is the history plus pending timers; nothing is lost if any process dies.

★ Staff-level signal The interview turns on two sentences. (1) The orchestrator is stateless about workflows: workflow state lives in an append-only history, and current state is reconstructed by replaying that history — so any orchestrator can pick up any run after a crash. (2) Orchestration is decoupled from execution via durable task queues, exactly like the poller-vs-worker split in the job scheduler. Seniors propose a status-column state machine; staff propose event sourcing and explain why it makes durability and resume fall out for free.

Deep Dives

1 · Durable execution via event sourcing & replay

How does a workflow survive a crash three steps into a ten-step process and resume without re-running the first three? The naive answer — a status column you mutate — loses the intermediate outputs and can't reconstruct exactly where complex branching code was. Temporal's model is event sourcing: the run's state is never stored directly; instead every decision and result is appended to an immutable event history, and the current state is derived by replaying that log through the workflow code.

How replay works:
  • The workflow is written as ordinary code: call activity A, branch on its result, sleep, call B.
  • Each interaction produces history events: StepScheduled, StepCompleted(result), TimerFired, …
  • To resume, the engine re-executes the workflow code from the top, but instead of really calling activities it feeds back the recorded results from history. Code fast-forwards deterministically to the first un-recorded point, then runs for real.
  • Because the code path is reconstructed from results, the in-memory state (local variables, position in the DAG) is rebuilt exactly — no separate snapshot needed.

The hard constraint this buys you a question about: workflow code must be deterministic. Same history in → same decisions out. So now(), random(), and direct network calls are banned inside the workflow — they must be done in activities (whose results are recorded) so replay reproduces the same path. The cost is replay length: a run with 100k events is slow to rehydrate. The fix is continue-as-new — at a safe point, close the current history and start a fresh run carrying forward only the needed state, capping history size. This is the event-sourcing / write-ahead-log idea you saw in Lesson 07, applied to program control flow rather than messages.

2 · Task queue + worker model — decoupling orchestration from execution

Why not let the orchestrator just call the user's code directly? Because the user's code is slow, untrusted, and may run for minutes; coupling it to the stateful engine would make the engine fail with every flaky API. So the orchestrator only ever schedules work onto a durable task queue, and a separate stateless worker fleet executes it — the same poller-vs-worker decoupling as the job scheduler, and the same delivery-semantics reasoning as messaging & async.

ConcernMechanismWhy
Who runs the stepWorker leases a task from the queue, executes, reports result.Workers scale and crash independently of the engine; add workers to absorb peaks.
Crash safetyLease / visibility timeout + ACK; no ACK → task re-delivered.A worker dying mid-activity simply means the activity is retried — at-least-once.
Routing & isolationOne logical queue per task type / tenant; workers poll the queues they serve.Hot or slow tenants get their own queue so they can't starve others.
Long activitiesWorker heartbeats to extend its lease.A slow-but-healthy activity isn't re-run underneath itself.
Pick & justify: Make activity dispatch go through a durable, leased task queue, never a direct RPC the engine waits on. The engine's job ends at "append event + enqueue task"; the result comes back asynchronously as the next history event. This keeps the stateful tier small and fast, lets the untrusted/slow execution tier scale elastically, and makes worker failure a non-event — it's just a retry.

3 · Retries, timeouts, compensation (saga) & idempotency

Steps fail and time out constantly — that's the normal case, not the exception. The engine owns the failure policy so the user's code stays simple.

The failure toolkit:
  • Retries with exponential backoff + jitter — a failed activity is retried after growing delays so a flaky downstream isn't hammered (see Lesson 10). The retry schedule is itself durable, driven by timers.
  • Timeouts — schedule-to-start, start-to-close, and heartbeat timeouts catch stuck or lost activities and convert them into retryable failures.
  • Compensation (the saga pattern) — there's no distributed transaction across "charge card → reserve inventory → book courier." Instead each completed step has a compensating undo (refund, release, cancel); on permanent failure the engine runs compensations in reverse to leave the system consistent. This is the saga from Lesson 10.

Retries mean every activity can run more than once, so idempotency is mandatory: give each activity attempt a stable idempotency key (e.g. runId + step-id) and have the downstream treat a repeat as a no-op. At-least-once delivery + idempotent activities ≈ exactly-once effect — the same impossibility-of-true-exactly-once reasoning as the job scheduler and messaging. State this explicitly: the engine guarantees the workflow logic runs exactly once logically (via replay), while activities run at-least-once and lean on idempotency for their side effects.

4 · Triggers, scheduling & integration connectors (the Zapier side)

Durable execution answers "how do steps run reliably." The automation product adds "what starts a workflow, and how does it talk to 1000s of third-party apps." Two pieces: triggers and connectors.

Trigger typeHow it starts a runTradeoff / note
Schedule (cron)A durable scheduler fires at the cron time and starts a run — reuse the indexed-by-next-run-time design from Lesson 34.Cheap; bounded-delay timeliness; recurring runs reschedule the next occurrence after the current acks.
Webhook / push eventA third-party POSTs to an ingestion endpoint; we validate, dedupe by event-id, and start (or signal) a run.Low latency, but must absorb bursts via a queue and dedupe replays at the edge.
Polling connectorFor apps without webhooks, a poller periodically asks "any new rows since cursor X?" and starts a run per new item.Simple but laggy and rate-limited; persist the cursor durably so polling is idempotent across restarts.
Connectors as activities: each integration ("create Salesforce lead," "send Slack message") is just an activity with a typed input/output schema and its own auth (OAuth token per tenant). Because every external call is an activity, it inherits retries, timeouts, and idempotency for free — the same machinery from deep dive 3. New integrations are new activity definitions, not new infrastructure. Per-tenant queues and rate limits keep one tenant's 10k-item sync from drowning a shared connector.

State the breadth/depth ratio out loud: you've gone deep on durable execution, the queue/worker split, and failure semantics — where this system actually breaks — and kept the API, storage layout, and UI shallow because they're not the hard part.

Check yourself — retrieval practice

Answer from memory before scrolling back up.

1. How does the engine resume a crashed run without re-running finished steps?

Event sourcing: re-execute the code, feeding recorded results so it fast-forwards to the first un-recorded point.

2. Why must workflow code be deterministic in the replay model here?

Replay reconstructs state from results, so now()/random()/IO must live in activities, not the workflow.

3. Why route activities through a durable task queue, not a direct call?

Decoupling keeps the stateful engine small/fast and makes worker crashes just a retry — poller-vs-worker again.

4. Multi-step run can't be one transaction. How is consistency kept on failure?

No distributed txn across APIs; each completed step has a compensating undo run in reverse on failure.
