Design LeetCode (Online Judge)

Running untrusted code at scale, judged asynchronously, ranked in real time.

Why this lesson, for your mission: LeetCode looks like a simple CRUD app until you notice the central problem: you are executing arbitrary code written by strangers on your machines. The L6/L7 signal is recognizing that isolation is the whole game, and modeling judging as a queue-backed long-running task with a worker pool — not a synchronous request handled in your API tier.

Functional Requirements

Scope ruthlessly. Three flows carry the entire design; everything else (auth, profiles, payments, social) is explicitly out of scope.[1]

#Users should be able to…
1View a list of coding problems and open one (statement, examples, language stub).
2Submit a solution, have it run against the problem's test cases, and see a verdict.
3Compete in a live contest with a real-time leaderboard.

Non-Functional Requirements

The "-ilities" are where this problem earns its difficulty. Lead with isolation — it is the one NFR an interviewer is waiting to hear.

NFRTarget / priority
Secure isolationUntrusted code must not touch the host, the network, or other submissions.[1]
LatencyVerdict back within ~5 s of submission.[1]
ScalabilityAbsorb spiky contest load — up to ~100k concurrent users.[1]
AvailabilityFavor availability over strong consistency for reads and the leaderboard.[1]
FairnessLeaderboard ranking deterministic; ties broken by submission time.

Capacity Estimation

Only compute the number that bends the design: peak judging throughput. Steady-state browsing is trivially cached; contests are the stress test.

Contest spike (the one that matters)
  • ~10k submissions arriving near-simultaneously at a contest deadline.[1]
  • Each runs against ~100 test cases × ~100 ms ⇒ ~10 s of CPU per submission.[1]
  • 10k × 10 s = 100,000 CPU-seconds. To clear in ~60 s ⇒ ~1,667 CPU cores.[1]
Design implication: a single large box maxes out at a few hundred vCPUs — nowhere near 1,667. You must scale horizontally with a queue that absorbs the burst and a worker fleet that drains it. This number is why the judge is asynchronous.

Core Entities & API

Three entities. Problem (statement, test cases, per-language code stubs, difficulty, tags). Submission (user code, language, status, runtime, timestamp). Leaderboard (contest rankings, derived — it lives in Redis, not as a table you scan).[1]

The user is derived from the auth token, never sent in the body.

EndpointPurpose
GET /v1/problems?page=&limit=Paginated problem list (cacheable).
GET /v1/problems/:id?lang=Full problem + language stub.
POST /v1/submissions{problemId, code, lang} → returns a submission id immediately.
GET /v1/submissions/:idPoll for status / verdict.
GET /v1/contests/:id/leaderboardTop-N ranked users (served from Redis).

POST /v1/submissions returning an id rather than a verdict is the tell that you understand the next two deep dives: judging is a long-running task, not a synchronous call.

High-Level Design

Trace each request through the boxes. Reads hit the API tier and a cache. A submission is enqueued and handed to an isolated worker fleet; the verdict is written back and the contest score lands in Redis.

ComponentRole
API serverAuth, validation, serves reads, accepts submissions, returns the submission id. Never runs user code.
Problem store (e.g. DynamoDB)Problem statements with nested test cases and per-language stubs.[1]
Submission queue (e.g. SQS)Buffers submissions during spikes; decouples accept from judge.[1]
Judge worker fleetPool of language-specific sandboxed runners (e.g. ECS) that pull from the queue.[1]
RedisSorted sets for leaderboards; cache for hot problem lists.[1]

Submit flow: client → POST /v1/submissions → API writes a PENDING row and enqueues the job → returns id → a worker pulls the job, runs the code in a sandbox, writes the verdict, and (if a contest) does a ZADD to the leaderboard → client polls GET /v1/submissions/:id until ACCEPTED / WRONG_ANSWER / TLE.

Deep Dive 1 — Running untrusted code safely

This is the heart of the problem and the first place to spend depth. A submission is hostile code: it may try a fork bomb, read your secrets, call your internal services, exfiltrate test cases, or spin forever. The cardinal rule: you never execute user code in the API tier. The API process holds DB credentials, service tokens, and network reach — handing it untrusted code is a direct path to RCE on your control plane. Execution happens only inside disposable, locked-down sandboxes on a separate fleet.

Choosing the isolation boundary

OptionIsolationStartupVerdict
Full VM (microVM)Strongest (own kernel)HeavySafest but slow to spin per-run.[1]
Container (Docker)Strong (shared kernel, namespaced)LightBest balance — the pick.[1]
Serverless (e.g. Lambda)GoodCold startsCold-start jitter hurts the latency SLA.[1]

Containers share the host kernel but get isolated process, filesystem, and network namespaces — fast to start, cheap to throw away. (Staff nuance: a shared kernel means a kernel exploit can escape; firms running truly hostile code at scale layer a microVM like Firecracker or gVisor under the container. Naming this shows judgement.)

Hardening every sandbox
  • Read-only filesystem — block writes outside a scratch dir.[1]
  • CPU & memory bounds (cgroups) — kill resource hogs, contain fork bombs.[1]
  • Explicit timeout (~5 s) wrapping the run — catches infinite loops as TLE.[1]
  • No network — drop all egress so code can't exfiltrate or reach internal services.[1]
  • seccomp profile — whitelist syscalls; deny the dangerous ones.[1]
  • One submission per container, then destroy it — no state leaks between runs.
★ Staff-level signal The senior answer is "run it in a Docker container." The staff answer treats untrusted execution as the central security problem of the system: it states the rule that the API tier never runs user code, enumerates the concrete sandbox controls (no network, read-only FS, cgroup limits, seccomp, timeout, destroy-after-use), and acknowledges the shared-kernel escape risk with a credible mitigation (microVM / gVisor) — without over-building it for a generic interview.

Deep Dive 2 — Async submit → judge → result

Judging takes seconds and is bursty, so it cannot block an HTTP request. This is the textbook long-running-task pattern: accept fast, work in the background, report later.

  1. API validates, writes a PENDING submission, enqueues {submissionId, problemId, code, lang}, and returns the id instantly.[1]
  2. A judge worker pulls the message, loads the test cases, runs the code in a sandbox, and compares output against expected.[1]
  3. Worker writes the verdict to the submission row (and updates the leaderboard for contest submissions).[1]
  4. Client learns the result.

How does the client get the verdict — poll or push?

MechanismTradeoff
Short polling (GET /submissions/:id ~1 s)Dead simple; what LeetCode actually does. Slight latency + wasted calls — fine for a ~5 s task.[1]
Long polling / SSELower latency, fewer requests; more server-side state to hold.
WebSocket pushInstant; overkill for a one-shot result, justified for live contest feeds.

Pick short polling and say why: the task is short and the simple option is correct. The queue gives you the real payoffs — durability (a crashed worker's message reappears), automatic retries, and a buffer that smooths the contest burst instead of melting the judge fleet.[1]

Deep Dive 3 — The contest leaderboard

A live leaderboard read by 100k users, refreshing every few seconds, cannot be a SELECT … ORDER BY scan over millions of rows — that load is unsustainable.[1] Use a Redis sorted set, which keeps members ranked by score in O(log n) per write and O(log n + k) per top-k read.

Sorted-set mechanics[1]
  • Key: contest:{id}:leaderboard.
  • On a passing submission: ZADD contest:{id}:leaderboard {score} {userId}.
  • Top N: ZREVRANGE contest:{id}:leaderboard 0 N-1 WITHSCORES.
  • A user's own rank: ZREVRANK — no full scan.

Encoding the tiebreak into one score

Ranking is "most problems solved, ties broken by earliest finish time." A sorted set takes a single float, so pack both into one monotonic score: score = solved * K − (finishTimestamp / scale). More problems dominates; for equal counts, an earlier finish yields a higher score, so faster solvers rank ahead — fairly and deterministically. (Equivalent: a composite numeric key with solved in the high bits and inverted time in the low bits.)

★ Staff-level signal Reaching for a sorted set is senior. Staff-level is encoding the tiebreak into the score so ranking stays a single O(log n) operation, and being explicit that the leaderboard is a derived, eventually-consistent cache of the durable submission log — if Redis is lost, you replay submissions to rebuild it. That keeps "availability over consistency" honest instead of a slogan.

Deep Dive 4 — Scaling the judge fleet for contest spikes

The capacity math demanded ~1,667 cores at peak and near-zero between contests. Provisioning for the peak burns money 99% of the time; provisioning for the average melts during a contest. The queue makes elasticity possible: it absorbs the burst so workers can scale on their own clock.

ApproachWhy it does / doesn't work
Vertical (bigger box)Hard ceiling at a few hundred vCPUs — can't reach 1,667.[1]
Horizontal + queueAdd language-specific worker containers; autoscale on queue depth.[1]

Scale the consumers on queue depth / age of oldest message, not just CPU — depth is the leading signal that submissions are backing up, and it reacts before latency blows the 5 s SLA. Between contests the fleet scales toward zero; at the deadline spike it fans out to hundreds of workers. Because the queue holds the durable backlog, a slow scale-up degrades gracefully (verdicts arrive a little late) rather than dropping submissions, and worker crashes simply re-deliver the message.[1]

Check yourself — retrieval practice

Answer from memory before scrolling back up.

1. Where should user-submitted code actually execute?

The API tier holds credentials and network reach; untrusted code runs only in disposable, hardened sandboxes.

2. Why does POST /v1/submissions return an id rather than a verdict?

Accept fast, judge asynchronously, report later — the long-running-task pattern. The client then polls the id.

3. How are leaderboard ties (same problems solved) broken in the sorted set?

Encode solved-count and inverted finish time into one float so ranking stays a single O(log n) op.

4. Which metric best drives autoscaling of the judge worker fleet?

Queue depth/age reacts before latency breaches the SLA; scale consumers on the backlog, not just CPU.
