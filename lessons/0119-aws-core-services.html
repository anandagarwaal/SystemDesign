Deep Dive: Core AWS Services for System Design

You don't need to memorize 200 AWS services. You need the dozen building blocks — and to know which generic component each one is, so you can reason from first principles.

Why this lesson, for your mission: Many interviews let you name concrete services, and doing so crisply signals you've shipped real systems. But the trap is name-dropping without understanding — saying "Lambda" without knowing the cold-start cost, or "S3" without the consistency model. This lesson maps the core AWS building blocks to the generic concepts you've already learned (blob store, queue, KV store, CDN) and flags the one gotcha per service interviewers probe. The goal: speak cloud fluently while reasoning from fundamentals.

The two gotchas interviewers love
  • Lambda cold starts: the first invocation after idle must spin up a runtime → added latency (tens to hundreds of ms, worse for heavy runtimes/VPC). Mitigate with provisioned concurrency or keeping functions warm. Lambda is great for spiky/event-driven work; poor for steady high-throughput low-latency paths where a warm fleet is cheaper.[2]
  • S3 is not a filesystem: it's an object store — no in-place edits, no real directories (prefixes only), list operations can be slow, and it's eventually consistent for some operations historically (now strong read-after-write). Use it for blobs, not as a database or a POSIX disk.[1]
Check before continuing

In SQS, what makes a message reappear if a worker crashes mid-processing?

A received message is hidden, not deleted. If it isn't deleted before the visibility timeout ends, it reappears for another worker — at-least-once delivery.

Reread the SQS row: 'visibility timeout + DLQ'.

Why is Lambda a poor fit for a steady 5k req/s, p99-sensitive API but a great fit for thumbnailing uploads?

Pay-per-use and auto-scale win for bursty/idle workloads; for steady high throughput a warm fleet is cheaper and avoids cold-start tail latency.

Think about the shape of the traffic in each case — flat vs bursty — and what a cold start does to p99.

A teammate wants to store a 2 GB log file in S3 and append one line per second to it. What's wrong?

S3 is an object store: whole-object PUTs, no in-place edits, prefixes not directories. Batch lines into new objects instead.

Reread 'S3 is not a filesystem' in the gotchas box.

A reference architecture, in AWS terms

A typical web app maps cleanly: CloudFront (CDN) → ALB (load balancer) → app servers on ECS/EKS or Lambda (compute) → Aurora (relational truth) + DynamoDB (high-scale KV) + ElastiCache (cache); async work flows through SQS/SNS or Kinesis; blobs live in S3; metrics and alarms in CloudWatch; secrets in Secrets Manager; identity via IAM roles. Every box is a generic component you already know — AWS just gives it a brand name and runs it for you.

★ Staff-level signal The signal isn't which services you name — it's that you name them as generic building blocks with a reason. A junior says "I'll use Lambda" everywhere. A staff candidate says "Lambda for the spiky image-processing trigger — but the always-on API stays on a warm ECS fleet because cold starts would hurt p99."[2] They map "I need a blob store → S3 with pre-signed URLs and CloudFront in front," "I need a durable task queue → SQS with a visibility timeout and DLQ," and they can fall back to the generic concept if the interviewer says "don't assume AWS." Knowing the one gotcha per service — cold starts, hot partitions, S3-isn't-a-filesystem — is what proves the knowledge is real.

In the interview

Lead with the generic component, then optionally the AWS name: "a blob store — say S3 — for the videos, fronted by a CDN like CloudFront." This keeps you portable (the interviewer may prefer GCP/Azure or pure concepts) while showing fluency. Reach for managed services to justify not building undifferentiated infrastructure ("I'll use SQS rather than running my own broker"). And when you name a service, drop its one trade-off unprompted — that's the difference between buzzword bingo and engineering judgment. With that, you've completed the deep-dive track; head back to the case studies and put these blocks to work.

Comprehensive check

What is the main performance gotcha with AWS Lambda?

Idle functions must initialize a runtime on first call, adding latency; it's great for spiky work but weaker for steady low-latency paths.

Reread the Lambda gotcha in 'The two gotchas interviewers love'.

Which generic component is Amazon S3?

S3 stores immutable objects under flat key prefixes with high durability — not a filesystem or a database; use pre-signed URLs for direct access.

Look at the S3 row of the mapping table.

What's the difference between SQS and SNS?

Consumers pull from an SQS queue (one consumer per message), while SNS pushes each message to many subscribers — often SNS→SQS fanout.

Compare the SQS and SNS rows of the table.

Why lead with the generic component before the AWS name?

Naming the concept first ("a blob store, e.g. S3") keeps the answer cloud-agnostic and proves you understand the role, not just the brand.

An 'order placed' event must reach billing, email and analytics, each at its own pace, surviving consumer outages. Which pattern?

SNS gives fan-out; a queue per consumer gives each one durable buffering and independent pace. One shared SQS queue would split events between consumers, not copy them.
