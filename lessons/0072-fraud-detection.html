Design a Real-Time Fraud Detection System

Score every card transaction in under 100ms — and own the precision/recall dial that decides who gets blocked.

Why this lesson, for your mission: This is the canonical "ML in the request path" interview. It tests whether you can put a model inline on a latency-critical payment path without becoming the reason checkout times out — and the staff differentiator is whether you treat fraud as a business tradeoff, not a classifier. A senior candidate trains a model; a staff candidate names the precision/recall threshold as a product decision, builds a feature store so the inline path stays under 100ms, and closes the loop with analyst feedback so the system gets smarter as fraudsters adapt.

Phase 1 · 0–5 minClarify the problemPin scope and the few NFRs that will drive every later decision.

Ask before you design

  • “Is scoring inline before authorization, or after the fact?” — Inline scoring imposes a ~100 ms budget on the whole pipeline.
  • “What's the business cost of a false decline versus missed fraud?” — The ratio sets the decision threshold.
  • “How quickly do fraud labels arrive?” — Chargebacks take weeks, which affects training and evaluation.

1 · Functional Requirements

Strip it to the flows that shape the design — the inline scoring decision and the human/learning loop behind it.

#Requirement
1The system can score a transaction in real time (approve / decline / step-up challenge) before the payment is authorized.
2The system combines hard rules (deterministic blocklists, velocity caps) with an ML risk score into one decision.
3Fraud analysts can review flagged cases, label them, and those labels feed back into model retraining.

Out of scope (say so): the payment authorization / settlement itself (see the money-path patterns), chargeback dispute workflows, KYC/identity onboarding. Naming them earns breadth credit without spending depth budget.

2 · Non-Functional Requirements

The "-ilities" here are unusually sharp because two of them fight: the inline decision must be both fast and smart, and "smart" is itself a precision-vs-recall negotiation.

NFRTarget / priorityWhy it bites
Inline latencyp99 < 100ms end-to-end scoringIt sits in the checkout path; slow scoring = abandoned carts or auth timeouts.
Recall vs precisionTunable; catch fraud without blocking good buyersA business dial, not a fixed target — false declines cost real revenue.[2]
Availability> 99.99%; never hard-fail checkoutIf scoring is down, you need a safe default, not a payment outage.

AdaptabilityRetrain on a regular cadenceFraud is adversarial — patterns drift, so a frozen model decays.
The core tension to name out loud. You cannot maximize precision and recall at once: lowering the block threshold catches more fraud (recall ↑) but also blocks more legitimate customers (precision ↓), and vice versa.[2] Where you set the threshold is a money decision — the cost of a missed fraud (chargeback + fees) vs. the cost of a false decline (lost sale + angry customer). That single dial is the heart of Deep Dive 3.

Say to move on → “Fast and smart inline decisions, with precision vs recall as a business tradeoff. Let me size TPS and the latency budget.”

4 · Core Entities & API

Entities: Transaction (txnId, cardId, merchantId, amount, geo, deviceId, timestamp), RiskDecision (txnId, score, action, rulesFired, modelVersion), FeatureVector (entityId, windowed aggregates), FraudLabel (txnId, isFraud, source, analystId).

EndpointPurpose
POST /v1/transactions/scoreSynchronous inline scoring. Body carries the transaction; returns {score, action} within the latency budget.
GET /v1/decisions/{txnId}Fetch the decision + which rules/features drove it (for analysts and auditing).
GET /v1/review/queuePull the prioritized queue of flagged transactions for an analyst (analyst derived from auth token).
POST /v1/labelsAnalyst submits a fraud/not-fraud label, feeding the retraining pipeline.
POST /v1/rulesCreate or update a deterministic rule (blocklist entry, velocity cap) — hot-reloadable.

The decision to make score a synchronous call (not fire-and-forget) is the whole game: the payment authorization waits on its response, which is why every component behind it is latency-engineered.

5 · Data Model

The key modeling decision is to log the exact feature vector and model version used at decision time alongside every decision. Labels arrive weeks later (chargebacks), and training on features recomputed "as of now" would leak the future and create train/serve skew. Online features are keyed by entity (card, device, IP, merchant) for single-read lookups; offline features are time-versioned for point-in-time joins. Card numbers are never stored — only network tokens or hashes.

6 · Data Flow

This is a data-processing system, so trace one transaction from swipe to label:

  1. Transaction → payment gateway calls POST /v1/transactions/score before authorizing.
  2. Feature fetch → the Scoring Service reads precomputed features (velocity counts, card history) from the low-latency Feature Store in a single KV lookup.
  3. Rules + model → deterministic rules evaluate first (instant block on a hit); otherwise the Model Serving layer returns a risk score, combined into one action.
  4. Respond → approve / decline / challenge returns to the gateway inside the budget; the gateway authorizes or declines.
  5. Emit event → the transaction + decision is appended to Kafka and persisted to a raw lake (S3) — the training and reconciliation source of truth.
  6. Stream-compute → a Flink job consumes the stream and updates windowed aggregates (e.g. "txns per card in last 60s") back into the Feature Store, keeping inline features fresh.
  7. Review & label → high-score cases enter the analyst queue; submitted labels join confirmed chargebacks as training data.
  8. Retrain → the offline pipeline retrains on labeled history, validates, and promotes a new model version to serving.

This is the recurring shape: a fast synchronous read path (features → model → decision) sitting on top of a slow asynchronous write path (stream → lake → retrain) that keeps the fast path smart.

9 · Deep Dives

Deep Dive 1 — Inline scoring path vs. offline training pipeline

The single hardest constraint is the p99 < 100ms inline budget, and the way you hit it is by doing almost no work online. Inference itself is fast; the killer is feature freshness — computing "how many transactions has this card made in the last 60 seconds" at request time would mean scanning recent history live, which blows the budget.[3] The fix is a feature store with two halves that share one feature definition:

PlaneJobLatency
Online storeServe the precomputed feature vector for this card/device in one KV read.[3]Single-digit ms.
Offline storeMaterialize the same features over history for training, point-in-time correct.[3]Batch / minutes.

The features are kept fresh asynchronously: Flink consumes the transaction stream and continuously upserts windowed aggregates into the online store, so the inline path only ever reads. The offline pipeline, decoupled on the other side of Kafka, retrains on the lake and promotes versions to serving on a cadence. The staff move is naming train/serve skew as the failure mode a single shared feature definition prevents — if the training features and serving features are computed by different code, your offline AUC lies to you.

Deep Dive 2 — Streaming feature computation (velocity & window aggregations)

The most predictive fraud features are velocity features: count and sum of activity for an entity (card, device, IP, merchant) over a sliding window — "5 txns on this card in 60s," "spend on this device in the last hour."[2] Computing these is exactly the windowed-aggregation problem from the ad-click aggregator: partition Kafka by entity key, run Flink with sliding windows, and emit running aggregates.

Window typeUse hereTradeoff
TumblingFixed billing-style buckets; coarse.Cheap, but misses bursts that straddle a boundary.
Sliding"Last 60s/1h" velocity — what fraud needs.More state & compute, but matches the threat.

For very high-cardinality entities (millions of cards) you don't keep exact sets — you reach for the approximate sketches from Lesson 41: a Count-Min Sketch for approximate per-key counts, HyperLogLog for distinct-device-per-card cardinality, and a Bloom filter to test "have we seen this card/device pair before" in O(1) memory. Unlike the ad-click case, a little approximation here is acceptable — you're producing a feature for a probabilistic model, not a billable count.

Deep Dive 3 — Rules + ML hybrid and the precision/recall threshold

You want both a rules engine and a model, and the order matters. Rules run first because they are deterministic, explainable, and instant — a hard blocklist hit, an impossible-geo-velocity ("two countries in five minutes"), or a known-compromised-BIN never needs a model.[2] They also give you a same-day kill switch against a novel attack, where retraining a model would take days. The model handles the fuzzy majority that rules can't enumerate.

The model outputs a probability, and you convert it to an action with a threshold — and that threshold is the central business decision, not an ML detail:

  • Lower threshold → higher recall (catch more fraud) but lower precision (more false declines, blocking good customers).[2]
  • Higher threshold → higher precision (fewer false declines) but lower recall (more fraud slips through).
  • Because fraud is ~0.1% of volume, accuracy is meaningless (predict "all legit" → 99.9% accurate, 0% useful); judge the model on ROC-AUC / PR-AUC and pick the operating point on the curve.[2]

The elegant resolution is a three-way action instead of binary block/allow: low score → approve, high score → decline, and the uncertain middle band → step-up challenge (3-D Secure / OTP). The challenge band converts a precision/recall tradeoff into a UX cost, letting you keep recall high without hard-blocking ambiguous good customers.

★ Staff-level signal Say the quiet part: "The threshold is a money decision — I'll set it where expected chargeback loss equals expected lost-sale cost, not where F1 is maximized." Then layer the defense: deterministic rules first for instant, explainable blocks and same-day response to new attacks; an ML score for the fuzzy majority; and a step-up-challenge middle band so the precision/recall dial doesn't have to hard-block ambiguous customers. Naming class imbalance (so accuracy is the wrong metric) and treating the threshold as a business lever is what separates staff from senior.

Deep Dive 4 — Analyst feedback loop & graph-based fraud-ring detection

Where do labels come from? A fraud system is only as good as its training labels, and you get them from two sources: confirmed chargebacks (ground truth, but delayed by weeks) and analyst reviews (fast, but you can only review a sliver). Because you can't review all ~500M/day, the Review Service prioritizes by score so analysts spend time where it matters; their labels plus chargebacks feed the offline retraining pipeline, which validates and promotes a new model version. This closed loop is what keeps the system adaptive against an adversary that mutates — a frozen model decays as fraudsters probe and adjust.

Beyond per-transaction scoring: graphs. Sophisticated fraud is organized — rings share devices, cards, addresses, and IPs. A point model scoring one transaction in isolation misses the structure. Model the entities as a graph (cards, devices, accounts as nodes; shared attributes as edges) and run connected-component or community-detection analysis to surface rings: ten "unrelated" accounts all transacting from one device is invisible per-transaction but glaring in the graph. Graph features (component size, shared-device degree) feed back as features into the model, and offline graph analysis flags whole clusters for analyst review. This is the proactive deep dive that signals you understand fraud as a network problem, not just a classification problem.

Availability fallback (don't skip this). Scoring sits inline on checkout, so what happens if Model Serving or the Feature Store is down? You must not hard-fail the payment. Degrade gracefully: fall back to the deterministic Rules Engine alone, or to a conservative default action, and emit an alert. Naming "fail open vs. fail closed" — and that the choice depends on the risk appetite for that merchant/amount — is a quick staff signal on the availability NFR.

15 · Privacy

Fraud systems process financial and behavioral PII (payment tokens, device fingerprints, IPs, locations, purchase patterns) — and make automated decisions about people. Scope: card data tokenized; PCI DSS scope minimized. Legal basis: fraud prevention is a recognized legitimate interest, but GDPR rights around automated decisions apply — provide review/appeal paths and explainable reasons. Minimization: hash IPs, emails and device ids used as features; restrict analyst views to what's needed. Retention: features and decisions kept for model training and dispute windows, then aggregated. Fairness: monitor decline rates across regions/segments to avoid proxy discrimination.

“How do fraudsters evade the model, and how do you adapt?”

18 · Closing Summary (60 seconds)

Fraud detection is a fast inline decision backed by a learning loop. Each transaction calls a stateless scoring service that fetches precomputed windowed features from an online store, runs deterministic rules for instant blocks, and scores an ML model within ~100 ms. The decision is approve, decline or step-up based on a cost-derived threshold. Kafka and Flink maintain velocity features, and decisions, labels from chargebacks and analysts, and graph signals feed offline retraining with shadow and champion-challenger deployment. At 10× we add scoring nodes and feature-store shards.

Check yourself — retrieval practice

Answer from memory before scrolling back up.

1. Why is a feature store the key to meeting the inline p99 < 100ms scoring budget?

Computing window aggregates live would blow the budget; the store precomputes them so the path only reads.

2. With a ~0.1% fraud base rate, why is plain accuracy the wrong success metric?

Extreme class imbalance makes accuracy trivially high and useless; judge on recall/precision and ROC-AUC.

3. Why run a deterministic rules engine alongside the ML model rather than just the model?

Rules are deterministic, explainable, and instantly editable — the model can't respond same-day to a novel attack.

4. What does lowering the model's decision threshold do to the precision/recall tradeoff?

Lower threshold = catch more fraud (recall up) but block more good customers (precision down); it's a money dial.
