Design Google Photos

Storing the pixels is the easy half — the interview lives in the async pipelines that make them searchable.

Why this lesson, for your mission: Google Photos is a trap if you treat it as "Dropbox with thumbnails." The blob/metadata split is table stakes here — borrow it from Lesson 12 (Dropbox) in five minutes and move on. The L6/L7 signal is recognizing that the hard system is the asynchronous ML pipeline behind "search by content and face": ingestion that never blocks the user, fan-out to expensive GPU inference, and serving billions of embeddings for semantic search. Spend your hour where the difficulty is.

Functional Requirements

Five flows, but they collapse into three layers: get the bytes in, make them browsable, make them findable. Scope to these and say the rest is out.

#Users should be able to…
1Upload photos and videos from any device.
2Auto-sync — new photos on a phone back up automatically in the background.
3View & organize — scroll a fast timeline, build albums.
4Search by content / face — "beach", "my dog", a particular person.
5Share albums with other people via a link or grant.

Explicitly out of scope (name them to show judgement): in-app editing/filters, collaborative real-time albums, and full version history of edits. Defer them aloud.

Capacity Estimation

Only the numbers that change a decision. For Photos, two forces dominate: total stored bytes (drives tiering) and the inference fan-out (drives the async pipeline).

  • Storage volume → tiering + dedup. Say 1B active users × ~4 GB/yr of new media = ~4 EB/yr ingested. Implication: bytes live in object storage, and old/cold photos must drop to cheaper tiers automatically — you cannot keep an exabyte on hot storage.
  • Variants multiply the bytes. Each original spawns several derivatives (a grid thumbnail, a few display sizes). Naïvely that's a 20–40% storage tax on top of originals. Implication: generate variants in a pipeline, store them on a cheaper/cacheable path, and serve via CDN — never resize on the read path.
  • Inference fan-out → async, not inline. Every uploaded image needs face detection + object/scene tagging + an embedding. At, say, 50K uploads/sec peak, doing GPU inference synchronously would stall every upload behind a model. Implication: ingestion must return the instant bytes are durable; all ML runs off a queue.
  • Read:write skew → cache thumbnails hard. A user uploads occasionally but scrolls thousands of thumbnails. Implication: the timeline is a CDN + cache problem, not a database-throughput problem.

Numbers are illustrative back-of-envelope estimates to drive decisions, not official figures.

Core Entities & API

Keep the bytes separate from everything that describes them — exactly the Dropbox split.[1] Search artifacts (tags, faces, embeddings) are derived entities produced asynchronously, not written by the client.

Data Flow

Photos is fundamentally a data-processing system: an upload triggers a pipeline whose stages are independent, retryable, and asynchronous. Trace one photo from camera to searchable:

StageWhat happensSync?
1. UploadClient PUTs bytes straight to blob storage via presigned URL; metadata row created with status processing.[1]Sync (fast)
2. Fan-outcomplete publishes one event onto a queue; multiple consumers subscribe.Async
3. ThumbnailsWorker decodes the original, generates variants, writes them back to blob storage.Async
4. ML inferenceGPU workers run object/scene tagging, face detection, and embedding generation.Async
5. IndexTags + face clusters land in a search store; embeddings land in a vector DB.[3]Async

The user sees the photo in their timeline after stage 3; it becomes searchable after stage 5. That gap is acceptable and is what lets you keep uploads fast.

High-Level Design

The system hinges on two splits. First, the metadata/blob split from Dropbox: small structured data flows through your app servers into a DB; huge opaque bytes go around the app tier straight to object storage.[1] Second — and this is the Photos-specific one — the synchronous ingest path is split from the asynchronous enrichment path by a queue, so expensive ML never sits on the user's request.

★ Staff-level signal The move that separates staff from senior here is refusing to do ML on the request path. A senior candidate often wires "upload → resize + run models → respond," then spends the deep dive trying to make a 2-second GPU call fast enough for a mobile timeout. A staff candidate says, in the first five minutes: "uploads return as soon as the bytes are durable; everything else — thumbnails, tagging, faces, embeddings — is an idempotent, retryable job behind a queue, and the photo simply becomes searchable a few seconds later." That single decision lets thumbnailing and GPU inference scale on totally different fleets, makes the pipeline resilient to a model outage, and turns a latency problem into a throughput problem. Borrowing the blob/metadata split from Dropbox without re-deriving it is itself a signal — you know what's solved and where the new hardness is.

Deep Dives

1. Blob storage, thumbnail pipeline & tiered storage

Originals are the source of truth and never change after write — content-address them by hash in an object store and lean on its replication for the durability NFR.[2] See Lesson 45 (Blob Store / S3) for the internals and Lesson 12 (Dropbox) for the presigned-upload mechanics.[1]

  • Generate variants, never resize on read. A thumbnailing worker decodes each original once and emits a fixed set of sizes (grid thumb, a couple of display widths). Resizing on the read path would burn CPU on the hottest requests; pre-generating means the timeline is pure cache hits.
  • Serve through a CDN. Thumbnails are tiny, immutable, and read enormously — ideal CDN objects. The originals are fetched rarely (only on full-screen open or download), so keep them off the edge.
  • Tier by access pattern. A photo from this week is hot; a photo from 2014 is opened almost never. Lifecycle policies migrate cold originals to infrequent-access / archival tiers automatically.[2] Keep all thumbnails hot (they're cheap and power the scroll) while the heavy originals sink to cold storage — the user still browses instantly, and you only pay archival retrieval on the rare full open.

2. Client auto-sync, background backup & dedup

Auto-backup is the feature users actually rely on, and the client carries most of the complexity — much like Dropbox's sync, but one-directional (phone → cloud) for the core flow.[1]

  • Background, resumable, battery-aware. The client queues new camera-roll items and uploads opportunistically (often Wi-Fi + charging by default). Uploads are chunked and resumable so a 4 GB video survives a dropped connection and continues, not restarts.[1]
  • Dedup so you don't re-upload or re-store. Before uploading, the client computes a cryptographic content hash; if the backend already has those exact bytes, skip the transfer entirely. Identical files (the meme shared into ten chats) are stored once and referenced many times.[1]
  • Perceptual hashing for near-duplicates. Cryptographic hashes only catch byte-identical files; a re-compressed or lightly cropped copy hashes completely differently. A perceptual hash (pHash) maps visually similar images to nearby hashes, so the product can group "looks the same" shots and de-clutter the library. Use it for grouping and suggestions, not for storage dedup — perceptual collisions are intentional and lossy, so they must never silently drop a user's distinct file.

3. ML-based search & tagging via an async pipeline + embeddings

This is the heart of the interview. "Search my photos for my dog on a beach" has no filename to match — it needs the system to understand the pixels. Three derived signals power it, all produced off the queue:

SignalModelPowers
Object/scene tagsImage classifier / detectorKeyword search: "beach", "cake", "dog".
Face clustersFace detect + face embedding"People" grouping; search by a person.
Image embeddingVision model (e.g. CLIP-style)Semantic text→image search via vectors.[3]
  • Why a queue, not inline. GPU inference is slow and bursty. Decoupling via a queue lets you batch requests for GPU efficiency, scale inference workers on their own fleet, and retry failures without touching the upload path. Jobs must be idempotent (keyed by media id) so a redelivered message re-indexes rather than duplicates.
  • Embeddings + vector DB for semantic search. The vision model turns each photo into a vector; the same model turns the query text into a vector in the same space. Search becomes approximate nearest-neighbor (ANN) over vectors — see Lesson 40 (Vector Databases) for HNSW/IVF indexing.[3] This is what makes "dog on a beach" work without anyone ever tagging it.
  • Scope search to the owner. A query must only ever search the caller's library (and albums shared with them). Partition the vector index per user, or filter by ownerId post-ANN — never let one user's nearest-neighbor results leak another user's photos.
  • Privacy boundary. Faces and embeddings are sensitive biometric-adjacent data. Keep them in the user's own partition, make face grouping opt-out, and never use one account's data to answer another's query. Calling this out unprompted is a staff signal.

4. Sharing & permissions

Sharing in Photos is album-centric, and the access check sits on the hot read path, so model it explicitly rather than scanning.

StageDesignProblem it fixes
GoodA sharelist array on each Album.Works, but "albums shared with me" needs a full scan.
BetterA ShareGrant table, PK userId / SK albumId.Cheap lookups in both directions; one source of truth.[1]
BestAdd unguessable signed link tokens with expiry for link-sharing.Share to non-users without exposing the owner's library.

For link access, hand out short-lived signed URLs for the underlying blobs (same mechanism as download), so a leaked link expires rather than granting forever.[1]

Check yourself — retrieval practice

Answer from memory before scrolling back up.

1. Why does ML inference run off a queue rather than during the upload request?

Decoupling keeps uploads fast and lets inference scale and retry independently.

2. What makes "search my photos for a dog on a beach" actually work?

A shared embedding space turns text→image search into ANN over vectors.

3. Why keep thumbnails hot while letting old originals sink to cold tiers?

Match the tier to access frequency: hot for the scroll, archival for rare opens.

4. Why use perceptual hashing only for grouping, not for storage dedup?

pHash intentionally collides similar images, so it must never gate storage.
