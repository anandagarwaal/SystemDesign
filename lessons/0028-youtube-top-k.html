Design Top-K (YouTube Top-K Videos)

A firehose of view events in, the current top K most-viewed videos out — at scale, exactness is the trap.

Why this lesson, for your mission: Top-K is the canonical streaming-analytics interview. The whole problem turns on one judgment call senior candidates miss and staff candidates reach for instinctively: you cannot keep an exact, globally-sorted count for billions of events per minute, so you trade a sliver of accuracy for orders of magnitude of capacity. Knowing when and why to approximate — and how to avoid a single hot aggregator — is the L6/L7 signal.

Phase 1 · 0–5 minClarify the problemPin scope and the few NFRs that will drive every later decision.

Ask before you design

  • “Must the ranking be exact, or is approximate acceptable?” — Approximate top-K unlocks bounded-memory sketches.
  • “Which windows — hour, day, month, all-time — and sliding or fixed?” — Windowing determines state size and expiry.
  • “How fresh must the results be?” — A minute of lag allows precomputing results from a stream.

Functional Requirements

Strip the prompt to the few things the system must do. For Top-K, everything orbits one query.

#Requirement
1Given a massive stream of view events, return the top K most-viewed videos over a requested time window — e.g. last hour, last day, last month, or all-time.[1]
2K is small and bounded — cap at K ≤ 1,000. We serve the current window, not arbitrary historical ranges.[1]
3Counts are correct enough to rank reliably; a near-tie at rank 998 is acceptable noise.

Explicitly out of scope (say this out loud — scoping is a staff move): arbitrary start/end ranges, per-user or per-region top-K, and "top videos as of last Tuesday." Pin the windows to a fixed menu and the design simplifies enormously.[1]

Core Entities & API

Entities: View (videoId + timestamp, the raw event), VideoCount (a videoId's view total within a window), and TimeWindow (the query spec — hour / day / month / all-time).[1]

The read API is a single endpoint. Ingest is not a REST call — views arrive as a stream (next section), so we don't expose a public write route here.

EndpointPurpose
GET /v1/top-k?window={hour|day|month|all}&k={K}Return the ranked list [{ videoId, views }] for the window, length ≤ K.[1] Caller identity (if any) comes from the auth token; the query itself is anonymous-readable.

Data Model

Almost all state is transient stream state, sized independently of the number of distinct videos: a fixed-size Count-Min Sketch plus a K-heap per task per window. The only durable, growing data is the event log (bounded by retention) and per-window rollups. The load-bearing key is the Kafka partition key videoId — it's what makes each task's local top-K complete and the merge provably correct.

Phase 4 · 17–27 minHigh-level designA simple end-to-end design that satisfies every functional requirement.

Data Flow

Top-K is a data-processing system, so trace the event end to end before drawing boxes. Five stages:

  1. Emit — a view fires a lightweight event {videoId, ts}.
  2. Stream — events land on a durable, partitioned log (Kafka), partitioned by videoId.[1]
  3. Count / aggregate — a stream processor folds events into per-video, per-window counts, doing local aggregation per partition.
  4. Maintain top-K — each partition keeps its own partial top-K; a merge step combines partials into the global top-K.
  5. Serve — the precomputed top-K lands in a cache that the read API answers from in single-digit milliseconds.

Stages 3 and 4 are where the design earns or loses its scalability — that's the two-level aggregation we deep-dive below. Stages 1–2 and 5 are mostly plumbing you've seen in other lessons.

High-Level Design

Walk the request and the event separately. The write path (event) and read path (query) are fully decoupled — a hallmark of analytics systems.

Phase 5 · 27–47 minDeep dives & tradeoffsGo deep where the system breaks; compare alternatives and justify the pick.

Deep Dives

1 · Why exact counting at scale is hard — the heavy-hitters problem

The naive design: one row per video, UPDATE counts SET views = views + 1 WHERE videoId = ?, with an index on views so ORDER BY views DESC LIMIT K is cheap. It works on a laptop and collapses in production for two compounding reasons.

Write amplification from the sort. The index that makes the read O(K) makes every write O(log n). At 700k writes/sec against a multi-billion-row index, you're re-balancing a B-tree on the hottest path in the system.[1] Drop the index and writes are O(1), but now the top-K query is a full scan over billions of rows — "prohibitively slow."[1] You cannot have both cheap writes and a globally sorted view of the data at this rate.

The state is enormous and skewed. This is the classic heavy hitters problem: among billions of keys, find the few with the highest frequency in a stream you can only read once. The honest exact answer needs a counter for every distinct key (~64 GB and rising)[1] even though the result you return is a thousand entries. Keeping that whole structure consistent and sorted under a firehose is the wall every naive design hits.

2 · Approximate counting — Count-Min Sketch + a min-heap

Relax the precision NFR and the problem dissolves. Two cooperating structures replace the giant sorted table:

Count-Min Sketch (CMS) — a 2D array of counters with d hash functions. add(videoId) increments one cell per row; estimate(videoId) returns the minimum across those cells.[1] Collisions only ever inflate a count, so the min is an upper bound with a tunable, bounded error. Fixed size — hundreds of MB, not 64 GB[1] — and O(1) per event regardless of how many distinct videos exist.
  • Min-heap of size K — alongside the sketch, keep a heap of the current top K. On each event, estimate the video's count; if it beats the heap's minimum, insert/update and evict.
  • The tradeoff knob: wider sketch (more columns) → less collision → tighter error → more memory. You dial accuracy against space directly. The true heavy hitters dominate their cells, so they're estimated accurately; only the long tail is fuzzy — exactly the part the NFR said we don't care about.
★ Staff-level signal Naming Count-Min Sketch isn't the signal — justifying it is. The staff framing: "the result is 1k entries but exact state is 64 GB and unsortable at 700k writes/sec; since we negotiated approximate ranking, a fixed-size sketch plus a K-heap gives O(1) updates and bounded error in the tail we don't rank on." That sentence connects the NFR, the bottleneck, and the data structure in one breath. Mention the alternative — Redis-native CMS.INCRBY + a sorted set — and its risk (data loss between the sketch update and the sorted-set write if Redis crashes)[1] to show you know more than one implementation.

3 · Windowing — fixed vs sliding, and expiring old counts

"Top videos this hour" means counts must forget. How you forget is a real design fork.

ApproachHow it worksCost / use
Tumbling (fixed) windowsHard boundaries — the "last hour" is the current clock hour, not a rolling 60-min trailing window.[1] Each window gets its own sketch/heap; old windows are dropped wholesale.Cheap, simple, no per-event expiry. Default choice; what the prompt's freshness NFR allows.
Sliding windowsTrue trailing 60 min, updated continuously: keep minute-grained buckets, increment by the newest minute and decrement by the minute falling out 60 ago.[1]Needs retained minute-level history and decrement logic. Reserve for "last hour" where smoothness matters; use tumbling for day/month.[1]

Multiple granularities come nearly free: maintain separate windows (hour, day, month, all-time) in one pass and roll coarser grains up from finer ones. Expiry is just "stop reading the old window's structure," which is why fixed windows scale so well — there is no per-key cleanup.

4 · The streaming pipeline — two-level local-then-global aggregation

This is the deepest idea in the problem and the one that separates levels. The danger: if every event flows to one aggregator to update one global top-K, that aggregator is a single hot bottleneck choking on 700k/sec. The fix is to aggregate in two tiers.

Level 1 — local (per partition). Kafka is partitioned by videoId, so each Flink/Spark task owns a slice of videos and sees all events for them.[1] Each task keeps its own sketch + local top-K heap, aggregating into tumbling windows. No cross-task coordination on the hot path.

Level 2 — global (merge). Each window's end, every task emits its small partial top-K. A merge step unions the partials and takes the overall top K.
  • Why this is correct: a video in the global top-K must be in the top-K of its own partition (that partition saw all its views). So merging per-partition top-Ks cannot miss a global winner — it's "mathematically guaranteed to contain the global top K."[1]
  • Why it scales: the firehose is spread across N tasks; only K×N tiny partial lists meet at the merge, never the raw events.
  • Fault tolerance: Flink checkpoints sketch state (RocksDB-backed) and replays from Kafka offsets on failure[1] — the count state survives a crash without a global lock.
★ Staff-level signal Two-level aggregation is the "avoid a single hot aggregator" insight, and the partition-by-key correctness argument is what proves you understand why it works, not just that Flink does it. Pair it with the partition choice: keying Kafka by videoId is what makes local top-K complete per partition. Get the key wrong (e.g. round-robin) and the local-then-global guarantee breaks — articulating that dependency is the depth interviewers probe for.

5 · Serving — precompute and read from cache

Reads need tens of ms and the answer is already computed by the pipeline, so the read path should touch almost nothing.

Precompute over lazy cache. A naive TTL cache (query the store on miss) means every expiry triggers a thundering-herd query against the count store and an SLA spike.[1] Instead, have the pipeline (or a short-interval job) write the top-K list into Redis before the old entry expires[1], keyed top-k:{window}, with a generous retention buffer.
  • Read path becomes a single key lookup → sub-millisecond, no store contention.
  • The materialized rollup tables (hour/day/month/all-time) back the precompute and serve as the durable source of truth if the cache is cold.[1]
  • Because K ≤ 1,000, every cached value is tiny; the whole serving tier is trivially replicable for read scale and HA.

Privacy

The output (top videos) is aggregate and non-personal. The input can be personal if events carry user ids or IPs — so don't put them there: the top-K topic carries only {video_id, ts}. User-level watch history belongs to a separate, access-controlled pipeline. Minimization: collectors strip IP and cookies before producing. Retention: raw events 3 days; rollups are aggregate-only. Small-count leakage: not a concern for top-1000 lists, but region-filtered variants should suppress windows with tiny counts.

Wrap-up · 58–60 minClose strongRecap decisions and tradeoffs in 60 seconds; name what you would do next.

Closing Summary (60 seconds)

Top-K is a streaming heavy-hitters problem. View events go into Kafka partitioned by videoId. Flink tasks keep local counts (Count-Min Sketch plus a min-heap) per window and emit local top-K lists to a global aggregator that merges them. That avoids a single hot aggregator and stays correct because each video's views live on one partition. Results for each window are precomputed into a cache, so reads take tens of milliseconds. At 10× we raise partitions and parallelism, and memory stays bounded.
