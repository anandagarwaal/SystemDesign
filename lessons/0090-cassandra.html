Deep Dive: Cassandra

A leaderless, write-optimized wide-column store — what the LSM engine and the consistent-hashing ring buy you, and the price you pay for them.

Why this lesson, for your mission: At L6/L7 you'll be asked why Cassandra, not just whether. A senior says "it scales writes." A staff candidate explains the LSM write path that makes writes append-only and cheap, sketches the token ring that removes the leader bottleneck, and then tunes R+W>N live on the whiteboard to trade latency for consistency.[1] This lesson gives you that machinery so you can reason from first principles instead of reciting a marketing line.

What it is & the data model

Cassandra is a wide-column, leaderless, distributed database originally built at Facebook and now an Apache project, drawing its replication and partitioning ideas from Amazon's Dynamo paper and its data model from Google's Bigtable.[1][3] "Wide-column" means a row lives under a partition and can hold many columns, and different rows need not share the same columns — think of each partition as an ordered map of rows, each row an ordered map of columns.[1]

The whole model hangs on the primary key, which has two parts:

Key partJobInterview one-liner
Partition key Hashed to a token; decides which node(s) store the row. All rows with the same partition key live together.[1] "This is my shard key — every query must name it."
Clustering columns Sort rows within a partition on disk, so range scans inside a partition are sequential and cheap.[1] "This is how I get sorted, paginated reads for free."

The cardinal rule is query-first modeling: you decide the queries before you design the table, then build one table per query pattern, duplicating data freely across tables.[1] There are no joins and no ad-hoc WHERE on un-keyed columns — the engine has no way to find a row except by partition key. A messaging app stores the same message in a messages_by_conversation table and a messages_by_user table because each serves a different read. Denormalization is not a smell here; it is the design. Contrast that with the relational, joins-and-normalize world of MySQL (Lesson 89).

The schema knobs that matter
  • Partition key — pick high cardinality and even access so load spreads; a celebrity user or a per-day key creates a hot partition.[1]
  • Clustering columns — order by what you page over (e.g. (user_id) , (ts DESC) for a feed).
  • Keep partitions bounded — a partition should not grow without limit; cap it (e.g. bucket by month) so a single read stays fast.

Internals — where the speed comes from

The LSM write path: commit log → memtable → SSTables

Cassandra's storage engine is a log-structured merge-tree (LSM tree), the same family covered in Data Structures for Big Data (Lesson 41). A write does two cheap things and returns:[2]

  1. Append to the commit log — a sequential, on-disk write-ahead log for durability; if the node crashes, it replays from here.[2]
  2. Insert into the memtable — an in-memory, sorted structure per table.[2]

That's it — no read, no in-place update, no seek. When a memtable fills, it is flushed to an immutable SSTable (Sorted String Table) on disk, written once and never modified.[2] Updates and deletes don't overwrite anything: an update is just a newer row in a newer SSTable, and a delete writes a tombstone marker.[2]

Why writes are fast: every write is a sequential append (commit log) plus an in-memory insert (memtable). There is no random-access disk seek and no read-modify-write, so the engine sidesteps the slowest thing a disk does. This is the structural reason Cassandra ingests writes far faster than a B-tree store that must locate and mutate a page in place.[2]

Compaction — paying the debt later

The cost of "never overwrite" is that data for one row gets scattered across many SSTables. Compaction is the background process that merges SSTables, keeps the latest value per cell, and discards tombstones and superseded data — reclaiming space and keeping reads from having to touch too many files.[2] It's the deferred work that makes the cheap write path sustainable.

The read path + Bloom filters

A read may have to consult the memtable and several SSTables and merge by timestamp. To avoid scanning files that can't contain the key, each SSTable has a Bloom filter — a probabilistic set membership structure (also from Lesson 41) that answers "is this key possibly here?" with no false negatives and a tunable false-positive rate.[2] A negative lets Cassandra skip an SSTable's disk I/O entirely, so most reads touch only the files that truly hold the key. Partition-key and row indexes plus a key cache then pinpoint the offset. Reads are still inherently more work than writes — the LSM design trades read cost for write speed.[2]

The ring: consistent hashing + virtual nodes

There is no leader. Nodes form a ring, and the partition key is hashed to a token that maps to a position on the ring; the node owning that token range stores the data.[1] This is consistent hashing — the same primitive from Sharding & Consistent Hashing (Lesson 5) — so adding or removing a node only reshuffles a slice of the keyspace, not everything.[1] Modern Cassandra assigns each physical node many virtual nodes (vnodes) — many small token ranges instead of one big one — which spreads data and streaming load more evenly and makes rebalancing after a node change far smoother.[1]

Gossip & replication factor

Nodes track each other's state with a gossip protocol: each node periodically exchanges membership and liveness info with a few peers, so knowledge of who is up/down propagates without any central coordinator.[1] The replication factor (RF) is how many copies of each partition exist; with RF=3 the data is stored on the token owner plus the next replicas around the ring, optionally placed across racks and data centers for fault tolerance.[1] Any node can serve as the coordinator for a request and forward it to the replicas — that leaderless symmetry is what lets writes scale horizontally with no single bottleneck.[1]

Tunable consistency

Because Cassandra is leaderless with RF copies, you choose, per query, how many replicas must acknowledge. The write consistency level W and read level R trade latency and availability against freshness.[1] The classic guarantee:

The quorum rule: R + W > N
  • N = replication factor (copies of the data).
  • W = replicas that must ack a write; R = replicas that must answer a read.
  • If R + W > N, the read and write replica sets must overlap by at least one node, so a read is guaranteed to see the latest acknowledged write — strong consistency on that key.[1] Example: N=3, QUORUM reads and writes (R=W=2) → 2+2>3. ✓
  • Choose W=ONE, R=ONE for lowest latency and highest availability, accepting eventual consistency — a read may briefly miss a recent write.[1]

Hinted handoff: if a replica is down when a write arrives, the coordinator stores a hint and replays it when the node returns, so the write isn't lost and the replica catches up.[1] Combined with read repair and anti-entropy repair, this is how replicas converge under eventual consistency.

Last-write-wins & the clock problem: Cassandra resolves conflicting versions of a cell by last-write-wins (LWW) using a timestamp.[1] The catch a staff candidate must name: those timestamps usually come from wall clocks across many machines, so clock skew can let a "later" write silently lose to one that actually happened earlier — and there are no multi-row transactions to protect you. This is why Cassandra suits append-mostly, conflict-light workloads, and why "I'll just update the same cell from two writers concurrently" is a design smell here.

When to reach for it — and when NOT to

Reach for Cassandra when…Avoid it when…
Write throughput is huge and sustained — time-series, event logs, IoT, metrics, messaging.[1] You need ad-hoc queries, joins, or flexible WHERE across non-key columns.[1]
Access patterns are known up front and can be modeled query-first.[1] You need multi-row ACID transactions or strong cross-entity invariants (use MySQL).
You need horizontal, multi-region, always-on availability with no single leader.[1] Data is small or moderate — a single relational node would do; don't import the operational cost.
You can accept tunable / eventual consistency and design for it.[1] Workload is read-heavy with frequent in-place updates to the same cells (LWW + clocks bite).

On CAP, Cassandra sits firmly on the AP side — it favors availability and partition tolerance, exposing consistency as a per-query dial rather than a fixed guarantee, which is exactly the trade discussed in Replication & CAP (Lesson 6).[1]

★ Staff-level signal Senior candidates say "Cassandra scales writes." Staff candidates explain the mechanism and its cost in the same breath: "Writes are an append to the commit log plus a memtable insert, so there's no read-modify-write — that's the speed. The bill comes due at read time and in compaction, and Bloom filters keep reads from scanning every SSTable."[2] Then they pre-empt the trap: "Because it's leaderless with last-write-wins, I won't put a counter or a contended balance here — clock skew makes concurrent same-cell updates unsafe; that belongs in MySQL or a Lightweight-Transaction path." Naming the failure mode before the interviewer probes it is the whole game.[1]

In the interview

When Cassandra is the right call, deliver it in this order: (1) justify the pick from the requirement — "write-heavy, predictable access, needs multi-region scale, can tolerate eventual consistency." (2) Show the data model — name the partition key and clustering columns and state the query each table serves. (3) Go one level deep on the engine — the LSM write path and why writes are cheap. (4) Tune consistency out loud — pick QUORUM/QUORUM for read-your-writes on critical keys, or ONE for max availability, citing R+W>N. (5) Name a boundary — hot partitions, tombstone buildup from heavy deletes, or LWW conflicts — and how you'd avoid it. That arc is breadth-then-depth done right: a fast justification, then 60% depth on the mechanism that matters.[1]

Check yourself — retrieval practice

Answer from memory before scrolling back up.

1. Why are Cassandra writes so fast?

LSM writes are a sequential commit-log append plus a memtable insert — no read-modify-write, no random seek.

2. With replication factor N=3, which setting guarantees strong reads?

R+W > N forces the read and write replica sets to overlap; QUORUM/QUORUM (2+2>3) gives read-your-writes.

3. What does a Bloom filter do on the Cassandra read path?

A Bloom filter answers "possibly present / definitely absent," letting reads skip SSTables and avoid disk I/O.

4. Which workload is the worst fit for Cassandra?

Leaderless last-write-wins plus no multi-row ACID makes contended, transactional updates a poor fit.
