Deep Dive: Database Internals (Storage Engines)

Strip away the SQL and the marketing. Every database is one of two engines underneath — and which one decides whether it loves your reads or your writes.

Why this lesson, for your mission: When you say "I'll use Cassandra for the write-heavy event log and Postgres for the transactional core," the interviewer's follow-up is "why?" The convincing answer isn't a feature list — it's the storage engine. A staff candidate knows that Cassandra is an LSM-tree (built for writes) and Postgres is a B-tree (built for reads), and can explain the read-vs-write amplification trade-off that follows. This one mental model lets you justify almost every datastore choice, reason about index cost, and explain how transactions survive a crash.

The two storage-engine families

A storage engine's whole job is to answer "where on disk is this key, and how do I write a new value fast?" Disk (even SSD) loves sequential I/O and punishes random I/O, so the entire field comes down to two strategies for laying bytes down.[1]

B-tree — read-optimized, in-place

A B-tree keeps keys sorted in fixed-size pages (typically 4–8 KB) arranged in a shallow, wide tree. A lookup walks from the root down a handful of levels to the leaf holding the key — O(log n) page reads, usually 3–4 disk seeks even for billions of rows.[1] Writes happen in place: find the page, modify it, write it back. This makes reads fast and predictable but writes do random disk I/O and may split pages. B-trees power Postgres, MySQL/InnoDB, and most relational engines.[1]

LSM-tree — write-optimized, append + merge

A Log-Structured Merge tree never updates in place. Writes go to an in-memory sorted structure (the memtable) plus an append-only log for durability; when the memtable fills, it's flushed sequentially to an immutable on-disk file (an SSTable).[1] Because every write is an append to RAM and the flush is sequential, write throughput is enormous. The cost is paid on reads and on cleanup:

  • Reads may check several SSTables (memtable → newest → oldest) since a key's latest value could be in any of them. A Bloom filter per SSTable (see Lesson 41) lets the engine skip files that definitely don't contain the key.
  • Compaction runs in the background, merging SSTables, discarding superseded values and tombstones (deletes are just markers). This reclaims space but consumes I/O.

LSM-trees power Cassandra, RocksDB, LevelDB, and HBase.[1]

The trade-off in one sentence: amplification
  • B-tree → lower read amplification, higher write amplification. Reads touch few pages; writes are random and a single logical write can rewrite a whole page (and the WAL).
  • LSM-tree → lower write amplification at ingest, higher read amplification. Writes are cheap sequential appends; reads may probe multiple files and compaction rewrites data repeatedly over its lifetime.
  • So: write-heavy (event logs, time series, metrics, messaging) → LSM. Read-heavy with complex queries and strong transactions → B-tree.[1] This single fact justifies "Cassandra for writes, Postgres for transactions."

Indexes

An index is a second sorted structure mapping a column's values to row locations — it turns an O(n) table scan into an O(log n) seek, at the cost of extra storage and slower writes (every insert updates every index).

  • Clustered (primary) index: the table rows are physically stored in the index, ordered by primary key (InnoDB does this). Primary-key lookups are one seek; this is why your PK choice affects layout.
  • Secondary index: a separate B-tree on another column that points back to the row (by PK or row id). Great for filtering, but each one taxes writes.
  • Covering index: includes all columns a query needs, so the query is answered from the index alone without touching the table — a key tuning trick.

Transactions & isolation internals

The same engine must also make changes durable and concurrent-safe. Two mechanisms do the heavy lifting:

  • Write-ahead log (WAL / redo): before touching the data pages, the engine appends the change to a sequential log and fsyncs it. If the process crashes mid-write, recovery replays the WAL to redo committed changes and roll back uncommitted ones — that's how a half-finished write doesn't corrupt the database.[2]
  • MVCC (multi-version concurrency control): rather than locking rows for readers, the engine keeps multiple versions of a row. Each transaction sees a consistent snapshot as of its start, so readers never block writers and writers never block readers.[2] A rollback simply discards the uncommitted versions (or applies undo records) — the old version is still there.

The anomalies, briefly: a dirty read sees another transaction's uncommitted change; a non-repeatable read gets two different values for the same row within one transaction; a phantom is a new row appearing in a repeated range query. Higher isolation removes more anomalies but costs concurrency. For coordination across machines, this local machinery isn't enough — see Distributed Transactions (Lesson 112).

★ Staff-level signal A junior says "Cassandra is fast for writes." A staff candidate says why: "It's an LSM-tree — writes are sequential appends to a memtable, flushed to immutable SSTables, so it sustains huge write throughput; the price is read amplification across SSTables, mitigated by Bloom filters, and background compaction I/O. Postgres is a B-tree, so it's the opposite — cheap reads, random-I/O writes — which is why I'll put the transactional core there."[1] When asked how a crash mid-write doesn't corrupt data, they reach for the WAL replay, and for concurrency they cite MVCC snapshots rather than locks.[2] Reasoning from the engine, not the feature sheet, is the tell.

In the interview

Use this to justify datastore picks, not as a lecture. When you choose a store, add one clause: "Cassandra (LSM, write-optimized) for the high-volume event stream; Postgres (B-tree, strong transactions) for orders." When asked about durability, say "WAL — log the change before the page, replay on recovery." When asked about read/write contention, say "MVCC, so reads see a snapshot and don't block writes." And remember the universal trade-off when someone asks you to add an index: faster reads, slower writes, more storage — so index for your actual query patterns, not every column.

Check yourself — retrieval practice

Answer from memory before scrolling back up.

1. Why does an LSM-tree sustain very high write throughput?

Writes hit an in-memory memtable plus an append log, and flushes are sequential SSTable writes — disk-friendly and fast, unlike random in-place updates.

2. What is the cost LSM-trees pay for cheap writes?

A read may probe the memtable and multiple SSTables; Bloom filters and background compaction reduce but don't eliminate this read overhead.

3. How does a write-ahead log prevent corruption on a crash?

Durability comes from logging the change sequentially before modifying data pages; recovery replays committed changes and undoes uncommitted ones.

4. What does MVCC give a database?

Keeping multiple row versions lets each transaction read a consistent snapshot without taking locks, so readers and writers don't block each other.
