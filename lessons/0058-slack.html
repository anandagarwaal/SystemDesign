Design Slack (Team Messaging)

WhatsApp routes a message to one person; Slack routes it to a channel whose membership and read-state you must model explicitly — the channel is the design.

Why this lesson, for your mission: Slack looks like "WhatsApp again" but the interview pivot is the workspace → channel → member model. At L6/L7 the bar is to recognize that delivery is now fan-out to a channel's members, that per-channel ordering and per-member unread state are first-class problems, and that one cheap thing (presence) and one expensive thing (full-text search) need separate subsystems. Reuse the WhatsApp connection layer [1], then spend your depth on what 1:1 chat never forced you to solve.

Phase 1 · 0–5 minClarify the problemPin scope and the few NFRs that will drive every later decision.

Ask before you design

  • “How big can a channel get?” — 100k-member channels break per-recipient fan-out on write.
  • “Is full message history searchable, and for how long is it retained?” — Search and retention drive storage and indexing cost.
  • “Are threads, reactions and unread counts required?” — Unread counts per member can explode write volume if done naively.

Functional Requirements

Scope to the team-messaging core and defer the suite (huddles, calls, apps/bots, file collaboration).

#Users should be able to…
1Create and join channels within a workspace (public and private).
2Send and receive messages in real time in a channel, and reply in threads.
3See presence (who is online) and per-channel unread counts.
4Search message history across the channels they belong to.

Out of scope (say so out loud): audio/video huddles, the app/bot platform and slash commands, file editing, and cross-workspace Connect/federation.

Phase 2 · 5–10 minEstimate what mattersOnly the numbers that change a decision — say the implication out loud.

Capacity Estimation

Estimate only what changes the design. For Slack the load-bearing numbers are concurrent connections and channel fan-out, not raw storage. (Numbers below are my own order-of-magnitude estimates for sizing, not Slack figures.)

  • Concurrent connections: assume ~30M concurrent users, each holding one WebSocket. Even at ~500K sockets/host that is ~60+ connection servers — so you again need a connection registry to find a user's socket [1].
  • Messages: ~5B messages/day ≈ ~60K msg/s average, several × at peak. Tiny payloads; the cost is in fan-out, not bytes.
  • Fan-out amplification (the big one): a message to a 50-member channel becomes up to 50 deliveries; a few large channels with 50K+ members turn one write into tens of thousands of pushes. This single fact forces a different delivery model than 1:1 chat.
  • Storage: 5B msgs/day × ~300 bytes ≈ ~1.5 TB/day of message text, retained for years — bounded and cheap on a partitioned store; the search index roughly doubles it.

Implication: the design's difficulty lives in channel fan-out, per-member read-state, and search — three things 1:1 messaging never made you build.

Phase 3 · 10–17 minAPI & data modelLock the contract and the storage shape before drawing boxes.

Core Entities & API

Entities: Workspace, Channel, ChannelMember (user ↔ channel, plus last_read_seq), Message (with channel_id, seq, optional thread_id), and User. The reusable WhatsApp pieces — connection registry, inbox — still apply [1], but membership and read-state are the new first-class tables.

The hot path is a persistent WebSocket (latency-sensitive, bidirectional). REST handles things fine to pull on demand: history, channel management, search. User is always derived from the auth token.

Data Model

The channel is the unit of everything: messages are partitioned by channel_id and ordered by a per-channel seq; membership stores last_read_seq so unread counts are derived, not incremented. Membership is stored in both directions (channel → members for fan-out, user → channels for the sidebar and search filters). Tenancy is enforced by carrying workspace_id on every row.

Phase 5 · 27–47 minDeep dives & tradeoffsGo deep where the system breaks; compare alternatives and justify the pick.

Deep Dives

1. Real-time delivery: channel fan-out, not per-recipient inbox

In WhatsApp, a send becomes one inbox write per recipient client — fine for chats bounded at ~100 [1]. In Slack a message targets a channel, and channels range from 3 people to tens of thousands. Doing a row-per-member write on the hot path would couple send latency to channel size — unacceptable.

The better primitive is topic-based fan-out: each channel is a pub/sub topic. The Channel service persists the message once and publishes once to channel:{id}. Connection servers subscribe to the topics for whichever members they currently hold, so a publish lands only on the servers that actually have an online member, each of which pushes to its local sockets. Send latency is now O(1) in channel size for the writer; the fan-out cost is paid in parallel across subscribers. Offline members aren't pushed at all — they reconcile via history + unread on reconnect (deep dive 4), so there is no per-offline-member write.

★ Staff-level signal The move that separates senior from staff: explicitly say "the unit of delivery changed from a user to a channel, so I move fan-out off the write path and onto the subscription path." A senior reuses WhatsApp's per-recipient inbox and quietly accepts O(members) writes per send; a staff engineer notices that unbounded channel size breaks that model and picks publish-once-per-channel + subscribe-by-membership — then names the one case where it breaks (huge channels, deep dive 5) before being asked.

2. Message storage & ordering per channel

The ordering NFR is strict order within a channel — not globally. That scopes the hard part: you need exactly one sequencing authority per channel, not one for the whole system.

  • Sequence: the Channel service assigns a monotonic per-channel seq (e.g. an atomic counter per channel_id) on accept. Clients render strictly by seq, so wall-clock skew never reorders a channel.
  • Storage layout: partition by channel_id, sort key seq. Reading a channel page is a single contiguous range scan; pagination is just seq < cursor.
  • Threads: a reply carries a thread_id (the root message's id) but still takes the channel's next seq. The thread view filters by thread_id; the channel view shows the root plus a reply count. Threads are a query concern, not a second ordering system.
  • Read-your-writes: the server echoes the accepted message (with its seq) back over the sender's socket, matched on clientMsgId, so the optimistic local copy is confirmed without a refetch.

3. Presence at scale

Presence is the trap: it looks trivial and silently becomes your heaviest write source. With 30M online users and naive "write online/offline to the DB on every change," plus typing and tab focus events, you generate millions of pointless writes per second.

ApproachVerdict
Persist every presence change to the primary DBBad — write storm; presence is the cheapest data but would dominate write load.
Poll a presence endpoint every few seconds per clientBad — N² chatter; latency-laggy and wasteful at scale.
In-memory online set in Redis, TTL refreshed by socket heartbeatGood — online = "has a key"; auto-expires on disconnect; cheap reads.
Subscribe only to presence of users currently on screenGreat — Slack's "Flannel" idea: fan out presence for the visible roster only [2].

Treat presence as volatile and best-effort: a momentarily-stale dot is acceptable, so it never touches the durable store. Heartbeats refresh a TTL'd key; on disconnect the key expires and a presence event is pushed only to clients viewing that user. This is the same heartbeat machinery WhatsApp uses for liveness [1], repurposed as a presence signal.

4. Unread counts & notifications

Unreads are not stored as a number — that would mean incrementing a counter for every member on every send (the same fan-out-on-write trap). Instead derive them from two values you already have:

  • Per channel, you know the latest seq (a single value).
  • Per member, you store last_read_seq in ChannelMember, advanced by markRead.
  • Unread = latest_seq − last_read_seq, computed at read time. One write per read (which is rare), zero extra writes per send.

Mentions and badge counts are the exception: @you / DMs need a small per-user counter or notification row, because they drive a push notification and must survive offline. Route those through a separate notification service (mobile push / email) keyed by user, fed from the same message change-stream — keeping the high-volume "channel got a message" path counter-free while the low-volume "you were mentioned" path is durable.

★ Staff-level signal The unifying staff insight across deep dives 1, 3, and 4: compute per-member state at read time instead of writing it per-member at send time. Unread = latest_seq − last_read_seq, presence = a TTL key, delivery = subscribe-by-membership. Each one refuses to multiply a single write by channel size. A senior reaches for a counter or an inbox row per member; a staff engineer keeps the write path O(1) and pushes the cost to the (cheaper, cacheable) read.

5. Huge-channel fan-out

The model in deep dive 1 strains for an #all-company channel with 50K+ members. Even subscribe-by-membership means one publish lands on most connection servers and triggers tens of thousands of near-simultaneous pushes — a thundering herd on every announcement.

TacticWhy it helps
Subscribe by membership, not per-user topicsPublish lands only on servers holding a member, and once per server — not per user.
Coalesce + batch pushes per connection serverOne server with 5K members of the channel pushes a single batched frame loop, not 5K independent lookups.
Lazy pull for very large / low-interaction channelsFor mega-channels, skip live push; clients pull new seq on focus — fan-out-on-read like a celebrity feed.
Rate-limit and prioritizeProtect the connection tier; DMs/mentions jump the queue ahead of a noisy mega-channel.

This is the same fan-out-on-write vs. fan-out-on-read judgement as the news-feed "celebrity problem": bounded channels push eagerly; a few giant channels flip to read-time pull. Naming that threshold — and that it's per channel, not global — is the staff-level call.

6. Full-text search over messages

Search is a separate subsystem, never the message DB doing LIKE '%term%'. Build an inverted index (Elasticsearch-style) fed asynchronously from the message change-stream (CDC), so indexing never slows the send path — satisfying the "searchable within seconds" NFR without blocking writes. This is the same pattern as the post-search lesson; reuse it rather than re-deriving it (see Lesson 25 · FB Post Search for tokenization, sharding the index, and ranking).

The Slack-specific twist is authorization: search results must be filtered to channels the querying user belongs to. Don't post-filter after ranking (you'd leak result counts and waste work) — encode the user's accessible channel_id set as a filter clause in the query so private channels never enter the candidate set. ACL-as-a-filter inside the search engine is the correct place for the check, and contrasts with the live-comments problem (see Lesson 24 · FB Live Comments) where ordering, not access scoping, dominates.

Privacy

Workspace data belongs to the customer organization and contains confidential business conversations. Tenant isolation: workspace_id on every row and index query; enterprise key management (customer-managed keys) so the customer can revoke access. Retention: per-workspace policies delete messages and files after N days, applied to the message store, search index and backups. eDiscovery and legal hold override deletion for held users. Data residency: pin workspaces to regional cells. Minimization: operational logs never contain message bodies; presence is ephemeral. Deletion: deleted messages are removed from search via the same CDC stream.

Wrap-up · 58–60 minClose strongRecap decisions and tradeoffs in 60 seconds; name what you would do next.

Closing Summary (60 seconds)

Slack reuses the messaging split between a stateful connection layer and a durable message store, but its unit of delivery is the channel. A message gets a per-channel sequence number, is persisted in the store sharded by workspace and channel, and is published once to the channel topic. Connection servers subscribe by their users' memberships. Unread counts are derived as latest_seq minus last_read_seq, and presence is a TTL key. Huge channels are rate-limited and loaded lazily, and search indexes messages asynchronously. At 10× we add cells and shards.

Reread deep dive 4, "Unread counts & notifications."

Why is presence treated as volatile, best-effort state?

A TTL'd Redis key refreshed by heartbeat gives cheap presence; a stale dot for a moment is acceptable.

Reread deep dive 3, "Presence at scale."

How does message search avoid leaking private channels to a user?

ACL-as-a-filter inside the engine keeps private channels out of the candidate set, not post-filtered after ranking.

Reread deep dive 6, "Full-text search over messages."

What single idea connects Slack's fan-out, presence, and unread-count designs across this whole lesson?

Publish-once-per-channel, TTL presence keys, and latest_seq minus last_read_seq are all the same move: keep the write path O(1) and compute per-member state lazily on read.

If Slack's channel could somehow shrink so every channel had at most 2 members, which design decisions in this lesson would stop being necessary?

Nearly every hard problem here — fan-out amplification, huge-channel throttling, cell isolation — traces back to channels being able to scale far past a 1:1 or small-group chat. Cap channel size at 2 and you're back to WhatsApp.
