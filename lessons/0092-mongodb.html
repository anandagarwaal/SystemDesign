Deep Dive: MongoDB

The document database — flexible schemas, embedded data, replica sets for HA, and sharding for scale. What it really is under the hood, and when the shape of your data makes it the right call.

Why this lesson, for your mission: A senior candidate says "I'll use MongoDB because it's NoSQL and scales." A staff candidate says "I'll model the post and its comments as one embedded document so the feed read is a single lookup, replicate it across a three-node replica set for HA, and shard on a hashed userId to spread writes." The difference is knowing the internals — the document model, WiredTiger, replica sets, and shard-key choice — well enough to justify every decision and name the failure modes before the interviewer does.[1]

1 of 6

What it is & the data model

MongoDB is a document database: instead of rows in tables, it stores documents — JSON-like objects — grouped into collections.[1] On disk and on the wire those documents are BSON (Binary JSON), a binary-encoded superset of JSON that adds types JSON lacks: Date, ObjectId, 64-bit ints, decimals, and binary blobs.[2] Every document carries a unique _id (an ObjectId by default) that is automatically indexed.[1]

The headline property is the flexible schema: two documents in the same collection need not have the same fields, and you can add a field to new documents without a migration or downtime.[3] This is power and footgun in one — great for evolving products, dangerous if you let the shape drift uncontrolled. (Schema validation rules exist to put guardrails back on.)[3]

The central modeling decision is embedding vs. referencing:

ApproachWhat it meansUse when…
Embed Nest related data inside the parent document (a post with its comments array) Data is read together, has a contains/one-to-few relationship, and the document stays under the 16 MB limit[4]
Reference Store the related doc separately and keep its _id (like a foreign key); join at read time with $lookup Data is large, shared across parents, or unbounded (one-to-many/many-to-many) so embedding would bloat or duplicate[4]

The guiding principle: data that is accessed together should be stored together.[4] Embedding turns what would be a multi-table join in SQL into a single document read.

The document model: when embedding wins

In a relational DB, a user profile with addresses, payment methods, and preferences is four tables and a four-way join. In MongoDB it's one document — fetch it with a single key lookup, no join, no N+1.[4] That locality is the entire performance argument: you trade the relational ability to recombine data arbitrarily for the ability to read a whole aggregate in one I/O. The cost is duplication and the 16 MB document size limit[4] — embed an unbounded array (every comment on a viral post) and you eventually blow that ceiling, which is exactly why unbounded one-to-many relationships should be referenced, not embedded.

Internals — storage engine & indexes

WiredTiger + B-tree indexes

The default storage engine is WiredTiger.[5] Two things to know for an interview. First, it uses document-level concurrency control — multiple clients can modify different documents in the same collection at the same time, so writes don't serialize on a collection lock.[5] Second, it uses an internal cache plus on-disk compression (snappy by default), and it implements multi-version concurrency control (MVCC) so readers see a consistent snapshot without blocking writers.[5]

Indexes are B-trees, just like a relational DB.[6] Without an index a query is a full collection scan; with one, MongoDB walks the tree. The same rules you learned for SQL apply: index the fields you filter and sort on, compound indexes follow the left-prefix rule, and every index you add taxes writes. MongoDB also offers multikey indexes (over array fields), and specialized geospatial and text indexes.[6] The mental model from the databases & indexing lesson transfers directly.

Check before continuing

Why does document-level concurrency control let WiredTiger handle more concurrent writes than a collection-level lock would?

Locking at the document, not the collection, means unrelated writes proceed in parallel instead of queueing behind one another.

Replica sets — high availability

A replica set is MongoDB's HA unit: a group of mongod processes holding the same data — one primary and one or more secondaries.[7] All writes go to the primary, which records every change in its oplog (operations log); secondaries tail that oplog and replay it asynchronously to stay in sync.[7] If the primary becomes unreachable, the remaining members hold an election and a secondary is voted in as the new primary — typically within seconds — giving automatic failover.[7]

Two interview levers fall out of this. Write concern (w) controls how many members must acknowledge a write before it's confirmed — w:1 is fast but can lose a just-written change on failover, w:"majority" is durable but slower.[7] Read preference lets you read from secondaries to offload the primary, accepting that secondaries may lag (eventual consistency on those reads).[7] Use an odd number of voting members (three is the canonical minimum) so elections always reach a majority.[7]

Check before continuing

What is the oplog's role inside a MongoDB replica set?

Secondaries tail the primary's oplog and replay it; on primary loss, an election promotes one.

Reread the sentence describing what the primary records every change into.

Why must a replica set use an odd number of voting members?

Elections need a strict majority; an even split with no majority means no winner and no primary.

Think about what happens if a 4-member set splits 2-2 during a network partition.

Why would you choose w:"majority" over w:1 for a payment write, despite the extra latency?

Durability across failover is the whole point of write concern — majority acknowledgment survives a primary crash, w:1 does not.

Ask what happens to an acknowledged-but-unreplicated write the instant the primary dies.

4 of 6

Scaling — sharding by shard key

A replica set scales reads and gives HA, but every write still lands on one primary that must fit on one machine. To scale writes and storage horizontally, MongoDB shards: it partitions a collection across multiple shards (each shard is itself a replica set), routed by a shard key.[8] A mongos router sends each query to the right shard(s) using config-server metadata.[8] This is the same partitioning idea from the sharding lesson, applied inside a managed database.

There are two sharding strategies:

StrategyHow it splitsTrade-off
Hashed Hash of the shard key decides the chunk Even write distribution, but range queries scatter to all shards[8]
Ranged Contiguous ranges of the key value map to chunks Efficient range scans, but a monotonic key (timestamp) hot-spots one shard[8]

Why shard-key choice is everything

This is the deepest, most interview-relevant point. A bad shard key creates hot shards (one shard takes most traffic while others idle) and jumbo chunks (a chunk that can't be split because too many documents share one key value, so it can't be balanced away).[8] A good shard key has high cardinality, low frequency (no single value dominates), and non-monotonic change so writes spread instead of always hitting the newest chunk.[8] The classic mistake — sharding time-series on a raw timestamp — funnels every new write to one shard. The fix is hashing the key, or a compound key that mixes a high-cardinality field in. And it's hard to undo: changing the shard key on a large collection is a heavyweight operation, so this is a decision you justify carefully up front.

Consistency & transactions

For analytics-style queries MongoDB has the aggregation pipeline: documents flow through ordered stages — $match (filter), $group (aggregate), $sort, $lookup (join), $project (reshape) — each transforming the stream.[9] It's MongoDB's answer to GROUP BY and joins, and it runs server-side so you don't pull raw data to the app.

And yes, MongoDB has multi-document ACID transactions.[10] Within one document, updates are always atomic — that's free, and embedding often means you never need a multi-doc transaction.[10] When you genuinely need atomicity across documents or collections (a transfer touching two accounts), transactions are available across replica sets and sharded clusters.[10] The staff framing: reach for embedding to make the transaction unnecessary first; use multi-doc transactions as the deliberate exception, since they carry coordination cost.

Check before continuing

Which is true of multi-document transactions in MongoDB?

Single-document writes are always atomic; multi-doc ACID exists but embedding avoids most needs.

Reread the sentence starting "Within one document, updates are always atomic..."

Why does the staff framing say to reach for embedding before reaching for a multi-document transaction?

If the data you'd need atomic together is already in one document, you get atomicity for free and skip the coordination cost of a transaction.

When to reach for it — and when NOT

Reach for MongoDB when…
  • Your data is naturally document-shaped and read as an aggregate — catalogs, user profiles, content/CMS, IoT events, mobile app state.[1]
  • The schema evolves fast and you want to ship fields without migrations.[3]
  • You need horizontal scale for writes/storage with built-in sharding and HA replica sets, managed for you (Atlas).[8]
Reach for something else when…
  • The workload is heavily relational with many-to-many joins and ad-hoc analytics across entities → a relational DB. See the databases lesson and the key-technologies tour.
  • You need massive write throughput with leaderless multi-region writes and tunable quorum → Cassandra.[11]
  • You need an in-memory cache, counter, or leaderboard → Redis. MongoDB is durable storage, not a sub-millisecond cache.
★ Staff-level signal Senior candidates pick MongoDB because "it's flexible." Staff candidates lead with the access pattern: "We read a post with its top comments as one screen, so I embed top comments and reference the long tail — one read serves the view, and we never hit the 16 MB limit."[4] Then they pre-empt the failure modes before being asked: "I'll shard on hashed userId, not createdAt, to avoid a hot shard on recent writes,[8] use w:majority on the payment write for durability across failover,[7] and keep multi-doc transactions to the rare cross-account transfer because embedding handles the rest atomically."[10] Naming the trade-off you're not taking — and why — is the tell that you've run this in production, not just read the marketing page.

In the interview

When MongoDB is the right answer, deliver it in this order: (1) name the data shape — "these entities are read together as an aggregate, so a document model fits." (2) State your embed/reference split and tie it to the 16 MB limit and the read path.[4] (3) Cover HA with a replica set and the write concern you'd choose for the critical path.[7] (4) Cover scale by stating the shard key and why it avoids hot shards — this is where the depth points live.[8] (5) Mention the aggregation pipeline for any reporting requirement and transactions for the rare cross-document atomic case.[9] Don't recite all of it — go deep on the one or two that the requirements actually stress.
