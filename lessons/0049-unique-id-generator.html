Design a Distributed Unique ID Generator

A primitive that hides under every other system — and a test of whether you can trade off coordination, sortability, and clock trust without flinching.

Why this lesson, for your mission: This prompt looks tiny, which is exactly the trap. The senior reaches for UUIDs and moves on. The staff move is to interrogate the requirements — "must IDs be roughly time-sortable? must they fit in 64 bits? can we tolerate any central coordination?" — because each answer eliminates a whole family of designs. Land on Snowflake not as a memorized answer but as the justified consequence of "64-bit, sortable, no central bottleneck," then go deep on the failure mode everyone forgets: the clock going backwards.

Functional Requirements

Pin the contract before the design. The whole problem lives in the tension between these four — drop "sortable" or "64-bit" and the answer changes entirely.[3]

Capacity Estimation

Here estimation isn't about storage — IDs aren't stored by the generator — it's about the bit budget. The numbers you compute literally become the design.

Throughput target

Assume a large platform doing on the order of 1M writes/sec at peak, each needing an ID. A single node that synchronously increments a shared counter caps out well before this. Implication: generation must be local and parallel — every app/server host mints its own IDs with no per-ID network call.

The 64-bit budget (the load-bearing math)

One signed 64-bit integer = 1 sign bit + 63 usable bits. We must pack time, who generated it, and a per-tick counter into those 63 bits. The canonical split is Snowflake's 41 / 10 / 12:[1][2]

FieldBitsWhat it buys you
Sign bit1Kept 0 so IDs are positive in any BIGINT
Timestamp (ms since custom epoch)41241 ms ≈ ~69 years of IDs
Machine / node ID10210 = 1024 nodes generating in parallel
Sequence (per node, per ms)12212 = 4096 IDs per ms per node

Implication: 4096 IDs/ms/node = ~4.096M IDs/sec per node, and 1024 nodes give a theoretical ~4.2 billion IDs/sec — orders of magnitude past our 1M/sec target, with a 69-year clock runway.[1] The bit split is a tunable knob: trade node-count bits for sequence bits if you have fewer hosts but burstier per-host load.

Core Entities & API

This service is almost stateless. The only durable "entity" is the node-ID assignment (which host owns which of the 1024 slots); the ID itself is ephemeral output. Most production designs embed generation as a library inside each service, but exposing a thin API is the interview-legible framing — derive the caller from the auth token, never trust a client-supplied node ID.

EndpointPurposeReturns

High-Level Design

The architecture's whole point is that the hot path touches nothing shared. Coordination happens once, at startup, to claim a node ID; after that every ID is computed from three local values: the current clock, the cached node ID, and an in-memory sequence counter.

ComponentRoleOn the hot path?
ID generator (per host)Reads clock, packs 41/10/12, increments sequenceYes — pure local computation
Coordination service (ZooKeeper/etcd)Hands out unique node IDs, holds leasesNo — startup + heartbeat only
Monotonic clock sourceNTP-synced wall clock with skew guardsYes — read once per ID

Flow for one POST /v1/ids: the generator reads now_ms; if it equals the last timestamp it increments the 12-bit sequence; if the sequence overflows it spins until the next millisecond; if it's a new millisecond the sequence resets to 0. It then shifts the three fields into a 64-bit word and returns. Because node IDs are disjoint and the timestamp advances, two hosts cannot collide.[1] See Lesson 5 — Sharding for why this "partition the keyspace, never coordinate per request" pattern recurs everywhere.

Deep Dives

This is 60% of your score. Lead with the approach comparison (breadth), then go deep on clock skew and node-ID coordination (the parts that actually break in production).

Deep Dive 1 — Comparing the approaches

Walk the ladder out loud. Each rung fixes the previous one's flaw, and the interviewer is watching whether you know why you climbed past it.[3]

ApproachHowFatal flaw for our FRs
UUIDv4122 random bits, generated locally128-bit (fails ~64-bit) and not time-sortable → index fragmentation on write[3]
DB auto-incrementSingle table's AUTO_INCREMENTSingle point of failure & throughput bottleneck; one DB caps all writes[3]
Ticket serverOne dedicated box owns the counterSame SPOF; HA pair risks duplicate or out-of-order IDs
DB segment / range allocationHosts lease blocks (e.g. 1000 IDs) from a DBGreat throughput, but IDs aren't time-sortable across hosts[3]
SnowflakeLocal pack of time + node + sequenceThe pick — 64-bit, k-sorted, zero per-ID coordination[1]
Why Snowflake wins for "64-bit + sortable + no bottleneck."
  • vs UUIDv4: UUIDs are local and collision-free but they're 128-bit and random, so inserting them into a B-tree index scatters writes across the tree (page splits, poor cache locality). Snowflake's time prefix means new IDs land at the right edge of the index — sequential, cache-friendly inserts.
  • vs DB auto-increment / ticket server: both create a single thing every write must touch. That's the exact "central bottleneck" our NFR forbids, and the availability liability that takes the whole platform down with it.
  • vs segment allocation: range leasing removes the bottleneck and is a perfectly good answer — but blocks handed to different hosts interleave in time, so global ordering is lost. If sortability is a hard FR, Snowflake's embedded timestamp is the differentiator.
  • Embedded metadata: a Snowflake ID is self-describing — you can decode its creation time and origin node for free, which is gold for debugging and sharding.

Deep Dive 2 — Clock skew & the clock going backwards

This is the deep dive that separates staff from senior. Snowflake's correctness depends on a monotonically increasing clock. But NTP can step a server's wall clock backwards (leap-second smearing, drift correction, VM pauses). If now_ms < last_timestamp, you risk minting an ID you already issued — a silent duplicate.[1]

How to handle a backwards clock.
  • Detect: store last_timestamp per node. Every mint, compare against the current clock.
  • Small regression → wait it out: if the clock went back by a few ms, block until the clock catches up to last_timestamp, then resume. Brief latency, zero duplicates.
  • Large regression → refuse: if it jumped back by seconds, do not generate. Reject requests / take the node out of rotation and alert. A failed request is recoverable; a duplicate primary key is a data-corruption incident.
  • Reduce skew at the source: run NTP with slewing (gradually adjusting rate) instead of stepping, so the clock never jumps backward in the first place.
  • Sequence as a buffer: within a single ms, the 12-bit sequence absorbs bursts; overflow just spins to the next ms — never reuse.

Say the quiet part: "Snowflake trades a hard dependency on clock monotonicity for its decentralization. I'd make that dependency safe with skew detection and a fail-closed policy, because a duplicate ID is worse than a momentarily unavailable one."

Deep Dive 3 — Coordinating unique machine IDs

The 10-bit node ID must be unique across all live generators, or two hosts share a slot and collide. Hardcoding IDs doesn't survive autoscaling or container churn. The clean answer is a coordination service.[1]

MechanismHow node IDs stay uniqueTradeoff
Static configOps assigns each host a fixed IDBreaks with autoscaling / ephemeral hosts
ZooKeeper / etcdHost claims an unused sequential znode on bootAdds a dependency, but only at startup[1]
Leased IDs (TTL)Lease expires if a dead host stops heartbeatingID can be safely reclaimed and recycled

On startup a host asks ZooKeeper for the lowest free node ID (0–1023), caches it, and heartbeats to renew the lease. If the host dies, the lease lapses and the ID returns to the pool. Crucially this coordination is off the hot path — it happens once per process lifetime, so ZooKeeper being briefly slow never affects ID-minting latency.

Deep Dive 4 — Sortability vs. leaking creation time

The embedded timestamp is a double-edged sword. It gives you k-sorted IDs and free debugging — but it also means anyone holding an ID can read off when the row was created, and adjacent IDs reveal creation rate (a competitor counting your signups). This is a real consideration for public-facing IDs.[3]

Resolving the tension — pick per surface.
  • Internal IDs: keep Snowflake as-is. Sortability and decodable timestamps are pure upside inside your own systems.
  • Public IDs: don't expose the raw integer. Map it through an opaque external alias, or for a non-sortable public artifact reach for the base62 scheme in Lesson 11 — Bitly.
  • Why 64-bit still matters: staying in one machine word keeps IDs cheap to index, store, compare, and pass around — the entire reason we rejected 128-bit UUIDs. Don't surrender that without a requirement forcing it.
★ Staff-level signal The senior names UUIDs and Snowflake. The staff engineer treats the requirements as the design driver — "if you don't need sortability, segment allocation or even UUIDv7 is simpler; you're asking for Snowflake, so let's earn it" — and then proactively surfaces the failure mode juniors never mention: the clock going backwards, with a concrete fail-closed policy. They keep coordination off the hot path, call out the creation-time leak as a real tradeoff rather than pretending sortability is free, and resist over-engineering when a leased range would do. Simple-by-default, deep where it bites.

Check yourself — retrieval practice

Answer from memory before scrolling back up.

1. What is the canonical Snowflake bit layout inside a 64-bit integer?

1 sign + 41 timestamp + 10 node + 12 sequence = 64 bits: ~69 years, 1024 nodes, 4096 IDs/ms/node.

2. Why is UUIDv4 a poor fit for these particular requirements?

UUIDv4 is local and unique but 128-bit and random — failing both the ~64-bit and the sortability FRs.

3. The wall clock on a node steps a few milliseconds backwards. Best response?

For a small regression, wait until the clock passes last_timestamp; large jumps should fail closed, never duplicate.

4. What keeps the 10-bit machine IDs unique without per-request coordination?

Coordination happens once at boot via ZooKeeper/etcd leases — off the hot path, so minting stays local.
