Deep Dive: Authentication & Authorization

OAuth2, OIDC, JWT, and sessions — four words people use interchangeably and almost always confuse. Here's the clean mental model.

Why this lesson, for your mission: Nearly every system has a user and a "who can do what" boundary, and security questions are where senior candidates quietly lose points by hand-waving. At L6/L7 the interviewer wants you to distinguish authentication from authorization, choose sessions vs JWTs with the revocation trade-off named, and sketch an OAuth flow without garbling it. This lesson gives you the vocabulary and the two or three failure modes (token revocation, where to store a JWT, alg=none) that prove you've actually built auth, not just read about it.

1 of 5

AuthN vs AuthZ

Two different questions, often jammed together:

  • Authentication (AuthN): who are you? Proving identity — password, passkey, OAuth login.
  • Authorization (AuthZ): what are you allowed to do? Checking permissions on a resource — can this user delete that post?

You authenticate once (login) and authorize on every request. Conflating them is the classic interview slip; keep them separate.

Sessions vs tokens — the central choice

After login, the server needs to remember the user across stateless HTTP requests. Two strategies, and the difference is where the state lives.

Server-side sessionJWT (stateless token)
What the client holdsAn opaque session id (in a cookie)A signed token containing the claims
Where state livesServer store (Redis/DB) keyed by idNowhere server-side — it's in the token
Validate a requestLook up the id in the storeVerify the signature locally — no DB hit
Revoke instantlyEasy — delete the session rowHard — token is valid until it expires
Scales bySharing/replicating the session storeJust distributing the signing key

A JWT (JSON Web Token) is three base64url parts: header.payload.signature.[2] The header names the algorithm, the payload carries claims (sub=user, exp=expiry, roles, etc.), and the signature is an HMAC or asymmetric signature over the first two parts. Any service holding the key can verify the token without a database lookup — that statelessness is the whole appeal, and also its curse.

The JWT revocation problem & how to live with it
  • Because validation is local, a stolen or no-longer-valid JWT keeps working until it expires — you can't "delete" it server-side.[2]
  • Standard fix: short-lived access tokens (5–15 min) + a long-lived refresh token. The access token does the work; when it expires the client trades the refresh token for a new one. To revoke, you invalidate the refresh token (which is tracked server-side) and the access token dies within minutes.
  • HS256 vs RS256: HS256 is symmetric (one shared secret — every verifier can also forge); RS256 is asymmetric (sign with a private key, verify with the public key) and is the right choice when many services verify but only the auth server should mint.
  • Where to store it in a browser: localStorage is readable by any injected script → XSS steals it. An HttpOnly cookie is not script-readable but is auto-sent → CSRF risk, mitigated with SameSite + CSRF tokens. There's no free lunch; pick the threat you can defend.
  • Classic vuln — alg=none: early libraries accepted a token whose header said "no signature." Always pin the expected algorithm server-side.

Rule of thumb: sessions for a single web app where instant revoke matters; JWTs for stateless APIs, microservices, and mobile where you want verification without a shared session store — accepting the short-TTL/refresh dance to regain revocation.

Session = opaque id + server-side lookup. JWT = self-contained signed claims, verified locally.

OAuth2 & OIDC

OAuth 2.0 is a delegated authorization framework: it lets a user grant a third-party app limited access to their resources without sharing their password ("Sign in with Google", "let this app read your calendar").[1] The headline flow is authorization code + PKCE:

  1. The app redirects the user to the authorization server (e.g. Google) with the scopes it wants.
  2. The user authenticates there and consents; the server redirects back with a one-time authorization code.
  3. The app exchanges that code (plus a PKCE verifier, which proves the same client that started the flow is finishing it — essential for mobile/SPA) for an access token (and refresh token).
  4. The app calls the resource API with the access token; scopes limit what it can touch.

OAuth2 alone answers AuthZ (delegated access), not "who is this user." OpenID Connect (OIDC) is a thin identity layer on top of OAuth2 that adds an ID token (a JWT describing the authenticated user) and a /userinfo endpoint — that's what actually powers "Sign in with…" as a login.[1] One line to remember: OAuth2 = authorization; OIDC = authentication built on it.

Check before continuing

'Sign in with Google' as a login — which protocol provides the identity part?

OAuth2 = delegated authorization. OIDC layers identity (ID token, /userinfo) on top.

Why does a mobile app need PKCE in the authorization-code flow?

A public client can't keep a secret, and redirect codes can be intercepted. The PKCE verifier ties the code exchange to the client that started the flow.

Authorization models

  • RBAC (role-based): permissions attach to roles (admin, editor), users get roles. Simple, ubiquitous, coarse-grained.
  • ABAC (attribute-based): policies evaluate attributes of user, resource, and context ("editors in the same org, during business hours"). Flexible, more complex.
  • ReBAC (relationship-based): permissions follow the graph of relationships ("can view a doc if you're in a folder shared with your team"). Google's Zanzibar is the canonical planet-scale implementation and the model behind fine-grained sharing.[3] See Post Privacy / ACL (Lesson 84).
★ Staff-level signal The tell is precision under the obvious follow-ups. A junior says "I'll use JWTs" and stops. A staff candidate says "JWTs for the stateless API so services verify with the public key (RS256) and no shared session store — but JWTs can't be revoked, so I'll keep access tokens at ~10 minutes and revoke via the tracked refresh token."[2] They keep AuthN and AuthZ separate, correctly call "Sign in with Google" OIDC, not bare OAuth2,[1] and when fine-grained sharing comes up they name ReBAC/Zanzibar rather than hand-waving "we'll check permissions."[3] Knowing the failure modes — revocation, token storage XSS/CSRF, alg=none — is what separates having used auth from having read about it.

In the interview

When auth comes up: (1) split AuthN vs AuthZ explicitly; (2) pick sessions or JWTs and state the trade-off ("JWT for the mobile API, accepting short TTL + refresh for revocation"); (3) if third-party login or delegated access is in scope, sketch the authorization-code + PKCE flow and call the login part OIDC; (4) for "who can do what," name RBAC by default and ReBAC/Zanzibar if sharing is graph-shaped. Drop one security failure mode unprompted (revocation or token storage) and you've signaled depth. Don't reinvent crypto — use an IdP (Okta/Auth0/Cognito) and a vetted library.
