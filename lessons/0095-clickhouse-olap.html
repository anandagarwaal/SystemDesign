Deep Dive: ClickHouse & OLAP / Columnar Stores

How a column-oriented store turns billion-row aggregations into sub-second scans — and when it's the wrong tool.

Why this lesson, for your mission: Half the "design X analytics" interviews — ad click aggregator, real-time dashboards, metrics platforms — end at the same fork: where do the cooked rollups live? The senior answer says "an OLAP store like ClickHouse." The staff answer explains why columnar + a sparse primary index + background merges make that store fast, and names exactly when you'd reach for Druid/Pinot or a cloud warehouse instead. Knowing the internals lets you defend the pick instead of name-dropping it.

1 of 6

OLAP vs OLTP

Every database is optimized for one of two workload shapes. Conflating them is the single most common analytics design mistake.

DimensionOLTP (e.g. Postgres, MySQL)OLAP (e.g. ClickHouse)
Query shapePoint reads/writes: "fetch/update one row by id."Wide scans: "aggregate one column over a billion rows."
Access patternA few rows, all their columns.A few columns, almost all the rows.
Write patternHigh-frequency single-row inserts/updates.Bulk appends; updates are rare or forbidden.
LayoutRow-oriented (a row's fields stored together).Column-oriented (a column's values stored together).
ConsistencyStrong, transactional (ACID).Relaxed; eventual rollups, append-mostly.

Why a row store is the wrong tool for analytics. Suppose you want SELECT sum(clicks) FROM events WHERE day = ... over a billion rows with 50 columns each. A row store lays each row's 50 fields out contiguously on disk, so to read just the clicks column the engine must drag every row — all 50 columns — off disk and into memory, then discard 49/50 of it. You pay I/O for data you never touch. That's fine when you wanted the whole row (OLTP point read); it's catastrophic when you wanted one column across the universe.[1] A column store inverts the layout so the scan touches only the bytes it needs — and that single inversion is the source of nearly every OLAP advantage below. (Foundations: Lesson 41 — data structures for big data.)

Check before continuing

Internals — columnar storage and compression

1 · Columnar storage + per-column compression

ClickHouse stores each column in its own file(s), values laid end to end.[1] Two compounding wins fall out of this:

  • Scan only what you query. A SUM over one column reads that column's file and nothing else — I/O scales with columns touched, not table width.[1]
  • Far better compression. Adjacent values in a column share a type and tend to be similar (timestamps that increment, low-cardinality enums, repeated ids). That homogeneity lets schemes like LZ4, ZSTD, and delta/double-delta encoding crush the data — often an order of magnitude better than a row store can manage on mixed-type rows.[1] Less data on disk means less I/O, and I/O is the bottleneck for scans. Compression isn't just a storage saving here — it's a speed feature.

2 · Vectorized execution

A traditional engine processes data a row (tuple) at a time, paying interpreter overhead per row. ClickHouse uses a vectorized engine: it processes columns in batches (blocks of thousands of values) through tight loops that the CPU can pipeline and run with SIMD instructions.[1] Because a column batch is one contiguous array of one type, the inner loop is branch-free and cache-friendly — you amortize dispatch cost over thousands of values instead of paying it per row. Columnar layout is the prerequisite that makes vectorization possible; the two are a package deal.

Check before continuing

Why does columnar storage compress so much better than row storage?

A column is one type of similar values, so LZ4/ZSTD/delta encoding crush it far better than mixed rows.

Reread "Far better compression" — what do adjacent values in one column have in common?

Why couldn't a row-oriented engine simply bolt on vectorized (batch) execution to get the same speedup?

Vectorized execution needs a contiguous, single-type array to run tight branch-free loops over. A row's fields are mixed types stored together, so there's no such array to batch.

The lesson calls columnar layout "the prerequisite" for vectorization — ask what a batch actually needs to be to pipeline well.

Internals — the MergeTree engine

MergeTree is ClickHouse's core table engine and where its write/read strategy lives.[2] The mental model: inserts create immutable sorted "parts," and a background process merges them.

  • Sorted parts. Each insert writes a new part — a self-contained chunk of columns, sorted by the table's ORDER BY key.[2] Inserts never touch existing data, so writes are fast sequential appends (this is why it's append-optimized, not update-optimized).
  • Background merges. A background thread continuously merges small sorted parts into larger sorted parts (a k-way merge, like LSM compaction).[2] This keeps the part count bounded so reads don't fan out across thousands of tiny files, and lets special engines (e.g. SummingMergeTree, AggregatingMergeTree) collapse/aggregate rows at merge time.
  • Sparse primary index. The primary key does not index every row. ClickHouse stores one index entry per granule (a fixed block of rows, ~8192 by default), so the index is tiny and lives in memory.[2] A WHERE on the sort key prunes to the handful of granules that can match, then scans only those — data skipping rather than per-row seeks. It trades pinpoint row lookups (which OLAP doesn't need) for a featherweight index over enormous tables.
Why append-optimized matters. MergeTree has no in-place row updates — there's no B-tree to rebalance, no write-amplifying page rewrite per insert. You append immutable sorted parts and let merges do the housekeeping in the background. That's perfect for an event firehose (clicks, logs, metrics) but means point updates/deletes are expensive and async (handled via mutations or special merge engines). If your workload needs frequent in-place edits, you've picked the wrong tool — that's OLTP territory.

Why are point updates/deletes expensive on MergeTree, when they're cheap on a B-tree row store?

There's no in-place mutation slot like a B-tree page. An "update" has to be handled asynchronously via mutations or merge-time collapsing of parts, which is inherently heavier than flipping bytes on one page.

The landscape

"OLAP store" is a family, not one product. Staff signal is knowing which sub-category a problem wants.

CategoryExamplesSweet spotTradeoff
Open-source columnar DBClickHouseSelf-hosted, blazing scans, flexible SQL, log/event analytics.You operate it; updates/joins are weaker than a warehouse.
Real-time OLAPDruid, PinotIngest-from-Kafka, low-latency, high-QPS user-facing dashboards.More moving parts; less ad-hoc SQL flexibility.
Cloud data warehouseSnowflake, BigQueryElastic, serverless, big batch analytics; storage/compute split.Per-query cost; higher latency; not for high-QPS serving.

ClickHouse vs Druid/Pinot. All three are columnar and aggregate fast. Druid and Pinot are purpose-built for real-time, high-QPS, user-facing analytics — they ingest streams (Kafka) natively and answer thousands of concurrent dashboard queries with tight tail latency. ClickHouse is a more general SQL database: superb at heavy scans and ad-hoc queries, often simpler to run, but historically tuned for fewer, fatter queries than for huge concurrent QPS. (See Lesson 75 — real-time analytics.)

vs Snowflake/BigQuery. The defining difference is separation of storage and compute: data sits in object storage and you spin compute up/down independently, paying per query/per second. That elasticity is ideal for spiky batch analytics and zero-ops scaling, but it adds latency and per-query cost that make warehouses a poor fit for the always-on, low-latency serving path that ClickHouse/Druid/Pinot own. Modern ClickHouse Cloud has moved toward a similar storage/compute split, but the classic distinction still frames the interview tradeoff.

When to reach for it — and when NOT

Reach for a columnar OLAP store when…
  • Queries are aggregations/scans over few columns of many rows (SUM, COUNT, GROUP BY, time ranges).
  • Writes are append-heavy event streams — clicks, logs, metrics, telemetry.
  • You serve analytics dashboards that pre-aggregate, not per-user transactional reads.
  • Data is immutable-ish: you rarely update or delete individual rows after the fact.
Do NOT reach for it when…
  • You need point lookups / single-row updates by primary key — that's OLTP (Postgres/MySQL/DynamoDB).
  • You need transactions and strong consistency across multi-row writes.
  • The workload is read-one-whole-row (user profile, order record) — row stores win there.
  • You need heavy normalized joins and frequent mutations — warehouses/OLTP handle these better.

Staff-level signal and interview guidance

★ Staff-level signal Don't say "I'll use ClickHouse" and stop. Say "reads here are column-aggregations over an append-only event stream, so a row store would scan 50× the bytes it needs — I want a columnar engine whose compression and sparse index turn this into a data-skip." Then show judgement on the family: ClickHouse for self-hosted flexible scans, Druid/Pinot if it's high-QPS user-facing dashboards, a warehouse if it's elastic batch. The staff move is grounding the pick in the workload shape (OLAP vs OLTP) and naming what you'd give up — not over-explaining that "columns are stored together," which any senior knows.

In the interview

This technology shows up as the serving store for cooked rollups in nearly every streaming-analytics design (Lesson 36 — ad click aggregator). When you reach the "where do reads land?" moment:

  • Justify by workload, not by name. "Aggregations over an append-only firehose → columnar OLAP." One sentence, then move on — don't burn depth budget re-deriving compression.
  • Pre-aggregate on write. The store is fast, but the bigger win is materializing minute/hour/day rollups so reads touch tiny pre-cooked tables, not raw events. ClickHouse's AggregatingMergeTree / materialized views do this at merge time.
  • Pick the right sub-category out loud. Real-time high-QPS → Druid/Pinot; elastic batch → warehouse; flexible self-hosted scans → ClickHouse. Naming the alternative you rejected is the breadth signal.
  • Don't propose it for OLTP. If the interviewer pivots to "now update a single user's balance," flag that you'd route that to a transactional store — recognizing the boundary is itself the signal.
