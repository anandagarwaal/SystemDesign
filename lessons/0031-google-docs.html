Design Google Docs (Collaborative Editing)

Many people typing into one document at once — and everyone converging on the same text.

Why this lesson, for your mission: This is the canonical "concurrency convergence" problem. A senior candidate hand-waves "we merge the edits." A staff candidate names the actual mechanism — Operational Transformation or CRDTs — states why naive last-write-wins corrupts the text, and defends a per-document authoritative server that orders operations. The interview is won in the deep dive, not the box diagram.

Phase 1 · 0–5 minClarify the problemPin scope and the few NFRs that will drive every later decision.

Ask before you design

  • “Plain text or rich text with formatting and comments?” — Rich text multiplies the operation types that must converge.
  • “Is offline editing required?” — Offline or peer-to-peer editing pushes toward CRDTs over server-sequenced OT.
  • “What's the maximum number of concurrent editors per document?” — A cap near 100 lets one server own each document.

Functional Requirements

Scope to the collaboration core. A simple text editor is enough [1] — rich formatting, comments, and permissions are explicitly out of scope so we can spend our depth budget on convergence.

#Requirement
1Multiple users can edit one document concurrently.
2Every editor sees others' changes in near real time.
3All editors converge to the same final text, regardless of edit order.
4Editors see collaborators' presence and cursor positions [1].

Out of scope: sophisticated document structure, permissions/sharing, and version history [1].

Non-Functional Requirements

PropertyTarget / priority
Low latencyLocal keystroke applies instantly (optimistic); remote edits land in <100–200 ms.
Convergence / consistencyStrong guarantee: all replicas must reach byte-identical state. This is the hard NFR.
AvailabilityHigh for read/edit; a brief reconnect blip is tolerable, silent text corruption is not.
DurabilityNo accepted edit is ever lost — the document survives any single node failure.

Note the deliberate tension: we want a document to feel always-editable (availability) yet provably converge (consistency). We resolve it by making one component — a per-document server — the authority that orders edits, while clients stay optimistically responsive.

3 of 8 — Phase 3 · API & data model

Phase 3 · 10–17 minAPI & data modelLock the contract and the storage shape before drawing boxes.

Core Entities & API

Entities: Document (id, current snapshot, latest version number), Operation (docId, authorId, type insert/delete, position, char(s), version it was based on), and Presence (ephemeral: userId, docId, cursor offset, selection range, color).

EndpointPurpose
POST /v1/documentsCreate a document; returns documentId.
GET /v1/documents/:idLoad the latest snapshot + version number to start editing.
WS /v1/documents/:id/streamBidirectional edit stream: client sends ops, server broadcasts ordered ops back.
WS /v1/documents/:id/presenceEphemeral presence/cursor channel (separate from durable edits).

User identity is derived from the auth token on connect, never passed in the body. The edit stream and presence are separate channels on purpose — one is durable, one is throwaway (Deep Dive 4).

Data Model

Everything is keyed by doc_id. The load-bearing constraint is the op log's primary key (doc_id, version) written with a conditional "insert if not exists": even if two collaboration servers briefly both believe they own a document (a failover split-brain), only one can write version N, so the log can never fork. Presence never touches durable storage.

High-Level Design

Walk a single edit through the system:

  1. Client opens the doc via GET, receives snapshot + version, renders it.
  2. Client opens a WebSocket to the collaboration server that owns this doc.
  3. User types. Client applies the edit optimistically (instant local feedback) and sends the op with the version it was based on.
  4. The collaboration server sequences the op (assigns the next version), transforms/integrates it against any concurrent ops, appends it to the durable op log, and broadcasts the canonical op to all other connected clients.
  5. Each peer applies the canonical op, reaching the same state. Presence flows on the separate channel.

5 of 8 — Phase 5 · Deep dive: OT vs CRDT

Phase 5 · 27–47 minDeep dives & tradeoffsGo deep where the system breaks; compare alternatives and justify the pick.

Deep Dives

1. The core problem: concurrent conflicting edits — OT vs CRDT

Two users edit "cat" at the same time. Alice inserts "s" at position 3 → "cats". Bob simultaneously inserts "!" at position 0 → "!cat". Each op was computed against the original text. If the server naively replays both by their literal positions, Bob's later op shifts Alice's index and you get garbage like "!ctas". Last-write-wins is worse: it silently drops one keystroke. This is why "we just merge" fails — concurrent ops are expressed against stale positions. Two real families solve it.

Operational Transformation (OT). Keep operations, but transform a new op against the ops that were applied since the version it was based on. transform(opA, opB) adjusts opA's position so it produces the same intent after opB already ran. With a central server doing the transforming, you never need every pairwise rule to commute — the server linearizes everything. This is what Google Docs and the old Google Wave / Apache Wave used; OT is famously fiddly to prove correct, which is exactly why a central sequencer is preferred over true P2P OT.

CRDTs (Conflict-free Replicated Data Types). Don't transform — give every character a globally unique, densely-orderable identity (a fractional/position identifier between its neighbors). Inserts and deletes (tombstones) then commute: apply them in any order and all replicas converge automatically, no central transform needed. Sequence CRDTs like RGA, Logoot, and Yjs/Automerge power Figma-style and offline-first collaborative editors. The cost: per-character metadata bloat and tombstone accumulation that needs garbage collection.

Convergence mechanismTransform ops against concurrent opsCommutative ops via unique position IDs

Justified pick: With one authoritative per-document server (which we already have for ordering), OT is the pragmatic choice — the server linearizes ops so we sidestep OT's hardest P2P proofs, and we avoid CRDT's per-char metadata. Choose CRDT if the requirement adds offline editing or true peer-to-peer with no central authority. State the pick and the trigger that would flip it.

6 of 8 — Phase 5 · Deep dive: sequencing, persistence, presence

2. Real-time propagation: a per-doc collaboration server as central sequencer

One server owns each document (routed by documentId at the gateway). It holds the doc in memory, receives ops over WebSocket, assigns each a monotonically increasing version, transforms it (OT), and broadcasts the canonical result to every other connected client. Because all ops funnel through one ordering point, we get a single global order "for free" — the property OT depends on. This is the long-lived stateful connection pattern from Lesson 2 (WebSockets), and the routing/fan-out is the Lesson 7 (Pub/Sub) pattern: the server publishes ordered ops to a per-doc topic.

Scaling and failover: shard documents across a fleet via consistent hashing on documentId; a coordination layer (e.g. ZooKeeper/etcd) tracks which server owns which doc. Clients reconnect with their last-known version, and the server replays the missed tail of the op log to catch them up — so a server crash or reconnect costs a brief replay, not lost edits. With tens of millions of sockets [1], the connection tier scales out independently of the (cheap) per-doc ordering work.

3. Persistence: op log + periodic snapshots + compaction

The op log is the source of truth: an append-only sequence of every accepted op, in server-assigned order. Append-only writes are fast and give durability and a natural audit/version trail. But replaying millions of ops to open a document is unacceptable, so we periodically snapshot the materialized text + its version number.

Loading a doc = latest snapshot + replay only the ops after it. Compaction then prunes the op log: once a snapshot at version V is durably stored, ops older than V can be archived or deleted (subject to any version-history retention, which we scoped out). This bounds storage even though total ops grow forever — directly answering "how do we keep storage under control" [1]. Snapshot cadence is a tunable knob: more frequent = faster loads + more storage; less frequent = cheaper + slower cold loads.

4. Presence and cursors as ephemeral state

Cursor positions, selections, and "who's here" are high-frequency and disposable — if a cursor update is lost, the next one corrects it within milliseconds, and on disconnect the state should simply vanish. So presence must not touch the durable op log. Route it on a separate channel through a pub/sub layer (e.g. Redis) keyed by documentId, with TTLs so a dropped client's cursor expires automatically. Updates are throttled/debounced (~10/s) to avoid drowning the edit path. The staff move is the clean separation: durable edits and throwaway presence are different systems with different guarantees — conflating them either bloats your log with noise or risks dropping real edits under presence load.

★ Staff-level signal Name the real mechanism. Say "Operational Transformation, with a central per-document server that linearizes ops, so we avoid OT's hardest peer-to-peer proofs — I'd switch to a CRDT only if we needed offline or P2P editing." Then keep the durable op log rigorously separate from ephemeral presence, and explain snapshots + compaction so storage stays bounded. That trio — honest OT-vs-CRDT tradeoff, an authoritative ordering point, and durable/ephemeral separation — is what separates a staff answer from "we merge the changes somehow."

Privacy

Documents contain whatever users write — contracts, medical notes, secrets — so treat content as highly sensitive. Encryption: at rest for op log and snapshots, with per-tenant keys for enterprise customers (customer-managed keys where required). Minimization: operational logs and metrics never include content; support access to content requires customer consent or break-glass with audit. Presence reveals who is viewing a document and when — shown only to people with access. Deletion: deleting a document removes snapshots and op log (including compacted archives) after a trash window; account deletion transfers or deletes owned docs per org policy. Residency: enterprise tenants pinned to regional storage.

Closing Summary (60 seconds)

Google Docs is a convergence problem. Each document is owned by one collaboration server, found by consistent hashing, which acts as the central sequencer. Clients apply edits optimistically and send ops tagged with their base version; the server transforms concurrent ops (OT), assigns a total order, appends to the op log and broadcasts. Periodic snapshots plus log compaction keep loads fast. Presence and cursors travel an ephemeral channel. At 10× we add servers and log nodes; CRDTs become worth it only for offline editing.
