Deep Dive: MySQL (InnoDB)

The world's most-deployed relational engine — and why its clustered-index design quietly shapes every schema and query decision you make.

Why this lesson, for your mission: At L6/L7, "I'll use MySQL" is a sentence, not a design. The signal comes from the next sentence: that the table physically is its primary-key B+tree, so a random UUID PK fragments your inserts, and every secondary-index lookup pays a double cost. This lesson gives you the InnoDB internals — clustered index, buffer pool, redo/undo, MVCC, gap locks — so you can reason about throughput, replication lag, and lock contention out loud instead of hand-waving.[1]

What it is & data model

MySQL is a relational database: data lives in tables of typed rows, queried with SQL, with ACID transactions and joins.[1] "MySQL" is really the server plus a pluggable storage engine; since MySQL 5.5 the default — and the only one you should assume in an interview — is InnoDB, a transactional, row-locking, crash-safe engine.[2] The old MyISAM engine (table-level locks, no transactions, no crash recovery) is legacy; naming InnoDB specifically is the first small signal that you know the engine matters.

The data model is the standard relational one: normalized tables, foreign keys, B-tree indexes, and a SQL optimizer that plans joins for you. What makes InnoDB worth a deep dive is how it lays those rows on disk.

Internals (InnoDB)

The clustered index — the table is the PK B+tree

This is the single most important InnoDB fact. InnoDB stores every table as a clustered index: the rows are kept inside the leaf nodes of a B+tree ordered by the primary key.[3] There is no separate "heap" of rows plus an index pointing at it — the primary-key index is the table. If you don't declare a PK, InnoDB uses the first UNIQUE NOT NULL key, or else synthesizes a hidden 6-byte row ID.[3]

Two consequences fall out of this directly:

  • PK lookups and range scans are fast. Finding a row by PK walks the tree straight to the leaf — the row data is right there, no second hop. Range scans on the PK read sequential leaf pages.
  • Insert order matters enormously. A monotonically increasing PK (AUTO_INCREMENT, or a time-ordered ID) appends to the rightmost leaf — cheap, dense pages. A random PK (a v4 UUID) inserts into random points in the tree, causing page splits, fragmentation, and a cold buffer pool. This is the reason "don't use random UUIDs as your InnoDB primary key" is interview canon.

Secondary indexes pay a double cost

A secondary (non-PK) index in InnoDB does not store a pointer to a physical row location. Its leaf nodes store the indexed columns plus the primary key value.[3] So a lookup by a secondary index is two B+tree searches: walk the secondary index to find the PK, then walk the clustered index to fetch the row. This is the "double lookup" (a.k.a. bookmark lookup).

Staff-level implication: a fat primary key bloats every secondary index, because each one copies the full PK into its leaves. And a covering index — one that includes every column the query needs — lets InnoDB answer entirely from the secondary tree and skip the second hop entirely. That is the lever you reach for when a hot query is index-bound.

The buffer pool

InnoDB caches table and index pages in memory in the buffer pool, managed with a variant of LRU.[4] Reads and writes happen against pages in the pool; dirty (modified) pages are flushed to disk in the background. On a well-tuned server the buffer pool is sized to hold the working set — often 50–75% of RAM — so most reads never touch disk. When someone asks "why is this query slow after a restart," the answer is usually a cold buffer pool.

Redo log + undo log: durability and rollback

InnoDB does not flush data pages to disk on every commit — that would be random I/O on every write. Instead it uses write-ahead logging: the change is written to the redo log (a sequential, append-only log) and the commit returns once that durable write lands.[4] Data pages are flushed lazily afterward. On crash recovery, InnoDB replays the redo log to bring data files forward to the last committed state. This is what makes commits fast and crash-safe at the same time — sequential log writes instead of random page writes.

The undo log is the complement: it records the previous versions of rows so a transaction can be rolled back, and — crucially — so other transactions can read the old version. That second job is the basis of MVCC.[5]

MVCC — readers don't block writers

InnoDB implements Multi-Version Concurrency Control: each row carries hidden transaction-id and roll-pointer fields, and old versions are reconstructed from the undo log.[5] A plain SELECT reads a consistent snapshot as of when the transaction (or statement) started — it sees a stable view and does not take row locks, so readers don't block writers and writers don't block readers.[5] Only locking reads (SELECT ... FOR UPDATE) and writes acquire row locks.

Isolation: REPEATABLE READ + gap locks

InnoDB's default isolation level is REPEATABLE READ (note: the SQL standard default and PostgreSQL's default is READ COMMITTED).[5] Under REPEATABLE READ, all plain reads in a transaction return the same snapshot. To stop phantom rows, InnoDB locking reads use next-key locks — a row lock plus a gap lock on the range before it — so another transaction can't insert into the gap your range query is reading.[6] Gap locks are a frequent, non-obvious source of deadlocks and contention on range writes; calling them out by name is a strong signal.

Scaling & replication

MySQL replication is built on the binary log (binlog) — an ordered record of every data-changing statement or row event, written on the primary.[7] Replicas connect, stream the primary's binlog events, and replay them locally. This single mechanism underpins read scaling, failover, and backups.

Async vs semi-synchronous

  • Asynchronous (default): the primary commits and returns without waiting for any replica. Lowest write latency, but a replica can lag, and a primary crash can lose the most recent commits that never reached a replica.[7]
  • Semi-synchronous: the primary waits until at least one replica acknowledges receiving (not applying) the event before the commit returns.[8] Stronger durability on failover, at the cost of one network round-trip of write latency.

Read replicas and the lag trap

The standard scaling move is one primary for writes, N read replicas for reads.[7] This scales reads horizontally and gives you a failover candidate. The trap is replication lag: because replication is asynchronous, a user who writes then immediately reads from a replica may not see their own write. The fixes are "read-your-writes" routing (send a user's reads to the primary for a short window) or reading from the primary for consistency-critical paths.

Sharding — when one primary isn't enough for writes

Replicas scale reads, not writes; a single primary still absorbs all writes. When write volume or dataset size outgrows one node, you shard: partition rows across independent MySQL clusters by a shard key (e.g. user_id).

Sharding patterns & their costs
  • Range sharding — partition by key ranges. Simple, supports range scans, but prone to hotspots (e.g. newest IDs all on one shard).
  • Hash sharding — hash the key to a shard. Even distribution, but range queries fan out to all shards.
  • Directory / lookup — a lookup service maps key → shard. Flexible rebalancing, but the directory is a new dependency to keep available.
  • The real cost: cross-shard joins and cross-shard transactions are hard or impossible — you lose the easy ACID and joins that made you pick MySQL. Shard late, and pick the shard key to keep hot queries single-shard.

MySQL vs PostgreSQL — when to pick which

Both are mature, ACID, relational, and the "safe default" for a transactional core. For most interviews either is a defensible pick — what matters is that you can justify the choice. (We covered Postgres internals in Lesson 88.)

One-liner for the whiteboard: pick MySQL when you want a lean, battle-tested OLTP engine with a massive operational ecosystem and a clear sharding path; pick Postgres when you want richer query features, advanced index types, and stricter SQL semantics. Don't litigate the religious war — state the requirement that decides it.

★ Staff-level signal Senior says "MySQL, with read replicas." Staff connects the internals to the requirement: "InnoDB clusters by primary key, so I'll use an auto-increment or time-ordered ID — not a random UUID — to keep inserts sequential and the buffer pool warm. Reads scale on async replicas, but checkout reads its own write, so I route that path to the primary to dodge replication lag. When write volume outgrows one primary, I shard by user_id and accept losing cross-shard joins — which is why I'd model to keep the hot path single-shard." The move is refusing to treat the database as a black box: you reason about page layout, lock granularity, and lag the same way you'd reason about a cache hit rate.[3]

In the interview

  • Name the engine and the PK strategy together. "MySQL/InnoDB, auto-increment PK" preempts the clustered-index follow-up.
  • Reach for a covering index when a read-hot query is the bottleneck — it kills the secondary-index double lookup.
  • Scale reads with replicas first; call out lag and how you route consistency-critical reads to the primary.
  • Treat sharding as a last resort for writes, and name what you lose (cross-shard joins/transactions) when you propose it.
  • Mention semi-sync when the prompt cares about not losing committed data on failover.

Check yourself — retrieval practice

Answer from memory before scrolling back up.

1. Why does a random UUID make a poor InnoDB primary key?

The table IS the PK B+tree, so random keys insert at random leaves, causing page splits and fragmentation.

2. A lookup via a secondary index in InnoDB normally does what?

Secondary leaves store the PK value, so InnoDB then walks the clustered index — a covering index avoids the second hop.

3. What does the redo log let InnoDB do on every commit?

Write-ahead logging means commits write the sequential redo log; random data-page flushes happen lazily in the background.

4. A user writes, then reads from an async replica and misses it. Why?

Async replication means the replica trails the primary; route read-your-writes paths to the primary to avoid the lag.
