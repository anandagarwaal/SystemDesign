System Design · Lesson 07 · Phase 1 — Core Concepts

Messaging & Async Processing

Stop making the user wait. Decouple the work, absorb the spike, and pick the right pipe — queue or log.

Why this lesson, for your mission: Almost every L6/L7 design eventually needs work done off the request path — sending notifications, aggregating clicks, processing payments, building a feed. The senior move is "add a queue." The staff move is knowing which async primitive (queue vs. event log), why, and how you keep it correct when messages get delivered twice. This lesson gives you that judgement.

1 of 6

Why go async at all?

A synchronous request does everything before it replies: validate, write, charge the card, send the email, update three caches — then return 200. The user waits for the slowest step, and a spike in traffic hits every downstream system at once. Async processing breaks that chain. The web server does the minimum to accept the request, drops a message onto a queue, and returns immediately. A separate pool of workers picks up the message and does the slow work later.

You reach for async for four recurring reasons:

  • Decoupling — the producer (web server) and consumer (worker) don't need to be up, fast, or scaled together. The queue sits between them as a buffer and a contract.
  • Load leveling / absorbing spikes — a queue smooths a bursty write rate into a steady consumption rate. A flash sale that triples writes for 30 seconds fills the queue; workers drain it at their own pace instead of falling over.
  • Slow work off the request path — video transcoding, generating a PDF, calling a flaky third-party API. Return fast, finish in the background.
  • Retries & durability — if a worker crashes mid-task, the message isn't lost; it goes back on the queue and gets retried. The request itself already succeeded.

The tradeoff is honesty about eventual consistency and complexity. The user gets a "we're on it" instead of a "done." You now operate one more moving part, you have to reason about duplicate and out-of-order messages, and debugging spans two systems. Async is not free — use it where the work is genuinely deferrable.

★ Staff-level signal A queue smooths a spike; it does not create capacity. If your consumers are permanently slower than your producers, the queue just grows without bound — "a queue is just obscuring the problem."[1] Say out loud whether you're buffering a temporary burst (good) or papering over a sustained under-provisioning (bad). Naming that distinction unprompted is the senior-to-staff jump.
Check yourself

Which of these is NOT one of the four recurring reasons to go async?

Async trades an immediate final result for "we're on it" plus eventual completion. The four reasons are decoupling, load leveling, slow work off the request path, and retries/durability.

Reread the four bullets in the box — none of them promise the caller a synchronous final answer.

Why does an ever-growing queue mean the queue "isn't the fix," even though messages aren't being lost?

Buffering absorbs a temporary mismatch between producer and consumer rate. If the gap is permanent, the backlog only grows, and the real fix is more consumer capacity or backpressure, not a bigger buffer.

Reread the staff callout: "a queue is just obscuring the problem" — obscuring what, exactly?

Queues vs. event logs — the core choice

Both are "messaging," and interviewers use the words loosely, but they solve different problems. A message queue (SQS, RabbitMQ) is for distributing work: a message is consumed once, by one worker, then removed. A distributed log / event stream (Kafka, Kinesis) is for durably recording events: messages are appended to an ordered log, kept for a retention window, and any number of independent consumer groups can read — and re-read — them.[2]

DimensionMessage Queue (SQS, RabbitMQ)Event Log / Stream (Kafka, Kinesis)
Mental modelTo-do list of tasksAppend-only ledger of events
After consumptionMessage is deletedMessage stays until retention expires
ConsumersCompeting workers share the load; each message goes to oneMultiple consumer groups each read the whole stream independently[2]
ReplayNo — once gone, it's goneYes — rewind to any offset or timestamp[2]
OrderingBest-effort / per-groupStrict within a partition
Best forTask distribution: send email, resize image, process jobEvent sourcing, analytics, fan-out to many systems[2]
The decision rule (say this in the interview):
  • Need one team of workers to chew through tasks, and you don't care about history once done? → Queue.
  • Need multiple independent consumers (notifications + analytics + search indexer all reading the same events), or the ability to replay after a bug, or ordered events? → Log (Kafka).
Justify by replay and consumer count, not by brand name.
Check yourself

Three independent teams (notifications, analytics, search indexing) must each react to the same "post created" events, with replay after a bug. Which fits best?

A log keeps events for a retention window and lets multiple consumer groups read independently and replay from any offset; a queue deletes a message after one consumer takes it.

Reread the decision rule box — what does "multiple independent consumers" and "replay" point to?

Why does a message queue delete a message after one worker consumes it, while a log keeps it around?

The two data structures encode different intents: a queue's job is "get this task done once," so keeping it after that is pointless; a log's job is "record what happened," so multiple independent readers each need their own view of the same history.

Compare the "mental model" row in the table: to-do list versus ledger.

Kafka specifics you must be able to draw

Kafka is the default streaming platform you'll name in interviews, so know its vocabulary cold.[2]

TermWhat it is
TopicA named stream of events, e.g. clicks or payments.
PartitionA topic is split into partitions across brokers. Ordering is guaranteed within a partition; partitions are how you scale and parallelize.[2]
Partition keyA field (e.g. userId) hashed to pick the partition. Same key → same partition → ordered together.[2]
Consumer groupA set of consumers sharing a topic's partitions. Different groups read the same topic independently.[2]
OffsetA consumer's bookmark — the position it has read up to. Committing offsets lets it resume; rewinding them replays.[2]
RetentionHow long events stay (e.g. 7 days, or by size). Within the window, anyone can re-read from any offset.[2]

Why your partition-key choice is the whole game

The partition key trades off two things you can't both maximize:

  • Ordering. If you need all of a user's events processed in order, key by userId so they land in one partition. Keyless events spread round-robin and lose cross-partition order.
  • Hot partitions. If one key is far busier than the rest (a celebrity's posts, one giant tenant), its partition becomes a bottleneck while others sit idle. You either pick a higher-cardinality key or accept that ordering and add a salt/sub-key.

Calling out "I'll partition by userId for per-user ordering, but watch for hot partitions on power users" is exactly the level of specificity interviewers want.

Check yourself

In Kafka, what does choosing userId as the partition key buy you, and what's the risk?

Same key hashes to the same partition, giving ordering within it — but a heavily used key (a power user) overloads that one partition while others idle.

Reread "Why your partition-key choice is the whole game" — ordering and hot partitions are the two named tradeoffs.

What would you expect to happen to cross-event ordering if events are published without any partition key at all?

Without a key, the producer has no reason to route related events to the same partition, so they scatter round-robin — fine for throughput, but you lose any cross-event ordering guarantee.

Reread the "Ordering" bullet — it explicitly contrasts keyed events against "keyless events."

Delivery semantics & idempotency

Networks fail between "worker did the work" and "worker acked the message." That gap forces a choice about what guarantee you can offer:

SemanticMeaningCost
At-most-onceAck first, then process. A crash can drop the message.Fast, lossy. OK for metrics you can lose.
At-least-onceProcess, then ack. A crash before ack means redelivery — possible duplicates. The common default.No loss, but you must handle duplicates.
Exactly-onceEvery message effected exactly once. Hard and expensive — needs transactional coordination across systems.Often impractical end-to-end.
The staff answer to "how do you get exactly-once?" You usually don't. You take at-least-once delivery and make the consumer idempotent — processing the same message twice has the same effect as processing it once. Practically: attach a unique messageId / requestId, and before acting, check whether you've already processed it (a dedup table, a unique DB constraint, or a conditional write). A retried "charge $10" then becomes a no-op the second time.
★ Staff-level signal When asked about duplicates, do not hand-wave "we'll use exactly-once delivery." Say: "At-least-once is the realistic delivery guarantee; I'll make the consumer idempotent with an idempotency key so duplicates are harmless." That single sentence signals you've actually run a queue in production. Reserve real exactly-once for cases where the broker and sink support a transaction (e.g. Kafka transactions into the same Kafka), and name that scope.
Check yourself

An interviewer asks how you'll prevent a double charge when a payment message might be delivered twice. Strongest answer?

At-least-once is the realistic guarantee; idempotency (a dedup/idempotency key) makes a redelivered message a harmless no-op. End-to-end exactly-once is hard and usually impractical.

Reread "The staff answer to how do you get exactly-once" — you usually don't get it, you route around needing it.

Why does at-most-once ("ack first, then process") risk losing messages, while at-least-once doesn't?

Acking is the broker's signal to forget the message. Ack before the work finishes, and a crash in between silently drops the task with no redelivery, since the broker already marked it handled.

Compare the order of operations in the table: "ack first, then process" versus "process, then ack."

The operational toolkit: DLQs, backpressure, outbox

Three names that make your design look battle-tested:

  • Dead-letter queue (DLQ) — a message that fails repeatedly (poison message) shouldn't block the queue or retry forever. After N attempts, route it to a DLQ for inspection/alerting, and keep draining the rest.
  • Backpressure — when consumers can't keep up, the system needs to push back: cap queue depth, slow or reject producers, or auto-scale workers. Without it, the queue grows unbounded and latency explodes. Backpressure is how a buffer stays a buffer.
  • Outbox pattern / CDC — to publish an event and commit a DB write atomically, write the event to an outbox table in the same transaction, then a relay (or Change Data Capture tailing the DB log) publishes it to Kafka. This avoids the "wrote to DB but crashed before publishing" inconsistency.

How this shows up in interviews

You introduce messaging the moment work doesn't need to happen inline. The pattern is always: producer writes to a queue/log, returns fast; workers consume and do the heavy lifting; the system stays responsive under load.

DesignWhere messaging lands
Ad Click AggregatorStream raw clicks into Kafka (keyed by ad), workers aggregate in windows; replay enables reprocessing.
Job SchedulerQueue of due jobs; competing workers pull and execute; DLQ for failures; idempotency for retries.
News FeedOn post, emit an event; fan-out workers write to followers' feeds off the request path.
PaymentsAt-least-once processing with idempotency keys; outbox to publish "payment succeeded" reliably.

Pick the primitive deliberately: a queue for "smooth a spike / distribute long-running tasks," a log when you need replay or multiple consumers (notifications + analytics + indexing off one event stream).

Check yourself

What specific inconsistency does the outbox pattern prevent?

Writing the event to an outbox table in the same DB transaction guarantees the event and the state change succeed or fail together; a relay or CDC then reliably publishes it afterward.

Reread the outbox bullet — it names the exact failure mode it avoids in quotes.

What breaks if a queue has no dead-letter queue and a message keeps failing every retry?

Without a DLQ to shunt permanently-failing messages aside, a poison message keeps consuming retry cycles and can block the queue from draining the healthy messages behind it.

Reread the DLQ bullet — it says what "shouldn't" happen without one: block the queue or retry forever.

A queue is filling faster than workers can drain it, indefinitely. What is the queue actually telling you?

Recall the first staff callout: a queue is just obscuring the problem when growth is sustained.

If you drop the partition key and let events scatter round-robin, what capability specifically do you lose, and why?

Ordering within Kafka comes from same-key events hashing to the same partition. Remove the key and events spread round-robin across partitions, so any guarantee about the order of related events disappears — durability, consumer-group isolation, and retention are unrelated to keying.

Recall why userId as a partition key gives per-user ordering in the first place.

A junior engineer proposes making every write path async "for resilience." What's the staff-level pushback?

Async isn't free: you add a moving part, must reason about duplicates and ordering, and the caller only gets "we're on it." Reach for it only when the work can genuinely wait, not as a reflexive resilience upgrade.

Recall the "tradeoff is honesty" paragraph in the first section — async costs something even as it buys decoupling.
