Design a Code Hosting Platform (GitHub / GitLab)

A git repository is just a content-addressed object store — host millions of them durably, and serve clones fast.

Why this lesson, for your mission: GitHub looks like a CRUD app with a fancy diff viewer, and a senior candidate will design it that way. The staff-level move is recognizing that the repository itself is the hard data-storage problem: git objects are immutable, content-addressed blobs that must be sharded across stateful storage, replicated for durability, and served over a streaming wire protocol with sub-second clone latency. Get the "repos are sharded, replicated data — not rows in a table" framing in the first five minutes, and the rest of the hour is deep dives you control.[1]

Functional Requirements

Scope to the flows that define the system. A code host is two systems bolted together: a git server (the repo bytes) and a collaboration app (PRs, search, hooks).[1]

#Users should be able to…
1Host git repositories and push / pull / clone over the git smart protocol (HTTPS & SSH).
2Open pull requests and review code (diffs, comments, approvals, merge).
3Browse & search code across files and across millions of repositories.
4Fire CI hooks — a push triggers webhooks / pipelines on downstream systems.

Explicitly out of scope (say it aloud): the issue tracker, the wiki, package registries, and the IDE/web editor. Naming deferrals shows judgement about the breadth/depth ratio.

Capacity Estimation

Only the numbers that change a decision. For a code host the load-bearing facts are repo count (sharding), read:write ratio (replicas), and the fact that a repo is a stateful blob (not a stateless row).

  • Repo count → sharding. ~100M+ users, ~400M+ repos at a few MB–GB each = tens of petabytes of git data.[1] Implication: no single file server holds it; repos are sharded across a fleet of stateful storage nodes, located via a routing layer.
  • Read:write ≈ 100:1. Every CI run, every developer pull, every browse hits the repo; pushes are comparatively rare. Implication: each repo has 1 primary + multiple read replicas; clones/fetches route to replicas, pushes to the primary.
  • Search corpus → dedicated index. Billions of source files, each tokenized into trigrams/symbols. The index is many TB and grows with every merge. Implication: code search is a separate service with its own inverted index — never a LIKE '%foo%' scan of git data.
  • Clone bandwidth → packfiles + CDN-like caching. A clone ships the whole history; without packing it is gigabytes of loose objects. Implication: serve compressed packfiles and cache common refs.

High-Level Design

The whole system hinges on splitting two paths that behave nothing alike: the git data path (huge, stateful, streamed, sharded) and the metadata path (small, relational, queried constantly). A stateless API/git-frontend tier authenticates and routes; it never stores a repo.[1]

ComponentRoleStore
Git frontend (stateless)Terminates SSH/HTTPS, authenticates, checks ACLs, then proxies the git protocol to the right storage node.—

Clone flow: client → frontend authenticates & ACL-checks → router picks a read replica of the repo → replica runs git-upload-pack, negotiates what the client lacks, streams a packfile back.[4] Push flow: client → frontend → router picks the primary → git-receive-pack writes objects and advances refs → primary replicates to followers → an event is published to the bus, fanning out to webhooks/CI and the search indexer.

★ Staff-level signal The line that separates senior from staff: "A repository is not a row in a database — it's a stateful, content-addressed blob store that I have to shard and replicate myself, like a mini storage system per repo." A senior candidate stuffs repos into S3 or a giant table and waves at "git magic." A staff candidate knows git objects are immutable and content-addressed by SHA, so replication is append-and-fast-forward (not row updates), reads scale trivially across replicas, and the only coordination point is advancing a ref on the primary. Naming the routing layer (repoId → shard) and the primary/replica split, unprompted, is the proactive deep dive that earns the level.

Deep Dives

1. Storing git repositories at scale — sharding & replication

A git repo is a content-addressed object database: every commit, tree, and blob is identified by the SHA of its contents, so objects are immutable and append-only.[6] That property is a gift for a storage designer.

  • Shard by repo. Repos are independent, so distribute them across a fleet of storage nodes; a routing service maps repoId → node. This is exactly the "RPC to a sharded fleet of stateful file servers" model GitHub uses with Gitaly + the routing layer.[1] Hot repos (e.g. a popular OSS project) get more replicas, not a bigger box.
  • Replicate for durability. Keep N copies (e.g. 3) of every repo on different nodes/failure domains. Because objects are immutable and pushes only fast-forward refs, replication is "ship the new packfile + update the ref" — there are no in-place mutations to reconcile.[2] A consensus/voting layer (GitHub's Spokes/DGit, or Gitaly Cluster's Raft-based design) confirms a write landed on a quorum before acking the push.[2]
  • Read replicas for clone latency. Since reads are ~100× writes, send clones/fetches/CI to replicas and only pushes to the primary. This is the same primary/replica pattern you learned for databases — see Lesson 6 · Replication & CAP. We pick availability over strong consistency: a replica might be a few seconds behind, which for a clone is invisible.
  • Failover. If a primary dies, promote a replica that has the latest acked ref. The voting layer guarantees a promotable replica exists.

2. The git smart protocol & large-repo handling

Don't hand-wave "git syncs the files." Git uses the smart protocol: a negotiation, then a single compressed stream.[4]

Clone/fetch (upload-pack): (1) server advertises its refs and their tip SHAs; (2) client says "I want X, I already have Y" (want/have negotiation); (3) server computes the difference and streams a packfile — objects delta-compressed against each other.[4][6]
  • Push (receive-pack) is the mirror: client sends a packfile of new objects + the ref update it wants; the primary validates connectivity (no missing objects), applies hooks, and fast-forwards the ref.[4]
  • Big-repo problem. A huge monorepo's full history is enormous, and naïvely repacking it per clone is CPU/memory death. Mitigations the interviewer wants to hear: cached packfiles / bitmaps so the server doesn't recompute the pack each time;[6] shallow clones (--depth) and partial clones (filter blobs) so clients fetch only what they need; and a CDN/byte-cache for the static portion of large fetches.
  • Large files. Binary assets bloat history forever (objects are immutable). Push them out of git into a blob store via Git LFS — git tracks a small pointer, the bytes go to object storage. This is the same metadata/blob split from Lesson 12 · Dropbox[3].

3. Code search over millions of repositories

You cannot grep petabytes of source per query. Code search is its own service with an inverted index — the identical machinery behind Lesson 25 · Facebook Post Search and classic web search.[5]

  • Index, don't scan. Tokenize every file and build a map token → list of (repo, file, positions). A query becomes set intersections over posting lists, not a filesystem walk.[5]
  • Code-specific twist: trigram indexing. Plain word tokens miss substring/regex queries like handleRequest(. The standard trick (Google Code Search, GitHub's Blackbird, Zoekt) is a trigram index: index every 3-character sequence, then a regex search becomes "find docs containing all required trigrams," then verify candidates with the real regex.[5] This is why code search feels like grep but scales.
  • Keep it fresh. The indexer subscribes to the same push/merge event bus; on a merge it re-indexes the changed files. The index is eventually consistent — a result lagging the repo by seconds is fine.
  • Scale & ACLs. Shard the index by repo and fan queries out; filter results by the caller's ACLs so private repos never leak into another user's results.

4. Pull-request & review metadata in a relational store

PRs are the part that is a CRUD app — and that's the point: keep it in a boring, well-understood relational DB rather than contaminating the git storage layer.

  • Why relational. PRs, reviews, comments, approvals, and ACLs are highly relational, need transactions (an approval count must be consistent), and demand rich queries ("open PRs assigned to me, awaiting my review"). Postgres/MySQL with foreign keys fits naturally.
  • The diff is computed, not stored. A PR stores only the two ref SHAs (source & target); the actual diff is computed on demand by the git layer from those immutable commits and cached. Don't store rendered diffs as rows.
  • Merge is the one cross-system transaction. "Merge PR" must: verify approvals/checks (DB), perform the git merge on the primary storage node (git), then flip PR state to merged (DB). Order it git-first: do the ref update, and only on success mark merged — so a crash leaves a still-open PR (safe) rather than a "merged" PR with no commit (corrupt).
  • Scale. Read replicas + caching for the read-heavy PR/timeline views; partition by repo or org as the table grows.

5. Webhooks to trigger CI

A push must reliably notify downstream systems (CI, deploy bots, chat). Doing this synchronously inside the push would couple clone/push latency to some third party's slow endpoint — never do that.

  • Async fan-out. On a successful receive-pack, the primary publishes a push/merge event to a message queue; webhook delivery workers consume it and POST to each subscribed URL. The push acks the instant the ref is replicated — delivery happens off the critical path.
  • At-least-once + retries. Treat delivery as at-least-once with exponential backoff and a dead-letter queue; sign each payload with the webhook secret (HMAC) so the receiver can verify authenticity. Consumers must be idempotent.
  • This feeds CI/CD. The CI system is just one webhook consumer that, on the event, schedules a pipeline against the new commit SHA — the subject of the very next lesson on CI/CD systems.

Check yourself — retrieval practice

Answer from memory before scrolling back up.

1. Why is replicating a git repository simpler than replicating mutable table rows?

Immutable SHA-addressed objects mean no in-place updates to reconcile — just ship new packs and advance the ref.

2. During a clone, what does the git smart protocol actually stream to the client?

After want/have negotiation the server computes the difference and streams one compressed packfile.

3. Why does code search use a trigram index instead of plain word tokens?

A 3-char index turns substring/regex search into "docs with all required trigrams," then verify candidates.

4. Why are CI webhooks fired asynchronously through a queue rather than inside the push?

Off-critical-path fan-out with retries keeps push acks fast and tolerates slow or failing consumers.
