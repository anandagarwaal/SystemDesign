Design Dropbox (File Storage & Sync)

Move the metadata through your servers and the bytes around them.

Why this lesson, for your mission: Dropbox looks deceptively simple — "store a file" — but it's the canonical test of one staff-level instinct: don't stream large blobs through your application tier. Get the metadata/blob separation and direct-to-S3 presigned upload right in the first five minutes, and the rest of the interview becomes a tour of well-known deep dives. Get it wrong, and you spend the hour fighting a bottleneck you invented.

Functional Requirements

Scope ruthlessly. Three flows carry the whole design; everything else is gravy.[1]

#Users should be able to…
1Upload a file from any device.
2Download a file from any device.
3Sync & share — changes propagate automatically across a user's devices and to people they share with.

Explicitly out of scope (say this aloud): in-browser editing, file preview without download, and full version history. Naming them shows judgement about what to defer.[1]

Capacity Estimation

Only estimate numbers that change a decision. For Dropbox, the load-bearing number is file size, not QPS.

  • File size → chunking. A 50 GB file over a 100 Mbps link takes ~1.1 hours to transfer.[1] No single HTTP request survives that (load balancers and proxies time out in 30–60s). Implication: uploads must be chunked and resumable.
  • Storage growth. 500M users × 50 GB cap, even at 1% fill = ~250 PB. Implication: blobs live in object storage, never on app-server disks; and dedup is worth real money.
  • Bandwidth. If every byte flowed through the app tier, you'd provision the app fleet for petabyte-scale throughput. Implication: bytes must bypass the app tier entirely (direct-to-S3 + CDN).

Core Entities & API

Three entities. Note how File (the bytes) is deliberately separate from FileMetadata (the description) — that split is the design.[1]

The user is derived from the auth token, never passed in the body.

High-Level Design

The whole system hinges on one decision: separate the metadata path from the blob path. Metadata (small, structured, queried constantly) flows through your app servers into a database. Blobs (huge, opaque, written once) go around the app tier, straight to object storage.[1]

ComponentRoleStore
ClientWatches the local folder; chunks files; PUTs bytes to S3; long-polls the change feed.—

Upload flow (three steps): (1) client POSTs metadata → backend writes a row with status uploading and returns a presigned URL; (2) client PUTs the bytes directly to S3; (3) an S3 event notification tells the backend to flip status to uploaded.[1] The file's bytes never touch an app server — that's the point.

★ Staff-level signal The instant you say "the client uploads the bytes straight to S3 via a presigned URL, and only the metadata flows through my service," you've shown the load-bearing insight. The anti-pattern — proxying multi-GB blobs through your app tier — forces you to scale the app fleet for raw bandwidth, doubles every byte's network hops, and couples upload throughput to your server count. A senior candidate often draws "client → app server → S3." A staff candidate draws "client → S3" for bytes and "client → app server → DB" for metadata, and can explain why the two paths must diverge.

Deep Dives

1. Large file uploads — chunking, resumable, multipart

A 50 GB file cannot ride a single request.[1] Break it into 5–10 MB chunks and track each one in metadata:

{ id, status:"uploading", chunks:[ {id:"c1", status:"uploaded"}, {id:"c2", status:"uploading"} ] }
  • Resumable. If the connection drops at chunk 7 of 5,000, the client asks which chunks already landed and uploads only the rest. Don't identify the file by name — names lie. Identify it by a cryptographic content hash (fingerprint) of the bytes, with a per-chunk hash too.[1]
  • Trust nothing. The client reports "chunk done," but a malicious or buggy client could lie. The backend verifies via S3's ListParts API and the per-chunk ETags before flipping status.[1] Server-side verification, not client assertion.
  • Assemble. Once every chunk is confirmed, the backend calls S3 CompleteMultipartUpload with the part numbers and ETags; S3 stitches them into one object.[1]
  • Parallelism. Upload chunks concurrently and size them adaptively to network conditions for throughput.[1]

2. Sync — change detection, the feed, conflicts, dedup

Sync is two directions stitched together.[1]

  • Local → remote: the client watches the filesystem, queues changes, and uploads via the file service.
  • Remote → local (hybrid): the server pushes changes over WebSocket/SSE for low latency, and the client also polls GET /v1/files/changes?since={ts} periodically as a fallback to catch anything missed when a connection dropped.[1] Push for speed, poll for correctness.

Conflicts: two devices edit offline, then both sync. The simple, defensible default is last-write-wins by timestamp; mention that real Dropbox keeps both as "conflicted copies" rather than silently dropping data.[1]

Dedup via content hashes. If two users upload the same file (or one user re-saves a 50 GB file after editing 1 KB), don't store it twice. Address blocks by their content hash; an identical hash means the bytes already exist — just point new metadata at them. Naïve fixed-size block boundaries break on insertion: adding one byte near the start shifts every later boundary, busting the whole dedup. The fix is content-defined chunking with a rolling hash (Rabin fingerprinting) so a local edit only re-chunks its neighborhood.[2] This is also how delta sync uploads only changed blocks.

3. Presigned URLs + CDN for download

Serving downloads is the mirror of uploads: the backend returns a presigned URL and the client fetches bytes directly — never through the app tier. To cut latency globally, don't hand out a raw S3 URL; hand out a CDN-signed URL so users pull from the nearest edge location.[1] Keep expirations short (e.g., 5 minutes) so a leaked link can't be reshared, and have the CDN validate the signature with a private key.[1]

4. Consistency between metadata and blob

The two paths can disagree: metadata says uploaded but the blob PUT actually failed, or the blob lands but the "complete" call is lost. The discipline is to treat the blob store as the source of truth for existence and metadata as a claim that must be verified. That's exactly why status starts at uploading and only advances after S3's own APIs (ListParts / event notification) confirm the bytes.[1] Reads should never surface a file whose metadata is still uploading. This gives you read-after-write correctness for the user without demanding strong consistency across the two stores.

Check yourself — retrieval practice

Answer from memory before scrolling back up.

1. Why do file bytes go directly to S3 instead of through the app servers?

Routing bytes around the app tier decouples upload throughput from server count.

2. What is the main reason files are uploaded as chunks?

Chunking enables resumable, parallel uploads that survive dropped connections.

3. Why use content-defined chunking instead of fixed-size blocks for dedup?

A rolling hash keeps boundaries stable so edits re-chunk only locally.

4. How does remote-to-local sync stay both fast and correct?

Push gives low latency; periodic polling catches anything missed during outages.
