Design Bitly (URL Shortener)

A deceptively simple prompt that is really two problems in a trench coat: generating unique IDs and scaling reads.

Why this lesson, for your mission: Bitly is the canonical warm-up. The trap is treating it as easy and burning your time on CRUD. The staff move is to see through the surface — recognize within the first two minutes that this is a unique-ID generation problem stacked on a read-scaling problem, then spend your depth budget there. Get this framing right and the same muscles carry into Ticketmaster, Pastebin, and any system with a hot read path.

Functional Requirements

Drive the interviewer to the two core flows; everything else is a "would you like fries with that" add-on. Auth, spam detection, and click analytics are explicitly out of scope for the base design.[1]

#RequirementNote
1Users can submit a long URL and get a short URL backCore write path
2Users can supply an optional custom alias and expiry dateModifiers on the write
3Visiting a short URL redirects to the original long URLCore read path — the money flow

Non-Functional Requirements

State the targets with numbers — vague "-ilities" are a senior tell. The single most important line you can say here: this system is read-heavy, on the order of 100:1 to 1000:1 reads per write.[1] That asymmetry is the design.

PropertyTargetWhy it drives design

Capacity Estimation

Only compute the numbers that change a decision. Three matter here: read QPS, write QPS, and short-code length.

Read vs. write QPS

100M DAU × ~5 redirects/day ≈ 500M reads/day ≈ ~6k reads/sec average, spiking toward ~600k/sec at peak.[1] Writes are ~100k new URLs/day ≈ ~1 write/sec. Implication: the write path can be a single boring SQL insert; the read path needs a cache and possibly a CDN. Scale the two independently.

Storage

~500 bytes/record × 1B URLs ≈ 500 GB.[1] Implication: this fits on one beefy node — sharding is a "later if asked" concern, not a day-one decision. Don't over-engineer a sharded cluster you don't need.

Short-code length (the load-bearing math)

We encode codes in base62 — [a-zA-Z0-9], 62 symbols. Why not base64? The / is a URL path separator and + decodes to a space in query strings, so both are unsafe in a path.[1] Each character multiplies the keyspace by 62:

LengthKeyspace (62^n)Verdict for 1B URLs
5≈ 916 millionToo small — runs out
6≈ 56.8 billionEnough today (50× headroom)
7≈ 3.52 trillionGenerous future-proof default

Implication: 6 characters covers 1B URLs with room to spare; pick 7 if you want headroom for years of growth at trivial extra cost.[1] This number directly feeds the ID-generation deep dive below.

Core Entities & API

One entity does almost all the work: the URL mapping (short_code, long_url, custom_alias, expires_at, created_by, created_at). A User entity exists if you support ownership.[1] Two endpoints cover both flows; derive the creator from the auth token, never from the request body.

EndpointPurposeReturns
POST /v1/urlsCreate. Body: long_url, optional custom_alias, expires_at201 + short_url
GET /{shortcode}Redirect to the original URL302 Found + Location header

High-Level Design

Separate the two flows from the start — they have wildly different traffic and SLAs.

FlowPathStores touched
Write (rare)Client → API/Write Service → generate code → insert rowDB (+ counter/key service)
Read (constant)Client → CDN/edge → Cache → (miss) DB → 302Cache, then DB

The write service validates the URL, obtains a unique code, and persists the mapping. The read service resolves short_code → long_url and issues the redirect. The DB enforces uniqueness via a UNIQUE constraint / primary key on short_code, which also gives you a B-tree index for O(log n) lookups for free.[1] Any of Postgres, MySQL, or DynamoDB works — read load is offloaded to cache and write load is tiny, so the DB choice is low-stakes; default to Postgres if unsure.[1]

Deep Dives

This is 60% of your score. The first two are mandatory; the rest are proactive depth that signals seniority.

Deep Dive 1 — Generating unique short codes

This is the heart of the problem. Three approaches, in increasing order of staff-ness:

ApproachHowProblem
Hash + truncateHash the long URL, base62-encode, take first N charsCollisions rise with scale (birthday problem); needs a read-before-write or retry-with-salt loop on every create[1]
Counter + base62Atomically increment a global counter; base62-encode the integerZero collisions by construction. But naive: a central counter is a hot dependency, and sequential codes are enumerable[1]
Key-generation serviceA service pre-generates/owns ranges of unique keys and hands them outRemoves the per-write coordination; the staff refinement of the counter idea
The staff-favored pick: counter + base62, hardened.
  • Why over hashing: hashing makes collision handling your steady-state cost — every write may need a DB round-trip to check, and the collision rate worsens as the table fills. The counter sidesteps the entire problem: monotonic integers are unique by definition. You are trading a probabilistic problem for a deterministic one.
  • Counter batching: don't hit the counter per write. Each write-service instance grabs a batch (e.g. 1,000 IDs) from Redis, which is single-threaded and atomic, then serves locally.[1] This collapses network calls and lets one Redis node sustain 100k+ ops/sec.
  • Enumeration fix: sequential codes let anyone scrape the corpus. Bias-shuffle the integer before encoding, or interleave with random bits, so codes look opaque without reintroducing collisions.[1]
  • Availability: Redis Sentinel / Cluster with failover; batching means an instance survives a brief counter outage on its remaining buffer.[1]
  • Multi-region: hand each region a disjoint counter range (region A: 0–1B, region B: 1B–2B) so they never coordinate cross-region.[1]

Deep Dive 2 — Scaling reads to 600k/sec

Raw DB IOPS (~100k on good SSD) cannot meet 600k peak reads. Layer the read path:

LayerMechanismWin
IndexPrimary key / B-tree on short_codeO(log n) DB lookup[1]
CacheRedis/Memcached, LRU eviction, read-throughMemory ~100ns vs SSD ~0.1ms; millions of reads/sec[1]
CDN / edgeCloudflare Workers / Lambda@Edge resolve hot codes at PoPPopular links never hit origin[1]
ReplicasRead replicas behind the cache for cache-miss fan-outScales miss traffic independently

Because the read:write ratio is so skewed and a small number of links go viral, cache hit rates are excellent — the long tail of URLs barely matters. CDN edge resolution is the latency win but adds cache-consistency and debugging cost, so reach for it only after the cache is in place.[1]

Deep Dive 3 — Custom aliases & collisions

Custom aliases share the same code space as generated codes, so a future counter value could collide with someone's existing alias. Two clean fixes: keep aliases in a separate namespace, or prefix generated codes with a character custom aliases are forbidden to use, making the two sets disjoint by construction.[1] On create, a UNIQUE constraint rejects a duplicate alias; surface a clear "alias taken" error.

Deep Dive 4 — Click analytics, asynchronously

Analytics is out of base scope but a great proactive extension. The rule: never let logging slow the redirect. On each read, fire a lightweight event onto a message queue (Kafka/Kinesis) and return the 302 immediately. A downstream consumer aggregates clicks into an analytics store off the hot path. This keeps redirects under 100ms while still capturing every click — and it's the reason the redirect-code choice below matters.

Deep Dive 5 — 301 vs. 302 redirect

The tradeoff is caching vs. control.
  • 301 (Permanent): browsers cache it, so repeat visits skip your server entirely. Lower load and latency — but you lose the click event and can no longer expire or repoint the link.
  • 302 (Found): not cached; every click returns through your server. You keep full control — analytics, expiry, repointing — at the cost of serving every hit.[1]
Pick 302 for a Bitly-style product: link-level control and click analytics are the business, and your cache/CDN already absorbs the extra hits cheaply.[1] Expired links return 410 Gone; set cache TTL to match expires_at.[1]
★ Staff-level signal The senior names the hashing-vs-counter tradeoff. The staff engineer reframes the whole problem in the first two minutes — "this is a unique-ID generator bolted to a read-scaling cache, the rest is CRUD" — and budgets time accordingly. They reject naive hashing not on vibes but because it makes collision handling a steady-state per-write cost, then harden the counter for the production concerns nobody asked about: enumeration security, counter failover, disjoint multi-region ranges, and async analytics off the hot path.[1] The trap is doing CRUD beautifully and running out of clock before the two parts that actually matter.

Check yourself — retrieval practice

Answer from memory before scrolling back up.

1. Why is the counter + base62 approach generally favored over hashing the long URL?

Monotonic counters are unique by construction; hashing turns collision handling into a steady-state per-write cost.

2. Roughly how many base62 characters are needed to encode 1 billion URLs?

62^6 ≈ 56.8 billion, comfortably above 1B; 7 chars (≈3.5T) adds headroom.

3. Why prefer a 302 over a 301 redirect for a URL shortener product?

302 isn't cached, so each hit returns through your server — needed for click tracking, expiry, and repointing.

4. What is the single most design-shaping fact about a URL shortener?

The ~100:1+ read:write skew is why the read path gets caches and CDNs while writes stay a trivial insert.
