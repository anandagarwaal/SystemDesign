System Design · Lesson 67 · Phase 4 — Case Study · Hard

Design a CI/CD System (Jenkins / GitHub Actions)

Turn a git push into parallel build/test jobs on a fleet of ephemeral, sandboxed runners — fast, fair, and safe against untrusted code.

Why this lesson, for your mission: A CI/CD platform is really three hard systems wearing a trench coat: a job scheduler, a multi-tenant sandbox, and a DAG executor. Seniors describe "a webhook starts a build." Staff candidates decompose untrusted-code isolation, an autoscaling pool of ephemeral runners, a stage DAG with fan-out/fan-in, and a caching strategy that decides whether builds take 2 minutes or 20. Pick those battles out loud and you've passed.

Phase 1 · 0–5 minClarify the problemPin scope and the few NFRs that will drive every later decision.

Ask before you design

  • “Hosted multi-tenant runners, customer self-hosted runners, or both?” — Multi-tenant runners make isolation of untrusted code the top concern.
  • “What's the expected job duration and burstiness?” — Spiky demand drives autoscaling and warm pools.
  • “Do pipelines need secrets for deployments?” — Secrets require scoped injection and protection from untrusted forks.

Functional Requirements

Scope to what a developer actually expects when they push code; everything else is out of scope.

The user should be able to…Detail
Trigger a pipelineA push or pull-request event fires the repo's pipeline automatically via a webhook.[1]
Run jobs in parallelBuild and test jobs execute concurrently across runners, respecting declared dependencies.[2]
See status & logsPer-job pass/fail status reported back to the commit/PR, with streamed logs.[1]
Store & deploy artifactsPersist build outputs (binaries, images) and run a deploy step on success.[2]

Out of scope (say it aloud): the source-control system itself (see Lesson 66), the contents of users' build scripts, billing/quotas, and rich pipeline-authoring UI. We deliver the engine, not the YAML.

Non-Functional Requirements

PropertyTarget / priority
Scalability of runnersElastically scale an ephemeral runner pool from zero to thousands on bursty, spiky load; a fresh runner per job is the default.[2]
Isolation / securityTop priority. Build code is untrusted and arbitrary; one tenant's job must never read another's secrets, cache, or host.[3]
ReliabilityAt-least-once job execution; a crashed runner reruns its job. Build results must be durable and reproducible.
FairnessNo tenant or one huge repo monopolizes the pool; small jobs aren't starved behind a 2-hour build. Bounded queue wait.

The defining tension: isolation vs. speed. Perfect isolation says "throw away the whole machine after each job"; speed says "keep the warm cache and reuse it." Most of the design below is negotiating that line.

Capacity Estimation

Estimate only the numbers that change the design.

QuantityEstimateDesign implication
Pipeline triggers~50k repos pushing ~10×/day → ~500k pipelines/day, ~6/sec avg but ~10× bursty peaks (9am, pre-deploy)6/sec is trivial to ingest; the spikiness is the whole problem — the runner pool must autoscale, not be sized for average.
Jobs per pipeline~10 jobs/pipeline → ~5M job-runs/day → ~60 job-starts/sec avg, ~600/sec peakThe scheduler dispatches hundreds of jobs/sec onto runners — this is the job-scheduler core, not a webhook problem.

The math that matters: ingestion QPS is a rounding error; the cost centers are compute (thousands of concurrent runner VMs at peak) and blob storage (PB-scale). That's where the design earns its keep — autoscaling and offloading bytes.

Interviewer pushback

“If ingest is only a few per second, what's hard?”

Staff answer: The execution fleet: thousands of concurrent VMs with bursty demand at 9am and before releases. Scaling runners from near-zero fast enough is the problem.

Say to move on → “Only ~6 triggers/s on average, but ~10× bursts and thousands of concurrent jobs. Let me define entities.”

Phase 3 · 10–17 minAPI & data modelLock the contract and the storage shape before drawing boxes.

Core Entities & API

Pipeline — a run triggered by one commit, holding a DAG of stages.[2] Job — one unit of work (build, test-shard) that runs on a single runner.[2] Runner — an ephemeral executor (container/VM) that claims and runs one job.[2] Artifact — a stored output blob with a lifetime.

EndpointPurpose
POST /v1/webhooks/{provider}Ingest a signed push/PR event; verify HMAC signature, enqueue a pipeline trigger.[1]
GET /v1/pipelines/{id}Fetch a pipeline's DAG, per-job status, and timing.
GET /v1/jobs/{id}/logsStream or page a job's log output from blob storage.
POST /v1/jobs/{id}/claimA runner leases the next eligible job (long-poll); returns its spec + scoped token.
POST /v1/jobs/{id}/statusRunner reports running/success/failure + uploads artifact references.
GET /v1/artifacts/{id}Redirect to a pre-signed blob URL for download.[4]

The repo and tenant are derived from the verified webhook payload and the runner's scoped token — never trusted from the caller's body.

Data Model

Orchestration state is small, transactional and relational; bytes are huge and append-only. The DAG is stored as jobs plus dependency edges, and each job keeps a remaining_deps counter so fan-in is a decrement-to-zero, and a lease (runner id + expiry) so a crashed runner's job is re-dispatched. Caches carry a trust scope so untrusted fork builds can read but never write caches consumed by trusted builds.

“Why is Runner ephemeral?”

Staff answer: A fresh VM per job means no state leaks between tenants or jobs and no cleanup bugs; it's the default isolation boundary.

Phase 4 · 17–27 minHigh-level designA simple end-to-end design that satisfies every functional requirement.

Data Flow

CI/CD is a data-processing pipeline, so trace one push end-to-end:

  1. Trigger: git host POSTs a signed webhook on push/PR. The ingestion service verifies the signature and writes a trigger to a durable queue (see Lesson 07) — return 200 fast, work async.[1]
  2. Plan: a worker reads the trigger, fetches the pipeline config, and materializes the stage DAG of jobs with their dependencies.[2]
  3. Schedule: jobs whose dependencies are satisfied become eligible and land on a dispatch queue, tagged by required labels (OS, GPU, tenant).
  4. Execute: an ephemeral runner claims a job, restores caches, runs the user's steps in a sandbox, streams logs, uploads artifacts.[2]
  5. Aggregate: on each job's ACK the scheduler re-evaluates the DAG, unlocking downstream jobs (fan-out/fan-in), until a final deploy job runs and status is reported to the commit.

Webhooks become durable triggers; the planner materializes the job DAG; the scheduler dispatches eligible jobs to label-matched runners under leases. Each job runs in a fresh microVM that streams logs and uploads artifacts to object storage, while the autoscaler sizes the runner pool from queue depth.

High-Level Design

Seven components, split cleanly into ingest, plan/schedule, and execute:

ComponentRole
Webhook ingestionVerifies HMAC signatures, dedupes, writes triggers to a queue. Stateless, autoscaled behind a load balancer.[1]
Trigger queueDurable buffer (Kafka/SQS) absorbing bursts so ingestion never blocks on planning.
Pipeline plannerExpands config into a DAG of jobs, persists it, marks dependency-free jobs eligible.[2]
Scheduler / dispatcherMatches eligible jobs to runners by label; leases with visibility timeout (the job-scheduler core).
Runner pool + autoscalerEphemeral containers/VMs that claim one job each; autoscaler sizes the fleet to queue depth.[2]

Flow: webhook → verify → trigger queue → planner builds DAG → scheduler dispatches eligible jobs onto labeled runners → runner sandboxes the build, streams logs to blob, uploads artifacts, ACKs → scheduler unlocks downstream jobs → deploy → report status. Keeping orchestration metadata (small, transactional) separate from artifacts/logs (huge, append-only) is the load-bearing split.

★ Staff-level signal Don't re-derive a job scheduler from scratch — name it: "the dispatch tier is the distributed scheduler from Lesson 34 with label-matching." Then spend your depth budget on the two things unique to CI/CD: isolating untrusted build code and a DAG executor with fan-out/fan-in. Treating isolation as the #1 NFR (not an afterthought) and reaching for ephemeral runners by default is the move that reads as staff.

Interviewer pushback

“Why a trigger queue before the scheduler?”

Staff answer: Webhook bursts are buffered durably and deduplicated, so a flood of pushes can't overload scheduling or lose triggers.

Phase 5 · 27–47 minDeep dives & tradeoffsGo deep where the system breaks; compare alternatives and justify the pick.

Deep Dives

1 · Scheduling jobs onto a pool of ephemeral runners + autoscaling

The dispatch tier is a distributed job scheduler with one twist: jobs carry labels (linux/x64, gpu, tenant-A) and must land on a matching runner. Runners are ephemeral — spun up, given exactly one job, then destroyed[2] — which is what makes isolation tractable (deep dive 2). Runners pull work via long-poll/lease+ACK so a crashed runner's job is re-dispatched (the same semantics as Lesson 34).

Autoscaling signalBehaviorTradeoff
Scale on queue depthAdd runners when eligible-job backlog grows; scale to zero when idle.Directly tracks demand; but cold-start latency (boot a VM) adds seconds to the first job.
Warm pool / pre-provisionKeep a small buffer of idle runners ready to claim instantly.Kills cold-start for the common case; costs money to hold idle capacity.
Predictive pre-warmScale up ahead of known peaks (9am, release windows) from history.Smooths bursts; wrong predictions waste spend or under-provision.
Pick & justify: Scale-to-zero on queue depth + a small warm pool for the hot labels. This gives elastic cost (idle tenants pay nothing) while hiding boot latency for typical jobs. Enforce fairness with per-tenant concurrency caps and weighted-fair dispatch so one repo's 500-shard test matrix can't starve everyone else — fairness lives in the scheduler, not the pool.

2 · Isolating & sandboxing untrusted build code — the security core

This is the deep dive that matters most: build steps run arbitrary attacker-controlled code (anyone can open a PR). A weak sandbox leaks secrets, poisons caches, or escalates to the host and pivots into your network.[3] Defense is layered.

Isolation levelBoundaryTradeoff
Shared host, OS usersJust process/user separation on one box.Fast and cheap, but a shared kernel + escapes make it unsafe for untrusted multi-tenant code.
ContainersNamespaces + cgroups isolate filesystem, network, resources.Lightweight and fast; shared kernel means a kernel exploit can still escape — not enough alone.
MicroVMs (Firecracker)Per-job lightweight VM with its own kernel.[5]Near-container speed with a true hardware/VM boundary; more infra complexity to operate.
Full VM per jobHeavyweight hypervisor isolation, destroyed after.Strongest blast-radius control; slowest to boot and most expensive per job.
Pick & justify: One ephemeral microVM (or fresh VM) per job, destroyed on completion, is the safe default for untrusted code — a fresh kernel boundary plus zero reuse means no cross-job leakage.[5] Layer on:
  • Least-privilege scoped tokens — the runner gets a short-lived token good only for this job's repo/artifacts, never org-wide secrets.
  • Egress control — restrict outbound network to prevent exfiltration and SSRF into internal services.
  • No reuse — never run a fork-PR job on a runner that later touches privileged caches or signing keys.
Ephemeral-by-default makes "throw the machine away" the cheap path, which is exactly why deep dive 1 chose ephemeral runners.

3 · The pipeline DAG — stages, dependencies, fan-out / fan-in

A pipeline isn't a list; it's a directed acyclic graph of jobs.[2] build fans out to test-shard-1..N running in parallel (fan-out); deploy waits for all shards to pass before it runs (fan-in). The scheduler is a DAG evaluator: a job is eligible only when every upstream dependency has succeeded.

How the executor drives the graph:
  • Persist the DAG with each edge as a dependency; track per-job state (pending → eligible → running → done/failed).
  • On each job ACK, re-evaluate downstream jobs: any whose dependencies are now all done become eligible and are dispatched (fan-out is just many eligible jobs at once).
  • Fan-in is a join node that stays pending until its last parent finishes — a counter of remaining upstreams hitting zero.
  • Fail-fast vs. continue: a failed required job marks the pipeline failed and cancels in-flight siblings; continue-on-error jobs don't.

Pass shard outputs forward as artifacts (deep dive 4), not shared mutable disk — that keeps parallel jobs independent and reschedulable. The DAG state lives in the metadata DB so an evaluator crash resumes from the last persisted state, not from scratch.

4 · Artifact & log storage + dependency caching

Two byte-heavy concerns, both offloaded to blob storage (see Lesson 45) — never the metadata DB.[4]

DataStorage approachWhy
ArtifactsObject store, content-addressed by hash; metadata DB holds only the pointer + TTL.[4]PB-scale, immutable, cheap; dedup identical builds; lifecycle policy expires old runs.
LogsStream live over websockets to viewers, then flush to blob in chunks for replay.[1]Append-only and huge; live tail needs low latency, history needs cheap durable storage.
Dependency cacheKeyed by a hash of the lockfile (package-lock, go.sum); restored before the build, saved after.[6]Turns a 20-min cold build into a 2-min warm one — the single biggest speed lever.
The caching subtlety (where it gets staff-level): caches collide with isolation. A cache writable by an untrusted job is a cache-poisoning vector — a malicious PR plants a backdoored dependency that a later trusted build consumes.[6] Mitigate by making caches read-only for untrusted (fork) PRs, scoping cache keys per-branch/per-tenant, and verifying integrity by content hash. Speed is great, but it must not punch a hole in deep dive 2.

State the breadth/depth ratio aloud: you went deep on isolation, scheduling/autoscaling, the DAG, and caching — the parts that break (security) or dominate cost/latency — and kept ingestion and the metadata schema shallow because they're boring and well-understood.

Privacy

CI handles customer source code, secrets, and logs that often leak personal or production data. Controls: automatic masking of registered secrets in logs; log and artifact retention limits with tenant-configurable deletion; tenant-isolated storage prefixes and encryption keys; ephemeral runners wipe all workspace data. Test data: guidance and scanning to keep production PII out of fixtures and logs. Residency: regional runner pools and storage for enterprises. Staff access to customer logs is exceptional and audited.

Interviewer pushback

“How do you protect secrets from pull requests by forks?”

Staff answer: Don't expose secrets to fork PR workflows by default, use short-lived OIDC tokens scoped to repo, branch and environment, require approvals for protected environments, and mask secrets in logs.

Assumptions: ~5M jobs/day averaging 10 minutes on 4 vCPU (~100M vCPU-hours/month), artifacts and logs retained 90 days (~20 PB), dependency downloads mostly served from pull-through caches, list prices from the course price sheet (spot capacity could cut compute ~60%).

Wrap-up · 58–60 minClose strongRecap decisions and tradeoffs in 60 seconds; name what you would do next.

Closing Summary (60 seconds)

A CI/CD system turns push events into DAGs of isolated jobs. Webhooks are verified, deduplicated and queued; a planner expands the pipeline into a DAG, and a scheduler dispatches ready jobs fairly across tenants. Each job runs on an ephemeral microVM runner claimed from a warm pool that autoscales on queue depth and is destroyed afterward. Artifacts and logs go to object storage, and dependency caches cut build time. Secrets use short-lived OIDC credentials. At 10× we add hosts, regions and scheduler shards.

Check yourself — retrieval practice

Answer from memory before scrolling back up.

1. Why are ephemeral, single-job runners the default for CI builds?

Untrusted code runs each job; destroying the box afterward guarantees no secret, cache, or state survives to the next tenant.

2. What is the single most important NFR for a CI/CD system?

Anyone can open a PR running arbitrary code; a weak sandbox leaks secrets or escapes to the host, so isolation leads.

3. In the pipeline DAG, when does a fan-in deploy job become eligible?

Fan-in is a join: the deploy job waits until its remaining-parents counter hits zero, i.e. all shards succeeded.

4. Why must dependency caches be read-only for untrusted fork PRs?

A writable shared cache is a poisoning vector: a fork PR could plant a backdoored dependency a trusted build then consumes.
