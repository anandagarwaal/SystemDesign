Design Hotel Booking (Airbnb / Booking.com)

A geo-and-date search problem fused to a reservation core that must never let two guests book the same room for the same night.

Why this lesson, for your mission: Hotel booking reads like a CRUD listing site until you notice that "is this room free for these dates?" is a range-overlap consistency question and that two guests can race for the last room on the same night. The L6/L7 signal is splitting the system into an availability-first search/browse path and a consistency-first reservation path, then picking the simplest correct concurrency mechanism for the latter. That same instinct powers Ticketmaster and online auctions — reuse it, don't reinvent it.

Functional Requirements

Lock scope to what a traveler actually does. Push reviews, messaging, host onboarding, and payouts out of scope and say so.

#Users should be able to…Note
1Search listings by location and date rangeRead path — highest volume; geo + availability filter
2View a listing and its availability calendarRead path — must reflect held/booked nights
3Book / reserve a listing for chosen datesWrite path — the hard part; no double-booking
4Manage their bookings (view, cancel)Read + light write; frees inventory on cancel

Non-Functional Requirements

One sentence carries the design: prioritize consistency for reservations — no double-booking a room-night — but prioritize availability and low latency for search and browse. Different NFRs for different paths is the framing move, exactly as in Ticketmaster.[1]

NFRTargetDrives
Strong consistency on bookingA room-night is sold to exactly one guest — everThe reservation/no-double-book mechanism (Deep Dive 2). The crux.
High availability for searchSearch & listing pages stay up under loadCaching, read replicas, a dedicated search store
Low search latency< 500ms for geo + date queriesGeo index + availability filtering (Deep Dive 1)
Read-path freshnessSearch may lag reality by secondsEventual consistency on the index is acceptable
★ Staff-level signal Say out loud that you are running two consistency regimes in one system: AP (available, eventually consistent) for search and browse, CP (consistent, may reject) for reservations. A guest seeing a just-booked room in results for a few seconds is fine; two guests confirming the same room-night is never fine. Naming that asymmetry — and refusing to let reservation machinery slow the read path — is the highest-leverage sentence in this interview.

Capacity Estimation

Only estimate numbers that change a decision. Two facts matter; all figures here are my own back-of-envelope estimates.

QuantityEstimateDesign implication
Read : write ratio~1000 : 1 — searches and listing views dwarf bookingsOptimize the read path independently; cache and index aggressively. The write path can be slower but must be correct.
Listings & availability rows~10M listings × ~365 nights ≈ a few billion room-night rowsAvailability is the big table, but it is keyed lookups, not the bottleneck. The challenge is concurrent contention on a few hot room-nights, not raw storage.

The contended set is tiny: at any instant only a handful of guests race for the same listing's same dates. As with Ticketmaster, the problem is never storage — it is concurrent contention on a small, hot set of rows.

Core Entities & API

Entities: Listing (host id, geo lat/lng, type, amenities, nightly base price), Availability (listing id, date, status: available | held | booked, price for that night), and Reservation (guest id, listing id, check-in, check-out, total, status: pending | confirmed | cancelled).[1] The status on Availability is where the consistency story lives.

User identity comes from the auth token, never the request body.

EndpointPurpose
GET /v1/listings/search?lat=&lng=&radius=&checkIn=&checkOut=&page=Search by geo + date range — served by the search store.
GET /v1/listings/{id}?checkIn=&checkOut=Listing detail + availability calendar + price.
POST /v1/reservationsReserve: body {listingId, checkIn, checkOut} → places a hold, returns reservationId.
POST /v1/reservations/{id}/confirmConfirm: finalizes after payment succeeds; idempotent.
GET /v1/reservationsList the caller's bookings (manage view).
DELETE /v1/reservations/{id}Cancel; releases the held/booked room-nights.

Splitting reserve from confirm is intentional: the guest gets a window to enter payment while the room-nights are held. That window is the entire reason the double-booking problem exists — identical to the reserve→pay→confirm split in Ticketmaster.

High-Level Design

An API Gateway (auth, routing, rate-limit) fans out to stateless services. Search and reservation share no critical-path infrastructure.

ComponentRoleData store
Search ServiceServes /listings/search (geo + date filter)Elasticsearch / geo index, synced from listings DB via CDC
Listing ServiceServes /listings/{id} + availability calendarPostgres (read replicas) + Redis cache
Reservation ServiceReserve / confirm / cancel; the only writer of availability statusPostgres (primary) + Redis (holds)
PaymentCharges card; signals successExternal (e.g. Stripe) via webhook

Flow. search → Search Service → geo/date index. GET listing → Listing Service → cache/replica. POST reservation → Reservation Service holds the requested room-nights and writes a Reservation(pending), returns reservationId; client goes to payment; on charge success the Payment webhook triggers confirm, which atomically flips the Availability rows → booked and the Reservation → confirmed. The listings DB is shared, but only the Reservation Service writes availability status — read services touch replicas and caches.

Deep Dive 1 — Availability search by date range + geo

A search is two filters ANDed together: "listings near (lat,lng) within radius" and "every night in [checkIn, checkOut) is available." Each needs a different index.

The geo filter

OptionVerdict
Lat/lng B-tree rangeWeak — a bounding-box on two independent columns can't prune well; degrades to scans.[2]
Geohash prefix indexGood — encode location to a string; a prefix match is a cheap range, easy to shard.[2]
Quadtree / geo index (recommended)Best — Elasticsearch geo_point or PostGIS answers "within radius" directly and ranks by distance.[2]

This is the same geo machinery as Yelp — reuse it. The new wrinkle is the date filter layered on top.

The date-range filter

Modeling availability per night (one row per listing per date) turns "free for [checkIn, checkOut)?" into "are all those date rows available?" — a clean keyed lookup, and the model that makes the reservation transaction simple.[1] The alternative — storing reservations as intervals and testing NOT (existing.end <= new.start OR existing.start >= new.end) — is compact but turns every check into a range-overlap scan that is awkward to index and to lock.

Why search availability is only "best effort". You cannot cheaply keep the full availability of every listing in the search index fresh to the millisecond — bookings change it constantly.
  • Index a coarse signal (e.g. has-any-availability, or a bucketed calendar) so search prunes most non-matches fast.
  • Re-check exact availability on the listing-detail read and again, authoritatively, inside the reservation transaction.
  • Accept that a result may occasionally be stale-booked — the reservation path is the source of truth, so the worst case is a "just got taken" message, never a double-book.

Deep Dive 2 — The reservation / no-double-booking problem

The hazard: two guests both see the last room free for the same nights, both reach payment, and both confirm.[1] You need a hold on the room-nights during the reserve→pay window that auto-releases if payment never lands. This is the same four-tier ladder as Ticketmaster and the bid-contention problem in online auctions; know it cold.

MechanismHowWhy it fails / wins
DB row lock (SELECT … FOR UPDATE)Lock the date rows for the whole checkoutBad. A minutes-long open transaction strains the DB and invites lock contention and deadlocks. A lock is not a business-duration tool.
Status column + cron sweeperSet rows → held with a timestamp; a job resets expired holds to availableOK. No long locks, but a held room stays stuck until the next sweep; correctness depends on the job running.
Status + expiry, checked inline (OCC)One short transaction: claim the nights iff each is available OR (held AND expired), set held + now+10minGreat. An expired hold is implicitly free the instant the next guest's transaction reads it; the sweep becomes optional cleanup.
Redis lock + TTLSET listing:{id}:{date} {guestId} NX EX 600 per night (one Lua script, all-or-nothing); release on confirmGreat, and the staff pick. Keeps the hot, short-lived hold out of the durable DB; the TTL is the expiry.
The staff pick — and why. Redis lock with TTL on each room-night, acquired atomically via a Lua script so a multi-night stay is all-or-nothing.
  • The hold is ephemeral, so store it ephemerally. A 10-minute hold is not durable business data — Redis keeps the churn off the primary DB.
  • The TTL is the expiry for free — no sweeper, no cron, no stuck nights.
  • Belt and suspenders: the final confirm still runs an OCC check inside the DB transaction, so even a total Redis outage degrades UX (more "just got taken") but cannot double-book. Redis is an optimization on top of a DB that is itself correct.
★ Staff-level signal Don't invent this from scratch — say "this is the same hold-with-TTL pattern as Ticketmaster and auctions, applied per room-night." Recognizing that double-booking, seat contention, and bid contention are one problem in three costumes, and reaching straight for the simplest correct member of the ladder, is the senior-to-staff jump. Then state the one local twist: the unit of contention is a set of nights, so the hold must be atomic across the range.

Deep Dive 3 — Pricing & calendar data model

Nightly price is not a single field on the listing — it varies by date (weekends, seasons, demand) and so does availability. Model both on the same per-night row.

ApproachVerdict
Single price on the listingToo coarse — can't express weekend or seasonal rates; wrong totals.
Price-rule engine evaluated at read timeFlexible but pushes per-night CPU into every search; cache the rendered calendar.
Per-night Availability row {listingId, date, status, price} (recommended)One row per listing per date: availability and price co-located, so booking and quoting read the same source. Materialize from rules nightly.

With this model, a price quote for a stay is just SUM(price) over the date rows in [checkIn, checkOut) — and the reservation transaction reads and flips those exact rows, so the price the guest saw and the inventory they hold come from one place. Pin the quoted total onto the Reservation at reserve time so a price change mid-checkout can't surprise the guest. Cancellations simply flip the rows back to available (see the manage-bookings flow).

Deep Dive 4 — Search ranking & caching

Search is the AP path; scale it the boring, reliable way and keep it entirely off the reservation primary.

  • Dedicated search store. Elasticsearch (or PostGIS) holds listing + geo + coarse availability, synced from Postgres via CDC so the index stays current; accept eventual consistency.[2]
  • Ranking. Blend geo distance, price, rating, and booking-likelihood into a score; the date filter is a hard gate, ranking decides order. Keep the first pass cheap and re-rank the top-N.
  • Cache popular queries. Location + date combinations cluster hard (cities, weekends, holidays). Cache result pages in Redis/CDN keyed by {geohash, checkIn, checkOut, page} with short TTLs; non-personalized pages can sit at the edge.
  • Stateless Search Service behind a load balancer — scale horizontally.

The point of this dive is restraint: the read path needs no exotic machinery. All the cleverness belongs in the reservation core — spending equal time on both signals poor prioritization.

Check yourself — retrieval practice

Answer from memory before scrolling back up.

1. Why model availability as one row per listing per night?

Per-night rows make "free for these dates?" a lookup over those rows, and make the reservation transaction simple to lock and flip.

2. What is the staff pick for preventing a double-booking?

Ephemeral hold in Redis (TTL = expiry), backstopped by an OCC check in the confirm transaction so even a Redis outage can't double-book.

3. Why is search availability treated as only best-effort?

Keeping every listing's calendar fresh in the index is too costly; search prunes, the reservation transaction is authoritative, so worst case is a "just taken" message.

4. Why pin the quoted total onto the reservation at reserve time?

Availability and price share the per-night row; freezing the total onto the Reservation makes the charge match what the guest saw.
