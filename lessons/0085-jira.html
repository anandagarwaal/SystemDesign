Design a Project Management Tool (Jira)

A multi-tenant issue tracker that lives or dies on three things: a schema flexible enough for arbitrary custom fields, a search engine that can answer JQL, and a workflow engine that's configurable rather than hard-coded.

Why this lesson, for your mission: Jira looks like "CRUD with a status dropdown." That framing is the trap. The staff move is to see that every hard part here is about configurability: customers define their own fields, their own workflows, their own queries — so the design problem is building an engine, not an app. A senior models a fixed Issue table; a staff candidate recognizes the flexible-schema, search-index, and state-machine sub-problems up front, sizes the read-heavy query load, and spends the interview on those three deep dives instead of the REST endpoints.

Functional Requirements

Scope ruthlessly, then say out loud what you're deferring. The core loop of every tracker is: create an issue, organize it on a board, move it through a workflow, find it again later.

#Users should be able to…
1CRUD issues/tickets with standard and tenant-defined custom fields.
2Organize issues on boards/sprints (backlog, columns, drag to reorder).
3Transition issues through a configurable workflow (e.g. To Do → In Progress → Done).
4Search and filter across all fields with a query language (JQL).
5Comment, and see a full activity/audit feed per issue.

Out of scope (state it): billing, time-tracking/reporting math, automation rules, marketplace plugins, rich-text editor internals, and dashboard chart rendering (we'll cover the data that backs dashboards, not the gadgets).

Non-Functional Requirements

This is where you commit to the priorities that shape every later decision. Jira is a read-heavy product dominated by complex queries, but unlike a social feed it needs strong consistency on writes — an engineer must never see their own status change roll back.

PropertyTarget / priority
Read/write ratioRead-heavy (~10:1) and, more importantly, query-heavy — boards/filters re-run rich queries constantly.
ConsistencyRead-your-writes / strong for issue mutations and transitions; search may lag seconds.
Multi-tenancyHard isolation per organization — no tenant can ever see another's data.[3]
AvailabilityHighly available (~99.9%+); a transient outage stops work for whole teams.
ScaleMillions of tenants, each small; a few very large tenants with 10M+ issues skew the design.

Capacity Estimation

Only compute numbers that change a decision. Two matter here: how query-heavy the read path is (does search need its own store?), and how skewed tenant sizes are (does one table fit everyone?).

How heavy is the query path?

  • Say ~10M daily active users, each loading boards/filters ~50×/day → ~500M reads/day ≈ 6K reads/sec average, multiples higher at peak — and most are filtered queries, not point lookups.
  • Implication: a board is a saved filter re-executed on every load. Running these as WHERE scans with many predicates over the primary DB won't hold up — search belongs in a dedicated index.[2]

How skewed are tenant sizes?

  • Most tenants have thousands of issues; a handful have 10M+. Total corpus across all tenants is easily billions of issues × a few KB ≈ tens of TB.
  • Implication: the long tail of tiny tenants packs cheaply into shared tables, but giant tenants need their queries isolated so a noisy neighbor can't starve everyone — tenancy strategy is a design-changing decision, not an afterthought.[3]

Core Entities & API

The modeling tension is right here: an Issue has a few fixed columns but an open-ended set of custom fields whose definitions belong to the tenant's Project. Get this boundary right and the rest follows.

EntityShape
Issueid, tenantId, projectId, type, status, assigneeId, reporterId, plus a bag of custom fields.
FieldDefinitionid, tenantId, projectId, name, dataType (text/number/date/select) — the tenant's schema.
Workflowid, states[], transitions[] (from→to + guards) — a per-project state machine.
Activityid, issueId, actorId, kind (comment/transition/edit), payload, createdAt.

Derive the acting user and tenant from the auth token, never from the request body.[3]

EndpointPurpose
POST /v1/issuesCreate an issue. Body: { projectId, type, fields:{…} }.
PATCH /v1/issues/:idEdit fields; writes an entry to the activity log.
POST /v1/issues/:id/transitionsMove status. Body: { to }; validated by the workflow engine.
GET /v1/search?jql=Run a JQL filter; returns { items, nextCursor }.
POST /v1/issues/:id/commentsComment. Body: { body }; appends to the activity feed.
GET /v1/boards/:idRender a board — i.e. run its saved filter and group by column.

Note GET /search returns a cursor, not an offset — result sets are large and shift as people edit issues, so offset paging causes duplicates and skips.

High-Level Design

Keep the HLD boringly simple; the cleverness belongs in the deep dives. Stateless services sit behind a gateway that resolves tenant + permissions, a primary store holds the source of truth, and a search index plus an event bus hang off the side.

ComponentResponsibility & store
API GatewayAuthN/Z, resolves tenantId + project role from the token before any handler runs.[3]
Issue ServiceCRUD + field validation against FieldDefinition. Writes to the Issue Store (relational, source of truth).
Workflow ServiceValidates and applies transitions against the project's state machine; rejects illegal moves.[4]
Search Service + indexElasticsearch holding denormalized issue docs; serves JQL/board queries.[2]
Event bus + CDCEvery issue write emits a change event; consumers update the index and activity feed.
Activity/Notification workerConsumes events to build per-issue feeds and fan out notifications.

Write path: PATCH /issues/:id → gateway resolves tenant+role → Issue Service validates fields → commits to Issue Store (strongly consistent) → emits a change event. Read path: GET /search?jql= → Search Service translates JQL → queries the index → returns denormalized hits. Point reads of a single issue go straight to the Issue Store for read-your-writes correctness.

Deep Dive 1 — Flexible schema for custom fields

The defining feature of Jira is that every tenant invents its own fields. You cannot ship a fixed table — but you also can't let query performance collapse. Three models, each a real-world choice with sharp tradeoffs.

ModelHow it worksTradeoff
EAV (entity-attribute-value)One skinny row per (issueId, fieldId, value).Infinitely flexible; reading one issue needs many joins, queries get ugly fast.[1]
JSON columnCustom fields live in a jsonb blob on the issue row.One-row reads, GIN-indexable; weaker per-field typing and constraints.[1]
Document storeWhole issue is a schemaless document (e.g. Mongo).Natural fit for variable shape; gives up relational joins/transactions.

The pragmatic pick for an interview: a relational core with a typed jsonb custom-fields column, validated on write against the tenant's FieldDefinition. You keep fixed columns (status, assignee) indexed and transactional, while custom fields stay flexible and still index-able via GIN. Crucially, you don't lean on the primary DB for the hard filtered queries at all — those go to the search index (DD2), which sidesteps EAV's join pain entirely.[1][2]

★ Staff-level signal The senior reaches for EAV because it's the textbook "dynamic attributes" answer. The staff candidate names EAV's failure mode out loud — N joins to reconstruct one issue, and a query planner that can't optimize cross-attribute filters — then makes the decisive move: separate storage from query. Use a simple, write-friendly model in the source of truth (JSON column) and push all flexible querying to a denormalized search index. They explicitly refuse to make one store do both jobs, and they validate field types on write so the index stays clean.

Deep Dive 2 — Powerful filtered search (JQL)

JQL is the product. project = ENG AND status IN (Open, "In Progress") AND assignee = currentUser() ORDER BY priority is not a query you serve from a transactional store with arbitrary custom-field predicates — that's a full scan with no useful index.[2] You need a dedicated search index holding denormalized issue documents: each doc carries the issue's fixed fields, all custom field values, project, and tenant flattened into one record.

Keep the index in sync with the Issue Store via CDC / change events, exactly the pattern from Lesson 25 · Post Search: a write commits to the source of truth, emits an event, and a consumer upserts the denormalized doc into Elasticsearch. Search tolerates seconds of lag, so this async pipeline is the right call — point reads stay strongly consistent on the primary, while filtered queries hit the index.

ConcernChoice & reason
Query engineElasticsearch — inverted index + structured filters handle JQL's mix of text and field predicates.[2]
SyncCDC/event-driven upserts. Writes never block on indexing; eventual within seconds.
Tenant isolationFilter every query by tenantId; large tenants get dedicated indices/shards.[3]
JQL → queryParse JQL to an AST, compile to an ES query DSL with a mandatory tenant filter injected.

Why denormalize? The index stores a flattened issue — no joins at query time. The cost is keeping it in sync, which the CDC pipeline owns. This is the read-side mirror of DD1: the source of truth optimizes for correct, transactional writes; the index optimizes for fast, flexible reads. Two stores, two jobs.

Deep Dive 3 — The configurable workflow / state-machine engine

The amateur version hard-codes if status == "todo" then allow "in_progress". That can't survive a product where every project defines its own states and transitions. You need a data-driven state machine: the workflow is a row in a table, not code.[4]

Model a workflow as a directed graph: states are nodes, transitions are edges with optional guards (who may move it, required fields, conditions). Applying a transition becomes: look up the issue's current state, check that an edge to the target exists, evaluate the guards, then commit the new state and append an activity entry — all in one transaction so the audit log can never disagree with the issue.

PieceRole
StateA node (e.g. To Do, In Review, Done) scoped to a project.
TransitionA directed edge from → to with guards (role, condition, validators).
GuardA predicate evaluated before the move — e.g. "only assignee", "resolution set".
EngineGeneric executor: validate edge + guards, commit state, log activity atomically.[4]
★ Staff-level signal The staff candidate frames this as configuration over code: the same engine runs every tenant's workflow because the workflow is data. They make the transition atomic and consistent — state change + activity entry commit together, satisfying the strong-consistency NFR — and they call out that validation is server-side only (the client greys out illegal buttons, but the engine is the real gate). They resist scope creep (no Turing-complete rule language) and note that storing transitions as a graph makes the whole workflow renderable and auditable for free.

Deep Dive 4 — Activity feed, notifications & multi-tenant permissions

Activity feed: derived from the same event stream

Every mutation — edit, comment, transition — already emits a change event for the search index. Reuse it: an activity worker consumes that stream and appends to a per-issue, append-only feed, and fans out notifications to watchers/assignees. Because it replays events, it must be idempotent so a redelivered event doesn't double-post. This is the same event-driven fan-out as the Q&A/forum design: one write → one event → many consumers.

Multi-tenancy & permissions: isolation is the hard NFR

The non-negotiable rule: no tenant ever sees another's data. Resolve tenantId from the auth token at the gateway and inject it into every query — primary store and search index alike.[3] Within a tenant, permissions are project-role based: a user has a role (admin/member/viewer) per project, and roles map to actions (transition, comment, admin). The full authorization model — token validation, role resolution, per-resource checks — is its own subsystem; see Lesson 68 · Auth Service.

Tenancy modelHow it worksTradeoff
Shared schema + tenantIdAll tenants in one set of tables, filtered by column.Cheapest, packs the long tail; one bad query risks cross-tenant leaks if a filter is forgotten.[3]
Schema/DB per tenantEach big tenant gets isolated storage.Strong isolation + noisy-neighbor protection; far more operational overhead.

The pragmatic answer: shared schema with a mandatory tenant filter for the millions of small tenants, and dedicated stores/indices for the handful of giant ones — a hybrid that matches the skew you found in capacity estimation. Enforce the tenant filter in a shared data-access layer so it's impossible for a single handler to forget it.[3]

Check yourself — retrieval practice

Answer from memory before scrolling back up.

1. Why prefer a JSON column over EAV for an issue's custom fields?

EAV needs N joins to rebuild one issue; a JSON column keeps the read a single row and is still GIN-indexable. Hard filtering goes to the search index.

2. Where should complex JQL filter queries actually be served from?

Arbitrary custom-field filters are a scan on the primary DB. Flatten issues into denormalized docs in Elasticsearch, synced asynchronously by change events.

3. What makes a configurable workflow engine different from hard-coded status checks?

The workflow is data — states are nodes, transitions are guarded edges — so one generic engine runs every tenant's distinct state machine, validated server-side.

4. How is cross-tenant data isolation most reliably enforced in a shared schema?

Resolve tenantId from the auth token at the gateway and inject it in a shared data-access layer so no single handler can ever forget the filter.
