Design a Webhook Delivery System

Customers register URLs; when events happen, you reliably POST the payload to them — at scale, without one slow customer poisoning the rest.

Why this lesson, for your mission: A webhook system is the canonical test of reliable delivery to endpoints you do not control. Seniors say "POST the event when it fires." Staff candidates make delivery async behind a durable queue, isolate slow/failing customers so they can't head-of-line block everyone, sign payloads and block SSRF so a registered URL can't be turned into an attack, and lean on at-least-once + idempotency. Those four moves are the interview.

Functional Requirements

Scope to what a webhook product must do; everything else is out of scope.

The user should be able to…Detail
Register & manage endpointsCreate, update, disable, and delete webhook endpoints (a URL + which event types it subscribes to).
Receive events on triggerWhen a subscribed event occurs internally, the system POSTs the event payload to every matching endpoint.
Get retries on failureIf an endpoint is down or returns a non-2xx, the system retries with backoff until it succeeds or is exhausted.
Inspect delivery logsView each attempt: status code, response, timestamps, attempt count — and replay a failed delivery.

Out of scope (say it aloud): the business logic that produces events, a customer-facing dashboard's UI, and guaranteed ordering across different endpoints. We deliver events; the customer's receiver does the work.

Non-Functional Requirements

PropertyTarget / priority
At-least-once deliveryEvery event reaches a healthy endpoint at least once; we never silently drop. Duplicates are possible, so consumers must dedupe (idempotency).[2]
Reliability & durabilityAn accepted event survives crashes — it lives in a durable queue/store, never only in memory, and is retried across worker failures.
Isolation between customersOne slow or failing endpoint must not delay deliveries to others — no head-of-line blocking across tenants.
SecurityPayloads are signed so receivers can verify origin; registered URLs cannot be used for SSRF against internal hosts.[3]
ScaleMillions of endpoints; design toward ~10k events/sec fanning out to many deliveries each.

The central tension is reliability vs. isolation: retrying hard for one dead endpoint must not consume the capacity other customers need. The resolution is async delivery with per-endpoint concurrency, developed below.

Capacity Estimation

Estimate only numbers that change the design.

QuantityEstimateDesign implication
Event ingest~10k events/sec at peakTrivial for a queue, but each event may fan out to many endpoints, so deliveries ≫ events.
Fan-out factoravg ~3 endpoints/event → ~30k deliveries/secThe delivery tier, not ingest, is the thing we scale; size the worker pool to deliveries/sec.
Delivery latencycustomer endpoints take 100ms–30sA worker blocked 30s on one slow endpoint is the core risk → concurrency must be per-endpoint, not global.
Delivery logs30k/s × ~1 KB × N retries → TB/monthLogs dwarf the live data; push to cheap append-only storage with TTL, not the hot DB.

The math that matters: 10k events/sec is easy; the killer is that a single slow endpoint at 30s ties up a worker for 30s. Multiply by a customer with thousands of queued events and you've starved everyone else unless deliveries are isolated per endpoint.

Core Entities & API

Endpoint — a customer's registered URL, secret, and subscribed event types. Event — something that happened internally (type + payload + id), produced once. Delivery — one attempt to POST a specific event to a specific endpoint (status, attempt #, response) — the log row.

EndpointPurpose
POST /v1/endpointsRegister a webhook: { url, event_types }. Returns endpointId and a generated signing secret.
PATCH /v1/endpoints/{id}Update URL/subscriptions or disable the endpoint.
DELETE /v1/endpoints/{id}Remove an endpoint (soft-delete so in-flight deliveries settle).
GET /v1/endpoints/{id}/deliveriesList delivery attempts with status, response code, and timestamps.
POST /v1/deliveries/{id}/replayManually re-enqueue a failed (or dead-lettered) delivery.

The owning customer is derived from the auth token, never sent in the body. Event production is internal (a service emits an event); customers don't call us to send — we call them.

Data Flow

A webhook system is a fan-out delivery pipeline, so it's worth tracing one event end to end:

  • 1. Emit — an internal service produces an event with a stable event_id and writes it durably (outbox or event log).
  • 2. Fan-out — a dispatcher looks up endpoints subscribed to that event type and creates one Delivery task per endpoint.
  • 3. Enqueue — each delivery task is pushed onto a durable queue, partitioned by endpoint.
  • 4. Deliver — a worker leases a task, signs and POSTs the payload, and waits for a 2xx.
  • 5. Record / retry — on success it ACKs and writes a log row; on failure it schedules a backoff retry, and after N attempts moves it to the dead-letter queue.

High-Level Design

Six components, with a hard split between accepting an event and delivering it:

ComponentRole
API / registration serviceCRUD on endpoints; validates URLs (incl. SSRF checks) and issues signing secrets.
Event ingest + outboxDurably records produced events so an accepted event is never lost before fan-out.
Dispatcher (fan-out)Matches an event to subscribed endpoints and creates a Delivery task per endpoint.
Delivery queueDurable broker (Kafka/SQS) buffering delivery tasks, partitioned by endpoint.[1]
Delivery workersLease a task, sign + POST to the customer URL, ACK on 2xx, schedule retries / DLQ on failure.
Log store + DLQAppend-only delivery logs (TTL'd) and a dead-letter queue for exhausted deliveries.

Flow: register endpoint → event emitted to durable outbox → dispatcher fans out one delivery per subscribed endpoint into the queue → a worker leases it, signs, POSTs, and on 2xx ACKs + logs success; on failure it re-enqueues with exponential backoff, and after the cap it dead-letters. Splitting ingest from delivery lets the cheap ingest path stay fast while the elastic worker tier absorbs fan-out and slow endpoints.

★ Staff-level signal The interview turns on making delivery async and isolated. Accept the event durably, then deliver from a queue so a customer outage can't block ingest. Partition by endpoint and cap per-endpoint concurrency so one slow tenant can't starve the rest. And treat registered URLs as untrusted input — sign payloads, and validate URLs against an allow-list so a webhook can't become an SSRF into your VPC. Everything below refines those points.

Deep Dives

1 · Reliable async delivery — queue, workers, retries, DLQ

Delivering synchronously inside the event-producing request is the trap: a customer endpoint that takes 30s (or is down) would block the producer and lose the event on crash. Decouple with a durable queue — the same async pattern as Lesson 07 (Messaging & Async) and the lease + ACK execution model from Lesson 34 (Job Scheduler).

Lease + ACK for at-least-once:
  • A worker leases a delivery (it becomes invisible for a visibility timeout); it isn't deleted yet.
  • On a 2xx the worker ACKs → the task is removed and a success log row written.
  • If the worker crashes or the endpoint fails, no ACK → the lease expires and the delivery is retried.[2]
Failure handlingHow
Exponential backoff + jitterRetry after growing delays (e.g. 10s, 1m, 10m, 1h) so a recovering endpoint isn't hammered; jitter avoids synchronized retry storms.
Max attempts → DLQAfter N attempts (often spanning ~24h), move the delivery to a dead-letter queue instead of looping forever and starving healthy work.[1]
Manual replayCustomers (or ops) re-enqueue from the DLQ once their endpoint is fixed, via the replay API.

At-least-once means duplicates happen (a worker can deliver, then crash before ACKing). That's fine here — the cure lives on the consumer side (deep dive 4), not in chasing impossible exactly-once over the network.

2 · Slow / failing endpoints — no head-of-line blocking

The defining webhook problem: customers' endpoints are arbitrarily slow or broken, and you don't control them. A single shared FIFO queue means one customer's 30s endpoint (or thousands of queued retries) blocks everyone behind it. Isolation is the whole game.

TechniqueHow it isolatesTradeoff
Partition by endpointKey the queue by endpointId so each endpoint's backlog is independent.[1]Many partitions/queues to manage; a hot endpoint still needs its own concurrency cap.
Per-endpoint concurrency capBound in-flight deliveries per endpoint; excess waits in that endpoint's lane only.Needs a shared counter / token bucket; mis-tuning throttles healthy endpoints.
Circuit breakingAfter repeated failures, "open" the circuit and stop trying for a cooldown, with periodic probes.Adds per-endpoint state; a flapping endpoint needs half-open probing to recover.
TimeoutsCap each POST (e.g. 5–10s) so no single request can pin a worker indefinitely.Too tight rejects legitimately slow receivers; treat a timeout as a retryable failure.
Pick & justify: Combine all four — partition by endpoint for fairness, a per-endpoint concurrency cap so a noisy tenant uses only its share of workers, a circuit breaker to stop pouring requests into a dead endpoint (its events keep durably queuing for later), and a tight timeout so a hung connection frees the worker. Together they guarantee a customer outage degrades only that customer, not the platform.

3 · Security — signing (HMAC) + SSRF prevention

Two distinct threats. First, the receiver can't trust that a POST is really from us — anyone could forge an event. Second, a registered URL is untrusted input: if a customer points an endpoint at http://169.254.169.254 or an internal host, our delivery worker becomes an SSRF proxy into our own network — a direct violation of secure-coding rules on outbound requests.[3]

Signing payloads (HMAC):
  • Each endpoint has a shared secret. We send HMAC-SHA256(secret, timestamp + "." + body) in a signature header.[4]
  • The receiver recomputes the HMAC with its copy of the secret and compares using a constant-time check.
  • Include a signed timestamp and reject old signatures to prevent replay; rotate secrets without downtime by accepting two valid secrets briefly.
SSRF prevention (allow-list, not block-list):
  • At registration and at delivery time, require https and a public host; reject anything else.
  • Resolve the DNS and validate the resolved IP against private/loopback/link-local ranges (10.x, 127.x, 169.254.x, etc.) — block-listing strings alone is bypassable.[3]
  • Re-check at connection time to defeat DNS rebinding (TOCTOU): pin the validated IP for the request.
  • Disable redirects (or re-validate each hop), and never forward internal headers/credentials to the customer URL.

This is the staff differentiator most candidates miss: a webhook sender makes outbound requests to attacker-chosen URLs by design, so SSRF defense is not optional hardening — it's a core requirement.

4 · Idempotency keys & delivery ordering

Because delivery is at-least-once, the same event can arrive twice. We can't make the network exactly-once, so we make repeats safe and push dedup to the consumer.

ConcernApproach
Duplicate suppressionSend a stable idempotency key (the event_id) in a header; the consumer records processed ids and treats a repeat as a no-op.[2]
Ordering, when neededOrdering across endpoints is meaningless; per-endpoint order can be approximated by keying the queue partition on endpointId and processing a partition serially.
When to drop orderingStrict ordering fights retries (a stuck event blocks newer ones). Prefer including a sequence number/timestamp and letting consumers reorder.
Pick & justify: Default to unordered, at-least-once + idempotency keys — it's the most available and scalable, and matches what Stripe/GitHub-style webhooks actually promise.[2] Offer best-effort per-endpoint ordering (serial partition) only if a customer needs it, and accept that it reduces throughput and complicates retries. Don't promise global ordering — it's the wrong tradeoff at scale.

State the breadth/depth ratio out loud: you went deep on delivery semantics, isolation, and security — the parts that break in production — and kept registration CRUD and storage shallow because that's not where this design fails. Check yourself — retrieval practice

Answer from memory before scrolling back up.

1. Why deliver webhooks asynchronously from a durable queue?

Async decouples ingest from delivery: events survive crashes and one slow endpoint can't stall producers.

2. What stops one failing endpoint from starving every other customer?

Per-endpoint partitions and concurrency caps confine a slow tenant to its own lane — no head-of-line blocking.

3. Why must a registered webhook URL be treated as untrusted input?

Outbound POSTs go to attacker-chosen URLs; resolve and allow-list the IP so it can't hit internal hosts.

4. At-least-once delivery can POST an event twice. What makes that safe?

An idempotency key (the event_id) lets the receiver treat a repeat delivery as a harmless no-op.
