Design Strava (Activity Tracking)

A write-heavy GPS ingestion problem wearing a social-app costume — get the time-series store right, treat the feed as secondary.

Why this lesson, for your mission: Strava looks like "another social feed," but the staff move is to name what it really is — a high-frequency time-series ingestion system. A run emits a GPS point every second or two; the feed is read-light by comparison. L6/L7 interviewers watch whether you anchor the design on the write path (batching, write-optimized store, offline durability) and downsample for reads, instead of burning your time on fan-out you've already solved elsewhere.

Functional Requirements

Strava's value is recording a workout, viewing it richly, and seeing what your friends did. Lock these three and explicitly punt the rest.[1]

#Users should be able to…
1Record an activity — start, pause, stop, and save a run or ride, capturing the GPS route as they move.
2View an activity with stats — distance, pace, elevation, time, and the route drawn on a map.
3See an activity feed of the people they follow, newest first.

Out of scope (say it out loud): auth, follow/friend management, likes & comments, segments and leaderboards.[1] Naming the cut is itself a signal.

Non-Functional Requirements

PropertyTarget / priority
Durability of captureNever lose GPS points. The phone records even offline (a tunnel, a remote trail) and syncs later — the device is the source of truth mid-activity.[1]
Availability > consistencyThe recording path must always accept writes. Eventual consistency on the feed and stats is fine.[1]
Low-latency readsOpening an activity or the feed should feel instant (<200ms), even though the route holds thousands of points.
Write scalabilitySupport ~10M concurrent activities, each streaming points.[1] The ingest path is the scaling pressure.
Accurate aggregate statsDistance/elevation/pace must match what the device computed locally — no drift between phone and server.[1]

Capacity Estimation

Only estimate the numbers that change the design. Here, one number dominates: write volume during an activity.

GPS write firehose
  • One point ≈ every 1–2 seconds. A 1-hour ride ≈ 2,000–3,600 points.
  • 10M concurrent activities × ~1 point/sec ⇒ ~10M point-writes/sec at peak.[1]
  • Each point ≈ lat, lng, timestamp, elevation ≈ ~30–40 bytes raw.
Per-activity storage
  • 3,000 points × ~36 B ≈ ~100 KB raw per activity track before compression.
  • Delta-encode + gzip the stream and that drops by 60–80%[4] ⇒ tens of KB stored.
Reads
  • Feed + activity views are orders of magnitude lighter than the write firehose — a few reads per user per session.

Design implication: 10M writes/sec is the whole problem. You cannot send one HTTP request per point and you cannot do one row-insert per point through a relational primary. You need device-side batching + a write-optimized store. Everything downstream is comparatively easy.

Data Flow — the recording pipeline

Strava is a data-processing system, so the flow is worth tracing explicitly:

  1. Device samples GPS once/sec into a local buffer, computing live stats on-device (so the user sees pace even with no signal).
  2. Every N seconds (or on reconnect) it flushes a batch to POST /points. Offline batches queue durably on the phone.
  3. The ingest service validates and appends to a write-optimized point store, partitioned by activityId.
  4. On /complete, a finalizer reads the full track, computes authoritative aggregate stats, builds an encoded polyline, and writes the immutable raw track to object storage.
  5. A feed worker fans the completed activity to followers.

Lead with the write path — batch on device, append to an LSM-tree store, never one row-per-point through a relational primary — and treat the feed as a familiar, secondary concern you can resolve in two minutes. Knowing which hard part deserves your 60% is the whole game.

Deep Dive 1 — Ingesting the GPS firehose

The naïve design — POST one point per second per user — melts at 10M writes/sec: HTTP overhead dwarfs the 36-byte payload, and a relational primary fsyncing every insert chokes on write amplification. Two moves fix it:

Batch on the device

The phone is already the source of truth (it computes live stats offline). Let it buffer points and upload in batches every few seconds or on reconnect. This collapses 10M req/sec into a manageable batch rate, and makes offline-then-sync free — the buffer just drains when signal returns.[1] Tag each batch with an idempotency key so retries after a flaky connection don't duplicate points.

Write-optimized store, not a relational primary

Append-heavy, time-ordered, rarely-updated data is the textbook case for an LSM-tree store like Cassandra. Writes land in an in-memory memtable and flush to disk sequentially, so disk access is infrequent and throughput is high — the opposite of MySQL flushing every write.[4] Partition by activityId so one activity's points colocate and a fetch is a single-partition range scan by timestamp.

ApproachVerdict
Point-per-request → relational✗ HTTP + fsync overhead; doesn't scale to 10M/s.
Batch → Kafka → store✓ Great for buffering/backpressure; adds a hop & ops cost. Justify if you need a stream for other consumers.
Batch → ingest → Cassandra/TSDB✓✓ Simplest design that meets the bar. Pick this; add Kafka only if pressed.

Deep Dive 2 — Computing route stats

Distance, elevation gain, and pace are derived from the point stream. Two timing choices:

  • On completion (batch): /complete kicks a finalizer that scans the full track once and writes authoritative stats onto the Activity row. Simple, accurate, and runs off the hot path.
  • Streaming (incremental): update running totals as each batch arrives, so a half-finished ride still shows server-side stats. More moving parts.

Pick on-completion as the default — the device already shows live stats locally, so the server doesn't need streaming aggregation to give the user real-time numbers. The server's job is to compute the canonical figures once, so they match the phone's. Store the route as a Google-encoded polyline[2] on the activity for cheap map rendering, and keep the full-resolution raw track in object storage for anything that needs every point later (re-analysis, segment matching).[4]

Deep Dive 3 — The activity feed (lighter touch)

This is the fan-out tradeoff you already worked in Lesson 16, so resolve it briskly:

StrategyWhen
Fan-out on write (push to followers' feeds)Fast reads; great for the common case. Activity volume is modest vs. point volume, so write amplification is tolerable.
Fan-out on read (query followees at read time)Avoids huge write blow-up for users with very many followers.

Hybrid: push for most users; for the rare high-follower account, pull at read time. Crucially, a feed entry carries only activity metadata + the polyline — never the raw point stream — so feed reads stay tiny. Don't over-build this; one paragraph in the interview is enough.

Deep Dive 4 — Serving the map efficiently

A 3-hour ride is ~10,000 points — far more than a phone-sized map can draw, and wasteful to ship. The fix is downsampling: serve a reduced point set (e.g. via Ramer–Douglas–Peucker) sized to the requested zoom, while the full-resolution track lives in object storage for detailed analysis.[4]

Read-efficiency stack
  • Encoded polyline on the activity row — compact string, decodes straight into a map overlay.[2]
  • Delta-encode + gzip the stored stream — 60–80% smaller on the wire and at rest.[4]
  • Zoom-aware downsampling — never send more points than the viewport can resolve.
  • CDN / object storage for the immutable raw track and tiles.

The principle generalizes: the resolution you capture (every second) is not the resolution you serve (whatever the screen needs).

Check yourself — retrieval practice

Answer from memory before scrolling back up.

1. What single number most shapes the Strava design?

~10M concurrent activities each streaming a point/sec ⇒ ~10M writes/sec. The write firehose is the design.

2. Why batch GPS points on the device before uploading?

Batching collapses millions of tiny requests and makes offline-then-sync free — the buffer drains when signal returns.

3. Why Cassandra over a relational primary for the point store?

Append-heavy, time-ordered data suits an LSM-tree: infrequent sequential disk flushes give high write throughput.

4. How do you render a 10,000-point route on a phone map?

Capture resolution ≠ serve resolution. Downsample (e.g. Douglas–Peucker) to what the viewport can resolve; keep full track in S3.
