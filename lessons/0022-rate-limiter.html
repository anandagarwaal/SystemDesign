Design an API Rate Limiter

The defensive component that caps requests per client per window and returns 429 — the canonical "small system, deep tradeoffs" interview.

Why this lesson, for your mission: Rate limiting looks tiny — one boolean check — but it is a favorite L6/L7 screen precisely because there is little breadth to hide behind. Your score is decided almost entirely by depth: which counting algorithm you pick and why, how you make the shared counter atomic, and whether you say the fail-open vs fail-closed tradeoff out loud. This lesson drills exactly those signals.

Phase 1 · 0–5 minClarify the problemPin scope and the few NFRs that will drive every later decision.

Ask before you design

  • “What do we limit by — user, IP, API key, endpoint?” — The key choice decides counter cardinality and fairness.
  • “Must limits be exact across the whole fleet, or approximately per node?” — Exact global limits need a shared store on the hot path.
  • “If the limiter fails, should requests be allowed or rejected?” — The fail-open vs fail-closed policy shapes availability.

Functional Requirements

Keep the core scope to three crisp capabilities. Resist the urge to design abuse-detection or billing — those are out of scope and naming them as out-of-scope is itself a senior signal.

#The system should…
1Permit up to N requests per time window per client key (user ID, IP, or API key) and reject the rest with HTTP 429, including X-RateLimit-Limit, X-RateLimit-Remaining, and X-RateLimit-Reset headers.[1]
2Support configurable rules — e.g. "100 requests/min per user" — that can differ per route and per user tier (free vs paid).[1]
3Expose a fast allow(key) decision the request path can consult before the request reaches application logic.

Non-Functional Requirements

Rate limiting sits in the hot path of every single request, so its NFRs are unusually sharp. State concrete targets, not adjectives.

PropertyTarget & priority
Low added latencyThe check must add < 10 ms per request — it is overhead on every call, so this is the top constraint.[1]
High availabilityThe limiter must not take the API down. This forces the explicit fail-open vs fail-closed choice when the counter store is unreachable (deep dive 4).
AccuracyEnforce the cap closely. Eventual consistency is acceptable — a small over/under-count at window edges across nodes is fine.[1]
Fleet consistencyA client's limit is one logical counter even though it is enforced by many horizontally-scaled servers — they must share state.

Say to move on → “It sits on every request, so added latency under 10 ms and never taking the API down are the top constraints. Let me size it.”

Phase 2 · 5–10 minEstimate what mattersOnly the numbers that change a decision — say the implication out loud.

Capacity Estimation

Only compute the numbers that change a decision. Three matter here: throughput, distinct keys, and counter memory.

  • Throughput: ~1M requests/sec across ~100M daily active users.[1] Implication: every check is on the hot path 1M times a second — a per-request network hop to a counter store must be cheap and shardable.
  • Distinct keys: ~100M active keys. Implication: we need an entry per key, but only a tiny one.
  • Counter memory: A token-bucket entry is ~2 fields — token count + last-refill timestamp — say ~100 bytes with overhead. 100M keys × 100 B ≈ ~10 GB. Implication: this fits comfortably in one (or a small sharded) in-memory store like Redis; we never need to persist counters to disk, and TTL-based expiry keeps idle keys from accumulating.

Interviewer pushback

“Why not store counters in a database for durability?”

Staff answer: Counters are short-lived and cheap to lose; persisting 1M updates/s would add latency and cost for no benefit. Redis with TTLs is enough.

Say to move on → “1M checks/s and ~10 GB of counters fits in a sharded in-memory store. Let me define the tiny interface.”

Phase 3 · 10–17 minAPI & data modelLock the contract and the storage shape before drawing boxes.

Core Entities & API

Three entities: Rule (a policy: limit, window, scope), Client (the keyed subject), and Counter (the per-key state).[1] The interface is deliberately tiny.

The hot-path check — returns the decision plus the headers the caller echoes back:

allow(key, ruleId) → { passes: boolean, remaining: number, resetTime: timestamp }[1]

Rule configuration (admin plane, low traffic, derives caller from auth token):

  • POST /v1/rules — create a rule { scope, key_type, limit, window_seconds }
  • PUT /v1/rules/{id} — update a limit or window (e.g. bump a paid tier)
  • GET /v1/rules — list active rules for a route/tier

Note the split: allow() runs millions of times a second and must be in-memory fast; the rule CRUD endpoints are rare and can hit a normal database, with rules cached at each enforcement point.

Data Model

Two very different stores. Rules are tiny, durable, and read from a local cache; counters are ephemeral, hot, and must be mutated atomically. The load-bearing key design is the Redis hash tag rl:{clientKey}:… — every counter for one client lands in the same cluster slot, so a multi-rule check (per-second and per-minute) runs as one Lua script on one shard.

EntityStoreKeysIndexes / access pattern
rules (rule_id, route_pattern, key_type [user|ip|api_key], tier, limit, window_s, burst, algorithm, fail_mode)Postgres (hundreds–thousands of rows)PK rule_id(route_pattern, tier); full table cached in every gateway, refreshed every 30 s
overrides (key, rule_id, limit, expires_at, reason)PostgresPK (key, rule_id)Allow-list a partner or clamp an abuser without redeploying
Token bucketRedis Cluster hashrl:{clientKey}:{ruleId} → {tokens, last_refill_ms}Lua script: refill, check, decrement; TTL ≈ 2× time-to-full so idle keys vanish

Interviewer pushback

“Why return remaining and reset headers?”

Staff answer: Well-behaved clients back off before hitting 429s, which reduces load and support tickets.

Say to move on → “allow(key, rule) returning remaining and reset is the contract. Now where it runs and what it reads.”

One atomic Lua round trip per request at the edge; denied traffic never reaches application servers. Rules change rarely and are pulled into each gateway's memory.

High-Level Design

The flow is short. A request arrives, the enforcement point extracts the client key and the matching rule, calls allow() against a shared counter store, and either forwards the request or short-circuits with 429 — the application servers ideally never see blocked traffic.[1]

ComponentRole
Enforcement pointSits at the edge (API gateway / middleware / sidecar — deep dive 3). Extracts key, looks up rule, calls allow(), returns 429 on deny.
Counter storeCentralized in-memory store (Redis) holding per-key counter state, mutated atomically. Sharded by client key at scale.[1]
Rules storeDurable DB of policies; rules are cached at each enforcement point and refreshed periodically.

Interviewer pushback

“Why enforce at the gateway instead of in each service?”

Staff answer: Blocked traffic should never consume application resources. The edge sees every request and can use consistent keys.

Say to move on → “Deep dives: counting algorithms, atomic shared counters, placement and failure mode.”

Phase 5 · 27–47 minDeep dives & tradeoffsGo deep where the system breaks; compare alternatives and justify the pick.

Deep Dives

This is where the interview is won. Four hard parts: the algorithm, atomic shared counting, placement, and the availability tradeoff.

1. Counting algorithms — and the staff-preferred default

Five standard algorithms, each trading accuracy against memory and burst behavior.

AlgorithmHow it worksWeakness
Fixed windowOne counter per fixed bucket (e.g. each minute); INCR on each request.Boundary burst: 100 reqs at 12:00:59 plus 100 at 12:01:00 = 200 in two seconds, double the intended cap.[1]
Sliding window logStore every request timestamp; drop those older than the window; count the rest.Accurate but memory-heavy — 1000 reqs/min means storing 1000 timestamps per key.[1]
Sliding window counterWeighted blend of current + previous fixed-window counts.Tiny memory, smooths the boundary burst; approximate, assumes evenly-spread traffic.[1]
Token bucketBucket holds up to burst tokens, refilled at a steady rate; each request spends one.Stores just count + last-refill time; allows controlled bursts. Hard to make wrong.[1]
Leaky bucketRequests queue and drain at a fixed rate (a smoothing queue).Enforces a steady output rate but adds queuing latency and disallows any burst.

The pick: token bucket as the default. The reasoning to say out loud: it "strikes the best balance between simplicity, memory efficiency, and handling real-world traffic patterns"[1] — two small fields per key, and it tolerates legitimate bursts (a user loading a page that fires several calls) while still capping the sustained rate. The sliding window counter is the strong runner-up when you want a strict per-window cap with minimal memory and no burst allowance. Fixed window is the trap answer because of its boundary burst.

2. Shared counting across the fleet — make it atomic

With many enforcement nodes, the counter cannot live in any one process — every node must read and update the same logical counter. Put it in a central store such as Redis. The non-obvious failure is the race: a naive read-then-write (e.g. HMGET outside a transaction, compute, then write back) lets two concurrent requests both read "1 token left" and both pass, busting the limit.[1]

Fix: collapse read-calculate-update into one atomic operation. For a simple counter, INCR followed by EXPIRE on the first increment gives you a self-expiring fixed-window count. For token bucket — which must read tokens, compute refill, and decrement together — wrap the whole logic in a small Lua script; Redis runs scripts atomically, eliminating the race in one round trip.[1]

Tradeoff to name: a centralized counter adds one extra network hop per request. That is the price of fleet-wide consistency, and why the < 10 ms latency budget and Redis's in-memory speed matter. At 1M RPS you also shard Redis (consistent hashing on the client key) so a client's requests always land on the same instance.[1]

3. Placement — where the check runs

PlacementTradeoff
In-process / local bucketsZero network hop, lowest latency. But each server only sees its own slice of traffic; behind a load balancer the global limit is wrong unless nodes reconcile state.[1]
SidecarCo-located proxy per service; isolates limiter logic from app code, still talks to a shared store.
API gateway / edge (preferred)Check at the system edge so blocked requests never reach application servers.[1] Centralizes config and is the cleanest interview answer.

The real spectrum is local in-memory buckets with periodic async reconciliation (fast, approximate — push each node's counts to a coordinator and pull back the global view every few seconds) versus a centralized counter on every request (exact-ish, one hop). For most APIs the gateway + centralized Redis counter wins; local buckets are the move only when latency is so tight that an extra hop is unacceptable and you can tolerate looser global enforcement.

4. Fail-open vs fail-closed when the store is down

The counter store will have outages. You must decide what allow() returns when it cannot reach Redis — and stating this tradeoff explicitly is a defining staff signal.

  • Fail-open — allow all requests, skip the check. Keeps the API serving, but during the outage abusive clients can flood the backend, and rate-limiter failures often coincide with the traffic spikes you most need protection from, risking cascade failure.[1]
  • Fail-closed — reject (503/429) until the store recovers. Sacrifices availability of that path but protects the backend exactly when it is most fragile.[1]

Hello Interview selects fail-closed here, on the logic that "rate limiting failures often coincide with traffic spikes when we need protection most."[1] The honest answer is that it depends on the route: fail-open a checkout flow you can't afford to block, fail-closed an expensive internal endpoint. Pair the choice with Redis Cluster replication and automatic failover so the store rarely goes fully dark in the first place.[1]

★ Staff-level signal Three moves separate staff from senior on this problem: (1) pick an algorithm with explicit reasoning — name token bucket (or sliding-window counter) and say why, while flagging fixed window's boundary burst; (2) make the shared-counter update atomic — call out the read-then-write race and reach for INCR+EXPIRE or a Lua script unprompted; (3) state the fail-open vs fail-closed tradeoff out loud and commit to one with a reason. Candidates who quietly assume "it just works" cap out at senior.

Interviewer pushback

“How do you avoid race conditions when two gateways update the same counter?”

Staff answer: Run the read-refill-decrement as one Redis Lua script, so the check is atomic without distributed locks.

Privacy

Low sensitivity, but keys are identifiers: IP addresses, user ids and API keys. Minimization: counters store only a hashed key and two numbers, expiring within minutes. Logs: decision logs hash or truncate IPs; raw API keys are never logged (log a key id). Retention: sampled decision events kept 30 days for abuse analysis, then aggregated. Nothing here needs a deletion workflow beyond log retention, because state is ephemeral by design.

Interviewer pushback

“Fail open or fail closed?”

Staff answer: Fail open for general API limits so a Redis outage doesn't become an API outage, with a local in-process fallback bucket. Fail closed for security-sensitive limits like login attempts.

Scaling 10× Without Changing the Architecture

10× = ~10M requests/s and ~1B active keys (~100 GB of counters).

ComponentTodayAt 10×Knob turned
Redis Cluster~10 primaries~100 primariesAdd shards; hash-tagged keys rebalance by slot
Counter memory~10 GB~100 GBStill trivial per shard; shorter TTLs
Gateway fleetScales with API traffic10×Nothing specific to the limiter
Round trips1 per request1 per requestPipeline multiple rules into one script; cache "definitely over limit" locally for a few hundred ms
RulesCached locallySameNothing

First bottleneck: Redis CPU on single hot keys (one giant client) — handled by local pre-deny caching. What forces a redesign: multi-region global limits with strict accuracy, which requires either cross-region counter replication (CRDT-style counters) or per-region budgets.

Cost of Running

Assumptions: 1M requests/s, 100M keys, 3 AZs, list prices from the course price sheet. The limiter's cost is mostly the Redis fleet and — surprisingly — network transfer.

Redis Cluster~10 primaries + 10 replicas (CPU-bound, ~150k Lua ops/s each)$5,000

Unit cost: ≈ $0.01 per million requests checked. Dominant driver: cross-AZ data transfer, not Redis. Lever: AZ-local limiter shards, each enforcing ~limit/3 (approximate but usually fine), or AZ-affinity routing to the shard's primary — this removes most cross-AZ bytes without changing the design.

Interviewer pushback

“What's surprisingly expensive?”

Staff answer: Cross-AZ traffic between gateways and Redis. Keep AZ-local replicas or local token caches to cut it.

Wrap-up · 58–60 minClose strongRecap decisions and tradeoffs in 60 seconds; name what you would do next.

Closing Summary (60 seconds)

A rate limiter is a latency-critical check on every request. Enforcement runs at the edge gateway, keyed by user, API key or IP. It calls a token bucket (or sliding-window counter) in a sharded Redis cluster through an atomic Lua script, so fleet-wide limits are accurate in under 10 ms. Rules come from a config service cached locally. General limits fail open with a local fallback, while security limits fail closed. Counters are tiny (~10 GB for 100M keys), so at 10× we just add Redis shards; cross-AZ traffic is a real cost.

Check yourself — retrieval practice

Answer from memory before scrolling back up.

1. What is the specific weakness of the fixed-window counting algorithm?

100 requests at 12:00:59 plus 100 at 12:01:00 yields 200 in two seconds — the boundary burst.

2. Why wrap the token-bucket update in a Redis Lua script instead of separate calls?

A naive read-then-write lets two requests both see the last token and both pass; atomicity prevents it.

3. Why is token bucket the common default rate-limiting algorithm choice?

Two small fields per key, and it allows controlled bursts while capping the sustained rate.

4. What does choosing "fail-closed" mean when the counter store is unreachable?

Limiter outages often coincide with traffic spikes, exactly when the backend needs protection most.
