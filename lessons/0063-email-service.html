Design an Email Service (Gmail / Outlook)

A read-heavy mailbox over a write-once log of immutable messages — where durability is non-negotiable and search is the hard part.

Why this lesson, for your mission: Email looks like CRUD and is anything but. At L6/L7 the interviewer watches whether you separate the immutable message blob from the mutable per-user metadata, whether you treat labels as a view rather than folders as storage, and whether you can wire up SMTP ingestion, full-text search, and attachment dedup without re-deriving each from scratch. Reaching for "store it in Postgres" is senior; modeling the storage/metadata split and naming the durability bar is staff.

Phase 1 · 0–5 minClarify the problemPin scope and the few NFRs that will drive every later decision.

Ask before you design

  • “Are we building the mail provider (SMTP in and out) or a client?” — A provider owns MX ingress, spam filtering and outbound reputation.
  • “What search capability — full text including attachments?” — Attachment text extraction and per-user indexes are big cost drivers.
  • “What retention and storage quota per user?” — Quotas and retention drive tiering and dedup.

Functional Requirements

Email's surface is huge; lock the core before designing so the deep dives stay focused.

#The user should be able to…
1Send and receive email, including attachments, to/from any internet address.[1]
2Organize mail with folders and labels (Inbox, Sent, archive, stars).[1]
3Search their mailbox by keyword over subject, body, and sender.[1]
4Define filters/rules that auto-label or route incoming mail.

Explicitly out of scope: calendar/contacts, rich collaborative editing, end-to-end encryption, threading heuristics, and the deliverability/reputation game. Naming these signals you know where the rabbit holes are and are choosing the interview-relevant core.

Non-Functional Requirements

NFRTarget / priority
DurabilityThe hard bar: a delivered message must never be lost — target ≥ 11 nines. Mail is a system of record.[1]
AvailabilityHigh availability for reads/sends; brief send delays are tolerable, data loss is not.
Search latencyMailbox search returns in < 500 ms over years of accumulated mail.[1]
Scale~1B users, billions of messages/day; per-user mailbox into the tens of GB.
ConsistencyRead-your-writes within a mailbox (a sent mail appears in Sent immediately); cross-user delivery is eventual.
The two tensions to name up front.
  • Durability vs. cost — never losing a message means replicated, write-once storage and acknowledged hand-offs at every hop, not best-effort fire-and-forget.
  • Read-heavy access vs. huge cold corpus — users touch recent mail constantly but keep everything forever, so the design splits hot metadata from cheap cold message bodies.

Say to move on → “Durability is the hard bar; search and sync must be fast. Let me size messages and storage.”

Phase 3 · 10–17 minAPI & data modelLock the contract and the storage shape before drawing boxes.

Core Entities & API

Entities: User (mailbox owner), Message (immutable: headers + body + attachment refs), MailboxEntry (mutable per-user metadata: labels, read/star flags, pointer to a Message), Attachment (a content-addressed blob). The split between immutable Message and mutable MailboxEntry is the whole design.[1]

EndpointPurpose
POST /v1/messagesSend a message (sender from auth token; body + attachment IDs).
POST /v1/attachmentsUpload an attachment, returns a content-addressed blob ID.
GET /v1/messages?label=&cursor=List a folder/label view, newest first, cursor-paginated.
GET /v1/messages/{id}Fetch one message (metadata + body + attachment links).
PATCH /v1/messages/{id}Mutate metadata only: add/remove label, mark read/starred.
GET /v1/search?q=&cursor=Full-text search across the caller's mailbox.

Note that PATCH touches the MailboxEntry, never the Message: labels and flags are mutable metadata, the message itself is write-once. And it's cursor, not page — offset pagination breaks when new mail arrives mid-scroll.

Data Model

Immutable message content and mutable per-user state are different tables in different stores. MailboxEntry is the hot, user-sharded row that carries labels and flags; list views are served from a label index ordered by date; a per-mailbox modseq change log powers delta sync. Message bodies and attachments are write-once blobs, attachments content-addressed and reference-counted within a tenant.

Deep Dive 1 — Mailbox storage model & metadata index

The instinct to "put each email in a row" collapses under the read-heavy/huge-corpus split. The staff move is to separate what the message is from where it lives for each user.

Two stores, two access patterns

  • Message store (immutable, cold): the raw RFC 5322 message — headers, body, attachment refs — written once to object storage and never edited.[2] Cheap, replicated, content-addressed.
  • Metadata store (mutable, hot): one small MailboxEntry per (user, message) holding labels, read/star flags, timestamp, and a pointer to the message blob.[1]

Sharding the metadata store by user keeps a mailbox's entries co-located, so listing a folder is a single-shard range scan — no scatter-gather for the common case.[1]

Folders vs. labels — the modeling tell

A folder implies one home per message; a label is a tag, and a message can carry many. Modeling labels as a set on the MailboxEntry (not as physical folders) means "Inbox", "Sent", and "Important" are all just queries over the same entries — and a PATCH to relabel never moves any bytes.

Index the views you list by. "List Inbox newest-first" and "list unread in label X" are the hot reads, so maintain secondary indexes on (user, label, timestamp) and (user, label, read). The message blob stays untouched; only the tiny metadata row is indexed and mutated.
★ Staff-level signal Recognizing that a delivered message is immutable and only per-user metadata changes is the unlock. It lets you store one blob per message regardless of recipients, make relabeling a metadata-only write, and tier cold bodies to cheap storage — all without ever rewriting the message. Senior candidates store rows; staff candidates store an append-only log with a mutable index on top.

Deep Dive 2 — Full-text search over mail

Search is the part that breaks the naïve design. Scanning a user's tens-of-GB mailbox per query is hopeless, so this reduces to the inverted index — the same machinery behind Facebook Post Search, scoped per user.[4]

Per-user index, not one global index

Unlike public post search, mail is private: a query must only ever touch the caller's own mail. So the index is partitioned by user — each mailbox owns its inverted index (term → message IDs) over subject, body, and sender. A search is a single-user lookup, which keeps both latency and the privacy boundary clean — no cross-tenant scatter.

user42 / "invoice"  → [m17, m412, m9981]
user42 / "refund"   → [m412, m9981]
user42 / "acme"     → [m17, m412]

Multi-word queries become an intersection of posting lists, exactly as in post search; sender/label filters are extra intersected lists. Indexing happens off the ingestion path: when the Mailbox Service writes a new entry, it emits an event to an indexer that tokenizes and updates that user's index.[4]

For the index mechanics — tokenization, posting-list intersection, document vs. term partitioning, and near-real-time freshness — see the Post Search deep dives; the only twist here is the per-user partition and the privacy constraint it enforces. Decoupling indexing via a queue is the same async/messaging pattern used everywhere else in the system.

Deep Dive 3 — Attachments as blobs with dedup

Attachments are ~95% of the bytes and the same file (a 5 MB deck mailed to 200 people) lands hundreds of times. Storing them inline in the DB, or once per recipient, is the expensive mistake.

Content-addressed blob storage

Push every attachment to an object store and key it by the hash of its content (e.g. SHA-256) — this is the canonical blob store / S3 pattern.[2] The Message holds only a reference: {blobId: sha256, filename, size}. Because the key is the content hash, identical files map to the same blob automatically.

Inline in metadata DBContent-addressed blob store
CostDB bloats with binary; backups balloon.Cheap object storage; tier cold blobs down.
DedupNone — N copies of one file.Hash key collapses duplicates to one blob.
Read pathCouples body fetch to heavy bytes.Fetch metadata fast; hydrate blob lazily.

Dedup needs reference counting

If one physical blob is shared by many messages, you can't delete it when one user trashes their copy. Maintain a reference count (or a set of referencing message IDs) per blob; garbage-collect a blob only when its count hits zero.[2] Uploads also go direct-to-blob via presigned URLs, so multi-MB files never stream through the API tier.

Dedup vs. isolation. Cross-user dedup maximizes savings but means one tenant's delete can't free shared bytes, and a corrupt blob hits everyone. A common middle ground: dedup within a user (or org) only, so blast radius and billing stay per-tenant while still collapsing the "mailed to the whole team" case.

Deep Dive 4 — SMTP send pipeline: queueing, retries & spam

Sending isn't a synchronous RPC — the recipient's server may be slow, greylisting, or down for hours. The send path must be a durable, retrying async pipeline, or you violate the durability NFR the moment a downstream MTA hiccups.[3]

Outbound flow

  1. Accept & persist: write the Sent entry and enqueue the message before ACKing the user — once accepted, it cannot be lost.[1]
  2. Authenticate: sign with DKIM and align SPF/DMARC so receivers trust the mail.[3]
  3. Deliver with retries: outbound MTA looks up the recipient's MX records and attempts SMTP delivery, retrying with exponential backoff over hours/days before bouncing.[3]

Inbound & spam filtering

SMTP Ingress accepts inbound mail to a durable queue first, then the Mailbox Service runs spam classification and user filters before writing the entry. Doing spam scoring asynchronously off the accept path keeps ingestion fast and lets the classifier evolve without touching the delivery hot path.[3]

★ Staff-level signal The durability bar is won at the hand-offs: every hop (accept → queue → deliver) acknowledges only after a durable write, so a crash anywhere replays rather than drops. Naming "at-least-once with idempotent delivery and dedup on Message-ID" — rather than hoping the network cooperates — is the staff-level answer.

Deep Dive 5 — Sync protocol to clients

A user has a phone, a laptop, and a webmail tab open at once. They expect a swipe-to-archive on one to appear on all within seconds — without each client re-downloading the whole mailbox.

Delta sync over a change log

Give each mailbox a monotonic change cursor (a version/sequence that bumps on every metadata mutation, IMAP's MODSEQ / JMAP's state string). A client stores its last cursor and asks "what changed since X?"; the server returns only the deltas — new messages, flag changes, relabels — plus the new cursor.

ApproachTradeoff
Full re-fetchSimple but burns bandwidth and battery; unusable at GB scale.
Client polling deltasBandwidth-light; freshness bounded by poll interval.
Push + delta syncServer notifies on change, client pulls delta — fast and cheap.

The metadata/message split pays off again: sync ships tiny metadata deltas, and a client hydrates message bodies from the blob store only when the user actually opens a message.

Privacy

A mailbox is a lifetime of personal correspondence. Encryption: TLS in transit (including MTA-to-MTA where supported), encryption at rest for blobs, metadata and indexes, with per-tenant keys for businesses. Access: no human access to content except with user consent or legal process, audited; automated processing (spam, search) runs without human exposure. Deletion: trash → permanent delete removes the entry and index postings, decrements attachment refcounts, and purges blobs and backups within a published window. Dedup boundary: within a tenant only, so one customer's data never shares storage with another's. Tracking protection: proxy remote images to hide recipients' IPs.

Closing Summary (60 seconds)

An email service separates immutable messages from mutable per-user metadata. Inbound SMTP is accepted only after a durable write, then spam-scored and delivered through queues. Bodies and content-addressed attachments go to blob storage with dedup and cold tiering, while mailbox entries (labels, flags, pointers) live in a user-sharded store. Each user has a private full-text index updated asynchronously, and clients sync deltas from a change log. Outbound mail goes through queued MTAs with retries and sender authentication. At 10× we add shards and ingress capacity.

Revisit Deep Dive 4's "Outbound flow" numbered list.

What would happen to the "never lose a message" guarantee if any hop (accept, queue, deliver) acknowledged before its write was durable?

The durability bar is won at hand-offs: acking before a durable write creates a window where a crash silently drops mail the sender believes was delivered.

Picture the server crashing one millisecond after it acknowledges but before its write reaches disk.

What breaks if a mobile client's stored sync cursor is dropped and it asks the server for "changes since cursor 0"?

Delta sync only works relative to a known state; an invalid or too-old cursor has no small diff to compute, so the system falls back to a full resync.
