Design Spotify (Music Streaming)

Spotify isn't YouTube with smaller files — it's a fixed, write-rarely catalog where instant playback and personalization carry the design.

Why this lesson, for your mission: Music streaming looks like video streaming, and the trap is to copy the YouTube answer wholesale. At L6/L7 the signal is recognizing what's different: the catalog is finite and read-mostly, files are tiny, and the hard parts shift from a transcoding pipeline to sub-second start latency, catalog search, and recommendations. Name that delta early and the interview is yours.

Phase 1 · 0–5 minClarify the problemPin scope and the few NFRs that will drive every later decision.

Ask before you design

  • “Do users upload content, or is it a licensed catalog only?” — A curated catalog removes the transcoding and moderation pipeline.
  • “Is offline download in scope?” — Offline adds DRM key management and device caches.
  • “What playback start latency target?” — ~250 ms drives edge caching and pre-buffering.

1. Functional Requirements

Pick the four flows that define the product and say the rest — social, lyrics, podcasts, offline downloads — is out of scope so you can spend depth where it counts.[1]

#Users should be able to…Note
1Stream a songTap play, hear audio in <~250 ms; skip/seek freely
2Search the catalogBy track, artist, album; typeahead and ranked results
3Create & manage playlistsAdd/remove/reorder tracks; save songs to a library
4Get recommendationsPersonalized home, radio, and Discover Weekly

The contrast with Lesson 33 (YouTube) is the whole point: there is no user upload flow. Content is ingested once by labels, not by millions of creators — which collapses the write path and reshapes everything downstream.

2. Non-Functional Requirements

State the target, not the adjective. The headline NFR is start latency.[1]

NFRTargetDrives
Low start latencyPlayback in <~250 ms after tapCDN edge + pre-buffering + first segment low-bitrate
AvailabilityHA > strong consistency for readsReplicated catalog cache; eventual counts
Read scalability~Billions of streams/day, extreme read:writeCDN absorbs audio; cache hot metadata
Smooth playbackNo rebuffer on network dipsAdaptive bitrate + client buffer ahead
Recommendation freshnessWeekly/daily, not real-timeOffline batch pipelines, precomputed

Start latency and read scalability are the load-bearing NFRs. Notice durability is not a headline: the master catalog is a recoverable, externally-sourced asset, not irreplaceable user data — the opposite emphasis from YouTube.

Say to move on → “Playback start latency is the headline. Let me size catalog and streams; it's the inverse of video.”

Phase 2 · 5–10 minEstimate what mattersOnly the numbers that change a decision — say the implication out loud.

3. Capacity Estimation

Only the numbers that move a decision. The capacity story is the inverse of video: the catalog is small.[1] Figures below are my own back-of-envelope estimates.

QuantityEstimateDesign implication
Catalog size~100M tracks × ~5 MB (multi-bitrate) ≈ low PBsFinite and static → fully CDN-cacheable; hot subset fits in RAM.
Catalog ingest~tens of thousands of new tracks/dayWrite QPS is trivial — not the bottleneck. No live pipeline.
Stream bandwidth~500M users × ~20 songs/day × ~5 MBThis is the cost. ~50 PB/day egress → must serve from CDN edge, never origin.
The number that reframes it. Unlike YouTube's ever-growing, user-supplied library, Spotify's catalog is bounded and changes slowly — so the entire popular set can live at CDN edges and in cache indefinitely. The dominant axis is still egress bandwidth, but the read:write skew is even more extreme: a hit song is encoded once and streamed billions of times. Optimize the read path; the write path is an afterthought.

Interviewer pushback

“If the catalog is small, what's actually hard?”

Staff answer: Egress volume and start latency: hundreds of billions of streams a month must start within ~250 ms. Nearly every byte is served from edge and device caches.

Say to move on → “The catalog is only a few PB and fits at the CDN edge. Let me define entities.”

Phase 3 · 10–17 minAPI & data modelLock the contract and the storage shape before drawing boxes.

4. Core Entities & API

Three entities carry the design. Track separates immutable metadata from the audio blob — the split that lets metadata live in a DB and bytes live in blob storage + CDN.[2]

EntityKey fields
Trackid, title, artistId, albumId, durationMs, audioManifestUrl, bitrate variants
Playlistid, ownerId, name, ordered list of trackIds, updatedAt
Userid, library (saved trackIds), listening history, taste profile

The API is small and read-heavy. The user is always derived from the auth token, never a body param.

EndpointPurpose
GET /v1/search?q=Typeahead + ranked track/artist/album results
GET /v1/tracks/{id}Return metadata + audioManifestUrl (the streaming entry point)
POST /v1/playlistsCreate a playlist; PATCH to add/reorder tracks
PUT /v1/me/library/{trackId}Save/remove a track in the caller's library
GET /v1/me/recommendationsPersonalized home rows + Discover Weekly
POST /v1/playsEmit a lightweight play event for analytics

Critical move: the client fetches a manifest, then pulls audio segments directly from the CDN — the app tier only ever serves small JSON and never proxies audio bytes (manifests & blobs → see Lesson 45, Blob Store (S3)).

5. Data Model

The catalog is read-mostly and globally cacheable; the only real user writes are playlists and library saves. The load-bearing modeling choice is the playlist fractional rank key: playlist_tracks is clustered by a sortable string key so inserting between two tracks writes one row. Plays are events, not rows — they feed two consumers: approximate counts for the UI and an auditable lake for royalties.

Interviewer pushback

“Why store playlist entries as rows instead of an array on the playlist?”

Staff answer: Collaborative playlists with thousands of tracks need concurrent inserts and reordering; rows with fractional positions avoid rewriting the whole list.

Say to move on → “Track metadata is separate from audio blobs; playlists are ordered entries. Now the play request path.”

The app tier serves small JSON: metadata and manifest URLs, search, playlists and precomputed recommendation rows. Audio comes from the CDN, with the next track pre-buffered. Play events flow through Kafka to royalty-grade storage, approximate counts and the offline recommendation pipeline.

Interviewer pushback

“Why doesn't Spotify need a heavy transcoding pipeline like YouTube?”

Staff answer: There are no user uploads. Tracks are encoded once at ingest into a few bitrates, so the work is small and offline.

Say to move on → “Deep dives: instant playback, search, playlists, recommendations and play counts.”

Phase 5 · 27–47 minDeep dives & tradeoffsGo deep where the system breaks; compare alternatives and justify the pick.

8. Deep Dives

This is 60% of the interview. Four hard parts, each with the alternative and a justified pick.

Deep Dive 1 — Instant playback: blobs + CDN + ABR + pre-buffering

The product promise is "tap and it plays." Audio is stored as immutable blobs in object storage, encoded once into a few bitrate variants (e.g., 96/160/320 kbps), split into short segments and indexed by a manifest (HLS/DASH).[2] Like YouTube, segments are served from the CDN edge, not origin — but a 3–4 MB song is small enough that the whole popular catalog stays cache-resident, so hit rates approach 100%.

Three tricks buy sub-250 ms starts: (1) request the first segment at a low bitrate so the first bytes arrive instantly, then ramp up via adaptive bitrate; (2) pre-buffer the next track in a playlist before the current one ends, so transitions are gapless; (3) cache the manifest itself at the edge so even the index lookup is local.[1]

ChoicePick & why
Encode on play vs onceOnce, at ingest. Catalog is static — precompute all variants and never transcode on the request path.
Stream from origin vs CDNCDN. Bandwidth is the cost; bounded catalog means near-100% edge hit ratio.
Buffer on demand vs aheadPre-buffer next track. Hides network latency at transitions; the key to "instant" feel.
Why this is easier than video. Files are ~1000× smaller than a movie and the catalog doesn't grow on a user-upload curve, so there's no async transcoding pipeline to design and edge caching is almost free. Spend the time you save on search and recommendations — that's the staff-level reallocation of depth.

Deep Dive 2 — Catalog search

Users search by track, artist, or album, expecting ranked typeahead as they type. The catalog is text-heavy and read-mostly — a textbook inverted index (Elasticsearch/OpenSearch).[2] Index the catalog once at ingest; updates are rare, so the index stays cheap to maintain.

ConcernApproach
Typeahead latencyEdge/CDN-cached prefix results + in-memory completion for top queries.
RankingBlend text relevance with popularity (play counts) so hits surface first.
Fuzzy / typosn-grams + edit-distance in the index; "biebr" still finds Bieber.

Don't over-build: search is a solved pattern here. Name the inverted index, note that popularity signals come from the analytics pipeline, and move on — knowing it's not the hard part is the signal.

Deep Dive 3 — Playlists & library data model

A playlist is an ordered list owned by a user, edited interactively, and potentially huge (10k+ tracks). The data-model question is how to store order cheaply while supporting insert/reorder. Store the playlist row with its track list, and store membership as rows keyed by (playlistId, position) — but use a fractional/rank position key so inserting between two tracks doesn't renumber the whole list.[2]

ApproachTradeoff
Integer positions (1,2,3…)Simple reads; every insert/reorder rewrites many rows. Poor for big lists.
Fractional rank keys (pick)Insert = one row with a between-value key; O(1) reorder, no mass rewrite.
Linked-list (prev/next)Cheap inserts but reads need traversal; awkward for paginated UIs.

The library ("saved songs") is the degenerate case: an unordered set of trackIds keyed by user. Both are the only real write paths in the system, and both fit a simple partitioned key-value/relational store — modest scale compared to the read fleet.

Deep Dive 4 — Recommendations & Discover Weekly

Personalization is what makes Spotify Spotify. The key insight: recommendations are not real-time — Discover Weekly refreshes weekly, home rows daily.[3] So compute them offline in batch and serve precomputed results, turning a hard ML-at-request-time problem into a cheap cache read. Full treatment in Lesson 50, Recommendation Systems.

StageWhat happens
SignalsPlay events, skips, saves, playlist adds → features in a data lake.
ModelsCollaborative filtering (users-like-you) + content/audio embeddings, run offline.
ServeWrite per-user rows to a fast store; GET /me/recommendations is a lookup.

The staff move is the latency reframe: by deciding freshness can be daily/weekly, you move the heavy computation off the request path entirely. Mention collaborative filtering for the cold-start fallback and audio-content embeddings for new tracks with no play history.

Deep Dive 5 — Play-count analytics pipeline

Every POST /v1/plays matters: it drives royalties, popularity ranking, and recsys features — but a synchronous UPDATE views = views + 1 on a hot song is a write hotspot, exactly the YouTube view-count trap.[1] Relax it: play counts are approximate and eventually consistent.

ApproachTradeoff
Sync increment in DBAccurate but hot-row contention on popular tracks; doesn't scale.
Event stream → batch aggregate (pick)Emit play events to a log (Kafka), window-aggregate, write rolled-up counts.
Probabilistic sketchesHyperLogLog for unique listeners; trade exactness for tiny memory.

One subtlety music adds over video: royalty accounting needs auditable, exactly-once-ish counts, so the pipeline writes raw events durably to the lake (for the financial path) while serving fast approximate counts to the UI (for ranking). Two consumers, one event stream.

★ Staff-level signal The senior-vs-staff tell is recognizing the delta from YouTube and reallocating depth accordingly: no user-upload flow, a bounded read-mostly catalog that lives almost entirely at the CDN edge, and tiny files — so the transcoding pipeline shrinks to a one-time ingest encode, and the genuinely hard parts become sub-second start latency (pre-buffering + low-bitrate first segment) and personalization. State that recommendations are batch-precomputed, not real-time, and that play counts must be async to dodge hot-row contention. Knowing which parts are solved (search, blob+CDN) and saying so is itself the staff move.[1]

Interviewer pushback

“How does playback start so fast?”

Staff answer: The client pre-buffers the next track, the first segment is low bitrate, audio files are small and CDN-cached, and on-device caching skips the network entirely for repeat plays.

14. Privacy

PII: account and payment data, and listening history, which can reveal mood, religion, politics or sexuality. Controls: private sessions (not used for recommendations), private playlists, history viewing and deletion. Minimization: recommendation training on pseudonymous ids; royalty reports aggregate plays and never expose listener identity to labels. Retention: raw play events kept as long as royalty audits require, with user identifiers separated/pseudonymized after the recommendation window. Deletion: account erasure deletes playlists, library and profile, and pseudonymizes historic play events retained for financial reporting.

Interviewer pushback

“How do you protect licensed audio?”

Staff answer: DRM-encrypted files with keys issued per device session, signed short-lived URLs, and region checks enforced at license issuance.

15. Scaling 10× Without Changing the Architecture

10× = 10× streams (~100B/day) and a larger catalog (podcasts/audiobooks).

ComponentTodayAt 10×Knob turned
CDN~1.5 EB/month (before device cache)~15 EBMore edge capacity; bigger on-device caches; lower default bitrate on cellular
Metadata + searchCached services10× readsMore replicas; edge-cached popular lookups
Playlist DBCassandra cluster10× rowsAdd nodes
Play pipeline~10B events/day~100B/dayMore partitions; compact event encoding
Recsys batchWeekly/daily jobs10× users/signalsBigger clusters; incremental model updates

First bottleneck: bandwidth cost. What forces a redesign: long-form user-generated content (podcasts/video uploads at scale), which reintroduces a YouTube-style ingest and transcoding pipeline.

16. Cost of Running

Assumptions: 500M users × 20 songs/day (~300B streams/month) at ~5 MB, ~50% served from on-device cache, ~1 PB catalog storage, list prices from the course price sheet. Royalties are excluded — they are roughly two-thirds of revenue and dwarf all infrastructure.

Wrap-up · 58–60 minClose strongRecap decisions and tradeoffs in 60 seconds; name what you would do next.

17 · Closing Summary (60 seconds)

Spotify is a read-mostly delivery system over a bounded licensed catalog. Tracks are encoded once into a few bitrates, DRM-protected and stored in blob storage behind a CDN with near-100% edge hit ratio. Playback fetches metadata and a manifest, pre-buffers the next track, and uses device caches to start in ~250 ms. Search runs on a dedicated index, and playlists are ordered rows supporting collaboration. Play events stream to analytics for royalties and batch recommendations like Discover Weekly. At 10× we add edge capacity.

Check yourself — retrieval practice

Answer from memory before scrolling back up.

1. What most distinguishes Spotify's design from YouTube's design?

No user-upload flow and a finite, slow-changing catalog mean the whole popular set lives at the CDN edge.

2. Which technique most directly enables sub-250 ms playback starts?

First bytes arrive instantly at low bitrate, then ABR ramps up; the next track is pre-buffered for gapless play.

3. Why can recommendations be computed offline in batch jobs?

Discover Weekly refreshes weekly, so heavy ML runs offline and serving is just a precomputed cache lookup.

4. Why are play counts aggregated asynchronously instead of incremented live?

A live UPDATE on the hottest songs is a write hotspot; events stream to a log and counts are window-aggregated.
