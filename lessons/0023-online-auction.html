Design an Online Auction

A bid is a compare-and-set. Get the contention right and the rest is fan-out.

Why this lesson, for your mission: An auction looks simple — post an item, take bids, pick a winner. The staff-level move is to recognize that the entire problem reduces to one hard primitive: accept a bid only if it beats the current max, with zero lost or out-of-order writes. Frame that as an atomic compare-and-set under contention, separate it cleanly from the eventually-consistent read/broadcast path, and you have demonstrated exactly the judgement L6/L7 interviewers probe for.

1 of 8

Phase 1 · 0–5 minClarify the problemPin scope and the few NFRs that will drive every later decision.

Ask before you design

  • “Is this English ascending auction only, or also proxy (max) bids?” — Proxy bidding changes the bid acceptance logic.
  • “Must the auction end exactly at end time, or can it extend on late bids?” — Soft close (anti-sniping) changes the close mechanism.
  • “How real-time must viewers see the highest bid?” — Sub-second updates need a push channel.

Functional Requirements

Three core flows. Anchor the whole design on these and defer everything else.[1]

#Users should be able to…
1Create an auction for an item with a starting price and an end time.
2Place a bid — accepted only if it exceeds the current highest bid.
3View an auction and see the current highest bid in real time.
4Have the auction close at the end time, awarding the item to the highest bidder.

Out of scope (say it out loud, then drop it): search, filtering, sorting, recommendations, payments/settlement, and full bid history.[1]

Non-Functional Requirements

These are the constraints that actually shape the architecture. Lead with consistency — it is the spine of the problem.

NFRTarget / priorityWhy it drives the design
Strong consistency on bidsThe recorded highest bid must always be correct — no lost, duplicated, or out-of-order accepted bidsForces a single serialization point per auction (atomic compare-and-set), not eventual consistency
Real-time price updatesViewers see new highest bid within ~1sPush channel (WebSocket) + pub/sub fan-out, not polling
High read fan-outA hot auction may have 100k+ concurrent viewersReads must not touch the bid-write path; cache + broadcast
DurabilityAn accepted bid is never lost, even on node failureReplicated, persisted store as the source of truth for bids

★ Staff-level signal The split-brain insight to voice early: the write path and the read path have opposite requirements. Bids demand strong, linearizable consistency on a single key. Viewing demands cheap, massively-replicated, eventually-consistent reads. A senior candidate builds one system and tries to make it do both. A staff candidate explicitly draws the seam between them and optimizes each independently.
Check before continuing

Why split the bid-write path from the read/broadcast path?

Bids must be linearizable on one key; views can be stale-but-cheap. Opposite requirements force separate paths.

Bids demand linearizable single-key writes; viewers demand massive cheap fan-out. A shared system trades one requirement off against the other, which is exactly the "senior tries to make one system do both" trap named in the staff callout.

Only estimate the numbers that change a decision. Work them out loud:

The punchline: total write volume is small (~230 bids/s average), but it concentrates on a single row in an auction's final seconds, with a 1000:1 audience watching. Design for per-auction contention and read fan-out, not aggregate throughput.

Interviewer pushback

“Why not a distributed lock around each bid?”

Staff answer: Locks add latency and expiry failure modes. An optimistic compare-and-set on one row (UPDATE … WHERE highest_bid < :amount) serializes bids atomically with no held lock.

Check before continuing

Why does the capacity estimate conclude "shard by auction_id" rather than by bidder_id?

A bid never spans auctions, so the compare-and-set never needs to touch two shards if data is sharded by auction_id — sharding by bidder_id would scatter one auction's contention across shards.

Phase 3 · 10–17 minAPI & data modelLock the contract and the storage shape before drawing boxes.

Core Entities & API

Entities: Auction (id, itemId, sellerId, startPrice, endTime, status, highestBid, highestBidderId, version) · Bid (id, auctionId, bidderId, amount, createdAt) · User (derived from the auth token, never passed in the body).

EndpointPurpose
POST /v1/auctionsCreate an auction. Body: itemId, startPrice, endTime → returns auctionId.
POST /v1/auctions/{id}/bidsPlace a bid. Body: amount. Returns 201 accepted, or 409 if outbid / auction closed.
GET /v1/auctions/{id}Fetch auction state including current highest bid (cache-served).
WS /v1/auctions/{id}/liveWebSocket subscription pushing each new highest bid to the viewer.

Note the bid endpoint returns 409 Conflict on a losing bid — the client learns it was beaten and the user can decide to re-bid. The amount is the only field; the bidder is the authenticated caller.

Data Model

The auction row is the serialization point: highest_bid, status and version live on it so a bid and a close contend on the same key. Money is stored as integer minor units. A transactional outbox row is written in the same transaction as the accepted bid, so "bid committed but broadcast lost" can't happen.

Writes serialize on one auction row; reads and live updates come from Redis and the WebSocket fleet and never touch the bid path. Bids and the close race on the same row, so the database decides the order.

High-Level Design

Trace each FR through the boxes. The seam between write and read paths is visible in the wiring.

ComponentRole
API gateway / LBAuth, routing; terminates HTTP and WebSocket connections.
Bid ServiceThe write path. Owns the atomic compare-and-set against the auction store. Single serialization point per auction.

Flow of a bid: client → API → Bid Service does compare-and-set on the auction row → on success, persist the bid, update cache, publish to pub/sub → Broadcast Service pushes the new high over every open WebSocket → viewers' prices tick up. On failure (someone bid higher first), return 409 and the broadcast never fires.

Interviewer pushback

“Why separate the bid service from the broadcast fleet?”

Staff answer: Writes need correctness and are rare; broadcasts are massive fan-out. Splitting them means a viewer surge can't slow bid acceptance.

The pushback answer is explicit: splitting them means a viewer surge can't slow bid acceptance — merging reintroduces exactly that coupling.

Phase 5 · 27–47 minDeep dives & tradeoffsGo deep where the system breaks; compare alternatives and justify the pick.

Deep Dives

1 · Accepting bids correctly under contention

This is the heart of the problem and where most candidates leak correctness. The requirement: a bid is valid only if amount > current highest, and concurrent bids must not lose updates. That is textbook contention — an atomic read-modify-write on a single key.[1][2] Three ways to get it right:

ApproachMechanismTradeoff
Optimistic concurrency (OCC)Read row + version; UPDATE … SET highest=$amt, version=version+1 WHERE id=$id AND version=$v AND $amt>highest. 0 rows affected ⇒ reject, client retries.[2][3]No locks held; cheap under low contention. Retries spike near close when many bids collide.
Pessimistic lockSELECT … FOR UPDATE on the auction row, compare, update, commit.[2]Always correct; serializes bids per auction. Lock held for the txn → throughput ceiling on a hot item.
Atomic counterRedis Lua script (or DynamoDB conditional write) that checks-and-sets the max in one atomic op.[4]Fastest for celebrity-item bursts; must still durably persist to the source of truth.
Justified pick: OCC as the default — a conditional UPDATE guarded on both version and amount > highest is atomic at the database, lost-update-proof, and holds no locks. For the rare celebrity auction with extreme last-second contention, route that single auctionId through a Redis atomic compare-and-set and stream the accepted bids to the durable store. Either way, the key property is the same: one atomic compare-and-set per bid; losers are rejected, never silently dropped.

2 · Broadcasting the new highest bid in real time

Once a bid is accepted, thousands of viewers must see it within ~1s — but the broadcast must never sit on the write path. The pattern: the Bid Service publishes the new high to a pub/sub channel keyed by auctionId; a fleet of Broadcast Services subscribes and pushes over the WebSocket connections it holds.[1][5] This is the same real-time-updates machinery as live feeds and chat.

ChoiceWhy
WebSocket over pollingBid arrivals are bursty and latency-sensitive; polling 100k viewers per second wastes the read tier.
Pub/Sub between write and fan-outDecouples a single durable write from N delivery sockets across many servers; the write commits in O(1), delivery scales out.
Eventually consistent on readIf a viewer misses a tick, the next bid or a periodic snapshot corrects it. The price display need not be linearizable — only the recorded bid is.

Scaling the socket tier: shard viewers across Broadcast nodes; each node subscribes only to the auctions its connected clients watch. A consistent-hash on auctionId keeps subscriptions cheap.

3 · Closing the auction exactly at end time

The auction must stop accepting bids at endTime and award the item to the highest bidder. Two parts: the trigger and the race.

Trigger — don't poll every row. Scanning all auctions for expiry is wasteful at 10M auctions. Instead use a delay queue / scheduled job: when an auction is created, enqueue a close-event with a visibility delay equal to its duration (e.g. SQS delay, a Redis sorted-set keyed by endTime, or a durable timer/cron worker). At fire time, a close worker flips status = CLOSED and finalizes the winner.[1]
The bid-vs-close race. A bid arriving in the same instant as the close must be unambiguously in or out. Make the close an atomic state transition on the same row the bids contend on: the close worker does a conditional update to CLOSED, and the bid's compare-and-set additionally guards on status = OPEN AND now < endTime. Because both go through the same single serialization point as the bid write, the database decides the order — there is no window for a "bid after close" to slip in. Tie-break by server-received timestamp recorded inside the same transaction, never by client clock.
★ Staff-level signal Naming the close as just another atomic write on the contended key — rather than a separate, racy "stop the auction" action — shows you understand that correctness comes from one serialization point, and that the same primitive that makes bids safe also makes the close safe. That unification is the senior→staff jump.

4 · Read scaling for popular auctions

A viral auction is a classic hot key: one auctionId drawing massive read traffic and a fan-out storm on every bid. Keep the read path entirely off the write path.

TechniqueEffect
Cache the current price in RedisEvery GET hits cache, not the bid store. Updated synchronously on each accepted bid.
Broadcast push replaces pollingActive viewers get pushed updates, so they never re-read; the cache absorbs only cold/first loads.
Hot-key replication / local cacheFor a single mega-auction, replicate its key across cache shards or add a short-TTL in-process cache on the read tier to spread the load.
Local fan-out aggregationA Broadcast node receives one pub/sub message and fans it to all its local sockets — N deliveries cost one cross-service message.

The result: bid writes stay strongly consistent and lock-light on one key, while bid reads scale to millions via cache and push — the two paths never contend.

Interviewer pushback

“How do you close the auction without accepting a late bid?”

Staff answer: The close is just another conditional write on the same row: set status=closed if now ≥ end_time. Bids check status in the same compare-and-set, so there's no race, and a durable delay queue triggers the close.

Wrap-up · 58–60 minClose strongRecap decisions and tradeoffs in 60 seconds; name what you would do next.

Closing Summary (60 seconds)

An online auction needs linearizable bids for each auction under a real-time audience. Each auction row is the single serialization point: bids are an optimistic compare-and-set on the current highest bid and status, and closing is the same conditional write triggered by a durable timer, so late bids can't race it. Accepted bids publish to a per-auction channel that pushes coalesced updates to viewers. Reads never touch the bid row. We shard by auction id (~4 shards at 5k bids/s peak), and at 10× we add shards and broadcast nodes.
