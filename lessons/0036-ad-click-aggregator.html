Design an Ad Click Aggregator

A write-firehose streaming pipeline where every event is billable — accuracy is the whole game.

Why this lesson, for your mission: This is the canonical "streaming analytics" interview. It tests whether you can stand up a windowed-aggregation pipeline (Kafka → Flink → OLAP) and — the staff differentiator — whether you treat clicks as money. Unlike Top-K, where approximation is fine, here a double-counted click is a double-charged advertiser. The senior answer aggregates; the staff answer aggregates exactly once and reconciles against a batch layer.

1 · Functional Requirements

Strip it to the two flows that actually shape the design — the click path and the query path.[1]

#Requirement
1Users can click an ad; we record the click event and redirect them to the advertiser's site.
2Advertisers can query aggregated metrics (clicks per ad) at 1-minute granularity, near real time.
3Advertisers can run time-range queries ("clicks for ad X from 09:00–17:00, hourly") and roll up across minute/hour/day.

Out of scope (say so): ad serving / targeting, billing settlement itself, fraud/bot detection (mention it exists, defer it). Naming these earns breadth credit without spending depth budget.

2 · Non-Functional Requirements

The "-ilities" here are unusually sharp because two of them are in direct tension: accuracy vs. latency.

The core tension to name out loud. A streaming layer gives you seconds of freshness but can drift (late events, processor bugs). A batch layer gives you correctness but minutes-to-hours of lag. You cannot maximize both with one path — which is exactly why the lambda/kappa conversation (Deep Dive 2) is the heart of this problem.

4 · Core Entities & API

Entities: ClickEvent (adId, impressionId, timestamp, userMeta), Ad (adId, advertiserId), AggregateBucket (adId, windowStart, granularity, count).

EndpointPurpose
POST /v1/clicksIngest a click. Body carries adId + signed impressionId; returns 302 redirect to the advertiser URL.
GET /v1/ads/{id}/metrics?from=&to=&granularity=Return aggregated counts for an ad over a time range at minute/hour/day granularity.
GET /v1/advertisers/{id}/metrics?from=&to=Roll up across all of an advertiser's ads (advertiser derived from auth token).

The server-side redirect on POST /v1/clicks matters: routing the click through our processor before the 302 guarantees we capture every click, rather than trusting a fire-and-forget browser beacon.[1]

5 · Data Flow (the streaming pipeline)

Follow one click from tap to dashboard:

  1. Click → user taps ad; browser hits POST /v1/clicks.
  2. Verify & dedup → Click Processor checks the signed impressionId against Redis (Deep Dive 2), then 302-redirects the user.
  3. Stream → event is appended to Kafka, partitioned by adId, and persisted in parallel to an S3 raw lake (the source of truth for reconciliation).
  4. Aggregate → a stream processor (Flink) consumes partitions and maintains tumbling 1-minute windows per adId, emitting a count when each window closes.
  5. Store cooked → rollups are upserted into an OLAP / time-series store (Druid, ClickHouse, Pinot, or Redshift/BigQuery).[1]
  6. Serve → GET /metrics reads pre-aggregated buckets directly — no raw scan.

This is the classic two-tier write, pre-aggregated read shape: the hot path buffers and rolls up; the read path touches only cooked, columnar data.

7 · Deep Dives

Deep Dive 1 — The real-time windowed-aggregation pipeline

The naive design — write raw clicks to a DB and GROUP BY adId, minute at query time — collapses at 10k writes/sec and turns every dashboard load into a full scan.[1] The progression:

ApproachMechanismFreshness
BadOne OLTP DB, GROUP BY at read time.Dies under load.
GoodRaw events to Cassandra; Spark batch job rolls up every ~5 min into OLAP.[1]Minutes.
GreatKafka → Flink tumbling windows → OLAP. Aggregate in flight.[1]Seconds.

Tumbling vs. sliding windows. Use tumbling (fixed, non-overlapping 1-minute windows) — they map cleanly to the "clicks per minute" rollup, each event belongs to exactly one bucket, and they're cheap to checkpoint. Sliding windows duplicate events across overlapping frames and are only worth it for moving-average style metrics, which advertisers don't need here.

Late events. A click may arrive after its window closed (mobile reconnects, processing lag). Configure a watermark + small allowed-lateness so Flink holds windows briefly before finalizing; anything later than that is the batch layer's job to repair (Deep Dive 2). State the bound explicitly — it's a correctness knob.

Deep Dive 2 — Accuracy vs. latency: exactly-once, dedup, and reconciliation

This is where you earn the offer. Clicks are money, so "roughly right" is unacceptable — the looser approximation you'd accept in a Top-K / trending-items design does not apply here. Two failure modes to kill:

(a) Double-counting → dedup with idempotency keys. The ad-placement service mints a unique impressionId per rendered ad and signs (impressionId, adId) with an HMAC.[1] On POST /v1/clicks the processor (1) verifies the signature, (2) checks the impressionId in Redis, (3) if unseen, writes to the log first, then records the id in Redis — that ordering means a crash between the two steps causes a harmless re-write, never a lost click.[1] A duplicate id is silently dropped. At ~1.6 GB/day the key set fits comfortably in a Redis cluster.[1]

(b) Drift / loss → lambda (or kappa) reconciliation. The speed layer can still drift from bugs, very late events, or partial failures. So run a batch layer: periodically re-aggregate the immutable S3 raw lake with Spark and overwrite the OLAP rollups, treating the batch result as the source of truth.[1] Kafka's 7-day retention lets a failed processor replay from its last checkpointed offset rather than losing the gap.[1]

ArchitectureShapeTradeoff
LambdaSpeed (Flink) + batch (Spark) layers, reconciled in OLAP.Two codebases to keep in sync, but maximally robust.
KappaOne stream path; reprocess by replaying the log.Simpler ops; reprocessing huge ranges is slow.
★ Staff-level signal Say the quiet part: "Because each click is billable, I'll spend my correctness budget here, not on freshness." Then propose exactly-once via signed idempotency keys and a batch reconciliation layer — and explicitly contrast it with the approximate counting you'd tolerate in a trending/Top-K system. Naming the accuracy-vs-latency tradeoff and resolving it with lambda/kappa is the move that separates staff from senior.

Deep Dive 3 — The write firehose and hot ads

Two scaling axes. Volume: partition Kafka by adId and run Flink consumers in parallel per partition; the Click Processor is stateless and scales horizontally behind a load balancer.[1] Skew: a viral ad (the "LeBron/Nike" case) overwhelms a single partition.[1] Fix it by salting the key — append a random suffix adId:0..N to spread the hot ad across partitions; Flink pre-aggregates each shard, strips the suffix, and upserts with a SUM so the shards recombine into one correct total.[1] This is pre-aggregation buying you headroom: you reduce 10k events/sec to a handful of per-minute rollup writes before they ever touch the serving store.

Deep Dive 4 — Fast range queries

Reads must be sub-second over arbitrary time ranges. Two levers: columnar storage and pre-rolled time buckets. A columnar/OLAP store (Druid, Pinot, ClickHouse, Redshift, BigQuery) scans only the count column for matching adId/time keys, which is dramatically faster than a row store for aggregations.[1] On top of that, materialize multiple granularities: Flink emits minute buckets in real time, and nightly cron jobs roll those up into hour/day/week tables.[1] A query for "last 90 days" then reads ~90 day-rows instead of 130k minute-rows — the query planner picks the coarsest bucket that satisfies the requested granularity. Pre-aggregation is the recurring theme of this whole design: do the work once on write so reads are trivial.

Check yourself — retrieval practice

Answer from memory before scrolling back up.

1. Why is exactly-once counting non-negotiable here, unlike in a Top-K design?

Clicks map to money; double-counting means double-billing, so approximation is unacceptable.

2. How does the design prevent a single viral ad from overwhelming one partition?

Salting spreads the hot key across partitions; Flink strips the suffix and SUMs the shards back together.

3. What makes sub-second time-range queries possible at this scale?

Reads touch pre-aggregated buckets in a columnar store; the planner picks the coarsest granularity that fits.

4. Why keep a batch layer when the Flink stream layer is already fast?

Lambda architecture: the speed layer gives freshness, the batch layer re-computes from the immutable lake for correctness.
