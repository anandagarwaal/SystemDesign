Deep Dive: ZooKeeper & etcd (Coordination Services)

The small, strongly-consistent brain that lets a fleet of unreliable machines agree on one truth — and the one rule that keeps it from becoming your bottleneck.

Why this lesson, for your mission: Distributed systems constantly need to agree on one fact: who is the leader, what is the current config, which nodes are alive, who holds the lock. At L6/L7 the interviewer wants to see that you reach for a purpose-built coordination service instead of hand-rolling consensus, that you understand why its writes are linearizable, and — critically — that you know to keep it tiny and never treat it as a database. Naming that boundary before you're asked is the staff move.[1]

1 of 5

What it is — the agreement layer

ZooKeeper and etcd are strongly-consistent, replicated key/value stores built for coordination, not bulk storage. They exist to be the one place a distributed system can write a fact and have every node read the same answer, even while machines crash and networks hiccup.[2] Where a normal database optimizes for throughput and large datasets, these optimize for correctness of small, hot metadata under contention: a few megabytes of state that must be right.

They turn a hard distributed-systems problem into a small API. Instead of every team re-implementing consensus, they expose simple primitives — read, write, watch, ephemeral nodes — and solve the genuinely hard part (agreement) underneath.[3] The canonical problems they solve:

ProblemWhat you actually need
Leader electionExactly one node becomes primary; the rest agree and fail over cleanly[3]
ConfigurationOne source of truth for settings that every node sees consistently[2]
Service discoveryA live registry of "who is up and at what address"[2]
Distributed locksMutual exclusion across machines, with the lock released on crash[3]
MembershipWhich nodes are currently alive in the cluster right now[2]

ZooKeeper is the older Java-based service born at Yahoo!, inspired by Google's Chubby lock service.[4] etcd is the newer Go service from CoreOS, best known as the backing store for Kubernetes.[5] Different lineages, near-identical job.

Internals — the data model and its two special node types

The data model: a tiny hierarchical key space

Both expose data as a filesystem-like tree of keys. In ZooKeeper each node is a znode addressed by a path like /services/api/leader, and a znode holds a small blob of data and can have children — it is both file and directory.[3] etcd's model is a flat, lexically-ordered keyspace, but range queries over a prefix like /services/api/ give you the same hierarchical feel.[6] The data is meant to be small: configuration, pointers, registration entries — kilobytes, not gigabytes.

Ephemeral and sequential nodes — the secret sauce

The primitives that make coordination recipes possible are two special node types:

  • Ephemeral nodes exist only as long as the session that created them is alive. When that client's session expires (it crashed or partitioned away), the service automatically deletes the node.[3] This is the magic behind liveness: a registration that disappears the instant a node dies, no garbage collector needed. etcd achieves the same with a lease attached to a key — when the lease expires, the key is removed.[7]
  • Sequential nodes get a monotonically increasing counter appended by the server, so creating /lock/n- repeatedly yields /lock/n-0000000001, ...0002, and so on — a globally agreed order, assigned by the cluster, not the client.[3]

Watches, consensus, and sessions

Watches: notification instead of polling

A client can set a watch on a key; the server pushes a one-time notification when that key changes.[3] This is what makes config and membership reactive: instead of every node polling "did the leader change?" a thousand times a second, they each register a watch and get told the instant it does.[2] etcd generalizes this into a streaming watch over a key range from a given revision, so a client never misses an event between reconnects.[6]

Consensus underneath: linearizable writes via quorum

The reason the answer is always consistent is that every write goes through a consensus protocol that a majority (quorum) of nodes must agree on before it commits.[8] One elected leader sequences all writes; followers replicate them; once a quorum has the write durably logged, it is committed and visible. This delivers linearizability: once a write returns, every subsequent read sees it — there is a single, real-time order of operations.[6]

  • ZooKeeper uses ZAB (ZooKeeper Atomic Broadcast) — a leader-based total-order broadcast protocol purpose-built for it.[8]
  • etcd uses Raft, the understandable-by-design consensus algorithm, for the same guarantee.[6]

You'll go a layer deeper on these in Lesson 107 (Consensus — Raft & Paxos). The key takeaway here: a quorum of (N/2)+1 is required, which is exactly why cluster sizes are odd.

Sessions & heartbeats

A client holds a session with the cluster, kept alive by periodic heartbeats. If heartbeats stop for longer than the session timeout, the cluster declares the session dead and reaps its ephemeral nodes / expires its lease.[3] This timeout is the tuning knob behind every failover: too short and a slow GC pause looks like a death (false failover); too long and real failures take ages to detect. Naming that tradeoff is high-signal.

Why clusters stay small, and the common recipes

Why these clusters stay small (3 or 5 nodes) — and are NOT a database
  • Every write needs a quorum to agree, so adding nodes makes writes slower, not faster — you're paying more round-trips for the same commit.[8] 3 nodes tolerate 1 failure; 5 tolerate 2. Beyond that you add latency, not safety.
  • Reads can fan out to followers, but the whole dataset is held in memory and meant to be small.[3] It is a coordination kernel, not a store for user data, blobs, or high-volume events.
  • The anti-pattern to call out: using ZooKeeper/etcd as a general key/value database. High write volume or large values will saturate the quorum write path and destabilize the very thing your whole system depends on for liveness.[1]

Leader election

Every candidate creates an ephemeral sequential node under /election/. The one with the lowest sequence number is the leader; each other node watches only the node just below it. When the leader's session dies, its ephemeral node vanishes, the next-lowest node's watch fires, and it becomes leader — a clean, herd-free failover.[3]

Distributed lock (ephemeral + sequential)

Same shape: each client creates an ephemeral sequential node under /lock/; the lowest sequence number holds the lock; others wait on the node ahead of them. Because the node is ephemeral, if the lock holder crashes the lock is released automatically — no orphaned lock can freeze the system.[3] That crash-safety is the whole reason you use a coordination service for locking instead of a row in a database.

Service registry / discovery

Each service instance registers itself by writing an ephemeral node (or an etcd key with a lease) at /services/<name>/<instance> with its address. Clients watch the prefix to get a live, self-healing list of healthy instances; a dead instance's entry disappears the moment its session/lease expires.[2][7]

etcd as the Kubernetes backing store

The flagship real-world use: etcd is the single source of truth for a Kubernetes cluster. Every object — pods, deployments, configmaps, secrets — is persisted in etcd, and the API server is the only component that talks to it.[5] Controllers use etcd watches to react to desired-vs-actual state changes; the linearizable store is what makes "the cluster's declared state" coherent. You'll see this from the K8s side in Lesson 104 (Kubernetes).

Why are ZooKeeper and etcd clusters kept to 3 or 5 nodes instead of scaled out wide?

Adding nodes adds more round-trips to reach a quorum on every write, which raises latency without adding write capacity.

In the distributed lock recipe, why must the lock node specifically be ephemeral rather than a plain persistent node?

A persistent lock node would survive its holder's crash and block everyone forever. Tying it to the holder's session means the lock releases automatically on crash.

When NOT to use it, and how this shows up in the interview

Reach for a coordination service when…Reach elsewhere when…
You need leader election or failover[3]You need a general database → Postgres / Cassandra
You need cluster-wide config & membership[2]High write volume or large values → a real store
You need crash-safe distributed locks[3]Best-effort caching / counters → Redis
Small metadata that must be linearizable[6]Massive horizontal scale-out is the goal → no

Adding a coordination service is real operational weight — another quorum cluster to run, monitor, and back up. If a single managed database or a Redis lock with a sane TTL meets the requirement, don't reach for ZooKeeper. The consistency model here is the strong end of the spectrum from Lesson 06 (Replication & CAP): under a partition these systems choose consistency over availability — the minority side stops serving writes rather than diverge.[8]

★ Staff-level signal Seniors say "I'll use ZooKeeper for leader election." Staff candidates frame the boundary in one breath: "I'll put a 3-node etcd cluster on the coordination path — leader election and config — because writes are linearizable through Raft quorum. I'll keep it tiny and out of the request hot path; it is not my database, so user data and high-volume events go to Postgres and Kafka." And they name the failure mode proactively: "the session timeout tunes failover — too short risks false failover on a GC pause, too long delays detection — and under a network partition the minority loses its quorum and stops accepting writes, which is the correct CP choice for coordination."[1] Choosing the purpose-built tool, keeping it small, and refusing to overload it is the simple-by-default judgement the bar rewards.

In the interview

When your design needs a leader, a config store, or service discovery, put a small coordination cluster on the board and justify it in one line ("3-node etcd for leader election; writes are linearizable via Raft quorum").[6] Be ready for the predictable follow-ups: "How does it stay consistent?" (one leader sequences writes; a quorum must agree; that gives linearizability) and "How does the lock release if the holder crashes?" (ephemeral node / lease tied to a heartbeated session). The moment that reads as staff is volunteering the limit: "I'm keeping this off the request path and small — it coordinates, it doesn't store." Don't deliver a Raft lecture unasked; pick the tool, name the boundary, move on.

A team proposes storing all user session data (millions of rows, frequent writes) in their existing etcd cluster instead of adding Redis. What breaks?

Coordination clusters are sized and tuned for small, hot metadata. Loading bulk data onto the same quorum write path slows or destabilizes the coordination duties everything else relies on.

Why do watches scale better than polling for a cluster of a thousand nodes checking "did the leader change"?

Polling costs a request per node per interval regardless of whether anything changed. A watch shifts the cost to a single push, only on an actual change.
