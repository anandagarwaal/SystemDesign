Deep Dive: CDN (Content Delivery Networks)

A planet-spanning cache that puts your bytes a few milliseconds from every user — and the invalidation problem you must respect before you lean on it.

Why this lesson, for your mission: At L6/L7 "I'll put a CDN in front of it" is table stakes. The interviewer wants to hear that you know what actually gets cached, how a request finds the nearest edge (anycast + DNS), why the cache key and Cache-Control headers decide your hit ratio, and the one genuinely hard problem — invalidation — that you must design around rather than wish away. Naming the origin-shield and signed-URL moves before you're asked is the breadth-then-depth signal that reads as staff.[1]

1 of 6

What it is: a read-through cache for the internet

A Content Delivery Network is a globally distributed fleet of caching servers ("edge" servers) placed in data centers close to end users.[1] When a user requests a file, the CDN serves it from the nearest edge instead of forcing the request to travel all the way back to your origin server.[2] The wins are direct: lower latency (fewer network hops, shorter physical distance), less load on your origin (the edge absorbs most traffic), and lower bandwidth cost (origin egress is reduced to cache fills).[1]

The mental model: a CDN is a read-through cache for the internet, sitting between users and your origin, replicated to dozens or hundreds of locations. It pairs naturally with object storage — your origin is often an S3 bucket (Lesson 45), and the CDN fans those objects out worldwide. It is one of the standard boxes from the key-technologies tour (Lesson 09).

Geographic proximity cuts latency dramatically, and replicas mean no single PoP failure kills the whole CDN — users route to a nearby alternative.

How requests reach the nearest edge and content freshness

Cache hit, miss, and the origin pull

The request lifecycle is the thing to know cold:

  • Cache hit: the edge already holds a fresh copy of the object and serves it immediately. No origin contact. This is the happy path you optimize for.[2]
  • Cache miss: the edge has no fresh copy, so it does an origin pull — fetches the object from your origin, stores it locally per the caching rules, then serves it. The next user in that region gets a hit.[2]

Your single most important metric is the cache hit ratio: the fraction of requests served from the edge. A high ratio means the CDN is doing its job; a low ratio means you're paying for the CDN and still hammering your origin.

Push vs pull CDNs

ModelHow content arrivesBest for
Pull (lazy)Edge fetches from origin on the first miss, then caches it[2]Large, frequently-updated catalogs; the default and simplest to operate
Push (eager)You upload content to the CDN ahead of demandLarge files / big launches where you can't afford the first-request miss penalty

Most designs use pull — you point the CDN at your origin and let it fill on demand. Reach for push when a small set of large assets must be warm before a traffic spike (a game patch, a video premiere).

How requests find the nearest PoP: anycast + DNS routing

The routing magic happens before your bytes move. Two mechanisms dominate:

  • DNS-based routing: when the client resolves your CDN hostname, the CDN's authoritative DNS returns the IP of an edge close to the user (inferred from the resolver's location).[2] This is how Akamai-style networks steer you to a nearby PoP.
  • Anycast: many PoPs announce the same IP address via BGP; the internet's routing naturally delivers the packet to the topologically nearest PoP.[6] Cloudflare leans heavily on anycast, which also makes it resilient — if one PoP fails, BGP reroutes to the next.
Check yourself

What triggers an origin pull?

A miss means the edge doesn't have a fresh copy, so it pulls from origin, caches, and serves.

When would an edge NOT have a fresh copy?

Why does anycast routing make a CDN more resilient than DNS routing alone?

DNS routing depends on the resolver updating records — slow failover. Anycast is automatic at the IP routing layer: a PoP goes down, BGP reroutes instantly.

If a PoP with an anycast IP goes offline, what does BGP do? What does a DNS client do?

Cache keys, TTL, and freshness headers

Cache keys: what counts as the same object

The edge decides whether two requests are for the same cached object using a cache key — by default the URL (host + path), but it can include query strings, specific headers, or cookies.[3] This is a quiet source of bugs: if you key on the full query string, then ?utm_source=x and ?utm_source=y become two cache entries for one identical image, fragmenting your cache and tanking the hit ratio. The staff move is to normalize the cache key — strip irrelevant query params and cookies so identical content collapses to one entry.[3]

TTL, Cache-Control, and ETag: how freshness is decided

How long an edge keeps an object is governed by HTTP caching headers from your origin, not magic:

HeaderRoleInterview-relevant detail
Cache-ControlSets the TTL / cacheabilitymax-age=N sets freshness seconds; no-store forbids caching; private blocks shared edge caching[4]
TTLTime-to-live for the entryAfter it expires the entry is "stale" and must be revalidated or refetched[4]
ETagVersion fingerprint of the objectOn a stale entry the edge sends If-None-Match; origin replies 304 Not Modified if unchanged — saves the body transfer[5]

The pattern to articulate: long TTLs maximize hit ratio but make content stale; short TTLs keep things fresh but increase origin pulls. Revalidation with ETags is the middle ground — it confirms freshness cheaply (a 304 with no body) instead of re-downloading the whole object.[5]

Check yourself

Why does an over-inclusive cache key wreck your hit ratio?

Keying on irrelevant params (e.g. utm tags) splits one object into multiple cache entries, fragmenting the cache.

If the cache key includes the full URL with tracking params, how many entries for one actual image?

What tradeoff does raising the TTL on static assets create?

Long TTLs mean fewer origin pulls (good) but also older cached copies stay on edges longer (bad for freshness).

If you update an image and the edge still has it cached for 7 more days, what does the user see?

4 of 6

Cache invalidation, versioning, and private content

Cache invalidation and purge — the genuinely hard part

"There are only two hard things in computer science: cache invalidation and naming things." A CDN is cache invalidation at planetary scale. You have a few levers:

  • TTL expiry — simplest: just let entries go stale and refetch. No active purge, but you tolerate up to max-age seconds of staleness.[4]
  • Explicit purge / invalidation — you tell the CDN to evict an object (or path prefix) now. It is eventually consistent across hundreds of PoPs and can be slow / rate-limited, which is why you don't rely on it for every write.[7]
  • Versioned URLs (cache busting) — the pro move: bake a content hash into the filename (app.3f9c2.js). New content = new URL = guaranteed fresh, and you set an effectively infinite TTL on the immutable asset. You never purge; you just stop referencing the old URL.[4]

Origin shield and signed URLs

With hundreds of PoPs, a cold cache or a purge can trigger a thundering herd — many edges pulling the same object from your origin at once. An origin shield is a designated intermediate caching layer that all PoPs pull through, so the origin sees at most one request per object and your hit ratio stays high.[8]

For private content you don't want world-readable, use signed URLs / signed cookies (a.k.a. pre-signed URLs): a time-limited, cryptographically signed link that the edge validates before serving — so a paywalled video or a private upload is cacheable yet access-controlled.[9]

Check yourself

Which approach guarantees users get updated content instantly when you change it?

A new content-hashed URL is guaranteed-fresh (it's a new cache entry). Purge is only eventually consistent across PoPs.

If you're in a hurry for users to see the new version, which is instant?

Why does an origin shield help when many PoPs have a cold cache (e.g. after a purge)?

Shield collapses the thundering herd: many PoPs request → one PoP request to origin → shield caches → all PoPs hit the shield cache.

If 200 edges all miss and try to fetch the same object, what breaks without a shield? What does the shield do?

Where a CDN pays off, and where it doesn't

CDNs shine for static, cacheable content (images, CSS/JS bundles, video segments). Truly dynamic, per-user responses can't be cached the same way, but modern CDNs still help by terminating TLS at the edge, keeping warm connections to origin, and routing over their optimized backbone.[1]

PatternHow the CDN earns its place
Static assetsImages, CSS, JS bundles served from edge with versioned URLs and long TTLs — the bread-and-butter use[1]
Video streamingHLS/DASH chop video into small segments + a manifest; each segment is a cacheable static file, so the CDN scales millions of viewers off a few origin fills[10]
DDoS absorptionThe distributed edge soaks up volumetric floods far from origin; anycast spreads attack traffic across many PoPs[6]
Reach for a CDN when…It buys you little / hurts when…
Static, cacheable, read-heavy content at global scale[1]Highly personalized, per-user dynamic responses with near-zero reuse
Latency matters and users are geographically spreadAll your users sit in one region next to your origin already
Large media / video segments hit by many viewers[10]Strong read-after-write needs — purge is eventually consistent, not instant[7]
You want edge DDoS absorption and origin offload[6]Rapidly mutating data where staleness is unacceptable and TTLs would be near-zero
Check yourself

When is a push CDN worth the extra operational work over the default pull model?

Push pre-warms the edges, so nobody eats the first-request miss. Pull fills on demand and is simpler for big, churning catalogs.

Push costs you an upload step. What does it buy on the very first request for an object?

Why does a per-user dynamic response get almost nothing from edge caching, even though it still travels the same network?

Caching pays off through reuse: one origin fill amortized over many hits. A response only ever valid for one user has a reuse count of one. The edge still helps on TLS termination and backbone routing, just not on hit ratio.

What is the actual currency of a cache? Count how many times one stored object gets served.

Video streaming and in the interview

Segmenting is why a CDN is non-negotiable in a design-YouTube interview (Lesson 33): you transcode once, segment with HLS/DASH, store segments in object storage, and let the CDN deliver them globally. Origin bandwidth stays flat while viewers scale.

When you put a CDN on the whiteboard, justify it in one line ("serve static assets and video segments from the edge to cut latency and offload origin"), then be ready for the predictable follow-ups: "How does a request reach the nearest edge?" (anycast and/or DNS routing), "How do you keep content fresh?" (TTL + Cache-Control, ETag revalidation, versioned URLs for instant updates), and "How do you serve private content?" (signed URLs).[9] Volunteering the origin-shield and cache-key normalization shows hands-on depth.

★ Staff-level signal Seniors say "add a CDN." Staff candidates reason about the hit ratio and its enemies in one breath: "I'll normalize the cache key so tracking params don't fragment the cache, set long TTLs with versioned URLs so I never purge for static assets, and add an origin shield to stop a thundering herd on cold start."[8] And they name invalidation as the hard problem proactively: "purge is eventually consistent across PoPs, so for anything that must be instantly fresh I bust the cache with a new URL rather than relying on purge."[7] Knowing that a CDN is just a read-through cache — with the same staleness/consistency tradeoffs you'd reason about anywhere — and not over-explaining what a cache is, is the simple-by-default judgement the bar looks for.

What happens on a CDN cache miss at an edge PoP?

What actually constrains you from setting all CDN TTLs to 1 year for maximum hit ratio?

Eventual staleness is the price of high cache hit ratio. You trade off freshness for hits — which is why versioned URLs and selective purges exist.

If you set TTL to one year and update your homepage tomorrow, what happens to the cached version?

Why should you proactively normalize cache keys (strip utm params) instead of keeping them as-is?

Each unique param becomes a separate cache entry for identical content — one image becomes 10 entries if you key on utm_source variation.

If image.png?utm_source=facebook and image.png?utm_source=twitter are two cache keys, how many caches are you paying for?
