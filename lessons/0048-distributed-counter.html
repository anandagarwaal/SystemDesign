Design a Distributed Counter (Likes at Scale)

Counting a billion likes a day when a single celebrity post can take tens of thousands of writes per second into one number — and the count is allowed to be a little behind.

Why this lesson, for your mission: A "like counter" sounds like a one-liner — UPDATE posts SET likes = likes + 1 — and that naive answer is exactly the trap. The whole L6/L7 interview is about what happens when one row gets hammered (the hot key) and how you trade strict consistency for throughput. Staff candidates name the contention problem before the interviewer does, reach for write sharding and aggregation instead of synchronous increments, and say out loud "this count is eventually consistent and that's fine."[1]

Phase 1 · 0–5 minClarify the problemPin scope and the few NFRs that will drive every later decision.

Ask before you design

  • “Must counts be exact, or is approximate acceptable?” — Exactness decides between idempotent aggregation and probabilistic counters.
  • “Can a user like a post only once?” — Per-user uniqueness requires a like record and idempotency.
  • “How fresh must counts be for other viewers?” — Seconds of lag allows async aggregation and caching.

Functional Requirements

Keep the core list to three. This is a counting service, not a social network — replies, notifications, and the feed itself are out of scope.

We own one thing: returning a number per (postId, metric) at scale. Likes, views, retweets, and reactions are all the same problem — a monotonic counter.[1]

Non-Functional Requirements

This system is defined by its NFRs, not its features. State the target and the priority order.

The key tension: a like is a tiny write, but they all collide on the same key for a popular post, and reads outnumber writes by orders of magnitude. Capacity Estimation

Only compute numbers that change a decision. Two matter here: the per-key write rate (does one row melt?) and the read/write skew (do we cache?).

  • Aggregate writes: ~1B likes/day ≈ ~12K likes/sec average, with peaks of 5–10× ⇒ ~50–100K write QPS globally. Easy to spread across a sharded store — aggregate throughput is not the problem.
  • Hot key: a viral post during a peak moment can take tens of thousands of likes/sec onto one postId. A single row / single Redis key serializes those increments — this is the entire problem. Implication: shard the counter (Deep Dive 1).
  • Read/write skew: every feed render reads many counts; reads can be 100×–1000× writes ⇒ millions of read QPS. Implication: reads must hit a cache, never a contended write row.
  • Storage: a counter is ~tens of bytes per (postId, metric). Even billions of posts is a few hundred GB — trivial. The count value is small; the write rate onto it is what hurts.
Design implication: you never scale for storage and rarely for aggregate QPS — you scale to defeat per-key write contention and to serve reads from cache.

API

Derive userId from the auth token, never the body. The write is a command (like/unlike), not a raw "+1", so the server can dedup it.

  • POST /v1/posts/{id}/likes — body { }; user from JWT. Idempotent: liking twice is a no-op. Returns 202 Accepted (write is async-aggregated).
  • DELETE /v1/posts/{id}/likes — user from JWT. Records an unlike; also idempotent.
  • GET /v1/posts/{id}/counts?metrics=like,view — returns the (eventually consistent) counts. Cache-served, may be a few seconds stale.
  • POST /v1/posts/{id}/views — fire-and-forget; feeds the distinct-viewer estimator (HyperLogLog, DD3).

Data Model

Three kinds of state with three consistency needs. The like relation (who liked what) is exact and durable — it is the idempotency source. The count is a derived, sharded aggregate that may lag. Distinct viewers are a probabilistic sketch. The load-bearing key choice is (post_id, metric, shard) with a per-post shard_count: cold posts use one shard, hot posts are split without changing any other table.

Phase 4 · 17–27 minHigh-level designA simple end-to-end design that satisfies every functional requirement.

Data Flow

This is a write-aggregation pipeline, the same shape as an ad click aggregator: high-rate events in, a counter out. The trick is to never apply each event to durable storage synchronously.[1]

The life of one like:
  • 1. Client POSTs a like → API service authenticates, builds a dedupKey = (postId, userId), and emits a LikeEvent to a log (Kafka), partitioned by postId.
  • 2. A stream processor (or Redis layer) dedups per user and aggregates events into per-shard deltas over a short window.
  • 3. Aggregated deltas are flushed to the durable counter store (incrementing one of N shards for that post).
  • 4. On read, the cache returns the post's count; on a miss it sums the N shards and re-caches. Done — millions of reads, near-zero contention.

Writes: conditional insert into user_likes makes the like idempotent, then an event flows through Kafka and Flink, which adds batched deltas to a random shard. Reads: the cached total is served; on a miss the service sums the shards and re-caches. The aggregator can also push fresh totals into the cache after each window.

High-Level Design

Two deliberately separated paths: a thin async write path (event → dedup → aggregate → durable shard) and a fat cached read path (cache → sum shards on miss).

Why async aggregation, not synchronous +1: a synchronous increment couples your write throughput to the durable store's per-row lock and round-trip latency. Buffering in a log and aggregating turns thousands of tiny increments into one batched delta — the DB sees a trickle, not a flood. This is the senior→staff move and the heart of every deep dive below.[1]

Deep Dives

Deep Dive 1 — The hot key: single-row contention & write sharding

One postId = one logical counter = one physical row or key. Tens of thousands of likes/sec all do count = count + 1 on that one place. Whether it's a SQL row lock, a Cassandra partition, or a single Redis key, every increment serializes behind the last — throughput collapses to what one shard can do, and the partition becomes a hotspot.[2]

The fix is the canonical sharded / distributed counter pattern: split the logical counter into N sub-counters (postId:shard0 … postId:shardN-1). Each write picks a random shard and increments only that one; a read sums all N shards.[2]

ApproachWriteReadVerdict
Single counterOne contended row — serializesOne cheap readMelts under a hot key
N sharded sub-countersIncrement a random shard — N× the write parallelismSum N shards (or read a cached total)The standard answer[2]
Adaptive shardingGrow N only for hot postsSum a variable NBest for skew; more bookkeeping
★ Staff-level signal Pick N for the hot case, not the average. The trade is read cost vs write contention: large N spreads writes but makes reads sum more shards. The staff move is adaptive — keep N=1 for the long tail of cold posts and split a counter only once it gets hot, so you don't pay summing cost on the 99% of posts nobody touches.[2] Naming "this is a hot-key problem and I'll shard the write, sum on read" before the interviewer pushes is the whole signal.

Deep Dive 2 — The write pipeline: aggregation vs synchronous increments vs Redis flush

Sharding fixes contention but you still choose how increments reach durable storage. Three options, in increasing sophistication.[1]

ApproachHowTrade-off
Synchronous DB +1Each like writes the store inline on the requestSimple; couples QPS to per-row latency; melts on hot keys even when sharded
Redis INCR + periodic flushAtomic in-memory increment; a job flushes Redis totals to the DB every few seconds[2]Blazing fast; durability risk — un-flushed counts vanish if Redis dies
Log + stream aggregationKafka buffers events; Flink dedups & sums per window, flushes deltas[1]Durable, replayable, decoupled; more infra, seconds of lag

Redis INCR is atomic so it sidesteps the read-modify-write race, and it's the fastest path — but Redis is memory-first, so a crash between flushes loses the delta. You mitigate with AOF persistence, replicas, and frequent flushes, but you can't fully escape the durability gap.[2] The log + Flink path makes the event stream itself the source of truth: if the aggregator dies, you replay from the last committed Kafka offset and recompute, so no count is lost.[1]

★ Staff-level signal There is no single right answer — there's a right justification. For a pure like count where a tiny loss is survivable, Redis INCR + flush is the simple-by-default pick. For counts feeding billing or analytics where exactness matters, the Kafka+Flink pipeline's replayability and exactly-once earns its complexity.[1] Stating that durability requirement first, then choosing, is the staff behavior — see the ad click aggregator for the exactly-once version.

Deep Dive 3 — Idempotent likes & approximate distinct counts

Likes must be idempotent. A double-tap, a client retry, or an at-least-once Kafka redelivery must not add 2. A raw "+1" command can't be deduped; a state command keyed by (postId, userId) can. Keep a set/bitmap of who liked: if (postId, userId) is already present, the like is a no-op; unlike removes it. This makes like/unlike convergent regardless of retries or reordering.[1]

Distinct counts are different. "Unique viewers" needs cardinality, not a sum — and storing every viewer's id to dedup exactly costs memory proportional to the audience. For billions of views that's prohibitive. Use a HyperLogLog: a probabilistic structure that estimates distinct cardinality in a few KB with ~1–2% error, mergeable across shards.[2] See data structures for big data for how HLL and Count-Min Sketch trade exactness for memory.

Exact vs approximate — pick per metric:
  • Likes → exact, idempotent, dedup set keyed by user. People notice if a like is lost.
  • Unique viewers → HyperLogLog estimate. Nobody can tell 1,000,000 from 1,012,000, and you save gigabytes.[2]
  • Total views → a plain sharded counter (DD1); over-counting a few is harmless.
★ Staff-level signal Matching the data structure to the tolerance of the metric is the staff insight: exact-and-idempotent where users would notice, probabilistic where they wouldn't. Proposing a HyperLogLog for unique viewers unprompted — and knowing it's mergeable so each shard keeps its own and you union them on read — separates breadth-only candidates from depth.[2]

Deep Dive 4 — Eventual consistency & read-time aggregation

Reads dwarf writes, so they must come from cache, not from summing live shards every time. The flow: read the cached total; on miss, sum the N shards, cache it with a short TTL, return it.[2] Between flushes the cached number lags reality by seconds — that's the eventual consistency you negotiated up front.[3]

Read strategyHowTrade-off
Sum shards per readAlways read N sub-counters and addAlways fresh; expensive at millions of QPS
Cache total, short TTLServe cached sum; recompute on TTL expiry/missCheap; bounded staleness — the standard pick
Push total on flushAggregator writes the summed total to cache each windowFreshest cache; couples read cache to write pipeline
The "monotonic" guarantee: users tolerate a count being behind, but a count that jumps down then back up looks broken. Make the cached value non-decreasing for likes (only replace if the new sum is ≥ old), and reconcile real unlikes through the same pipeline. For the viewer's own like, return an optimistic incremented value locally so their action feels instant while the true count converges.[1]
★ Staff-level signal The staff framing is "read-your-own-write for the actor, eventual consistency for everyone else." The person who clicked like must see it increment immediately (optimistic UI); a stranger refreshing can be seconds behind and nobody cares. Explicitly separating those two consistency requirements — and only paying for strong consistency where a human would notice — is exactly the L6/L7 judgement.[3] See common patterns for caching and CQRS read/write split.

Wrap-up · 58–60 minClose strongRecap decisions and tradeoffs in 60 seconds; name what you would do next.

Closing Summary (60 seconds)

A distributed counter separates idempotent recording from aggregation. A like writes a per-user record keyed by (postId, userId), so repeats are no-ops, and emits an event to Kafka. A stream aggregator batches increments into sharded counters, and hot posts get more sub-counters to avoid row contention. Reads come from a cache, summing shards on a miss. The actor sees their like immediately with optimistic UI; everyone else is seconds behind. HyperLogLog handles approximate unique viewers. At 10× we add partitions and adaptive shards.

Why can't a raw "+1" command be made idempotent on its own?

A raw increment has no key to dedup against; a state command keyed by (postId, userId) does.

Reread Deep Dive 3's opening paragraph.

Why does the actor who clicked "like" see it update instantly while everyone else sees it seconds later?

Optimistic UI gives the actor an immediate local increment; the shared cached total converges for everyone else without anyone paying for strong consistency they don't need.

What determines whether a metric gets exact tracking versus a probabilistic estimate?

Likes are exact because people notice a missing like; unique viewers are approximate because nobody can tell 1,000,000 from 1,012,000.
