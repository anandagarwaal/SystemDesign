Choosing a Data Store: Case Studies

Five real migrations — Discord, Uber, Figma, Notion, Stack Overflow — read as answers to the same four questions, so you can borrow the reasoning instead of the product name.

Why this lesson, for your mission: Lesson 124 gave you the four-question framework. This lesson pressure-tests it against what real companies actually did, including two who moved within a category and two who refused to move at all. The staff-level skill is not knowing that Discord runs ScyllaDB — it's being able to say which question drove them there, and whether your system's answer to that question is the same. A candidate who cites an outcome sounds well-read; a candidate who cites the constraint behind it sounds like someone who has made the call.
You should already know: the four questions from Choosing a Database (access pattern → consistency → scale & shape → source of truth vs. derived view), plus partition keys, B-tree vs. LSM storage, and replication. If any of those is fuzzy, read that lesson first — this one assumes all four.

How to read a migration story

Predict first. Discord stores messages in ScyllaDB. Uber runs MySQL. Figma runs Postgres. Stack Overflow runs SQL Server. Before reading on: if all four are serving enormous traffic successfully, what does that tell you about the question "which database is best at scale?"

It tells you the question is malformed. Each of those picks is the output of a different workload, a different failure they hit first, and a different team's operating experience. Copy the output without the input and you inherit someone else's constraints instead of solving your own.

So read every migration story as four separate facts, kept apart:

AskWhy it matters
What actually broke? Not "it didn't scale" — the specific ceiling: IOPS, GC pauses, vacuum, connection count, a query shape.This is the only part that transfers. If you don't have that ceiling, the migration doesn't apply to you.
Did the category change, or just the engine? Cassandra → ScyllaDB is the same category; Postgres → Redis is not.Engine swaps are tuning. Category swaps mean the access pattern or consistency answer changed.
What did they give up? Every migration pays: joins, transactions, a rewrite, months of engineer time.A story told without a cost is marketing, not engineering.
What could they operate? Existing in-house expertise is a real input, not an excuse.This is the "fifth question" you'll meet in chunk 4 — the one frameworks usually leave out.
★ Staff-level signal Senior candidates name-drop outcomes ("we'd use Cassandra, that's what Discord does"). Staff candidates name the ceiling first and let the product fall out of it ("this is an append-heavy per-channel range scan with no cross-row transactions, so a wide-column store keyed by channel fits; Cassandra or ScyllaDB both work"). Same conclusion, completely different signal — because the second one survives the interviewer changing the requirements.
Check yourself

When reading a company's migration story, which detail actually transfers to your own design?

A ceiling is a testable claim about a workload — you can check whether your workload has it. A product name is just the output of someone else's constraints.

Reread the first row of the table — what does "not 'it didn't scale'" point at?

Discord, Uber, Figma and Stack Overflow all serve enormous traffic on four different databases. Why does that make "which database is best at scale?" the wrong question?

"Best" is only meaningful relative to a workload. Four different workloads with four different first-failures produce four different right answers, and every one of them is defensible.

Think about what "best" would have to mean for it to have one answer across four different workloads.

2 of 6

Discord — when the engine is wrong but the category is right

Discord stores trillions of messages. By early 2022 that lived on a 177-node Cassandra cluster, and the pain wasn't storage capacity — it was operational toil: frequent pages, unpredictable latency, and maintenance work that grew with the data [1].

Run the four questions on their message workload and you get the category immediately:

QuestionDiscord's answer
Access pattern"Give me the last N messages in this channel, newest first" — a range scan inside one partition. Never a join, never a global query.
ConsistencyMessages are append-only and independent; two sends never conflict on the same row. No transaction needed.
Scale & shapeUnbounded, append-heavy, write-dominated — the textbook LSM-tree workload.
Truth vs. derivedSource of truth. Losing a message loses a fact.

That's a wide-column store keyed by (channel_id, bucket) with message_id as the clustering key — partition for locality, sort for the range scan. The category was right in 2017 and still right in 2022.

What actually broke

  • Hot partitions. A channel with a few friends and a channel with hundreds of thousands of people are the same shape of key but differ by orders of magnitude in traffic. One hot partition drags its node's latency up, and the node falls further behind the harder it tries [1].
  • GC pauses. Cassandra runs on the JVM; garbage-collection pauses showed up directly as latency spikes, and the team spent real time tuning heap and collector settings [1].
  • Compaction backlog. Nodes fell behind on compaction, so Discord ran a "gossip dance" — pulling nodes out of rotation so they could catch up without serving traffic [1].

Read that list again: none of those are category problems. Not one says "a wide-column store is wrong for chat." They all say "this implementation of a wide-column store costs too much to operate." So the fix was an engine swap, not a redesign — ScyllaDB, same data model, written in C++ with no GC and a shard-per-core architecture. Result: 177 nodes → 72 nodes, historical message reads from 40–125 ms p99 down to 15 ms p99, inserts from 5–70 ms to a flat 5 ms [1].

And the hot-partition problem — the one that was a data-model problem — wasn't fixed by the new engine at all. They fixed it separately with request coalescing in their data service: when many users ask for the same row at once, only one query reaches the database [1]. Different problem, different layer, different fix.

Check yourself

Why does Discord partition messages by channel and sort by message id?

Partition key gives locality (all of a channel's messages on one node); clustering key gives order, so "newest N" is a contiguous read rather than a sort.

Look at the access-pattern row of the table — what exactly does a client ask for?

GC pauses, compaction backlog and maintenance toil pushed Discord off Cassandra. Why did that not mean the wide-column category was the wrong choice?

The access pattern, key design and consistency need were unchanged — they carried straight over to ScyllaDB. A JVM pause is a property of the runtime; compaction tuning is a property of the engine. Neither says anything about whether a partitioned, sorted log fits chat.

Ask which of the three problems would disappear if you rewrote the same design in C++, and which would not.

Discord's hot-partition problem survived the engine migration and was fixed with request coalescing instead. What does that tell you about where hot partitions actually come from?

If one key gets a thousand times the traffic of another, every store that routes by that key sends that traffic to one place. Changing engines moves the problem; changing the key, adding a bucket, or deduplicating the reads in front of it solves it.

Would a busy channel still be a busy channel on a different wide-column engine?

3 of 6

Uber — when the category is right and the internals decide

Uber moved its core data off Postgres and onto MySQL [2]. That headline gets cited constantly as "Postgres doesn't scale," which is not what happened. Both are relational stores; the category never changed. What changed was which engine's internals matched a write-heavy workload with many secondary indexes.

What Uber hitThe mechanism
Write amplificationPostgres rows are immutable: an UPDATE writes a new tuple, and every secondary index must be updated to point at it — even indexes on columns that didn't change. With many indexes, one field update fans out into many writes [2].
Index layoutPostgres secondary indexes point at a physical on-disk location (the ctid). InnoDB's secondary indexes point at the primary key value instead, so moving a row only touches the primary index [2].
Replication costPostgres ships physical WAL changes, so all that index churn crosses the network to every replica. MySQL's logical replication ships "change the timestamp for row X" and lets the replica derive its own index updates — far more compact [2].
ConnectionsPostgres forks a process per connection, which is expensive in memory and IPC and struggles past a few hundred active connections; MySQL's thread-per-connection model reaches roughly 10,000 [2].

Notice the shape of that list. Rows 1–3 are all the same fact seen three times: Postgres ties secondary indexes to physical row location, so a row that moves drags its indexes with it, and the WAL carries the whole mess to the replicas. One design decision inside the storage engine, amplified by a workload with many indexes and a high update rate.

What this does and doesn't license you to say.
✅ "For an update-heavy table with many secondary indexes, Postgres's write amplification is a real cost — Uber hit it hard enough to migrate."
✅ "If the workload were insert-mostly with few indexes, that finding wouldn't apply."
❌ "Postgres doesn't scale." Figma and Notion, in the next chunk, run enormous Postgres deployments — because their first failure was somewhere else entirely.
A finding is scoped to the workload that produced it. Stripping the scope is how a good engineering post turns into a bad interview answer.
★ Staff-level signal Uber's case is the best illustration of why database internals are worth knowing. At senior level you compare products on a feature table. At staff level you can say "this table takes 40 writes per update because of how secondary indexes are stored" — which is a statement an interviewer can check, and which points straight at fixes (fewer indexes, a covering index, a different engine) rather than just a different logo.
Check yourself

Why did updating one field cost Uber many writes on Postgres?

Immutable rows plus indexes that store physical locations means the update fans out to every index, including ones on unchanged columns.

Look at what Postgres does to a row on UPDATE, then at what the indexes were pointing at.

How does InnoDB's secondary index design avoid that fan-out?

One level of indirection: the secondary index names the row logically, so a row that moves physically only needs the primary index updated.

What does a Postgres index point at, and what does InnoDB's point at instead?

Figma and Notion run huge Postgres deployments while Uber migrated away from it. Why are both decisions correct?

Uber's binding constraint was write amplification on heavily-indexed, frequently-updated rows. Figma's and Notion's were single-node capacity and vacuum — problems sharding solves without leaving Postgres. Same product, different bottleneck, different right answer.

Name the specific thing that broke first in each case, then ask whether the other company had that thing.

4 of 6

Figma and Notion — the fifth question: what can you operate?

Two companies, same era, same problem shape: one enormous Postgres instance holding everything, growing past what a single node could serve. Both refused to change category. Both sharded Postgres instead. Their reasoning is the part the four questions don't capture.

Notion — forced by vacuum, sharded by workspace

Notion's monolith had survived "five years and four orders of magnitude of growth" before it started failing in a very specific way: the Postgres VACUUM process stalled and stopped reclaiming disk, which put them at risk of transaction ID wraparound — the safety mechanism where Postgres halts all writes rather than risk corruption [3]. That's not a gradual slowdown you can tune around; it's a wall with a date on it.

Shard key: workspace ID. Chosen because every block belongs to exactly one workspace and users query within a single workspace — so almost no query has to cross shards, and distributed joins (expensive, and with weak transactional guarantees across hosts) mostly disappear [3]. The layout: 480 logical shards over 32 physical databases, 15 logical schemas each. 480 was picked for its divisors — 2, 3, 4, 5, 6, 8, 10, 12, 15, 16, 20, 24, 30, 32, 40, 48, 60, 80… — so future growth can redistribute logical shards without having to double the hardware [3].

Figma — vertical first, then horizontal, and a deliberate "no" to distributed SQL

Figma's database stack grew nearly 100× since 2020, from a single Postgres instance on AWS's largest instance type [4]. They bought runway first by vertical partitioning — splitting groups of related tables (files, organizations) onto separate databases — which is cheap, fast, and requires no application rewrite [4]. Only then did they build horizontal sharding, shipping the first sharded table in September 2023, roughly nine months in, with ten seconds of partial availability at failover [4].

Two design choices worth stealing:

  • Colos. Tables that share a shard key and physical layout are grouped together, which preserves cross-table joins and full transactions as long as a query stays within one shard key [4]. Sharding usually costs you joins; colocation buys most of them back.
  • Multiple shard keys, not one. Rather than force every table onto one key, they used UserID, FileID and OrgID — because almost every table at Figma naturally belongs to one of those [4]. Sharding follows the access pattern; the access pattern isn't uniform, so the key shouldn't be either.

They explicitly evaluated CockroachDB, TiDB, Spanner and Vitess and said no. The reasons were not technical inferiority: a complex data migration across two different stores, months of runway left, and deep in-house expertise in running RDS Postgres reliably. They chose, in their words, "known low-risk solutions over potentially easier options with much higher uncertainty" [4].

★ Staff-level signal That last paragraph is the fifth question, and it's the one junior answers never include: what can this team actually operate, and what does the migration cost against the runway we have? A technically superior store your team has never run, adopted under time pressure, during a live migration, is often the higher-risk choice. Saying that out loud in an interview — "distributed SQL would fit the requirements, but I'd shard the store we already know how to run, because the migration risk dominates here" — reads as senior judgement, not as ignorance of CockroachDB. The trap is using it as a blanket excuse; it's an argument about this migration's risk against this deadline, not a permanent veto on learning new things.
Check yourself

Why did Notion shard by workspace ID?

The shard key follows the access pattern: pick the boundary that queries naturally never cross, and cross-shard joins mostly stop existing.

What does a Notion user's query touch — one workspace, or many at once?

What did Figma do before building horizontal sharding, and why?

Vertical partitioning is cheap and needs no application rewrite, so it buys time to build the harder thing properly.

Which change is easier: moving whole tables to a new database, or splitting one table across many?

Figma judged CockroachDB and Spanner technically capable and still chose to shard Postgres themselves. Why can that be the lower-risk decision rather than the lazy one?

Risk is the product of unfamiliarity, migration complexity and time pressure. Running an unfamiliar store during a live cross-store migration with months of runway left compounds all three; sharding a store you already debug well at 3am compounds none of them.

Count what a team has to learn and move at once in each option, then weigh it against the runway they had.

Stack Overflow — the counterexample that keeps you honest

Every case so far involved outgrowing something. This one is the control group. In 2016 Stack Overflow served the entire Q&A network — one of the most-visited sites on the internet — from two SQL Server clusters, each a handful of machines, and on one sampled day ran 504,816,843 SQL queries [5].

TierWhat it isRole
SQL Server (2 clusters)384–768 GB RAM, 4–6 TB PCIe SSD, master + local replica + a remote async replica [5]Source of truth. Relational, transactional, joins intact.
Redis~256 GB master/replica pair plus dedicated machines; ~160 billion ops/month at under 2% CPU [5]Derived view for hot reads. Rebuildable.
ElasticsearchThree-node clusters per data centre, 192 GB RAM, all SSD [5]Derived view for text search. Rebuildable.

That is Question 4 from Lesson 124 rendered in hardware: exactly one store holds truth, and the other two are read-optimised projections of it that can be thrown away and rebuilt. Redis absorbs the read volume that would otherwise crush the database; Elasticsearch serves the query shape (full-text relevance ranking) that a relational engine serves badly. Neither is the only copy of anything.

Two things this case proves, both uncomfortable.
  • The single-node ceiling is much higher than candidates assume. Half a billion queries a day, no sharding, no NoSQL for the primary data. When you propose sharding in an interview, you are claiming the workload exceeds this — so you had better name the number that does.
  • Caches and search indexes are not "extra complexity" — they are load relief. Redis at 160 billion operations a month is the reason two database clusters suffice. The polyglot setup is precisely what lets the relational core stay simple.

Worth noting what makes this workload cooperative: it is read-dominated (millions of readers, comparatively few writers), the hot data is small enough to cache well, and there is no fan-out write problem. Change any of those — Discord's write-dominated firehose, say — and the same architecture falls over. The counterexample is not "always scale up"; it's "check whether your workload is this shape before assuming it isn't."

Check yourself

In Stack Overflow's three-tier setup, what distinguishes SQL Server from Redis and Elasticsearch?

Losing Redis or the search index costs a rebuild; losing the database loses facts. That asymmetry is exactly Question 4 of the framework.

Ask what is permanently lost if each tier is wiped.

Redis serves roughly 160 billion operations a month for Stack Overflow. Explain how adding a second store makes the overall system simpler rather than more complex.

Complexity isn't store count — it's how hard the hardest component is to reason about. A cache that removes the need to shard trades one easy component for one very hard one, and that is a bargain.

Picture those 160 billion operations landing on SQL Server instead. What would they be forced to build?

What property of Stack Overflow's workload makes this architecture work, and would break it if reversed?

Caching only helps where reads vastly outnumber writes and the hot set is small. A write-dominated firehose like Discord's gets no relief from a cache, which is why it needs a store that partitions writes instead.

Which kind of traffic can a cache absorb, and which kind must always reach the store?
