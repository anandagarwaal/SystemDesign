Design an Authentication / Authorization Service (Auth0 / Okta)

An identity provider offering authn + authz as a service — social login, SSO, and centralized fine-grained authorization at global scale.

Why this lesson, for your mission: Auth is the system every other system depends on, so an L6/L7 interviewer is testing whether you can hold security and low latency in tension and not blink. The depth lives in three places: do you understand why a stateless JWT trades revocation for scale, can you reason about OAuth2/OIDC without hand-waving, and do you know how Google's Zanzibar makes a fine-grained authorization check return in single-digit milliseconds globally. Get those right and you signal you can own a foundational platform.

Phase 1 · 0–5 minClarify the problemPin scope and the few NFRs that will drive every later decision.

Ask before you design

  • "Are we authenticating our own users, or offering identity as a multi-tenant service?" — Multi-tenancy adds per-tenant keys, IdP configuration and isolation.
  • "How quickly must a revoked session stop working?" — Revocation latency decides token lifetime and deny-list design.
  • "Is fine-grained authorization (sharing, groups) in scope, or just roles?" — Relationship-based access needs a Zanzibar-style service.

Functional Requirements

This is two products fused: an authentication service (prove who you are) and an authorization service (decide what you may do). Keep the core to five capabilities; name advanced flows (device code, SAML legacy, account linking) as explicitly out of scope.

#The system should…
1Sign up & log in users via password and via social/federated login (Google, GitHub), then store credentials and profiles per tenant.
2Issue tokens on successful login — a short-lived access token and a long-lived refresh token — and let clients exchange or revoke them.[1]
3Support SSO / federation: one login grants access to many relying-party apps using standard OAuth2 / OIDC flows.[2]
4Authorize a resource access: given a subject, action, and object, return allow/deny — including fine-grained checks ("can user U view doc D?").[3]
5Manage users, roles, and relationships — admins assign roles/permissions; the model supports both RBAC and relationship-based (ReBAC) authorization.[3]

Non-Functional Requirements

Auth NFRs are unusually sharp because everything else is downstream. Lead with security, then latency, then availability — and say the priority order out loud.

PropertyTarget & priority
Security firstTop priority. Credentials hashed with a slow KDF (bcrypt/argon2)[4], tokens signed (asymmetric), TLS everywhere, no secret in a log. A breach here compromises every tenant.
Low-latency authzAuthorization checks sit on the hot path of every protected request — target p99 < 10 ms. This forces aggressive caching and a stateless access-token verify.
Very high availability~99.99%+. If auth is down, every dependent app is down. Multi-region, no single point of failure, graceful degradation.

Phase 2 · 5–10 minEstimate what mattersOnly the numbers that change a decision — say the implication out loud.

Capacity Estimation

Only the numbers that change the design. Logins are rare; token verifications and authz checks dominate, and that ratio is the whole story.

  • Logins vs verifies: say 100M DAU logging in ~once/day ≈ ~1.2K logins/sec, but each then makes hundreds of API calls → ~1M+ token verifications/sec. Implication: the verify path must be local and crypto-only (no DB hit) — this is the core argument for stateless JWTs.
  • Authz checks: a UI page can fan out to dozens of "can I see this?" checks → easily millions/sec. Implication: a per-check database round trip is impossible; you need a purpose-built, cached authorization store (deep dive 4).
  • User/credential storage: 1B users × ~1 KB profile + hash ≈ ~1 TB. Implication: trivially fits a sharded relational store; storage is not the constraint — read latency and security are.

Interviewer pushback

"If verifications are millions per second, won't the auth service melt?"

Staff answer: Access tokens are signed JWTs verified locally by resource servers using cached public keys, so verification never calls the auth service.

Say to move on → "Logins are ~1k/s; token verifications and authz checks are millions per second. Let me define entities and the two planes."

Phase 3 · 10–17 minAPI & data modelLock the contract and the storage shape before drawing boxes.

Core Entities & API

Core entities: User (identity + hashed credential, scoped to a tenant), Tenant (isolation boundary + its signing keys + identity-provider config), Token (access + refresh), and a Relation/Grant tuple (object, relation, subject) powering authorization.[3]

Auth plane (derives caller from the bearer token, never a body field):

  • POST /v1/signup — create user { email, password, tenant }
  • POST /v1/oauth/token — exchange a credential or auth code for { access_token, refresh_token }[1]
  • POST /v1/oauth/token (grant_type=refresh_token) — rotate a refresh token for a fresh access token
  • POST /v1/oauth/revoke — revoke a refresh token (logout / compromise)
  • GET /v1/.well-known/jwks.json — public signing keys so anyone can verify tokens[2]

Authz plane (the hot check + relation writes):

  • POST /v1/check — { subject, action, object } → { allowed: bool }[3]
  • POST /v1/relations — write a tuple (doc:42, viewer, user:7) or a role grant

Data Model

Every row carries tenant_id, and every secret is stored as a hash or a KMS reference — never in the clear: password hashes (argon2id with parameters), refresh tokens and authorization codes stored by hash, client secrets hashed, signing private keys held in KMS/HSM. Refresh tokens form families (parent → child on rotation) so reuse of an old token revokes the whole chain. Authorization data is a separate tuple store keyed like Zanzibar.

Authentication is centralized (login, MFA, token minting with KMS-held keys); verification is decentralized — resource servers check JWT signatures locally with cached JWKS. Authorization decisions come from a Zanzibar-style service backed by a consistent tuple store and a denormalized membership index/cache.

High-Level Design

Two request shapes flow through the system. A login hits the Auth service, which validates the credential (or completes an OAuth2 redirect with an external IdP), then signs and returns tokens. Every subsequent API call carries the access token; the resource server verifies the signature locally using cached public keys, then calls the Authz service for a permission decision.

Phase 5 · 27–47 minDeep dives & tradeoffsGo deep where the system breaks; compare alternatives and justify the pick.

Deep Dives

Where the interview is decided. Four hard parts: the token strategy, the OAuth2/OIDC flow, credential security, and the fine-grained authz check at scale.

1. Token strategy — sessions vs JWT, and the revocation problem

The central tradeoff of the whole design. A server-side session stores a random opaque ID; every request looks it up in a shared store. A JWT is a self-contained, signed token whose claims the resource server verifies with crypto alone — no lookup.[1]

DimensionServer sessionJWT (stateless)
Verify costNetwork hop to session store per requestLocal signature check, no I/O
RevocationInstant — delete the rowHard — valid until it expires[1]
ScaleStore is a bottleneck/SPOFScales horizontally, easily

The pick: a hybrid — short-lived (5–15 min) stateless access token for the hot verify path, plus a long-lived (days) refresh token that is tracked server-side. The access token gets the scale benefit; the refresh token gets the revocation benefit.

The revocation problem, stated plainly: you cannot un-issue a JWT.[1] Three mitigations: (1) keep access-token TTL short so a leaked token expires fast; (2) revoke at the refresh layer — delete the refresh token so no new access tokens are minted; (3) for emergencies, a small deny-list of revoked token IDs (jti) checked on verify, accepting a tiny lookup to regain instant revocation.

Refresh-token rotation: issue a new refresh token on every use and invalidate the old one; if an already-used refresh token reappears, treat it as theft and revoke the whole chain.

2. OAuth2 / OIDC at a high level

This is how SSO and social login actually work, and interviewers expect you to narrate the Authorization Code flow without confusing the two specs. OAuth2 is for authorization (delegated access via an access token); OIDC is a thin layer on top for authentication that adds an ID token (a JWT proving who the user is).[2]

Authorization Code flow (with PKCE for public clients):

  • App redirects the user to the IdP's /authorize with its client ID, scopes, and a redirect URI.
  • User authenticates and consents at the IdP; the IdP redirects back with a one-time authorization code.[2]
  • App's backend exchanges the code (+ client secret / PKCE verifier) at /token for an access token and an ID token.
  • App verifies the ID token's signature against JWKS and trusts the identity. SSO falls out naturally: a second app reuses the IdP session.

Why the code, not the token, rides the browser redirect: the short-lived code is useless without the backend's secret, so a leaked redirect URL doesn't leak a usable token. Saying that distinguishes you from someone who memorized the diagram.

3. Password storage and MFA

The security NFR is most visible here. Never store plaintext, never use a fast hash (MD5/SHA-256) for passwords. Use a deliberately slow, salted KDF — bcrypt or argon2id — so brute-forcing a stolen dump is economically infeasible.[4]

ControlWhy it matters
Salted slow KDFPer-user salt defeats rainbow tables; the work factor makes each guess expensive.[4]
Constant-time compareAvoid timing side channels when comparing hashes/tokens.
MFA (TOTP / WebAuthn)A second factor blocks attackers who already have the password; WebAuthn/passkeys are phishing-resistant.
Rate limit + lockoutThrottle login attempts to stop credential stuffing (see Lesson 22).

4. Fine-grained authorization at scale — RBAC vs ReBAC (Zanzibar)

The deepest part. RBAC assigns users to roles and roles to permissions — simple, but it can't express "users who can see this specific document because it was shared with them." That per-object, relationship question is ReBAC, and Google's Zanzibar is the canonical design for answering it globally in milliseconds.[3]

ModelExpressesLimitation
RBAC"Editors can edit." Coarse, role → permission mapping.Can't do per-resource sharing or inheritance.
ReBAC / ZanzibarRelation tuples (doc:42, viewer, user:7); permissions inherit through relationships (group → folder → doc).[3]More moving parts; needs a purpose-built engine.

How Zanzibar hits low latency:

  • Relation tuples as the universal primitive: a check() walks the tuple graph (is user:7 a viewer of doc:42, directly or via a group/folder it belongs to).[3]
  • Leopard index + heavy caching of denormalized group membership so deep graph walks don't happen per request.[3]
  • Zookies (consistency tokens): a snapshot token that prevents the "new enemy" bug — you must not enforce a stale ACL after a permission was revoked. This gives external consistency without paying global-sync latency on every read.[3]

Result: Zanzibar serves millions of authorization checks/sec at p99 in single-digit ms across data centers.[3] For the interview, pick ReBAC for fine-grained needs, fall back to RBAC when role-level is enough, and cache decisions hard (see Lesson 4) — flagging that cache invalidation on revocation is the dangerous edge.

5. Multi-tenancy and key rotation

One bonus deep dive worth banking. Each tenant gets isolated data (row-level tenant ID or separate schema) and its own signing keys. Tokens are signed with a private key (asymmetric, e.g. RS256) so resource servers verify with the public key from the JWKS endpoint and the private key never leaves the KMS.[2] Key rotation: publish multiple keys in JWKS, each tagged with a kid; sign new tokens with the new key while old keys stay published until outstanding tokens expire, then retire them — zero-downtime rotation.

★ Staff-level signal Senior candidates describe JWTs and OAuth diagrams. Staff candidates do three things on top: (1) name the JWT revocation problem out loud and resolve it with short TTL + refresh-token rotation + an optional jti deny-list, rather than pretending stateless tokens are free; (2) distinguish OAuth2 (authz) from OIDC (authn) and explain why the auth code, not the token, traverses the browser; (3) reach for Zanzibar-style relation tuples + zookies for fine-grained authz and articulate the "new enemy" consistency bug caching introduces — security correctness under caching is the line between senior and staff here.

Privacy

The service holds identity data for billions of people: emails, phone numbers, IP/device history, and MFA factors. Minimization: tokens carry only necessary claims (no PII in access tokens beyond a subject id unless requested by scope); login telemetry stores hashed/truncated IPs after a short window. Tenant isolation is a privacy boundary: per-tenant data partitions, keys and audit trails; residency per region. Deletion: user erasure removes profile, identities, factors, refresh tokens and tuples mentioning the user, while audit records are pseudonymized. Consent: OIDC consent screens record granted scopes per client, revocable by the user.

Wrap-up · 58–60 minClose strongRecap decisions and tradeoffs in 60 seconds; name what you would do next.

Closing Summary (60 seconds)

An auth service splits identity from authorization. Login verifies credentials (Argon2id-hashed passwords, MFA or passkeys) or completes an OIDC flow with an external IdP, then issues short-lived signed JWT access tokens and rotating, revocable refresh tokens. Resource servers verify tokens locally using cached public keys from a JWKS endpoint, so verification scales with the callers. Fine-grained authorization is a Zanzibar-style relation-tuple service with cached checks. Each tenant has its own signing keys, rotated with overlap. At 10× verification is still local; we add authz nodes.

Comprehensive check

What is the core downside of a stateless JWT access token?

You can't un-issue a signed token; mitigate with short TTLs, refresh rotation, and an optional jti deny-list.

Reread deep dive 1's revocation-problem box.

Why is bcrypt or argon2 chosen over SHA-256 for password storage?

Fast hashes let attackers test billions of guesses; a slow salted KDF makes each guess expensive.

Reread deep dive 3's opening paragraph.

What problem do Zanzibar "zookies" (consistency tokens) primarily solve?

The "new enemy" bug: enforcing a stale ACL after revocation; zookies pin a fresh-enough snapshot.

Reread deep dive 4's Zanzibar box.

The mission box says the interview tests "security and low latency in tension." Where does this lesson resolve that tension most directly?

The hybrid token design is the whole lesson's answer to the tension: speed from statelessness, security clawed back through TTL and rotation.

If a product only ever needs "editors can edit, viewers can view" with no per-document sharing, what would change in this design?

ReBAC earns its complexity only when access depends on per-object relationships; role-level rules alone don't need a tuple graph.
