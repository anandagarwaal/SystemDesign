Deep Dive: Secure System Design

Security isn't a feature you bolt on at the end — it's a property of the whole architecture. Here's how to weave it through a design and talk about it like a staff engineer.

Why this lesson, for your mission: Most candidates treat security as "we'll add HTTPS and call it done." At L6/L7 — and especially for fintech, healthcare, or any system handling money or PII — the interviewer wants a threat-aware design: defense in depth, least privilege, encryption in transit and at rest, and a plan for the OWASP-class attacks. This lesson gives you a reusable security checklist you can layer onto any case study, plus the secure-cloud-architecture vocabulary (VPCs, secrets, zero trust) that signals you've shipped systems people try to break.

1 of 4

The mindset: think like an attacker

Secure design starts by asking "what could go wrong, and who benefits?" for each component — a lightweight threat model. A handy frame is STRIDE: Spoofing, Tampering, Repudiation, Information disclosure, Denial of service, Elevation of privilege.[2] Two principles run through everything:

  • Defense in depth: never rely on one control. If the firewall fails, network segmentation, auth checks, and encryption should each still limit the blast radius.[2]
  • Least privilege: every user, service, and credential gets the minimum access needed. A compromised image-thumbnail service should not be able to read the payments database.[2]
Check yourself

What does 'defense in depth' mean?

No single control is trusted to hold; each layer (segmentation, authz, encryption) independently limits blast radius.

Reread the first bullet under 'The mindset'.

An attacker fully compromises your thumbnail service. What single principle decides whether they can now read payment data?

Once compromised, the attacker IS the service. What they can touch equals what the service's identity is allowed to touch.

Think blast radius: after compromise, the attacker has exactly the service's permissions.

The layered checklist

LayerWhat to secure
Network / perimeterPrivate subnets in a VPC; only load balancers in public subnets; security groups as host firewalls; WAF + DDoS protection at the edge; internal services unreachable from the internet.
TransportTLS everywhere (in transit), including service-to-service (mTLS / zero-trust); HSTS; valid certs, no InsecureSkipVerify.
Identity & accessStrong AuthN, least-privilege AuthZ on every request (see Lesson 115); short-lived credentials; MFA for humans; service identities, not shared keys.
ApplicationValidate & sanitize all input; parameterized queries (no SQL injection); output encoding (no XSS); CSRF tokens; rate limiting; safe deserialization.
Data at restEncrypt databases, disks, and backups (KMS-managed keys); hash passwords with bcrypt/argon2 (never plain SHA); tokenize/encrypt PII & card data; field-level encryption for the most sensitive fields.
SecretsNo secrets in code or env files in the repo; use a secrets manager / vault; rotate keys; scope each secret to one service.
ObservabilityAudit logs for security events (logins, permission denials), tamper-evident; anomaly/fraud detection; no secrets or full PII in logs.
The OWASP attacks you should be able to name & block
  • Injection (SQL/command): attacker input becomes code. Block with parameterized queries and input validation — never string-concatenate queries.[1]
  • Broken access control: the #1 risk — a user reaches another user's data by changing an id (IDOR). Block with an authorization check on every object access, server-side.[1]
  • XSS: injected script runs in a victim's browser. Block with output encoding, a Content-Security-Policy, and HttpOnly cookies.
  • CSRF: a malicious site triggers an authenticated action. Block with CSRF tokens and SameSite cookies.
  • SSRF: the server is tricked into calling an internal URL (e.g. cloud metadata). Block by validating/allow-listing outbound destinations.
  • Sensitive data exposure: unencrypted PII or weak password hashing. Block with encryption at rest and argon2/bcrypt.
Check yourself

A user changes /invoices/1001 to /invoices/1002 and sees someone else's invoice. What is this, and the fix?

IDOR is broken access control, OWASP's #1: authentication proved WHO they are, but nobody checked they may see THIS object.

The user was logged in. What check was missing?

Why are bcrypt/argon2 better than SHA-256 for passwords, even though SHA-256 is 'more secure'?

SHA-256 is designed to be fast — billions/sec on a GPU. Password hashes are designed to be slow (and salted) so guessing is expensive.

What does an attacker who stole the hash table do next — and how fast can they do it?

Why does a parameterized query stop SQL injection when escaping strings often fails?

Injection = data crossing into the code channel. Parameters never go through the parser as SQL text, so there's no boundary to escape.

Injection means input 'becomes code'. Where does a bound parameter go — the SQL text, or somewhere else?

Secure cloud architecture

For the "secure cloud" framing specifically: design from the network outward. A VPC with public subnets (just the ALB/NAT) and private subnets (app + data tiers) is the spine; security groups and NACLs enforce who-talks-to-whom; a bastion / SSM replaces direct SSH; KMS manages encryption keys with rotation; IAM roles (not long-lived access keys) grant scoped, temporary credentials to each service. The modern endpoint is zero trust: trust nothing by network location — every request is authenticated and authorized even inside the perimeter, often via mTLS between services.[2]

★ Staff-level signal A junior says "we'll use HTTPS." A staff candidate weaves security through the whole design: "PII is encrypted at rest with KMS, passwords are argon2-hashed, the payments service runs in a private subnet with an IAM role scoped to only its tables, and every API call re-checks authorization server-side so an attacker can't IDOR into another account."[1] They name defense in depth and least privilege as principles, not buzzwords, and proactively call out a concrete attack and its mitigation ("the upload endpoint validates content type and stores files outside the web root to prevent RCE"). The tell is treating security as a cross-cutting property and reasoning about blast radius when a component is compromised — not as a single checkbox.

In the interview

Don't deliver a security monologue up front — weave it in. When you place the database, add "encrypted at rest, in a private subnet." When you design auth, mention least-privilege and server-side authz on every object. When money or PII appears, name the specific controls (argon2, KMS, tokenization, audit logs). If asked to "do security properly," walk the layers top-down — network → transport → identity → app → data → secrets → monitoring — and for each name one concrete control and the attack it stops. Closing with "and I'd threat-model the critical flows with STRIDE" signals maturity.

Why store passwords with bcrypt or argon2?

Password hashing must be deliberately slow and salted; fast hashes like SHA-1 let an attacker brute-force a leaked table cheaply.

Your 'import from URL' feature fetches any URL a user gives. What's the specific danger?

The server fetches from INSIDE your network with its own identity, so user-chosen URLs can reach internal services. Allow-list destinations, block private ranges.
