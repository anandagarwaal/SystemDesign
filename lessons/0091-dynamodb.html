Deep Dive: DynamoDB

A fully managed, serverless key-value store that hides the Dynamo ring behind an API — what you get for free, and what you must still design for yourself.

Why this lesson, for your mission: At L6/L7 the interviewer doesn't want "I'd use DynamoDB because it scales." They want to hear that you know what AWS operates for you (partitioning, replication, repartitioning) and what is still your job (the partition key, the access patterns, the hot-partition fix). A staff candidate models the table query-first, names the GSI that backs each read, and pre-empts the hot-partition trap with write sharding — out loud, before being asked.[1] This lesson gives you that machinery.

1 of 6

What it is & the data model

DynamoDB is a fully managed, serverless, NoSQL key-value and document store from AWS.[1] "Managed/serverless" is the whole pitch: there are no nodes, clusters, or disks for you to size, patch, or rebalance — you create a table and read/write items, and AWS handles partitioning, replication, scaling, and failover beneath the API.[1] It descends directly from the 2007 Dynamo paper, so the lineage is the same one behind Cassandra (Lesson 90): consistent hashing, replication, and quorum-style reads — just operated for you instead of by you.[4]

The data model is small and rigid, which is what makes it predictable:

ConceptWhat it isInterview one-liner
Table A collection of items. No fixed schema beyond the key; each item can carry different attributes.[1] "Schema-on-read for everything except the key."
Item One record (like a row), a set of attributes, capped at 400 KB total.[1] "My unit of read and write; keep it small."
Partition key (PK) Required. Hashed to decide which partition stores the item.[1] "My shard key — every fast query names it."
Sort key (SK) Optional. Orders items within a partition, enabling ranges.[1] "Free sorted, paginated reads inside a partition."

A table with only a partition key is a pure key-value lookup; a table with partition key + sort key (a "composite primary key") lets many items share a partition and be range-scanned in sort order — the structural twin of Cassandra's partition key + clustering columns.[1]

Check before continuing

What does the partition key determine about an item?

The partition key is hashed, and the hash decides which physical partition holds the item.

Reread the table row for "Partition key (PK)."

Why add a sort key at all, instead of always using a partition-key-only table?

Without a sort key you get one item per partition-key value. With one, related items (an order and its line items) can live under the same partition key and be fetched as an ordered range in one query.

Internals — what AWS runs for you

Partitioning by hash of the partition key

DynamoDB stores a table across many partitions — physical storage units that each hold a slice of the data on SSD.[1] To place an item, DynamoDB feeds the partition-key value through an internal hash function; the hash output determines which partition the item lives on.[1] This is the same idea as sharding by consistent hashing (Lesson 5) — hashing spreads keys evenly so no single partition is a default bottleneck, and a single item read becomes "hash the key, go straight to one partition."[4]

Automatic re-partitioning & adaptive capacity

Here is the part you'd otherwise operate by hand on Cassandra. As a table grows past a partition's size limit, or as traffic to it rises, DynamoDB splits partitions and redistributes items automatically — no downtime, no manual resharding.[1] It also applies adaptive capacity: it can shift throughput toward partitions receiving more traffic, smoothing moderately uneven load.[2] This auto-repartitioning is the single biggest operational difference from running your own ring — but, as we'll see, it does not rescue a genuinely hot single key.

Replication across Availability Zones

Every item is synchronously replicated across three Availability Zones in a Region before a write is acknowledged, giving durability and high availability with no action from you.[1] If an AZ or a node fails, DynamoDB serves from the survivors and heals in the background. This is the Dynamo replication model — copies on multiple independent failure domains — packaged as a default rather than a configuration.[4] (Cross-Region replication is the separate global tables feature, multi-active and eventually consistent across Regions.)[1]

The Dynamo lineage & single-digit-ms latency

Consistent hashing for placement, multi-replica storage, and quorum-style reads all trace to the Dynamo paper.[4] Because placement is a hash and a read goes to one partition's replica set, DynamoDB delivers consistent single-digit-millisecond latency at any scale — the headline SLA-class promise, and the reason it underpins shopping carts, sessions, and high-volume metadata.[1] The mental model to carry into the room: you give up joins and ad-hoc queries; in return you get predictable latency that does not degrade as the table grows from megabytes to petabytes.

Why can't adaptive capacity alone save a single overloaded partition key?

Adaptive capacity redistributes throughput across partitions, but a single hot key's requests all hash to the same partition — there's no "spreading" a single value's own traffic without changing the key itself.

Think about what the hash function does with one fixed key value, every single time.

Access patterns & indexes

Query-first & single-table design

Like Cassandra, DynamoDB rewards query-first modeling: enumerate your access patterns first, then design keys so each pattern is a direct key lookup or a sort-key range — never a scan.[3] The advanced expression of this is single-table design: store multiple entity types (users, orders, order-items) in one table, using a generic PK/SK and overloaded keys so related items share a partition and can be fetched in a single query.[3] It looks alien next to a relational schema, but it exists to collapse what would be joins into one round trip. Don't over-apply it: for a beginner answer, one-table-per-entity with the right indexes is perfectly defensible.

GSIs vs LSIs

You model the table for your primary access pattern; secondary indexes serve the others by giving you an alternate key.[1]

Global Secondary Index (GSI)Local Secondary Index (LSI)
KeyAny attribute as a new partition key + sort key.[1]Same partition key, a different sort key.[1]
When createdAny time, add or drop freely.[1]Only at table creation — locked in.[1]
ConsistencyEventually consistent only.[1]Can serve strongly consistent reads.[1]
CapacityIts own throughput, separate from the table.[1]Shares the base table's throughput.[1]

The staff-level summary: reach for a GSI by default (flexible, addable later, independently scaled); reach for an LSI only when you need a strongly consistent alternate sort within the same partition and you knew that at table-creation time.[1]

The hot-partition problem & write sharding

Hashing spreads load across keys, but it can't spread the load of one key. If a single partition-key value takes disproportionate traffic — a celebrity user, a "today" date bucket, a viral product — you get a hot partition: that one partition saturates and throttles even while the table is mostly idle.[3] Adaptive capacity softens skew but cannot save a single overloaded key.

Two fixes a staff candidate names without prompting
  • Pick a high-cardinality, evenly-accessed partition key — the root cause is almost always a low-cardinality or time-clustered key.[3]
  • Write sharding — append a suffix (e.g. userId#0..N) to fan one hot key across N partitions, then scatter-gather on read. You trade read complexity for write spread.[3]

Capacity: on-demand vs provisioned

ModeHow it billsPick it when…
On-demandPay per request; scales instantly, no planning.[1]Spiky, unknown, or new traffic.[1]
ProvisionedReserve read/write units; cheaper at steady load, can autoscale.[1]Predictable, high, steady traffic.[1]

DAX & read consistency

For read-heavy, latency-critical workloads, DAX (DynamoDB Accelerator) is a managed, write-through in-memory cache that drops read latency from milliseconds to microseconds for cached items — a built-in caching layer (Lesson 9 tour) you don't operate yourself.[1] On consistency, DynamoDB gives you a per-read dial: an eventually consistent read (the default) may miss the very latest write but is cheaper and lower-latency, while a strongly consistent read always reflects the last acknowledged write at higher cost and no availability on a network partition.[1] Same R/W-quorum trade as Cassandra — just exposed as one boolean instead of a tuning level.

When to reach for it — and when NOT to

Reach for DynamoDB when…Avoid it when…
You want zero-ops scale and predictable single-digit-ms latency.[1] You need ad-hoc queries, joins, or analytics over many dimensions.[3]
Access patterns are known up front and key-addressable.[3] Access patterns are unknown or change constantly (no key to model).[3]
Key-value / item workloads: carts, sessions, profiles, metadata.[1] Items are large or relationships are deeply relational and normalized.[3]
You're all-in on AWS and want a managed service, not a cluster.[1] You need cross-cloud portability or self-host control (use Cassandra).[4]

DynamoDB and Cassandra share the Dynamo lineage and the query-first discipline; the real choice is operational. DynamoDB = managed, serverless, AWS-locked, you-design-keys-only. Cassandra = self-operated, multi-cloud, you-tune-consistency-and-the-ring.[4]

★ Staff-level signal Senior candidates say "DynamoDB scales infinitely." Staff candidates draw the line between managed and your job in one breath: "AWS hashes the partition key, splits partitions, and replicates across three AZs for me — so I never resize a cluster. But it cannot rescue a hot key, so my job is a high-cardinality partition key and, for the celebrity case, write-sharding the key across N suffixes with a scatter-gather read."[3] Then they pre-empt the next probe: "Joins and ad-hoc filters don't exist here; I model query-first and back each access pattern with a GSI, defaulting to eventually consistent reads and flagging the one path that needs a strongly consistent read." Naming the boundary before the interviewer pushes is the whole game.[1]

In the interview

When DynamoDB is the right call, deliver it in this order: (1) justify the pick from the requirement — "key-value access, known patterns, need predictable low latency and zero ops on AWS." (2) List the access patterns, then (3) design the keys — name the partition key and sort key for each pattern and the GSI that backs any secondary read. (4) Pre-empt the hot partition — show you chose a high-cardinality key, and describe write sharding for the celebrity case. (5) Set capacity & consistency — on-demand vs provisioned, eventual-by-default reads with strong reads where correctness demands it, DAX if read-heavy. That arc is breadth-then-depth: a fast justification, then 60% depth on key design and the hot-partition fix — the parts AWS does not do for you.[1]
