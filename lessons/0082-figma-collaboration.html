System Design · Lesson 82 · Phase 4 — Case Study · Hard

Design Real-Time Collaboration (Figma)

Many designers dragging shapes on one canvas at once — and everyone seeing the same picture.

Why this lesson, for your mission: The trap is treating this like Google Docs. A senior candidate reaches for the same OT/CRDT-for-text answer. A staff candidate spots that a design tool isn't a string — it's a tree of objects with typed properties — and that this changes everything: you can converge with simple per-property last-writer-wins and skip text CRDTs entirely. Naming why the data model dictates the conflict-resolution strategy is the staff signal.

Functional Requirements

Scope to the multiplayer canvas core. This is a 2D design surface — shapes, frames, text blocks — not a document of characters.

#Requirement
1A user can open a document and see its current canvas state.
2Many users concurrently edit objects — move, resize, restyle, add, delete shapes — and all converge.
3Editors see collaborators' live cursors and presence moving in real time.
4Edits are durably persisted; a reopened document reflects every accepted change.
5An editor can keep working briefly offline and reconcile on reconnect.

Out of scope: rich text editing inside a shape (that's the Google Docs problem), comments, permissions, version history UI, and the vector-rendering engine.

Non-Functional Requirements

PropertyTarget / priority
Low-latency real-time syncLocal edits apply instantly (optimistic); remote edits and cursors land in <100 ms. This is the headline NFR — collaboration must feel live.
Conflict resolution / consistencyAll clients converge to the same canvas. Eventual convergence is enough — unlike text, a stray shape pixel isn't "corruption." [1]
AvailabilityHigh for open/edit; a reconnect blip is fine. Optimistic local edits keep the canvas usable through brief drops.
DurabilityNo accepted edit is lost; the document survives any single node failure.

The tension mirrors Google Docs — feel always-editable, yet converge — but the resolution is cheaper here. Because a canvas is structured data (objects + properties), not a linear sequence, we don't need OT or a text CRDT; a central server applying last-writer-wins per property converges with far less machinery [1].

Capacity Estimation

Estimate only what bends the design.

QuantityEstimateDesign implication

The headline: per-document load is tiny; system-wide connections and per-doc object counts are large. That asymmetry justifies sharding by documentId, keeping each doc's object map in RAM, and syncing fine-grained property deltas rather than whole documents.

Core Entities & API

Entities: Document (id, root object id, latest version), Object (id, parentId, type rect/text/frame/group, and a map of typed properties — x, y, width, fill, z-index…), and Presence (ephemeral: userId, docId, cursor x/y, selection, color). The document is the map/tree of objects; parentId is itself just a property.

EndpointPurpose
POST /v1/documentsCreate a document; returns documentId.
GET /v1/documents/:idLoad the latest snapshot (full object map + version) to start editing.
WS /v1/documents/:id/syncBidirectional edit stream: client sends property changes, server broadcasts canonical changes back.
WS /v1/documents/:id/presenceEphemeral cursor/presence channel, separate from durable edits.

User identity is derived from the auth token on connect, never passed in the body. The sync and presence channels are deliberately separate — one is durable and converges, one is throwaway (Deep Dive 3).

High-Level Design

Walk a single edit — "Alice drags a rectangle" — through the system:

  1. Client opens the doc via GET, downloads the snapshot (object map + version), renders the canvas.
  2. Client opens a WebSocket to the sync server that owns this document.
  3. Alice drags the rect. The client updates the object's x/y optimistically (instant local feedback) and streams the property changes.
  4. The sync server applies each change to its in-memory object map under last-writer-wins per property, appends it to the durable change log, and fans it out to every other connected client.
  5. Peers apply the canonical change to the same object/property, reaching the same canvas. Cursors flow on the separate presence channel.

Deep Dives

1. The document as a tree of objects + per-property last-writer-wins

A Figma file is not a string — it's a tree of objects: a page contains frames, frames contain groups, groups contain shapes. Every object has a stable id and a map of typed properties (x, width, fill, parentId, z). Crucially, the parent link is just another property, so reparenting a layer is a property write like any other [1].

This structure is the whole trick. Two users editing the same object usually touch different properties — Alice moves it (x), Bob recolors it (fill) — and those merge trivially, each property updated independently. Only when two users write the same property of the same object do we have a real conflict, and there last-writer-wins (LWW) resolves it: the server's arrival order decides, the shape ends one color, and nobody's canvas is "corrupted." Compare the text case in Lesson 31: there, LWW silently drops keystrokes because order and position carry meaning in a sequence. On a canvas, the loser of an LWW race just loses one property value — visually fine. The data model is what makes the cheap strategy safe.

AxisText CRDT / OT (Google Docs)Per-property LWW (Figma)
Unit of editCharacter in a sequenceProperty of an identified object
Why conflicts hurtLost char = corrupted textLost property = one stale value
Convergence mechanismTransform ops / commutative char idsObject id + property key + LWW register
Engineering costHigh (OT proofs / char metadata)Low (a map of registers)
Justified pick: Treat the doc as a map of objects, each a map of LWW property registers, with one authoritative server deciding order — not a text CRDT or OT. It's inspired by CRDTs (commutative, convergent) but far simpler because we have a central authority and don't need offline-P2P guarantees [1]. Two edge cases need explicit handling: delete-vs-edit (an edit to a deleted object is dropped — deletion wins) and tree cycles (a reparent that would make A a child of its own descendant is rejected by the server, which can see the whole tree). Name those two and you're at staff level.

2. The realtime sync server: in-memory state + fan-out

One sync server owns each document, routed by documentId at the gateway. It loads the object map into memory once, then every editor's WebSocket attaches to that single process. The server receives property changes, applies LWW to its authoritative copy, appends them to the durable change log, and broadcasts the canonical change to all other connected clients. Because every change funnels through one process, ordering is trivial — there's no distributed consensus on the hot path. This is the long-lived stateful connection pattern from Lesson 19 (WhatsApp / WebSockets), and the broadcast is per-doc pub/sub.

Clients edit optimistically: apply locally, then send. If the server's LWW ordering disagrees, the canonical change the client receives back simply overwrites the local guess — usually invisible. Scaling and failover: shard documents across a fleet via consistent hashing on documentId, with a coordination layer (etcd/ZooKeeper) tracking ownership. On reconnect a client sends its last-seen version and the server replays the missed tail of the change log — so a crash costs a brief catch-up, never lost edits.

3. Presence and live cursors as ephemeral, high-frequency state

Cursors move 30–60 times a second per editor and mean nothing a moment later — if one update is lost, the next corrects it; on disconnect the cursor should just vanish. So presence must never touch the durable change log (it would drown real edits and bloat storage). Route it on the separate /presence channel through a pub/sub layer keyed by documentId, with TTLs so a dropped client's cursor expires automatically, and throttle/interpolate on the client so the wire carries ~10–20 updates/s while the cursor still looks smooth. The staff move is the clean separation: durable converging edits and throwaway presence are different systems with different guarantees — conflating them risks dropping real edits under cursor load.

4. Persistence: snapshots + change log, and loading large documents

The change log is the durable source of truth: an append-only sequence of accepted property changes. But a file can hold 100k+ objects, and replaying every historical change to open it is far too slow — so the server periodically snapshots the materialized object map plus its version. Loading a document = fetch the latest snapshot + replay only the changes after it; then the live WebSocket takes over. For very large files, stream the snapshot and render progressively rather than blocking on a full download. Snapshot cadence is a tunable knob (frequent = fast loads, more storage), and once a snapshot at version V is durable, older log entries can be compacted away. Offline edits (FR 5) are buffered locally as property changes and replayed on reconnect — LWW then resolves them against whatever changed meanwhile, which is exactly why the cheap conflict model also gives us offline almost for free.

★ Staff-level signal Lead with the data model, not the diagram: "It's a tree of objects, each a map of typed properties, so I converge with per-property last-writer-wins on one authoritative server — I don't need OT or a text CRDT like Google Docs, because a lost property value is visually fine while a lost character is corruption." Then call the two edge cases unprompted — delete-vs-edit and reparent cycles — keep presence rigorously off the durable log, and explain snapshots + change log for fast loads of huge files. Matching the conflict strategy to the data model is what separates this from a copy-pasted Google Docs answer.

Check yourself — retrieval practice

Answer from memory before scrolling back up.

1. Why is per-property last-writer-wins safe for Figma but unsafe for Google Docs text?

Canvas objects are structured; losing a property value is visually fine. In a text sequence, order and position carry meaning, so a dropped char corrupts.

2. Two users edit the same rectangle: Alice moves it, Bob recolors it. What happens?

Different properties (x/y vs fill) of one object update independently and merge. LWW only kicks in on the same property.

3. Why are live cursors routed on a separate channel from durable edits?

Presence is throwaway and very frequent; logging it would bloat storage and risk crowding out real edits.

4. Why does Figma snapshot documents instead of always replaying the full change log?

A document can have 100k+ objects; load = latest snapshot + replay only the recent tail, then go live.
