Design a To-Do List System

A high-latency-tolerant CRUD system that teaches consistency under concurrent edits and mobile-first optimizations.

Why this lesson, for your mission: To-do lists seem trivial until you ask "what happens when I edit on my phone, then my laptop, in the subway with no connectivity?" The staff move is recognizing that this is really a conflict-free replicated data type (CRDT) problem hidden in a simple feature, plus designing for offline-first clients. You trade latency for consistency and learn when eventual consistency is actually the right call. The same patterns apply to collaborative documents, shared spreadsheets, and real-time editing.

Phase 1 · 0–5 minClarify the problemPin whether offline edits matter and how to handle conflicts.

Ask before you design

  • "Do users work offline and expect their edits to sync later?" — Offline support changes the entire architecture. You now need eventual consistency and conflict-free merges, not real-time locks.
  • "Can two users edit the same list concurrently, and how should conflicts resolve?" — Last-write-wins loses data. Operational transformation or CRDTs preserve both edits.
  • "Is it multi-device, or single-device per user?" — Multi-device raises sync complexity and requires a server-side merge strategy.

Phase 2 · 5–10 minEstimate what mattersConcurrent users, list size, and sync frequency.

Capacity Estimation

User and list scale

100M DAU. Average user has 5 lists, ~50 items/list. Total items: 100M × 5 × 50 = 25B items. Implication: database must partition by user and list; no global queries.

Concurrent writes per user

A user typically has 1–3 devices syncing. Peak: ~10 concurrent items being edited (phone + laptop). At 100M DAU, concurrent users online: ~10M. Peak WPS (write operations): 10M users × 10 items × 1 update/sec ≈ ~100M writes/sec server-side — but heavily partitioned by user. Implication: no global lock; partition by user_id for parallelism.

Sync traffic

Average user syncs 5 times/day; each sync is ~1 KB (delta). 100M × 5 × 1 KB = 500 GB/day bandwidth. Implication: delta encoding is essential; send only diffs, not full state.

Interviewer pushback

"Why not just use timestamps for conflict resolution?"

Staff answer: Timestamp-based last-write-wins loses data. If Alice adds "buy milk" at 10:01 and Bob adds "call mom" at 10:01 on the same list, one edit is silently overwritten. CRDTs or OT preserve both.

Say to move on → "With offline support and 100M users, I'll design the list schema to support eventual consistency."

Interviewer pushback

"Why store edits separately instead of just the current item state?"

Staff answer: Edits are the source of truth for conflict resolution. If two users edit the same item, we reconstruct the state from the edit log and merge using CRDT rules. Storing only the final state loses the edit history needed for merging.

Offline-first: local writes are instant. Sync is bidirectional: client sends edits, server merges and returns authoritative state.

High-Level Design

The client is offline-first: all reads and writes hit local storage instantly. A sync engine runs in the background, computes diffs against the last-known server state, and pushes them to the server. On sync, the server merges using a CRDT rule (e.g., last-write-wins per field, with tie-breaking by device ID). The server returns the merged state and any conflicts the client flags for manual resolution.

FlowPathStores touched
Offline writeUser → local storage (instant) → mark "unsynced"IndexedDB/SQLite
Sync (periodic or manual)Client → POST /sync {edits, vector_clock} → Server merges → returns merged statePostgres + edit log
ConflictServer detects (same item edited twice) → returns both versions → client flags for userUser chooses or merges manually

Sync protocol: the client sends a list of edits with a vector clock (version per device). The server merges edits using CRDT rules, returns the authoritative state, and updates the client's vector clock. On the next sync, the client only sends new edits, not the full state.

Interviewer pushback

"What if sync fails mid-way?"

Staff answer: Syncs are idempotent via the vector clock. If the client sends edits with clock v=5 and the network drops, the next sync sends the same edits (or newer ones starting from v=5). The server detects duplicates and reapplies them safely.

Say to move on → "The design is offline-first with eventual consistency. The hard parts are CRDTs and handling multi-device conflicts."

Phase 5 · 27–47 minDeep dives & tradeoffsCRDT vs. OT, merge strategies, and mobile constraints.

Deep Dives

Deep Dive 1 — Conflict-Free Replicated Data Types (CRDTs)

A CRDT ensures that any two replicas with the same edits converge to the same state, without coordination. For to-do lists, use a CRDT list with tombstones:

Simple CRDT rule: last-write-wins per field.
  • Each edit has a timestamp (device_id, lamport_clock)
  • When merging two edits on the same item, the one with the higher timestamp wins
  • If timestamps tie, the device_id breaks ties (e.g., alphabetically)
  • Deletions are soft (set deleted_at); removed items stay in the log for conflict detection
  • Concurrent additions always merge; additions never conflict

For to-do lists, this is sufficient: item text and done-state are small; last-write-wins is intuitive. For collaborative text editing, use a more sophisticated CRDT (Yjs, Automerge) that preserves character-level edits.

Deep Dive 2 — Vector clocks and causality tracking

A vector clock is a per-device counter that tracks the order of edits. Client 1 increments its clock to v1=[2, 0] (2 edits from device 1, 0 from device 2). On sync, the server learns v1, merges, and returns v2=[2, 3] (server has seen 2 from device 1, 3 total edits). This prevents replaying the same edit twice.

Deep Dive 3 — Offline edits with server conflicts

Suppose Alice edits item 5 offline (change text), then syncs. Meanwhile, Bob deletes item 5 and syncs. When Alice's sync arrives, the server must decide: preserve Alice's edit or honor Bob's deletion? Rule: a delete always wins (tombstone semantics). Alice's edit is stored but the item remains logically deleted. If Alice asks "why did my edit vanish?", show her that Bob deleted it concurrently.

Deep Dive 4 — Bandwidth optimization: delta sync

Syncing the full state every time is expensive. Instead, send only diffs:

ApproachBandwidthComplexity
Full state on every sync~1 KB per sync (all items)Simple
Delta sync (only edits since last sync)~100 bytes per sync (just diffs)Requires version tracking
Incremental CRDT (send only operations)~50 bytes per edit; cumulative for all usersComplex: OT or CRDT ops

Pick delta sync: send edits since last vector clock. This is simpler than full OT and efficient for to-do lists.

Deep Dive 5 — Mobile constraints: battery and data

Mobile clients are constrained. Sync strategy: coalesce writes (wait 5 seconds after last edit before syncing), batch edits (upload 10 at once), and compress (gzip diffs to ~20% size). WiFi-only sync option for users with metered plans.

Interviewer pushback

"What if a user has 10,000 items in one list and syncs every second?"

Staff answer: Delta sync solves this: send only edits, not the full state. If there are 5 edits per second, that's ~500 bytes each, not 10 MB. Also, consider splitting large lists into sub-lists by date or status for better UX and sync performance.

2 · Closing Summary (60 seconds)

The to-do system is offline-first with eventual consistency: clients write to local storage instantly, sync bidirectionally with the server, and use CRDTs (vector clocks + tombstones) to merge conflicts without data loss. Delta sync and bandwidth optimization keep mobile data usage low. Multi-device support is natural: sync treats all devices as equal replicas. The first architectural change at 10× is increased Postgres shard count. The design trades latency for correctness: concurrent edits are detected and surfaced to the user, never silently lost.

Check yourself — retrieval practice

Answer from memory before scrolling back up.

1. Why use CRDTs instead of simple last-write-wins for merge?

Last-write-wins silently overwrites concurrent edits. CRDTs ensure convergence: any two replicas with the same edits end up in the same state. They don't hide conflicts, but they don't lose data either.

2. What is the primary benefit of delta sync over full-state sync?

If a user has 10k items and syncs daily, sending the full state is wasteful. Delta sync sends only the edits (maybe 20 bytes each), reducing bandwidth by ~100x. Full state is simpler but expensive at scale.

3. A user edits item A offline, then deletes the same item online before syncing. After sync, what should happen?

Deletion is a strong operation; it always wins via tombstone semantics. The offline edit is recorded in the log but the item remains logically deleted. This avoids resurrections.

4. How do vector clocks prevent duplicate syncs?

A vector clock is a tuple like [device1: 5, device2: 3]. If a sync arrives with the same clock twice, the server recognizes it as a duplicate and avoids reapplying. New edits increment the clock.
