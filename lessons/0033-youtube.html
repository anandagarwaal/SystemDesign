Design YouTube (Video Streaming)

Three decisions carry this design: async transcoding, adaptive-bitrate segments, and a CDN. Everything else is plumbing.

Why this lesson, for your mission: YouTube is the canonical "media at scale" interview. The trap is treating it like a CRUD app and burning time on the metadata DB. At L6/L7 you must recognize that the real system is a transcoding pipeline feeding a CDN, and that bandwidth — not storage or QPS — is the dominant cost and scaling axis. Get the three load-bearing decisions right and you've passed.

1. Functional Requirements

Scope is mercilessly narrow. Two flows define the product; everything else (search, comments, recommendations, channels) is explicitly out of scope and you should say so to buy depth elsewhere.[1]

#Users should be able to…Note
1Upload a videoFiles up to 10s of GBs; must be resumable
2Watch a videoStreamed, with adaptive quality across devices/bitrates
3View metadata + view countTitle, description, uploader, approximate view count

The third item is a deliberate add to this lesson — view counts are a classic "approximate at scale" sub-problem worth a deep dive.

2. Non-Functional Requirements

These are where the design lives or dies. State the target, not just the word.[1]

NFRTargetDrives
DurabilityNever lose an uploaded videoObject storage (S3) with replication
Low-latency playbackStart in <~2s, no rebufferingSegments + CDN + adaptive bitrate
Read scalability~100M watches/day, extreme read:writeCDN absorbs reads; cache hot metadata

Order matters. Low-latency global playback and read scalability are the headline NFRs — they're what justify the CDN and segmentation that make this problem "hard."

3. Capacity Estimation

Only compute the numbers that change a decision. Three matter here.[1]

QuantityEstimateDesign implication
Uploads~1M videos/day → ~365M/yr~12 uploads/sec. Trivial write QPS — not the bottleneck.
Storage1M/day × ~1–5 GB raw, ×~5 for transcoded copies → PBs/yrHuge, but cheap object storage; not the hard part.
Watch bandwidth100M watches/day × ~5 min × ~5 MbpsThis is the cost. Tens-to-hundreds of Tbps at peak → must serve from the CDN edge, never origin.
The one number that reframes the problem. Write QPS (~12/s) is laughable. The metadata DB is easy. The interview-defining figure is egress bandwidth: serving 100M streams from origin S3 is both impossible and ruinously expensive. Bandwidth dominates everything — so the architecture must push bytes to the edge and keep them there.

4. Core Entities & API

Three entities. Note VideoMetadata carries the manifest URL and per-chunk upload progress — those two fields wire the whole system together.[1]

EntityKey fields
Userid, uploaders and viewers
Videothe raw + transcoded byte assets in blob storage
VideoMetadataid, title, description, uploaderId, status, manifestUrl, chunk list + per-chunk status

The API is small. The user is always derived from the auth token, never a body param.

EndpointPurpose
POST /v1/videosCreate metadata, return chunk plan + presigned upload URLs (resumable)
PATCH /v1/videos/{id}/chunksReport a chunk's ETag after a successful direct-to-S3 PUT
GET /v1/videos/{id}Return metadata + manifestUrl (the streaming entry point)
GET manifest & GET segmentsServed directly by the CDN, not the app tier

Critical move: the client uploads bytes directly to object storage via presigned URLs, and downloads segments directly from the CDN. The app tier only ever touches small metadata — it never proxies video bytes. (Presigned uploads → see Lesson 45, Object Storage.)

5. Data Flow — upload to playable

YouTube is a pipeline, so trace the bytes once before drawing boxes:

  1. Upload: client splits the file into ~5–10 MB chunks and PUTs each to S3 via presigned URLs; backend tracks chunk status for resumability.[1]
  2. Store raw: on the final chunk, S3 assembles the object and fires an ObjectCreated event.
  3. Transcode: the event enqueues a job; a worker fleet runs a DAG — split into 2–10s segments, transcode each into multiple codecs/resolutions, process audio.
  4. Segment + manifest: workers write segments to S3 and generate the manifest (the index of every variant + segment URL).
  5. Distribute: segments + manifest are served via CDN; metadata is flipped to READY with the manifestUrl set.

6. High-Level Design

Map each requirement to a component and follow a request through.

ComponentRole

Queue + Transcoding workersAsync DAG-based processing fleet, orchestrated (e.g., Temporal).[1]

Watch path: GET /v1/videos/{id} → Video Service → Cassandra (or cache) → returns manifestUrl → client fetches manifest from CDN → client requests segments from CDN, adapting quality as it goes. The app tier is touched once, for tiny JSON; all heavy bytes flow edge → client.

7. Deep Dives

This is 60% of the interview. Four hard parts, each with the alternative and a justified pick.

Deep Dive 1 — Resumable upload + async transcoding pipeline

A 10 GB upload over a flaky connection will fail mid-flight. A single PUT means restarting from zero — unacceptable. So: the client splits the file into ~5–10 MB chunks (each with a fingerprint hash), the backend records a chunk list as NotUploaded, and the client PUTs chunks directly to S3 via presigned URLs, reporting each ETag back. On resume, the client re-reads metadata and skips chunks already marked Uploaded.[1]

Transcoding is the expensive, slow part — minutes to hours of CPU — so it must be asynchronous. The S3 ObjectCreated event enqueues a job (see Lesson 07, Messaging & Async); an autoscaling worker fleet pulls jobs and runs a DAG with ffmpeg: split → transcode-per-format → audio → manifest → mark ready. Intermediate files live in S3, URLs passed between stages.[1]

ChoicePick & why
Sync vs async transcodeAsync. Upload returns instantly; processing happens off the request path. Decouples spiky load.
One job vs DAG of stagesDAG. Resolutions transcode in parallel; a failed stage retries without redoing the whole video. (Worker patterns → Lesson 10.)
Queue vs cron-poll S3Event → queue. No polling lag, natural backpressure, at-least-once retries.

Deep Dive 2 — Adaptive bitrate streaming

Why not just download the file? At 10 GB it's a 13+ minute wait before playback, and a phone on 3G never finishes.[1] The fix is two-part: segment the video into 2–10s chunks, and produce each segment at multiple bitrates/resolutions. A manifest (HLS .m3u8 or MPEG-DASH .mpd) indexes every variant and segment URL.

The player downloads the manifest, fetches the first low-bitrate segment to start fast, then continuously measures throughput: bandwidth improves → request higher-bitrate segments; it degrades → drop down. Quality adapts per-segment, so a network dip causes a resolution drop, never a stall.[1]

Why segments are the keystone. Segmentation is what makes both adaptive bitrate and CDN caching possible. Small, immutable, independently-addressable files can be cached at the edge, requested à la carte, and swapped mid-stream. HLS vs DASH is a near-coin-flip (HLS = universal Apple/device support; DASH = codec-agnostic, open standard) — name both, pick HLS for reach, move on. Don't burn time here.

Deep Dive 3 — Global delivery via CDN

Recall the capacity math: serving 100M streams from origin S3 is impossible and bankrupting. The CDN is the answer to the dominant NFR. Segments and manifests are immutable, cacheable assets — perfect CDN payloads. They're pushed/pulled to edge PoPs near viewers, so a stream is served from a city away, not a continent away.[1]

ConcernHow the CDN handles it
LatencyBytes served from the nearest edge → fast first-segment, low RTT for the next.
Origin offloadHot videos hit cache, not S3 — solves the "viral video" hotspot.[1]
CostEdge egress < origin egress; cache hit ratio is the lever that controls the bill.

The cost story is the staff insight: the read:write ratio is extreme — a viral video is uploaded once and watched millions of times.[1] The CDN, not the database, is what makes that economically survivable. Tune for cache hit ratio; consider tiered caching and pre-warming for predictable hits (premieres).

Deep Dive 4 — View count at scale

A naive UPDATE ... SET views = views + 1 per watch creates a write hotspot on the hottest videos — exactly the rows everyone reads. And users don't need an exact count; "1.2M views" is fine. So relax consistency: counts are approximate and eventually consistent.

ApproachTradeoff
Sync increment in DBAccurate but hot-row contention; doesn't scale to viral.
Async aggregation (pick)Watch events → stream → batch/windowed aggregate → write count periodically. Smooths writes.
Probabilistic / sketchesHyperLogLog for unique views; trade exactness for tiny memory at extreme scale.

Emit a lightweight watch event, aggregate it asynchronously, and write the rolled-up count back on an interval. Same counting-at-scale machinery as Lesson 22 — name the pattern and the interviewer knows you've seen it.

★ Staff-level signal The three load-bearing decisions are async transcoding, adaptive-bitrate segmentation, and the CDN — say so explicitly and structure your deep dives around them. The senior-vs-staff tell is the capacity insight: candidates who optimize the metadata DB have missed the problem. Articulate that egress bandwidth is the dominant cost and scaling axis, that segmentation is what makes both ABR and edge caching possible, and that the app tier must never proxy video bytes. Treat HLS-vs-DASH as a quick named tradeoff, not a tangent — knowing what not to over-explain is itself the staff move.[1]

Check yourself — retrieval practice

Answer from memory before scrolling back up.

1. What is the dominant cost and scaling axis for YouTube?

Uploads are ~12/s and storage is cheap; serving 100M streams/day is tens of Tbps — bandwidth dominates.

2. Why must transcoding run asynchronously off the request path?

Transcoding takes minutes to hours; an event enqueues a job for an autoscaling worker fleet so upload returns instantly.

3. What makes both adaptive bitrate and CDN edge caching possible?

Small immutable segments can be cached at the edge, fetched à la carte, and swapped mid-stream as bandwidth changes.

4. Why is an approximate, async view count the right choice?

Users don't need exactness; aggregating watch events asynchronously avoids contention on the hottest rows.
