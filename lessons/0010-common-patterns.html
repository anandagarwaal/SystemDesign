Common Patterns

The handful of recurring sub-problems behind every case study — and the go-to solution for each.

Why this lesson, for your mission: Almost every L6/L7 design problem decomposes into a few recurring sub-problems you have seen before. Ticketmaster is "contention." A photo app is "large blobs." A chat app is "real-time updates." Recognizing the pattern fast — and reaching for the simplest adequate mechanism — is what separates a senior who reinvents the wheel from a staff engineer who names the wheel and moves on to the part that's actually hard.[1]

The mental model: problems, not technologies

A case study is rarely novel end-to-end. Under the surface it is a specific mix of six or seven canonical sub-problems, each with a small menu of standard answers.[1] Interviews reward the engineer who can say "this is the contention problem, here are the three ways to solve it, and here's why I'd pick the cheapest one that holds." Memorize the menus below; spend your interview minutes on the selection, not the discovery.

Pattern 1 — Real-time updates

Clients need data as it changes, not when they next ask. Lesson 02 walked the delivery ladder; here is the recap, then the fan-out layer that interviews actually probe. Default to the simplest rung that meets the latency need — HelloInterview explicitly recommends starting with polling until it stops serving you.[1]

MechanismDirectionReach for it when
PollingClient pulls on a timerSeconds-stale is fine; simplest possible (Bitly stats, job status)
Long-pollingClient holds request openNear-real-time, low message rate, no new infra
SSEServer → client, one wayServer pushes a stream (notifications, live scores)
WebSocketFull duplex, persistentBidirectional, high rate (chat, collaborative editing, games)

Fan-out: getting an event to the right connections

SSE/WebSocket give you a pipe to one client. The hard part at scale is: an event happens on server A, but the interested user is connected to server B. The standard answer is a connection-server + pub/sub tier:

  • Stateful connection servers hold the open WebSocket/SSE connections and a local map of userId → socket.
  • A pub/sub bus (Redis Pub/Sub, or Kafka for durability) decouples publishers from subscribers.[1] Each connection server subscribes to the channels for the users it holds.
  • When a write happens anywhere, it PUBLISHes to the channel; every connection server holding a relevant socket gets the message and pushes it down the wire.
  • For heavier routing, place connection servers in a consistent hash ring so a given user always maps to the same server.[1]

Pattern 2 — Contention & concurrency (the double-booking problem)

Two users try to buy the last seat, bid on the same auction, or debit the same balance at the same instant. Without coordination you double-book. "Databases are built around problems of contention"[1] — so the cheapest correct answer usually lives inside the database, not in a separate locking service. Walk the menu from cheapest to heaviest:

MechanismHow it worksReach for it when
Atomic / conditional writeOne statement does check-and-set: UPDATE seats SET held=:u WHERE id=:s AND held IS NULL. Affected-rows = 0 means you lost.The fight is over one row. Start here — almost always enough.
Optimistic concurrency (OCC)Read a version, write back with WHERE version=:v (compare-and-swap). Mismatch → retry.Conflicts are rare; you read-modify-write across fields. Cheap when contention is low.
Pessimistic lockSELECT ... FOR UPDATE holds a row lock for the whole transaction.Conflicts are likely and retries are expensive; you must hold across multiple steps.
Distributed lockA key in Redis (SET k v NX PX 30000) gates access across services / non-transactional resources.The contended resource isn't a single DB row (e.g. a held inventory count spanning systems).
Decision rule.
  • One row, simple update? Atomic conditional write. Done.
  • Read-modify-write, low conflict? OCC with a version column — no locks held, scales reads freely.
  • High conflict or a multi-step transaction? Pessimistic FOR UPDATE — OCC would just thrash on retries.
  • Resource outside one DB? Distributed lock with a TTL (so a dead holder can't deadlock you).
★ Staff-level signal Reach for the simplest mechanism that's correct. A surprising number of candidates jump straight to a Redis distributed lock for what is one row in Postgres — that's an atomic conditional write, and it's both faster and impossible to get wrong with TTLs and clock skew. Distributed locks are famously hard to make safe (fencing tokens, expiry races). Show you'd pay that complexity only when the resource genuinely spans systems. Naming the cheaper option first, then justifying when you'd escalate, is the move.

Pattern 3 — Scaling reads

Reads are usually the first wall you hit; read-to-write ratios of 100:1 are common.[1] Apply these in order — each is cheaper and less invasive than sharding the write path:

LeverWhat it buysCost / watch-out
IndexingTurns scans into lookups; first thing to checkSlows writes slightly; pick the right keys
Caching (Redis)Absorbs hot reads in memory, microsecond latencyInvalidation is the hard part; pick a TTL/strategy
CDNServes static/edge content near the userBest for cacheable, public-ish assets
Read replicasHorizontal read capacity; offload the primaryReplication lag → stale reads; route accordingly
DenormalizationPre-join data so a read is one fetchWrite-time fan-out and consistency burden

Pattern 4 — Scaling writes

A single DB server caps out long before reads do.[1] The write-side menu:

Pattern 5 — Large blobs & files

The cardinal rule: do not push gigabytes through your application servers. They become the bottleneck and you pay for the bandwidth twice.[1] The standard flow keeps bytes out of your app entirely:

  • Store the bytes in object storage (S3 / GCS), the metadata in your DB.
  • Client asks your app for a presigned URL; the app authorizes and returns a short-lived signed URL.[1]
  • Client uploads/downloads directly to/from S3 — resumable, with progress, no app hop.[1]
  • S3 fires an event notification on completion so your app can update state.[1]
  • Serve reads through a CDN with signed URLs for low latency and access control.[1]

Pattern 6 — Long-running tasks

Video encoding, report generation, bulk exports — anything that outlasts a request must come off the request path. The pattern is uniform: accept, enqueue, ack with a job id, process async, report status.[1]

  • Web server validates the request, pushes a job to a queue (Redis/Kafka), and returns a jobId in milliseconds.[1]
  • A separate worker pool consumes the queue, scaling independently of the API tier.[1]
  • Client learns the result by polling GET /jobs/:id or via a push (SSE/WebSocket) — this is Pattern 1 again.
  • Add a dead-letter queue for jobs that keep failing so they don't block the line.[1]
  • For multi-step workflows that must coordinate and retry, escalate to a durable workflow engine (Temporal, Step Functions).[1]

Pattern 7 — Multi-step processes

Some operations span several services that each own their own database, so there is no single transaction to wrap them in: place an order → charge the card → reserve inventory → notify shipping. If step 3 fails, steps 1–2 are already committed elsewhere. You cannot ROLLBACK across service boundaries, so you manage the workflow explicitly and make each step idempotent and retryable, undoing earlier work with compensating actions (a refund, not a rollback).[1] This is the saga pattern, and it comes in two shapes:

  • Orchestration — a central coordinator calls each step in turn and drives compensations on failure. Easy to reason about and observe; the coordinator is the thing to make durable.
  • Choreography — each service emits an event, the next service reacts. No central brain, looser coupling, but the end-to-end flow is implicit and harder to debug at scale.
  • Don't lose the trigger. Use a transactional outbox — write the state change and the "to-emit" event in the same local transaction, then a relay publishes it — so a crash between commit and publish can't drop the next step. Pairs with the messaging tier from Lesson 07.
  • When it gets gnarly, reach for a durable workflow engine (Temporal, Step Functions) that persists each step's state and resumes after crashes — the same escalation as Pattern 6, now coordinating multiple services.
★ Staff-level signal The senior answer is "use a saga." The staff answer adds the failure reasoning: at-least-once delivery means steps repeat, so every step must be idempotent (dedupe on an operation key); you accept temporary inconsistency and converge via compensations; and you justify orchestration over choreography (or vice-versa) by how much you value central observability versus loose coupling. You see this exact pattern in Payment System and Job Scheduler.

How this shows up in the interview

When you hear the prompt, silently tag the sub-problems before you draw a single box. "Design Ticketmaster" → contention on seats + scaling reads on the event catalog. "Design YouTube" → large blobs + long-running tasks (transcode) + scaling reads via CDN. "Design a payment flow" → multi-step process (saga + outbox) + contention on balances. Then, in your deep dives, walk the menu and justify the cheapest adequate pick. Naming the pattern buys you credibility; picking the simple-but-correct mechanism buys you the staff bar.

Check yourself — retrieval practice

Answer from memory before scrolling back up.

1. Two users race to claim the single last seat in one DB row. What is the first mechanism to reach for?

It's one row, so a single conditional UPDATE (affected-rows tells you who won) is the cheapest correct option. Save locks for cross-system resources.

2. A user uploads a 4 GB video. Where should the bytes flow?

Never route blobs through app servers. Hand out a presigned URL so the client uploads straight to S3; an event notifies you on completion.

3. An event happens on server A but the user is connected to server B. What bridges them?

Connection servers hold the sockets; a pub/sub tier (Redis/Kafka) fans the event out to whichever server holds the relevant connection.

4. Read-modify-write on a row where conflicts are rare. Which concurrency control fits best?

With rare conflicts, OCC holds no locks and only retries on the occasional version mismatch — cheaper and more scalable than pessimistic locking.

5. A charge succeeds but the inventory step fails, across two separate services. How do you recover?

There's no cross-service rollback. A saga undoes committed work with compensating actions (refund), and each step is idempotent so retries are safe.
