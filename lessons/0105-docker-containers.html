Deep Dive: Docker & Containers

Not a tiny VM — a normal Linux process the kernel has been told to lie to about what it can see and use.

Why this lesson, for your mission: At L6/L7 "we'll containerize it" is a throwaway phrase the interviewer will test. They want to know you understand that a container is just a process with three kernel tricks applied — namespaces for isolation, cgroups for resource limits, and a union filesystem for layered images — and that this is precisely why containers start in milliseconds, ship reproducibly, and underpin Kubernetes. The staff move is also naming the limit out loud: a shared kernel is not the security boundary a VM gives you.[1]

What it is — containers vs VMs

A container packages an application together with its dependencies, libraries, and config into one immutable image, then runs it as an isolated process on a host.[2] The defining fact: containers share the host's Linux kernel. There is no guest operating system inside — the container is a regular process the kernel has been configured to isolate.[1] A virtual machine, by contrast, runs a full guest OS on top of a hypervisor that emulates hardware; every VM carries its own kernel, drivers, and boot sequence.

That single difference explains everything downstream. Because a container skips the guest OS, its image is megabytes not gigabytes, it boots in milliseconds not seconds-to-minutes, and you can pack far more containers than VMs onto the same box.[2] The cost is the flip side of the same coin: sharing a kernel means weaker isolation than a VM's hardware boundary — covered in the limits section below.

Internals — how a Linux container actually works

"Container" is not a kernel object. There is no container syscall. A container is an emergent illusion built from three independent Linux features that Docker (via a runtime like runc) composes around one process.[3] Knowing these three by name — and which job each does — is the whole deep dive.

1. Namespaces — what the process can see

Namespaces partition kernel resources so that a process inside one sees only its own slice of the system and believes it is alone.[4] Docker creates a fresh set of namespaces for each container; the process inside gets PID 1, its own network stack, its own mount table.[3] The kernel maintains several namespace types:

NamespaceIsolates
pidProcess IDs — the container sees its app as PID 1, not host PIDs[4]
netNetwork interfaces, IPs, ports, routing tables[4]
mntMount points — its own view of the filesystem tree[4]
utsHostname and domain name[4]
ipcInter-process comms — shared memory, semaphores[4]
userUser and group IDs — root inside can map to non-root outside[4]

2. cgroups — what the process can use

Namespaces hide the rest of the system; they do nothing to stop one container from eating all the CPU and RAM. That is the job of control groups (cgroups), the kernel feature that meters and caps the resources a group of processes may consume — CPU, memory, block I/O, and more.[5] When you run docker run --memory=512m --cpus=1.5, Docker is writing those limits into a cgroup.[3] Without cgroups a noisy-neighbor container could starve every other tenant on the host, so cgroups are what make dense multi-tenant packing safe and predictable. Namespaces isolate visibility; cgroups isolate consumption — say it that way and the distinction lands.

3. Union / overlay filesystems — layered images & copy-on-write

The third trick is the filesystem. A Docker image is not one blob — it is a stack of read-only layers, and a union filesystem (today usually overlayfs) presents that stack as a single merged directory tree.[6] Each instruction in a Dockerfile (FROM, RUN, COPY) produces one new layer on top of the previous ones. When a container runs, Docker adds one thin writable layer on top; the read-only image layers underneath are untouched and shared.[6]

This is copy-on-write: reads come straight from the shared lower layers, and only when the container modifies a file is that file copied up into the writable layer.[6] The payoff is large: a hundred containers from the same image share one on-disk copy of the base layers, so they are cheap to start and cheap to store. It also means container writable layers are ephemeral — destroy the container and those writes vanish — which is why persistent data belongs in volumes, not the container.

The build cache & registries

Because layers are content-addressed and stacked, Docker can cache them. On a rebuild it reuses every layer up to the first Dockerfile instruction whose inputs changed, then rebuilds only from there down.[7] This is why ordering matters: put rarely-changing steps (installing dependencies) before frequently-changing steps (copying your source) so a code edit doesn't bust the expensive dependency layer. Registries (Docker Hub, ECR, GCR) store and distribute images; docker push/pull moves layers, and shared base layers are deduplicated so only missing layers transfer.[2] This layer model is also what powers fast rollbacks in CI/CD pipelines.

In a design, containers are the layer that makes horizontal scaling believable: identical stateless instances behind a load balancer, each spun up from one image, each disposable. That uniformity is exactly the contract an orchestrator needs to do its job — which is why every Kubernetes discussion (Lesson 104) sits directly on top of this lesson.

When NOT to / the limits

The boundary you must name: a container is not a security sandbox like a VM.
  • Containers share the host kernel, so a kernel exploit or container escape can reach the host and its siblings — the isolation is process-level, not hardware-level.[1]
  • For hostile multi-tenant workloads (running untrusted customer code) reach for stronger isolation: a VM per tenant, or microVM/sandbox runtimes (Firecracker, gVisor, Kata).
  • Containers are ephemeral & stateless by design — the writable layer dies with the container, so databases and durable state need external volumes or managed stores, not the container itself.[6]
  • They don't run a different kernel: a Windows container needs a Windows host; "Linux containers on Mac/Windows" actually run inside a hidden Linux VM.
★ Staff-level signal Seniors say "we'll put it in a container." Staff candidates explain the mechanism in one breath — "a container is just a process with namespaces for what it sees, cgroups for what it uses, and an overlay filesystem for layered copy-on-write images" — and then proactively name the ceiling: "but it shares the host kernel, so it's not a security boundary; for untrusted tenants I'd isolate with VMs or a microVM runtime."[1] They also resist over-reaching: not every workload needs Kubernetes, and they won't volunteer a Dockerfile when the question is about architecture. Knowing the three primitives, why startup is fast, and exactly where the abstraction is not safe is the simple-by-default judgement the bar rewards.

In the interview

When you draw a service box and say "containerized," be ready for the predictable probes. "Why containers over VMs here?" — answer with shared kernel, fast startup, and reproducible images, not buzzwords.[2] "How does isolation actually work?" — namespaces (see) + cgroups (use) + overlay FS (layers); naming the trio reads as hands-on depth. "Any risk?" — that's your cue to volunteer the shared-kernel security caveat before they corner you. Don't drift into Dockerfile syntax or a layer-by-layer tour unless asked; pick the abstraction the requirement needs and move up the stack to orchestration.

Check yourself — retrieval practice

Answer from memory before scrolling back up.

1. What is the core structural difference between a container and a VM?

Containers share the host kernel and run as isolated processes; VMs each ship a full guest OS.

2. Which kernel feature LIMITS how much CPU and memory a container uses?

cgroups meter and cap CPU, memory, and I/O; namespaces isolate visibility, not consumption.

3. What does copy-on-write give a running container's filesystem?

Reads hit shared lower layers; only modified files copy up into the thin writable layer.

4. Why is a container NOT a security boundary equal to a virtual machine?

Shared-kernel isolation is process-level; a kernel exploit or escape can reach the host and siblings.
