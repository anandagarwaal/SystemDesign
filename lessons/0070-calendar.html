Design a Calendar Service (Google Calendar)

Events, invites, recurrence, and free/busy — where the hard parts are time math and consistency, not raw scale.

Why this lesson, for your mission: A calendar looks like CRUD, and that is the trap. Seniors store events and move on; staff candidates spot the three landmines — recurring events (store the rule, don't materialize a million rows), free/busy across many calendars (a range query that must not double-book a room), and timezones (store UTC + the original zone, never a naive local time). Naming those before being asked is the whole signal at L6/L7.

Phase 1 · 0–5 minClarify the problemPin scope and the few NFRs that will drive every later decision.

Ask before you design

  • “Are recurring events and exceptions in scope?” — Recurrence decides whether we store rules or expanded rows.
  • “Do we book shared resources like meeting rooms?” — Room booking needs strong consistency to prevent double-booking.
  • “Which reminder channels and how precise must reminders be?” — Reminders need a durable, time-indexed pipeline.

Functional Requirements

Scope to what a calendar must do; say the rest aloud as out of scope.

The user should be able to…Detail
Create & edit eventsTitle, start/end, location, attendees; edit or delete later.[1]
Invite attendees + RSVPAdd guests who each get accepted / declined / tentative status.[1]
Create recurring events"Every weekday", "first Monday monthly" — one rule, many occurrences.[2]
See free/busy + room suggestionsQuery several calendars for open slots; suggest a free meeting room.
Get remindersA push/email/popup notification N minutes before an event.

Out of scope (state this aloud): video-call provisioning, attachments, calendar sharing/ACL UX, and external interop via iCalendar feeds — we model the core engine, not every Google feature.

Non-Functional Requirements

PropertyTarget / priority
Consistency (invites & booking)Strong on the write path that matters: an RSVP and especially a room booking must be read-your-writes and free of double-booking. Read-heavy views can lag slightly.
AvailabilityHigh — people live in their calendar all day; reads stay up even if a region degrades. Lean AP for views, CP for the room-booking transaction.
Low latencyMonth/agenda view in <200 ms p99; this drives expanding recurrence at read time fast, or caching expansions.
DurabilityAn event never silently disappears — it lives in a replicated, backed-up store.

The tension to name: a calendar is overwhelmingly read (everyone refreshes their day) but the few writes that conflict — two people grabbing the last room — need real isolation. So most of the system is an eventually-consistent read path with one small, strongly-consistent booking core.

Phase 3 · 10–17 minAPI & data modelLock the contract and the storage shape before drawing boxes.

Core Entities & API

Event — the source of truth: time, recurrence rule, organizer, timezone.[2] Attendee — a (event, user) join row carrying RSVP status, so a 500-person invite is 500 small rows, not one fat blob. Calendar — a container a user owns or subscribes to; resources (rooms) are calendars too, which is what lets us book a room like an attendee.

EndpointPurpose
POST /v1/eventsCreate an event: { start, end, tz, rrule?, attendees[] }. Returns eventId.
PATCH /v1/events/{id}Edit; for recurring, a scope of this / this_and_following / all.
PUT /v1/events/{id}/rsvpSet the caller's status to accepted / declined / tentative.
GET /v1/calendars/{id}/events?from=&to=List occurrences in a window (recurrence expanded server-side).
POST /v1/freebusyBody { calendarIds[], from, to } → merged busy blocks + free slots.
POST /v1/rooms/bookAtomically reserve a room for a slot; fails if already taken.

The acting user is derived from the auth token, never sent in the body.

Data Model

Events store a rule, not rows: rrule plus a precomputed series_end_utc (or open-ended) so a window query can find recurring series whose span overlaps the window, then expand them. One-off changes live in an exceptions table keyed by the original occurrence start. Times are stored as UTC instants plus the IANA zone. Room bookings are protected by a database exclusion constraint on overlapping time ranges.

Staff answer: Each attendee has their own RSVP and appears on their own calendar view; small rows make a 500-person invite and individual updates cheap.

Check yourself

Why store attendees as separate rows rather than a JSON list on the event?

500 people changing RSVPs on one blob = 500 conflicting rewrites. Rows make each update small and isolated, with a reverse index per user.

Picture 500 attendees all clicking 'Accept' within a minute on one JSON blob.

Why model a meeting room as a calendar/attendee?

Rooms get free/busy, invites and booking for free; the only special part is the overlap constraint.

What features does a room need? Which of them does a calendar already have?

High-Level Design

A read-optimized core with one small strongly-consistent booking path:

ComponentRole
API / Event serviceValidates, writes events & attendees, expands recurrence for range reads.
Event DBDurable store sharded by calendar_id; holds events (with RRULE), attendees, exceptions. Source of truth.
Free/Busy serviceRange-queries many calendars, merges busy intervals, returns open slots & room candidates.
Booking serviceThe CP island: takes a row lock / unique constraint on (room, slot) so a room is booked exactly once.
Reminder pipelineRegisters a trigger with the job scheduler; fan-out goes to the notification service.
Cache / read replicasServe hot month/agenda views at <200 ms; absorb the 100:1 read skew.

Flow: create event → API writes the Event (+ RRULE) and Attendee rows → if attendees include a room, the booking service reserves it transactionally → reminders are registered with the scheduler. On a view read, the Event service pulls the window, expands recurrence on the fly, and serves from cache/replicas.

★ Staff-level signal Three sentences win this round: (1) store the recurrence rule and expand at read time, never materialize every instance; (2) model a room as a calendar/attendee and book it with a DB uniqueness/lock so it can't double-book; (3) store every time as UTC + the originating IANA zone, not naive local time. Volume, sharding, and CRUD are the shallow 40% — spend your depth here.

Phase 5 · 27–47 minDeep dives & tradeoffsGo deep where the system breaks; compare alternatives and justify the pick.

Deep Dives

1 · Event model & recurring expansion — store the rule, not the rows

The naive design writes one row per occurrence. "Daily standup forever" then becomes ~10k rows, editing the series rewrites all of them, and storage explodes. The disciplined design stores a single event with a recurrence rule and computes occurrences when needed.

ApproachHowTradeoff
Materialize instancesPre-write every occurrence as its own row.Trivial reads, but unbounded storage and painful "edit the whole series" — bad for infinite recurrence.
Store RRULE, expand on readKeep one event with an RRULE (RFC 5545); generate occurrences in the queried window.[2]Tiny storage, cheap edits; expansion is CPU at read time — bound it to the window and cache it.
Hybrid + exceptionsStore the rule plus override rows (EXDATE / modified single instances).[2]Best of both: rule stays compact, one-off changes ("move just this Tuesday") are small deltas.
Pick & justify: Store the RRULE plus an exceptions table, expand only inside the requested date window, and cache the expansion for hot views. "Edit this event" inserts an exception/override; "edit this & following" splits the series (end the old rule, start a new one); "edit all" rewrites one rule. This keeps a 30-year daily meeting as one row and makes every edit O(1) instead of O(occurrences).

2 · Free/busy across calendars & conflict-free room booking

Free/busy is an interval-merge problem: pull each calendar's busy blocks in [from, to], sort by start, merge overlaps, and the gaps are free slots. The room-booking write is the dangerous part — two organizers can race for the last room and both "succeed" without isolation.

Concurrency controlHow it stops double-booking
Read-then-write check"Is it free? then insert." Broken under races — both readers see free and both write (TOCTOU).
Unique constraint on (room, slot)Model the booking as a row the DB rejects on duplicate; the loser gets a clean conflict error. Simple and correct for discrete slots.
Row lock / serializable txnSELECT … FOR UPDATE the room, check overlap, insert — the DB serializes contenders so only one wins arbitrary ranges.
Distributed lockLock per room key in Redis/etcd before booking. Use only across services without a shared DB; adds a dependency.
Pick & justify: Treat the room as a calendar and make the booking a single transactional write guarded by a row lock or a uniqueness constraint on overlapping slots — the database's concurrency control is your double-booking defense, no read-modify-write window. This is the same first-to-commit-wins reservation logic as seat selection in Ticketmaster (Lesson 15); a meeting room is just a seat with a calendar.

3 · The reminder / notification pipeline

A reminder is "fire a notification N minutes before an event." The anti-pattern is polling the event table every minute for "what's due" — that's a scan at calendar scale and bunches violently at the top of the hour. Reuse infrastructure you've already designed instead of rebuilding timing.

Pipeline:
  • On create/edit, compute remind_at = start − lead_time and register a trigger with the job scheduler (Lesson 34), indexed by next-run-time so "due" is a range read, not a scan.
  • At fire time the scheduler enqueues a job; a worker fans out to attendees via the notification service (Lesson 46) (push / email / popup).
  • Idempotency key = (eventId, occurrence, userId) so an at-least-once retry can't double-send a reminder.
  • For recurring events, register only the next occurrence's reminder and roll forward after it fires — never pre-schedule infinity.

State the breadth/depth ratio aloud: you didn't reinvent a timer; you delegated timing to the scheduler and delivery to the notification service, and spent your words on the calendar-specific edges — recurrence and idempotency.

4 · Timezone & DST correctness

This is where calendars quietly break. Store an instant as a naive "3 PM" and the meeting jumps an hour when daylight-saving flips or the user travels. The rule: store UTC for the instant and the original IANA timezone (e.g. America/New_York), never a fixed offset like -05:00.

CaseCorrect behavior
One-off meetingStore UTC instant + creator's zone; render in each viewer's local zone. The instant is absolute.
Recurring "9 AM daily"Anchor recurrence to wall-clock time in the stored zone, then convert each occurrence to UTC — so it stays 9 AM local even across a DST change.[2]
DST transition dayRecompute the offset per occurrence from the IANA database; a fixed offset would drift by an hour for half the year.
All-day eventStore as a floating date with no zone, so "March 3rd" is March 3rd everywhere — not 23:00 the day before.
Pick & justify: Persist { utc_instant, tz_id, rrule } and resolve offsets from the IANA tz database at expansion time. Recurrence math runs in the event's local wall clock, then each occurrence is converted to UTC for storage and re-rendered per viewer. This single decision prevents the classic "the standup moved itself after the clocks changed" bug, and it's the detail interviewers probe to separate someone who's shipped a calendar from someone who hasn't.

Check yourself

Two organizers both run 'SELECT: is room free?' → both see free → both INSERT. What's the bug and the fix?

Time-of-check vs time-of-use. An exclusion/unique constraint or row lock makes check+insert atomic so exactly one wins.

Between the SELECT and the INSERT, what can the other organizer do?

'9 AM daily' in New York, stored as a fixed UTC-5 offset. What happens in summer?

14:00 UTC is 9 AM at UTC-5 but 10 AM at UTC-4. Anchor recurrence to wall-clock time in the IANA zone and recompute the offset per occurrence.

Convert: 9 AM at UTC-5 = 14:00 UTC. What is 14:00 UTC at UTC-4?

User edits 'this and all following' on a recurring event. What does the data model do?

Split the series: cap the old RRULE, create a new one. O(1), and history stays intact.

Privacy

Calendars reveal where people will be, who they meet, and why (doctor appointments, interviews, legal meetings). Controls: free/busy-only sharing by default (busy blocks without titles); private events hidden even from people with read access; external invites carry only necessary details. Minimization: notification payloads omit sensitive descriptions on lock screens. Deletion: deleting an event removes attendee copies, exceptions, bookings and pending reminders; account deletion transfers or cancels organized events. Residency and retention policies for enterprise tenants.

Wrap-up · 58–60 minClose strongRecap decisions and tradeoffs in 60 seconds; name what you would do next.

Closing Summary (60 seconds)

A calendar service is a read-optimized event store with one strongly consistent booking path. Events store recurrence rules, exceptions and IANA timezones, and are expanded on read for the requested window, with caching. Attendees are per-user rows carrying RSVP state. Free/busy aggregates busy intervals across calendars without exposing details. Room booking checks overlap transactionally on the resource calendar, so rooms can't be double-booked. Reminders are indexed by trigger time and fired by a durable scheduler into notification queues. At 10× we add shards and archive old years.
