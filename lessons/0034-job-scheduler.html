Design a Distributed Job Scheduler

Fire millions of one-off and recurring jobs close to their scheduled time, reliably, even when workers die.

Why this lesson, for your mission: A scheduler is the canonical test of whether you can reason about time and delivery semantics under failure. Seniors describe a cron loop; staff candidates index jobs by next-run-time, pull due work into a queue with a lease + ACK so a crashed worker's job retries, and make execution idempotent. Those three moves are the whole interview.

Phase 1 · 0–5 minClarify the problemPin scope and the few NFRs that will drive every later decision.

Ask before you design

  • “One-off jobs, recurring cron jobs, or both?” — Recurring jobs need next-run rescheduling after each execution.
  • “How precise must execution timing be?” — A ~2-second bound allows polling rather than per-job timers.
  • “Exactly-once or at-least-once execution?” — At-least-once plus idempotent handlers is achievable; true exactly-once isn't.

Functional Requirements

Scope the system to the three things that matter; everything else is out of scope.

The user should be able to…Detail
Schedule a jobRun once at a specific future time (one-off) or on a recurring cron schedule.[1]
Have the job executedThe system runs the job's payload close to the scheduled time.[1]
View status & historyInspect whether a job is pending, running, succeeded, or failed.[1]

Out of scope (state this aloud): cancellation/rescheduling, complex DAG dependencies between jobs, and the business logic inside the job — we deliver the trigger, the user's handler does the work.[1]

Non-Functional Requirements

PropertyTarget / priority
TimelinessJobs fire within a bounded delay of their scheduled time — e.g. within ~2 seconds.[1] This is a soft real-time goal, not a hard guarantee.
ReliabilityAt-least-once execution: every job runs at least once even across worker/coordinator failures. Exactly-once is approximated via idempotency.
ScalabilityMillions of scheduled jobs at rest; high throughput at peak — design toward ~10k jobs/sec executed.[1]
DurabilityA scheduled job survives crashes — it lives in durable storage, never only in memory.

Reliability vs. timeliness is the central tension: firing fast tempts you to keep state in memory, but durability demands it survive a crash. The resolution is "durable store + a poller," developed below.

Say to move on → “Timely, at-least-once execution at scale. Let me size jobs at rest and the fire rate.”

Phase 3 · 10–17 minAPI & data modelLock the contract and the storage shape before drawing boxes.

Core Entities & API

Task — the reusable kind of work (e.g. "send-email").[1] Job — an instance of a task plus its schedule and payload.[1] Execution — one attempt to run a job (status, worker, timestamps) for the history view.

EndpointPurpose
POST /v1/jobsCreate a job: { schedule, payload } where schedule is an ISO timestamp or a cron expression. Returns jobId.
GET /v1/jobs/{id}Fetch a job's current status and recent executions.
GET /v1/jobs?status=List the caller's jobs, filtered by status.
DELETE /v1/jobs/{id}Delete / disable a job (soft-delete so in-flight runs settle).

The owning user is derived from the auth token, never sent in the body.

Data Model

The whole design hinges on one index: a partial index on next_run_at for pending jobs, so "what's due?" is a range read over only the jobs that can fire. Claims are conditional updates with a lease expiry; executions are keyed by (job_id, scheduled_time), which doubles as the idempotency key a handler can dedupe on.

EntityStoreKeysIndexes / access pattern
tasks (task_type, owner_id, handler_url / queue, timeout_s, max_attempts, retry_policy)PostgresPK (owner_id, task_type)Looked up by workers (cached)

Interviewer pushback

“Why separate Job from Execution?”

Staff answer: A recurring job has many runs; executions record each attempt's status and worker for history and retries without mutating the job definition.

Say to move on → “Task, Job and Execution. Now separate deciding what's due from running it.”

Pollers only do cheap index reads and atomic claims; workers lease messages, call the job's handler with an idempotency key, ACK, and write back status and the next run time for recurring jobs. Repeated failures land in the DLQ.

High-Level Design

Five components, with a clean split between deciding what's due and running it:

ComponentRole
API serviceValidates requests, computes the job's next_run_at, writes to the Job DB.
Job DBDurable store of all jobs, indexed by next_run_at. Source of truth.
Poller / schedulerPeriodically queries for jobs whose next_run_at ≤ now and enqueues them.
Execution queueDurable message queue (e.g. SQS/Kafka) buffering due jobs for workers.
Worker poolPulls from the queue, runs the payload, ACKs, writes an Execution record; reschedules recurring jobs.

Flow: create → API writes job with next_run_at → poller sweeps due jobs every tick and pushes them to the queue → a worker leases one, executes, ACKs, records status; if recurring, it computes the next next_run_at from the cron expression and updates the row. Splitting the poller from the workers lets each scale independently — the poller does cheap index reads, the workers do the expensive work.

★ Staff-level signal The interview turns on not scanning all jobs. Index by next-run-time so "what's due?" is a range read, not a table scan. Decouple the poller (decides) from workers (execute) via a durable queue so they scale and fail independently. Everything below is a refinement of those two sentences.

Interviewer pushback

“Why put a queue between the poller and workers?”

Staff answer: The poller decides what's due and workers run it; the queue buffers bursts and gives lease-and-ACK semantics, so either side scales independently.

Say to move on → “Deep dives: finding due jobs, lease-and-ACK execution, avoiding duplicates and scaling workers.”

Phase 5 · 27–47 minDeep dives & tradeoffsGo deep where the system breaks; compare alternatives and justify the pick.

Deep Dives

1 · Finding due jobs efficiently — never scan

The trap is a poller that reads every job each tick to check its time. At 100M jobs that's a full scan per second — dead on arrival. The fix is to make "due jobs" a cheap, ordered lookup.

ApproachHowTradeoff
Indexed DB queryB-tree index on next_run_at; poll WHERE next_run_at ≤ now ORDER BY next_run_at LIMIT N.Simple, durable, easy to reason about. Polling interval bounds latency; index writes on every reschedule.
Time-bucketed tablePartition jobs into buckets per minute/second; poller reads only the current bucket.Keeps the working set tiny and shards naturally by time. Hot bucket if many jobs share a timestamp.
Priority queue / heapIn-memory min-heap keyed on next-run-time; pop the earliest.O(log n) and very low latency, but volatile — must be rebuilt from the durable store on restart.
Delay queuePush to a broker that holds a message until its delay elapses (SQS delay, RabbitMQ TTL+DLX).Offloads timing to infra. Per-message delay caps (e.g. SQS 15 min) hurt far-future jobs.
Pick & justify: For far-future and recurring jobs, keep the durable store as source of truth, indexed/bucketed by next_run_at, and run a poller that sweeps due rows into the execution queue every ~1s. Bound timeliness with a hybrid: the poller hands jobs due in the next few minutes to a delay queue or in-memory heap for sub-second firing, while the index handles everything farther out. This hits the ~2s target[1] without scanning and without losing jobs on restart.

2 · Reliable execution semantics — lease + ACK

A worker can crash mid-job. If we mark a job "done" when we hand it out, a crash silently drops it (at-most-once). We want at-least-once: the job must be retried until something confirms success.

Lease / visibility timeout + ACK:
  • When a worker pulls a job, it isn't deleted — it becomes invisible for a lease window (the visibility timeout).
  • On success the worker ACKs, which deletes the message / marks the row complete.
  • If the worker crashes, it never ACKs; the lease expires, the job becomes visible again and another worker re-runs it.
Set the lease longer than the expected execution duration, or have long jobs heartbeat to extend it, so a slow-but-healthy job isn't re-run underneath itself.

At-least-once means duplicates are possible: a worker can finish, then crash before ACKing, and the job runs again. The cure is idempotency — give each execution an idempotency key (e.g. jobId + scheduled-time) so a repeat is a no-op. This is the at-least-once + idempotency ≈ exactly-once pattern from Lesson 07, and the same delivery-semantics reasoning behind message queues in Lesson 07. True exactly-once delivery across a network is impossible; exactly-once effect via idempotency is what you actually deliver.

3 · Avoiding duplicate execution under multiple schedulers

For availability you run several poller instances. Without coordination, two pollers read the same due rows and enqueue the same job twice — duplicate executions before a worker even touches it.

MechanismHow it prevents double-enqueue
Leader electionOne poller is elected leader (ZooKeeper/etcd lease) and is the only one that sweeps. Simple, but the leader is a throughput ceiling and a failover gap.
Distributed lockPollers take a lock per time-bucket before claiming it, so only one owns a bucket. Adds lock-service dependency and contention.
Atomic claimEach poller claims rows with a conditional update — UPDATE … SET status='claimed', owner=me WHERE id IN (…) AND status='pending'. The DB serializes it; only one poller wins each row.
Pick & justify: Prefer the atomic claim — it lets every poller run in parallel (no single leader bottleneck) while the database's row-level concurrency control guarantees each job is enqueued once. Combine with the lease+ACK above and you have two independent dedup layers: claim stops double-enqueue, idempotency stops double-effect.

4 · Scaling workers, retries & dead-letter

The execution queue decouples arrival rate from processing rate, so workers scale horizontally — add consumers to absorb the ~10k/sec peak[1] and autoscale on queue depth. The poller stays cheap because it only does index reads; the heavy lifting is in the elastic worker tier.

Failure handling:
  • Retries with exponential backoff + jitter — a failed job is retried after growing delays so a flaky downstream isn't hammered (see Lesson 07).
  • Max attempts → dead-letter queue (DLQ) — after N failures the job moves to a DLQ for inspection instead of looping forever and starving healthy work.
  • Recurring jobs — only schedule the next occurrence after the current one is acknowledged, so a missed fire doesn't compound.

State the breadth/depth ratio out loud: you've gone deep on timing, semantics, and dedup — the parts that fail in production — and kept the API and storage shallow because they're not where this design breaks.

Interviewer pushback

“Two poller instances pick the same due job. What happens?”

Staff answer: Claim atomically with UPDATE … WHERE status=due (or SELECT … FOR UPDATE SKIP LOCKED), so only one poller wins. Workers are idempotent anyway because delivery is at-least-once.

Privacy

The scheduler itself is low-PII, but payloads are opaque tenant data that may contain emails, ids or tokens. Rules: encrypt payloads at rest (envelope encryption per tenant), never log payloads, and cap payload size so tenants store references rather than data. Retention: execution history TTL 30 days; error messages truncated and scrubbed. Deletion: tenant offboarding deletes jobs, executions and DLQ messages, and crypto-shreds the tenant key.

Interviewer pushback

“A tenant's job handler is slow or hangs. How do you protect others?”

Staff answer: Per-tenant queues and concurrency limits, execution timeouts that expire leases, and dead-letter queues after N retries.

Scaling 10× Without Changing the Architecture

10× = ~1B jobs at rest, ~100k fires/s at peak.

ComponentTodayAt 10×Knob turned
Job DB~4 shards, 100 GB~40 shards, 1 TBMore hash shards; each shard's poller works on its own partial index
PollersN instancesOne or more per shardClaim batches with SKIP LOCKED; shorter poll interval
QueueSQS10× messagesNothing structural; per-tenant queues for fairness
Workers~50 nodes~500Autoscale on queue depth
Executions store~1.5 TB/month~15 TB/monthAdd nodes; shorter TTL

First bottleneck: the "top of the minute" thundering herd (cron jobs cluster at :00) — mitigated by jittering recurring jobs and pre-loading the next minute into the near-term timer. What forces a redesign: sub-second precision at hundreds of thousands of timers/s, moving to in-memory timing wheels (alternative B).

Cost of Running

Assumptions: 100M jobs at rest, ~10k fires/s peak (~2k/s average ≈ 5B executions/month), workers make webhook calls (tenant handler compute is not ours), list prices from the course price sheet.

Wrap-up · 58–60 minClose strongRecap decisions and tradeoffs in 60 seconds; name what you would do next.

Closing Summary (60 seconds)

A job scheduler separates deciding what's due from running it. Jobs live in a durable DB indexed by next_run_at; pollers query a small window of due jobs and claim them atomically with SKIP LOCKED, then enqueue them. Workers lease tasks, run them and ACK; expired leases are redelivered, so execution is at-least-once, and idempotency keys give an exactly-once effect. Recurring jobs compute their next run after success, and failures retry with backoff into a dead-letter queue. At 10× we add shards, per-shard pollers and workers.

Check yourself — retrieval practice

Answer from memory before scrolling back up.

1. Why is scanning the whole job table each tick the wrong design?

At 100M jobs a per-tick scan is ruinous; index/bucket by next_run_at so "due" is a range read.

2. What does a lease (visibility timeout) plus ACK actually buy you?

No ACK means the lease expires, the job reappears, and another worker reruns it — at-least-once.

3. At-least-once delivery can run a job twice. What makes that safe?

An idempotency key (jobId + scheduled time) turns a duplicate run into a harmless no-op.

4. Best way to stop two pollers from enqueueing the same due job?

A conditional UPDATE lets the DB serialize the claim so exactly one poller wins each row.
