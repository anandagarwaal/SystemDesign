Design TikTok / Short Video

YouTube taught you to deliver bytes. TikTok is harder: the product is the recommendation feed, and a single perceptible delay between swipes is a failure.

Why this lesson, for your mission: TikTok looks like "YouTube but vertical," and that framing is the trap. The video pipeline (upload → transcode → CDN) is largely solved territory from Lesson 33 — at L6/L7 you should compress it and spend your depth where the product actually lives: the For-You recommendation feed and the prefetch that makes infinite scroll feel instant. The senior-vs-staff tell is recognizing that here the recommendation system and the perceived-latency engineering — not transcoding — are the load-bearing problems.

1. Functional Requirements

Three flows define the product. State them, declare the rest (DMs, search, profiles, duets, ads) out of scope, and buy yourself room for the feed deep dives.

#Users should be able to…Note
1Upload a short video~15–180s, <~100 MB; transcoded to multiple bitrates
2Scroll the For-You feedVertical, full-screen, one video at a time, infinite
3Like / comment / shareLightweight engagement that also feeds ranking

Item 3 is doing double duty: it's a user feature and the signal source that powers item 2. Calling that out early signals you see the system as one loop, not three CRUD endpoints.

2. Non-Functional Requirements

State the target, not just the "-ility." Order signals priority.

NFRTargetDrives
Very low feed latencyNext video plays in <~100ms on swipePrecomputed feed + aggressive client prefetch
Video availabilityHA playback; never a blank screenMulti-region CDN, fallback to generic feed
Recommendation freshnessNew posts & signals reflected in minutesStreaming engagement pipeline, not nightly batch
Read scalabilityExtreme read:write; billions of views/dayCDN for bytes, cached precomputed feeds

Feed latency is the headline. Users swipe several times per minute; any visible spinner between videos breaks the core experience. This single NFR justifies precomputing feeds and prefetching ahead of the user — the two ideas that make this problem "hard."

3. Capacity Estimation

Only the numbers that change a decision. Two reframe the design.

QuantityEstimateDesign implication
Feed reads500M DAU × ~50 videos/day → ~25B views/day → ~300K feed-item reads/sec avg, multiples at peakFeed must be served from cache/precompute; ranking can't run synchronously per swipe.
Engagement events25B views + likes/skips/watch-time → ~10⁵–10⁶ events/secThis firehose is its own system. Needs a streaming pipeline, not row-by-row DB writes.
Uploads~10s of M/day → low hundreds/secTrivial write QPS; same async-transcode pattern as YouTube. Not the bottleneck.
The number that reframes TikTok. Uploads are a rounding error; the action is on the read and signal side. ~25B feed reads/day means you cannot rank on-demand per request, and the engagement firehose (~10⁵–10⁶ events/sec) is a high-throughput stream-processing problem in its own right. The product is a feedback loop running at massive read scale — design for that, not for the upload path.

4. Core Entities & API

Four entities. Video (blob) is deliberately separated from VideoMetadata (a small, queryable row) — that split is itself a deep dive below.

EntityKey fields
Userid, follows, inferred interest profile / embedding
Video (blob)raw + transcoded byte assets in object storage
VideoMetadataid, authorId, caption, status, manifestUrl, counters, tags/embedding
EngagementuserId, videoId, type (like/comment/share/skip), watchMs, ts

The API is small; the user is always derived from the auth token, never a body param.

EndpointPurpose
POST /v1/videosCreate metadata, return presigned upload URL (direct-to-blob)
GET /v1/feed?cursor=Return next batch (~5–10) of ranked videos + their manifestUrls
POST /v1/videos/{id}/engagementsRecord like/comment/share; emits an event to the pipeline
POST /v1/videos/{id}/viewsReport watch-time/skip — the strongest ranking signal
GET manifest & segmentsServed directly by the CDN, never the app tier

Two critical moves: bytes upload directly to object storage via presigned URLs and download directly from the CDN (the app tier only touches small JSON), and GET /v1/feed returns a batch so the client can prefetch ahead — see Deep Dive 2.

5. Data Flow — engagement to a better feed

TikTok is a feedback loop, so trace the signal once before drawing boxes:

  1. Watch: client plays a video and emits view + watch-time/skip + any like/comment/share to the ingestion endpoint.
  2. Ingest: events land on a high-throughput log/stream (Kafka) — fire-and-forget, never a synchronous DB write.
  3. Process: stream jobs update per-video counters, per-user interest signals, and training data for the ranking model. (Stream patterns → Lesson 50.)
  4. Recompute: candidate generation + ranking refresh each user's precomputed feed within minutes.
  5. Serve: next GET /v1/feed reads the freshened, ranked list from cache — the loop closes.

6. High-Level Design

Map each requirement to a component, then follow a request through.

ComponentRole
Upload / Video ServiceStateless; mints presigned URLs, serves metadata. Same shape as YouTube's. Behind a load balancer.
Blob Storage (S3)Raw uploads + transcoded segments + manifests — the durability layer (Lesson 45).
Transcoding workersAsync DAG: segment → multi-bitrate transcode → manifest → mark ready (per Lesson 33).
CDNCaches segments + manifests at the edge; absorbs nearly all read bandwidth.
Feed Service + Feed CacheServes precomputed ranked lists per user; the <100ms read path.
Recommendation pipelineCandidate generation → ranking; writes feeds to the Feed Cache.
Engagement pipeline (Kafka + stream)Ingests the event firehose, updates signals and counters.

Scroll path: GET /v1/feed → Feed Service → Feed Cache returns a batch of ranked metadata + manifestUrls → client immediately prefetches the next 1–3 videos' first segments from the CDN → on swipe, the next video is already buffered, so playback is instant. The app tier is touched once per batch for tiny JSON; all heavy bytes flow edge → client, and ranking happens offline, never on the swipe.

7. Deep Dives

This is 60% of the interview. Four hard parts — note the upload pipeline is compressed because it's reuse, while the feed and prefetch get the depth.

Deep Dive 1 — Upload + transcoding pipeline (compressed reuse)

This is largely Lesson 33 at smaller file sizes, and the staff move is to say so and not re-derive it. Client requests a presigned URL and PUTs bytes directly to object storage (blob store, Lesson 45); an ObjectCreated event enqueues an async transcoding job; a worker fleet runs a DAG — split into 2–10s segments, transcode each to multiple bitrates/resolutions, generate an HLS/DASH manifest — then flips metadata to READY with the manifestUrl. Segments and manifests are immutable, so the CDN caches them at the edge and viewers stream from a nearby PoP.

ChoicePick & why
Sync vs async transcodeAsync. Upload returns instantly; CPU-heavy work runs off the request path.
Origin vs CDN deliveryCDN. Immutable segments cache at the edge; origin egress would be ruinous.
Re-derive vs referenceReference. Name it as solved, move depth to the feed — that is the staff signal.

Deep Dive 2 — The For-You feed: candidate generation → ranking → prefetch

You cannot rank TikTok's entire catalog per swipe at ~300K reads/sec — so split the problem into the standard two-stage funnel and serve the result from cache.[2] (Full treatment in Lesson 50, Recommendation Systems.)

StageJob
Candidate generationCheaply narrow billions → ~hundreds: trending pools, followed authors, embedding/ANN similarity to the user's interest vector, fresh content.
RankingA heavier model scores those few hundred on predicted watch-time / engagement, then orders them.[2]

Run this funnel offline/near-line per user and write the ordered list to a per-user Feed Cache; GET /v1/feed is then a fast cache read returning a batch. Prefetch is the other half of "instant": because each response carries 5–10 items, the client eagerly fetches the next 1–3 videos' opening segments from the CDN while the current one plays. On swipe, the next video is already buffered — the <100ms NFR is met by the network being ahead of the user, not by a faster server.

Why precompute + prefetch, not rank-on-read. Synchronous ranking per swipe blows the latency budget and wastes compute on videos never reached. Precomputing decouples expensive ranking from the hot read path; prefetching hides even the CDN round-trip. The tradeoff is staleness (minutes) and wasted prefetch on a fast scroller — both cheap relative to a visible spinner. Pull from the cold cache only when a user exhausts their precomputed list.

Deep Dive 3 — Engagement event pipeline feeding ranking

The freshness NFR ("new signals in minutes") and the ~10⁵–10⁶ events/sec firehose mean engagement can't be synchronous DB writes — that would couple the watch path to the database and melt it.[2] Instead, every view/skip/like/comment/share is emitted fire-and-forget to a partitioned log (Kafka). Stream processors then fan the events out: update per-video counters (approximate, like YouTube's view count), update each user's interest signals, and append to the model's training set.

ChoicePick & why
Sync DB write vs event streamStream. Decouples the watch path; absorbs spikes; enables fan-out to many consumers.
Nightly batch vs streamingStreaming. Batch can't hit "fresh in minutes"; stream updates signals continuously.
Exact vs approximate countersApproximate. Windowed aggregation avoids hot-row contention on viral videos.

Watch-time and skips are the strongest signals — far richer than the sparse like button — which is exactly why the views endpoint reports duration, not just a play. The pipeline turns that firehose into the features that close the feedback loop.

Deep Dive 4 — Storing video metadata vs blobs

Conflating these is a classic mistake. The two have opposite access patterns and belong in opposite stores.

AspectVideo bytes (blob)Metadata (row)
StoreObject storage + CDN[1]Wide-column / KV (e.g. Cassandra)
SizeMBs–GBs per objectBytes–KBs per row
Accessed byCDN edge, streamedFeed/ranking, queried + cached

The metadata row holds the manifestUrl pointer plus the tags/embedding and counters that ranking needs; it's small, queryable, and partitioned by videoId for uniform spread and HA. The blob lives in object storage behind the CDN and is never read by the app tier. Never store video bytes in your database — it destroys the DB's read performance and can't be edge-cached. The row points at the bytes; that pointer is the seam that lets each layer scale on its own axis.

★ Staff-level signal The load-bearing decisions are the precomputed For-You feed, the client prefetch that hides latency, and the streaming engagement pipeline that keeps recommendations fresh — structure your time around those, not the upload path. The senior-vs-staff tell is judgement on where the depth goes: candidates who re-derive transcoding have re-solved YouTube and missed TikTok. Say explicitly that the product is a read-heavy feedback loop, that ranking must be offline because you can't rank ~25B reads/day synchronously, and that <100ms scroll is won by prefetching ahead of the user, not by a faster server. Name the metadata-vs-blob split as obvious and move on — knowing what not to over-explain is itself the staff move.[2]

Check yourself — retrieval practice

Answer from memory before scrolling back up.

1. Why can't the For-You feed be ranked synchronously per swipe?

At ~25B reads/day you precompute the funnel offline and serve from cache; ranking on the hot path is too slow and wasteful.

2. How is the <100ms next-video experience actually achieved?

The feed returns a batch, so the client buffers the next 1–3 videos while the current plays — the network is ahead of the user.

3. Why are engagement events sent to a stream, not written to the DB?

~10⁵–10⁶ events/sec can't be synchronous writes; a log decouples the watch path and feeds many consumers, fresh in minutes.

4. Where should the raw video bytes be stored?

Bytes belong in object storage + CDN; the small metadata row just holds the manifestUrl pointer, keeping each layer scalable.
