Deep Dive: Distributed Locks

A mutex protects a critical section inside one process. But when the "process" is 50 servers, how do you make sure only one of them runs the job — and why is that surprisingly hard to get right?

Why this lesson, for your mission: Contention problems are everywhere in interviews — "only one worker should send this reminder," "two booking servers must not sell the same seat," "run this cron on exactly one node." The naive answer is "use a distributed lock," but a staff candidate knows that distributed locks are leaky: they need a TTL to survive crashes, the TTL creates a correctness hole, and the real fix is often a fencing token or avoiding the lock entirely. Knowing when NOT to reach for one is as valuable as knowing how to build it.

1 of 4

The problem & why a TTL is mandatory

A distributed lock lets multiple machines coordinate so that only one holds a named resource at a time. The minimal recipe with Redis is an atomic conditional set:

SET lock:resource <owner_id> NX PX 30000 — set the key only if absent (NX), with a 30-second expiry (PX).[1] If it succeeds you hold the lock; to release, you delete the key — but only if you still own it (check owner id in a Lua script, so you don't delete someone else's lock).

The TTL is not optional. Without an expiry, a holder that crashes (or is network-partitioned) before releasing would leave the lock held forever — a deadlock that wedges the whole system. The TTL guarantees liveness: the lock auto-releases so progress resumes.[2] But that same TTL is the source of the deepest bug in distributed locking.

The TTL safety hole — and fencing tokens
  • The bug: Client A acquires the lock (30s TTL), then pauses — a long GC pause, slow disk, or network blip — for 31 seconds. The lock expires, Client B acquires it, and now both believe they hold it. A then wakes up and writes, corrupting the resource.[2] A TTL too short fails like this; too long means a crash wedges everyone for ages. There is no safe value.
  • The fix — fencing tokens: the lock service returns a monotonically increasing token with each grant. Every write to the protected resource includes its token, and the resource rejects any write with a token older than the highest it has seen. So A's stale write (token 33) is refused after B's write (token 34) lands.[2] This makes correctness independent of timing — the only truly safe construction.
  • Implication: the protected resource must be able to check the token. If it can't, the lock cannot be made safe under pauses — design around it.
Check yourself

What does SET lock:x owner NX PX 30000 do?

NX = only if not exists (acquire), PX = millisecond expiry (liveness).

NX and PX each mean one thing — reread the recipe line.

Why is a TTL mandatory even though it causes the safety hole?

TTL buys liveness: a dead holder's lock eventually disappears. The price is that a merely-slow holder can lose the lock while still working.

Imagine the holder's machine loses power. Who ever deletes the key?

Picture A (token 33) paused past its TTL while B (token 34) writes. Why does fencing make A's late write harmless?

Correctness moves from timing (which you can't control) to a check at the resource. A can't check reliably itself — it might pause right after checking.

Why wouldn't 'A re-checks before writing' work? A could pause right AFTER checking.

Where the lock should live

BackendHowTrade-off
Redis (single)SET NX PX + Lua releaseFast and simple, but a failover can lose the lock (not safe for strict mutual exclusion).[1]
Redis RedlockAcquire on a majority of N independent nodesMore robust to single-node failure, but its safety under clock/pause assumptions is contested — still needs fencing.[2]
ZooKeeper / etcdEphemeral + sequential znode; lowest sequence winsStrongly consistent (consensus-backed), auto-releases on session loss — the safest choice when correctness matters.[3]
DatabaseConditional row / advisory lockNo new infra; lower throughput, and you own the cleanup.

ZooKeeper/etcd locks (see Lesson 106) are the gold standard because the coordination layer is consensus-backed and the ephemeral node tied to the client's session disappears automatically if the client dies — no arbitrary TTL guesswork, and natural fencing via the sequence number.[3] Redis locks are the pragmatic choice when "mostly once" is acceptable and speed matters.

Check yourself

Why are ZooKeeper/etcd locks the safest choice?

Consensus gives linearizable state; session-tied ephemeral nodes auto-release; sequence numbers give natural fencing.

Single-Redis lock: A acquires on the primary, then the primary dies before replicating. What happens?

Async replication means the new primary may never have seen A's key — two holders. That's why single-Redis locks aren't safe for strict mutual exclusion.

Often you shouldn't lock at all

The strongest move is frequently to avoid the distributed lock:

  • Idempotency instead of mutual exclusion: if running the operation twice is harmless (dedupe by a key), you don't need a lock. This is the preferred fix for "process each message once."
  • Database constraints / conditional updates: a unique constraint or UPDATE … WHERE version = ? (optimistic concurrency) lets the database enforce single-winner without an external lock — the right tool for "don't double-book a seat" (see Ticketmaster, Lesson 15).
  • Single-partition ownership: route all work for a key to one consumer/shard (as Kafka partitions do), so there's only ever one writer by construction.
  • Leader election (via ZK/etcd) for "run on exactly one node" — a lock specialized for singleton work.
★ Staff-level signal A junior says "I'll use a distributed lock" and moves on. A staff candidate first asks "do I actually need mutual exclusion, or just correctness?" — and often replaces the lock with idempotency or an optimistic WHERE version=? update. When a lock is genuinely needed, they specify the TTL for liveness and immediately name its hole: "a GC pause longer than the TTL means two holders, so I need fencing tokens rejected by the resource, or a consensus-backed lock in ZooKeeper/etcd."[2] Knowing that a Redis TTL lock is not safe for strict mutual exclusion — and saying so — is the exact signal interviewers look for.

In the interview

When contention appears: (1) ask whether the operation can just be made idempotent or guarded by a DB constraint / optimistic lock — prefer those. (2) If you truly need a lock, sketch SET NX PX with an owner id and a Lua-checked release, and say the TTL is required for liveness. (3) Pre-empt the bug: "a pause past the TTL allows two holders, so I'll use fencing tokens or a ZooKeeper ephemeral-node lock for strict correctness." (4) For singleton jobs, say leader election. That arc — avoid it, then build it safely, then name the failure mode — is exactly the depth they want.

Comprehensive check

Why must a distributed lock have a TTL?

Without expiry, a holder that dies before releasing wedges the resource forever; the TTL guarantees the lock eventually frees up (liveness).

Reread 'The problem & why a TTL is mandatory'.

What is the core safety hole created by the TTL?

If a holder stalls (GC, network) longer than the TTL, the lock expires and another client acquires it — now two clients act, risking corruption.

Reread the first bullet of the fencing-token box.

How does a fencing token make a lock safe?

Each grant gets an increasing token; the resource only accepts the highest seen, so a stale holder's late write is refused regardless of timing.

Reread the second bullet of the fencing-token box.

What's often the best alternative to a distributed lock?

If the operation is idempotent or a unique constraint / version check can pick a single winner, you avoid the lock's timing pitfalls entirely.
