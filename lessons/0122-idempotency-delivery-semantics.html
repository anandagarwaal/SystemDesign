Deep Dive: Idempotency & Delivery Semantics

Every network call can be retried — so the only safe operation is one you can run twice and get the same result. How do you build that, and what does "exactly-once" actually mean?

Why this lesson, for your mission: The moment your design has a retry, a queue, or a webhook, you have a duplicate problem — and at L6/L7 the interviewer will push on it. "The client's request times out and they retry — does the customer get charged twice?" A senior says "I'll use a queue." A staff candidate says the magic words: "true exactly-once delivery is impossible, so I'll build at-least-once delivery plus idempotent processing — effectively-once." Then they show the idempotency key, the dedup store, and the TTL without being asked. This lesson gives you that vocabulary and the concrete mechanisms so duplicates become a non-event in every design you draw.

Why this matters: the network always retries

Networks are unreliable, and the unreliability has a nasty asymmetry. When client A sends a request to server B and the response never comes back, A has no way to know whether B processed it. Maybe the request was lost on the way in (B did nothing). Maybe B did the work and the response was lost on the way out (B did everything). The two cases are indistinguishable to A.[2]

So A does the only sensible thing: it retries. And every layer of the stack — TCP, HTTP client libraries, load balancers, message brokers, service meshes — retries on your behalf, often invisibly. The result is that any operation will eventually be delivered more than once. If that operation isn't safe to repeat, the consequences are real money:

  • A retried POST /charge double-charges the customer's card.
  • A re-delivered "order placed" message gets processed twice — two shipments, two inventory decrements.
  • A webhook the provider re-sends (because your 200 was slow) fires your fulfillment logic twice.

The fix is not "stop retrying" — you need retries for reliability. The fix is to make the operations safe to retry. That property is idempotency: performing it once or many times yields the same effect and the same observable result.[1]

Delivery semantics: the three guarantees

When one component hands a message to another — producer to broker, broker to consumer, client to server — the channel can promise one of three things. This is the core vocabulary, so know it cold.

SemanticGuaranteeFailure modeWhen acceptable
At-most-once Delivered zero or one time; never duplicated. Can lose messages (no retry after a failure). Metrics, logs, telemetry — where a dropped sample is cheaper than a duplicate.
At-least-once Delivered one or more times; never lost. Can duplicate messages (retries until acked). The default for anything that matters — payments, orders, events. You handle the duplicates.
Exactly-once Delivered once and only once — no loss, no duplicate. The ideal — but see below. What everyone wants; what no channel can truly deliver end-to-end.

The choice between the first two comes down to when you acknowledge. Ack before processing and crash mid-work → the message is gone (at-most-once). Ack after processing and crash before the ack lands → the sender redelivers (at-least-once). You cannot ack both before and after, so you must pick which failure you can tolerate. For almost every real system the answer is at-least-once: losing a payment event is unacceptable, so you accept duplicates and deal with them.[2]

Why true exactly-once delivery is impossible

Go back to the two-generals asymmetry. To never lose a message, the sender must retry until it gets an ack. To never duplicate, it must stop after exactly one successful delivery. But a lost ack is indistinguishable from a lost message — so a sender that retries on a missing ack will sometimes redeliver something that already arrived. You can have "never lose" or "never duplicate" as a pure delivery property, but not both at the message-transport layer. Exactly-once delivery is a myth.[2]

What "effectively-once" really means

The honest, achievable goal is exactly-once processing (also called effectively-once), and it has a precise recipe:

  • At-least-once delivery — the transport retries until acked, so nothing is ever lost.
  • + idempotent processing — the receiver detects and discards duplicates, so the effect happens once.

You don't prevent the duplicate from arriving; you make the duplicate harmless. When a "exactly-once" system (Kafka transactions, Flink) claims the guarantee, this is what it's doing under the hood — dedup + atomic state commit, not magic on the wire.[3]

How to make operations idempotent

There are two flavors. Some operations are naturally idempotent; the rest you make idempotent with a dedup mechanism. A staff answer reaches for natural idempotency first because it's free, then falls back to keys.

1. Natural idempotency — design the operation to be repeat-safe

The cleanest fix is to make the operation set an absolute value rather than apply a relative change. Compare:

  • balance = balance - 10 (a delta) — running it twice subtracts 20. Not idempotent.
  • status = 'SHIPPED' or PUT /order/42 {state: shipped} — running it twice leaves the same state. Idempotent.

This is exactly why HTTP defines PUT and DELETE as idempotent but POST as not: PUT overwrites to an absolute state; POST creates a new thing each time.[1] When you can model a mutation as "set to X," you've removed the duplicate problem instead of detecting it.

2. Idempotency keys — a client-supplied id plus a dedup store

For operations that can't be naturally idempotent (charging a card creates a new transaction), the standard pattern is the idempotency key, popularized by Stripe.[1] The mechanism:

  1. The client generates a unique id (a UUID) for the logical operation and sends it, e.g. in an Idempotency-Key header. Crucially the same key is reused on every retry of that one operation.[1]
  2. The server checks a dedup store (e.g. Redis or a table) keyed by that id. If unseen, it processes the request, then stores the key together with the saved response.
  3. If the key is already present, the server skips the work and replays the stored response — the retry gets the same answer as the original, and the side effect happens only once.[1]

Storing the response, not just the key, is what makes a retry look identical to the first call — the client can't tell it was deduped, which is the whole point.

Mechanisms for the dedup / "have I seen this?" check
  • Dedup table / processed-message ids: a consumer records each handled message id in a processed_messages table; on redelivery it sees the id and drops the message. This is how you make an at-least-once queue effectively-once.
  • Unique constraints: let the database enforce it. A UNIQUE index on the idempotency key (or a natural key like order_id) means a duplicate insert fails atomically — no race, no read-then-write gap. The cheapest, most reliable dedup you have.
  • Conditional writes / optimistic versioning: "update row to v2 only if current version is v1" (compare-and-set). A replayed write that expects v1 but finds v2 is rejected — duplicates and concurrent writers both bounce off the version check.
  • TTL on the dedup store: you can't keep keys forever. Expire them after a window long enough to outlast all realistic retries (Stripe keeps idempotency keys ~24h[1]). After the TTL the same key is treated as new — fine, because no legitimate retry happens days later. The TTL bounds storage growth and is the detail seniors forget.

Mind the race: check-then-act is not atomic

"Read the dedup store, and if absent do the work" has a window: two concurrent retries both read "absent" and both proceed. Close it the same way you'd close any check-then-act race — push the atomicity into one operation: an insert that relies on a unique constraint (the second insert fails), a conditional/atomic write, or processing inside a transaction that commits the dedup record and the side effect together. Never two separate steps with a gap.

In the interview

When duplicates could occur — and they almost always can — deliver it in this arc: (1) Spot the retry source — "the client retries on timeout, and the broker is at-least-once, so this handler will run more than once." (2) State the goal in the right words — "exactly-once delivery is impossible, so I'm targeting effectively-once: at-least-once delivery + idempotent processing." (3) Try natural idempotency first — "can I make this an absolute set rather than a delta?" (4) Otherwise, idempotency key + dedup store — client-supplied id, store the response, dedupe via a unique constraint to avoid the check-then-act race. (5) Close the loose ends — TTL on the keys, and confirm every retry returns the original response. That sequence is breadth-then-depth: a one-line framing, then 60% depth on the dedup mechanism and its races.

Check yourself — retrieval practice

Answer from memory before scrolling back up.

1. Why is true exactly-once delivery impossible at the transport layer?

The sender can't tell a lost ack from a lost message, so retrying to avoid loss will sometimes redeliver — you get loss-free OR duplicate-free, not both.

2. "Effectively-once" processing is built from which two ingredients?

Nothing is lost (at-least-once delivery) and duplicates are made harmless (idempotent processing), so the net effect happens exactly once.

3. Why store the response alongside the idempotency key, not just the key?

Replaying the stored response makes the deduped retry indistinguishable from the first call; the side effect still happens only once.

4. Which mechanism best avoids the check-then-act race when deduping?

A read-then-write has a gap two retries can slip through; a unique constraint makes the duplicate fail atomically with no window.
