Deep Dive: Message Queues (RabbitMQ, SQS, SNS)

The other half of async — task queues that hand out work and delete it, not logs you replay. Knowing which one to reach for is the whole signal.

Why this lesson, for your mission: In Lesson 99 you learned the replayable log. At L6/L7 the trap is reaching for Kafka for everything async. A staff candidate distinguishes a task/work queue (decouple a producer from a worker, process each job once, then delete it) from an event log (durable, replayable history fanned out to many readers). Saying "RabbitMQ or SQS here, not Kafka, because I want competing consumers on transient jobs — not a retained log" is the judgement that reads as staff.[1]

The job: queues vs logs

Both decouple a fast producer from a slower consumer with a durable buffer in the middle. The difference is what happens to a message after it's read.

A task / work queue (RabbitMQ, SQS) is consume-and-delete: a message is delivered to one worker, acknowledged, then removed.[2] Multiple workers pull from the same queue — competing consumers — so adding workers spreads the load and drains the backlog faster. The queue is a to-do list that empties as work gets done; there is no history to re-read.

A log (Kafka, Kinesis) is an append-only, replayable record. Messages are retained for a window regardless of who read them, each consumer group tracks its own offset, and many independent readers replay the same stream.[1] See Lesson 99 for the full treatment.

DimensionTask queue (RabbitMQ, SQS)Log (Kafka)
After readAcked & deleted[2]Retained for a window[1]
Scaling readsCompeting consumers drain fasterMany groups replay independently
OrderingBest-effort (or FIFO mode)Ordered within a partition
Mental modelA to-do list that emptiesA durable history you re-read

RabbitMQ

RabbitMQ is a mature broker built on AMQP (Advanced Message Queuing Protocol). Its defining trait is the smart broker / dumb consumer model: routing logic lives in the broker, and consumers just receive what's handed to them.[3] Producers never publish straight to a queue — they publish to an exchange, which decides which queues get the message based on bindings and a routing key.[4]

Exchange typeRouting ruleUse for
DirectRouting key matches binding key exactly[4]Point a job at one specific queue
TopicRouting key matches a wildcard pattern[4]orders.eu.* style selective routing
FanoutCopy to every bound queue, ignore key[4]Broadcast one event to all subscribers

Acknowledgements are how RabbitMQ guarantees a message isn't lost: a consumer sends an ack only after it finishes processing, and until then the broker keeps the message. If the consumer dies before acking, the message is requeued and redelivered — that's at-least-once delivery, so your handler must be idempotent.[5] A message that keeps failing (rejected, or expired) can be routed to a dead-letter queue (DLQ) — a separate queue for poison messages so one bad job doesn't block the line and you can inspect it later.[6]

RabbitMQ in one breath: publish to an exchange → bindings + routing key fan it to queues → competing consumers pull and ack → failures go to a DLQ. The broker is smart so the consumers can be simple. Reach for it when you need rich routing, per-message TTLs, priorities, or protocols beyond plain HTTP.[3]

Amazon SQS & SNS

SQS (Simple Queue Service) is AWS's fully managed task queue — no brokers to run, scales elastically. It comes in two flavours, and naming the right one is the interview signal.[7]

PropertyStandard queueFIFO queue
DeliveryAt-least-once (dupes possible)[7]Exactly-once processing[8]
OrderingBest-effort, not guaranteed[7]Strict order per group[8]
ThroughputNearly unlimited[7]Lower, capped per second[8]

Two SQS mechanics earn depth. Visibility timeout: when a worker receives a message it isn't deleted — it becomes invisible to other workers for a set window. The worker must finish and explicitly delete it before the window expires, or SQS makes it visible again and redelivers it.[9] Set it too short and a slow job gets processed twice; too long and a crashed worker's message stalls. Long polling tells SQS to wait until a message arrives (up to 20s) before responding, instead of returning empty immediately — it cuts empty receives, cost, and latency versus short polling.[10] SQS also has a native DLQ: after a configurable number of failed receives, a poison message is moved aside automatically.[11]

SNS (Simple Notification Service) is the pub/sub fanout counterpart: a publisher sends one message to a topic, and SNS pushes a copy to every subscriber — other services, HTTP endpoints, email, SMS, Lambda.[12] The canonical AWS pattern is SNS → SQS fanout: publish once to an SNS topic, subscribe several SQS queues to it, and each downstream service drains its own queue at its own pace.[13] You get the broadcast of pub/sub plus the durable buffering and retry of a queue per consumer — exactly the shape behind Lesson 46's notification service.

Choosing: RabbitMQ vs SQS vs Kafka

This is the decision the interviewer actually wants. Lead with the requirement, then the pick.

If you need…Reach forBecause
Replayable history, many independent readers, high throughput streaming[1]KafkaRetained, partitioned, ordered log
Rich routing, priorities, TTLs, AMQP — self/managed broker[3]RabbitMQSmart broker with flexible exchanges
Dead-simple managed task queue on AWS, zero ops[7]SQSElastic, no brokers, pay-per-use
One event delivered to many AWS services at once[12]SNS (+SQS)Managed pub/sub fanout
The default-reach heuristic:
  • On AWS, async jobs, no replay needed? SQS. It's the lowest-ops choice and "good enough" is the staff answer.[7]
  • Need an event broadcast to N consumers? SNS→SQS fanout.[13]
  • Need replay, event sourcing, or a stream many teams re-read? Kafka — and only then.[1]
  • Need routing rules SQS can't express (topic patterns, priorities, per-message TTL)? RabbitMQ.[3]
★ Staff-level signal Seniors say "I'll add a queue." Staff candidates pick the right one out loud and justify the delete-vs-retain choice in one breath: "These are fire-and-forget jobs with no replay, so a task queue — SQS Standard — over Kafka; I don't want to operate a retained log for transient work." They proactively name the gotchas of whichever they pick: at-least-once means idempotent handlers, visibility timeout must exceed processing time, and a DLQ isolates poison messages so one bad job doesn't wedge the worker pool.[9] Reaching for the simplest tool that meets the requirement — and refusing to default to Kafka for everything — is the simple-by-default judgement the bar rewards.

In the interview

When you draw a queue between two services, say in one line which kind and why: "SQS task queue here — decoupling checkout from the slow email/receipt work, at-least-once with idempotent workers."[7] Be ready for the predictable follow-ups: "What if a worker crashes mid-job?" (visibility timeout / unacked redelivery → idempotency), "What about a message that always fails?" (DLQ), and "Why not Kafka?" (no replay needed, fewer ops). If the prompt is "notify many downstream services," reach for SNS→SQS fanout, not a hand-rolled broadcast. The depth lives in the failure modes, not in re-explaining what a queue is — see Lesson 44 for designing one from scratch.

Check yourself — retrieval practice

Answer from memory before scrolling back up.

1. What is the core difference between a task queue and a log?

Task queues are consume-and-delete; logs retain messages for replay by many readers.

2. In RabbitMQ, where do producers publish messages?

Producers publish to an exchange; bindings plus a routing key decide which queues receive it.

3. What does the SQS visibility timeout do for a received message?

A received message goes invisible; if not deleted in time, SQS makes it visible and redelivers it.

4. Which choice fits "deliver one event to many AWS services at once"?

SNS→SQS fanout broadcasts once and gives each consumer its own durable, retryable queue.
