Deep Dive: Apache Kafka

A distributed commit log dressed as a message system — understand the log and partition model and you can reason about almost everything it does.

Why this lesson, for your mission: At L6/L7, dropping a "Kafka" box on the board is table stakes. The interviewer wants to see that you know why it is fast (append-only log + page cache + zero-copy), what the partition really buys you (parallelism and ordering, but only within a partition), how it stays durable (replication, ISR, acks), and the exact delivery guarantee you are signing up for. The staff move is choosing Kafka for a stream and explicitly not for a task queue — and naming the tradeoff before you're asked.[1]

1 of 5

What it is & the log model

Kafka is a distributed, durable append-only commit log exposed as a publish/subscribe system.[1] Producers append records to the end of a log; consumers read forward from a position they control. The mental model that unlocks everything: it is not a queue that deletes messages on read — it is a replayable log that retains records and lets many independent readers move through it at their own pace.[2]

The core vocabulary:

TermWhat it is
TopicA named stream of records (e.g. clicks); the logical channel[2]
PartitionAn ordered, immutable log; a topic is split into N of them[2]
OffsetThe monotonic position of a record within one partition[2]
ProducerAppends records, choosing the partition (often by key)[2]
Consumer groupA set of consumers sharing the work of a topic's partitions[3]

Within a consumer group, each partition is read by exactly one consumer, so the group splits the topic's throughput across its members.[3] Different groups are independent — the analytics group and the billing group each read the whole topic without interfering, because each tracks its own offsets. That single design choice is why Kafka serves both fan-out streaming and load-balanced consumption from one log.

Internals — the part that earns depth

The partition: unit of parallelism and ordering

The partition is the atom of Kafka. It is the unit of parallelism — more partitions means more consumers can read in parallel, so a topic's throughput ceiling is set by its partition count.[2] It is also the unit of ordering: Kafka guarantees order only within a single partition, never across them.[2] This is the most common Kafka misconception and a favourite interview trap — "Kafka is ordered" is false; "Kafka is ordered per partition" is the correct, staff-level statement.

So if every event for one user must be processed in order, you must route them to the same partition — which is exactly what the producer key does (below). The cost of ordering is concentration: a hot key sends all its traffic to one partition, capping that key's throughput at one consumer.

Why it's fast: segments, page cache, zero-copy

Kafka's throughput comes from refusing to be clever. Each partition is stored on disk as a sequence of segment files, and writes are pure sequential appends — which on spinning and SSD media is dramatically faster than random I/O.[4] It deliberately does not maintain a per-message index in memory; the offset and the file layout are enough.

Two more tricks do the heavy lifting:

  • OS page cache, not a JVM cache. Kafka writes to the filesystem and lets the operating system's page cache hold hot data. Recently written records are usually still in cache, so consumers reading the tail of the log serve from RAM without Kafka managing a heap cache.[4]
  • Zero-copy with sendfile. To ship bytes from disk to a consumer's socket, Kafka uses the sendfile system call, which copies data straight from the page cache to the network card, skipping the trip through application memory and the redundant copies it implies.[4]

The payoff: Kafka moves data at close to network/disk hardware limits because the bytes barely touch user space. This is the "why is it fast" answer interviewers are fishing for — sequential I/O + page cache + zero-copy, not a magic in-memory store.

Replication: leaders, followers, ISR, and acks

Each partition is replicated across brokers for durability. One replica is the leader (all reads and writes go through it); the others are followers that pull the leader's log to stay current.[5] The followers that are sufficiently caught up form the in-sync replica set (ISR). A record is considered committed once all in-sync replicas have it; only committed records are ever handed to consumers.[5] If the leader dies, a broker is elected from the ISR, so no acknowledged data is lost.

The producer chooses how much durability to pay for via acks:

acksLeader waits forTradeoff
acks=0Nothing — fire and forgetFastest; can silently lose records on failure[5]
acks=1Leader write onlyLoses data if the leader dies before followers copy[5]
acks=allAll in-sync replicasStrongest durability; higher write latency cost[5]

Staff signal: pair acks=all with min.insync.replicas so a write fails fast rather than silently weakening durability when replicas fall out of the ISR.[5]

Retention: the log is the storage

Kafka does not delete a record when it is consumed. It keeps records for a configured retention window — by time (e.g. 7 days) or by size — independent of who has read them.[2] This is why a new consumer group can replay history from offset zero, and why a buggy downstream can be fixed and re-run. Log compaction is the alternative policy: instead of dropping by age, it retains the latest record per key, turning the topic into a durable changelog of current state.[2]

Why is Kafka ordered only within a partition, and not across the whole topic?

Ordering requires a single sequential writer/reader path. Spreading a topic across partitions is what gives parallel throughput — global order would force everything back through one lane.

Reread "unit of parallelism" — parallelism and a single global order are in tension.

What breaks if a producer keys 90% of traffic to the same value (e.g. one giant customer's user_id)?

The key deterministically hashes to one partition. Concentration is the price of per-key ordering — one consumer, one partition, one throughput ceiling.

Delivery semantics

What guarantee you get depends on how producers and consumers handle failure and offsets — this is the highest-leverage thing to get right in an interview.

GuaranteeHow you get itRisk
At-most-onceCommit offset before processingCrash loses the in-flight record[6]
At-least-onceProcess, then commit the offsetCrash reprocesses — needs idempotency[6]
Exactly-onceIdempotent producer + transactionsMore overhead; Kafka-to-Kafka scope[6]

At-least-once is the sane default: process the record, then commit the offset, and make your handler idempotent so a replay is harmless.[6] Exactly-once is real but narrow: the idempotent producer dedupes retried sends so a network hiccup doesn't double-append, and transactions let a consume-process-produce cycle commit its output records and input offsets atomically.[6] The honest framing: exactly-once is a Kafka-to-Kafka property — once you write to an external database or call an API, you're back to needing idempotency at the boundary.

Rebalancing and keys

When a consumer joins or leaves a group, Kafka triggers a rebalance that reassigns partitions across the surviving members.[3] During a rebalance, consumption briefly pauses — frequent rebalances (from flapping consumers or slow processing) are a real-world throughput killer, which is why staff candidates mention tuning session/heartbeat timeouts and using cooperative rebalancing.

Because order is per-partition, the producer key is your ordering and locality control: Kafka hashes the key to pick a partition, so all records with the same key (say user_id) land on the same partition and are read in order by one consumer.[2] Choose the key to match your ordering requirement — and beware that a skewed key distribution creates a hot partition.

Check before continuing

What is the "sane default" delivery approach for most Kafka consumers?

At-least-once plus an idempotent handler is the practical default; exactly-once is narrower and Kafka-to-Kafka only.

Reread the sentence starting "At-least-once is the sane default."

Why does "exactly-once" stop being true once a consumer writes to an external database instead of another Kafka topic?

The transactional guarantee is scoped to what Kafka itself coordinates. Anything outside that boundary needs its own idempotency, same as any distributed write.

Reread "the honest framing" sentence at the end of the delivery-semantics paragraph.

Why do frequent rebalances hurt throughput more than a single, rare rebalance would?

Each rebalance has a pause cost. A flapping consumer (crashing, restarting, missing heartbeats) triggers that cost over and over.

Reread "During a rebalance, consumption briefly pauses."

When to reach for it / when NOT to

Kafka is a stream / event log, not a task queue. That distinction is the whole decision.

Reach for Kafka when…Reach for RabbitMQ / SQS when…
High-throughput event streams & pipelines[1]Discrete background jobs / task work queue
Many independent consumers replay the same data[2]Per-message ack, retry, and dead-letter queues
Durable, ordered (per-key) event sourcing / CDC[2]Routing / fan-out by topic-exchange rules (Rabbit)
You need to retain & reprocess history[2]You want a managed, zero-ops queue (SQS)

The trap: using Kafka as a job queue. Kafka has no per-message acknowledgement or built-in delivery-retry/dead-letter per record — progress is a single offset per partition, so one slow "poison" message blocks the partition behind it. For task queues with redrive and visibility timeouts, a broker like RabbitMQ or SQS is the right tool. We cover that side in Lesson 44 — Distributed Message Queue, and Kafka in a real pipeline in Lesson 36 — Ad Click Aggregator.

★ Staff-level signal Seniors say "I'll put Kafka here." Staff candidates reason from the log model in one breath: "It's an append-only log, so it's fast via sequential I/O, page cache, and zero-copy sendfile; the partition is my unit of parallelism and ordering, so I'll key by user_id to keep per-user order, accept at-least-once and make consumers idempotent, and run acks=all with min.insync.replicas=2." And they name the boundary proactively: "this is an event stream — if these were discrete tasks needing per-message retry and a DLQ, I'd use SQS, not Kafka." Knowing the internals, picking the matching guarantee, and refusing to force Kafka into a task-queue shape is the judgement the bar rewards.[1]

In the interview

When you draw a Kafka box, justify it in one line ("durable, replayable event stream feeding the aggregator"), then be ready for the predictable follow-ups: "How do you guarantee ordering?" (per-partition only; key by the entity that needs order) and "What delivery guarantee?" (at-least-once + idempotent consumers, or transactions for exactly-once Kafka-to-Kafka).[6] Mentioning page cache + zero-copy when asked why it's fast, or acks=all with min.insync.replicas for durability, signals hands-on depth.[4] Don't over-explain pub/sub basics — and don't reflexively reach for Kafka when the requirement is a simple task queue.

Why does one "poison" message stuck in a Kafka partition block every message behind it, when a task queue wouldn't have this problem?
