Design a Blob / Object Store (like S3)

Sell infinite, indestructible storage — then make the math survive contact with physics.

Why this lesson, for your mission: An object store is the substrate half the other systems in this course are built on — Dropbox, feeds, logs, backups all lean on it. At L6/L7 the interviewer isn't testing whether you can "store a file"; they're testing whether you reach for the two non-obvious moves before being prodded: separate the metadata index from the data plane, and buy 11 nines of durability with erasure coding instead of paying 3× for replication. Get those two right and you've shown you understand storage economics at exabyte scale, not just an API.

Functional Requirements

An object store is a flat key→bytes map grouped into buckets. Scope to the operations that shape the architecture.

#Users should be able to…
1PUT / GET / DELETE an object by (bucket, key) — the bytes plus user metadata.
2List objects in a bucket, optionally by key prefix (photos/2026/).
3Multipart upload large objects in parallel parts, then complete them into one object.[1]
4Version objects — overwrites and deletes keep prior versions rather than destroying them.[1]

Out of scope (name it to show judgement): a POSIX filesystem with in-place random writes, cross-region replication, and query-in-place. Objects are immutable once written — there is no "append to byte 4." That immutability is a gift; it makes durability and caching far simpler.

Non-Functional Requirements

NFRTarget / priority
Durability (the cardinal NFR)11 nines — 99.999999999% of objects survive a given year. Losing data is the one unforgivable failure; AWS markets S3 at exactly this level.[1]
Availability~4 nines for the request path. Lower than durability: a brief inability to read is recoverable; losing the bytes is not.
ScalabilityExabytes of data and trillions of objects, with no global bottleneck. Capacity grows by adding nodes.
ThroughputSaturate client and disk bandwidth on large objects; tens of thousands of small ops/sec per bucket prefix.
CostStorage efficiency is a first-class NFR at this scale — every 1× of overhead is exabytes of disk. Drives the EC choice.

Capacity Estimation

Only the numbers that change a decision. Here three numbers each force a specific structural choice.

  • Total size → erasure coding, not replication. At ~1 EB of usable data, 3× replication means buying 3 EB of raw disk. A 10+4 erasure code gives comparable durability at 1.4× overhead — ~1.4 EB. Implication: the savings (~1.6 EB of disk) make EC mandatory, not optional.[2]
  • Object count → shard the metadata. Trillions of objects × ~1 KB of metadata each ≈ petabytes of index that no single database holds. Implication: the object index is a horizontally sharded, separate service from where bytes live.
  • Object size range (bytes → terabytes). One API must serve a 2 KB JSON and a 5 TB video. Implication: multipart upload for large objects, and small objects get packed together so per-object overhead doesn't dominate.
  • Throughput → bytes bypass the control plane. If every GET/PUT streamed through the metadata tier you'd size it for exabyte bandwidth. Implication: presigned URLs / a thin data plane move bytes directly to storage nodes.[1]

Core Entities & API

Three entities. The load-bearing idea is that Object bytes and ObjectMetadata live in different systems — the data plane and the metadata (index) service.

EntityHolds
BucketNamespace + owner, region, versioning flag, lifecycle policy, default storage class.
ObjectThe immutable bytes, written once to storage nodes and addressed by an internal blob id.
ObjectMetadatakey, versionId, size, content hash/ETag, storage class, and the placement map (which nodes/shards hold the bytes). Lives in the index.

The caller is derived from the auth token / request signature, never the body. Endpoints map almost 1:1 to S3.[1]

EndpointPurpose

Data Flow

A PUT is where the whole design shows itself — control plane decides where, data plane writes the bytes, durability is earned on the way down:

  1. Client calls the API; the request is authenticated and routed to the metadata service for that bucket.
  2. Metadata service allocates a blob id and a placement (which storage nodes / failure domains will hold the shards), and returns a presigned target.[1]
  3. Client streams bytes to the data plane, which splits the object into k data + m parity shards (erasure coding) and writes each shard to a different failure domain.[2]
  4. Once a write quorum of shards is durable, the data plane acks; the metadata service commits the version and ETag. Only now is the object visible.

High-Level Design

The architecture is one decision repeated everywhere: split the control/metadata plane from the data plane. Metadata (small, queried constantly, needs strong consistency) is sharded across an index. Bytes (huge, immutable, write-once) live on dumb, dense storage nodes and are protected by erasure coding.

ComponentRoleStore
API / front doorAuth, request signing, rate limits, routes by bucket to the right shard.Stateless fleet
Metadata service (index)Maps (bucket,key,version) → placement; serves LIST; enforces consistency. Sharded by bucket+key.Sharded KV / NewSQL
Data plane (storage nodes)Stores erasure-coded shards on disk; handles streaming reads/writes and repair.Dense JBOD nodes
Placement / coordinatorChooses failure domains for new writes; drives re-replication when a disk dies.—
Background / GCLifecycle transitions (hot→cold→archive), compaction, deleted-version cleanup, scrubbing.Workers + queue

Read path: metadata lookup → placement map → data plane reads k of k+m shards (any k suffice) → reconstructs and streams the object. Write path: as in Data Flow above. Notice the metadata service is never in the byte path for the bulk transfer — it hands out a target and steps aside.[1]

★ Staff-level signal A senior candidate stores three full copies and moves on. A staff candidate says: "Three copies costs 3× — at an exabyte that's two extra exabytes of disk I don't need. I'll erasure-code: a 10+4 Reed–Solomon stripe tolerates any 4 simultaneous failures at 1.4× overhead, same durability class as 3-way replication for far less disk."[2] The deeper move is naming the cost of EC — reads/repairs must touch k nodes instead of one, so it pays for cold, large objects and hurts tiny, latency-critical ones. Knowing when not to erasure-code (small/hot objects → keep replicated) is the real signal. The same instinct shows in refusing to stream bytes through the metadata tier.

Deep Dives

1. Durability: erasure coding vs replication

Both survive disk loss; they trade storage overhead against access cost.

SchemeOverheadToleratesCost / best for
3× replication3.0×2 lost copiesCheap, fast single-node reads; pays for small/hot objects.
EC 10+4 (Reed–Solomon)1.4×Any 4 of 14Reads/repair gather k shards; pays for large/cold objects.[2]
EC 6+31.5×Any 3 of 9Smaller stripe → cheaper repair, slightly more overhead.

The mechanism: split the object into k data shards, compute m parity shards so that any k of the k+m can rebuild the original. Spread the 14 shards across 14 independent failure domains (different racks/hosts/power) so no single failure takes two shards.[2] Durability is then a function of how fast you repair a lost shard before others die — so a background scrubber continuously reads, verifies checksums, and rebuilds. The catch staff candidates name: a single small read now fans out to k nodes, and repairing one lost shard reads k shards' worth of data ("repair amplification"). That's why hot/tiny objects often stay replicated and only large/warm data is coded. (See replication & CAP for the copy-based baseline.)

2. Metadata service vs data plane — and sharding the index

The object index is the brain; the storage nodes are dumb muscle. Keeping them separate lets each scale on its own axis: bytes scale with capacity, the index with request rate and object count.

  • Why separate: if metadata lived next to bytes you couldn't LIST a bucket without scanning storage nodes, and you'd couple index hotspots to disk capacity. The index is a sorted map (bucket,key,version) → placement.
  • Sharding key: shard by a hash of bucket+key so load spreads evenly. But LIST-by-prefix wants keys sorted — so within a shard keep keys range-ordered, and route prefix scans to the owning shard(s).
  • The hot-bucket / hot-prefix problem: sequential keys (log-0001, log-0002) all hash near each other or land on one range shard, creating a hotspot. Mitigation: hash-prefix the key or split ranges adaptively — the same lesson S3 teaches with key naming.[1]
  • Consistency: the metadata commit is the linearization point. Use a consensus-backed shard (Raft/Paxos group per range) so a committed PUT is immediately visible — this is what makes modern S3 strongly consistent for read-after-write.[1]

3. Multipart upload + presigned URLs — offloading the data plane

A 5 TB object cannot ride one request, and you never want bytes flowing through the control plane.[1] Multipart solves both:

POST ?uploads → uploadId; PUT part 1..N (parallel); POST complete[ {n,ETag} ] → object
  • Parallel + resumable. Parts (e.g., 8–64 MB) upload concurrently; a failed part retries alone. The client lists uploaded parts to resume after a crash.[1]
  • Server verifies, never trusts. Complete supplies each part's ETag; the service checks them before stitching — a buggy client can't fake a part.
  • Presigned URLs offload bytes. The control plane signs a short-lived URL granting exactly one operation on one key; the client then transfers directly to the data plane.[1] Same move as Dropbox — keep the multi-GB stream off your application tier so throughput scales with storage nodes, not API servers.
  • Garbage: abandoned multipart uploads leak storage; a lifecycle rule aborts incomplete uploads after N days.[1]

4. Placement, storage tiers & listing consistency

Placement across nodes. The coordinator picks failure domains for each stripe to balance free space and spread risk; it tracks disk health and, on failure, schedules repair of just the affected shards. Writes target the emptiest healthy domains so capacity fills evenly — avoiding the classic "one rack full, rest idle" trap.

Storage tiers / lifecycle. Most bytes go cold fast, so let the bucket policy migrate objects hot → cold → archive automatically.[1]

TierProfileTrade
Hot (Standard)Frequent reads, ms latencyMost $/GB; often replicated for tiny objects.
Cold (Infrequent)Rare reads, still onlineCheaper/GB, small retrieval fee; wider EC stripe.
Archive (Glacier-like)Backups, minutes–hours to restoreCheapest/GB; offline-ish media, retrieval latency.

Listing consistency — strong vs eventual. Read-after-write on a single key is strongly consistent because the metadata commit is the source of truth.[1] But a bucket LIST spans many shards; offering a globally strong, point-in-time snapshot across a trillion-key bucket is brutally expensive. The pragmatic answer (and the interview-worthy nuance): keep per-object reads strong, but allow LIST to be eventually consistent — a just-written key may take a moment to appear in a prefix scan. State the trade explicitly and tie it to CAP: you're choosing bounded staleness on the aggregate query to keep listing scalable, while individual GETs stay correct.

Check yourself — retrieval practice

Answer from memory before scrolling back up.

1. Why prefer erasure coding over 3× replication at exabyte scale?

A 10+4 code is ~1.4× overhead vs 3.0× — exabytes of disk saved at similar durability.

2. Why split the metadata index from the data plane?

Bytes scale with capacity; the index scales with object count and request rate.

3. What does a presigned URL buy a multipart upload design?

Signing one short-lived op moves the multi-GB stream off your application tier.

4. Why allow bucket LIST to be only eventually consistent?

Per-key reads stay strong; only the cross-shard aggregate trades staleness for scale.
