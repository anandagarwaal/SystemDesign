Design Typeahead / Autocomplete

Every keystroke is a query, the answer must beat the eye, and the whole game is moving work off the read path.

Why this lesson, for your mission: Typeahead looks deceptively easy — "just match a prefix" — which is exactly the trap. The L6/L7 signal is recognizing that this is a latency problem disguised as a string-matching problem: you serve millions of partial queries per second under a sub-100ms budget, so you precompute the answer at write time, push popularity into the data structure itself, and let the read path do almost nothing. Staff candidates spend their breath on the trie's top-K layout, the hot-prefix shard, and the streaming count pipeline — not on how a trie works.

Functional Requirements

Strip the prompt to the few things the system must do. Typeahead is a read-dominated suggestion service.

#Requirement
1As a user types a prefix, return the top ~10 ranked completions for that prefix, updated on each keystroke.[1]
2Suggestions are ranked by popularity (and lightly by recency), so common queries surface above rare ones.
3The suggestion corpus is built from what people actually search — the trie is fed by aggregated query logs, not a static dictionary.

Explicitly out of scope (scoping out loud is a staff move): spell-correction / fuzzy matching, personalization per user, and multi-word semantic ranking. Pin it to prefix → popular completions and the design stays sharp. Say you'd add fuzzy matching as a follow-up rather than baking it into v1.

Non-Functional Requirements

NFRTarget & priority
Low latency (dominant)Suggestions must return in under ~100ms end-to-end, ideally tens of ms server-side, or the UI feels laggy. This single constraint shapes everything.
Read-heavy scaleReads dwarf writes by orders of magnitude — every keystroke is a read, but the corpus changes slowly. Optimize hard for reads.
Eventually-fresh rankingA newly trending query can take minutes to hours to climb the rankings. Strict real-time freshness is not required.
High availabilityAutocomplete is an enhancement, not the core flow — stale or degraded suggestions beat an error. Favor AP over CP here.
★ Staff-level signal Notice the relaxations you volunteer: ranking can be eventually fresh, and suggestions can be slightly stale or approximate. Those two concessions are what let you precompute everything offline and serve from a read-only structure. A senior candidate tries to keep counts perfectly live and fights write amplification forever; a staff candidate negotiates "minutes-fresh is fine" up front and designs straight to a cheap, cacheable read path.

Capacity Estimation

Only the numbers that change the design. These are back-of-envelope estimates — derive them out loud, don't memorize them.

The punchline: the answer per keystroke is tiny (10 short strings), traffic is enormous, and the data changes slowly. That asymmetry says precompute aggressively, cache everything, and make reads touch almost nothing.

Core Entities & API

Entities: Suggestion (a completion string + its popularity score), TrieNode (a character/prefix that stores its own precomputed top-K list), and QueryEvent (a logged search that feeds ranking).[1]

The hot path is one read endpoint. Logging a completed search is a separate, asynchronous write — it is not on the suggestion path.

EndpointPurpose
GET /v1/suggestions?prefix={p}&limit=10Return the ranked completions [{ phrase, score }] for prefix p. Anonymous-readable; caller identity (if present) comes from the auth token, not the query.
POST /v1/search-eventsFire-and-forget log of a completed search { phrase, ts }; user derived from the auth token. Feeds the offline ranking pipeline, never blocks reads.

Data Flow

Typeahead has a real data-processing back end (query logs → ranked trie), so trace it before drawing boxes.

  1. Collect — completed searches land in a query log via POST /v1/search-events.
  2. Aggregate — a streaming pipeline counts phrase frequency over rolling windows, weighting recent activity.
  3. Build — a batch/stream job constructs (or updates) the trie, computing the top-K completions at every node.
  4. Distribute — the immutable trie is sharded by prefix and shipped to read replicas; popular prefixes are warmed into cache.
  5. Serve — GET /v1/suggestions hits CDN/cache first, then a trie replica for a single node lookup.

Stages 2–4 are the offline brain (where ranking and the top-K layout live); stage 5 is the deliberately dumb, fast read path. The separation is the whole design.

High-Level Design

The write path (logging + rebuild) and the read path (suggestions) are fully decoupled — classic for a precompute-heavy system.

ComponentRole
Suggestion service (stateless)Front door for GET /v1/suggestions; checks cache, then queries the right trie shard. Trivially replicable for read scale.
CDN + suggestion cache (Redis)Absorbs the bulk of QPS. Popular prefixes ("y" → youtube) are served without ever touching the trie.[1]
Trie store (sharded, in-memory)The ranked prefix tree with top-K stored per node, sharded by prefix; read-only replicas behind the service.
Query log (Kafka)Durable buffer of completed-search events feeding the ranking pipeline; never on the read path.
Ranking / build pipeline (Flink/Spark)Aggregates counts, computes scores, and rebuilds the top-K trie offline, publishing new versions.

Read path: GET /v1/suggestions → CDN/cache → (on miss) suggestion service → trie shard → single node lookup → return precomputed top-10. Write path: completed search → Kafka → pipeline aggregates & ranks → rebuild trie → publish new immutable version → replicas swap atomically. Reads never wait on writes.

Deep Dives

1 · The trie with top-K stored at each node

The naive trie stores the corpus and, at query time, descends to the prefix node and then walks its entire subtree collecting and sorting every descendant phrase. That subtree can hold thousands of completions; sorting them per keystroke under a 100ms budget at 35k+ QPS is the wall.[1]

The fix: precompute top-K at each node. When the trie is built offline, every node caches the K (≈10) highest-ranked completions of its own subtree. A query for prefix p walks p.length nodes to the prefix node and reads its stored list — done. No subtree scan, no per-request sort.
  • Read cost: O(length of prefix) to descend, then O(1) to grab the cached list. This is what buys the latency.
  • Cost paid: extra storage (every node carries ~10 entries) and a heavier build — but build is offline and amortized over a million reads.
  • It's the same instinct as Top-K: the result is tiny, so move the expensive ranking work off the hot path and store the answer.

2 · Precompute vs query-time top-K

This is the core tradeoff fork, and naming both sides with a justified pick is the interview-relevant part.

ApproachHow it worksCost / when
Query-time top-KStore only the corpus; on each request descend, scan the subtree, rank, and return.Cheap to build & always fresh, but reads are slow and CPU-heavy. Only viable at low QPS or tiny subtrees.
Precomputed top-KBuild job ranks once and writes the top-K into every node; reads just read.Fast, cacheable reads; costs storage and a rebuild lag. The default for this read:write ratio.

Pick precompute, then state the honest cost: staleness. A new trending phrase isn't suggestable until the next rebuild. Mitigate with frequent incremental rebuilds (minutes) and a small "fresh/trending" overlay merged at read time if the interviewer pushes on real-time freshness — but only if asked. Don't over-engineer freshness the NFR didn't demand.

★ Staff-level signal The depth here isn't "use a trie" — it's articulating why precompute wins in one breath: "reads outnumber writes ~1000:1 and the answer is 10 strings, so I pay a one-time offline build to make every read O(prefix length); the cost is bounded staleness, which the eventually-fresh NFR already allows." Connecting the read:write asymmetry → precomputation → the staleness tradeoff → the NFR that licenses it is the staff move. Mentioning the query-time alternative and dismissing it with a reason shows judgment, not just recall.

3 · Sharding the trie by prefix — and the hot-prefix problem

The trie is too big and too hot for one box, so shard it. The natural key is the prefix itself — route all queries for prefixes starting "a…" to one shard, "b…" to another.

The hot-prefix problem. Prefix popularity is wildly skewed — short, common prefixes ("a", "th", "yo") take a huge share of traffic, while most long prefixes are nearly idle.[1] Sharding by first letter dumps all that heat onto a few shards while others sit idle — a textbook hot-shard / celebrity problem.
  • Mitigation 1 — shard by a hash of the whole prefix (e.g. first 2–3 chars hashed) to spread load more evenly, accepting that one logical prefix's data is co-located on one shard.
  • Mitigation 2 — cache the hot prefixes hard. The skew that hurts sharding helps caching: a tiny set of popular prefixes serves most traffic, so a high cache/CDN hit rate means the hot shard is rarely touched at all.
  • Mitigation 3 — replicate hot shards so reads for the hottest prefixes fan out across several replicas.

The clean answer: hash-based sharding to flatten the distribution, plus caching popular prefixes so the long tail is what actually reaches the trie. Don't rely on one mechanism alone.

4 · Ranking from a streaming pipeline; caching & the latency budget

Two coupled concerns close the design: where the popularity scores come from, and how the ~100ms budget is actually met.

Ranking by popularity & recency. Scores come from aggregated query counts, not guesses. Completed searches stream into Kafka; a processor (Flink/Spark) maintains windowed frequency counts and a recency-weighted score, then feeds the trie build. Because exact, perfectly-fresh counts aren't required, the pipeline can aggregate in rolling windows and even use approximate counters for the long tail — the same heavy-hitters logic as Top-K. New rankings land on the next rebuild.

Meeting the sub-100ms budget is a stack of cheap wins, not one trick:
  • Client-side debouncing — wait ~50–150ms after the last keystroke before firing a request, collapsing a burst of keystrokes into one call. This cuts QPS dramatically and is the first thing to mention.
  • CDN + edge cache of popular-prefix responses — many keystrokes are answered before the request reaches your data center.[1]
  • In-memory trie with precomputed top-K — the server-side lookup is O(prefix length), no disk, no sort.
  • Prefetch & trim on the client — return a few extra results so the next keystroke can often be filtered locally without a round trip.
★ Staff-level signal Many candidates obsess over server internals and forget the cheapest latency win lives on the client: debouncing turns "a request per keystroke" into "a request per pause," slashing load by ~5–10×. Staff candidates reason about the whole latency budget — network RTT, edge cache, debounce, server lookup — and spend effort where the milliseconds actually are, rather than micro-optimizing a trie lookup that's already sub-millisecond.

Check yourself — retrieval practice

Answer from memory before scrolling back up.

1. Why precompute and store the top-K completions at each trie node?

Each node caches its subtree's top-K, so a query just descends the prefix and reads the list — O(prefix length), no per-request sort.

2. What is the main risk of sharding the trie by prefix range?

Prefix popularity is heavily skewed, so first-letter sharding overloads a few hot shards. Hash-sharding plus caching the hot prefixes fixes it.

3. How are popularity counts kept fresh without slowing the read path?

Completed searches stream into Kafka; an offline pipeline aggregates scores and rebuilds the trie, so reads stay read-only and fast.

4. Which tactics together keep typeahead latency under the ~100ms budget?

Debouncing collapses keystroke bursts into one call, and CDN/cache answers popular prefixes near the edge before they hit the trie.
