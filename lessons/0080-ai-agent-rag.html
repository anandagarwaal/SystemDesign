Design an AI Agent / RAG Application

An LLM that answers from your knowledge base — and can act — where the design problem is retrieval quality and grounding, not just serving the model.

Why this lesson, for your mission: Lesson 39 (ChatGPT) made the GPU the scarce resource. This case study moves the hard part upstream: the LLM is now a black box you call, and your job is to feed it the right context and stop it from making things up [1]. The senior answer is "embed docs, retrieve top-k, stuff the prompt." The staff move is to treat retrieval quality, grounding/citations, and the agent loop as the system — with eval as the thing that proves any of it works. This one template covers RAG apps, Perplexity-style AI search, support chatbots, and MCP tool-using agents.

Functional Requirements

One shape covers the whole family — RAG Q&A, AI search, virtual agent. Pin the core flows early; everything else (auth, doc-upload UI, fine-tuning the base model, training embeddings) is out of scope.

#Requirement
1A user asks a question and gets an answer grounded in a knowledge base (docs, wiki, tickets), not just the model's parametric memory [1].
2Answers cite their sources — each claim links back to the retrieved passage it came from, so the user can verify [2].
3Conversations are multi-turn: follow-ups resolve against prior turns ("and its pricing?").
4The agent can call tools / APIs — search, a calculator, a database query, an MCP server — and use the results in its answer [3].

Scope note: we call the LLM and the embedding model as black boxes (Lesson 39 owns serving them). The interesting system is the retrieval + orchestration layer around them [1].

Non-Functional Requirements

NFRTarget / priority
Grounding / accuracyThe top priority. Answers must be faithful to retrieved context; minimize hallucination, and abstain ("I don't know") when retrieval is weak [2].
Low latencyInteractive: aim for time-to-first-token under ~1–2s. Retrieval + rerank must be tens of ms; stream the answer so the user sees progress.

ScaleTarget ~10M docs in the KB, ~1M DAU, multi-turn sessions. Vector index in the tens-of-millions-of-chunks range.

Capacity Estimation

Only the numbers that change the design — and here they all point at chunk count, context size, and cost-per-turn.

Vector index size. 10M docs × ~10 chunks/doc = ~100M chunks. At 1536 dims × 4 bytes ≈ 6 KB/vector → ~600 GB of raw float vectors. Implication: this won't sit in one box's RAM — you need quantization and/or sharding in the vector DB (see Lesson 40), exactly as that lesson predicts.

Tokens per turn drive cost. Retrieve top-k (say 20) → rerank → stuff ~5 passages × ~500 tokens = ~2.5k context tokens, + history + system prompt ≈ 4–5k input tokens per turn. At 1M DAU × a few turns/day that's billions of input tokens/day. Implication: context size is a cost lever — bloating the prompt with low-value passages burns money and dilutes accuracy.

Query QPS is modest; the LLM call is the slow leg. Even 1M DAU × 5 turns ≈ ~60 QPS average — trivial for the stateless tier and vector DB. The wall-clock cost is the multi-second LLM generation. Implication: spend the design budget on retrieval quality, caching, and the agent loop — not on QPS scaling.

Core Entities & API

Entities: Document (source content + metadata) · Chunk (a passage with its embedding + back-reference to its Document) · Conversation (ordered Messages) · Tool (a callable function/MCP server with a schema). User identity is derived from the auth token, never sent in the body.

EndpointPurpose
POST /v1/chatAsk a question in a conversation; response is an SSE stream of answer tokens followed by a citations payload referencing the chunks used.
POST /v1/documentsIngest a document into the KB (triggers async chunk → embed → upsert into the vector DB).
DELETE /v1/documents/{id}Remove a doc and its chunks from the index (compliance / staleness).
GET /v1/conversations/{id}Fetch message history to render or resume a thread.
GET /v1/toolsList tools/MCP servers available to the agent (name + JSON schema).
Request shape for POST /v1/chat:
  • conversation_id — server loads prior turns for context.
  • query — the new user question.
  • Server replies with SSE answer tokens, then a final event with citations: [{chunk_id, doc_id, span}] so the UI can render footnotes.

Data Flow

This system has two pipelines, and naming them separately is half the battle. Ingestion is an offline/async data-processing pipeline; query is the online request path.

PipelineSteps
Ingestion (write, async)Document arrives → chunk it (split into ~200–500-token passages with overlap) → embed each chunk with the embedding model → upsert vectors + metadata into the vector DB → keep the raw doc in a durable blob/document store as source of truth [1].
Query (read, online)Embed the query (same model) → retrieve top-k nearest chunks (ANN) → rerank to top-n → stuff them into the prompt as context → LLM generates a grounded, cited answer → stream it back [1].

The agent variant wraps the query path in a loop: the LLM may decide to call a tool (including "search the KB" as just one tool) before answering — covered in the deep dives.

High-Level Design

Trace a question through the boxes. The vector DB and the LLM are the two heavy dependencies; everything else is glue.

ComponentRole on a POST /v1/chat
API gateway / LBAuth, rate-limit, TLS. Routes to a stateless orchestrator.
OrchestratorThe brain. Loads history, embeds the query, calls retrieval, builds the prompt, runs the agent loop (tool calls), calls the LLM, streams tokens, assembles citations. Stateless and horizontally scalable.
Embedding serviceTurns query (and, in ingestion, chunks) into vectors. A GPU model call — cache results.
Vector DBANN index over ~100M chunks (HNSW), sharded + quantized. Returns top-k chunk ids by similarity (Lesson 40).
RerankerCross-encoder that rescores ~100 candidates → top ~5 by true relevance.
LLM servingThe generation fleet (Lesson 39). Called with the stuffed prompt; streams tokens. A black box here.
Doc / blob storeSource-of-truth raw documents + the Conversation/Message history. Cheap, durable.
Semantic cacheReturns a cached answer for a semantically-equivalent prior query, skipping retrieval + LLM.
Ingestion workersOff the request path: consume a queue of new docs, chunk/embed/upsert. The freshness path.

Read path for history is trivial — GET /v1/conversations/{id} hits the doc store, no LLM. The vector DB is a derived index: the blob store is the source of truth, and the index is rebuilt/refreshed from it.

Deep Dives

This is the 60%. Four hard parts, each tied to an NFR.

1 · The RAG pipeline — ingestion and query time

RAG = Retrieval-Augmented Generation: instead of relying on what the model memorized at training, you fetch relevant text at query time and put it in the prompt so the model answers from it [1]. Two halves:

Ingestion (offline). The decisions that quietly make or break recall:
  • Chunking — too big and you stuff irrelevant tokens (cost + dilution); too small and you sever context. ~200–500 tokens with overlap is the default; chunk on semantic boundaries (headings, paragraphs) when you can.
  • Embedding — one model, versioned. Change it and you must re-embed every chunk (embedding drift, Lesson 40) — use a versioned namespace.
  • Upsert — store vector + metadata (doc id, title, ACLs, timestamp) so you can filter and cite.
Query (online). The four-step retrieval chain:
  • Embed query with the same model.
  • Retrieve top-k (~50–100) via ANN — cheap, recall-oriented. Often hybrid: combine dense vectors with keyword/BM25 so exact terms (error codes, names) aren't lost.
  • Rerank the candidates with a cross-encoder → keep top ~5 by true relevance. Two-stage retrieval: cheap recall first, expensive precision on a tiny set [1].
  • Stuff & generate — put the top passages in the prompt with instructions to answer only from them and cite.
★ Staff-level signal Senior says "embed, retrieve top-k, stuff the prompt." Staff names the two-stage retrieve-then-rerank split and why (cheap recall, then precision), reaches for hybrid search so keywords survive, and treats chunking + embedding versioning as first-class design decisions rather than afterthoughts — because that's where retrieval quality, the top NFR, is actually won or lost.

2 · The agent loop & orchestration

A pure RAG app retrieves once and answers. An agent can reason about what to do: it may search, call an API, do a calculation, then decide whether it has enough to answer — a loop, not a single pass [3]. The classic shape is plan → act → observe → iterate:

StepWhat happens
PlanLLM, given the query + tool schemas, decides the next action (call a tool, or answer now).
ActOrchestrator executes the chosen tool — KB search, MCP server, SQL query, calculator — with model-supplied arguments.
ObserveTool result is appended to context; the LLM sees it on the next turn.
IterateLoop until the model emits a final answer or a step/cost budget is hit.
MCP & the orchestrator's job. Tools are exposed via schemas; the Model Context Protocol (MCP) standardizes "here is a tool, its inputs, and how to call it," so an agent can use third-party tools without bespoke glue [3]. The orchestrator is the deterministic harness around the non-deterministic model: it validates tool arguments, enforces a max-iteration / cost budget (or the loop runs forever and bills you), runs independent tool calls in parallel, and sandboxes side-effecting tools behind allow-lists and permissions.

Keep it simple by default. Most "agent" problems are one retrieval + one generation. Reach for the full loop only when the task genuinely needs multi-step tool use — an unnecessary agent loop adds latency, cost, and failure modes.
★ Staff-level signal The staff candidate puts the guardrails on the loop, not just the loop: bounded iterations, a token/cost budget, argument validation, sandboxed tools, and idempotency for side-effecting calls. They also say out loud "a single RAG pass beats an agent for most questions" — knowing when not to add the loop is the simple-by-default judgement L6/L7 rewards.

3 · Grounding, citations & hallucination mitigation

The #1 NFR. An LLM will confidently invent facts; grounding forces it to answer from retrieved evidence and to show its work [2].

LeverHow it reduces hallucination
CitationsPrompt the model to attach the chunk id behind each claim; the UI renders footnotes. Forces traceability and lets users verify [2].
AbstentionIf retrieval scores are weak/empty, instruct "say you don't know" rather than guess. Better to refuse than fabricate.
Retrieval qualityGarbage context → garbage answer. Reranking + hybrid search (deep dive 1) is the real grounding fix — most "hallucinations" are retrieval failures.
Faithfulness checkA second pass (or a cheaper model) verifies each sentence is supported by a cited chunk before returning. Costs a call; reserve for high-stakes answers.

The throughline: grounding is mostly an information-retrieval problem wearing an LLM costume. If the right passage isn't in the context, no prompt trick will save you.

4 · Caching, cost/latency control & streaming

Every turn costs an embedding call, a vector search, maybe a rerank, and a multi-second LLM generation. The levers:

  • Semantic cache — key on the query's embedding, not its exact text, so "what's your refund policy?" and "how do refunds work?" hit the same cached answer. A nearest-neighbor lookup with a tight similarity threshold; huge cost/latency win for FAQ-shaped traffic. Invalidate on doc changes.
  • Cache embeddings & retrieval — identical queries skip the embedding model and the vector DB entirely.
  • Control context size — fewer, better passages (thanks to reranking) cut input tokens, which cuts both cost and latency, and improves accuracy. Don't dump top-50 into the prompt.
  • Stream the answer — SSE token streaming for low time-to-first-token, same as Lesson 39. The user reads while the model writes.
  • Model tiering — route easy queries to a small/cheap model, hard ones to the frontier model. A router or the agent itself decides.

5 · Evaluation — proving it works

You can't ship grounding you can't measure, and "looks good in the demo" is not an answer at L6/L7. RAG eval splits in two:

LayerWhat you measure
RetrievalDid we fetch the right chunks? recall@k, precision@k against a labeled query→passage set. Cheap, deterministic, run in CI.
GenerationFaithfulness (is every claim supported by context?) and answer relevance. Often scored by an LLM-as-judge on a fixed eval set, sampled in prod.
OnlineThumbs up/down, citation click-through, deflection rate. Feeds the offline eval set.

The staff framing: most quality regressions are in retrieval, so eval the two stages separately — a bad answer from good context is a prompt problem; a bad answer from bad context is a retrieval problem, and you fix them in different places.

Check yourself — retrieval practice

Answer from memory before scrolling back up.

1. What is the point of the rerank step between retrieve and generate?

Two-stage retrieval: cheap ANN maximizes recall (~100 candidates), then a cross-encoder reranker picks the few most relevant for the prompt.

2. Most "hallucinations" in a RAG system are really a failure of what?

Grounding is an IR problem: if the correct chunk isn't retrieved, no prompt trick recovers it. Fix retrieval before blaming the model.

3. Why key a semantic cache on the query embedding instead of its text?

Semantic caching matches by meaning, so paraphrases of the same question share a cached answer — a big win for FAQ-shaped traffic.

4. What must the orchestrator enforce on the agent's plan-act-observe loop?

An unbounded loop runs forever and bills you; the harness caps iterations/cost, validates arguments, sandboxes tools, and parallels independent calls.
