Deep Dive: Elasticsearch

A distributed inverted index that pretends to be a database — know exactly where that illusion ends.

Why this lesson, for your mission: Almost every search, log-analytics, or "find me documents matching X" design ends with a candidate reaching for Elasticsearch. At L6/L7 the interviewer doesn't care that you named it — they probe whether you know what it's doing: the Lucene segment lifecycle, near-real-time refresh, BM25 scoring, the shard/routing model, and the one thing that gets candidates dinged hardest — treating it as a system of record. Naming the tool is senior. Explaining its internals and its failure boundaries is staff.

What it is

Elasticsearch is a distributed search and analytics engine built on top of Apache Lucene, a single-node Java search library that implements the inverted index.[1] Lucene gives you indexing, scoring, and querying on one machine; Elasticsearch wraps Lucene in a cluster: it handles sharding, replication, node discovery, a JSON/HTTP API, and aggregations.[2]

The mental model: a document store with a search engine bolted to the front of it. You index JSON documents; it builds inverted indexes over their fields; you query with rich full-text, filtering, and aggregation semantics and get back ranked results in milliseconds over billions of documents. It is the same machinery behind the Facebook Post Search and web search engine designs — this lesson is the "what's inside the black box" companion to those.

Where it fits in the stack.
  • Lucene — single-node library: inverted index, segments, BM25 scoring.[1]
  • Elasticsearch — distribution layer over Lucene: shards, replicas, routing, REST, aggregations.[2]
  • The ELK / Elastic Stack — Elasticsearch + Kibana (viz) + Beats/Logstash (ingest). Out of scope here.

Internals — the meat

This is the section that separates senior from staff. Everything below happens inside one shard, which is a complete Lucene index.[2]

The inverted index

A forward index maps document → terms; searching it means scanning every document. The inverted index flips it to term → posting list — for each term, the sorted list of document IDs containing it (plus term frequencies and positions for phrase queries).[1] A keyword lookup becomes a hash/tree lookup; a multi-word query becomes an intersection of posting lists.

"elastic"   → [d3, d17, d42, d91, ...]
"search"    → [d3, d42, d88, d91, ...]
"distributed" → [d3, d91, ...]

This is the lesson from Post Search — but Lucene adds a crucial twist in how the index is physically stored: segments.

Lucene segments — immutable, then merged

Lucene never edits an inverted index in place. Each batch of buffered documents is flushed to disk as an immutable segment: a self-contained mini inverted index.[1] A shard is just a set of segments plus a small "commit point" listing the live ones. Three consequences fall out of immutability, and naming them is the staff signal:

  • No locking on read. Segments never change, so queries read them without contention — great for concurrency and OS page-cache friendliness.[1]
  • Updates and deletes are not in-place. A "delete" just marks the doc ID in a per-segment .del bitset; an "update" is a delete + re-index of a new doc. The old bytes linger until merge.[1]
  • Segments accumulate. Many small segments slow queries (more lists to consult), so Lucene runs background segment merges: combine small segments into bigger ones and physically drop deleted docs.[1]

Merging is steady-state I/O and CPU you must budget for — it's why heavy-update Elasticsearch clusters burn disk and why "just update the doc" is more expensive than it looks.

Analyzers & tokenization

Before a text field is indexed, it passes through an analyzer: character filters → tokenizer → token filters.[2] Typical English analysis: lowercase, split on whitespace/punctuation, drop stop-words, optionally stem (running → run). The query string is analyzed by the same analyzer so query terms match indexed terms. Get this wrong (e.g. index with one analyzer, search with another) and results silently vanish — a classic real-world Elasticsearch bug.

Near-real-time refresh & the translog

Newly indexed documents are not instantly searchable. They sit in an in-memory buffer until a refresh turns the buffer into a new searchable segment — by default once per second.[2] That ~1s gap is why Elasticsearch is called near-real-time (NRT), not real-time. It's the same freshness budget you saw in the Post Search design.

But a refresh is not a durable fsync — so what protects data between refreshes and the slower flush (a real Lucene commit to disk)? The translog (transaction/write-ahead log).[2] Every write is appended to the translog before being acknowledged; on a crash, Elasticsearch replays the translog to recover acknowledged-but-not-yet-committed writes. Refresh makes data visible; the translog makes it durable; flush makes it committed and trims the translog.

The three lifecycle verbs — don't conflate them.
  • Refresh (≈1s): buffer → new segment → searchable. Visibility, not durability.[2]
  • Translog: append-only WAL; replayed on crash for durability between flushes.[2]
  • Flush: fsync segments via a Lucene commit, then clear the translog. Durability + committed.[2]

Relevance scoring — BM25

Returning matches is easy; ranking them is the search problem. Since Lucene's default, the scoring function is BM25, a refinement of TF-IDF.[1] Intuition: a document scores higher when a query term appears often in it (term frequency), but with diminishing returns — the 20th occurrence barely beats the 10th — and rarer terms across the corpus count for more (inverse document frequency). BM25 also normalizes for document length so a long document isn't unfairly favored just for containing more words.[1] Filters (e.g. status = active) skip scoring entirely and are cacheable; full-text queries pay the BM25 cost.

Distribution

Lucene is one node. Elasticsearch's job is to make many Lucene indexes behave like one.

Indices → shards → replicas

An index is a logical collection of documents. It is split into primary shards, each a full, independent Lucene index; each primary has zero or more replica shards (copies on other nodes).[2] Primaries give you horizontal scale (the corpus spans nodes); replicas give you availability (survive a node loss) and read throughput (queries can hit replicas).

UnitWhat it isBuys you
IndexLogical doc collection (e.g. logs-2026).Namespacing, mapping/schema.
Primary shardOne independent Lucene index; a slice of the data.[2]Horizontal scale of data + indexing.
Replica shardA copy of a primary on another node.[2]HA + extra read throughput.

Routing — which shard owns a document

A document's home shard is deterministic: shard = hash(routing) % number_of_primary_shards, where routing defaults to the document ID.[2] This is why you can fetch a doc by ID without a cluster-wide search — and, crucially, why the primary shard count is fixed at index creation: it's baked into the modulo.

Scatter-gather query & aggregations

A search doesn't know which shards hold matches, so it fans out. The coordinating node scatters the query to one copy of every shard; each shard runs the query locally and returns its top-K (the cheap query phase); the coordinator merges into a global top-K and then fetches the full documents for just those winners (the fetch phase).[2] Aggregations work the same way: each shard computes a partial aggregation, the coordinator combines them — which is why some aggregations are approximate (e.g. terms cardinality) at high shard counts.

The reindex & shard-count pain

Because routing hard-codes the primary shard count, you cannot change it on a live index. Outgrowing your shard count means reindexing into a new index with a new count and swapping an alias over — an expensive, full-corpus rewrite.[2] The staff move is to dodge this entirely:

Avoiding the reindex trap.
  • Size shards up front — aim for tens of GB per shard, not too many tiny shards (each carries overhead).[2]
  • Time-based indices + aliases for logs/metrics: roll over to a fresh index daily/by size; query the alias. New scale = new index, no reindex.[2]
  • Replicas, not primaries, are the dial you can change live — add them for read throughput on the fly.[2]

When to reach for it — and when NOT

The single highest-value judgement in an interview: Elasticsearch is a search and analytics index, not a system of record. It is eventually consistent, has no multi-document transactions, and its update model (delete + re-index + merge) is poor for hot mutable rows. Lose a shard mid-write and you can lose acknowledged data in ways a primary database would not.

Reach for it when…Reach for something else when…
Full-text / fuzzy / relevance-ranked search over large corpora.You need ACID transactions or strong read-your-write (use Postgres/MySQL).
Log & metrics analytics, faceting, aggregations at scale.It's your only copy of critical data (it must not be the source of truth).
Read-heavy, eventually-consistent, append-mostly workloads.Heavy per-row updates / counters (the merge cost crushes you).
★ Staff-level signal The pattern that signals seniority: keep the source of truth in a database, and feed Elasticsearch from it. Don't dual-write from the app (the two stores will silently drift on partial failures). Instead, stream changes via CDC (e.g. Debezium reading the DB binlog) → a queue → an indexer that upserts into Elasticsearch. The DB owns correctness and transactions; Elasticsearch owns search. If the index is corrupted or you must change shard count, you rebuild it from the DB — it's a derived, disposable view. A candidate who proactively says "Elasticsearch is a secondary index, not my database" has already passed this part of the loop.

In the interview

How this topic actually shows up, and how to handle it like staff:

  • Don't stop at "use Elasticsearch." Say it, then immediately explain the inverted index, NRT refresh, and that it's a secondary index fed from your DB. That one extra breath is the senior→staff jump.
  • Lead with the source-of-truth boundary. State it before the interviewer probes — proactive deep dives are exactly the staff behavior being scored.
  • Know the freshness story. "~1s refresh, durable via translog, NRT not real-time" answers the consistency question crisply.
  • Anticipate the shard-count trap. Mention fixed primary count + reindex/alias up front; reach for time-based indices for log workloads.
  • Don't over-explain BM25. "TF-IDF with saturation and length normalization, default since Lucene" is enough — model the judgement of not rabbit-holing.

Check yourself — retrieval practice

Answer from memory before scrolling back up.

1. Why are Lucene segments designed to be immutable?

Immutable segments mean lock-free reads; updates/deletes are deferred and reclaimed at merge time.

2. What makes Elasticsearch "near-real-time" rather than real-time?

Writes become visible only when a refresh turns the buffer into a segment — the default ~1s gap.

3. Why is the primary shard count fixed when an index is created?

Document placement is hash(routing) % primaries; changing the count would break every lookup, so you reindex.

4. What is the staff-correct way to keep Elasticsearch in sync with data?

DB owns correctness; CDC → queue → indexer feeds ES as a derived, rebuildable secondary index. Dual-writes drift.
