System Design · Lesson 123 · Phase 4 — Case Study · Hard

Design an Inventory Management System

Hundreds of warehouses, millions of stock movements a day, and two conflicting demands: never let two pickers claim the same unit, and never make a store manager in Ohio wait more than a second to see what a picker in Texas just took off the shelf.

Why this lesson, for your mission: Inventory looks like a CRUD counter until you notice it's actually a ledger under contention — hundreds of warehouses each running thousands of concurrent scans, reservations, and adjustments against the same SKUs, while dashboards, replenishment jobs, and e-commerce storefronts all need to see the change within a second or two.[1] The staff signal is recognizing this as the same shape as the flash-sale inventory problem generalized across geography and time: partition the ledger so contention stays local to one warehouse-SKU pair, make every mutation an atomic, idempotent, auditable event, and propagate that event out over a change-feed instead of asking every client to poll. That's the difference between "I can decrement a counter" and "I can run a global, race-free, real-time ledger."

Phase 1 · 0–5 minClarify the problemPin scope and the few NFRs that will drive every later decision.

Ask before you design

  • "Is stock tracked per warehouse, or one global pool?" — Per-warehouse partitioning is what keeps contention local; a global pool would make every write globally contended.
  • "Do we need to support reservations/holds (e.g. an order being packed), or just direct decrements?" — Holds add a second state machine (reserved vs. available) on top of raw stock.
  • "How fresh must a read be — can a dashboard show stock that's 2 seconds stale, or must it be exact?" — Decides whether reads go through cache/streams or must hit the source of truth.

Functional Requirements

Lock scope to the core ledger operations. Push supplier ordering, demand forecasting, and returns/RMA workflows out of scope and say so — they consume this ledger, they don't define it.

#Users / systems should be able to…Note
1Adjust stock at a warehouse (receive, pick, cycle-count correction)Write path — the contended core
2Reserve stock for an order and later commit or release the holdTwo-phase claim, same shape as flash-sale reservations
3Query current stock for a SKU at one warehouse or aggregated across allRead path — far higher volume than writes
4Receive near-real-time updates when stock they're watching changesThe crux: push, not poll, to every subscribed client within ~1–2s

Non-Functional Requirements

One sentence carries the whole design: every stock mutation must be linearizable per warehouse-SKU, and every observer must see it within about a second, without serializing unrelated SKUs against each other.

★ Staff-level signal Say out loud that contention in this system is naturally partitioned by warehouse and SKU — a forklift in Dallas and a forklift in Seattle never touch the same physical unit. The staff move is refusing to build one global lock or one global sequence number, and instead making the partition key do the work: correctness only needs to be strict within a (warehouse, SKU) pair, and everything across pairs can run fully in parallel. That's the same principle as sharding a database by tenant, generalized to physical inventory.

Interviewer pushback

"25M movements a day doesn't sound like much — why is this hard?"

Staff answer: The volume is modest; the hardness is in guaranteeing linearizable updates independently across hundreds of thousands of partitions while pushing every one of them to interested subscribers in near real time — breadth and freshness, not raw QPS.

Say to move on → "Low per-partition contention, high fan-out. Let me define entities."

Phase 3 · 10–17 minAPI & data modelLock the contract and the storage shape before drawing boxes.

Core Entities & API

Entities: Sku (id, name, category), Warehouse (id, region, address), StockLevel (warehouse_id, sku_id, on_hand, reserved, version — the hot row), StockMovement (id, warehouse_id, sku_id, delta, reason, actor, timestamp — the append-only audit event), and Reservation (id, warehouse_id, sku_id, qty, order_id, expiry). StockMovement is the source of truth; StockLevel is a materialized, cached aggregate of it.

Caller identity always comes from a service token or authenticated session, never the request body.

EndpointPurpose

GET /v1/stock/{sku}?aggregate=trueCross-warehouse total for a SKU — served from a read-optimized aggregate.
POST /v1/warehouses/{wid}/movementsRecord a stock movement: {sku, delta, reason}. Atomic, idempotent via Idempotency-Key.
POST /v1/reservationsReserve: atomically moves qty from on_hand to reserved for an order; TTL-bound.

WS /v1/stock/stream?warehouse=&sku=Subscribe to near-real-time stock-level change events for a filter set.

Splitting movement (unconditional ledger entry, e.g. receiving or a cycle-count correction) from reservation (conditional hold tied to a pending order) mirrors the reserve/commit split in flash sale checkout — a reservation is a soft claim that can expire; a movement is a durable fact.

Data Model

A relational store (Postgres/CockroachDB/Spanner-class) holds the ledger and current levels as the source of truth; Redis caches hot read-aggregates; Kafka carries the change feed. The write path never touches a global table — every operation keys on (warehouse_id, sku_id), which is also the shard/partition key.

Interviewer pushback

"Why keep both a mutable stock_levels row and an immutable movement log?"

Staff answer: The log is the audit trail and the recovery mechanism — if the aggregate ever drifts, replaying movements rebuilds it exactly. The mutable row is just a cached projection for fast reads; it's never the only copy of the truth.

Say to move on → "Ledger plus cached level, event-sourced. Now the end-to-end flow."

Flow. A picker's scan or an order's hold hits POST /movements or /reservations; the Inventory Service applies it as one optimistic-concurrency update keyed on (warehouse_id, sku_id) and commits the ledger row in the same transaction. CDC picks up that commit, in order, per key, and publishes to Kafka. Two consumers fan out independently: one refreshes the Redis cache so the next GET is fresh, the other pushes the delta over WebSocket/SSE to every client subscribed to that warehouse or SKU — typically landing within a second of the original write.

Interviewer pushback

"Why CDC instead of having the Inventory Service publish the event itself after the DB write?"

Staff answer: A dual-write (commit to Postgres, then publish to Kafka) can succeed on one and fail on the other, silently desyncing cache and clients from the ledger. CDC reads the database's own commit log, so the event stream is guaranteed to match what was actually durably written — no dual-write, no lost events.

Say to move on → "Deep dives: concurrent writes, real-time fan-out, sharding, and the audit ledger."

Phase 5 · 27–47 minDeep dives & tradeoffsGo deep where the system breaks; compare alternatives and justify the pick.

Deep Dive 1 — Concurrent updates to the same warehouse-SKU row

Two pickers scan the last two units of a SKU within milliseconds of each other; a cycle-count job corrects the same row at the same instant. Any of these racing without coordination can lose an update. Mechanisms, escalating in fit:

MechanismHowWhy it fits / fails
Last-write-wins, no coordinationBlind UPDATE on_hand = ? with a client-computed new valueBroken. Two concurrent reads-then-writes silently clobber each other; one movement is lost with no error.
Pessimistic row lock (SELECT … FOR UPDATE)Lock the stock_levels row for the duration of the updateWorks, usually overkill. Correct, but per-row contention here is low (~2 writes/s/warehouse) — a lock is fine but adds latency for no real throughput benefit at this contention level.
Optimistic concurrency (version column) — staff pickUPDATE stock_levels SET on_hand = on_hand + delta, version = version + 1 WHERE warehouse_id=? AND sku_id=? AND version = ?; retry on 0 rows affectedBest fit. No lock held across a network round trip; a losing writer just retries with the fresh version. Cheap when contention is low, and it's exactly what this workload is — unlike the flash-sale case, we don't need Redis-speed atomics here.
CRDT counter (commutative merge)Each warehouse node applies deltas locally; counts converge via commutative merge, no coordinationOverkill here. Useful for multi-master, offline-tolerant edge writes (e.g. a warehouse temporarily disconnected), but adds merge complexity this system doesn't need if each warehouse has one authoritative shard.
The staff pick — and why. Optimistic concurrency control (a version column, conditional update, retry-on-conflict) per (warehouse_id, sku_id) row.
  • Match the tool to the actual contention. This is not a flash sale — write rates per row are low, so paying for a distributed lock or an in-memory atomic counter buys nothing. OCC gives full correctness with zero lock-hold latency.
  • Movements are commutative deltas, not overwrites. Because every write is on_hand = on_hand + delta rather than on_hand = new_value, a retry after a version conflict simply reapplies the same delta against the fresh row — no re-derivation needed.
  • Escalate only where it's warranted. If a specific SKU becomes hot (e.g. a single popular item during a promo at one warehouse), that pair can fall back to the same Redis-atomic-counter pattern as the flash-sale deep dive — the two systems share a playbook, applied where each fits.

Deep Dive 2 — Near-real-time propagation to other clients

A store manager's dashboard, a storefront's "in stock" badge, and a replenishment job all need to learn about a change within about a second — without every one of them polling the database.

MechanismHowWinsLoses
Client pollingEach client GETs stock every N secondsTrivial to buildEither stale (long interval) or hammers the read path (short interval); doesn't scale with subscriber count
Long pollingClient blocks until a change or timeoutLower latency than fixed pollingTies up a connection per client; still not truly push
CDC → Kafka → WebSocket/SSE fan-out — staff pickLedger commit is tailed via CDC, published once per key on Kafka, and pushed to subscribed connectionsSub-second delivery, one write triggers exactly one fan-out event, scales with consumer group parallelism (see Real-Time Delivery)More infrastructure (CDC connector, Kafka, connection-holding gateway)
★ Staff-level signal The insight to name: the change feed is the same artifact that both refreshes the cache and drives the real-time push — one CDC stream, two consumers. Building a separate "notify clients" code path inside the write transaction (rather than deriving both from the commit log) is the classic mistake that reintroduces the dual-write problem this design exists to avoid.

Subscribers filter by warehouse or SKU range at the gateway (consumer group partition assignment mirrors the Kafka key), so a storefront watching 200 SKUs isn't pushed the other 199,800. Where a client can't hold a socket (e.g. a batch replenishment job), it reads the same feed via a durable Kafka consumer instead of WebSocket — same freshness guarantee, different transport.

Deep Dive 3 — Partitioning and sharding at hundreds of warehouses

With (warehouse_id, sku_id) as the natural key, the sharding decision is which part of that key to shard on.

Shard by warehouse_id.
  • Every write for a given warehouse hits one shard — matches the physical reality (one warehouse's forklifts never contend with another's) and keeps transactions single-shard, avoiding distributed transactions on the hot path.
  • A single warehouse going down (network partition, maintenance) only affects reads/writes for that warehouse; the other 499 are unaffected — directly satisfies the availability NFR.
  • Cross-warehouse aggregate reads (total stock for a SKU nationwide) become a scatter-gather across shards — acceptable because aggregates are read from the pre-built materialized view (Deep Dive 4's downstream consumer), not computed live across shards per request.
  • Hot warehouses (a regional distribution center doing 50× the movements of a small store) can be split further by sku_id range within that warehouse if one shard becomes disproportionately busy.

Sharding by sku_id instead would make popular-SKU aggregation cheaper but scatter every single warehouse's writes across all shards, turning a routine local operation (receiving a truckload at one warehouse) into a cross-shard fan-out — the wrong tradeoff for this workload.

Interviewer pushback

"Could we just use HBase or Bigtable, row-keyed on warehouse_id:sku_id, instead of sharded Postgres?"

Staff answer: The row key fits, and single-row checkAndMutate gives us the same atomic conditional update as OCC. But two things this design needs aren't there: a supported CDC connector (Debezium has no HBase source), and secondary/range queries for the cross-warehouse aggregate — both would have to be bolted on, reintroducing the dual-write risk CDC exists to avoid. HBase also drags in an HDFS/ZooKeeper stack sized for far higher throughput than our ~3-6k writes/s peak. It's the right tool for wide-column time-series at 10-100× this volume with no relational needs, not for a transactional ledger with real-time fan-out.

Deep Dive 4 — The movement ledger as the source of truth (event sourcing)

If stock_levels were the only record, any bug, bad retry, or partial failure permanently corrupts the count with no way to check or replay it. Treating every change as an immutable, appended StockMovement event — and deriving stock_levels from it — buys three things:

Event-sourced ledger.
  • Auditability. "Why does the count say 340?" is answered by replaying every movement for that key — required for loss investigations and financial reconciliation of inventory value.
  • Idempotent retries. Each movement carries an Idempotency-Key; a retried scan (flaky warehouse Wi-Fi) inserts the same movement row once via a unique constraint, never double-applies.
  • Drift detection and repair. A periodic reconciler recomputes on_hand from the movement log and compares it to the cached aggregate; any mismatch is a bug signal, and repair is "replay from the log," not "guess."
  • The CDC stream falls out for free. Because movements are append-only inserts, tailing the WAL for new rows is exactly the change feed Deep Dive 2 needs — no separate event-authoring step.

The unifying principle across all four deep dives: partition correctness to where contention actually lives (per warehouse-SKU), and derive everything else — cache, real-time push, audit trail, aggregates — from one append-only log of what actually happened.

Interviewer pushback

"What happens if two warehouses need to transfer stock between each other atomically?"

Staff answer: Model the transfer as two movements (a decrement at the source, an increment at the destination) tied by a saga: the destination increment only commits after the source decrement is durably recorded, with a compensating re-increment at the source if the destination leg fails. It stays two independent single-shard transactions instead of one distributed one.

Wrap-up · 58–60 minClose strongRecap decisions and tradeoffs in 60 seconds; name what you would do next.

Closing Summary (60 seconds)

Inventory management is a partitioned-ledger problem: shard by (warehouse_id, sku_id) so contention never crosses warehouses, use optimistic concurrency because per-row write rates are low, and store every change as an immutable movement event rather than mutating a bare counter. A CDC stream off that ledger's commit log is the single source for both the read cache and a WebSocket/SSE fan-out, giving every subscriber sub-second visibility without polling and without a dual-write hazard. Reservations layer a TTL-bound hold on top of the same ledger for order fulfillment. At 10× warehouses, only shard count, Kafka partitions, and cache/gateway fleets grow — the aggregate builder is the first thing to need real redesign attention.

Check yourself — retrieval practice

Answer from memory before scrolling back up.

1. Why shard the inventory ledger by warehouse_id rather than by sku_id?

A forklift's scan only ever touches its own warehouse's rows. Sharding by warehouse_id keeps every routine write single-shard and isolates one warehouse's incidents from the rest.

2. Why is optimistic concurrency control preferred over a pessimistic row lock here?

Unlike a flash sale's single hot row, each warehouse-SKU pair here sees only a couple of writes per second — OCC gives full correctness without paying for a held lock.

3. Why derive the cache refresh and the real-time push from CDC on the same commit log, instead of publishing an event from the write path directly?

A direct dual-write can commit to the database but fail to publish (or vice versa), silently desyncing clients from the ledger. CDC reads the database's own durable commit log, so the event stream can never diverge from what was actually written.

4. Why is stock tracked as an append-only movement log rather than only a mutable on_hand counter?

The mutable counter is just a cached projection of the log. If it ever drifts from reality, replaying the immutable movement log rebuilds the correct value and shows exactly what happened.
