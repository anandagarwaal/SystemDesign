Deep Dive: Change Data Capture (CDC)

Your database just changed a row. How do search, the cache, the warehouse, and three other regions find out — reliably, in order, without you bolting on a second write?

Why this lesson, for your mission: The moment a system has more than one place that needs the same data — Postgres for the source of truth, Elasticsearch for search, Redis for the cache, a warehouse for analytics — you face the synchronization problem. The naive answer ("write to the DB, then also write to Elasticsearch") is the dual-write bug, and it silently corrupts data on every crash. CDC is the staff-level answer interviewers hope you'll reach for in feed, search, cache-invalidation, and migration designs. Knowing it lets you say "I'll stream changes off the WAL" instead of "I'll keep them in sync somehow."

What it is & why you need it

Change Data Capture is the practice of streaming row-level changes (inserts, updates, deletes) out of a database as an ordered event stream, so downstream systems can react to every change without polling and without the source application doing extra writes.[2]

It exists to kill the dual-write problem. Suppose your service must update Postgres and index the document in Elasticsearch. Doing both from application code means two independent systems and no shared transaction: if the process crashes after the Postgres commit but before the Elasticsearch write, the two stores disagree forever — and no try/catch fixes it, because the crash can land between any two lines.[2] CDC inverts the flow: the application writes to one database, and that database's own change log becomes the single, ordered source of truth that everyone else follows. Consistency becomes "downstreams converge to the DB," not "hope two writes both succeed."

Internals: three ways to capture changes

ApproachHowVerdict
Query-based (polling)Periodically SELECT … WHERE updated_at > last_seen.Simple but adds DB load, misses deletes, and can skip changes between polls; coarse latency.
Trigger-basedDB triggers write change rows to an audit table on every mutation.Captures everything but doubles write load and couples to schema; heavy.
Log-based ✅Tail the DB's write-ahead log / binlog (Postgres WAL, MySQL binlog) directly.The preferred method — near-zero overhead, captures every change in commit order, including deletes.[1]
Why log-based CDC wins (the Debezium model)
  • Every durable database already writes a write-ahead log for crash recovery and replication (see Postgres, Lesson 88). That log is an authoritative, totally-ordered record of every committed change — CDC just reads a log that already exists.[1]
  • A connector (e.g. Debezium) registers as a replication consumer, reads the WAL, and emits a structured event per row change: {op, before, after, table, ts, lsn}.[1]
  • Snapshot + stream: on first start it takes a consistent snapshot of existing rows, then switches to streaming the log from that point — so downstreams get the full dataset, then live deltas.
  • Offsets: the connector checkpoints its position (the log sequence number / LSN). After a restart it resumes from the last committed offset, giving at-least-once delivery — which is why every consumer must be idempotent.
  • Schema changes (DDL) flow through the log too and must be handled (schema registry / evolving event shape) — a common real-world gotcha.

Patterns CDC unlocks

  • DB → Kafka → consumers: the canonical pipeline. CDC publishes changes to a Kafka topic; search indexers, cache updaters, and analytics jobs each subscribe independently and stay in sync. One source, many materialized views.[2]
  • Transactional outbox: the application writes business state and an outbox row in one local transaction; CDC tails the outbox table and publishes the events, eliminating the dual write (the robust backbone of the Saga pattern — see Lesson 112).
  • Cache invalidation: when a row changes, the CDC stream tells the cache layer to evict or update the affected key — no more stale reads from a cache the writer forgot to bust.
  • Zero-downtime migration & cross-region replication: snapshot the old store, then stream ongoing changes via CDC into the new store / other regions until they're caught up, then cut over — the basis of online schema migrations and replicating ~30 regional DBs into one central warehouse.

When NOT to use it / pitfalls

CDC adds operational weight — a connector to run, a broker to feed, offsets to monitor, and replication slots that, if a consumer stalls, can pin WAL on the source and fill its disk (a classic Postgres outage). For a single small service with one datastore, you don't need it. Other traps: it's eventually consistent (downstreams lag the source by the pipeline latency), at-least-once (design idempotent consumers), and ordering is only guaranteed per-key/partition, not globally.

★ Staff-level signal When a design needs the same data in two places, a junior says "I'll keep them in sync" or "write to both." A staff candidate names the dual-write problem out loud — "writing to Postgres and Elasticsearch separately means a crash between them corrupts state forever" — and reaches for log-based CDC: "I'll stream the WAL with Debezium into Kafka; the search indexer and cache updater consume it idempotently."[1] The deeper signal is naming the failure modes unprompted: at-least-once delivery (hence idempotency), per-key ordering only, and the replication-slot-fills-the-disk risk if a consumer falls behind. That's the difference between having heard of CDC and having operated it.

In the interview

Reach for CDC whenever your design has a source of truth plus derived stores: a feed that needs search, a write DB that feeds a cache, an analytics pipeline, or a migration. Say it in one arc: "There's a sync problem here — writing to both stores from the app is a dual-write bug. I'll make Postgres the single writer and stream its WAL via CDC into Kafka; downstream search/cache/warehouse consumers apply changes idempotently and in per-key order." Then flag the cost (eventual consistency, an extra moving part) so it's clear you're choosing it, not cargo-culting it.

Check yourself — retrieval practice

Answer from memory before scrolling back up.

1. What core problem does CDC primarily solve?

By making the DB the single writer and streaming its changes, CDC removes the corruption risk of writing to two systems independently.

2. Why is log-based CDC preferred over polling or triggers?

The WAL already exists for recovery, is totally ordered, and records every change including deletes — far cheaper than polling or triggers.

3. Why must CDC consumers be idempotent?

After a restart the connector resumes from its last checkpoint and may re-emit events, so each change can arrive more than once.

4. How does CDC enable zero-downtime data migration?

A snapshot seeds the new store and the change stream keeps it current, so you can cut over once the new store has caught up — no downtime.
