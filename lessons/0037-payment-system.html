Design a Payment System

Charge an external provider, record the result exactly once, and never lose or double-spend a cent.

Why this lesson, for your mission: Payments is the canonical "correctness over everything" interview. A senior candidate draws the happy path; a staff candidate assumes the network will fail mid-charge and designs so that no failure produces a lost or duplicated payment. The whole bar here is reasoning about partial failure across a system you don't control (the provider) — idempotency, dual-write consistency, and an auditable ledger.

Functional Requirements

Scope tightly to what actually exercises the hard parts. The interview version centers on charging a customer, recording the result, and being able to prove that record later.[1]

#Requirement
1A user can pay for an order — the system charges an external payment provider (e.g. Stripe) and records success or failure.
2A user/merchant can view the status of a payment (initiated, pending, succeeded, failed).[1]
3A user can refund a completed payment.
4The system reconciles its own ledger against the provider's settlement records to catch discrepancies.

Out of scope (state it, then drop it): recurring/subscription billing, payouts to merchants, fraud scoring, PCI tokenization internals. HelloInterview explicitly defers refunds and recurring payments in its base scope[1] — we pull refunds in because they exercise the same idempotency machinery in reverse.

Non-Functional Requirements

Payments invert the usual priority order: correctness beats availability beats latency. It is better to reject a payment than to charge twice.

PropertyTarget / priority
CorrectnessHighest. No lost money, no double-charge. Every charge maps to exactly one provider charge.
Durability & auditabilityNo transaction data is ever lost, even on failure;[1] every state change is permanently recorded for audit.
ConsistencyOur DB and the provider's view must converge — eventual is acceptable, divergence is not.
ReliabilitySurvive provider timeouts/outages without corrupting state; degrade by queuing, not by guessing.
LatencySoft target: charge confirmation in seconds. Acceptable to go async and confirm later.

Capacity Estimation

Estimate only the numbers that change the design.

  • Throughput: ~10,000 transactions/sec at peak is the canonical target.[1] At ~864M txns/day this rules out a single DB node — we shard the payments store and process asynchronously.
  • Storage: a payment record (ids, amounts, status, timestamps, provider refs) ≈ 1 KB. Plus ledger entries (two per txn under double-entry). ~10K/s × 86,400 s × ~2 KB ≈ ~1.7 TB/day. Cheap per row, but it compounds.
  • Retention: financial records are kept for years (often 7+ for compliance), never deleted, only archived to cold storage. This forces an append-only design — you never overwrite, you append the next state.

Design implications: shard + queue for the 10K/s; append-only ledger for the retention/audit need.

Core Entities & API

Three entities carry the weight. The caller's identity comes from the auth token, never the request body.

  • Payment — one attempt to charge an order. Holds orderId, amount, status, idempotencyKey, and the provider's charge id once known.
  • LedgerEntry — an immutable debit or credit. Append-only; the source of truth for "what happened".
  • Refund — a payment in reverse, with its own idempotency key, linked to the original payment.

High-Level Design

Request flow for POST /v1/payments: the client hits the Payment API behind a load balancer. The service first checks the idempotency store for the key; if seen, it returns the stored result. Otherwise it writes a Payment row in initiated state plus an outbox event in one local transaction, then a worker calls the external provider, and the provider's webhook (with polling as a fallback) drives the payment to succeeded/failed. Every state transition appends ledger entries.

Deep Dives

1 · Exactly-once — no double-charge

The core threat: a client times out, retries, and you charge twice. Defense is a client-supplied idempotency key per logical payment.[2] On arrival the API does a conditional insert into an idempotency store keyed by (idempotencyKey). First write wins and proceeds; any later write with the same key short-circuits and returns the stored response. This is the same retry-dedup discipline from Lesson 07 (idempotency) and Lesson 10 (message-delivery semantics) — at-least-once delivery + idempotent processing = effectively exactly-once.

Crucially, pass that same key through to the provider — Stripe and similar accept an idempotency key and dedupe on their side, so even if our worker retries the HTTP call, the provider charges once.[2]

Model the lifecycle as an explicit state machine so illegal transitions are impossible:

initiated → pending (provider call in flight) → succeeded | failed.
  • Only initiated may start a charge; a second attempt sees a non-initiated row and refuses.
  • Transitions are forward-only and recorded; succeeded/failed are terminal.
  • A refund is its own state machine on a linked entity, with its own key.

2 · Consistency between your DB and the provider — the dual-write problem

The trap: "write my DB, then call the provider" is a dual write. If the process dies between them you have a charge with no record (lost money) or a record with no charge. You cannot wrap a remote API call in a local DB transaction.

The fix is the transactional outbox: in one local transaction, write the Payment row and an event into an outbox table. A relay then reads the outbox and publishes to the queue, retrying until the provider call succeeds. Because the event and the state are committed atomically, the message is never lost and never published without the matching DB change.[2]

For the multi-step flow (reserve → charge → confirm → fulfill), a Saga coordinates the steps with a compensating action for each — e.g. if fulfillment fails after capture, trigger a refund rather than leaving money stranded. Async confirmation arrives via provider webhooks; because webhooks can be missed or delayed, run a polling fallback that periodically queries the provider for any payment stuck in pending.

3 · Reconciliation & the append-only ledger

Even with the above, drift happens: a webhook is lost, a provider reverses a charge, a bug miscounts. The safety net is a daily reconciliation job that parses the provider's settlement file and compares it line-by-line against your ledger, flagging any record present on one side but not the other (or with mismatched amounts) for investigation.[3]

That comparison only works if your ledger is trustworthy, which is why it's an append-only, double-entry store. Money is never updated in place; every transaction writes at least two entries — a debit from one account and a matching credit to another, and they must sum to zero.[3] This makes the balance derivable from history, makes tampering obvious, and gives reconciliation a stable thing to diff against.

4 · Provider timeouts & failures — "was the charge made?"

The nastiest case: you call Stripe, the request times out, and you don't know if the charge succeeded. Never blindly retry a charge — that's how you double-bill. Instead:

  • Retry with the same idempotency key. The provider recognizes it and returns the original result instead of charging again, so a retry is safe by construction.[2]
  • Or query before acting: look up the payment by your idempotency key on the provider to learn the true state, then advance your state machine accordingly.
  • Bound retries with backoff; if the provider is down, payments sit in pending in the durable queue and drain when it recovers — degrade by queuing, not by guessing.
★ Staff-level signal Three moves separate staff from senior here: (1) reach for idempotency keys unprompted and pass them through to the provider, treating double-charge as the default risk; (2) name the dual-write problem by name and solve it with a transactional outbox (or Saga for multi-step), rather than hand-waving "we update both"; (3) propose an append-only double-entry ledger plus reconciliation as the auditability backstop. Bonus: stating that correctness outranks availability, and that you'd rather fail a payment than risk charging twice.

Check yourself — retrieval practice

Answer from memory before scrolling back up.

1. A client times out and retries the same payment. What prevents a double-charge?

The idempotency key is deduped locally and passed through, so the provider charges once.

2. "Write our DB, then call the provider" is risky because it is a:

A crash between the two non-atomic writes loses money or a record — solve with a transactional outbox.

3. What makes the daily reconciliation job trustworthy to diff against?

Append-only double-entry means balances derive from history and tampering is visible.

4. The provider call times out and the charge's outcome is unknown. The safe move is:

Same-key retry is idempotent on the provider; querying reveals the true state without re-charging.
