Design a Voting System

Millions of people cast votes on a live poll, the tally updates on everyone's screen in near-real-time, and yet the final number has to be exactly right — accuracy and low latency pulling in opposite directions.

Why this lesson, for your mission: A voting system looks like a counter with one extra rule — "one vote per user" — and that rule is the whole interview. The L6/L7 signal is recognizing two systems hiding inside one: a fast, eventually-consistent live tally that viewers watch, and a slow, authoritative source of truth that decides the result. Staff candidates separate those paths up front, make votes idempotent so a retry can't double-count, and say out loud which number is allowed to be wrong and which one never is.[1]

Functional Requirements

Keep the core list tight. This is a vote-recording and tallying service — comments, the poll-authoring UI, and identity provisioning are out of scope.

#Users should be able to…Why it shapes the design
1Cast a vote on an option (and update it)Write path — must enforce one-per-user; "latest vote wins" needs an upsert, not a blind insert
2Be prevented from double-votingIdempotency + dedup keyed by (pollId, userId) — the core correctness rule
3See near-real-time results per optionRead path — huge read volume on a live poll, tolerant of a few seconds of lag
4Have the poll close and freeze a resultTransition from live tally to authoritative final count — the accuracy moment
Out of scope (say it out loud): poll creation/editing, authentication itself (we trust a verified identity in the token), rich result analytics, and weighted or ranked-choice ballots. We own one thing: recording a verified user's choice exactly once and showing a correct tally per (pollId, optionId). The "latest-vote-wins" and "one-and-done" variants are the same machine with one flag.[1]

Non-Functional Requirements

This system is defined by its NFRs. Two numbers must be right (final tally, one-per-user); the live view is allowed to be approximate.

NFRTarget / priority
No double countingA retried or double-clicked vote counts once; the final per-option tally is exact[1]
Integrity / one-per-userOne identity = one effective vote; a changed vote moves, never adds[2]
Near-real-time resultsLive tally visible within a few seconds; sub-second is nice, not required
Accuracy > latency at closeThe displayed live count may lag; the final count is authoritative and reconciled[3]
Absorb spikesA poll on a live broadcast can 50–100× in seconds; never drop or block a vote
The key tension: viewers want the bar to move now, but the result that decides a winner must be provably correct. You cannot get instant and authoritative from the same number cheaply. So you build two: an eventually-consistent live tally fed by an aggregation pipeline (fast, approximate, may lag) and a durable per-vote ledger that is the source of truth (slower, exact, replayable). Naming "the live number is eventually consistent, the final number is authoritative" is the unlock.[3]

Capacity Estimation

Only the numbers that change a decision: per-poll write spikes (does one poll melt?), the read/write skew (do we cache?), and storage of the ledger (does exact dedup fit?).

  • Spiky writes: a poll on a live TV moment might take 10M votes in 5 minutes ≈ ~33K votes/sec average, peaking 2–3× ⇒ ~100K write QPS onto one poll. A single row/key serializes that. Implication: shard the per-option counter and buffer in a queue (DD3).
  • Read/write skew: every viewer polls or subscribes for the live tally; reads can be 100×–1000× writes ⇒ millions of read QPS. Implication: reads served from a cached tally, never from the live ledger.
  • Ledger storage: one vote row is ~tens of bytes (pollId, userId, optionId, ts). Even 10M votes/poll is a few hundred MB — trivial, and it gives us exact dedup and a recount. Keep the ledger; it is the source of truth.
  • Dedup set: a bitmap/set of (pollId, userId) is small per poll and answers "has this user voted?" in O(1) without scanning the ledger.
Design implication: you never scale for storage — you scale to defeat per-poll write contention during spikes and to serve the live tally from cache while a durable ledger guarantees the final number.

Core Entities & API

Entities

EntityFields (sketch)
PollpollId, options[], mode (latest-wins/one-shot), status (open/closed), closesAt
VotepollId, userId, optionId, ts — the durable ledger row; PK (pollId, userId) makes it an upsert (DD1)
TallypollId, optionId, count — logically one number per option, physically N shards; the cached live view (DD2)

API

Derive userId from the auth token, never the body. The write is a command ("user U chose option O"), not a raw "+1", so the server can dedup and apply latest-wins.

  • POST /v1/polls/{id}/votes — body { optionId }; user from JWT. Idempotent upsert keyed by (pollId, userId). Returns 202 Accepted (tally is async-aggregated).
  • DELETE /v1/polls/{id}/votes — retract this user's vote (where allowed). Also idempotent.
  • GET /v1/polls/{id}/results — returns the (eventually consistent) live per-option tally. Cache-served, may be a few seconds stale.
  • POST /v1/polls/{id}/close — admin/scheduled; freezes status and triggers the authoritative recount from the ledger.
  • GET /v1/polls/{id}/results?final=true — returns the reconciled final result once closed.

High-Level Design

Two deliberately separated paths: a thin async write path (vote command → dedup/upsert ledger → aggregate into sharded tally) and a fat cached read path (cache → sum shards on miss). The ledger is durable truth; the tally is a fast projection of it.

ComponentResponsibility
Vote ServiceAuth, rate-limit, builds (pollId, userId) key, emits a VoteEvent; serves results from cache
Event queue (Kafka)Durable buffer partitioned by pollId; absorbs spikes and decouples vote rate from DB write rate[1]
Vote ledger (DB)Source of truth — one upsertable row per (pollId, userId); enables exact recount & audit[2]
Aggregator (Flink / stream)Applies latest-wins, computes per-option per-shard deltas over a window, flushes to the tally[1]
Tally store (sharded)N sub-counters per (pollId, optionId) — the distributed counter pattern
Results cache (Redis)Serves the hot read path; holds the summed per-option totals, TTL'd to bound staleness
Why async aggregation, not a synchronous +1: a synchronous increment couples vote throughput to the durable store's per-row lock and round-trip — exactly what dies in a spike. Writing each vote to a durable ledger and a buffered log, then aggregating into the tally, turns a flood of tiny writes into batched deltas. The DB sees a trickle, the queue eats the spike, and the live tally is a cheap projection you can always rebuild from the ledger.[1]

Deep Dives

Deep Dive 1 — Idempotent, one-per-user vote recording (latest-wins)

The rule "one vote per user" is enforced by the primary key, not by application checks. Make the ledger row's PK (pollId, userId) and every vote an upsert: the first vote inserts, a changed vote overwrites (latest-wins), and a duplicate/retry is a harmless no-op writing the same value. There is no path that produces two rows for one user, so retries, double-clicks, and at-least-once queue redeliveries all converge to one effective vote.[2]

For the strict one-shot variant ("you can't change your vote"), use insert-if-absent: a conditional write (INSERT … IF NOT EXISTS / DynamoDB condition expression) that the second attempt fails cleanly. A raw "+1 to option O" command can't do either — it has no identity to dedup on — which is why the write must carry the userId and target a state, not a delta.[1]

ApproachHowVerdict
App-level "check then insert"Read "has voted?", then writeTOCTOU race — two concurrent votes both pass the check
Upsert on (pollId, userId)PK enforces one row; write overwritesLatest-wins, idempotent — the standard pick[2]
Conditional insert-if-absentAtomic create; second write rejectedThe one-shot variant — same machine, one flag
★ Staff-level signal The senior answer is "check if they voted, then count it." The staff answer is "I won't check — I'll make the data model enforce it." Pushing uniqueness into a primary key or conditional write removes an entire class of race conditions for free, and it means an idempotent retry can't corrupt the tally. Stating the mode flag (latest-wins vs one-shot) as a one-line config rather than two systems is the judgement signal.[2]

Deep Dive 2 — Durable source of truth vs fast cached tally (accuracy vs latency)

Here is the heart of the problem: the number viewers watch and the number that decides the result are not the same number. The live tally is an eventually-consistent projection produced by the aggregation pipeline — fast, cacheable, and allowed to lag by seconds. The ledger is the authoritative source of truth: every vote, durably stored, recountable on demand.[3] Treat the live tally like a read-model in CQRS and the ledger like the event store behind it.

NumberSourceConsistencyUsed for
Live tallySharded counter, fed by aggregatorEventually consistent, seconds of lagThe bar viewers watch move
Final resultRecount over the durable ledgerStrongly consistent, exactDeclaring a winner / audit

When a poll closes, you stop accepting writes, drain the queue, and run an authoritative aggregation directly over the ledger — this is the moment accuracy beats latency. The final number may differ from the last live number by the in-flight votes; reconciling to the ledger value is correct, and because each vote is one idempotent row, the recount is deterministic and replayable. This links straight to the distributed counter: the live tally is a sharded counter, and the trick is knowing it's the approximate view, not the truth.[1]

★ Staff-level signal "Which number is allowed to be wrong?" is the question that separates levels. Staff candidates declare the live tally eventually consistent and cheap, keep an authoritative ledger for the final result, and reconcile to it at close — paying for strong consistency only at the one moment a human decides a winner. Treating the displayed count as truth, or trying to make every read strongly consistent under a spike, is the senior trap.[3]

Deep Dive 3 — Surviving spikes: queue + async aggregation

A poll tied to a live broadcast goes from a trickle to ~100K votes/sec onto one poll in seconds. If the request thread writes the durable store synchronously, the per-row lock serializes every vote and the service falls over exactly when it matters. The fix is two-fold: absorb the spike in a durable queue and spread the counter so no single key is contended.[1]

The life of one vote under load:
  • 1. Vote Service authenticates, rate-limits, and writes the ledger upsert (or emits it), then appends a VoteEvent to Kafka partitioned by pollId — returns 202 immediately.
  • 2. Kafka buffers the burst; the DB never sees 100K QPS, only the aggregator's steady drain.
  • 3. The stream aggregator applies latest-wins, batches per-option deltas across N shards, and flushes to the sharded tally every window.
  • 4. Reads hit the results cache; on miss it sums the N shards per option and re-caches with a short TTL. Millions of reads, near-zero contention.

Sharding the per-option counter (see distributed counter) gives N× write parallelism; the queue gives elasticity and replay — if the aggregator dies, you reprocess from the last committed offset and the tally rebuilds, losing nothing.[1]

★ Staff-level signal Naming "this poll is a hot key during a spike" before the interviewer, then reaching for a queue to absorb plus a sharded counter to spread — instead of a bigger database — is the move. The subtle staff point: the queue isn't just for throughput, it's for durability and replay, which is what lets you guarantee the final tally even if the live aggregator crashes mid-spike.[1]

Deep Dive 4 — Preventing fraud & bot voting; auditability

"One vote per user" is only as strong as the identity behind it. Integrity has layers, and you state the threat model explicitly: casual double-voting is stopped by the PK (DD1), but ballot-stuffing and bots need defense before the vote is even recorded.[2]

ThreatDefense
Retry / double-clickIdempotent upsert on (pollId, userId) — already free (DD1)
One user, many requestsPer-user rate limiting at the edge before the write
Bots / scripted floodsAuth required, device/IP rate limits, CAPTCHA or proof-of-work on signup
Sybil / fake accountsVerified identity (phone/email), trust scoring — the residual hard problem

The ledger doubles as the audit log: because every vote is a durable, timestamped, per-user row, you can recount, prove the result, and retroactively void votes from accounts later flagged as fraudulent — then re-aggregate. Append-only ledgers are what make a voting result defensible, not just fast. See the rate limiter for the per-identity throttle and common patterns for the CQRS read/write split underpinning the dual-number design.[1]

★ Staff-level signal Stating the threat model out loud — "what does an attacker gain, and how do they cheat?" — then layering rate limiting + auth + a recountable ledger, shows you treat integrity as a first-class requirement, not an afterthought. The depth move is recognizing the ledger is simultaneously the source of truth, the audit trail, and the remediation tool: void fraudulent rows and re-aggregate, with no guesswork.[2]

Check yourself — retrieval practice

Answer from memory before scrolling back up.

1. What is the cleanest way to enforce "one vote per user" with latest-wins semantics?

A PK of (pollId, userId) makes the write an idempotent upsert — first vote inserts, a change overwrites, retries are no-ops. No race, no double count.

2. Why keep a durable per-vote ledger separate from the fast cached live tally?

The live tally is an eventually-consistent projection; the ledger is the authoritative source you recount at close, when accuracy must beat latency.

3. How do you keep a single poll alive when votes spike to ~100K/sec in seconds?

A queue absorbs the burst (and enables replay) while sharding the counter spreads writes across N keys — neither a single row nor synchronous writes survive the spike.

4. Beyond the primary key, what stops organized ballot-stuffing and bot voting?

Idempotency stops accidental duplicates; deliberate fraud needs auth + rate limiting at the edge, and the append-only ledger lets you void flagged votes and re-aggregate.
