Databases & Indexing

How data is stored, found fast, and why "boring relational" is usually the right answer.

Why this lesson, for your mission: The data store is the heart of almost every design. At L6/L7, interviewers aren't testing whether you can name databases — they're testing whether you reach for the simplest thing that works, justify it, and can defend the indexing and data-model choices that fall out of your access patterns. This lesson gives you a default and the judgement to deviate from it.

1 of 6

SQL vs NoSQL: what they actually are

A relational (SQL) database — Postgres, MySQL — stores data as tables of rows and columns with a fixed schema, and lets you combine tables with JOINs and query them with SQL. A NoSQL database is an umbrella term for everything else: key-value stores, document stores, wide-column stores, graph databases. They typically relax the schema and the join in exchange for a simpler, more scalable storage model.

The classic framing is ACID vs BASE. ACID (Atomicity, Consistency, Isolation, Durability) is the guarantee a transactional relational DB gives you: a group of operations either all happen or none do, and the data is never left in a half-written state. BASE (Basically Available, Soft state, Eventual consistency) describes the looser contract many NoSQL systems offer: they stay available and fast, and reads may briefly see stale data that "settles" into consistency.

Why do NoSQL stores typically drop joins and fixed schema instead of just being "SQL but faster"?

Busting the "NoSQL = web scale" myth

The most common rookie mistake is "I'll use NoSQL because I need scale." Hello Interview calls this out directly: statements like "I need NoSQL because I need scale" are yellow flags that reveal inexperience, because both relational and NoSQL databases can scale effectively.[2] A single well-tuned Postgres instance comfortably handles tens of thousands of writes per second and terabytes of data, and with read replicas, partitioning, and sharding it scales far further than most candidates assume. Companies have run Postgres and MySQL at enormous scale for years. Scale alone is rarely the reason to abandon relational.

Pick relational when you have meaningful relationships between entities, need transactions/integrity (money, orders, inventory), or you don't yet know all your query patterns and want ad-hoc query flexibility.

Pick NoSQL when you have a specific reason: a single, well-understood access pattern at very high scale; massive write throughput; or a data shape (huge documents, time-series, wide rows) that maps badly onto tables. The reason should be concrete, not "scale."

What an index is, and why it speeds reads

Without an index, finding "the user with email x@y.com" forces the database to scan every row — a full table scan, linear in table size. An index is an auxiliary data structure that keeps a copy of one or more columns in a sorted/searchable form, pointing back to the full row. With it, the database jumps straight to the target in milliseconds instead of scanning everything.[1]

Indexes aren't free. Because the index is a second copy of the data that must stay in sync, every write (insert/update/delete) now also updates every index on that table. That's the fundamental trade: an index speeds reads at the cost of writes and storage. So you don't index everything — you index the fields you query frequently. The interview move is exactly that: "think about your query patterns and propose indexes on the fields you're querying frequently."[1]

Check before continuing

Why does adding an index speed reads but slow writes?

An index duplicates columns in searchable form; every insert, update, or delete must keep that copy in sync, which is extra write work.

Reread the second paragraph — what happens to "every index on that table" during a write?

Since indexes make reads faster, why not add one to every single column?

Each index is upkeep cost on every write. If nothing queries that column often, the index is pure overhead with no offsetting read win.

Think about the trade stated directly: "speeds reads at the cost of writes and storage." What happens if you pay that cost for a column nobody queries?

B-tree vs LSM-tree: two ways to build an index

There are two dominant storage engines underneath modern databases, and they sit at opposite ends of a read/write trade-off.[3]

B-tree — read-optimized (the default)

A B-tree keeps keys sorted in a balanced, fan-out tree of fixed-size pages. Lookups, inserts, and range scans are all O(log n), and writes update pages in place. This is the default index in Postgres and MySQL.[1] It excels at reads, exact lookups, and range queries (WHERE created_at BETWEEN …) because the data is already sorted. The cost: in-place updates cause random disk writes and write amplification under heavy write load.

LSM-tree + SSTables — write-optimized

A Log-Structured Merge tree takes the opposite approach: buffer writes in memory (a "memtable"), then flush them to disk as immutable sorted files called SSTables. Writes are fast sequential appends — never in-place edits — so the engine absorbs huge write volume. Background compaction merges SSTables to reclaim space and keep reads fast. This is the engine behind Cassandra and RocksDB.[3] The cost: a read may have to check the memtable plus several SSTables (mitigated by Bloom filters), and compaction consumes background I/O.

B-treeLSM-tree
Optimized forReads & range scansHigh write throughput
WritesIn-place updateSequential append + compaction
Used byPostgres, MySQL (InnoDB)Cassandra, RocksDB, ScyllaDB
Pick whenRead-heavy, mixed, defaultWrite-heavy ingest (logs, events)
One-line mental model: B-tree updates the data where it lives (great for reads); LSM-tree just keeps appending and cleans up later (great for writes). If a workload is "log everything, query later," LSM wins. For most CRUD apps, the B-tree default is right.
Check before continuing

A workload is append-heavy: ingest millions of events per second, query later. Which engine fits?

LSM-trees (Cassandra, RocksDB) buffer writes in memory and flush sequential SSTables — built for write throughput, not in-place updates.

Compaction belongs to LSM-trees, not B-trees — reread which engine does sequential appends.

Why can an LSM-tree read be slower than a B-tree read for the same lookup, despite LSM writes being faster?

Unlike a B-tree's single sorted structure, an LSM-tree spreads data across memtable plus multiple SSTables, so a read may check several places, mitigated but not eliminated by Bloom filters.

Beyond the basics: secondary, composite, geospatial

The primary index is on the primary key. A secondary index is any additional index — e.g. on email or status — so you can query rows by something other than their key. Each one you add speeds a query but slows writes, so add them deliberately.

A composite (multi-column) index, e.g. on (user_id, created_at), sorts by the first column then the second. It's perfect for "all posts by this user, newest first." The catch is the leftmost-prefix rule: that index helps queries filtering on user_id (with or without created_at), but not a query on created_at alone. Postgres lets you create arbitrarily many indexes, including multi-column and specialized ones.[2]

For location queries ("restaurants near me"), ordinary indexes fail because 2-D proximity doesn't reduce to one sorted column. Geospatial indexes solve this by mapping 2-D space onto a searchable 1-D structure — a quadtree recursively subdivides the map into quadrants, while a geohash encodes lat/long into a string prefix so nearby points share prefixes. In Postgres this comes via the PostGIS extension.[1] (You'll use this in the Yelp/Uber case studies later.)

When to reach for what

Don't memorize a decision tree — internalize the access pattern each store is built for. Hello Interview's own defaults: Postgres for transactional/relational data, DynamoDB as the favored managed NoSQL choice, and Cassandra for write-heavy workloads.[2]

StoreShapeReach for it when
PostgreSQLRelational, ACID, B-treeDefault. Transactions, joins, integrity, unknown query patterns.[2]
DynamoDBManaged key-value/docKnown access pattern, huge scale, want zero ops; tunable consistency.[2]

A key nuance on search indexes: you typically keep your source of truth in Postgres/Dynamo and stream changes into Elasticsearch via change data capture. That read path is "going to be stale by some small amount, but for search use cases that's almost always acceptable."[1]

How DB choice shows up in an interview

State your default and move on: "I'll use Postgres unless I have a specific reason not to." That single sentence signals experience and frees minutes for the parts that earn points. Then let the design pull you off the default — "this table is append-only at 200k writes/sec, so here I'd switch to Cassandra" — with a concrete reason, not a vibe.

Avoid the trap of debating SQL vs NoSQL in the abstract. Hello Interview is blunt: "Many candidates trip themselves up by trying to insert a comparison of relational and NoSQL databases into their answer." The stronger move is to "discuss the specific database you've chosen and how its features solve your particular problem."[2]

★ Staff-level signal Seniors pick a database. Staff engineers let the access pattern drive the data model, not the other way around. With DynamoDB that means designing the partition/sort key (and often a single-table design) around the exact queries you'll run; with Cassandra it means choosing a partition key that co-locates the data each query needs and avoids hot partitions. The tell: you can recite your top 3 queries before you draw a table, and your schema obviously serves them. Pair that with a "boring relational by default, justify the exception" posture and you sound like someone who has operated these systems at 3 a.m. — not just read about them.
