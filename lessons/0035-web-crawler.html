Design a Web Crawler

Start from seeds, fetch the web politely, and never crawl the same page twice — at a scale of billions.

Why this lesson, for your mission: A crawler is a pure pipeline problem with no user-facing API, so it tests whether you can reason about throughput, idempotency, and back-pressure rather than CRUD endpoints. The L6/L7 signal is whether you proactively raise the three hard parts — a politeness-aware partitioned URL frontier, dedup at the URL and content level, and a resumable distributed pipeline — before the interviewer has to ask.

Phase 1 · 0–5 minClarify the problemPin scope and the few NFRs that will drive every later decision.

Ask before you design

  • “How many pages and how fast — one 10B-page crawl in 5 days, or continuous recrawling?” — A one-shot vs continuous crawl changes frontier priority and freshness logic.
  • “Do we need to render JavaScript-heavy pages?” — Headless rendering is 10–100× more expensive per page.
  • “Who consumes the output — search index, training data, archive?” — It decides storage format (WARC, text) and dedup strictness.

1. Functional Requirements

The crawler's job is narrow but deep: given seed URLs, fetch pages, extract their links, and recursively crawl outward to cover a large fraction of the web, storing the page content for downstream consumers (a search index, an LLM training corpus, an archive).[1]

#The system should…
1Start from a given set of seed URLs and fetch each page's content.
2Parse each page to extract outbound links and enqueue newly discovered URLs.
3Store the page content (raw HTML and/or extracted text) for later processing.

Out of scope (call these out, then drop them): ranking/indexing the content, rendering JavaScript-heavy SPAs, handling logins or paywalls. We crawl and store; someone else indexes.

2. Non-Functional Requirements

PropertyTarget / priority
ScaleBillions of pages. A common framing: 10B pages × ~2MB each, crawl completed in ~5 days.[1]
PolitenessRespect robots.txt and a per-domain rate limit (e.g. ≤1 req/s/domain) so we never DoS a site.[1]
Efficiency / no wasteAvoid re-crawling the same URL and storing near-duplicate content. Dedup is a first-class requirement, not a nicety.
Fault tolerance + resumableA machine dying must not lose in-flight URLs or restart the crawl from scratch.
FreshnessRe-crawl pages over time; the web changes, so a one-shot crawl decays.

Say to move on → “Scale plus politeness plus no wasted fetches. Let me size fetch rate and storage.”

Interviewer pushback

“If one box can do ~3,750 pages/s, why is this hard?”

Staff answer: Politeness caps each domain at ~1 req/s, DNS becomes a bottleneck, and the frontier must juggle billions of URLs across millions of domains. Throughput is limited by coordination, not CPU.

Say to move on → “~23k pages/s and ~20 PB raw means distributed fetchers and object storage. Let me define the stage contracts and control API.”

4. Pipeline Stages & Control-Plane API

A crawler has two interfaces. The data plane is an internal pipeline, where the interface is the contract between stages, each of which can scale and fail independently. The control plane is a small REST API that operators and downstream teams use to start, steer and consume crawls. Data plane first. State each stage's input → output:

StageIn → OutResponsibility
URL FrontierURL → URL (dequeued when polite)Durable queue of URLs to crawl; enforces politeness + priority.
FetcherURL → raw HTML + statusDNS resolve, check robots.txt, download, write raw HTML to blob store.
Parser / ExtractorHTML → text + outbound linksExtract text for storage; extract <a href> links as candidate URLs.
Dedupcandidates → novel URLs / pagesDrop already-seen URLs and near-duplicate content.
Store + Enqueuetext → blob store; new URLs → frontierPersist content; feed novel links back into the frontier (the recursion).

Control-plane API. Nothing here is on the per-page hot path. These endpoints create and steer crawl jobs, which the pipeline then executes asynchronously. The caller's identity comes from the token; mutations are audited.

EndpointPurpose
POST /v1/crawlsCreate a crawl job. Body: { seedUrls[] | seedListUri, scope: { allowDomains[], urlPatterns[], maxDepth }, maxPages, recrawlPolicy, outputs: ["warc","text"] }. Requires Idempotency-Key; returns 202 { crawlId }, and seeds are enqueued into the frontier asynchronously.
GET /v1/crawls/{crawlId}Status: state (running/paused/done), pages fetched, pages/s, frontier size, error and duplicate rates, ETA.
POST /v1/crawls/{crawlId}/pause · /resume · /cancelStop or restart dequeuing for this crawl. The frontier stays durable, so a resumed crawl picks up exactly where it stopped.
POST /v1/crawls/{crawlId}/seedsAdd seed URLs to a running crawl. They pass through the same normalization and dedup as discovered links.
PUT /v1/domains/{domain}/policyOperator override: { crawlDelayMs, maxConcurrency, blocked, reason }, e.g. after a site owner complains. The politeness gate reads it on the next fetch.
GET /v1/urls/{urlHash}Crawl state of one URL: last crawl time, HTTP status, content hash, and WARC (file, offset, length) pointer. Used for debugging and point lookups.
GET /v1/crawls/{crawlId}/outputs?cursor=Paged manifest of finished WARC and Parquet files, so consumers (indexers, training pipelines) can ingest incrementally.

5. Data Model

Three stores with three shapes. URL state is a key-value table keyed by a hash of the normalized URL. Content is written to object storage in large WARC files (thousands of pages per object), with each URL row storing a (file, offset, length) pointer — this avoids billions of tiny S3 objects and PUT requests. The frontier is partitioned by hash(domain) so every URL of a domain lands in the same queue partition, which is what makes per-domain politeness enforceable.

6. Data Flow

Trace one URL through the loop — this is the spine of the whole design:

seed → URL Frontier (dequeue a URL whose domain is currently allowed) → Fetcher (resolve DNS, read cached robots.txt, download HTML, write raw bytes to blob storage) → Parser/Extractor (pull out text + outbound links) → Dedup (URL seen before? content a near-duplicate? if so, drop) → Store extracted text to blob storage + record URL state/content-hash in the metadata DB → Enqueue the novel outbound URLs back into the Frontier. Loop.

The loop is what makes a crawler a crawler: the output of one page becomes the input for the next. Everything hard about the system is about controlling that loop — pacing it (politeness), pruning it (dedup), and surviving crashes mid-loop (fault tolerance).

The crawl loop: dequeue politely → fetch → store raw bytes in batched WARC files → parse → dedup → record state and feed novel URLs back into the frontier. Workers are stateless; the queue, metadata DB and S3 hold all state, so any box can die.

8. High-Level Design

Map each pipeline stage to a concrete, horizontally-scalable component connected by durable queues so a slow or dead stage applies back-pressure instead of dropping work.[1]

ComponentConcrete choiceWhy
URL FrontierManaged queue(s) (e.g. SQS / Kafka), partitioned by domainDurable, supports retry + dead-letter so crashes don't lose URLs.[1]
Fetcher fleetStateless worker pool (~8+ network-optimized boxes)Scale out to hit ~23K pages/s; restart freely since state lives in the queue.
Parser fleetStateless worker poolCPU-bound HTML parsing, scales independently of fetch I/O.
Metadata DBWide-column / KV store (e.g. DynamoDB)Tracks URL state, last-crawl time per domain, content hashes.[1]
Content storeObject storage (S3 / blob)20 PB of raw HTML + text; cheap, durable, not query-shaped.[1]

The recurring move: keep the workers stateless and push all durable state into the queue, the metadata DB, and blob storage. That is what makes the fleet elastic and the whole pipeline resumable.

Interviewer pushback

“Why durable queues between every stage?”

Staff answer: A slow or crashed stage applies back-pressure instead of losing URLs, and each stage scales independently.

9. Deep Dives

Deep Dive 1 — The URL Frontier (politeness-aware queue)

The frontier is the heart of the system. Naively it's "a queue of URLs to crawl" — but a single FIFO queue is wrong for two reasons: it would let one popular domain dominate the workers, and it offers no way to crawl important pages first.

The staff answer is a partitioned frontier: many sub-queues, one per domain (or per domain-hash bucket). A fetcher only pulls from a domain whose per-domain rate-limit window has elapsed, so a single domain can never be hammered no matter how many of its URLs are pending. Layer a priority dimension on top — front-page / high-rank URLs jump ahead of deep, low-value links — typically by routing into high/low priority queues. This is exactly the message-queue back-pressure pattern from Lesson 07: the queue decouples a fast producer (parser emitting links) from a deliberately throttled consumer (the polite fetcher).

Two axes the frontier must satisfy at once:
  • Politeness axis — partition by domain so per-domain rate limits are enforceable and no host is overloaded.
  • Priority axis — order within/across partitions so valuable pages are crawled before junk and freshness re-crawls slot in.

Deep Dive 2 — Deduplication (URL and content)

Two distinct duplicates, two distinct mechanisms — conflating them is a senior-level mistake:

TypeQuestionMechanism
URL dedup"Have I already queued/crawled this URL?"A "seen" set keyed by normalized URL. At billions of URLs an exact set is too big for memory, so use a Bloom filter as a cheap probabilistic gate; on a "maybe-seen" hit, confirm against the metadata DB.[1]
Content dedup"Is this page (near-)identical to one I already stored?"Hash/fingerprint the content (e.g. SHA-256 for exact, SimHash/MinHash for near-duplicate) and compare against stored hashes before writing.[1]

Why both? Two different URLs (mirrors, tracking params, ?utm= variants) routinely serve identical content — URL dedup won't catch those, content fingerprinting will. The Bloom filter's tunable false-positive rate is the classic space/accuracy tradeoff: a false positive means we skip a novel URL, so we size the filter to keep that rare and back it with the authoritative DB check.

Deep Dive 3 — Politeness (robots.txt + per-domain pacing)

Politeness is both an ethical and a survival requirement — crawl too aggressively and sites block your IP range. Three layers:

LayerHow
robots.txtFetch and cache per domain; honor its Disallow rules and Crawl-delay.[1]
Per-domain delayEnforce a minimum gap (e.g. 1 req/s/domain) via a Redis-backed last-crawl timestamp/lock; defer a URL if its window hasn't elapsed.[1]
Domain partitioningRoute all of a domain's URLs through one queue/worker so the rate limit is trivially enforced and no host is hit in parallel.

Add jitter to retry timing so transient failures don't produce a synchronized retry storm against the same host.[1] Note the tension with throughput: politeness caps per-domain rate, so total throughput comes from crawling many domains in parallel — which is precisely why the frontier partitions by domain.

Deep Dive 4 — Scale & fault tolerance

Three things bite at scale:

  • DNS is the hidden bottleneck. Classic measurements found DNS lookups consuming up to ~70% of a crawl thread's time.[1] Mitigate with an aggressive DNS cache and round-robining across multiple resolvers.[1]
  • Crawler traps & cycles. Calendars and infinite parameterized URLs generate unbounded links. Cap crawl depth (~15–20 hops from seed) and rely on URL dedup to break cycles.[1]
  • Resumability. A fetcher crash mustn't lose work. Because workers are stateless and a URL stays in the queue (invisible during a visibility timeout) until processing is confirmed, a dead worker's URLs simply reappear; after N failed retries they go to a dead-letter queue for inspection rather than spinning forever.[1]

Content lives in object storage, the frontier and pipeline in durable queues, and crawl state in the metadata DB — so the entire system can be killed and restarted and pick up exactly where it left off. That "kill any box, lose nothing" property is the resumable-distributed-pipeline signal.

★ Staff-level signal Three things separate a staff answer from a senior one here. (1) You design the frontier as a politeness-aware partitioned queue with separate politeness and priority axes — not "a queue of URLs." (2) You split dedup into Bloom-filter URL dedup and content fingerprinting, and you can articulate the false-positive tradeoff. (3) You frame the whole thing as a resumable distributed pipeline — stateless workers, durable queues, visibility timeouts, dead-letter queues — and you flag DNS and crawler traps before being asked. Naming the bottleneck (DNS, not CPU) unprompted is a strong tell.

Interviewer pushback

“How do you enforce one request per second per domain across hundreds of fetchers?”

Staff answer: Partition the frontier by hash(domain) so each domain's URLs sit in one queue partition. A per-domain next-fetch time gates dequeues, so politeness is enforced by the queue, not by coordination.

15. Privacy

Public pages still contain personal data (names, emails, phone numbers, photos). Respect signals: robots.txt, noindex/noarchive, and opt-out lists. Scope: never crawl authenticated areas or follow session/token URLs (strip tracking and session parameters during normalization). Removal: support takedown and right-to-be-forgotten requests by URL/domain — delete from url_state, mark WARC records as tombstoned, and exclude from downstream datasets on the next build. Downstream use: PII scrubbing in the text-extraction stage when data feeds ML training. Retention: old crawl generations expire on a schedule.

Interviewer pushback

“How do you avoid crawler traps and malicious pages?”

Staff answer: Max depth and URL length limits, URL normalization, per-domain page budgets, content-similarity dedup, and sandboxed parsing with size and time limits.

First bottleneck: DNS resolution and per-domain politeness — at 10× many popular domains can't go faster, so the crawl budget must shift to more domains and smarter priority. What forces a redesign: rendering JavaScript at scale (headless browsers are ~100× more expensive per page).

17. Cost of Running

Assumptions: one 10B-page crawl in 5 days, HTML compressed ~5× into WARC files (~4 PB), fetchers with public IPs (no NAT gateway), list prices from the course price sheet. Shown as cost per crawl plus one month of storage.

Line itemSizing~$ per crawl
S3 storage (first month)~4 PB compressed WARC + text$92,000
Metadata DB~10B writes + ~50B dedup reads + 2 TB$25,000
Fetcher fleet + DNS resolvers~20 network-optimized boxes × 5 days$6,000

Unit cost: ≈ $13 per million pages crawled and stored. Dominant driver: storage, then metadata writes. Two expensive traps avoided by design: one S3 object per page would add ~$100k in PUT requests per crawl (batching into WARC files removes it), and routing 20 PB of downloads through a NAT gateway would add ~$900k in data-processing charges. Levers: compress aggressively, keep only text for low-value pages, and skip refetching unchanged pages via conditional GETs (ETag/Last-Modified).

18 · Closing Summary (60 seconds)

A web crawler is a politeness-aware pipeline. A durable URL frontier partitioned by domain feeds fetchers that check robots.txt, pace each domain, download pages and write them to large compressed WARC files on S3. Parsers extract text and links; a Bloom filter plus a URL-state table and SimHash deduplicate URLs and near-duplicate pages before new links return to the frontier. Every stage is queue-connected, so failures cause retries, not loss. A small control-plane API starts, steers and exposes crawls. At 10× we add fetchers and DNS resolvers.

Check yourself — retrieval practice

Answer from memory before scrolling back up.

1. Why partition the URL frontier by domain rather than using one global FIFO queue?

Per-domain partitions are how politeness (≤1 req/s/domain) is enforced; throughput then comes from many domains in parallel.

2. Two different URLs return byte-identical content. Which mechanism prevents storing it twice?

URL dedup can't catch mirrors or tracking-param variants; only hashing the content body detects identical/near-identical pages.

3. At billions of pages, what is the surprising dominant cost per crawl thread to mitigate?

Classic crawler studies found DNS lookups consuming up to ~70% of a thread's elapsed time; cache aggressively and spread across resolvers.

4. What property makes the pipeline resumable after any single worker crashes mid-fetch?

Visibility timeouts hold the URL invisible-but-undeleted; a dead worker's URLs reappear, and after N retries move to a dead-letter queue.
