Design Facebook Live Comments

Broadcasting a river of comments to millions of concurrent viewers, in under 200ms, when one stream can dwarf the rest of the platform combined.

Why this lesson, for your mission: This is the canonical real-time fan-out problem. The breadth is small — post a comment, read recent comments, see new ones live. The whole interview lives in one deep dive: how does a comment reach millions of open connections in 200ms? An L6/L7 candidate picks the right transport, names the pub/sub channel as the fan-out primitive, and proactively breaks the design on the hottest stream before the interviewer does.[1]

Phase 1 · 0–5 minClarify the problemPin scope and the few NFRs that will drive every later decision.

Ask before you design

  • “How big is the largest single stream?” — A 10M-viewer stream breaks designs that work for the long tail.
  • “Must every viewer see every comment?” — If sampling is allowed on huge streams, fan-out becomes tractable.
  • “What latency counts as live?” — Under 200 ms needs push; 1–2 s allows CDN snapshots.

Non-Functional Requirements

This system is defined by its NFRs more than its features. State the target, not just the "-ility."

The key tension: reads vastly outnumber writes, and the read/write skew is extreme — a hot stream might take hundreds of comments/sec but must deliver each one to millions. The architecture optimizes the read fan-out, not the write. That asymmetry is what makes SSE the right transport (see Deep Dive 1).

2 of 7 — Estimate what matters

Phase 2 · 5–10 minEstimate what mattersOnly the numbers that change a decision — say the implication out loud.

Capacity Estimation

Only compute numbers that change a decision. Two matter here: the fan-out factor and the per-stream connection count.

  • Fan-out factor: a hot stream at 1,000 comments/sec delivered to 10M concurrent viewers = 10 billion message-deliveries/sec for one video. The write QPS is trivial; the delivery QPS is the entire problem.
  • Connections per server: a single box holds maybe ~50–100K open SSE connections (memory + file descriptors). 10M viewers on one stream ⇒ ~100–200 connection servers must each carry a copy of that stream — for one video.
  • Tail history: "recent comments" = last ~50–200 comments per video. At ~200 bytes each that's ~40KB/video — small enough to cache the entire tail in memory (Redis), per video.
  • Comment storage: writes are cheap (thousands/sec aggregate is easy for DynamoDB-style storage); durability and the read tail dominate, not raw write throughput.
Design implication: you never scale the database for the broadcast — you scale a layer of connection servers fronted by a pub/sub backplane, and you cache the tail.

Interviewer pushback

“If writes are only thousands per second, why is this hard?”

Staff answer: Because each comment fans out to millions of viewers. The delivery count, not the write rate, sizes the system.

Say to move on → “Delivery, not writes, is the problem: up to 10B deliveries/s on one hot stream. Let me define the API.”

Check yourself

A hot stream does 1,000 comments/sec to 10M viewers. What is the number that actually sizes the system?

Deliveries = comments/sec × viewers = 10B/sec. That delivery count is what drives every scaling decision, not the write rate.

Multiply comments/sec by concurrent viewers, not just look at either number alone.

Why does the design implication say "you never scale the database for the broadcast"?

The DB only sees the write rate (thousands/sec), which never explodes with viewer count. The thing that explodes — delivery — lives in the connection-server and pub/sub layer, so that's what you scale.

Does the database ever see 10 billion operations/sec, or only the connection layer does?

API

Derive userId from the auth token, never the body. Use cursor pagination for history — offset pagination forces the DB to count preceding rows and breaks when comments are inserted under you.[1]

  • POST /v1/videos/{id}/comments — body { text }; user from JWT. Returns the created comment.
  • GET /v1/videos/{id}/comments?cursor={lastCommentId}&pageSize=50&sort=desc — the recent-comments tail when you join.
  • GET /v1/videos/{id}/comments/stream — SSE subscription. Long-lived HTTP response; server pushes each new comment as an event. Carries Last-Event-ID for reconnect replay.

Data Model

Every read and write is scoped to one live video, so live_video_id is the partition key everywhere — the DB, the Redis tail, the pub/sub channel and the load-balancer hash. Comment ids are time-sortable (Snowflake) so the sort key doubles as the pagination cursor and the SSE Last-Event-ID.

What is chosen as the partition key across the DB, the Redis tail, and the pub/sub channel?

Every access pattern (post, tail, subscribe) is scoped to one video, so live_video_id is used consistently everywhere to keep routing simple and colocated.

Why does offset pagination break for comment history but cursor pagination doesn't?

Offset N means "skip N rows," but if rows are inserted above your window, "row N" now refers to something different — you skip or repeat comments. A cursor keyed on a stable, sortable id doesn't shift.

Picture new comments arriving while you page through page 2 with an offset — what happens to "row 50"?

High-Level Design

Two paths, deliberately separated: a thin write path (POST → store → publish) and a fat read/broadcast path (a fleet of connection servers fed by a pub/sub backplane).

ComponentResponsibility
API gateway / LBRoutes POSTs to the comment service; routes SSE subscriptions to connection servers (Layer-7, consistent-hash on liveVideoId)
Comment ServiceValidates & persists the comment, then publishes it to that video's channel
Comments DBDurable store, partitioned by liveVideoId (e.g. DynamoDB — scalable, highly available, no joins)[1]
Pub/Sub backplaneOne logical channel per video (Redis Pub/Sub or Kafka topic/partition). The fan-out primitive.

Tail cachePer-video ring buffer of recent comments (Redis), serves the "join mid-stream" read without hitting the DB
The happy path of one comment:
  • 1. Viewer POSTs → Comment Service writes to DB and to the tail cache.
  • 2. Comment Service publishes the comment to channel video:{id}.
  • 3. Every connection server subscribed to video:{id} receives it once.
  • 4. Each server pushes it as an SSE event to its locally-held connections for that video. Done — one publish, millions of deliveries.

Interviewer pushback

“Why not one global pub/sub channel?”

Staff answer: Every connection server would receive every comment for every video. Use one channel per video and subscribe servers only to channels their viewers watch.

Say to move on → “Deep dives: transport, the pub/sub backplane, write bursts and the very hot stream.”

Check yourself

In the happy path, what happens right after the Comment Service persists a new comment?

Store then publish: the write path persists first, then hands off to the pub/sub channel, which is the actual fan-out primitive.

Reread the numbered happy-path list — what is step 2?

Why would one single global pub/sub channel for all videos be worse than one channel per video?

With one channel, subscribing means subscribing to everything — a server serving one small video would still process traffic from every mega-stream on the platform.

If there's only one channel, can a server subscribe to just the videos its viewers are watching?

5 of 7 — Deep dives & tradeoffs

Phase 5 · 27–47 minDeep dives & tradeoffsGo deep where the system breaks; compare alternatives and justify the pick.

Deep Dives

Deep Dive 1 — The transport: SSE vs WebSocket vs polling

Polling is the trap. To feel real-time you'd poll every ~200ms; with millions of viewers that's a tidal wave of requests hammering the DB, mostly returning nothing new. Reject it early — the senior signal is realizing this without prompting.[1]

So you need a push model with a persistent connection. The choice is WebSocket vs SSE.

DimensionWebSocketSSE (Server-Sent Events)
DirectionFull duplex (both ways)One-way: server → client
ProtocolCustom upgrade over TCPPlain HTTP; works with existing infra
ReconnectManual / app-builtBuilt in, with Last-Event-ID replay
Fit for this skewOverkill — bidirectional channel for a read-mostly feedIdeal — broadcast is one-way
★ Staff-level signal Pick SSE and justify it by the read/write skew. Comments are written rarely (a plain POST) but read constantly. A WebSocket pays for a duplex channel you barely use; SSE gives one-way streaming over vanilla HTTP plus free reconnect-with-replay. Then pre-empt the gotchas yourself: some proxies/load balancers don't stream responses, and browsers cap concurrent SSE connections per domain.[1] Naming the downside before the interviewer does is the move.

Deep Dive 2 — Scaling connections: the pub/sub backplane

Once you horizontally scale connection servers, viewers of the same video land on different servers. So how does a comment that arrives at the Comment Service reach the server holding viewer #7,000,000? This is the core question, and pub/sub is the answer — but the naive version doesn't scale.[1]

ApproachIdeaProblem
Naive pub/subOne global channel; every server subscribes to everythingEvery server processes every comment for every video — wasteful
Channel-per-video + co-locationChannel video:{id}; L7 LB consistent-hashes on liveVideoId so same-video viewers cluster on the same servers; each server subscribes only to channels it actually servesHot stream still overflows one server (Deep Dive 4)
Dispatcher serviceInvert it: a dispatcher tracks which servers serve which video and routes each comment directlyKeeping the mapping accurate under churn is hard
The pick: a channel per video over a pub/sub backplane (Redis Pub/Sub for low latency, or Kafka if you want durability/replay), with the L7 load balancer co-locating same-video viewers via consistent hashing.[1] One publish reaches every subscribed server exactly once; each server fans out locally to its own connections. The channel is the fan-out primitive — internalize that phrase.
★ Staff-level signal The leap from "use pub/sub" to "one channel per video, and route viewers so a server only subscribes to channels it serves" is the senior→staff jump. Anyone can say "Redis Pub/Sub." Staff explains why a single global channel melts down (N servers × all-videos of work) and how consistent-hash routing turns fan-out into a bounded, shardable problem.

Deep Dive 3 — Write burst & loading recent comments

Two smaller-but-real problems on the read path.

Burst absorption: a hot stream spikes to thousands of comments/sec. The DB write is fine, but you don't want every read to hit it. Keep a per-video ring buffer of the last ~50–200 comments in Redis — that's the "tail." Writes update the tail and the DB; the publish carries the comment to live viewers.

Joining mid-stream: when a viewer opens the stream you serve them the tail from cache (one fast Redis read), then attach their SSE connection so new comments flow in. They never see a gap and the DB is barely touched. For deep scrollback, fall to cursor pagination against the DB.

Reconnection (don't skip this): SSE auto-reconnects and sends Last-Event-ID; the server replays comments since that id.[1] Bound the replay to ~5 minutes — if someone was gone an hour, replaying thousands of stale comments would drown them. For longer gaps, treat it as a fresh join (serve the tail, move on).

Deep Dive 4 — The very-hot stream (the part that breaks everything)

Now the headline case: hundreds of millions of viewers, thousands of comments/sec, on one video. Sub-200ms per-comment fan-out to that many connections is impractical — no realistic number of connection servers and pub/sub throughput delivers 10B+ messages/sec cheaply. You change the contract.[1]

TechniqueHowTrade-off
SamplingDon't broadcast every comment — show a curated subset, prioritizing comments from people you follow, ones getting reactions, or verified accountsViewers see a representative feed, not all comments (which is fine — nobody reads 1,000/sec anyway)
Hierarchical fan-outTree of relays: origin → regional relays → connection servers, so no single layer does the full fan-outMore moving parts and a few extra ms of latency
CDN tail snapshotMaintain a ring buffer of ~100–200 recent comments; every ~1s snapshot it to Redis/CDN origin; clients poll the CDN once/sec1–2s latency instead of 200ms — but scales to ~unlimited viewers, and the client optimistically shows the user's own comment instantly
★ Staff-level signal The elegant answer is to relax the NFR you can afford to relax. On a mega-stream, trading 200ms for ~1–2s and pushing delivery onto the CDN converts an impossible per-connection push into a trivially-cached static object that scales to hundreds of millions for almost nothing.[1] Pair it with sampling so the feed stays readable, and show the user's own comment optimistically so they still feel instant. Recognizing that the hottest stream needs a different delivery model than the long tail of normal streams — and reaching for it unprompted — is exactly the L6/L7 signal.

“SSE or WebSockets?”

Staff answer: SSE. Writes are occasional POSTs and reads are one-way streams; SSE is plain HTTP, proxy-friendly, and has built-in reconnect with Last-Event-ID. WebSockets pay for duplex we don't use.

Check yourself

What is the core reason SSE beats WebSocket for this system?

Comments are written rarely and read constantly; SSE gives one-way push over plain HTTP with free reconnect, matching that skew exactly.

Reread the "Fit for this skew" row of the transport table.

Why does the CDN tail snapshot trick let a mega-stream scale to hundreds of millions of viewers?

A per-connection push must do work proportional to viewer count. A cached static object is fetched by however many clients want it at no extra origin cost — that's what breaks the scaling wall.

Compare the cost of pushing to N connections versus N clients reading one cached object.

Why is the dispatcher-service alternative (Deep Dive 2 table) rejected in favor of channel-per-video?

The dispatcher must track live server-to-video assignments under constant churn — that bookkeeping problem is harder to keep correct than just letting pub/sub subscriptions handle routing.

Privacy

PII: commenter name/avatar and comment text, public to everyone watching that stream; viewing activity (who watched what) is private. Audience: comment visibility follows the video's audience — a friends-only stream's comments must never land in a public CDN snapshot. Deletion: a deleted comment is removed from DynamoDB and the tail, and a delete event is published so connected clients remove it; account deletion uses the user GSI. Retention: comments kept with the video replay; deleted with it. Minimization: connection logs keep video id and a hashed viewer id, rotated quickly.

Why must friends-only stream comments never land in a public CDN snapshot?

Wrap-up · 58–60 minClose strongRecap decisions and tradeoffs in 60 seconds; name what you would do next.

Closing Summary (60 seconds)

Live comments are a fan-out problem with extreme skew. The write path is a thin POST that stores the comment and publishes it to a per-video pub/sub channel. Viewers hold SSE connections to servers routed by video id, and each server subscribes only to channels its viewers watch. Recent comments load from a capped per-video list. For mega-streams we relax the latency NFR: sample comments and serve CDN-cached snapshots every ~1–2 s. At 10× we add connection servers and pub/sub shards; egress is the main cost.
