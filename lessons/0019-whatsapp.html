Design WhatsApp

A real-time messenger is a routing problem dressed as a storage problem — the hard part is millions of stateful sockets, not the messages themselves.

Why this lesson, for your mission: WhatsApp is the canonical "real-time delivery" interview. At L6/L7 the bar is not "draw a chat server" — it is to separate the stateful connection layer from the durable message store, route through a connection registry, and guarantee delivery to offline users via per-user inboxes with ACKs. Get those three right and the rest is detail.

Functional Requirements

Scope tightly. State three core capabilities and explicitly defer the rest (calls, status/stories, payments).

#Users should be able to…
1Send and receive 1:1 messages in real time, with delivery and read receipts.
2Participate in group chats (the source models 2–100 participants [1]).
3Receive messages sent while offline once they reconnect — no message is lost [1].

Out of scope (say so out loud): voice/video calls, media is mentioned but the deep dive is text, end-to-end encryption is acknowledged but not designed.

Non-Functional Requirements

The "-ilities" drive every design decision below. Lead with latency and deliverability.

Capacity Estimation

Estimate only what changes the design. For messaging, the load-bearing number is concurrent connections, not total storage.

  • Concurrent connections (the big one): ~200M concurrent users out of ~1B total [1]. WhatsApp historically packed 1–2M connections per host [1], so even at that density you need ~100–200 connection servers just to hold the sockets — and a way to find which one holds a given user.
  • Messages: ~4B messages/day ≈ 40K msg/s average [1]. Peak is several × higher.
  • Fan-out write amplification: a 100-person group message becomes 100 inbox writes. The source budgets ~100K writes/s once group fan-out is included [1].
  • Heartbeats: with 200M sockets and a ping every 10–30s, that's ~20M ping/pong exchanges/s [1] — itself a non-trivial load the connection layer must absorb.

Implication: message payloads are tiny and storage is bounded by a 30-day TTL; the design's whole difficulty lives in the connection and routing tiers.

Core Entities & API

Entities: User, Client (a device — a user has several), Chat, ChatParticipant, Message, and Inbox (per-client queue of undelivered messages) [1].

Messaging is bidirectional and latency-sensitive, so the hot path is a persistent WebSocket, not REST. REST is reserved for things that are fine to pull on demand (history, chat management).

WebSocket (the real-time path)

DirectionFrameMeaning
C → SsendMessage { chatId, clientMsgId, body }Send; clientMsgId is the idempotency key.
C → ScreateChat, modifyChatParticipantsGroup setup / add-remove members [1].
S → CnewMessage { messageId, chatId, body }Server pushes a message to the recipient.
C → Sack { messageId, state: RECEIVED|READ }Confirms receipt; releases the inbox entry [1].

REST (the cold path)

GET /v1/chats/{chatId}/messages?before={cursor}&limit=50 — paginated history. POST /v1/chats, POST /v1/media (returns a pre-signed blob URL so attachments never traverse the chat server [1]). The user is always derived from the auth token, never passed in the body.

High-Level Design

The defining move is separating two tiers that beginners conflate: the stateful connection layer (who is online, on which socket) and the stateless message store (the durable record).

ComponentRoleState
L4 Load BalancerDistributes WebSocket connections; L4 chosen over L7 for long-lived socket efficiency [1].Stateless
Chat / Connection serversHold the persistent WebSockets; keep an in-memory map of which local users are connected [1].Stateful

Pub/sub backplaneCarries a message from the sender's server to the recipient's server.Transient

Send-message flow: client → WebSocket → its chat server persists the message + writes an inbox entry per recipient client → looks the recipient up in the connection registry → routes via pub/sub to the recipient's chat server → that server pushes newMessage over the recipient's socket → recipient replies ack, which deletes the inbox entry. If the recipient is offline, the message simply waits in the inbox until reconnect.

Deep Dives

1. Real-time delivery: persistent sockets + a connection registry

Polling for new messages every few seconds is the senior-level wrong answer — it adds latency and crushes the server with empty checks. The right primitive (recap Lesson 02 on the network and Lesson 10 on long-lived connections) is a WebSocket over TLS: one bidirectional connection per device, held open, so the server can push the instant a message arrives [1].

That creates a new problem. Alice's socket lives on chat server A; Bob's on chat server B. When A receives Alice's message for Bob, A has no idea where Bob is. You need a connection registry: a lookup of userId → which server holds the socket. A writes the message to the store, queries the registry, finds Bob is on B, and forwards the message to B over the backplane; B does the local push. This connection-registry routing is the load-bearing idea, and naming it explicitly is the difference between a senior and a staff answer.

★ Staff-level signal The single most important sentence you can say: "Connection state and message state are different systems with different properties." Connection state (who's online, on which socket) is volatile, rebuildable, and lives in memory + a registry. Message state is durable and lives in a replicated store. Conflating them — e.g. treating "delivered" as "online" — is the classic senior mistake. Separating them is what lets a chat server die without losing a single message: clients reconnect, re-register, and re-sync their inbox.

2. Offline delivery: the durable per-user (per-client) inbox

The reliability NFR says no message is lost even if the recipient is offline. A push-only design can't satisfy that — if Bob's offline, the push evaporates. The fix is a durable Inbox: when a message is accepted, the server writes one inbox entry per recipient client [1].

  • Delivery: push from the inbox; the entry stays until the client returns an ack (RECEIVED), then it is deleted. ACK-then-delete is what makes delivery at-least-once and guaranteed.
  • Reconnect: on reconnect the client syncs its inbox and drains everything queued while it was gone [1].
  • TTL: entries auto-expire after 30 days so the inbox never grows unbounded — this keeps server-side storage minimal, a stated NFR [1].
  • Multi-device: the inbox is keyed per client, not per user. A user with 3 devices [1] gets fan-out to all active sockets and an independent ACK per device, so each device converges independently.

3. Group message fan-out

A 1:1 message produces one inbox write; a group message produces one per member. With groups up to 100 [1], this is the write-amplification that pushes you from ~40K to ~100K writes/s [1]. The chat server looks up ChatParticipant (partitioned by chatId, with a GSI on participantId for the reverse lookup) [1], then writes an inbox entry for each participant's clients and routes a push to whichever are online. Because groups are bounded at 100, write-time fan-out is fine — you do not need the read-time fan-in you'd use for a celebrity-scale feed (contrast with the news-feed problem). Calling out that the bounded group size justifies fan-on-write is exactly the judgement an interviewer wants.

4. Ordering, receipts, and idempotency

ConcernMechanism
Ordering within a chatThe receiving server stamps each message with a server timestamp on receipt and clients display by server time, not send time; NTP keeps server clocks aligned [1]. A monotonic per-chat sequence is the stronger variant when clock skew matters.
Delivery / read receiptsThe ack frame carries a state (RECEIVED → one tick, READ → blue ticks). The ACK both updates the sender's UI and releases the inbox entry — the same signal does double duty.
Idempotency / dedupThe client attaches a clientMsgId; a retried send (after a flaky network) is deduped on that key so it isn't stored or delivered twice. At-least-once delivery requires the receiver to dedupe on messageId too.

5. Managing millions of stateful connections

This is the scale deep dive, and the interviewer is watching you reject the naive options before landing on a good one.

ApproachVerdict
Naive horizontal scaling, no routingBad — a server can't reach a recipient on another box [1].
A Kafka topic per userBad — ~50KB overhead × 1B users ≈ 50TB+ just for empty topics [1].
Consistent hashing user → server, coordinated by ZooKeeper/etcdGood — deterministic routing; minimal reshuffle when a server joins/leaves [1].
Redis Pub/Sub sharded by userIdGreat — lightweight in-memory channels; servers subscribe to the recipients they hold, messages flow over the backplane with at-most-once semantics (durability comes from the inbox, not the bus) [1].

Failure handling: application-level heartbeats — ping every 10–30s, pong required within ~5s; a missed pong tears down the socket and the client reconnects and re-syncs its inbox [1]. LastSeen is written only on disconnect (not per heartbeat) to keep write load down, and "online?" is answered by querying the target's chat server, not the database [1].

★ Staff-level signal Notice the layering of durability: the pub/sub bus is allowed to be lossy (at-most-once) because the inbox is the source of truth. If a push is dropped, the inbox entry simply isn't ACKed, so it's redelivered on the next sync. Designing a fast, lossy transport on top of a slow, durable store — and being explicit about which layer owns each guarantee — is the staff move. A senior often over-engineers the bus to be exactly-once; a staff engineer puts the guarantee where it's cheap (the inbox) and keeps the hot path light.

Check yourself — retrieval practice

Answer from memory before scrolling back up.

1. Why does WhatsApp need a connection registry on top of WebSockets?

Sender and recipient sockets live on different servers; the registry maps userId → server for routing.

2. How does the design guarantee delivery to a user who was offline?

The inbox persists the message; the ACK releases it. Offline clients drain the inbox on reconnect.

3. Why is a Kafka topic per user the wrong scaling choice here?

~50KB × 1B users ≈ 50TB+ just for mostly-empty topics. Sharded Redis Pub/Sub is far lighter.

4. Why is it acceptable for the pub/sub backplane to be at-most-once (lossy)?

Durability lives in the inbox; a dropped push just stays unACKed and is resent on the next sync.
