Design a Machine Learning Platform

The internal product that turns "a team has a model" into "the model is trained, deployed, served, and watched." You're not designing a model — you're designing the factory that produces and runs hundreds of them.

Why this lesson, for your mission: This is the case study that separates the candidate who builds one ML system from the one who builds the platform a hundred teams build on. At L6/L7 the signal is abstraction and leverage: you provide paved-road components — a feature store, a training orchestrator over a shared GPU cluster, a model registry, a serving tier, and drift monitoring — so individual teams don't each reinvent them. The load-bearing insight is the two-clock split: an offline/batch world (ingest → features → train) and an online world (low-latency serving), connected by exactly two artifacts — versioned features and versioned models. Get those two contracts right and train/serve skew, reproducibility, and safe rollout all fall into place.

1. Functional Requirements

The "users" here are internal ML teams, not end customers. The product is a self-service platform that covers the full lifecycle. Keep the scope to the platform plumbing; the actual modeling math is the tenant's job, not ours.[1]

#Teams should be able to…Note
1Ingest data into the platformBatch + streaming sources land in a lake/warehouse as raw material
2Define & compute featuresAuthor transforms once; reuse across models; served online + offline
3Train & track experimentsSubmit training jobs to a shared cluster; log params/metrics/artifacts
4Deploy a modelPromote a registered model version to a serving endpoint
5Serve predictionsOnline (low-latency request/response) and batch (bulk scoring)
6Monitor models in productionLatency, errors, and data/model drift with alerts

The through-line: a model is born from data and features, trained on a cluster, registered as a versioned artifact, deployed to an endpoint, and watched. The platform owns every arrow between those nouns.

2. Non-Functional Requirements

State the target, not just the "-ility." Four NFRs shape this platform, and they pull in different directions for the offline and online halves.[1]

NFRTargetDrives
Scalability100s of teams, 1000s of models, elastic GPU/CPUMulti-tenant cluster + shared services; quota & isolation
ReproducibilityAny model re-trainable byte-for-byte from logged inputsVersion data, features, code, params, and artifacts together
Low-latency servingOnline p99 <~50–100ms; batch throughput over latencyOnline feature store; autoscaling; model-as-a-service tier
ReliabilityServing 99.9%+; failed train jobs retried, never silentSafe rollout (canary/A-B), rollback via registry, health checks

The headline tension is reproducibility (offline) vs low-latency (online): the offline world optimizes for correctness, lineage, and "compute it exactly the same next year"; the online world optimizes for milliseconds. The feature store is the seam where these two value systems must agree — which is exactly why train/serve skew is the platform's central hazard.

3. Capacity Estimation

Only the numbers that change the design. ML platform scale is about concurrency on shared resources and feature read latency, not raw QPS, so estimate those.

QuantityEstimateDesign implication
Concurrent training jobs~1000s queued, 100s running, each needing 1–8 GPUsCan't give every team a static cluster → shared pool + scheduler with quotas (see Lesson 34).
Online prediction QPSTop models at 10k–100k req/s each, burstyPer-model autoscaling; one giant shared server would couple noisy neighbors.
Feature reads per request1 prediction → 10s–100s of feature lookupsOnline store needs single-digit-ms batched reads, not per-feature round-trips.
Feature/data volumePBs in the offline lake; GBs–TBs hot in the online storeTwo stores: cheap columnar offline, fast KV online — same values, kept in sync.
The number that forces the architecture. Hundreds of teams times thousands of models means you cannot let each team self-host its own GPUs, feature pipeline, and serving stack — utilization would be terrible and skew bugs would be everywhere. The economics of a shared GPU pool (high utilization via a scheduler) plus shared feature and registry services (consistency by construction) are what justify a platform at all. Multi-tenancy on shared, scarce resources is the constraint that creates the platform.[2]

4. Core Entities & API

Four entities. Feature and Model are the two versioned contracts the whole platform turns on; Dataset and Endpoint bracket them.[3]

EntityKey fields
Datasetid, source, schema, version, location (lake path), lineage
Feature (set)name, entity (user/item), transform def, version, offline+online refs
Model (version)id, version, training run id, metrics, artifact uri, stage (staging/prod)
Endpoint / Deploymentid, modelVersion, traffic split, replicas, autoscale policy, status

The API is the self-service surface. The team/owner is always derived from the auth token; artifacts are immutable and addressed by version.

EndpointPurpose
POST /v1/featuresRegister/version a feature definition (transform + entity + freshness)
POST /v1/training-jobsSubmit a training run (code ref, dataset, resources) to the cluster
POST /v1/models/{id}/versionsRegister a trained artifact + metrics into the model registry
POST /v1/deploymentsDeploy a model version to an endpoint with a traffic split
POST /v1/predict/{endpoint}Online inference: features fetched + scored, returns prediction
POST /v1/batch-predictionsBulk score a dataset offline; write results back to the lake

Critical move: POST /v1/training-jobs is async — it enqueues onto the cluster scheduler and returns a job id, never blocking on a multi-hour GPU run. Promotion to production is a registry state change (stage: prod), not a redeploy, so rollback is instant.

5. Data Flow — raw data to watched prediction

This is a pipeline platform, so trace the lifecycle once before drawing boxes. Two clocks again: a slow offline clock (hours) that builds features and models, and a fast online clock (milliseconds) that serves them.[3]

  1. Ingest: batch + streaming sources land in the data lake/warehouse as raw, versioned datasets.[1]
  2. Features (offline): transforms turn raw data into features, written to the offline store (for training) and materialized to the online store (for serving) — same definition, two destinations.[3]
  3. Train (offline, on cluster): the scheduler places jobs on GPUs; runs log params/metrics/artifacts to experiment tracking.[2]
  4. Register: the winning artifact + its metrics + lineage go into the model registry as an immutable version.[4]
  5. Deploy & serve: a registry version is promoted to an endpoint; online requests fetch features from the online store and return predictions; batch jobs score in bulk.
  6. Monitor & loop: serving logs feature values and predictions; drift detectors compare live distributions to training and trigger retraining. The monitoring loop is what keeps the platform honest.[5]

6. High-Level Design

Map each requirement to a component, then follow one request through. The offline/online split is the spine; the registry and feature store are the bridges across it.

ComponentRole
Ingestion + Data LakeBatch/stream connectors; PB-scale columnar storage of versioned datasets.[1]
Feature Store (offline + online)One transform → offline store (training) + low-latency online store (serving). Single source of truth.[3]
Training Orchestrator + ClusterQueues jobs, schedules onto shared GPUs with quotas/priorities (see Lesson 34).[2]
Experiment TrackingLogs params, metrics, datasets, and artifacts per run for comparison + reproducibility.[2]
Model RegistryImmutable, versioned artifacts with stages (staging/prod) and lineage; the deploy/rollback control plane.[4]
Serving TierPer-model autoscaled endpoints (online) + batch scoring jobs; handles traffic splits.[4]
Monitoring + DriftTracks ops metrics + data/model drift; alerts and triggers retraining.[5]

Online predict path: POST /v1/predict/{endpoint} → serving tier resolves the prod model version from the registry → fetches that model's features for the entity from the online store in one batched read → runs inference on an autoscaled replica → returns the prediction and logs features+output for monitoring. The expensive work — computing features, training the model, materializing the online store — all happened offline, hours earlier. The online path is a lookup plus a forward pass inside a tight latency budget.

7. Deep Dives

This is 60% of the interview. Four hard parts, each with the alternative and a justified pick. Keep ML at "interview depth" — name the technique and explain why the platform is shaped that way; don't derive losses or gradients.

Deep Dive 1 — The feature store: offline training vs online serving, and train/serve skew

A model is trained on features computed in a batch pipeline, but it must serve on features computed in a live request path. If those two computations differ — even slightly — predictions silently degrade. This is training/serving skew, the single most common production-ML bug, and the platform's job is to make it impossible by construction.[3]

AspectOffline storeOnline store
ConsumerTraining + batch scoringOnline inference
Access patternLarge scans, point-in-time joinsSingle-entity key lookup, <~10ms
TechColumnar lake / warehouseIn-memory KV / cache
Read shapeWhole history, many rowsLatest values, batched per request

The fix is a single feature definition that writes to both stores. The offline store answers "what was this feature's value at the timestamp of each training label?" — a point-in-time correct join that prevents label leakage (using future data to predict the past). The online store answers "what is this feature's value right now?" for the same entity. Because both come from one transform, training and serving see the same logic.[3]

Why not just recompute features in the serving code? Because two implementations of the same feature drift apart the moment either changes — that's the skew. A feature store makes the definition the contract: author once, materialize to both stores, and the online path becomes a fast read instead of a re-derivation. This is the same consistency play the recommendation system (Lesson 50) relies on for its ranking features.

Deep Dive 2 — Training on a shared cluster: scheduling + experiment tracking + registry

Hundreds of teams want GPUs; GPUs are scarce and expensive. You cannot statically partition them — utilization would crater. So training is a scheduling problem over a shared pool, which is why this leans directly on Lesson 34, the Job Scheduler.[2]

ConcernMove
Fair sharingPer-team quotas + priority queues; preempt low-priority jobs for high.
Resource fitBin-pack jobs by GPU/CPU/memory request; gang-schedule multi-GPU jobs together.
ResilienceCheckpoint long runs; retry on node failure; idempotent job ids.
ReproducibilityPin code ref, dataset version, container image, and params per run.

Around the scheduler sit two services that turn "ran a script" into "an engineering asset." Experiment tracking logs every run's params, metrics, dataset version, and output artifact, so teams compare runs and the platform can reproduce any result.[2] The chosen artifact is then pushed to the model registry: an immutable, versioned record with metrics and lineage, plus a stage (staging → prod). Promotion and rollback are registry state changes, decoupling "which model exists" from "which model serves."[4]

Why a registry as the deploy control plane? Because it makes rollout safe and auditable. The serving tier always asks the registry "what's the prod version of model X?" To roll back a bad model you flip a stage pointer — instant, no rebuild. To audit an incident you trace the prod version → training run → dataset version. That lineage chain is what makes the platform reproducible, the NFR juniors forget.

Deep Dive 3 — Model serving: online low-latency vs batch, autoscaling, A/B + canary

Serving has two modes with opposite goals, and conflating them is a classic mistake. Decide per use case.[4]

ModeGoalShape
OnlineLow latency, per-requestAutoscaled model-as-a-service endpoints; p99 budget in ms
BatchHigh throughput, bulkScheduled jobs scoring whole datasets; latency irrelevant

For online, each model gets its own autoscaled deployment so a popular model's traffic spike doesn't starve a quiet one (no noisy neighbors). Autoscaling tracks QPS/GPU utilization; bursty traffic from capacity estimation is why per-model elasticity beats one shared server. To keep the latency budget, features arrive via a single batched online-store read, and replicas are warm (model already loaded in memory).[4]

Shipping a new model version safely is its own subsystem. Because the registry decouples versions from endpoints, the platform can do traffic-split rollout:

StrategyWhat it does
CanarySend ~1–5% of traffic to the new version; watch errors/latency; auto-rollback on regression.
A/B testSplit traffic across versions; compare business metrics (not just accuracy) to pick a winner.
ShadowMirror live traffic to the new model without serving its output; compare predictions offline.

This mirrors the recommendation lesson's point: offline accuracy isn't ground truth — a live A/B test on real metrics is. The platform's contribution is making canary/A-B/shadow a config on the endpoint, not custom code each team writes.[4]

Deep Dive 4 — Monitoring for data & model drift

Unlike a normal service, an ML model can be perfectly healthy on ops metrics (200s, low latency) while quietly getting wrong, because the world it was trained on has moved. The platform must watch the data, not just the servers.[5]

Drift typeWhat changedSignal
Data / feature driftInput distribution shifts (new users, seasonality)Live feature distribution diverges from training (e.g. PSI / KL divergence)
Concept driftThe input→output relationship changesAccuracy drops once labels arrive, even if inputs look stable
Prediction driftOutput distribution shiftsScore histogram moves vs baseline — early proxy before labels exist

The mechanism: every prediction logs its input features and output, so the monitor can compare live distributions against the training baseline continuously. The hard part is labels — ground truth often arrives late (a fraud chargeback (Lesson 72) can take weeks; a recommendation's "did they click?" is fast). So you watch feature/prediction drift as leading indicators before true accuracy can be measured.[5]

What drift triggers. Alerts to the owning team, plus optionally an automated retraining job through the same training pipeline — closing the loop from monitoring back to ingestion. This is the same drift problem the recommender (Lesson 50) and the fraud system (Lesson 72) each solve individually; the platform's win is providing it once so every tenant model gets drift detection for free.
★ Staff-level signal The senior-vs-staff tell is recognizing this is a platform, not a model. Say it up front: "I'll treat each team's model as a black box and design the shared lifecycle services around it." Then anchor the whole answer on the two versioned contracts — the feature store (one definition → offline + online, killing train/serve skew) and the model registry (immutable versions + stages, making deploy/rollback/lineage trivial). Show judgement on the multi-tenancy economics: a shared GPU pool with a scheduler beats per-team clusters, and per-model autoscaling beats one shared server. Proactively raise the three things juniors miss: reproducibility (pin data+code+params+artifact), point-in-time-correct features (no label leakage), and that ops health ≠ model health — you need drift monitoring because a model can rot while returning 200s. Naming what you're not building (the ML math) is itself the staff move.[1]

Check yourself — retrieval practice

Answer from memory before scrolling back up.

1. Why does a feature store write one definition to both an offline and an online store?

One transform materialized to both stores means training and serving see the same feature logic, which is what prevents training/serving skew.

2. Why train on a shared cluster with a scheduler instead of per-team GPUs?

GPUs are scarce and bursty; statically partitioning them wastes capacity, so a shared pool plus quota-aware scheduling drives high utilization.

3. What makes the model registry the right control plane for safe rollback?

Immutable versioned artifacts with stage pointers let the serving tier swap or revert by changing which version is prod — no rebuild, instant rollback.

4. Why monitor data and prediction drift, not just latency and error rates?

A model can be ops-healthy (200s, low latency) yet degrade as the input world shifts; drift on features/predictions is the leading indicator before labels arrive.
