Deep Dive: Amazon Aurora

The managed database that rewrote the storage engine around one idea — the log is the database — and what that buys you over plain replication.

Why this lesson, for your mission: At L6/L7 it isn't enough to say "I'll use Aurora because it's managed Postgres." The interviewer wants to hear that you understand the one architectural move that makes Aurora interesting — separating compute from a purpose-built, distributed storage layer and shipping only redo log records to it — and can reason about what that buys you (less network I/O, fast crash recovery, near-instant replicas) and where it still hits a wall (one writer per cluster). Naming that single-writer ceiling and contrasting it with Spanner-class systems before you're cornered is the move that reads as staff.[1]

What it is

Amazon Aurora is a cloud-native, fully managed relational database that is wire-compatible with MySQL and PostgreSQL.[2] Your application keeps speaking the same protocol and SQL it already uses for Postgres or MySQL — drivers, ORMs, and queries don't change — but AWS replaces the storage engine underneath with its own distributed design.[2] So the deal is: keep the familiar relational engine and ACID semantics on top, swap the durability and replication machinery below for something built for the cloud.

The headline numbers AWS markets — several times the throughput of stock MySQL on the same hardware, storage that auto-grows in 10 GB chunks up to 128 TB, six copies of your data across three Availability Zones — all fall out of that re-architected storage tier.[2] Aurora is best understood not as "MySQL with better defaults" but as a different answer to the question "where does durability live?"

Internals — "the log is the database"

This is the section that earns depth. In a traditional database, the engine writes both a write-ahead/redo log and the actual data pages, and to make a replica it ships full pages (or the binlog) over the network and replays them. That is a lot of writes for one logical change. Aurora's core insight, from the 2017 SIGMOD paper, is that in a replicated, durable system the redo log is the only thing you truly need to send over the network — the data pages can be materialized from the log wherever they're needed.[1]

Storage–compute separation

Aurora splits the database into two independently scaled tiers. The compute tier is a normal MySQL/Postgres engine instance that parses SQL, runs the query planner, manages the buffer cache, and enforces transactions — but it does not own durable storage. The storage tier is a purpose-built, multi-tenant, distributed service that stores data in 10 GB segments and knows how to apply redo log records to pages.[1] The only thing the writer sends down to storage on a commit path is redo log records, not dirty data pages.[1]

6-way replication, 4/6 quorum

Every log record is replicated six ways across three Availability Zones — two copies per AZ.[1] Writes use a 4-of-6 write quorum and reads (when needed) a 3-of-6 read quorum.[1] Why those numbers? They let Aurora tolerate failures without losing availability: it can lose an entire AZ (two copies) and still reach a write quorum of 4, and it can lose an AZ plus one more node and still serve reads.[1] The quorum, not synchronous mirroring of full pages, is what delivers durability — the same CAP/quorum reasoning from Lesson 06, applied at the storage layer.

Why this slashes network I/O

Because only redo log records cross the network — not pages, not the binlog, not double-writes — Aurora collapses the write amplification of traditional replication. The SIGMOD paper reports that for the same workload Aurora performs roughly an order of magnitude fewer network I/Os than a mirrored MySQL setup, which is the bulk of where the throughput win comes from.[1] The storage nodes asynchronously coalesce log records into pages in the background, off the commit critical path, so the foreground write is cheap and the heavy page-materialization work is pushed to the storage fleet.[1]

Fast crash recovery

In a classic engine, crash recovery means replaying the redo log from the last checkpoint at startup — and the further back the checkpoint, the longer you wait.[1] Aurora doesn't recover this way. Because the storage tier already applies redo continuously in the background, recovery isn't a foreground replay step the engine must finish before opening — the database can come back and let the distributed storage reconcile pages on demand.[1] The practical result is recovery measured in seconds rather than minutes, which directly improves your availability NFR.[2]

Replicas & failover

The shared-storage design pays off again here. Because the durable data lives in one storage volume that all instances see, adding a read replica means standing up a compute instance and pointing it at the same volume — there is no re-replication of the dataset.[2] Aurora supports up to 15 reader replicas per cluster, all reading from the shared storage, with replica lag typically in the low milliseconds because they're reading the same log-backed pages rather than replaying a stream.[2]

That same property makes failover fast: if the writer dies, Aurora promotes one of the existing readers to writer. The new writer doesn't need to recover or copy data — the volume is already there and current — so failover is typically on the order of tens of seconds, not the minutes a copy-and-replay system needs.[2] A cluster endpoint (writer) and a reader endpoint abstract this so the app reconnects to the role, not a specific host.[2]

Aurora Serverless v2 takes it further by auto-scaling the compute tier up and down in fine-grained capacity units in response to load, so you don't pre-provision a fixed instance size for spiky or unpredictable workloads.[3]

When to reach for it / when NOT

Reach for Aurora when…Reach elsewhere when…
You want MySQL/Postgres semantics, managed, on AWS[2]You need multi-region active-active writes → Spanner / Cockroach
Read-heavy load that fans out to many replicas[2]Sustained write QPS beyond one writer → shard, or NoSQL
High durability + fast failover within a region[1]You're not on AWS / want to avoid lock-in → self-run Postgres
Spiky load that benefits from serverless autoscaling[3]Microsecond KV reads / counters → Redis

The ceiling to name: Aurora separates storage from compute, but a standard cluster still has exactly one writer instance — it scales reads brilliantly, not writes.[2] When sustained write throughput exceeds one writer, you're back to sharding (Aurora's own multi-writer and "Limitless" options exist but add complexity), or to a system designed for distributed writes from the ground up. That's the line where Spanner / CockroachDB belong: they use synchronized clocks and consensus to offer horizontally-scalable, multi-region write consistency, which Aurora's single-writer model does not.[4]

★ Staff-level signal Seniors say "use Aurora, it's managed and durable." Staff candidates explain the why in one breath: "Aurora's trick is that the log is the database — the writer ships only redo records to a 6-way, 4/6-quorum storage tier across three AZs, so it does roughly an order of magnitude less network I/O than mirrored MySQL, recovers in seconds, and spins up readers on the same volume with no re-replication."[1] Then they name the ceiling proactively: "it's still one writer per cluster — great for read fan-out and fast failover, but if I need multi-region active-active writes I'd reach for Spanner-class distributed SQL instead." Knowing precisely what the architecture buys and where it stops — without over-explaining that it 'speaks SQL' — is the simple-by-default judgement the bar looks for.

In the interview

When you put Aurora on the whiteboard, justify it in one line ("managed Postgres-compatible, durable across AZs, scales reads to 15 replicas"), then be ready for the predictable follow-ups. "Why is it faster than RDS MySQL?" → the log-is-the-database storage tier ships only redo, far less network I/O.[1] "How does failover work?" → promote an existing reader on the shared volume, tens of seconds, no data copy.[2] "How does it scale writes?" → here you must be honest: it doesn't past one writer; you fan out reads, then shard or move to distributed SQL.[4] Mentioning the 6-copy / 4-of-6 quorum or background page coalescing signals hands-on depth without lecturing on what ACID means.

Answer from memory before scrolling back up.

1. What does an Aurora writer actually send to its storage tier?

Aurora's core idea is "the log is the database": the writer ships only redo records, slashing network I/O.

2. How is Aurora storage durability actually achieved?

Six copies across three AZs with a 4/6 write quorum let Aurora lose a whole AZ and still commit.

3. Why can Aurora add a read replica without copying data?

Storage is shared, so a replica is just compute pointed at the existing volume — no re-replication, low lag.

4. Where does standard Aurora hit a wall versus Spanner?

Aurora scales reads but keeps a single writer; multi-region active-active writes call for distributed SQL.
