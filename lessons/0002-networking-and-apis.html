System Design · Lesson 02 · Phase 1 — Core Concepts

Networking & APIs

How clients and servers talk — and the three or four decisions an interviewer actually probes.

Why this lesson, for your mission: In step 3 of the framework you define an API; in step 5 you draw boxes and decide how they connect. Both rest on networking. The good news: interviewers care about a handful of decisions here, not the OSI model. Learn those, make the call quickly, and bank your minutes for the deep dives where L6/L7 is won.

1 of 6

1 · The default: HTTP over TCP

Two transport protocols underlie almost everything. TCP sets up a connection and guarantees every byte arrives, in order — at the cost of a little setup latency. UDP just fires packets with no guarantees — faster, lossy, used for video calls, gaming, DNS. For system design, your reflex should be: HTTP over TCP by default. It's well-understood, works everywhere, and covers ~90% of use cases.[1]

Only deviate when a requirement forces you to — which brings us to real-time.

Check before continuing

Which transport protocol guarantees ordered, complete delivery of every byte?

TCP is the connection-oriented, reliable transport. UDP trades reliability for speed.

Reread the first two sentences on TCP versus UDP.

Why should HTTP over TCP be your reflex default, rather than starting from UDP or a custom protocol?

The lesson frames it as covering ~90% of use cases: familiar, universal, and reliable. You only pay UDP's tradeoffs when a requirement demands it.

2 · When you need real-time: the decision tree

Plain request/response can't push data to a client. When the design needs the server to send updates (chat, live scores, notifications), pick the simplest option that meets the requirement — not the fanciest.[1]

Does the client need updates from the server?
  • No, just request/response → HTTP/TCP. Done.
  • Yes, but seconds-stale is fine & rare → Polling (the baseline)[4] — client asks every N seconds. Dead simple; wasteful at scale.
  • Yes, near-real-time, server→client only → Long polling (the easy solution)[4] or SSE (the efficient one-way street)[4] — works over ordinary HTTP, no special infra.
  • Yes, frequent two-way chatter → WebSockets (full-duplex)[4] — a persistent, bidirectional connection. Powerful, but stateful: it complicates load balancing and adds cost at scale.[1]

That single sentence shows simple-by-default thinking and judgement on alternatives — two of the four staff signals at once.
Check before continuing

A live-scores screen pushes occasional one-way updates to many viewers. Best first choice?

One-directional + infrequent = SSE. WebSockets adds stateful cost you don't need here.

Why does defaulting to WebSockets for a one-way, infrequent-update feature read as a junior mistake?

WebSockets work technically, but they pay for a two-way, persistent connection the use case doesn't need. Reaching for the fanciest tool over the simplest sufficient one is the junior tell.

3 · gRPC: REST outside, gRPC inside

gRPC uses binary serialization over HTTP/2 for fast service-to-service calls. You won't expose it publicly — browsers don't speak gRPC natively. The pattern to state in an interview: REST for public/client-facing APIs, gRPC for internal service-to-service hops where latency matters.[1]

Check before continuing

Two internal microservices need a low-latency call. Best protocol?

REST outside, gRPC inside. Binary + HTTP/2 makes internal hops fast.

Reread the pattern sentence: what goes public, and what stays internal?

Why is gRPC kept to internal service-to-service calls instead of exposing it directly to browsers?

The blocker is client support, not speed: gRPC is actually faster internally, but browsers can't speak it, so the public edge stays REST.

Your service uses persistent WebSocket connections. Which load balancer?

WebSockets ride a long-lived TCP connection, so L4 (transport) is required.

Why can't Layer 7 balancers route by URL path as cheaply as Layer 4 balancers forward raw connections?

Seeing the path means understanding the application protocol, not just the transport envelope. That extra parsing is exactly the speed/smart tradeoff in the table.

5 · Latency, CDNs, and designing the API

You can't beat the speed of light. A round trip New York ↔ London is ~80 ms minimum before any processing.[1] That's why we deploy regionally and put a CDN (edge cache near the user) in front of static or cacheable content. When a design has global users and latency NFRs, "regional deployments + CDN" is the reflex answer.

Most interviewers don't want perfect API design — they want reasonable endpoints, quickly, so you can move on.[2] Sketch 4–5 endpoints in a couple of minutes.[1] The rules:

  • REST by default — resources as URLs, HTTP verbs: GET /v1/users/{id}, POST /v1/events/{id}/bookings.[1]
  • Derive the user from the auth token, never from the request body — the cardinal security rule.[2]
  • Pagination: cursor-based for real-time/large feeds; offset-based is fine otherwise.[1]
  • Auth: JWT for user sessions, API keys for service-to-service.[1]
  • Mention rate limiting if the system is exposed to bot abuse.[1]
Check before continuing

Where should the current user's identity come from on a request?

Always derive identity from the token — trusting client-supplied ids is a security hole.

Reread the "cardinal security rule" bullet.

Why does a CDN reduce latency for global users when you can't speed up the network itself?

Since you cannot beat the speed of light, the fix is to shrink the distance data travels by serving cached content from an edge node near the user.

Reread the sentence right after the New York to London round-trip number.
