Design Confluence Popular Feed

Real-time activity feed that surfaces trending pages, with heavy reads and denormalized, eventually consistent data.

Why this lesson, for your mission: Feed systems are everywhere: social networks, workplace platforms, news aggregators. The staff move is recognizing that this is a write-heavy, read-at-scale problem with soft consistency requirements that trades freshness for performance. You optimize reads via denormalization and caching, accept eventual consistency, and batch aggregations. The same architecture powers Slack activity, Discord channels, and LinkedIn feeds.

Phase 1 · 0–5 minClarify the problemPin scope: which events, which users, real-time or batch?

Ask before you design

  • "What events trigger the feed — page updates, comments, watches, shares?" — Scope determines ingestion volume and ranking complexity.
  • "How many users see the feed — workspace members or selected followers?" — Fanout strategy depends on audience size.
  • "How fresh must rankings be — real-time or is 5-minute staleness acceptable?" — Real-time demands streaming aggregation; 5-minute staleness allows batch computation.

Phase 2 · 5–10 minEstimate what mattersRead:write ratio, event volume, feed freshness.

Capacity Estimation

Event volume

100M DAU × ~5 events/user/day (page view, comment, edit) ≈ 500M events/day ≈ ~6k events/sec average, peaking at ~100k/sec during business hours. Implication: streaming ingestion is required; batch processing for ranking.

Feed reads

Each user checks the feed ~10× per day; scroll loads ~50 items per request. 100M × 10 × 50 ≈ ~50B read operations/day ≈ ~580k reads/sec. Implication: heavy caching; denormalization is mandatory.

Read:write ratio

580k reads / 6k writes ≈ ~100:1, skewed toward reads. Implication: optimize read path; write path can be eventual.

Interviewer pushback

"Can you guarantee real-time consistency on the feed?"

Staff answer: No. At 100k events/sec and 100:1 read skew, maintaining perfect consistency on every read is impossible. Instead, emit events to Kafka, aggregate in batches (every 5 minutes), and cache the result. Users see eventual consistency.

Say to move on → "With 6k events/sec and 580k reads/sec, I'll design a denormalized feed schema."

Interviewer pushback

"Why denormalize the feed? Can't you compute it on-read from events?"

Staff answer: Computing the feed on-read from 6k events/sec is too expensive. Instead, publish events to Kafka, aggregate offline into a denormalized FeedEntry table (ranked by score), and serve from cache. This trades storage for read latency.

High-Level Design

Events are published to Kafka, partitioned by user_id or page_id (depending on fanout strategy). A batch aggregator runs every 5 minutes, computes popularity scores, and updates the denormalized feed table. For real-time: WebSocket connections push new events to clients immediately. For reads: queries hit the cached feed table, returning sorted entries by score.

Interviewer pushback

"What if a user creates 100 pages in one go — won't the feed explode?"

Staff answer: Feed entries are truncated: keep only the top 10k entries per user; older entries are archived. Bulk operations (bulk edit, bulk delete) are deduplicated in aggregation, so 100 edits become 1 entry per page.

Say to move on → "The design is event-driven with batch aggregation. The hard part is ranking and fanout strategies."

Phase 5 · 27–47 minDeep dives & tradeoffsDenormalization, ranking, batch aggregation, and fanout.

Deep Dives

Deep Dive 1 — Ranking and score computation

Score feed entries by popularity: score = views × 0.1 + comments × 1.0 + edits × 0.5, with time decay (newer = higher). Recompute every 5 minutes. Cache the score in Redis; serve from cache on reads.

Deep Dive 2 — Fanout strategies (push vs. pull)

Two approaches: (1) Push: on every event, update all followers' feeds. (2) Pull: on read, merge all followed pages' recent activity. Push is simpler but scales poorly (high follower count causes write amplification). Pull is read-heavy but scales better.

StrategyWrite costRead costBest for
Push (fan-out on write)1 event × 1k followers = 1k writesO(1) — feed is pre-computedLow-follower users; celebrities are expensive
Pull (on-read merge)1 write to event logO(followers) — merge 1k feedsHigh-follower users; most users at scale
HybridPush for followers < 1k; pull for > 1kBalancedDefault — handles both extremes

Deep Dive 3 — Deduplication and aggregation

The same page may have multiple edits in 5 minutes. In aggregation, deduplicate by page_id and keep the most recent timestamp. Aggregate comments separately: sum them, show top 3 comments.

Deep Dive 4 — Real-time updates via WebSocket

To show new events in real-time, maintain WebSocket connections from clients. On event publish, emit to connected clients immediately (via Redis pub/sub or direct connection). Clients render the new entry without waiting for batch aggregation.

★ Staff-level signal A senior engineer designs a basic feed with events and cache. A staff engineer recognizes that denormalization is the architecture, not an optimization. They identify the push/pull tradeoff before writing any code and justify the hybrid strategy based on follower distribution. They know that ranking can be batch-computed and that eventual consistency (5-minute staleness) is acceptable. They add real-time WebSocket updates as a later layer, not the main story.

Interviewer pushback

"What if a trending page gets 1M events in one batch cycle?"

Staff answer: Deduplicate by page_id in the aggregator; 1M events become 1 feed entry. Keep the most recent edit timestamp and aggregate comment counts. Total storage is constant; only the comment count and edit timestamp change.

Say to move on → "With batch aggregation and eventual consistency, scaling is about partitioning users and caching."

Closing Summary (60 seconds)

The feed system is event-driven with batch aggregation: events stream to Kafka, a batch aggregator ranks every 5 minutes, and denormalized feeds are cached and served to users. Push/pull hybrid fanout avoids write amplification for high-follower users. Real-time updates come via WebSocket; eventual consistency (5-minute staleness) is acceptable. At 10×, partition by user_id and increase cache size. The architecture is simple, scales linearly, and trades freshness for performance.

Check yourself — retrieval practice

Answer from memory before scrolling back up.

1. Why denormalize the feed instead of computing it on-read?

At 580k reads/sec, computing every feed on-the-fly (merging 1000s of events, ranking) is too slow. Precompute and cache the feed; refresh every 5 minutes.

2. When should you use push fanout vs. pull for the feed?

Push (fan-out on write) is cheap for low-follower users. High-follower users (celebrities) amplify write volume; use pull (compute on-read) for them. Hybrid handles both extremes.

3. How should duplicate page edits within a 5-minute batch be aggregated?

If the same page is edited 10 times in 5 minutes, the feed shows 1 entry with the latest timestamp. This keeps feed entries deduplicated and recent.
