Design a Live Score / Sports Updates System

Pushing the latest score to millions of phones the instant a goal is scored — and surviving the moment ten million of them refresh at kickoff of the World Cup final.

Why this lesson, for your mission: This is a read-fan-out problem wearing a sports jersey. The write side is tiny — a few events per match per minute. The entire interview is the read side: deliver one tiny piece of state (the score) to a colossal, spiky audience, cheaply. An L6/L7 candidate spots immediately that this is the Live Comments[1] fan-out pattern with one crucial simplification — the payload is a single latest value, not a stream — and that simplification unlocks CDN/edge caching as the dominant tool. Reaching for the edge before the interviewer asks "what about the World Cup final?" is the move.

Functional Requirements

Keep the core list tight. A live-score product is small in surface area — the difficulty is entirely in scale and latency, not features.

#Users should be able to…Why it shapes the design
1Ingest match events (goal, card, period end)Write path — trickle of events, but the source of truth
2Receive live score updates while watching a matchThe fan-out / broadcast problem — the whole interview
3View a single match's current score & timelineRead path — the hot object that must be cacheable
4List today's / live matchesThe discovery surface that funnels everyone into hot matches
Out of scope (say it out loud): betting odds, full play-by-play video, user accounts/social, comments, push notifications to closed apps. We model a match as a small state object — {score, clock, status, recent events} — and broadcast changes to it. We do not own the cameras or the officiating.[1]

Non-Functional Requirements

This system is defined by its NFRs far more than its features. State the target and the priority, not just the "-ility."

NFRTarget / priority
Low-latency updatesScore change visible to viewers in ~1–2s (humans tolerate a small lag here; sub-200ms is not required)
Huge read fan-outTens of millions of concurrent viewers on a single marquee match; reads dwarf writes by ~10⁶:1
Spike handlingSurvive kickoff/goal "thundering herd" — load can 100× in seconds[2]
Availability over consistencyAlways show a score; a viewer being 1–2s behind beats an error page (AP, not CP)[1]
Cost efficiencyServing the same byte to 10M people must not cost 10M DB reads
The key tension: the data is tiny and changes rarely, but is wanted by everyone, all at once, the instant it changes. That profile — small hot object + enormous read multiplier + bursty — is the textbook case for edge caching. The architecture optimizes read distribution, not write throughput. Internalize that the score is just one cacheable object per match.

Capacity Estimation

Only compute numbers that change a decision. Two matter: how spiky the read load is, and how trivial the write load is.

  • Write rate (events): a football match has maybe ~10–30 meaningful events over 90 minutes — well under 1 event/sec even across thousands of simultaneous matches. The write path is effectively free; do not scale for it.
  • Read fan-out: 10M concurrent viewers of one match each wanting the latest score. If they polled every 5s naively, that's 2M req/sec to origin for a single match — impossible to serve from a DB, trivial to serve from a CDN as one cached object.
  • Payload size: a score snapshot is ~1–2 KB of JSON. 10M viewers × 2KB = ~20 GB per fetch wave — a rounding error for a CDN, a meltdown for an origin.
  • Spike shape: at kickoff and after a goal, near-simultaneous demand. The design must collapse N identical requests into one origin fetch (cache + request coalescing).
Design implication: you never scale the database for reads — you push the latest score to the edge and let the CDN absorb the fan-out and the spikes. The origin only ever serves cache misses, which you can count on one hand per match per update.

Core Entities & API

Entities

EntityFields (sketch)

EventeventId, matchId, type (goal/card/sub), team, minute, seq

API

Ingest is authenticated to trusted feed providers (the data-entry team or an automated feed), never the public. Reads are public, anonymous, and aggressively cacheable.

  • POST /v1/matches/{id}/events — feed-provider auth; body { type, team, minute }. Appends an event and recomputes MatchState.
  • GET /v1/matches/{id} — the latest MatchState. Returns Cache-Control: max-age=1 + ETag; this is the object the CDN holds.[2]
  • GET /v1/matches?status=live — today's live matches list (also CDN-cached, short TTL).
  • GET /v1/matches/{id}/stream — SSE/WebSocket subscription; server pushes each new MatchState version for engaged viewers.
  • GET /v1/matches/{id}/events?since={seq} — backfill the timeline (cursor by seq).

Data Flow

This is a data-processing system: raw events in, a clean broadcastable state out. The pipeline is short but worth naming.

Event → broadcastable state, end to end:
  • 1. A goal happens. The feed (manual operator or automatic provider) calls POST /events.
  • 2. The Ingest Service validates, appends the event to the durable event log, and recomputes MatchState (bumps version).
  • 3. It writes the new MatchState to the fast store and publishes it to the match's channel.
  • 4. Two readers consume it: the edge cache is invalidated/updated so the next pull is fresh, and the connection servers push it to subscribed viewers.
One write event becomes one cache update plus one publish — both O(1). The 10M deliveries happen at the edge and the connection fleet, not in the pipeline.

High-Level Design

Two paths, deliberately separated: a tiny ingest path (events → state → publish) and a massive read path dominated by the CDN, with a push fleet layered on top for engaged viewers.

ComponentResponsibility
Ingest ServiceAuthenticates feeds, validates & appends events, recomputes & versions MatchState, publishes the change
Event Log + State StoreDurable append-only event log (source of truth) + fast key-value MatchState by matchId (Redis/DynamoDB)
CDN / EdgeCaches GET /matches/{id} as one object per match with a ~1s TTL; absorbs the read fan-out and spikes[2]
Read API (origin)Serves cache misses only — reads MatchState from the fast store; stateless, lightly scaled
Pub/Sub backplaneOne channel per match; the fan-out primitive feeding the connection fleet[1]
Connection (Realtime) serversHold open SSE/WebSocket connections for engaged viewers; push each new MatchState version
The mental model: the score is one small object per match. Most of the world reads it pulled through the CDN; a smaller set of actively-engaged viewers get it pushed. Both are fed by the same versioned MatchState, so they never disagree by more than one update.

Deep Dives

Deep Dive 1 — Ingesting match events: manual & automatic feeds into one pipeline

Scores come from heterogeneous, sometimes-unreliable sources: a human operator tapping a tablet at a lower-league game, an official league data feed (Opta/Stats Perform-style) for the big ones, sometimes redundant providers for the same match. The job is to fold all of them into one authoritative, monotonic MatchState.

ConcernApproachWhy
Multiple/duplicate feedsIdempotent ingest keyed on (matchId, eventId); dedupe before applyingTwo providers reporting the same goal must not make it 2–0
Out-of-order / correctionsAppend-only event log + recompute state from events; support a correction event typeRefs disallow goals; you must be able to walk the score back
Source of truthEvent log is canonical; MatchState is a derived, cached projectionYou can always rebuild the snapshot by replaying events
★ Staff-level signal Treat ingest as event sourcing, not "UPDATE the score." Modeling state as a projection of an idempotent, append-only event log is what makes corrections, late events, and dueling feeds tractable instead of a tangle of mutation bugs. The versioned MatchState projection is also exactly the artifact your CDN and your push fleet both consume — one derivation, two delivery channels. Naming idempotency and corrections unprompted signals you've shipped a real ingest system. (The score itself is a tiny distributed counter[3], but here counting is trivial — distribution is the hard part.)

Deep Dive 2 — Read fan-out to millions: push vs pull, and the hybrid

How does the new score reach 10M viewers? Two families, and the right answer is to use both for different audiences.

ModelHowTrade-off
Pure push (SSE/WS)Persistent connection per viewer; pub/sub fans new versions out[1]~Instant, but you hold 10M live connections — a huge, spiky connection fleet to provision and rebalance
Pure pull (polling)Clients GET /matches/{id} every ~1–5s through the CDN[2]~1–5s lag, but the object is cached at the edge — one origin fetch serves millions, scales for almost nothing
Hybrid (the pick)Default everyone to CDN-cached polling; upgrade actively engaged viewers (match page in foreground) to a pushed streamCheap at rest, instant where it matters; bounded connection fleet
Why CDN-cached pull is the workhorse: the score is one tiny object with a ~1s TTL. The CDN serves the same cached bytes to every viewer at the edge, close to them, and only forwards a request to origin on a miss — roughly once per second per match per POP, regardless of whether 10K or 10M people are watching.[2] A 2M-req/sec match becomes a handful of origin reads. This is the same insight as the Live Comments CDN-snapshot trick[1]: turn an impossible per-connection push into a trivially-cached static object.
★ Staff-level signal The senior answer is "use WebSockets." The staff answer is "polling is not a dirty word when the payload is one cacheable object." Recognizing that a 1–2s NFR lets you serve the masses from the edge for pennies — and reserving the expensive persistent-connection fleet only for engaged foreground viewers — is the judgement call that separates levels. You're matching delivery cost to how much each viewer actually cares.

Deep Dive 3 — The thundering herd at kickoff (and after every goal)

At kickoff of the final, 10M clients may request the match within the same second; after a goal, every cached copy expires at once and they all re-fetch. If those misses reach origin simultaneously, you've built a self-inflicted DDoS.[2]

TechniqueHowEffect
Request coalescingCDN collapses concurrent misses for the same key into one origin request (e.g. proxy_cache_lock)10M simultaneous misses → 1 origin fetch per POP
Stale-while-revalidateServe the slightly-stale cached score instantly while one background fetch refreshes itNobody waits on the miss; origin sees a trickle, not a flood
Jittered TTL / client pollRandomize TTLs and client poll intervals slightly so expiries don't alignSmears the spike across the second instead of a single wall of traffic
★ Staff-level signal The thundering herd is the specific failure this system invites, and an L6/L7 candidate names it before being asked. The fix isn't "more origin servers" — it's request coalescing + stale-while-revalidate at the edge so that synchronized demand still costs one origin fetch. Saying "the masses are eventually consistent on purpose, so I can serve stale-while-revalidate and coalesce misses" demonstrates you understand the herd is a caching problem, not a capacity problem.

Deep Dive 4 — Eventual consistency of the displayed score

We chose availability over consistency, so different viewers will briefly see different scores: a pushed viewer sees 1–0 at t+0.5s, a CDN-cached viewer at t+1.5s, someone behind a stale edge maybe t+3s. That's acceptable — but only if it never goes backwards or shows nonsense.

Guardrails that make eventual consistency safe:
  • Monotonic versions: every MatchState carries a monotonic version; clients ignore any update with a lower version than they've seen, so the score never appears to regress.
  • Last-writer-wins on a single projection: all channels derive from the same versioned projection, so push and pull can differ in recency but not in content for a given version.
  • Bounded staleness: short TTLs (~1s) cap how far behind any viewer can be; the final whistle gets a forced invalidation so nobody is stuck on a non-final score.
★ Staff-level signal Eventual consistency is fine; non-monotonic consistency is not. The staff move is to allow viewers to disagree on how fresh the score is while guaranteeing it never flickers 1–0 → 0–0 → 1–0. A version number on the projection is a one-line idea that makes a wildly distributed, multi-path delivery system feel correct to a human watching their team. Calling out the "score went backwards" bug before it bites is the kind of failure-mode foresight L6/L7 rewards.

Check yourself — retrieval practice

Answer from memory before scrolling back up.

1. Why is CDN-cached polling the workhorse for delivering the score to the masses?

A small hot object with a ~1s TTL caches at the edge; one origin miss per match per interval serves everyone, regardless of audience size.

2. What collapses 10M simultaneous cache misses at kickoff into a single origin fetch?

The edge coalesces concurrent misses for one key into a single origin request and serves stale-while-revalidate, so the herd costs one fetch.

3. How is the displayed score kept from ever appearing to go backwards across viewers?

A monotonic version on the projection lets viewers differ in freshness while guaranteeing the score never regresses on any client.

4. Why model ingest as an append-only event log rather than updating the score in place?

State becomes a derived projection of an idempotent log, so duplicate feeds, late events, and ref corrections are reconciled by replay, not mutation.
