Deep Dive: Load Balancing

The box that sits in front of your servers, hides them behind one address, and decides which one handles each request — without it, "just add more servers" doesn't actually scale.

Why this lesson, for your mission: Almost every L6/L7 design starts with a client, a load balancer, and a fleet of stateless app servers — the LB is the first box you draw and the one interviewers probe hardest. A senior candidate says "put a load balancer here" and moves on. A staff candidate says which layer (L4 vs L7), why (do you need to route on URL or terminate TLS, or just spray packets fast?), picks an algorithm with a reason, and then — unprompted — points out that the load balancer is itself a single point of failure and explains how they'd make it redundant. This lesson gives you that full mental model so the LB stops being a black box you wave at and becomes a place you can show depth.

What load balancing is

A load balancer (LB) is a reverse proxy that sits between clients and a pool of backend servers and distributes incoming traffic across them.[1] It exists to deliver two things you can't get from a single machine: scalability (spread load so you can add servers horizontally instead of buying a bigger one) and availability (if one backend dies, route around it so users never notice).[1]

Two roles matter beyond just spreading traffic. First, the LB is a single entry point: clients connect to one stable address (a DNS name or virtual IP), and the LB hides the fleet behind it. You can add, remove, deploy, or restart backends without clients knowing — they only ever see the LB.[1] Second, the LB runs health checks: it periodically probes each backend and removes any that fail from rotation, sending new requests only to healthy nodes.[2] Spreading traffic across a pool that includes a dead server isn't load balancing — it's load balancing plus an outage. The health check is what turns a list of servers into a self-healing pool.

Because the LB owns the entry point, it's also the natural home for cross-cutting concerns: TLS termination, basic rate limiting, and routing — which is exactly where the L4-vs-L7 distinction comes in.

L4 vs L7 — the distinction that matters

Load balancers operate at one of two layers of the network stack (see Networking & APIs, Lesson 2). This is the single most important thing to get right in an interview, because it determines what the LB can and can't do.

A Layer-4 (transport) load balancer routes at the level of TCP/UDP connections. It sees source/destination IP and port — not the contents.[2] It picks a backend when the connection opens and forwards every packet of that connection to the same server, without ever parsing the bytes inside. Because it does almost no work per packet, it's extremely fast and cheap, and it works for any protocol (it doesn't need to understand HTTP).

A Layer-7 (application) load balancer actually terminates the connection, reads the HTTP request, and routes based on its content — URL path, hostname, headers, cookies, method.[2] This unlocks content-based routing: send /api/* to one fleet and /images/* to another, or route by Host header for multi-tenant apps. Because it terminates the connection, it's also where you do TLS termination — decrypt HTTPS once at the edge so backends speak plain HTTP — plus header rewriting, sticky cookies, and request-level observability. The cost: parsing every request is more CPU and slightly more latency than L4.

When to pick which
  • Reach for L7 by default for HTTP/HTTPS web traffic — you almost always want TLS termination, path-based routing, and per-request visibility. It's the standard front door for an API or website.
  • Reach for L4 when you need raw throughput and ultra-low latency, a non-HTTP protocol (databases, gRPC streams, game traffic), end-to-end TLS the backend must terminate, or long-lived connections like WebSockets where there's no per-request routing to do anyway.
  • Common real setup: an L4 LB at the very edge for raw scale, fronting an L7 layer (or per-region L7 LBs) that does the smart HTTP routing — breadth at L4, depth at L7.

Balancing algorithms

Once the LB knows the healthy pool, it needs a rule for picking which backend gets the next request. The common ones, in order of how often they come up:

AlgorithmHow it picksBest for
Round robinNext server in rotation, one by one.[1]Uniform requests & identical servers; the simple default.
Weighted round robinRotation biased by a per-server weight.[1]Heterogeneous hardware; canary/gradual rollouts.
Least connectionsServer with the fewest active connections.[1]Variable request durations (long-lived/slow requests).
IP / consistent hashHash of client IP (or key) maps to a server.[1]Sticky sessions; cache locality (see below).

Round robin is the honest default — cheap and fair when requests cost about the same. But if one request takes 10ms and the next takes 10s, round robin will happily pile slow requests onto a server that's already drowning. Least connections fixes that by tracking live load and steering away from busy nodes — the right call when request durations vary widely. Weighted variants let a beefier box (or a freshly deployed canary) take a deliberately larger or smaller share.

Hashing, sticky sessions, and the link to Lesson 5

IP hash / hash-based routing sends the same client (or the same key) to the same backend every time. That gives you sticky sessions (session affinity): useful when a server holds in-memory session state, or when routing the same key to the same node maximizes cache hits. The naive version — hash(client_ip) % N — has a fatal flaw: change N (add or lose a server) and almost every key remaps to a different backend, blowing away every cache and session at once. The fix is consistent hashing, which remaps only the small fraction of keys near the node that changed.[1] This is the exact mechanism you learned in Sharding & Consistent Hashing (Lesson 5) — the same ring that keeps shard movement minimal also keeps a hashing load balancer's affinity stable as the pool scales.

Prefer stateless backends over sticky sessions. Stickiness is a crutch: it pins users to a node, so a deploy or crash drops their session, and load skews toward whoever holds the heavy sessions. The staff-default is to make app servers stateless — push session state into a shared store (Redis) or a signed token — so any backend can serve any request and plain round robin just works. Reach for stickiness only when you truly can't externalize state.

Scaling & availability — including the LB itself

Health checks (above) handle a backend dying. But the LB introduces its own risk, and this is the deep-dive interviewers love.

The load balancer is a single point of failure

You put the LB in front so a backend failure is invisible — but now everything flows through the LB. If it dies, your entire service is down, no matter how healthy the backends are.[1] You never run a single LB in production. The standard answers:

  • Active-passive (failover) pair: two LBs share a floating virtual IP; the passive one health-checks the active and takes over the VIP within seconds if it fails.[1]
  • Active-active + DNS / anycast: run multiple LBs and spread clients across them via DNS round robin or anycast (many LBs announce the same IP; the network routes each client to the nearest healthy one). More capacity and no idle standby.
  • Managed redundancy: cloud LBs (AWS ELB/ALB/NLB) are themselves horizontally scaled, multi-AZ services — the provider handles LB redundancy for you, which is why "use a managed LB" is a perfectly good interview answer.[2]

Connection draining and graceful changes

When you remove a backend (deploy, scale-down), don't cut its live connections. Connection draining (a.k.a. deregistration delay) stops sending the node new requests while letting in-flight ones finish, then removes it.[2] This is what makes zero-downtime deploys possible.

Why WebSockets want L4 / sticky

A WebSocket (see Real-Time Delivery, Lesson 120) is a single long-lived TCP connection, not a stream of independent requests. There's no per-request routing decision to make after the upgrade, so an L4 LB (or an L7 LB with sticky routing) that pins the whole connection to one backend is the natural fit — and that backend must stay in rotation for the connection's lifetime, so draining matters even more.

Global server load balancing (GSLB)

Everything above balances within one region. To balance across regions — for latency and for surviving a whole-region outage — you use GSLB, typically via GeoDNS: the DNS resolver returns the IP of the closest or healthiest regional LB based on the client's location.[1] It's the same geo-routing idea that powers a CDN (Lesson 109) — get the user to the nearest edge — applied to your origin load balancers.

★ Staff-level signal Senior candidates draw a box labeled "LB" and stop. Staff candidates do four things without being asked. First, they choose a layer with a reason: "L7 here because I want path-based routing and TLS termination at the edge; if this were raw WebSocket traffic I'd drop to L4." Second, they pick an algorithm to match the workload: "requests here vary from 5ms to 5s, so least-connections beats round robin." Third — the move that separates levels — they flag the LB as a SPOF before the interviewer can: "this LB is now my single point of failure, so it's an active-active pair behind anycast (or a managed multi-AZ LB)." Fourth, they keep backends stateless so they can use the simplest algorithm and avoid sticky sessions entirely. Naming the LB's own failure mode and reaching for the simplest-by-default stateless design is the whole signal.

In the interview

When you place a load balancer, deliver it in this arc: (1) say why — "stateless app servers behind an LB so I can scale horizontally and survive a node failure." (2) Pick the layer with a reason — L7 for HTTP routing + TLS termination, L4 for raw throughput or WebSockets. (3) Name an algorithm tied to the workload — round robin for uniform requests, least-connections for variable ones. (4) Pre-empt the SPOF — "the LB itself is redundant: active-active behind anycast, or a managed multi-AZ LB." (5) If the design is multi-region, add GSLB/GeoDNS for cross-region routing and failover. That's breadth-then-depth: a fast justified placement, then 60% depth on layer choice, statelessness, and the LB's own availability.

Check yourself — retrieval practice

Answer from memory before scrolling back up.

1. What can an L7 load balancer do that an L4 one cannot?

L7 terminates the connection and reads the HTTP request, so it can route by URL/header/cookie and terminate TLS — L4 only sees IP and port.

2. Why prefer consistent hashing over hash(ip) % N for affinity?

With modulo hashing, changing N remaps nearly every key (dropping all caches/sessions); consistent hashing only moves keys near the changed node — same as Lesson 5.

3. When does least connections beat plain round robin?

Round robin ignores live load; with highly variable request times it can pile slow requests onto a busy node, so least-connections steers around them.

4. Why is a single load balancer a problem you must address?

The LB hides backend failures but becomes the single point of failure itself; you make it redundant (active-passive, active-active + anycast, or a managed multi-AZ LB).
