Deep Dive: gRPC

The default for fast, typed, internal service-to-service calls — and knowing exactly why you'd never put it raw in a browser.

Why this lesson, for your mission: At L6/L7 "we'll use gRPC between services" is only a starting move. The interviewer wants to know why it's faster than JSON-over-REST (binary Protobuf on HTTP/2, not magic), what its streaming modes buy you, and — the real depth — why long-lived HTTP/2 connections wreck naive L4 load balancing and what you do about it. Naming that load-balancing problem before you're asked is the signal that reads as staff.[1]

What it is

gRPC is a high-performance, open-source RPC (Remote Procedure Call) framework: you call a method on a remote server as if it were a local function, and gRPC handles serialization, transport, and the round trip.[2] Two design choices define it. First, the contract is written in Protocol Buffers (Protobuf) — a language-neutral interface definition language (IDL) — and a code generator emits typed client and server stubs in your language.[2] Second, the wire transport is HTTP/2, which gives it multiplexing, streaming, and header compression for free.[3]

The net effect: a strongly-typed, versioned contract; a compact binary payload; and full-duplex streaming over a single connection. That combination is why gRPC became the default for the chatty east-west traffic between microservices in large fleets, where JSON's verbosity and the cost of one-connection-per-request actually add up.[1] It builds directly on the transport choices from Lesson 09.

Internals — the part that earns depth

Protobuf: the IDL and the binary wire format

You declare messages and services in a .proto file. Each field gets a name, a type, and — critically — a small integer field tag:

.proto definitionWhat the tag is for
message User { string name = 1; int32 age = 2; }Tags 1 and 2 identify fields on the wire — not the names[4]

On the wire a Protobuf message is not self-describing text like JSON. Each field is encoded as a key (the field tag combined with a 3-bit wire type) followed by the value.[4] Integers use varints — variable-length integers where small numbers cost one byte and only large ones cost more — so common small values are tiny.[4] Field names never travel; the tag number is the identity. Compare the two encodings of the same record:

JSONProtobuf
{"age":150} — 11 bytes, ships the key text and digits as characters~3 bytes — one byte tag/type, value as a varint, no key text[4]

Why it's smaller and faster: no repeated field-name strings, no quotes or braces, numbers stored as bytes rather than ASCII digits, and parsing is a tight length-prefixed walk instead of tokenizing text.[4] The cost is that the bytes are opaque — you cannot read them without the .proto, which is exactly why Protobuf shines internally and JSON wins for human-debuggable public APIs.

The same tag-based design gives schema evolution: add a new field with a new tag and old clients simply ignore it; never reuse or renumber a tag and forward/backward compatibility holds. This is the staff-relevant property — you can deploy producer and consumer independently.[4]

HTTP/2: multiplexing and streaming

gRPC runs on HTTP/2, whose key feature is multiplexing: many independent streams share one TCP connection concurrently, with no head-of-line blocking at the HTTP layer.[3] HTTP/1.1 forced one in-flight request per connection (or clumsy pipelining), so high call volume meant many sockets; HTTP/2 collapses that to a single long-lived connection. Headers are compressed (HPACK), and frames are binary.[3] Because a stream is bidirectional and long-lived, gRPC exposes four call types:

Call typeShapeUse
Unary1 request → 1 responseThe normal RPC; most calls[2]
Server streaming1 request → N responsesSubscriptions, large result feeds[2]
Client streamingN requests → 1 responseUploads, telemetry batches[2]
BidirectionalN ↔ N, independentChat, real-time sync[2]

Codegen stubs

Running protoc (with the gRPC plugin) on your .proto generates a typed client stub and a server skeleton in each target language.[2] The client calls stub.GetUser(req) like a local method; the stub marshals the Protobuf, opens an HTTP/2 stream, and unmarshals the reply. You get compile-time type safety across a polyglot fleet from a single source of truth — no hand-written client libraries drifting out of sync.

Deadlines, cancellation, metadata, status codes

gRPC bakes in the operational primitives REST leaves to convention:

  • Deadlines/timeouts: the caller sets an absolute deadline that propagates with the call; when it passes, the RPC fails fast on both ends rather than hanging — essential for bounding cascading latency.[5]
  • Cancellation: if the caller goes away or cancels, the server is notified and can stop work, freeing resources.[5]
  • Metadata: key-value pairs (carried as HTTP/2 headers) for auth tokens, tracing IDs, etc. — the gRPC analog of HTTP headers.[2]
  • Status codes: a fixed enum (OK, NOT_FOUND, DEADLINE_EXCEEDED, UNAVAILABLE…) — a uniform error vocabulary across languages, unlike REST's reuse of HTTP status codes.[6]

gRPC vs REST

This is the comparison the interviewer is actually after. They are not rivals so much as tools for different edges of the system.

DimensiongRPCREST / JSON
PayloadBinary Protobuf — compact, opaque[4]JSON text — verbose, human-readable
TransportHTTP/2, multiplexed, streaming[3]Usually HTTP/1.1, request/response
ContractStrict .proto + codegen[2]OpenAPI/convention, looser
BrowserNo native support → needs gRPC-Web[7]Works everywhere, natively
Best atInternal service-to-service[1]Public / browser-facing APIs

The rule of thumb: reach for gRPC for internal east-west traffic — high-volume, low-latency, polyglot service-to-service calls behind your edge. Reach for REST (or GraphQL, the subject of Lesson 111) for public, browser-facing APIs where ubiquity, caching, and debuggability matter more than raw bytes.[1]

gRPC-Web: browsers can't speak raw gRPC because they don't expose the HTTP/2 frame control gRPC needs. gRPC-Web is a variant plus a proxy (e.g. Envoy) that translates the browser's calls into real gRPC behind the edge — so you keep the typed contract but pay a proxy hop.[7]

The load-balancing trap — name this before they make you
  • gRPC opens one long-lived HTTP/2 connection and multiplexes every call over it. A naive L4 (connection-level) load balancer picks a backend once, at connect time, then pins all that traffic there.[8]
  • Result: connections distribute evenly but requests don't — a few backends get hammered while new ones added during a scale-up sit idle, because nobody opens fresh connections to them.[8]
  • Fixes: use an L7 (request-aware) proxy like Envoy that balances individual streams; or client-side load balancing where the client resolves all backends and round-robins calls; or periodically recycle connections so rebalancing happens.[8]
  • This is the gotcha that separates "I used gRPC" from "I've run gRPC in production."

When NOT to use it

Avoid gRPC when…Because…
The client is a browser / public web appNo native support; needs a gRPC-Web proxy hop[7]
You want human-readable, easily-debugged APIsBinary payloads need the .proto to decode[4]
You rely on HTTP caching / CDNs for GET readsRPC POST semantics don't map to HTTP caching[1]
It's a simple low-traffic CRUD or third-party APIREST is simpler and ubiquitous; gRPC overhead unjustified[1]
★ Staff-level signal Seniors say "gRPC between services because it's faster." Staff candidates say why and what it costs in one breath: "Protobuf over HTTP/2 — compact binary, multiplexed streams, typed stubs across our polyglot fleet — but it's opaque to debug and browsers can't speak it natively, so the public edge stays REST and we'd front internal gRPC with gRPC-Web only where a browser needs it." And they raise the real operational trap unprompted: "long-lived HTTP/2 connections defeat L4 load balancing, so I'd put Envoy (L7) or client-side LB in front, otherwise scaling out adds idle backends."[8] Choosing the protocol per edge, and surfacing the load-balancing failure mode before being cornered, is the judgement the bar rewards — without over-explaining what RPC is.

In the interview

When you draw arrows between internal services, justify the protocol in one line ("gRPC for east-west — typed contracts and a compact binary payload at high call volume") and keep REST/GraphQL at the public edge.[1] Be ready for the two predictable follow-ups: "Why is it faster than REST?" (binary Protobuf + HTTP/2 multiplexing, not magic) and "How do you load-balance it?" (L7/Envoy or client-side LB, because long-lived HTTP/2 connections fool L4).[8] Mentioning deadlines propagating to bound cascading latency, or streaming for a feed, signals hands-on depth. Don't pitch gRPC for the browser path — that's the tell that you've only read about it.

Check yourself — retrieval practice

Answer from memory before scrolling back up.

1. Why is a Protobuf payload smaller than the equivalent JSON?

Protobuf encodes fields by integer tag plus varint values — field-name strings never travel, so bytes shrink.

2. What does HTTP/2 multiplexing give gRPC over HTTP/1.1?

HTTP/2 multiplexes independent streams on a single long-lived connection, removing one-request-per-socket limits.

3. Why do long-lived gRPC connections break naive L4 load balancing?

L4 balances at connect time; with one pinned connection, requests aren't spread — use L7/Envoy or client-side LB.

4. When is REST the better choice over gRPC for an interface?

Browsers lack native gRPC and HTTP caching wants REST; public edges favor REST while gRPC stays internal.
