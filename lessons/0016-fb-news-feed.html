Design Facebook News Feed

A read-heavy feed for two billion users — where the whole interview turns on one question: who pays the cost of fan-out, and when?

Why this lesson, for your mission: The News Feed is the canonical "fan-out" problem, and it separates seniors from staff with surgical clarity. A senior recites "fan-out on write vs read." A staff candidate derives the hybrid from the follower-count distribution, names the celebrity fan-out as the real bottleneck, and treats every choice as a tradeoff — not a memorized answer. This lesson teaches you to do the second thing.

Functional Requirements

Scope ruthlessly. Three capabilities cover the core; everything else (likes, comments, visibility rules) you name as out-of-scope so the interviewer knows you saw them and chose to defer.[1]

#Users should be able to…
1Create a post (text/media) that their followers can see.
2Follow / friend other users (a uni-directional follow edge).
3View a feed of posts from people they follow, and page through it.

Out of scope: likes, comments, visibility controls, notifications. State this explicitly.

Non-Functional Requirements

NFRs are where you set the targets that the design must hit. For a feed, the dominant tension is the classic one — you trade consistency for availability and latency, because nobody is harmed by seeing a post one minute late.[1]

PropertyTarget / priority
LatencyPosting and feed reads fast — < 500ms (target <200ms for the feed read path).
AvailabilityHighly available, prioritized over consistency.
ConsistencyEventual is fine — up to ~1 minute of post staleness is acceptable.
Scale~2B users, unlimited follow relationships, including celebrities with tens of millions of followers.
Read/write ratioRead-heavy. Feeds are viewed far more often than posts are created.

Capacity Estimation

Only compute the numbers that change a decision. Here, two numbers matter: the cost of precomputing feeds (does it even fit?), and the write amplification of the worst-case poster (what breaks?).

Can we precompute feeds for everyone?

  • Store ~200 recent post references per user, ~2KB total per feed.
  • 2KB × 2B users ≈ 4TB.[1] That's trivially cheap on modern infra (a fraction of a cent per user per month). Implication: precomputation is affordable — the constraint is write cost, not storage.

What is the write cost of a single post?

  • An average user posts → fan out to a few hundred followers. Cheap.
  • A celebrity with 90M+ followers posts → fan out to 90M feeds in one shot.[1] Implication: a single post can trigger tens of millions of writes — this is the bottleneck the whole design must answer.

Core Entities & API

Three entities. Note that Follow is a uni-directional edge — modeling it as a directed graph is what later lets you query "who follows X" cheaply.

EntityShape
UserAn individual account.
FollowDirected edge: (followerId → followedId).
PostAuthor-created content with id, authorId, body, createdAt.

Derive the acting user from the auth token, never from the body.

EndpointPurpose
POST /v1/postsCreate a post. Body: { body, media? }; author from token.
POST /v1/followFollow a user. Body: { followedId }.
GET /v1/feed?cursor=&pageSize=Read the feed. Returns { items: Post[], nextCursor }.[1]

Note the feed uses a cursor, not an offset. That choice gets its own deep dive below — it's not cosmetic.

High-Level Design

Trace each request through the boxes. Keep it simple by default; the cleverness belongs in the deep dives, not in the HLD.

ComponentResponsibility & store
Post ServiceStateless service behind the API gateway. Writes posts to the Post Store (e.g. DynamoDB/Cassandra, keyed by postId).[1]
Follow Service + graphStores the follow edges. Partition key follower, sort key followed, plus a GSI on followed for the reverse lookup ("who follows X").[1]
Feed ServiceServes GET /feed. Returns a precomputed feed (the common case) and merges in recent celebrity posts at read time (the hybrid).
Fan-out workersConsume a queue (e.g. SQS/Kafka) of new-post events and append the post into each follower's precomputed feed.[1]
Feed cacheRedis holding the materialized per-user feeds for fast reads.

Write path: POST /posts → Post Store → emit event to queue → fan-out workers append postId to each follower's feed. Read path: GET /feed → Feed Service reads the user's precomputed feed from cache → hydrates post bodies → returns a page.

Deep Dive 1 — Fan-out on write vs. fan-out on read

This is the heart of the problem. "Fan-out" = the work of getting one post in front of N followers. The only question is when you do it: at write time (push) or at read time (pull).

Fan-out on read (pull)

Store nothing extra. When a user opens their feed, look up everyone they follow, gather each one's recent posts, merge, and sort by timestamp.[1] Writes are trivial — one insert. Reads are brutal: a user following 1,000 accounts fans a single read into 1,000 sub-queries, then an in-memory merge — all inside your <500ms budget.

Fan-out on write (push)

When a post is created, immediately append its postId into every follower's precomputed feed (via the queue + workers).[1] Reads become a single lookup of an already-assembled list — blazing fast, which is exactly what a read-heavy system wants. The cost moves to write time and to storage (the 4TB we sized above — cheap).

DimensionFan-out on write (push)Fan-out on read (pull)
Read latencyFast — one list lookupSlow — N lookups + merge
Write costHigh — write to N feedsCheap — one insert
Write amplification1 post → N writes1 post → 1 write
StorageHigher (materialized feeds)Minimal
Worst caseCelebrity posts (90M writes)Heavy followers (1000s of reads)
Best forRead-heavy, normal fan-outInactive users / huge authors

Why neither alone wins. Push gives the latency we need but detonates on celebrities. Pull stays cheap on writes but blows the read budget for active users. The distribution of follower counts is bimodal — billions of normal users, a handful of huge ones — so a single uniform strategy is wrong by construction.

Deep Dive 2 — The hybrid (the staff answer)

The judgement call: push for normal users, pull for celebrities. Don't fan out a celebrity's post to 90M feeds. Instead, flag high-follower accounts in the Follow table, skip precomputation for them, and merge their recent posts in at read time.[1]

  1. On post: if the author is below a follower threshold → fan out on write (push to all follower feeds). If above → do not fan out; just store the post.
  2. On read: load the user's precomputed feed, then look up the small set of celebrities this user follows, pull their recent posts, and merge-sort the two streams.

The merge is cheap because a user follows few celebrities — the expensive list (their normal follows) is already materialized, and the small list (celebrities) is gathered live.

★ Staff-level signal The senior says "use a hybrid." The staff candidate explains why the threshold exists at all: it's a knob set by the follower-count distribution, not dogma. They say out loud, "Push is correct until write amplification exceeds the read cost it saves — which happens precisely at celebrity scale, so I move that tail to pull." They name the celebrity fan-out as the real bottleneck, size it (90M writes per post), and design the system around that tail rather than the average case. Treating the threshold as a tunable tradeoff — and admitting you'd measure it in production rather than hard-code it — is the move.

Deep Dive 3 — Ranking & pagination

Ranking: recency, then signals

The MVP feed is reverse-chronological — merge by createdAt descending. Real feeds rank by a score: recency × affinity × engagement-prediction × content-type weights. The interview move is to separate generation (which posts are candidates — the fan-out problem) from ranking (how to order the candidates — an ML scoring pass on a few hundred items). Keep ranking out of the hot write path; score the small candidate set at read time.

Pagination: cursor, not offset

The feed is a constantly-growing list, so OFFSET-based paging is wrong: new posts arriving between page loads shift every item, causing duplicates and skips, and deep offsets force the store to scan-and-discard. Use a cursor — an opaque token encoding the timestamp/id of the last item seen.[1] Each page says "give me items older than this cursor," which is stable under inserts and a cheap indexed range scan.

CursorOffset
Stable under new postsYesNo — items shift
Deep-page costConstant (indexed seek)Grows (scan + discard)

Deep Dive 4 — Caching feeds & the hot-key celebrity

Caching the feeds

Hold materialized feeds in Redis with a long TTL and LRU eviction, so the common read never touches the database.[1] Feeds are the perfect cache citizen — read constantly, written by the fan-out workers, and tolerant of staleness (we already accepted ~1 min).

The hot-key problem

A viral post is read by millions at once. In a sharded cache, every post lives on exactly one node, so a single viral postId hammers one shard while the rest sit idle — a hot key.[1]

ApproachBehaviorVerdict
Sharded cacheEach post on one node — viral post melts that shard.Hot key
Replicated cacheEvery node can serve any post; load balancer spreads reads across all N.[1]Great

With replication, a viral post's read traffic is spread across all N instances instead of one shard.[1] The tradeoff: a cold viral post can cause N initial misses (N DB reads instead of 1) — a tiny, one-time cost in exchange for massively higher steady-state throughput.

★ Staff-level signal Notice that celebrity fan-out (write side) and the hot-key viral post (read side) are the same phenomenon — extreme skew — attacked from two ends. Staff candidates connect them: pull-on-read handles skew at write time; cache replication handles skew at read time. Recognizing that both bottlenecks come from the long tail of the popularity distribution, and that you solve each on its own side, is the unifying insight.

Check yourself — retrieval practice

Answer from memory before scrolling back up.

1. Why is pure fan-out on write a poor fit for celebrity accounts?

Storage is cheap (~4TB). The killer is write amplification: one celebrity post → 90M+ feed writes.

2. What is the hybrid feed strategy that staff candidates arrive at?

Normal authors are precomputed (push); celebrity posts are pulled live and merged in — driven by the follower distribution.

3. Why use a cursor instead of an offset for feed pagination?

Offsets shift when new posts arrive (duplicates/skips) and scan-and-discard at depth; cursors are stable and indexed.

4. How does a replicated cache beat a sharded one for a viral post?

Sharding pins a hot key to one node; replication lets every node serve it, so the load balancer spreads the storm.
