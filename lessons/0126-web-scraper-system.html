Design a Web Scraper at Scale

A distributed system that crawls millions of pages while respecting robots.txt, managing IP reputation, and handling failures gracefully.

Why this lesson, for your mission: Web crawlers are a masterclass in distributed systems under adversary conditions: the internet is unreliable, servers block scrapers, and scale compounds every problem. The staff move is recognizing that this is a graph traversal problem wrapped in a rate-limiting and fault-tolerance system. You trade crawl freshness for robustness, design for cascading failures, and learn which corners are safe to cut. The same patterns apply to indexing, data pipelines, and any system that consumes untrusted external data at scale.

Phase 1 · 0–5 minClarify the problemPin what you're crawling and how fresh the data must be.

Ask before you design

  • "What domain(s) are we crawling — specific sites, or open internet?" — Crawling specific sites is simpler (known robots.txt, lower diversity). Open internet requires scale and politeness discipline.
  • "How fresh must the data be — daily, weekly, or yearly?" — Freshness drives crawl frequency and conflict with politeness. Every re-crawl risks IP blocking.
  • "What do we extract — full HTML, just text, or metadata (title, links)?" — Storage and bandwidth scale with extraction complexity.

Phase 2 · 5–10 minEstimate what mattersPage count, crawl frequency, and network throughput.

Capacity Estimation

Page count and crawl depth

~100B pages indexed (Google-scale order of magnitude). Average 10 MB per domain; unique domains: ~10B. Implication: you can't crawl everything; prioritize by popularity (Alexa rank, link count).

Crawl frequency

Re-crawl active sites every 30 days. 100B pages ÷ 30 days ≈ ~3.3B crawls/day ≈ ~40k pages/sec. At ~500 ms per page (HTTP + parse), you need ~20k concurrent workers (20k × 500 ms = 10k seconds to fetch 20k pages). Implication: horizontal parallelism is mandatory.

Storage and bandwidth

Average page: 50 KB (HTML + assets not stored, just indexed). 3.3B × 50 KB ≈ 165 TB/day crawled. If you store only metadata (title, URL, links): ~1 KB per page ≈ 3.3 TB/day index growth. Implication: compress and deduplicate aggressively.

Interviewer pushback

"Isn't crawling 40k pages/sec against robots.txt?"

Staff answer: No. Rate limits are per domain, not global. If you crawl 10B domains at < 1 page/sec each, you reach 10B pages/sec in aggregate. Respect robots.txt and User-Agent conventions; the rate limit is the bottleneck, not the global throughput.

Say to move on → "With 40k pages/sec and rate limits per domain, I'll model the frontier and storage."

Staff answer: Partition by domain hash. Each crawler reads from its shard, respecting the per-domain rate limit. If a crawler crashes, the domain is reassigned to another; Kafka or a distributed queue handles rebalancing.

High-Level Design

The crawler is a distributed, stateless pipeline. URLs are partitioned by domain and queued in Kafka. Crawlers are stateless workers that pull from a partition, check the domain's robots.txt (cached in memory or Redis), wait for the per-domain rate limit, fetch the page, and extract links. New URLs are re-enqueued; visited URLs are cached in a content-addressed store (RocksDB or DynamoDB) for deduplication. Pages are stored in S3 daily, indexed in Elasticsearch, and queryable via an API.

The system is designed for fault tolerance: if a crawler crashes, Kafka rebalances the partition to another worker, and the URL remains in the frontier for retry. Checkpointing (e.g., every 10k URLs processed) avoids re-crawling on restart.

Interviewer pushback

"What if a domain is down for a week?"

Staff answer: URLs are retried with exponential backoff. After 3 failures, the URL is moved to a "dead letter" queue and retried less frequently (e.g., weekly). The frontier prioritizes live domains to maximize crawl coverage.

Say to move on → "The pipeline is stateless and fault-tolerant. The hard parts are politeness, deduplication, and IP reputation."

Phase 5 · 27–47 minDeep dives & tradeoffsPoliteness, deduplication, and failure recovery.

Deep Dives

Deep Dive 1 — Politeness: robots.txt and rate-limiting

Crawlers must be "good citizens." Respect three rules: (1) check robots.txt for /disallow and /crawl-delay, (2) identify via User-Agent, (3) limit to ~1 request/second per domain.

Implementation:
  • Cache robots.txt per domain (TTL 30 days); fetch on first crawl of a domain
  • Per-domain token bucket: refill at 1 token/sec; each fetch costs 1 token
  • User-Agent header includes company name and contact (e.g., "MyBot/1.0 (http://example.com)")>
  • If you hit a 429, 503, or robots.txt /disallow, back off exponentially
  • Respect Retry-After header if present

An IP that crawls too aggressively gets blocked (HTTP 403 or 429). Mitigation: rotate IPs using a pool of residential/datacenter proxies, monitor for blocks, and use exponential backoff. If blocked, skip that domain for 24 hours.

Deep Dive 2 — Deduplication: avoiding re-crawls

The frontier can have millions of URLs pointing to the same page (via redirects, different query strings, canonical tags). Store a content hash (SHA256 of the page HTML) in a distributed cache (RocksDB or DynamoDB). Before fetching, check: if the hash exists and is recent, skip the fetch. This saves bandwidth and respects rate limits.

Deep Dive 3 — Handling redirects and soft errors

A URL may redirect (301, 302, etc.). Follow up to 5 redirects; if a loop is detected, drop the URL. Soft errors (timeouts, 503) are retried with exponential backoff; hard errors (404, 410) are dropped after one retry.

Deep Dive 4 — URL prioritization and frontier freshness

Not all pages are equally important. Prioritize by domain popularity (PageRank, inbound links, Alexa rank) and freshness (last crawled date). The frontier uses a priority queue per partition: high-PageRank domains are dequeued first.

Deep Dive 5 — Handling JavaScript-rendered pages

Modern sites render content in JavaScript; plain HTTP GET returns a skeleton. Two approaches: (1) use a headless browser (Chromium/Puppeteer) for a small fraction of pages, or (2) rely on APIs if available. Headless rendering is 10–100× slower, so use only for known high-value domains.

★ Staff-level signal A senior engineer designs a basic crawler with rate limits. A staff engineer recognizes that politeness is the load-bearing architecture, not an afterthought. They identify deduplication as the key to respecting rate limits (crawl fewer pages by avoiding duplicates) and model the per-domain token bucket before coding anything. They call out IP reputation and rotation without prompting, know robots.txt caching is load-bearing (if you fetch it every time, you hit a 1:1 fetch:robots check ratio), and design for cascading failures (if one domain gets blocked, the system self-heals by deprioritizing it).

Interviewer pushback

"How do you avoid crawling the same page twice across crawlers?"

Staff answer: Partitioning by domain hash ensures each domain is assigned to one crawler at a time. Kafka rebalancing on crawler crash reassigns partitions; the new crawler reads from the same frontier and sees unprocessed URLs. Content dedup (hashing) removes near-duplicates globally.

Legal & Ethics

Check the site's Terms of Service and robots.txt. Identify as a crawler (User-Agent); include a contact URL. Respect copyright; never republish full content. Honor Do-Not-Track and Similar signals (via User-Agent opt-out). In GDPR/CCPA jurisdictions, honor deletion requests (e.g., via robots.txt).

2 · Closing Summary (60 seconds)

The crawler is a distributed, stateless pipeline that respects per-domain rate limits, caches robots.txt, and deduplicates via content hashing. Kafka partitions by domain hash; workers are stateless and fault-tolerant. Politeness is the architecture: token buckets enforce rate limits, IP rotation avoids blocks, and exponential backoff handles transient failures. At 10×, add crawlers and domain partitions; the design scales linearly. The hard part is sustaining crawl coverage over years without getting IP-banned, which requires constant monitoring and politeness discipline.

Check yourself — retrieval practice

Answer from memory before scrolling back up.

1. Why partition the URL frontier by domain hash rather than round-robin?

Per-domain rate limiting requires that a single crawler handles a domain's URLs (no interleaving). Hash partitioning ensures this: domain A always goes to partition 1, domain B to partition 2, etc. Round-robin would split a domain across crawlers, breaking rate limiting.

2. What is the primary benefit of content-hash deduplication?

If 10 different URLs point to the same page (via mirrors, redirects, or copy-pasta), content dedup detects this via SHA256 and skips the re-fetch. This saves bandwidth and respects per-domain rate limits.

3. How should the crawler respond to a 429 Too Many Requests?

429 means you're rate-limited. Back off exponentially, read the Retry-After header, and pause the domain. If you get 429 repeatedly, the domain is hostile; deprioritize for a day. This preserves IP reputation.

4. Why cache robots.txt instead of fetching it for every domain?

robots.txt is rarely updated. Caching it (TTL 30 days) means you fetch once, not once per crawl. This reduces requests and respects rate limits. If you fetched it every time, you'd hit a 1:1 ratio of robots.txt:crawl requests, which is inefficient.
