Deep Dive: Distributed SQL (Spanner / CockroachDB)

Relational tables, ACID transactions, and SQL — but spread across hundreds of nodes and multiple regions without giving any of it up.

Why this lesson, for your mission: The classic interview reflex is "need scale → drop SQL, go NoSQL, accept eventual consistency." Distributed SQL breaks that reflex: you can keep ACID and joins and shard horizontally. At L6/L7 the signal is knowing how that's possible — per-range consensus, distributed 2PC, and a clock trick (TrueTime / HLC) — so you can reach for it deliberately when a workload genuinely needs both strong consistency and horizontal scale, and reject it when a cheaper design wins.

1 of 7

Why NewSQL exists

For a decade the scaling story had two unhappy ends. Single-node SQL (Postgres, MySQL — Lesson 89) gives you ACID transactions, joins, and a real query language, but one primary can only hold so much data and serve so many writes; you scale it by sharding manually in the application, and the moment a transaction spans two shards you lose atomicity. NoSQL (Dynamo, Cassandra) scaled writes horizontally by giving up the things that made SQL pleasant: multi-key transactions, secondary indexes, joins, and often strong consistency.[1]

Distributed SQL (the "NewSQL" category) refuses the tradeoff. The goal: a relational, strongly-consistent, transactional database that scales out by adding nodes, with the database — not your application code — handling the sharding, replication, and cross-shard transactions.[1][2]

Internals — how it actually works

Both Spanner and CockroachDB are built from the same three layers. Understanding them is the whole game.

1. Data is split into ranges (tablets), and the splits are automatic

The full key space is sorted and chopped into contiguous chunks. Spanner calls them splits / tablets; CockroachDB calls them ranges (~512 MB each by default).[2] Because the keys stay sorted, range scans and ORDER BY are cheap — this is range-based sharding (Lesson 05), not hash sharding. When a range grows too big or too hot, the system splits it and rebalances pieces across nodes automatically. The application never picks a shard key by hand.[2]

2. Each range is replicated by a consensus group

Every range is stored on (typically) 3 or 5 replicas, and those replicas form a consensus group. Spanner uses Paxos; CockroachDB uses Raft — different algorithms, same job: agree on an ordered log of writes so a majority always shares the same committed history.[1][2] One replica is the leader (Raft leader / Paxos leader); writes go through it, get appended to the log, and commit once a majority (quorum, Lesson 06) acknowledges. This buys two things at once:

  • Strong consistency — the quorum agrees on every write's order before it commits.
  • High availability — lose a minority of replicas and the range keeps serving; a new leader is elected automatically.[2]

Note the scope: consensus is per range, not per cluster. A 1,000-node cluster runs thousands of independent Raft/Paxos groups in parallel — that's what lets writes scale instead of funneling through one log.[2]

3. Cross-range transactions use two-phase commit (2PC)

A transaction touching one range is easy: the range's consensus leader orders it. But a transaction that spans multiple ranges (transfer money from account A on range 1 to account B on range 9) needs atomicity across independent consensus groups. The solution is two-phase commit layered on top of consensus: a coordinator runs PREPARE across every participating range, each range durably consensus-commits its intent, and only after all vote yes does the coordinator send COMMIT.[1][2]

Why 2PC isn't fragile here. Classic 2PC's weakness is the coordinator crashing mid-commit and blocking everyone. In distributed SQL the coordinator's state and each participant's vote are themselves stored in consensus-replicated ranges — so a crashed coordinator is recovered by its own Raft/Paxos group and the transaction still resolves. 2PC handles atomicity; consensus handles durability of the 2PC state.[2]

The clock problem — TrueTime vs HLC

To behave like a single database, the system needs external consistency (a.k.a. linearizability / strict serializability): if transaction T1 commits before T2 starts in real time, every observer must see T1's effects before T2's. Achieving that across machines means agreeing on the order in time of commits — and machine clocks drift. This is where Spanner and CockroachDB diverge.[1][3]

Spanner — TrueTimeCockroachDB — HLC
Idea Clocks backed by GPS + atomic clocks expose time as an interval [earliest, latest] with bounded uncertainty ε.[3] Hybrid Logical Clock = wall-clock time fused with a logical counter; no special hardware.[2]
Commit trick Commit wait: after picking a commit timestamp, deliberately wait out the uncertainty ε (a few ms) so no later transaction can claim an earlier time.[3] On a read that hits uncertain data, restart the transaction at a higher timestamp (uncertainty restart) within a bounded max-offset window.[2]
Guarantee External consistency globally, even across continents.[3] Serializable isolation; single-key linearizable, slightly weaker cross-key ordering guarantees.[2]
Cost Requires Google's GPS/atomic-clock infrastructure. Runs on commodity hardware / any cloud.

The headline: Spanner buys correctness by waiting (commit wait spends the clock uncertainty up front); CockroachDB buys deployability by occasionally retrying (it tolerates commodity clocks by restarting transactions that read inside the uncertainty window).[2][3]

How does Spanner's TrueTime give external consistency on top of clocks that drift?

Commit wait deliberately sleeps for the uncertainty interval ε so no later transaction can claim an earlier real-time order.

Reread the "Commit trick" row for Spanner — what does it do after picking a timestamp?

Why would skipping commit wait break external consistency, even though the clock uncertainty ε is often just a few milliseconds?

External consistency requires that real-time order matches commit-timestamp order. Uncertainty ε means two nearby timestamps could overlap in real time; waiting it out guarantees separation.

Think about two transactions committing within ε of each other, and what "external consistency" promises about their real-time order.

What is the fundamental tradeoff CockroachDB makes by using HLC and uncertainty restarts instead of TrueTime?

Spanner pays a fixed small wait on every commit using expensive hardware; CockroachDB avoids that hardware but occasionally retries transactions that land inside the uncertainty window.

Tradeoffs — and when (not) to reach for it

Nothing is free, and the price of "ACID at scale" is concrete and worth naming:

CostWhy it happens
Higher write latencyEvery write needs a consensus round trip to a majority of replicas — often cross-AZ or cross-region. Single-node Postgres commits locally; here you pay quorum latency on every commit.[2]
Expensive cross-range txnsMulti-range transactions add 2PC coordination on top of consensus — more round trips, more contention. Keeping related data in one range (locality) is a real design lever.[2]
Write hotspotsSequential keys (auto-increment IDs, timestamps) all land on the newest range → one leader takes all writes. Fix: hash-prefix or UUID keys to spread load.[2]
Operational/cost weight3–5× storage from replication; Spanner needs Google infra, CRDB needs careful topology tuning.
Reach for distributed SQL when:
  • You genuinely need multi-row ACID transactions AND horizontal scale — payments, ledgers, inventory, orders.
  • You need strong consistency across regions (a global bank balance, not eventual).
  • You're outgrowing a single Postgres primary but refuse to hand-roll sharding + cross-shard txns.
Do NOT reach for it when:
  • A single Postgres/MySQL primary (with read replicas) still fits — it's simpler and lower-latency. Don't pay consensus tax you don't need.
  • The workload is append-heavy / eventually-consistent-friendly (feeds, logs, metrics) — Cassandra/Dynamo is cheaper and faster.
  • You need the absolute lowest single-row write latency — local commits beat quorum commits.
Check before continuing

Which workload is the WEAKEST fit for reaching for distributed SQL?

Append-heavy, eventually-consistent workloads are cheaper and faster on Cassandra/Dynamo — paying the consensus tax buys nothing here.

Why do sequential keys like auto-increment IDs create a write hotspot in a range-sharded distributed SQL system?

Because ranges are sorted by key, monotonically increasing keys keep appending to the same range, funneling all writes through that range's one leader.

Staff-level signal

★ Staff-level signal A senior says "let's use Spanner, it scales." A staff candidate frames it as a deliberate tradeoff: "This ledger needs cross-account ACID and is going multi-region, so I'll accept ~10ms quorum write latency to keep one strongly-consistent store instead of hand-rolling sharding plus 2PC in the app." The deeper signal is knowing the mechanism — per-range Raft/Paxos for consistency+HA, 2PC for cross-range atomicity, TrueTime/HLC for external consistency — and the limits: calling out the sequential-key hotspot and proposing hashed keys before the interviewer does, and being willing to say "actually, a single Postgres primary still fits here — distributed SQL would be over-engineering." Reaching for the powerful tool and knowing when not to is the judgement they're testing.

In the interview

How this earns points in a design loop:

  1. Trigger it from an NFR, not a buzzword. "Orders need multi-item atomicity and we're multi-region → this is a distributed-SQL case, not a Cassandra case."
  2. Name the mechanism in one breath. "Each range is Raft-replicated for consistency and HA; cross-range order transactions use 2PC over those groups."
  3. Pre-empt the hotspot. "Order IDs are sequential, so I'll hash-prefix the key to avoid hammering one range's leader."
  4. Show restraint. "If this were single-region and fit one primary, I'd use plain Postgres — distributed SQL only earns its latency cost at this scale."

When to choose Spanner-style SQL vs. the alternatives

Pulling the tradeoffs and mechanisms together: the decision is never "distributed SQL is better than NoSQL." It's "does this workload need multi-key ACID and horizontal scale at the same time." If yes, and the consensus/2PC/clock costs above are acceptable, distributed SQL wins. If the workload can tolerate eventual consistency or never needs multi-key transactions, a cheaper system wins instead.[1][2]

Every capability in this lesson (consensus, 2PC, TrueTime/HLC) has a latency or complexity cost. The right lens is "does the workload need what only this combination provides," not raw capability.
