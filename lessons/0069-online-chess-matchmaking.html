Design Online Chess + Matchmaking (chess.com / lichess)

Two players, one board, sub-second moves — the design lives in pairing strangers by skill, then running an authoritative session that no one can cheat.

Why this lesson, for your mission: Online chess is the canonical "real-time turn-based multiplayer" interview, and it doubles as the generic matchmaking problem. At L6/L7 the bar is not "draw a chat server for moves" — it is to separate the matchmaking control plane from the game data plane, run an authoritative server so move validation and anti-cheat can't be bypassed, and pick the right pairing strategy (Elo buckets + a widening queue) under a latency constraint. Get the authority boundary and the matchmaking widening right and the rest is detail.

Phase 1 · 0–5 minClarify the problemPin scope and the few NFRs that will drive every later decision.

Ask before you design

  • “Which time controls — bullet, blitz, correspondence?” — Bullet makes latency and clock fairness critical.
  • “How should matchmaking trade speed against rating accuracy?” — That's the widening-window policy.
  • “Is cheat detection in scope?” — Engine analysis adds a heavy async pipeline.

Functional Requirements

Scope tightly. State the four core capabilities and explicitly defer the rest (chat, puzzles, tournaments, video).

#Users should be able to…
1Find / request a match against a similarly-skilled opponent for a chosen time control (blitz/rapid).
2Play a live game: exchange validated moves in real time with a shared clock.
3Spectate an in-progress game and see moves as they happen.
4See leaderboards / ratings updated after games complete.

Out of scope (say so out loud): in-game chat, puzzles/lessons, bracket tournaments, friend invites, and bot/engine opponents. We design the 1v1 ranked path; everything else reuses it.

Non-Functional Requirements

The "-ilities" drive every decision below. Lead with move latency and with consistency, because this is a game where a single wrong-trusted byte is a cheat.

Phase 2 · 5–10 minEstimate what mattersOnly the numbers that change a decision — say the implication out loud.

Capacity Estimation

Estimate only what changes the design. For a turn-based game the load-bearing numbers are concurrent connections and moves/sec, not storage — a whole game is tiny.

  • Concurrent connections (the big one): ~1M concurrent players ⇒ ~1M open sockets and ~500K live games. A single game server can comfortably hold tens of thousands of lightweight sockets, so you need on the order of tens to a few hundred game servers — and a way to find which one owns a given game.
  • Move rate: in blitz a player moves every ~2–5s; ~1M players ⇒ very roughly 200K–500K moves/s at peak. Each move is a handful of bytes, but each must be validated server-side and fanned out to opponent + spectators.
  • Spectator fan-out: a popular game (top streamer) can draw 100K+ concurrent watchers. One move on that board becomes 100K+ pushes — the fan-out, not the move, is the cost. This is why spectating gets its own deep dive.
  • Storage (small): a full game ≈ the move list in algebraic notation, ~40–80 moves ≈ <1 KB. Even 1B archived games is single-digit TB — storage is a non-issue; replayability is the reason to store moves, not space.

Implication: the design's difficulty is in the connection/session tier and the matchmaking tier, not the database. Persist the move log (not per-move board snapshots) so any state can be rebuilt by replay.

Phase 3 · 10–17 minAPI & data modelLock the contract and the storage shape before drawing boxes.

Core Entities & API

Entities: User (with a rating/Elo), Game (two players, time control, status, result), Move (the append-only log: ply number, SAN/UCI, clock left), and a transient MatchTicket (a player waiting in the matchmaking queue). Spectators are not stored; they're subscribers.

Gameplay is bidirectional and latency-sensitive, so the hot path is a persistent WebSocket. REST is reserved for things that are fine to pull on demand: requesting a match, fetching history, reading leaderboards. The user is always derived from the auth token, never passed in the body.

Data Model

The durable truth is tiny: a game row plus an append-only move log keyed by (game_id, ply), from which any position, clock and result can be rebuilt. The primary key on (game_id, ply) also makes a duplicate or out-of-turn write impossible. High-Level Design

The defining move is separating two planes beginners conflate: the matchmaking control plane (pairing strangers, runs occasionally per player) and the game data plane (the live authoritative session, runs many times per second). They scale differently and fail differently.

Phase 5 · 27–47 minDeep dives & tradeoffsGo deep where the system breaks; compare alternatives and justify the pick.

Deep Dives

1. Real-time moves + the authoritative game-server session

Polling for the opponent's move every second is the senior-level wrong answer — it adds latency and floods the server with empty checks. The right primitive is a WebSocket over TLS per player: one bidirectional connection the server can push down the instant a move is validated. Both players in a game connect to the same game server — a sticky session — because the live board lives in that server's memory; bouncing requests across boxes would mean no single owner of the truth.

That truth ownership is the whole point: the game server is authoritative. The client UI is a renderer and a predictor, never the referee. When Alice sends makeMove, the server checks it against the in-memory board (legal piece move? her turn? not in check after?), and only then does it apply it, append it to the move log, and broadcast moveApplied. A move claimed by the client is never trusted on its word — that is the line between a game and an exploit. Clock enforcement is server-side too: the server, not the client, decides a flag fall.

For availability, the in-memory board must be rebuildable. Because we persist an append-only move log, a crashed game's state is just a replay of its moves; on reconnect a client fetches GET /v1/games/{id} to re-sync, and a failed server's games can be rehydrated on a replacement from the log. We persist the log, not snapshots, because chess state is fully determined by its moves and the log is tiny.

★ Staff-level signal The single most important sentence: "The server is authoritative; the client is a renderer." Everything cheat-related follows from drawing that boundary correctly — legality, turn order, clock, and result are decided server-side, and the client may predict for responsiveness but must reconcile to server truth on moveRejected. A senior says "validate moves"; a staff engineer names where authority lives, why sticky sessions are a consequence of in-memory authority (not an arbitrary choice), and how the durable move log makes a stateful server tolerant of crashes without trusting the client. Anti-cheat for engine assistance (statistical move-quality analysis) is then an offline layer on top — out of the hot path.

2. Skill-based matchmaking: Elo buckets + a widening queue

This is the generic multiplayer matchmaking problem. A player enters the queue with a rating R, a region, and a time control. Naively scanning all waiting players for the closest rating is O(n) per match and doesn't scale. Instead, partition the waiting pool into Elo buckets (e.g. 100-point bands) per (region, time control), stored as Redis sorted sets keyed by rating so a range query is cheap.

  • Pairing loop: for a ticket at rating R, query the bucket for any other waiting ticket within ±Δ of R; if found, pop both atomically and create the game.
  • Widening over time: start with a tight Δ (say ±50) for a good match; if no opponent after a few seconds, widen Δ (±100, ±200, …). This trades match quality for wait time — the core matchmaking knob. The longer you've waited, the worse a match you'll accept.
  • Latency-aware: prefer opponents in the same region so move RTT stays low; only cross regions once Δ and wait have grown. Region is part of the bucket key, not an afterthought.
  • Fairness / abuse: the atomic pop (Lua / ZPOPMIN-style) prevents two matchers from grabbing the same opponent (double-booking). Cancelling removes the ticket; a TTL reaps abandoned tickets.

Note the asymmetry with gameplay: matchmaking runs once per player per game (low rate, can tolerate hundreds of ms), while moves run many times a second. That's why it's a separate service with its own store — and why it's fine for it to be a touch slow.

★ Staff-level signal State the explicit tradeoff out loud: match quality vs. queue time, controlled by a Δ that widens with wait. A senior describes "match similar players"; a staff engineer frames matchmaking as a search over a sorted structure with a time-decaying acceptance window, calls out the atomic-pop race that prevents double-booking, and notes that latency/region is a first-class bucket dimension — not something you bolt on after rating. Bonus signal: recognizing this is the same shape as ride-matching or ad-auction queueing, so the pattern transfers.

3. Spectating: read-only fan-out

Players are a fixed pair; spectators are an unbounded, bursty crowd (100K+ on a marquee game). You must not let spectator load slow the players' move path. The fix is a classic fan-out over pub/sub: the authoritative game server publishes each moveApplied to a topic for that gameId; spectator connections (held on separate, horizontally-scaled fan-out/edge servers) subscribe and receive the broadcast. Spectators are read-only — they can never send makeMove — so they never touch authority.

  • Bootstrap then stream: a joining spectator first pulls the move log via GET /v1/games/{id} to render the current board, then subscribes to receive subsequent moves — the same "snapshot + tail" pattern as live comments (Lesson 24 [3]).
  • Decouple from players: the player game server fans out one message to the bus; edge servers multiply it to thousands of watchers. The board's hot path does O(1) work regardless of audience size.
  • Acceptable lag: spectators can tolerate a few hundred ms of delay (and platforms often add a deliberate delay to deter cheating-by-spectator), so this path can be at-most-once and best-effort, unlike the players' guaranteed move exchange.

4. Leaderboards + game-state / move-history storage

When a game ends (checkmate, resign, timeout, draw), the game server emits a game-finished event. Two consumers act on it:

ConcernMechanism
Ratings + leaderboardThe leaderboard service computes the Elo delta for both players and updates ranked structures (Redis sorted sets / a ranked store). This is its own well-trodden problem — delegate to Lesson 47 rather than redesigning ranking here [2].
Move history / replayThe durable append-only move log already written during play is finalized as the archived game. Storing moves (SAN/UCI) — not board snapshots — keeps a full game under ~1 KB and makes replay, analysis, and reconnect trivial: rebuild any position by replaying plies.
Result integrityBecause results derive from the authoritative server's validated move log (not a client claim), ratings can't be gamed by reporting a fake win — anti-cheat and storage share the same source of truth.

This is also why we resisted snapshotting board state per move: it's redundant. The move log is the compact, replayable, tamper-evident record that serves reconnect, spectating bootstrap, history, and rating — one structure, four jobs.

Privacy

Low sensitivity data, but still personal: usernames, ratings, game history, IP addresses used for fair-play analysis, and chat (out of scope). Public by design: games and ratings of public accounts are public. Minimization: IP/device signals retained for a limited window for anti-cheat, then aggregated. Wrap-up · 58–60 minClose strongRecap decisions and tradeoffs in 60 seconds; name what you would do next.

Closing Summary (60 seconds)

Online chess separates matchmaking from live game sessions. Players enter a matchmaking queue bucketed by rating and time control, and the acceptable rating window widens with wait time to trade match quality for queue time. Each game runs on a sticky, authoritative server that validates moves and clocks and relays them over WebSockets. Every move appends to a durable log, so a crashed server's games can be replayed elsewhere. Spectators subscribe read-only, and ratings update from results. At 10× we add game servers and partitions.

Check yourself — retrieval practice

Answer from memory before scrolling back up.

1. Why must the game server be authoritative over moves rather than the client?

The client renders and predicts; the server decides legality, turn, clock, and result so it can't be exploited.

2. How does the matchmaking queue keep matches fair without long waits?

Tight Δ first for quality; widen Δ over time to bound wait — match quality vs. queue time is the knob.

3. Why is spectator fan-out handled on pub/sub, separate from the players' path?

Spectators are unbounded and read-only; fan-out via the bus keeps the players' hot path O(1).

4. Why persist an append-only move log instead of per-move board snapshots?

Chess state is fully determined by its moves; a <1 KB log serves reconnect, replay, history, and rating.
