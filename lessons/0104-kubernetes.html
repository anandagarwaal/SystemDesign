Deep Dive: Kubernetes

Declare the state you want; let a reconciliation loop fight entropy on your behalf — and know when that machinery is worth its operational tax.

Why this lesson, for your mission: At L6/L7 you rarely have to configure Kubernetes on a whiteboard — but you must reason about it like a platform. The interviewer wants to hear that you understand the one idea that makes K8s tick (declarative desired state driven by reconciliation loops), where the single source of truth lives (etcd), how self-healing and rolling deploys fall out of that loop for free, and — the staff move — when the operational complexity is not worth it versus serverless or a managed PaaS.[1]

1 of 5

What it is

Kubernetes (K8s) is an open-source container orchestrator: it runs and manages containerized workloads across a fleet of machines so you treat the cluster as one pool of compute rather than naming individual servers.[1] It descends directly from Google's internal cluster manager, Borg, whose central lessons — pack many workloads densely onto shared machines, give every task a stable identity, and let a controller keep things running — are baked into its design.[2] If you haven't met the unit it schedules, read Lesson 105 · Docker & Containers first; K8s assumes you already have images.

The defining idea is declarative, desired-state management. You don't issue imperative commands ("start three copies, now start a fourth"). You submit a manifest that says "I want 3 replicas of this image, reachable on port 80," and Kubernetes continuously works to make reality match that declaration.[3] You describe the destination; the system figures out the steps and re-derives them whenever something drifts.

The control plane: brains of the cluster

Every cluster splits into a control plane (makes global decisions) and a set of worker nodes (run the workloads).[4] Four control-plane components matter:

ComponentJob
API serverThe single front door. All reads/writes go through its REST API; it validates and persists every object.[4]
etcdThe consistent key-value store that holds all cluster state — the single source of truth.[5]
SchedulerWatches for Pods with no node assigned and picks the best node based on resources and constraints.[4]
Controller managerRuns the controllers — the loops that drive actual state toward desired state.[4]

etcd is the centre of gravity. It is a distributed key-value store that uses the Raft consensus algorithm for strong consistency, so a majority quorum agrees on every write.[5] Lose etcd and you lose the cluster's memory; this is why it's run as an odd-sized replicated cluster and backed up. (The consensus machinery underneath is the same family covered in Lesson 106 · ZooKeeper & etcd.) Crucially, components don't talk to etcd directly — only the API server does.[4]

Check before continuing

What is Kubernetes's core operating model?

You declare desired state in a manifest; controllers continuously drive actual state toward it.

Reread the difference between imperative commands and a manifest declaring "I want 3 replicas."

Why does Kubernetes route every component's reads and writes through the API server instead of letting each one talk to etcd directly?

The API server is the single front door: it validates and persists every object, so no component can write inconsistent or unvalidated state straight into etcd.

Think about what could go wrong if the scheduler, kubelets, and controllers all wrote to the shared store independently.

The reconciliation loop: the one pattern to remember

A controller is a non-terminating loop that watches a resource through the API server and nudges the cluster toward the recorded desired state.[6] The cycle is always the same: observe actual state → compare to desired state → act to close the gap → repeat.[6] The ReplicaSet controller is the canonical example: you declared 3 replicas, it observes 2 running (a node died), so it creates 1 more — without anyone issuing a command.

This single pattern is why Kubernetes self-heals. There is no special "recovery mode"; the steady-state loop that creates Pods is the exact same loop that replaces crashed ones. Understanding that desired-vs-actual reconciliation is the whole engine — not a grab-bag of features — is the conceptual unlock that reads as depth.

Nodes: where workloads actually run

Each worker node runs three things that turn scheduling decisions into running processes:[7]

  • kubelet — the node agent. It reads the Pods assigned to its node and tells the container runtime to start them, then reports health back.[7]
  • kube-proxy — programs the node's network rules so traffic to a Service is routed to the right Pods.[7]
  • container runtime — the software that actually runs containers (e.g. containerd), via the CRI interface.[7]
Check before continuing

Why does a crashed Pod get replaced without anyone issuing a command?

Self-healing is the same reconciliation loop: observe actual below desired, act to close the gap.

Reread the observe-compare-act cycle and which controller owns replica count.

Why does the lesson say Kubernetes has no special "recovery mode" for failures?

There's one loop, always running: observe, compare, act. A crash just changes what "actual state" looks like, so the identical loop closes the gap.

Ask what would have to exist separately if recovery were a distinct mode instead of the same loop.

Core objects: the vocabulary

ObjectWhat it is
PodSmallest deployable unit: one or more co-located containers sharing network and storage.[8]
ReplicaSetKeeps a stable set of N identical Pods running at all times.[9]
DeploymentManages ReplicaSets to give you declarative rolling updates and rollbacks.[10]
ServiceStable virtual IP / DNS name fronting a changing set of Pods (load balancing + discovery).[11]
IngressHTTP(S) routing rules that expose Services to the outside world by host/path.[12]
ConfigMap / SecretDecouple config and sensitive values from images, injected at runtime.[13]

The mental hierarchy to recall: a Deployment owns a ReplicaSet, which owns Pods; a Service gives those ephemeral Pods one stable address. Pods are cattle, not pets — they die and get recreated with new IPs, which is exactly why Services exist.

Check before continuing

What is the correct ownership hierarchy of core Kubernetes objects?

Deployment manages ReplicaSets for rolling updates; ReplicaSet keeps N Pods running; Service gives them a stable address.

Reread "the mental hierarchy to recall" line.

Why does Kubernetes need a Service object at all, instead of callers just tracking Pod IP addresses directly?

Pods are ephemeral, cattle not pets. A Service's stable virtual IP/DNS shields callers from Pods constantly dying and reappearing with new IPs.

Think about what changes every time a Pod crashes and gets replaced by the reconciliation loop.

Scaling & networking

Because everything is a reconciliation loop over declared state, the operationally hard things become configuration, not scripts:

  • Horizontal Pod Autoscaler (HPA) — watches metrics (e.g. CPU) and adjusts the Deployment's replica count up or down to hold a target.[14] It is itself just another controller closing a gap.
  • Rolling updates & rollbacks — a Deployment swaps Pods to a new version incrementally, keeping the app available; if the new version fails it can roll back to the previous ReplicaSet.[10] This is your zero-downtime deploy primitive — pairs naturally with a CI/CD pipeline (Lesson 67).
  • Self-healing — failed Pods are recreated, unhealthy ones (failing liveness probes) are restarted, all by the same loop.[6]

Service discovery & the network model. Kubernetes mandates a flat network: every Pod gets its own cluster-wide IP, and any Pod can reach any other Pod directly without NAT.[15] That keeps the model simple — Pods look like VMs on one big network. A Service sits on top with a stable virtual IP and a DNS name; kube-proxy load-balances requests across the current healthy Pods, so callers never track individual Pod IPs.[11]

Check before continuing

What is the Horizontal Pod Autoscaler, mechanically?

HPA is just another controller: it observes a metric, compares to a target, and acts by changing replica count.

Reread "it is itself just another controller closing a gap."

Why does the flat, no-NAT Pod network make the Service abstraction simpler to build on top of?

Because any Pod can already reach any other Pod directly, kube-proxy's job for a Service reduces to picking a healthy backend IP and forwarding, no NAT translation layer to also manage.

Consider what extra problem a Service would have to solve if Pods sat behind separate, NAT'd address spaces.

When you need it / when NOT

Reach for Kubernetes when…Reach elsewhere when…
Many services, polyglot, needing portable orchestration[1]One or two simple apps → a PaaS or managed container service
You need self-healing, autoscaling, rolling deploys as defaults[6]Spiky / event-driven workloads → serverless (Lambda, Cloud Run)
You have platform engineers to run it (or use managed EKS/GKE)[1]A tiny team with no ops bandwidth → avoid the YAML & etcd tax
Multi-cloud / on-prem portability is a real requirementSingle cloud, want least ops → that cloud's native primitives

The honest framing: Kubernetes buys you a uniform, self-healing control plane at the cost of real operational complexity — etcd to back up, networking and RBAC to reason about, upgrades to manage. For a small app, serverless (no servers to manage, scales to zero, pay-per-use) or a managed PaaS gives you most of the resilience with a fraction of the burden. K8s earns its keep at scale and breadth, not on day one.

★ Staff-level signal Seniors say "we'll run it on Kubernetes." Staff candidates collapse the whole system into one sentence — "K8s is a reconciliation loop: I declare desired state in etcd via the API server, and controllers continuously drive actual state to match, which is why self-healing, rolling updates, and HPA are all the same mechanism." Then they show judgement on the alternative: "but for this workload I wouldn't introduce a cluster — it's three services with bursty traffic, so serverless avoids the etcd-and-YAML operational tax until we actually need multi-service orchestration."[1] Naming the operational cost and declining to over-engineer is the simple-by-default bar.

In the interview

If your design has a fleet of microservices, it's fair to put "deployed on Kubernetes (managed EKS/GKE)" on the board — then justify it in one line ("self-healing + rolling deploys across N services") and expect two follow-ups.[1] "How does it stay up when a node dies?" → the ReplicaSet controller's reconciliation loop recreates the Pods; the Service re-routes once they're healthy.[6] "How do services find each other?" → stable Service IP/DNS over the flat Pod network, load-balanced by kube-proxy.[11] Don't narrate every object type; name the loop, name etcd as the source of truth, and — if the workload is small — proactively say you'd skip K8s for serverless. That restraint is the signal.

Comprehensive check

Where does Kubernetes keep the cluster's source of truth?

etcd is the consistent key-value store of all cluster state; only the API server reads/writes it.

Reread the control-plane table's etcd row.

When is Kubernetes most likely the WRONG choice?

For a small, bursty app with no ops bandwidth, serverless avoids K8s's heavy operational tax.

Reread the "when you need it / when NOT" table's last row.

Why can self-healing, rolling updates, and HPA all be described as "the same mechanism," as the staff-level framing claims?

Self-healing reconciles replica count, rolling updates reconcile which image version is running, HPA reconciles replica count against a metric. Same loop, different target field.

Reread the reconciliation loop's observe-compare-act cycle and ask what "desired state" each feature is comparing against.

What would happen to a running cluster if etcd's data were permanently lost, even though all Pods were still running fine at that moment?

etcd is the cluster's memory. Existing Pods keep running short-term, but the control plane has no record of what "should" be true, so any future reconciliation, scheduling, or recovery breaks.

Reread "lose etcd and you lose the cluster's memory" and consider what a controller needs to compare against.
