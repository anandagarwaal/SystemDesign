Vector Databases

Storing meaning, not keywords — embeddings, approximate nearest-neighbor search, and the index that makes "find me similar things" fast at a billion vectors.

Why this lesson, for your mission: Every modern AI prompt — semantic search, recommendations, and especially RAG for LLMs — eventually hits "how do I retrieve the most relevant items from millions of candidates in <50ms?" The senior answer is "use a vector database." The staff answer names the index (HNSW), explains the recall-vs-latency knob, knows why brute force is impossible at scale, and reaches for pgvector before a dedicated cluster when the scale doesn't justify it.[1]

1 · The problem: similarity, not equality

A normal database answers equality queries: "give me the row where id = 42" or "rows where city = 'Pune'". But AI works in embeddings — an embedding model (an LLM, CLIP, sentence-transformer) turns text/image/audio into a fixed-length array of floats, say 1536 dimensions, where semantic closeness becomes geometric closeness.[1] "king" and "queen" land near each other; a photo of a dog lands near other dogs.

The query you now want is nearest-neighbor: "given this query vector, return the k stored vectors closest to it" by a similarity metric (cosine similarity or L2 distance). That's the one operation a vector database is built around.[2] The flow is always the same three steps: embed your corpus → store vectors (with a reference back to the source content) → embed the incoming query with the same model and search for nearest neighbors.[1]

2 · Why brute force dies — and ANN saves you

The exact answer is easy to describe: compute the distance from the query to every stored vector and keep the top k. The cost is O(N·D). At 100M vectors × 1536 dims that's ~153 billion multiplications per query — on the order of seconds per query, which is unusable.[2]

So production systems use Approximate Nearest Neighbor (ANN) search: trade a sliver of accuracy for orders-of-magnitude speed. Instead of exact top-k, you get ~95–99% of the true neighbors in milliseconds.[3] The metric for "did we find the real neighbors" is recall, and the central tension of this entire topic is one tradeoff:

The one tradeoff to internalize: higher recall ⇄ higher latency (and memory). Every ANN index exposes a knob — search wider and you find more of the true neighbors but pay more time. Naming this tradeoff out loud, and the parameter that controls it, is the core signal of this topic.[2]

3 · The index algorithms

An ANN index is a data structure that lets you skip almost all the vectors. Three families come up; know HNSW cold and the others by one line.[1][2]

IndexIdeaProfileReach for it when…
HNSW
(graph)		 Multi-layer "navigable small world" graph. Upper layers = sparse long-range motorways; layer 0 = dense short hops. Search greedily descends toward the query.[3] O(log N) search, 99%+ recall; memory-hungry; build is O(N·log N).[2] The default. High recall + low latency. What Pinecone, Weaviate, Qdrant, Milvus use under the hood.[3]
IVF
(clustering)		 k-means partitions vectors into clusters; at query time scan only the nprobe nearest clusters, not all N.[2] Less recall than HNSW, simpler, lower memory; needs a training step. Very large datasets where memory matters and a little recall loss is fine.
LSH
(hashing)		 Locality-sensitive hashing drops similar vectors into the same bucket with high probability.[1] Very fast, lower recall. Rarely the production pick today — know it exists.[2]

HNSW, in one breath

Think of a road network. The top layer has a few cities connected by long highways; each layer down adds more towns and shorter roads; layer 0 contains every vector with dense local streets. A search starts at an entry point on the top layer, greedily hops to whichever neighbor is closer to the query, and when it can't get closer it drops a layer and repeats — until it does a fine local search on layer 0.[3] Two knobs: M (edges per node, set at build time) and ef_search (how many candidates to keep during traversal). Raising ef_search raises recall but raises latency — that's the tradeoff from §2 made concrete.[2]

Quantization — how you fit it in RAM

100M × 1536 dims × 4 bytes ≈ 600 GB of raw floats — too much for one box's memory.[2] Product Quantization (PQ) (and scalar quantization) compress each vector into a small code by splitting it into chunks and replacing each chunk with a codebook entry, shrinking memory ~10–30× at a small recall cost.[1] Mention quantization the moment scale enters the conversation — it's the answer to "where does all this live?"[2]

4 · Filtering: vectors + metadata together

Real queries are rarely pure similarity. "Find products like this one that are in stock and under ₹5000" mixes an ANN search with a structured filter. The DB keeps a vector index and a metadata index, and the order you combine them matters:[1]

StrategyHowFailure mode
Pre-filterApply the metadata filter first, then ANN over the survivors.Accurate, but if the filter is narrow the graph is fragmented → slow, or you fall back to brute force.[2]
Post-filterRun ANN for top-K, then drop rows failing the filter.Fast, but you may return fewer than K if most candidates get filtered out.[2]

Modern engines (Pinecone, Weaviate) blend the two with filtered-graph traversal so the filter guides the search itself rather than bolting on before or after.[2]

5 · Vector index vs. vector database vs. "just use Postgres"

A standalone vector index (e.g. FAISS) is just the ANN data structure. A vector database wraps it with the things a real system needs: CRUD and real-time updates, metadata filtering, horizontal scaling/sharding, backups, security, and multitenancy via namespaces.[1] The staff-relevant nuance is the deployment choice:

Decision reflex
  • Already on Postgres, ≲ a few million vectors? → pgvector. One datastore, transactional, no new infra.[1]
  • Tens of millions+, strict latency, heavy filtering? → dedicated vector DB (Pinecone/Weaviate/Qdrant/Milvus).
  • Cost control at scale → separate storage from compute and add a freshness layer (a small in-memory tier serving brand-new vectors while the partitioned index rebuilds in the background).[1]

6 · How it shows up in an interview

You'll meet vector search inside a bigger system — a RAG chatbot, semantic search, "similar items", or dedup. The expected pipeline for RAG: chunk docs → embed → store in vector DB, then per query embed → ANN top-k → stuff into the LLM prompt as context.[3] The depth move is two-stage retrieval: cheap HNSW returns ~100 candidates at ~95% recall, then a heavier cross-encoder re-ranker rescores those 100 with full attention and keeps the top 10 for the LLM.[3] First stage maximizes recall cheaply; second stage maximizes precision on a tiny set.

Two operational gotchas worth naming: embedding drift — if you change the embedding model, every stored vector must be re-embedded (use versioned namespaces);[2] and sharding — partition vectors by id, fan a query out to all shards, each returns local top-K, then merge to global top-K.[2] (Same scatter-gather pattern as Lesson 28.)

★ Staff-level signal Senior says "use a vector database." Staff says four things in one breath: (1) "brute force is O(N·D) — seconds per query at 100M vectors — so we use an ANN index, HNSW"; (2) "ef_search is our recall-vs-latency dial, and quantization is how it fits in RAM"; (3) "at our scale this is just pgvector on the Postgres we already run — a dedicated cluster is unjustified complexity"; and (4) "the vector DB is a derived index, not the source of truth — the document store is, and we re-embed on model upgrades." Knowing when not to add a vector cluster is the simple-by-default judgement L6/L7 rewards.[1]

Check yourself — retrieval practice

Answer from memory before scrolling back up.

1. Why can't a brute-force scan serve similarity search at 100M vectors?

Exact search is O(N·D) — ~153B multiplications per query at 100M×1536, i.e. seconds. ANN trades a little recall for speed.

2. What happens when you raise HNSW's ef_search parameter?

A bigger candidate list finds more true neighbors (higher recall) but visits more nodes (higher latency) — the core tradeoff.

3. Post-filtering (ANN first, filter after) risks which failure?

Post-filter takes top-K then drops non-matches, so a strict filter can leave you with fewer than K results.

4. What does a vector database add over a standalone FAISS index?

A vector DB wraps the index with database features — updates, filtering, scaling, backups, namespaces — that a raw index lacks.
