Design Robinhood (Stock Trading)

Two systems wearing one logo: a soft-real-time firehose of prices, and a must-never-lie ledger of money.

Why this lesson, for your mission: Trading is the canonical interview where you must refuse to treat the whole system uniformly. The price path can drop a tick and nobody dies; the order path can never lose, duplicate, or misreport a trade. Staff candidates split these two paths on the first whiteboard stroke and pick wildly different consistency, durability, and delivery guarantees for each. That split — plus idempotent submission and an append-only ledger — is the whole interview.

Functional Requirements

Robinhood is a broker, not an exchange — it doesn't match buyers to sellers itself; it routes orders to external market makers / exchanges and reflects the result back.[1] Scope the three things a user actually does:

#User can…Why it shapes the design
1View live prices for the symbols on their watchlistReal-time, high-fan-out, lossy-tolerant read path
2Place a buy / sell order (market or limit), routed to an external exchangeCorrectness-critical write path with an external dependency
3View their portfolio / positions (holdings, cost basis, value)Derived from the order/fill history — a computed read

Out of scope (say so explicitly): options, crypto, ETFs, extended-hours trading, and showing the full exchange order book.[1] Naming exclusions is itself a senior signal — it bounds the 45 minutes.

Non-Functional Requirements

This is where you draw the line down the middle of the system. The two paths get opposite guarantees, and saying so out loud is the headline move.

NFRTarget / priorityApplies to
Real-time deliveryPrice updates pushed to clients in <~200 ms; lossy is acceptable (a dropped tick is superseded by the next)Price path
Correctness & strong consistencyNo lost, duplicated, or phantom orders — ever. An order is in exactly one state at all timesOrder path
Durability & auditabilityEvery state change persisted before acknowledged; full append-only audit trail for regulatorsOrder path
Low latency on submitOrder accepted/rejected fast; fills arrive asynchronouslyOrder path
AvailabilityHigh, with brutal load spikes at market open (9:30 ET)Both
The one sentence that frames everything: "Prices are soft real-time and lossy; orders are strongly consistent and durable. I'll build two separate paths so neither compromises the other." Say this before any boxes.

Capacity Estimation

Estimate only the numbers that change a decision. Two dominate: price fan-out and order throughput.

QuantityRough mathDesign implication
Concurrent users at open~20M active, say 10M connected at once10M live WebSocket connections → need a horizontally-scaled connection tier
Price update fan-outA hot symbol (AAPL) ticks many times/sec and is watched by millions. Naive: ticks × watchers = billions of msgs/secCannot broadcast every tick to everyone. Must subscribe clients only to symbols they watch + collapse update rate
Order volume20M users × a few orders/day ≈ low millions/day ≈ tens–hundreds of orders/sec, spiking at open/closeTiny compared to prices. The order path is bound by correctness, not throughput — a single Postgres can hold the ledger

The asymmetry is the punchline: the price path is a scale problem (millions of connections, huge fan-out) while the order path is a correctness problem (modest volume, zero tolerance for error). Different problems → different machines.

Core Entities & API

Entities: User, Symbol (ticker + current quote), Order (the durable state machine: side, qty, type, status), Execution/Fill (a confirmed match from the exchange), Position (computed holding per symbol), and an append-only LedgerEntry.

User identity comes from the auth token, never the body.

EndpointPurpose
WS /v1/prices?symbols=AAPL,TSLAOpen a WebSocket; subscribe to per-symbol price channels. Server pushes quote updates only for subscribed symbols.
POST /v1/ordersPlace an order. Body includes symbol, side, qty, type and a client-generated idempotency_key. Returns the created order (submitted). Duplicate key → 409, returns the original.[2]
DELETE /v1/orders/{id}Request cancellation (routed to the exchange; may race a fill).
GET /v1/orders/{id}Read current order status from the state machine.
GET /v1/portfolioReturn positions, cost basis, and current market value.

High-Level Design

Draw two columns. They share auth and a client, and almost nothing else.

ComponentPathRole
Price IngestorPriceConsumes the exchange's trade/quote feed for all symbols; normalizes ticks.[1]
Pub/Sub (Kafka-style topics)PriceOne channel per symbol. Decouples ingest rate from delivery.[2]
WebSocket / Connection tierPriceStateful gateway holding millions of client sockets; each gateway subscribes to only the symbols its connected clients watch and pushes updates out.
Order Gateway / ServiceOrderValidates, dedupes on idempotency key, writes the order to durable storage before routing to the exchange.
Order DB + append-only ledgerOrderStrongly-consistent store (e.g. Postgres) for order state + an immutable event log of every transition.
Exchange AdapterOrderTalks to the external exchange's order API (synchronous submit/cancel) and ingests the asynchronous fill callback.[1]
Portfolio ServiceReadDerives positions from the fill/ledger history (live + cached).

Flows. A price flows: exchange feed → Ingestor → per-symbol topic → WebSocket gateways → only subscribed clients. An order flows: POST /orders → dedupe → persist (submitted) → route to exchange (routed) → later, an async callback marks it filled → ledger appended → portfolio updated. Notice the order is durable before it ever leaves for the exchange.

★ Staff-level signal The whole interview is one judgement: don't let the price firehose and the money ledger share a code path or a consistency model. A senior engineer builds one nice real-time pipeline. A staff engineer says "these are two systems" in the first minute, gives prices best-effort pub/sub fan-out and gives orders idempotent writes + an append-only ledger, and can defend why a dropped tick is fine but a dropped fill is a regulatory incident.

Deep Dive 1 — Streaming live prices to millions

The exchange exposes a trade feed that pushes data every time a trade occurs.[1] The challenge is purely fan-out: a few hot symbols are watched by nearly everyone (see Lesson 19 on fan-out, Lesson 24 on WebSockets / SSE).

Why naive broadcast explodes

If every gateway forwarded every tick to every connected client, a single popular symbol ticking dozens of times a second against millions of watchers is billions of messages per second. Two tools tame it:

  • Per-symbol channels, demand-driven. Ingestor publishes each symbol to its own pub/sub topic. A WebSocket gateway only subscribes to the union of symbols its connected clients are watching — so a gateway with no TSLA watchers never receives TSLA traffic.[2] Fan-out happens at the edge (gateway → its own sockets), not centrally.
  • Rate collapsing / conflation. A human can't read 50 price changes/sec. Coalesce to the latest value per symbol on a short tick (e.g. push at most every 200 ms). Because prices are lossy by design, dropping intermediate ticks is correct, not a bug — the newest quote supersedes all prior ones.
The scaling lever: connections scale with users (add gateways), but message volume scales with symbols × update rate, which conflation caps. Decoupling the two is what makes 10M connections affordable. Hot quotes also live in an in-memory cache so a fresh subscriber gets the current price immediately, not on the next tick.

Deep Dive 2 — Order placement correctness

Here, every guarantee flips. Model an order as a deterministic, persisted state machine, not a single action — each transition durable and auditable.[4]

submitted → routed → partially_filled → filled (or rejected / canceled). The order row is written and committed before we call the exchange, so a crash mid-route leaves a durable submitted record we can recover and reconcile — never a lost order.

Idempotency: the duplicate-order killer

The client generates an idempotency_key per order intent and sends it with POST /orders. On a network timeout the client retries with the same key. The server stores the key uniquely; a second request with a seen key returns the original order (or 409) instead of placing a second trade.[2] Without this, a flaky connection at market open buys a stock twice — a real financial loss, not a UI glitch.

Consistency with the external exchange

The exchange is the source of truth for fills; our DB is the source of truth for intent. They drift (timeouts, missed callbacks). Defenses:

  • Append-only ledger (event sourcing). Never mutate an order in place; append an immutable event for every transition. Current state is a fold over events. This gives a perfect audit trail and lets you replay/recover after any failure.
  • Reconciliation job. Periodically (and end-of-day) compare our ledger against the exchange's authoritative record, flagging any discrepancy for investigation — the same pattern brokers use to reconcile internal balances against external statements.[3]

Deep Dive 3 — The async fill callback

Submit is synchronous; execution is not. A market order may fill in milliseconds; a limit order may sit for hours. So routing returns immediately, and the exchange later calls back with the fill.[1]

  • Make the callback idempotent too. Exchanges retry callbacks; key fills by execution ID so a re-delivered fill doesn't double-count the position.
  • Apply the fill as a ledger event, transition the order state, then notify the user (push/WebSocket).
  • Missed-callback recovery. Don't trust the network. A poller queries open orders' status from the exchange to catch fills whose callbacks never arrived — reconciliation as a safety net.

Deep Dive 4 — Portfolio computation

A position is derived state, not stored truth: fold the fill history per symbol → net quantity and cost basis. Two presentations:

  • Quantity & cost basis come from the ledger (exact, slow-changing) — cache a materialized position per user and update it on each fill event.
  • Current market value = cached position × the live quote from Deep Dive 1's price cache. This cleanly reuses the price path for the display number while keeping the holding itself sourced from the authoritative ledger.

The elegance: the lossy price path supplies the "what's it worth right now" number, while the durable order path supplies "what do I own" — exactly the split from the NFRs, visible in a single screen.

Check yourself — retrieval practice

Answer from memory before scrolling back up.

1. Why are the price path and the order path designed with opposite guarantees?

A dropped tick is superseded by the next; a dropped or duplicated order is a financial and regulatory failure.

2. What keeps the live-price fan-out from exploding to billions of messages per second?

Gateways subscribe only to watched symbols and push at most the newest quote per short interval — lossy is fine.

3. What does the client-generated idempotency key on POST /orders prevent?

A retry with the same key returns the original order (or 409) instead of placing a duplicate.

4. Why is an append-only ledger the right model for orders rather than mutating rows in place?

Immutable events = auditability for regulators plus recoverability — state is a fold over the log.

Ask me anything. I'm your teacher for this one — push on it. Try: "Walk me through what happens to an in-flight order if the order service crashes right after routing to the exchange." Or: "How would partial fills change the state machine and the portfolio math?" Or: "Compare per-symbol Kafka topics vs. a single topic with client-side filtering for the price fan-out."
