Design a Weather App

A billion reads a day, sourced from one slow government API. The whole interview is admitting you don't need fresh data.

Why this lesson, for your mission: This problem hands you the staff signal on a plate, and most candidates miss it: weather is extremely read-heavy and tolerant of staleness. The L6/L7 move is naming that within the first minute and letting it collapse the design — decouple reads from the slow upstream provider, serve everything from cache and a CDN keyed by a coarse location cell, and let stale-while-revalidate keep you up when the source goes down. If you instead reach for real-time freshness, you've over-built the easy part and skipped the interesting one.

Functional Requirements

Three capabilities define the product. Everything else (radar tiles, alerts, maps) is out of scope — say so.[1]

#A user should be able to…
1Get the current weather for a location (lat/lng or city), with slightly stale values acceptable.
2Get a short hourly forecast for that location.
3Have the system periodically refresh weather from an upstream source (e.g. NWS) into our store.[2]

Out of scope (defer explicitly): severe-weather push alerts, animated radar/precipitation map tiles, historical climate queries, and user accounts. We are a read API in front of a refreshed cache of provider data.

Capacity Estimation

Only the numbers that change a decision. These are my own back-of-envelope estimates.

  • Read QPS: ~100M DAU × ~5 lookups/day ≈ 500M reads/day ≈ ~6k QPS average, ~30k QPS peak. Tiny for an edge cache, fatal for an unprotected origin → CDN does the heavy lifting.
  • Distinct locations: the globe at a ~5 km grid is ~10M land cells; cut to populated areas and you have ~1–2M hot cells. The entire current-conditions dataset is small enough to fit in memory.
  • Write (ingestion) rate: refresh ~1M cells every ~10 min = ~1.7k writes/sec — and that's the only traffic that touches the provider, not the user QPS. This is the core decoupling.
  • Storage: ~2M cells × ~2 KB (current + hourly) ≈ ~4 GB of hot state. Trivial — one Redis cluster holds the working set; durability lives in a modest origin store.
Takeaways: reads dwarf writes by ~1000×, the hot dataset is small, and staleness tolerance means almost every read should be a cache hit. The design is a caching problem, not a storage problem.

Two entities. The read endpoints are public and cacheable; derive any user from the auth token, never the body.

Data Flow

This is a data-processing system (ingestion + serving), so trace the two independent lifecycles before drawing boxes:

Ingestion (write path, ~1.7k/s):
  1. Scheduler enqueues "refresh cell X" jobs on a cadence (e.g. every 10 min for hot cells).
  2. Ingest workers call the upstream provider (NWS gridpoint API), normalize the payload.[2]
  3. Persist the snapshot to the origin store and warm it into the cache, keyed by cellId.
Serving (read path, ~6k–30k/s):
  1. Request → CDN edge: normalize lat/lng to cellId, check edge cache (hit → done).
  2. Miss → app + Redis: return the latest snapshot for the cell; never call the provider inline.

The two paths never block each other. Users read pre-fetched data; the provider is only ever touched by the scheduler-driven ingestion workers. Each path gets its own deep dive.

Deep Dive 1 — The read path: aggressive caching + CDN

With a ~1000:1 read ratio and a small hot dataset, the entire design rests on a high cache hit ratio. Staleness tolerance is what makes this easy: because a 9-minute-old value is acceptable, you can set genuinely long TTLs instead of fighting invalidation. (See Lesson 4 — Caching for the fundamentals this builds on.)

Layered cache, edge-first
  • CDN edge serves the vast majority of reads near the user — low latency and it shields the origin. Key on the normalized cellId, not raw lat/lng, so nearby users collapse onto one entry.[3]
  • Redis behind the API holds the same snapshots for edge misses; the ~4 GB working set fits in memory.[4]
  • TTL: max-age=600 matches the <10-min staleness budget; the read path never calls the provider synchronously.

Why this works: a TTL-based cache only goes stale by at most one TTL, which the requirement explicitly permits. You trade a small, bounded staleness for a massive drop in origin/provider load and p99 latency.

★ Staff-level signal The highest-leverage sentence here is "staleness tolerance lets me set a long TTL, so I never need cache invalidation on the read path." Cache invalidation is one of the hard problems in CS; recognizing that the requirement removes it — rather than dutifully building a pub/sub invalidation mesh — is exactly the judgement that separates senior from staff. Don't over-engineer the easy part.

Deep Dive 2 — Geospatial keying so neighbors share cache entries

If you cache on raw lat=37.7749,lng=-122.4194, every user gets a unique key and your hit ratio collapses — the classic high-cardinality cache-key mistake. Quantize the coordinate into a coarse cell so everyone in a neighborhood hits the same entry. (This is the same grid/geohash trick used for proximity in Lesson 20 — Yelp.)

SchemeWhat it gives youTradeoff
Geohash prefixTrim precision (e.g. 5 chars ≈ ~5 km cell) to set granularity.Edge cells split nearby points across keys; fine for weather.
Fixed grid (lat/lng buckets)Simple integer math, uniform cell size in degrees.Cells distort near the poles; usually irrelevant for population.
Provider gridpointNWS already exposes a /points → gridpoint mapping.[2]Couples your key to one provider's grid.

The cell size is a dial: coarser cells = fewer keys = higher hit ratio + fewer provider fetches, but lower spatial accuracy. For consumer weather, a few-km cell is plenty accurate and dramatically improves sharing — the number of distinct keys (and provider calls) drops from "per user" to "per populated cell."

★ Staff-level signal Framing cell size as an explicit accuracy-vs-cache-efficiency tradeoff — and tying it to both hit ratio and upstream cost — shows you see the cache key as a design parameter, not an afterthought. Bonus points for noting it also bounds how many cells the ingestion pipeline must refresh.

Deep Dive 3 — The ingestion pipeline (decoupling from a slow source)

The upstream provider is slow and rate-limited, and the user QPS is ~1000× the data's change rate. Calling the provider on the read path would be insane. So a scheduler-driven pipeline pulls data asynchronously and the read path only ever touches our cache. (This mirrors the poll-via-queue pattern in Lesson 26 — Price Tracking.)

Scheduler → Queue → Ingest workers
  • Scheduler enqueues refresh jobs per cell on a cadence, varied by demand: hot cities every ~10 min, sparse regions much less often. This concentrates provider budget where users actually are.
  • Queue decouples scheduling from fetching and absorbs bursts; workers scale horizontally and self-pace against the provider's rate limit.[2]
  • Politeness: per-provider rate limiting, exponential backoff + retries, and a dead-letter queue for cells that repeatedly fail to refresh.
  • Write-through: each successful fetch updates the origin store and warms the cache, so reads are already hot — no cold-start stampede.

Why a queue rather than the scheduler calling the provider directly? Backpressure and replay. If the provider slows, jobs buffer instead of piling up; after an outage you replay the backlog. The number of provider calls is bounded by cells × cadence, completely independent of user traffic — that's the decoupling that makes the whole system cheap and resilient.

Deep Dive 4 — Surviving provider outages with stale-while-revalidate

The source of truth is an external API you don't control; it will have outages and rate-limit rejections. Because staleness is tolerable, an outage should degrade gracefully, not error.

TechniqueWhat it buys you
stale-while-revalidateServe the expired snapshot instantly while a background refresh runs; users never see an error during a refresh.[3]
stale-if-errorIf the provider/origin is down, keep serving the last good snapshot well past its TTL instead of failing.[3]
Bounded staleness signalReturn fetchedAt/age so clients (and you) can show "as of 9:42am" and detect drift.
Retry + backoff + DLQFailed refreshes retry without hammering the source; persistent failures are visible, not silent.
Last-known-good in originThe durable store always has a value to rebuild the cache from after a flush or restart.

The mental model: the cache is the contract with users, the provider is a best-effort feeder. As long as the cache has a recent-ish value, a provider outage is invisible. You only have a user-facing incident if data goes stale past what's useful (hours, not minutes) — and even then you serve data plus an age, not a 500.

Check yourself — retrieval practice

Answer from memory before scrolling back up.

1. Which requirement most shapes a weather app's design?

Read-heavy + staleness-tolerant is what unlocks long TTLs, CDN caching, and async refresh.

2. Why key the cache on a coarse location cell, not raw lat/lng?

Quantizing coordinates removes per-user key cardinality so neighbors share one cache entry.

3. Why pull from the provider via a scheduler instead of on each read?

Provider calls are bounded by cells×cadence, independent of the much larger user QPS.

4. The provider goes down mid-refresh. What is the right behavior?

stale-while-revalidate / stale-if-error keep you up; staleness tolerance makes this acceptable.
