Data Structures for Big Data

Probabilistic structures — Bloom filter, HyperLogLog, Count-Min Sketch — that answer set, cardinality, and frequency questions in kilobytes when the exact answer would cost gigabytes.

Why this lesson, for your mission: At scale, "just store it in a set / hash map" silently becomes a multi-gigabyte memory bomb. The staff move is to recognize when exact is unaffordable and approximate is fine, then name the right probabilistic structure and its error profile in one breath. This is the single most reusable deep-dive lever across the case studies — it shows up in the crawler, Tinder, YouTube, and dedup pipelines.[1]

1 · The big idea: trade a little accuracy for 1000× memory

Probabilistic data structures (PDS) use hash functions to represent a huge set in a tiny, fixed footprint, returning an approximate answer with a bounded, predictable error.[4] When data grows to billions of items, exact counting and membership become prohibitively expensive; PDS deliver ~1000× memory reduction with a configurable error rate.[2] The decision rule:

Reach for a probabilistic structure when the dataset is huge, you can tolerate a small bounded error, and the exact structure (a set, a hash map of counters) won't fit in memory. Stay exact when the data is small or an error has real consequences (money, auth, correctness).[1]

3 · Bloom filter — set membership

A bit array plus k hash functions. To add an item, hash it k ways and set those bits. To test membership, hash it k ways and check those bits: if any bit is 0 the item is definitely absent; if all are 1 it's probably present.[5] The asymmetry is the whole point — zero false negatives, only false positives. You tune the false-positive rate p with the bit-array size: m = -n·ln(p) / (ln2)².[1]

Classic uses: a web crawler's "have I seen this URL?" gate (a maybe-hit falls through to the authoritative DB), Tinder's "already swiped?" set, and cache penetration defense. You met it in Lesson 35 and Lesson 17 — this is the same tool, generalized.

4 · HyperLogLog — cardinality (count distinct)

Counting 1 billion unique user IDs in an exact set costs ~12 GB of RAM. HyperLogLog (HLL) does it in ~12 KB — a million-to-one reduction — with ~0.81% standard error, regardless of how many items you add.[2] The trick: hash each element, count the leading zeros in the hash, and track the maximum seen across a set of registers. Seeing many leading zeros is statistically rare, so the max observed is a logarithmic proxy for cardinality; the estimate is the harmonic mean across registers.[4]

Uses: unique visitors, distinct search terms, "how many unique videos were watched" — exactly the unique-view counting noted in Lesson 33. HLLs also merge (union two sketches by taking per-register maxima), which makes them perfect for distributed roll-ups.[4]

5 · Count-Min Sketch — frequency / heavy hitters

A d × w matrix of counters with d hash functions, one per row. Insert: hash the item with each row and increment that cell. Query: hash with each row, read the d cells, return the minimum.[4] Collisions can only push counts up, so the minimum is an upper bound — it over-counts but never under-counts.[5] Fixed memory regardless of how many distinct keys stream through, O(1) per update.

Pair it with a min-heap to track the top-K heaviest items — the exact recipe from Lesson 28 (trending videos), and the standard tool for network-traffic monitoring and abuse detection.[3]

★ Staff-level signal Naming "Bloom filter" isn't the signal — justifying it with its error direction is. The staff sentence connects the NFR, the bottleneck, and the structure: "exact dedup is 1.6 GB and we don't need certainty, so a Bloom filter gives O(1) membership with no false negatives — the only failure is occasionally re-skipping a novel item, invisible at this scale." The deepest tell is choosing the structure by the direction of acceptable error: Bloom never says "no" wrongly; Count-Min never under-counts; HLL is symmetric ±0.81%. A senior builds exact-first and struggles to scale; staff negotiates the relaxed accuracy NFR up front and designs straight to kilobytes.[3]

Check yourself — retrieval practice

Answer from memory before scrolling back up.

1. Which structure answers "have I seen this key?" with zero false negatives?

A Bloom filter never gives a false negative: "no" means definitely absent, "yes" means probably present.

2. You must count ~1B unique visitors in about 12 KB. Reach for…

HyperLogLog estimates cardinality in ~12 KB fixed with ±0.81% error, regardless of set size.

3. A Count-Min Sketch's frequency estimate errs in which direction?

Hash collisions only increase counters, so the minimum across rows is an upper bound — it never underestimates.

4. What actually justifies the accuracy loss of these structures?

PDS trade a small, bounded error for ~1000× memory savings and O(1) speed — worth it only when error is tolerable.
