Design Hierarchical Data Storage (Folders & Trees)

A scalable system for storing and querying tree-structured data (files, folders, permissions) without expensive recursive queries.

Why this lesson, for your mission: Trees are deceptively complex at scale. The naive approach (parent-child pointers + recursive queries) crumbles under deep hierarchies and concurrent modifications. The staff move is recognizing that this is a materialized path problem, and choosing between denormalized paths, nested sets, or materialized views based on the query patterns. You learn when to denormalize and when to keep queries simple. The same patterns apply to file systems, organizational charts, and any hierarchical domain model.

Phase 1 · 0–5 minClarify the problemPin what queries matter and tree depth.

Ask before you design

  • "What are the hot queries — list children, full path, all ancestors, or subtree search?" — Schema choice depends on access patterns.
  • "How deep is the tree — 5 levels or 100?" — Deep trees make recursive queries expensive; denormalization becomes mandatory.
  • "Do users move folders frequently, or is the tree mostly static?" — Frequent moves require efficient path updates; static trees can use materialized paths.

Phase 2 · 5–10 minEstimate what mattersTree size, depth, and query patterns.

Capacity Estimation

Tree size

1B total nodes; 100M users, ~10k files/folders per user. Average folder depth: ~10 levels. Implication: partition by user_id; each shard has ~10k nodes, manageable in Postgres.

Query patterns

Hot: list children (~1k/sec per user), get full path (~500/sec). Cold: subtree traversal (~100/sec), move (~10/sec). Implication: optimize for list children and path; move operations are rare enough to accept O(n) cost.

Interviewer pushback

"Why not use a recursive query for subtree traversal?"

Staff answer: Recursion with parent pointers requires multiple round-trips or a recursive CTE, which is slow for deep trees. At 10 levels, a recursive CTE is 10 joins. Materialized paths avoid this: query by path prefix in O(1).

Say to move on → "With 1B nodes and 10-level depth, I'll use materialized paths to avoid recursion."

Interviewer pushback

"What if you rename a folder in the middle of the tree?"

Staff answer: Only the name field changes; the path (which is IDs, not names) is stable. If you want display names in the path, use a separate cached materialized view that you recompute on rename (eventually consistent).

Say to move on → "The schema uses materialized paths. Let me design operations on this tree."

High-Level Design

The tree is partitioned by user_id. Each node stores id, parent_id, name, and path (materialized ID sequence). List children queries parent_id directly (indexed). Move operations compute new paths for all descendants and apply in a transaction (or via an event log for eventual consistency).

Interviewer pushback

"What if you move a million-node subtree? Won't the query timeout?"

Staff answer: For large moves, use eventual consistency: enqueue the move as an event, apply it asynchronously, and return immediately. Users see the old path briefly, then it updates. Or batch the update: do 10k nodes per second in background jobs.

Say to move on → "The design is simple: materialized paths avoid recursion. The hard part is efficient moves and permissions."

Phase 5 · 27–47 minDeep dives & tradeoffsMaterialized paths, nested sets, move/rename operations.

Deep Dives

Deep Dive 1 — Materialized paths vs. nested sets vs. parent pointers

Three approaches to store hierarchies:

ApproachStructureList childrenFull pathSubtree searchMove
Parent pointersid, parent_idO(n) index scanO(h) recursive queryO(n) recursive CTEO(1) update
Materialized pathsid, path = "/1/2/3"O(1) parent_id prefixO(1) direct columnO(n) LIKE prefixO(n) bulk update
Nested setsid, left, rightO(n) BETWEENO(n) ancestor scanO(1) BETWEEN rangeO(n) recompute range

Pick materialized paths: list children and full path are the hot queries. Move is rare (10/sec). Materialized paths are simplest.

Deep Dive 2 — Efficient move operations

To move node Y (with path /1/2/3) under node X (path /4/5): update all descendants where path LIKE '/1/2/3/%' and replace prefix. For large subtrees, split into batches or use async jobs.

Deep Dive 3 — Permissions and cascading ACLs

When you share a folder, do children inherit permissions? Model as: node has owner and explicit grants, plus inherited grants from ancestors. On move, permissions change (lose ancestors' grants, gain new parent's grants).

Deep Dive 4 — Soft deletes and recovery

Don't hard-delete; soft-delete (mark with deleted_at). Store backups; allow undelete. On move, skip deleted descendants. Periodically compact: hard-delete after 90 days.

Security & Privacy

Implement permissions: owner can grant read/write to team members. On move, audit the operation. Soft-delete (not hard-delete) for recovery. Mask paths in logs (PII: don't log full folder names of deleted items).

Permissions cascading

When you move a folder, do inherited permissions change? Design: store explicit grants on each node. On move, re-evaluate inherited permissions from the new parent. Cache the permission matrix; invalidate on move.

Say to move on → "With permissions and soft deletes in place, scaling is straightforward."

Closing Summary (60 seconds)

The hierarchy is stored with materialized paths (/1/2/3) to avoid expensive recursion. List children and full path queries are O(1). Move operations are O(n) bulk updates (acceptable since rare). Permissions cascade via inherited grants; soft deletes allow recovery. The schema scales linearly by user_id partitioning: each user has ~10k nodes, small and cacheable. The trade-off: materialized paths require bulk updates on move, but that's acceptable since moves are rare.

Check yourself — retrieval practice

Answer from memory before scrolling back up.

1. Why use materialized paths instead of parent pointers for hierarchies?

Parent pointers require recursive CTEs (slow for deep trees). Materialized paths (e.g., /1/2/3) let you query list children by parent_id (indexed) and full path directly.

2. How do you efficiently query all descendants of a folder with materialized paths?

Materialized paths like /1/2/3 let you use LIKE prefix matching: WHERE path LIKE '/1/2/3/%'. With a B-tree index, this is O(log n) + scan.

3. When you move a folder with 1M descendants, what should you do?

Moving 1M rows synchronously can timeout. Instead, publish the move as an event and apply it in background jobs (10k nodes per second). Users see the old path briefly, then it updates.

Ask me anything. How would you handle shared folders (where multiple users own the tree)? What about syncing hierarchies across regions? How would you implement search that respects the tree structure?
