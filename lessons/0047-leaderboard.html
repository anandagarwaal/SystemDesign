Design a Leaderboard

Millions of score updates in, an instant "where do I rank — globally and among my friends?" out. One data structure does the heavy lifting; the hard parts are everything around it.

Why this lesson, for your mission: A leaderboard looks trivial — "just sort by score" — and that is exactly the trap. The senior candidate reaches for a Redis sorted set and stops. The L6/L7 candidate names the sorted set in thirty seconds, then spends the rest of the interview on the parts that actually break at scale: the friends leaderboard, ranking across a sharded set, and keeping a fast in-memory index honest against a durable source of truth. Knowing which 20% is hard — and going there unprompted — is the whole signal.

Phase 1 · 0–5 minClarify the problemPin scope and the few NFRs that will drive every later decision.

Ask before you design

  • “Which boards — global, friends, time windows?” — Friends and windowed boards need different structures than a single global board.
  • “How are ties broken?” — Tie-breaking rules must be encoded into the ranking score.
  • “Do scores only increase, or can they decrease?” — Monotonic scores simplify anti-cheat and incremental updates.

Functional Requirements

Strip the prompt to what the system must do. A real-time game leaderboard has one write and three reads.

#Requirement
1A player's score can be submitted/updated — set an absolute score or increment after a match.
2Anyone can fetch the global top-N (e.g. top 100) with rank and score.
3A player can fetch their own global rank and a window of players around them ("rank around me").
4A player can fetch a friends leaderboard — their ranking restricted to people they follow.

Explicitly out of scope (scoping out loud is a staff move): anti-cheat/score validation, matchmaking, rewards payout, and arbitrary historical replays. We do support time-windowed boards (daily / weekly / all-time) because that's a near-free extension we'll cover in a deep dive.

Non-Functional Requirements

NFRTarget & priority
Low-latency readsTop-N, rank-around-me, and friends views return in tens of milliseconds at p99. Reads dominate; this is the primary constraint.
Fast writesScore updates apply in single-digit ms and are reflected in rankings near-instantly — this is a "real-time" board.
Read-heavy & scalableMillions of users/day; read:write skews heavily toward reads. Must scale horizontally without a single global bottleneck.
Durability / correctnessScores are the product — they must survive a cache crash. The ranking index may be approximate at the tail, but the underlying scores are exact.

The global rank number can be slightly stale or approximate once the set is sharded, and saying so up front is what licenses the cheap sharded design later. A senior candidate treats "the leaderboard" as one consistency problem; a staff candidate negotiates exact-scores / approximate-rank and designs straight to it.

Core Entities & API

Entities: Player (id, display name, friend/follow edges), Score (playerId → numeric score, the value we rank on), and Leaderboard (a named, optionally time-windowed board such as global:alltime or global:2026-W24).

The caller's identity comes from the auth token; we never trust a playerId in the body for "my rank" queries.

EndpointPurpose

GET /v1/leaderboards/{board}/top?n=100Global top-N with rank + score. Maps to ZREVRANGE … WITHSCORES.
GET /v1/leaderboards/{board}/meThe caller's rank + score + a window around them. Maps to ZREVRANK + a ranged ZREVRANGE.
GET /v1/leaderboards/{board}/friendsThe caller's ranking restricted to their friend set (the hard one — see deep dive 2).

Data Model

The durable model is a score row per (board, player) plus an append-only score event log keyed by match id — the log makes submissions idempotent and lets any board be rebuilt. Redis holds only derived indexes: one sorted set per board-window whose score is a composite (points in the high bits, inverted timestamp in the low bits) so ties resolve by who got there first.

Writes go to the durable score log and table first, then to the Redis sorted set (write-through). Reads hit Redis replicas in O(log n); the friends view fetches friend ids from the social graph and scores them with one ZMSCORE call. Redis can always be rebuilt from Postgres.

High-Level Design

Reads and writes share one core index but lean on different supporting components. Walk each path.

Phase 5 · 27–47 minDeep dives & tradeoffsGo deep where the system breaks; compare alternatives and justify the pick.

Deep Dives

1 · The Redis sorted set — why it is the leaderboard

A sorted set (ZSET) stores unique members each with a floating-point score, kept ordered by score; internally it's a skip list plus a hash, which is what gives logarithmic ordered operations alongside O(1) score lookup.[1] Every leaderboard primitive maps to exactly one command:

  • ZADD board score player — set an absolute score. ZINCRBY board delta player — bump after a match. Both O(log n).[1]
  • ZREVRANGE board 0 99 WITHSCORES — the global top-100 with scores, highest first. O(log n + m) for m returned.[1]
  • ZREVRANK board player — the player's 0-based rank from the top. O(log n).[1]
  • "Rank around me" — ZREVRANK to get rank r, then ZREVRANGE board r-5 r+5 WITHSCORES for the surrounding window. Two O(log n) calls, no scan.

This is why "use a sorted set" is the correct 30-second answer[2] — and why it is not a complete answer. Everything interesting is what these commands can't do directly: ranking a friend subset, ranking across shards, and surviving a crash. The sorted set was introduced in the key-technologies tour and reused for approximate ranking in Top-K; here it's load-bearing.

★ Staff-level signal Name the command and its complexity in the same breath: "ZREVRANK is O(log n), so even at 50M members rank is microseconds — no scan, no precomputed rank column." Then immediately pivot to what the ZSET doesn't solve. Dwelling on the obvious sorted-set basics is a junior tell; the staff move is to spend ten seconds there and bank the rest of your time on the friends query and sharding.

2 · The friends leaderboard — the part everyone underestimates

"Rank me among my friends" has no single sorted set to point a command at. The friend set is per-user and overlapping, so the tempting fix — materialize one sorted set per player's friends — is a trap: with 50M players averaging hundreds of friends, you'd maintain billions of memberships, and a single score change would fan out a write into every friend's board. Per-user materialization is quadratic write amplification for data that's read sparsely. Reject it explicitly.

ApproachHow it worksVerdict
Fetch + sort in appGet friend ids from the graph service, then ZSCORE (or one ZMSCORE) each against the global board, sort the (typically few hundred) results in memory.Default pick. Friend counts are small and bounded; a few hundred O(log n) lookups is still sub-ms. Simple, no extra state.
ZINTERSTORE with a friend setBuild a temporary ZSET of the friend ids, intersect it against the global board into a result ZSET, then ZREVRANGE it.[1]Push the work into Redis when friend lists are large; cost scales with the smaller set. Watch the temp-key churn.
Per-user materialized boardOne persistent ZSET per player holding their friends' live scores, updated on every score change via fan-out.Avoid. Billions of memberships and write amplification on every match. Only justified for a tiny set of "whales" read constantly.

The friends "rank" you return is a rank within the fetched subset (1 of N friends), not the global rank — clarify which the product wants, since "you're #3 among friends" and "you're #41,902 globally" are different queries answered from the same scores.

★ Staff-level signal The interviewer is watching whether you reach for the "obvious" per-user materialization and feel the write-amplification pain, or whether you reason from the access pattern first: friends lists are small and read infrequently, so compute on read beats maintain on write. Quantifying the rejected option ("hundreds of friends × 50M users = billions of edge writes per score update") is the depth that separates levels.

3 · Sharding the set and computing global rank across shards

One ZSET on one primary is fine for tens of millions of members, but you shard when a single node's rank-query load, memory, or blast radius becomes unacceptable — or when the all-time board grows past one machine. Sharding a leaderboard breaks the one thing the ZSET gave us for free: a single global ordering. ZREVRANK on a shard returns rank within that shard, not globally.

The core problem: if players are hash-partitioned across S shards, a player ranked #1 on their shard could be #1 or #500,000 globally — you can't know without the other shards.
  • Top-N across shards: ask each shard for its local top-N, merge the S×N lists, take the overall top-N. Same local-then-global merge as Top-K — a global winner must be in its own shard's top-N.
  • Exact global rank (expensive): for "what's my exact global rank," fan out a ZCOUNT(myScore, +inf) to every shard and sum "how many beat me." Correct, but S round-trips per query — fine for the rare exact case.
  • Approximate rank via score bucketing (the scalable pick): maintain a small, separate structure of score histogram buckets (e.g. count of players in each score range) aggregated across shards. To estimate a rank, sum the bucket counts above the player's score. O(buckets), not O(shards × log n), and accurate enough for "you're in the top 2%."

This is where the NFR you negotiated pays off: because approximate global rank is acceptable, you ship bucketing for the common "top X%" display and reserve the exact ZCOUNT fan-out for the few places exactness matters. A senior design tries to keep exact global rank everywhere and drowns in cross-shard coordination.

4 · Persistence, ties, and time-windowed boards

Three smaller decisions that interviewers probe because they reveal whether you treat Redis as a database (wrong) or an index (right).

Source of truth. Redis holds the live ranking index, but the authoritative scores live in a durable DB; writes go DB-first (or to a durable log), then to the ZSET. If Redis dies, replay the DB to rebuild every board. Redis AOF/RDB persistence shortens recovery, but the contract is "Redis is a derived, rebuildable index" — that's what lets you run it memory-first without risking the product.[2] See caching for the write-through pattern.

Ties. Sorted sets order equal scores lexicographically by member,[1] which makes ties arbitrary and unstable. To break ties by "who reached the score first," encode time into the score itself: a 64-bit composite of score in the high bits and an inverted timestamp in the low bits, so earlier achievers sort ahead at equal points. One number, no secondary query.

Time windows. Daily/weekly/all-time boards are just a key per window: global:2026-06-16, global:2026-W24, global:alltime. A score write fans out to the relevant live keys; expired windows get a Redis TTL and disappear with no cleanup job. Rotating periods cost nothing because each is an independent ZSET.
★ Staff-level signal Encoding the tie-break into the score (composite score+timestamp) instead of doing a second sort is the kind of small, decisive trick that signals you've actually built one of these. Likewise, "key per time window + TTL" shows you get that the elegance of windowing is no cleanup logic — the same insight as fixed windows in Top-K.

Wrap-up · 58–60 minClose strongRecap decisions and tradeoffs in 60 seconds; name what you would do next.

Closing Summary (60 seconds)

A leaderboard is a Redis sorted set in front of a durable score store. Authoritative game servers submit scores through a stateless API that writes the database and updates the sorted set; ZADD, ZREVRANGE and ZREVRANK make updates, top-N and rank queries O(log n). Ties are encoded into a composite score. Friends boards are computed at read time from a small friend list. Time-windowed boards are separate keys with TTLs, and Redis is rebuildable from the event log. At 10× we shard boards and merge top-N.
