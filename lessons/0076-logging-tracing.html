Design Distributed Logging & Tracing (Jaeger / Datadog)

Collect logs and request traces from thousands of services at petabyte scale, then make them searchable in seconds — observability from first principles.

Why this lesson, for your mission: Observability is the canonical "ingest-heavy, read-rarely, cost-dominated" system. The senior answer is "ship logs to Elasticsearch." The staff answer recognizes that at petabyte scale you cannot index or even keep everything — so you make sampling and tiered storage first-class design decisions, and you treat cost per useful query, not raw throughput, as the metric to optimize. This prompt rewards judgement over completeness.

Functional Requirements

Two telemetry signals — logs and traces — sharing one pipeline. Scope tightly.[1]

#Users should be able to…
1Ingest logs & traces. Thousands of services emit structured log lines and spans; the platform accepts both via lightweight agents.
2Search logs. Full-text and field queries (service=checkout AND status=500) over a time range, returning matching lines fast.
3View a trace. Look up one trace_id and see the full request waterfall — every span across every service that touched it.
4Retention. Keep recent data hot and searchable; age older data into cheap cold storage on a configurable schedule.

Out of scope (say it): metrics/dashboards (covered in Lesson 38), alerting, and ML anomaly detection. Logs, metrics, and traces are the "three pillars," but conflating them in one answer is a red flag.[2]

Capacity Estimation

Only the numbers that change a decision.

  • Event rate: 10k services × ~1k events/sec ≈ 10M events/sec. At ~1 KB/event that's ~10 GB/s on the wire. → No single node ingests this; horizontally sharded agents + Kafka.
  • Raw volume: 10 GB/s ≈ ~850 TB/day, ~25 PB/month before sampling/compression. → You cannot index or even retain all of this on hot storage. This number alone forces sampling + cold tiering.
  • Trace sampling: keeping 100% of spans is the cost killer. At 1% sampling, trace volume drops ~100× while still surfacing nearly all error/latency patterns.[4] → Sampling is a design decision, not an afterthought.
  • Index amplification: an inverted index over logs costs ~1–2× the raw size on top of storage. → You only index the hot window; cold data is unindexed object storage.

Core Entities & API

Entities: LogEvent (timestamp, service, level, message, fields), Span (trace_id, span_id, parent_span_id, service, operation, start, duration, tags), Trace (a tree of spans sharing one trace_id).

EndpointPurpose
POST /v1/logsIngest a batch of log events. Hot path — cheap, async, never blocks the caller.
POST /v1/spansIngest a batch of spans (OTLP). Hot path; spans of one trace may arrive separately.
GET /v1/logs?q=&from=&to=Search logs by query expr over a time range; paginated results.
GET /v1/traces/:trace_idFetch and assemble all spans for one trace into a waterfall.
GET /v1/traces?service=&minDuration=&from=&to=Find traces matching criteria (slow, errored) for an entry point.

Tenant/team is derived from the agent's auth token, never a body field.

Data Flow — one event end to end

  1. Emit. The app writes a log line or a span to a local agent (sidecar/daemonset) over a local socket — non-blocking, in-process buffering.[3]
  2. Buffer. Agents batch and ship to a durable queue (Kafka), partitioned so spikes and a slow storage tier never back-pressure the app.
  3. Process. Stateless consumers parse, enrich (add service/host tags), apply sampling for traces, and route logs vs spans to their stores.
  4. Store. Logs go to an indexed hot store (Elasticsearch/columnar); spans go to a trace store keyed by trace_id. Both age into object storage as cold tiers.
  5. Query. The query service hits the hot index for recent data, or scans cold object storage for older ranges, then assembles traces from spans.

Deep Dives

1. The ingestion pipeline at petabyte scale

The non-negotiable rule: telemetry must never slow the application it observes. So the app only writes to a local agent over a fast local channel; everything else is asynchronous.[3] The agent batches and ships to Kafka, which is the load-bearing piece: it decouples a bursty 10 GB/s firehose from downstream storage, gives at-least-once durability, and lets you replay if a consumer or index falls over. Partition by service (or by trace_id for spans) so load spreads evenly and related data co-locates.

StageWhy it exists
Agent (local)Non-blocking capture; protects the app even if the backend is down.
Kafka bufferAbsorbs spikes, smooths writes, enables replay and back-pressure isolation.
Stateless processorsScale horizontally; parse/enrich/sample without holding state.
Why not write straight to storage? A direct write couples app latency to index health: one slow Elasticsearch shard would stall request threads across the fleet. The buffer turns a hard dependency into a soft one — exactly the pattern from the metrics ingestion firehose in Lesson 38.

2. Sampling — head vs tail (the cost lever)

Keeping every span is the single biggest cost. Sampling decides which traces to keep. The hard tradeoff is when you decide.[4]

Head samplingTail sampling
Decision pointAt trace start, before spans runAfter the full trace completes
CostCheap — drop early, never collectedExpensive — buffer all spans first
QualityRandom; may drop the rare error traceKeeps slow/errored traces by policy
StateStateless per serviceNeeds a collector holding spans by trace_id

Head sampling is a coin-flip at the root, propagated via the trace context so the whole trace is consistently kept or dropped — simple and cheap but blind to outcomes. Tail sampling buffers all spans of a trace in a collector, waits for completion, then keeps it only if it errored or was slow — far more useful for debugging, but it must hold spans in memory and route every span of a trace to the same collector.[4] Staff move: propose a hybrid — aggressive head sampling for the common case, tail-based keep-rules for errors and high latency, so you pay full price only for the traces worth keeping.

3. The distributed tracing model — context propagation & assembling a trace

A trace is a tree of spans. Each request gets one trace_id at the edge; every operation creates a span_id and records its parent_span_id. The magic is context propagation: when service A calls service B, it injects trace_id + parent span_id into the outbound request headers (the W3C traceparent header is the standard), and B reads them to attach its spans to the same tree.[3][5]

Assembling a trace on read. Spans are written independently, often out of order, by different services at different times. To view a trace you fetch all spans with that trace_id (hence trace_id is the storage key), then rebuild the tree by linking each span_id to its parent_span_id and sort by start time into a waterfall.[5] This is why the trace store is keyed and partitioned by trace_id — a single point lookup returns the whole request's spans together.

Clock skew across hosts means you display relative offsets within a trace, not absolute cross-host timestamps. A missing parent span (sampled out, or a service not instrumented) leaves a gap — render it as an orphan rather than failing the view.

4. Log storage, indexing, and hot/cold tiering

Search needs an index; petabytes can't all be indexed. So you split by age and access pattern.

ApproachStrengthCost
Inverted index (Elasticsearch)Fast full-text + field search~1–2× storage overhead; expensive at PB
Columnar (ClickHouse/Parquet)Cheap storage, fast field scans/aggregationsWeaker arbitrary full-text search
Object storage (S3)Cheapest durable bulk storeNo index — scan-on-demand only
Hot/cold tiering. Keep the recent window (hours–days) in an indexed hot store for second-level search; roll older data into columnar files on object storage with lightweight per-file metadata (time range, services) so queries skip irrelevant files. This is the same tiered-retention idea as the rollup tiers in the metrics TSDB and the downsampling in time-series databases — observability is fundamentally a time-partitioned, retention-tiered problem. Retention/cost tradeoff: shorter hot windows and lower sampling cut cost linearly; you tune them per signal and per team budget rather than treating "keep everything" as the default.
★ Staff-level signal Three things separate the staff answer: (1) you make sampling a first-class decision and can defend head vs tail vs hybrid by cost and debug value — not "keep everything"; (2) you treat cost and tiering as the architecture, indexing only the hot window and pushing the rest to columnar/object storage; (3) you explain context propagation and trace_id-keyed assembly precisely, including clock skew and orphan spans. Senior candidates wire up Elasticsearch; staff candidates decide what not to store and why.

Check yourself — retrieval practice

Answer from memory before scrolling back up.

1. What is the dominant constraint in a petabyte-scale observability system?

Raw volume (~25 PB/month) makes "keep and index everything" unaffordable, so sampling and tiering become core design decisions.

2. How does tail sampling differ from head sampling for traces?

Tail sampling buffers all spans, waits for completion, then keeps high-value traces (errors/latency) — costlier but smarter than a coin-flip at the root.

3. How are the spans of one request reassembled into a trace?

Spans share a trace_id (the storage key); the tree is rebuilt by linking span_id to parent_span_id and sorting by start time.

4. Why index only the recent window and tier older logs to object storage?

An inverted index roughly doubles storage cost; at PB scale you index only the hot window and scan cheap columnar/object cold tiers on demand.
