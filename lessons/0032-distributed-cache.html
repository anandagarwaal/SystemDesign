Design a Distributed Cache

Build Redis/Memcached at scale: a key-value store that lives in RAM across hundreds of nodes and answers in single-digit milliseconds.

Why this lesson, for your mission: A cache is the system every other system leans on, so this question really probes whether you understand partitioning and replication as first principles. The staff signal is owning the three pillars — consistent hashing to spread keys, an O(1) eviction structure inside a node, and an explicit consistency/availability tradeoff — without being told to.

Functional Requirements

This is a building-block question: you are designing the cache itself, not using one. Keep the surface tiny and get to the hard parts fast.[1]

#Requirement
1GET(key) returns the value, or a miss if absent or expired.
2PUT(key, value, ttl) stores a value with an optional time-to-live.
3The cache spans many nodes — data is partitioned across the cluster, not held on one machine.
4Entries are evicted when their TTL expires or the node hits its memory limit.

Out of scope (say so explicitly): durability to disk, strong consistency, secondary indexes / querying, and transactions.[1] Naming these is itself a signal — you know what a cache deliberately gives up.

Non-Functional Requirements

The "-ilities" are where a cache earns its keep. State a target for each.

NFRTarget & implication
Low latency<10ms p99 for GET and PUT.[1] Forces in-memory storage and at most one network hop to the right node.
High throughput~100k+ requests/sec.[1] No single coordinator on the hot path; clients reach nodes directly.
Horizontal scalabilityGrow to 1TB+ by adding nodes.[1] Adding a node must reshuffle only a small slice of keys.
AvailabilityA node loss must not take down the cache. Pushes us toward replication and eventual consistency.[1]
Tunable consistencyStaleness is tolerable — a cache is a copy of truth. We can pick eventual consistency to buy latency and availability.[1]

Capacity Estimation

Estimate only the numbers that shape the design.

  • Data: ~1TB total.[1] Average entry ~1KB (key + value + metadata) → ~1 billion keys.
  • Memory per node: a commodity box holds ~64GB usable for cache. 1TB / 64GB ≈ 16 nodes for data; round up for headroom and replicas.
  • QPS: 100k rps / 16 ≈ ~6k rps per node — trivial for an in-memory store (Redis does 100k+ on one core), so RAM size, not CPU, is the binding constraint.
  • Bandwidth: 100k × 1KB ≈ 100MB/s across the fleet — comfortable. Replication multiplies write traffic by the replica factor N.

The takeaway that drives the design: we need many nodes, so the entire problem becomes "how do we split keys across them and survive one dying?"

Core Entities & API

One entity — the Entry (key, value, expiresAt, lastAccessed) — and a tiny API. A cache speaks a binary protocol in practice, but the shape is REST-like:

EndpointPurpose
GET /v1/cache/:keyReturn value or 404/miss.
PUT /v1/cache/:keyBody {value, ttl}. Upsert with expiry.
DELETE /v1/cache/:keyRemove a key immediately.

No auth/user derivation here — a cache is an internal infra component called by trusted services, so we skip the token dance and spend the budget on the deep dives.

High-Level Design

Three logical pieces: the client/router that decides which node owns a key, a fleet of cache nodes each holding a partition in RAM, and a lightweight membership/coordination service tracking which nodes are alive.

ComponentRole
Smart client (or proxy)Hashes the key, looks up the owning node from the ring, sends the request directly — one hop.
Cache nodeIn-memory hashmap + eviction structure; serves GET/PUT/DELETE for its key range; replicates writes to followers.
Coordination servicee.g. ZooKeeper/etcd or a gossip protocol — holds the authoritative ring and membership, detects node failures via heartbeats.

Request flow: client hashes key → resolves owner node from the ring → node reads/writes its local map → on a PUT, the owner asynchronously copies to N−1 replicas → returns. The whole path is one network hop plus a memory lookup, which is how we keep p99 under 10ms.

Deep Dives

1 · Partitioning keys with consistent hashing

The naive approach is node = hash(key) % N. It works until N changes. Add or remove one node and nearly every key remaps to a different node, because the modulus shifts — the cache effectively flushes itself, and the cold cache stampedes the origin database. Unacceptable when nodes join and leave routinely.

Consistent hashing fixes this (see Lesson 05). Map both keys and nodes onto a circular hash ring (0…2³²−1). A key is owned by the first node clockwise from its position. When a node leaves, only the keys between it and its predecessor move — to a single neighbor — so on average just 1/N of keys reshuffle, not all of them.

Why virtual nodes (vnodes)?
  • With one ring position per node, the ring is lumpy — a few nodes own huge arcs and become hot, and removing a node dumps its entire load on one neighbor.
  • Give each physical node 100–200 virtual positions scattered around the ring. Load smooths out toward uniform, and a departing node's keys spread across many neighbors instead of crushing one.
  • Vnodes also let you weight heterogeneous hardware — a bigger box simply gets more vnodes.

2 · Eviction within a node — O(1) LRU

Each node has finite RAM, so when it fills up it must evict. The default policy is Least Recently Used.[1] The interview test is implementing LRU at O(1) for both lookup and recency update — naively scanning for the oldest entry would be O(n) and blow the latency budget (see Lesson 04).

The classic structure: hashmap + doubly linked list.
  • HashMap key → node gives O(1) lookup.
  • Doubly linked list orders entries by recency: most-recently-used at the head, least at the tail.
  • On GET/PUT: unlink the node and move it to the head — O(1) because the map hands you the node directly, no traversal.
  • On evict: drop the tail node and delete its key from the map — O(1).
PolicyWhen to prefer it
LRUDefault. Good for recency-skewed access (recent items likely re-read).
LFUKeep frequently used items even if not recent; better for stable popular keys. Costs a frequency counter per entry, often with a small min-heap or counter buckets.
TTL expiryOrthogonal to both. Lazy (check expiresAt on read) plus a background sweeper sampling random keys avoids scanning the whole keyspace.

3 · Replication & availability

If a node dies, its slice of the cache is gone — every key it owned now misses and hammers the origin. To survive a node loss, replicate each key to N nodes (commonly N=2 or 3): the owner plus the next N−1 nodes clockwise on the ring. When the owner fails, membership detects it via heartbeat and the next replica takes over reads.[1]

The async-replication staleness tradeoff.
  • Synchronous replication (write acked only after all replicas confirm) gives stronger consistency but adds a round trip — straight against our <10ms target.
  • Asynchronous replication acks the write immediately and copies to replicas in the background. Fast and available, but a reader hitting a lagging replica can see a stale value.
  • For a cache, async wins — staleness is acceptable[1] because the cache is just a copy of an authoritative store, and TTLs bound how long any staleness can last. This is the CAP/PACELC choice made concrete: we pick availability + low latency over strong consistency.

4 · The hot-key problem & locating the node

Consistent hashing spreads keys evenly, but it can't help one single wildly popular key (a celebrity's profile, a flash-sale item). All traffic for that key lands on one node and melts it, regardless of how balanced the ring is.

MitigationHow it helps
Replicate hot keysDetect high-traffic keys and copy them to extra nodes; clients fan reads across replicas, splitting the load.
Client-side cachingCache the hottest keys in the requesting service's local memory for a few seconds, so most reads never hit the cluster at all.
Key splittingFor a hot write counter, shard it as key#1…key#K across nodes and sum on read, removing the single contended owner.

How does a client find the right node? Two architectures:

  • Client-side hashing (smart client): the client library holds the ring and routes directly — zero extra hops, lowest latency. Cost: every client must learn ring changes (via the coordination service), and the logic lives in many languages.
  • Routing/proxy layer: a thin proxy (e.g. Twemproxy, Envoy) owns the ring; clients are dumb and just call the proxy. Simpler clients and centralized ring management, at the cost of one extra network hop and a component to scale. Memcached leans client-side; many managed Redis fleets put a proxy in front.
★ Staff-level signal Lead with consistent hashing + virtual nodes as the partitioning backbone and explain why plain modulo causes a full flush — that single insight separates senior from staff. Then show you can write the O(1) LRU (hashmap + doubly linked list) on the whiteboard, and name the async-replication staleness tradeoff as a deliberate CAP choice you're allowed to make because a cache tolerates staleness. Don't burn time re-explaining what a cache is — model the judgement, not the basics.

Check yourself — retrieval practice

Answer from memory before scrolling back up.

1. Why is hash(key) % N a poor way to partition keys across cache nodes?

A changed modulus shifts nearly all keys to new nodes, causing a mass miss and origin stampede. Consistent hashing moves only ~1/N.

2. What data structures give an O(1) LRU eviction inside a node?

The map gives O(1) lookup; the linked list lets you move-to-head and drop-the-tail in O(1) without any scan.

3. Why do virtual nodes improve a consistent-hashing ring?

Many ring positions per physical node even out arc sizes and stop one neighbor from absorbing all of a departed node's load.

4. Why is asynchronous replication an acceptable choice for a cache?

A cache mirrors an authoritative store and TTLs bound staleness, so we trade strong consistency for the latency and availability async buys.
