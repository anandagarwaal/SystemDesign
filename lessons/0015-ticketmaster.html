Design Ticketmaster

A read-heavy browsing system bolted onto a fiercely contended booking core — the whole interview turns on keeping those two paths apart.

Why this lesson, for your mission: Ticketmaster looks like a CRUD app until 10 million people hit "buy" on the same 50,000 seats at 10:00am sharp.[1] The staff signal is not "I know about locks" — it's framing booking as a contention and consistency problem, picking the simplest correct hold mechanism, and surgically isolating the strongly-consistent path from the availability-first browse path. That judgement is exactly what separates an L6/L7 hire from a senior one.

Functional Requirements

Lock scope to the three things a ticket buyer actually does. Push history, admin event creation, and dynamic pricing out of scope and say so.[1]

#Users should be able to…Note
1Search and view eventsRead path — by far the highest volume
2View available seats for an event (the seat map)Read path — must feel live during on-sale
3Book a seat: reserve → pay → confirmWrite path — the hard part; no double-booking

Non-Functional Requirements

One sentence carries the whole design: prioritize availability for searching and viewing, but prioritize consistency for booking — no double-booking.[1] Different NFRs for different paths is the framing move.

NFRTargetDrives
Strong consistency on bookingA seat is sold to exactly one buyer — everThe reservation/lock mechanism (Deep Dive 1). This is the crux.
High availability for browseSearch & event pages stay up under any loadCaching, read replicas, stateless services
Spiky-demand scalability10M concurrent on one hot on-saleVirtual waiting queue (Deep Dive 3)
Low search latency< 500msElasticsearch over LIKE scans (Deep Dive 4)
★ Staff-level signal Say out loud that you are deliberately running two consistency regimes in one system: AP (available, eventually consistent) for browse, CP (consistent, may reject) for booking. Naming that split — and refusing to let strong-consistency machinery leak onto the read path — is the single highest-leverage sentence in this interview.

Capacity Estimation

Only estimate the numbers that change a decision. Two facts matter here.

QuantityEstimateDesign implication
Read : write ratio~100 : 1 — browsing dwarfs booking[2]Optimize the read path independently; cache aggressively; the write path can be slower but must be correct.
Concurrency on a hot eventUp to ~10M users on a single on-sale[1]A single popular event is a hotspot. You cannot let 10M requests hit the booking DB; you must shed/serialize load at the door.

Inventory itself is tiny: a 50,000-seat venue is 50k rows. The challenge is never storage — it's concurrent contention on a small, hot set of rows.

Core Entities & API

Entities: Event (date, type, links to performer/venue), Venue (seat-map layout, capacity), Performer, Ticket (event id, seat coords, price, status: available | reserved | booked), and Booking (user id, ticket ids, total, status: in-progress | confirmed).[1] The status fields on Ticket and Booking are where the consistency story lives.

User identity comes from the auth token, never the body.

EndpointPurpose
GET /v1/events/search?keyword=&start=&end=&page=Search events — served by Elasticsearch.
GET /v1/events/{id}Event detail + venue + performer + seat map (ticket statuses).
POST /v1/bookingsReserve: body {eventId, ticketIds[]} → places a hold, returns bookingId.
POST /v1/bookings/{id}/confirmConfirm: finalizes after payment succeeds; idempotent.

Splitting reserve from confirm is intentional: the user gets a window to enter payment while the seat is held. That window is the entire reason the double-booking problem exists.

High-Level Design

An API Gateway (auth, routing, rate-limit) fans out to three stateless services. Browse and booking share no critical-path infrastructure.

ComponentRoleData store
Search ServiceServes /events/searchElasticsearch (kept in sync from the events DB via CDC)
Event ServiceServes /events/{id} + seat mapPostgres (read replicas) + Redis cache
Booking ServiceReserve / confirm; the only writer of ticket statusPostgres (primary) + Redis (reservation holds)
PaymentCharges card; signals successExternal (e.g. Stripe) via webhook

Flow. search → Search Service → Elasticsearch. GET event → Event Service → cache/replica. POST booking → Booking Service acquires a hold and writes a Booking(in-progress), returns bookingId; client goes to payment; on charge success the Payment webhook triggers confirm, which atomically flips Ticket → booked and Booking → confirmed.[1] Note the events DB is shared but only the Booking Service writes ticket status — the read services touch replicas and caches.

Deep Dive 1 — Preventing double-booking (the central problem)

The hazard: a user reaches the payment page, types their card, and the seat is gone — sold to someone faster.[1] You need a hold on the seat during the reserve→pay window, that auto-releases if payment never lands. Four mechanisms, escalating in quality:

MechanismHowWhy it fails / wins
DB row lock (SELECT … FOR UPDATE)Lock the ticket row for the whole 5–10 min checkoutBad. Holding a transaction open for minutes strains the DB and invites lock contention and deadlocks.[1] A lock is not a business-duration tool.
Status column + cron sweeperSet Ticket → reserved with a timestamp; a cron job resets expired ones to availableOK. Correct, no long locks — but a held seat stays "stuck" until the next sweep runs, hurting hot events. Correctness depends on the job.[1]
Status + expiry, checked inline (optimistic / OCC)One short transaction: claim the seat iff it is available OR (reserved AND expired), set reserved + now+10minGreat. No background job needed for correctness — an expired hold is implicitly free the instant the next buyer's transaction reads it. The sweep becomes optional cleanup; a delayed sweep changes nothing.[1]
Redis distributed lock + TTLSET ticket:{id} {userId} NX EX 600 — atomic, auto-expiring; release on payment successGreat, and the staff pick. Keeps the hot, short-lived hold state out of the durable DB entirely; the TTL is the expiry. Store userId as the value so only the reserver can confirm.[1]
The staff pick — and why. Redis lock with TTL is the recommended staff+ answer.[1] But the reasoning matters more than the choice:
  • The hold is ephemeral, so store it ephemerally. A 10-minute hold is not durable business data — putting it in Redis keeps churn off the primary DB.
  • The TTL is the expiry mechanism for free — no sweeper, no cron, no stuck seats. (See Deep Dive 2.)
  • Multi-seat bookings: acquire locks for all requested seats atomically via a Lua script — all-or-nothing, no partial holds.
  • Belt and suspenders: the final confirm still runs an OCC check in the DB transaction. So even a total Redis outage degrades the experience (more "seat taken" surprises) but cannot double-book.[1] Redis is an optimization on top of a DB that is itself correct.

The cost of Redis is read-path complexity: the Event Service must reflect held seats on the seat map. Resolve it with a per-event Redis Set of reserved seats, or write the reserved status through to the DB. State this tradeoff — interviewers probe it.[1] If you want a single-store answer with no second system, the inline-OCC status column (row 3) is a fully defensible "great" alternative, and is the expected answer at mid-level.

Deep Dive 2 — How a held seat gets released

Whatever holds a seat must release it when payment never arrives. The mechanisms differ sharply in how they handle the "nothing happens" case:

ApproachRelease triggerVerdict
Redis TTL keyThe key simply expires after N minutes — no code runsCleanest. Expiry is a property of the data, not a process.
Sweeper / cron jobPeriodic scan resets reserved rows past their timestampWorks, but introduces release lag = sweep interval; risky for hot events.
Delay queue (e.g. SQS delay / scheduled msg)A "release this hold" message fires N min after reservationPrecise per-hold timing, but adds a moving part and must be cancelled on confirm.
Inline lazy expiry (OCC)Next buyer's transaction treats an expired hold as availableZero release infrastructure; the seat frees the moment someone wants it.
★ Staff-level signal The insight to verbalize: prefer expiry that requires no process to run. A TTL key or a lazy inline check has nothing to "miss" — there is no job whose failure leaves seats stuck. A sweeper is a background process you now have to monitor, alert on, and reason about during incidents. Choosing the mechanism with the fewest failure modes is the senior-to-staff jump.

Deep Dive 3 — The on-sale thundering herd

When a Taylor-Swift-tier event opens, 10M users arrive in seconds. Pushing live seat updates via Server-Sent Events helps the seat map feel fresh, but it doesn't help when 50k seats vanish in moments and millions are hammering the booking path anyway.[1]

Virtual waiting queue (staff pick). Put a queue in front of the Booking Service.[1]
  • On requesting the booking page, the user is enqueued in a Redis sorted set keyed by arrival timestamp (fair ordering).
  • A persistent connection (SSE) shows the user their position and ETA — turning a failure into a waiting-room experience.
  • The system dequeues at a controlled rate, writing admitted users to a Redis "admitted" set with a TTL.
  • The Booking Service checks the admitted set before allowing any reservation — so the booking core only ever sees a trickle it can handle.

This is the cleanest expression of the load-shedding principle: don't scale the contended core to 10M — serialize admission and protect it. The queue converts an unbounded spike into a bounded, paced stream.

Deep Dive 4 — Search

Sub-500ms search over event names, performers, and dates. The progression:

OptionVerdict
DB B-tree indexesFine for exact/prefix, but LIKE '%taylor%' can't use them — full scans are slow.[1]
Postgres full-text (tsvector + GIN)Good for token search without a second system; weaker on fuzzy matching, harder to tune.[1]
Elasticsearch (recommended)Inverted index → very fast token lookup; fuzzy search tolerates typos ("Tayler Swift"). Sync from Postgres via CDC so the index stays current.[1]

The honest tradeoff: Elasticsearch is a second store you must keep in sync, so name CDC (and accept eventual consistency on search — which is fine, since browse is the AP path). For caching, lean on Elasticsearch's own shard/request caches plus a CDN edge cache for non-personalized result pages.[1]

Deep Dive 5 — Scaling the seat-map reads

Event pages get hammered the instant tickets go on sale.[1] Because this is the AP path, scale it the boring, reliable way and keep it entirely off the booking primary:

  • Cache the static parts — event details, venue layout, performer bios — in Redis/Memcached under eventId:event with long TTLs; invalidate via DB triggers on change.[1]
  • Read replicas for the dynamic seat statuses, so browse load never touches the write primary.
  • Stateless Event Service behind a load balancer — scale horizontally, route by least-connections.[1]
  • SSE for live updates during a hot on-sale so clients see seats go grey without polling.[1]

The point of this dive is restraint: the read path needs no exotic machinery. All the cleverness belongs in the booking core. Spending equal time on both signals poor prioritization.

Check yourself — retrieval practice

Answer from memory before scrolling back up.

1. Why is holding SELECT … FOR UPDATE for the whole checkout the worst option?

A lock is not a business-duration tool — keeping a transaction open for the checkout window invites contention and deadlocks.

2. Why is a Redis TTL key the cleanest seat-release mechanism?

A TTL key just expires — there is no sweeper job whose failure could leave seats stuck.

3. What does the virtual waiting queue fundamentally do for the booking core?

It serializes and rate-limits admission so the contended core only ever sees load it can handle.

4. What is the load-bearing framing sentence for this whole design?

Two consistency regimes in one system: AP for browse, CP for booking. Everything downstream follows from that split.
