Capacity Estimation Cheat Sheet

The back-of-envelope numbers and one-line formulas for the math you do out loud in an interview. Memorize the bold rows.

The point of estimation: not precision — it's to decide the design. Do the math only when a number changes an answer ("does this fit on one machine?", "do I need a cache/CDN/shards?"). Round aggressively, use powers of 10, and state assumptions out loud.

Powers of 2 → data sizes

Power≈ ValueName
2^10~1 Thousand1 KB
2^20~1 Million1 MB
2^30~1 Billion1 GB
2^40~1 Trillion1 TB
2^50~1 Quadrillion1 PB

ASCII char = 1 byte; typical UUID = 16 B; a "row" of metadata ≈ 0.1–1 KB; a typed message/tweet ≈ 100–300 B; a web page ≈ 100 KB–1 MB; a photo ≈ 200 KB–2 MB; a minute of HD video ≈ 50 MB.

Time → seconds (for QPS math)

WindowSecondsMemorize
1 day86,400~10^5 (100k)
1 month2.6 million~2.5 × 10^6
1 year31.5 million~3 × 10^7
The one QPS shortcut everyone uses: 1 million requests/day ≈ 12 QPS (since a day ≈ 86,400 s ≈ 10^5). So 1 billion/day ≈ 12,000 QPS. Scale linearly from there.

Latency numbers every engineer should know

Order-of-magnitude (Jeff Dean's classic list, rounded). Know the relative gaps, not exact ns.

Operation≈ Latency
L1 cache reference~1 ns
Branch mispredict~3 ns
L2 cache reference~4 ns
Mutex lock/unlock~17 ns
Main memory (RAM) reference~100 ns
Compress 1 KB (Zippy/Snappy)~2 µs
Read 1 MB sequentially from RAM~10–250 µs
SSD random read~16–100 µs
Round trip within same datacenter~500 µs
Read 1 MB sequentially from SSD~1 ms
Disk (HDD) seek~3–10 ms
Read 1 MB sequentially from disk~20–30 ms
Round trip CA ↔ Netherlands~150 ms
The three takeaways that win arguments: (1) memory is ~100× faster than SSD, SSD ~10–100× faster than disk → cache hot data. (2) A cross-continent round trip (~150 ms) dwarfs everything → put data/CDN near users, minimize round trips. (3) Sequential ≫ random on every medium → why LSM-trees, logs, and batching win.

Availability — the "nines"

AvailabilityDowntime / yearDowntime / day
99% (two nines)3.65 days14.4 min
99.9% (three nines)8.76 hours86 s
99.99% (four nines)52.6 min8.6 s
99.999% (five nines)5.26 min0.86 s

Availability multiplies across hard dependencies: two 99.9% services in series ≈ 99.8%. Redundancy (parallel paths) adds nines; serial dependencies subtract them.

Single-machine rules of thumb

ResourceRough ceiling on one modern box
RAM~64–512 GB (so a dataset under ~100 GB may fit in memory)
QPS — simple app server~1k–10k QPS
QPS — Redis / in-memory~100k+ ops/s
QPS — single SQL primary (writes)~1k–10k writes/s (the usual first bottleneck)
Persistent connections (tuned)~10k–100k+ per node (C10K/C10M)
Network~10–25 Gbps NIC

Use these to trigger decisions: writes > ~10k/s → shard or switch to an LSM store; dataset > one box's RAM → cache tier + sharding; reads ≫ writes → replicas + cache; global users → CDN + multi-region.

The estimation workflow (say this out loud)

  1. Traffic: DAU × actions/user/day → requests/day → ÷ 10^5 → average QPS. Then peak ≈ 2–10× average.
  2. Read:write ratio: state it (e.g. 100:1 for a feed) — it decides caching/replication.
  3. Storage: writes/day × bytes/write × retention (years × ~3×10^7 s if per-second). Add replication factor (×3).
  4. Bandwidth: QPS × payload size, both ingress and egress (egress often dominates for media).
  5. Memory (cache): apply the 80/20 rule — cache the hot ~20% of data; size = hot set × object size.

Worked micro-example

Twitter-like feed, 200M DAU, each posts 2× and reads 100×/day. Writes = 400M/day ≈ ~4.6k QPS (peak ~10–46k). Reads = 20B/day ≈ ~230k QPS → read-heavy → cache + fan-out + replicas. Tweet ≈ 300 B → 400M × 300 B ≈ 120 GB/day raw; ×3 replication ≈ 360 GB/day → multi-TB/year → shard it. The numbers told us the architecture.

Interview tell: don't compute for its own sake. Estimate, then immediately say what the number decides: "~230k read QPS, so a single DB can't serve reads — I'll add a cache and read replicas." That conversion of math → design choice is the whole point at L6/L7.
