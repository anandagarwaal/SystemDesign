System Design · Reference

Decision Guides

The "which one do I reach for?" cheat sheets — datastore selection, messaging selection, and a map of which patterns each case study exercises. Use them to justify choices out loud with tradeoffs, not vibes.

How to use in an interview: never say "I'll use X" — say "the requirement is Y, which means I need property Z, so X fits and here's the tradeoff I'm accepting." These trees encode the Y→Z→X chain.

1 · Which datastore?

Is the data a hot, ephemeral, sub-ms working set (cache, session, rate-limit counter, leaderboard)?

→ Redis (in-memory; sorted sets, TTL). See L93.

Do you need full-text / fuzzy search, ranking, or faceted filtering?

→ Elasticsearch (inverted index) alongside your source of truth. See L94.

Is it heavy analytical aggregation over huge columns (OLAP, dashboards, ad/metrics rollups)?

→ ClickHouse / columnar OLAP. See L95.

Is it append-heavy, time-stamped metrics/events with time-range queries?

→ Time-series DB. See L42.

Highly connected data with multi-hop traversals (social graph, fraud rings, recommendations)?

→ Graph DB (Neo4j). See L98.

Do you need strong multi-row ACID transactions + rich queries/joins (payments, orders, ledger)?

→ Relational (PostgreSQL/MySQL); if it must scale writes globally with strong consistency → distributed SQL (Spanner/CockroachDB) or Aurora. See L88, L96.

Massive write throughput, simple access by key, availability > strong consistency, easy horizontal scale?

→ Wide-column / KV (Cassandra, DynamoDB) — design around the query/partition key. See L90, L91.

Flexible/evolving documents, nested objects, single-document atomicity?

→ MongoDB (document). See L92.

Large immutable objects (images, video, backups, files)?

→ Blob store (S3) + CDN; keep metadata in a DB. See L45.

Default & escalate: start with PostgreSQL — it does KV, JSON, full-text, and geo "well enough" to ship. Only introduce a specialized store when a concrete requirement (scale, access pattern, latency) forces it. Adding stores adds operational + consistency cost; say that.

2 · SQL vs NoSQL — the honest table

DimensionRelational (SQL)NoSQL (KV / wide-col / doc)
Best whenRelationships, transactions, ad-hoc queriesKnown access pattern, massive scale, high write rate
ConsistencyStrong ACID by defaultOften tunable / eventual (AP-leaning)
Scaling writesVertical first; sharding is manual & painfulHorizontal by design (partition key)
JoinsYesAvoid — denormalize / duplicate
SchemaFixed, migrationsFlexible
Failure modeWrite primary is the bottleneckHot partitions / skew; eventual-read surprises

Modern reality: the line is blurry (Postgres scales far; DynamoDB has transactions). Choose on access pattern + scale + consistency need, not the label.

3 · Which messaging system?

Do you need a durable, replayable, ordered log for streams / event sourcing / many consumers / high throughput?

→ Kafka (partitioned log, consumer groups, replay). See L99.

Do you need flexible per-message routing, priorities, and classic task-queue semantics with ack/retry?

→ RabbitMQ (AMQP broker). See L100.

Want zero-ops managed decoupling on AWS, simple work queue?

→ SQS (+ SNS for fan-out pub/sub). See L100, L119.

Just need lightweight in-process / cache-adjacent pub/sub, fire-and-forget?

→ Redis Pub/Sub or Streams (no strong durability for plain pub/sub).

Stateful stream processing with event-time windows & exactly-once?

→ Kafka as transport + Flink (or Spark Streaming) for compute. See L102.
